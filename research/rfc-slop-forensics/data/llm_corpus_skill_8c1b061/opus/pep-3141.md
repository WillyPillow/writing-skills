Title: A Type Hierarchy for Numbers
Status: Draft
Type: Standards Track
Requires: 3119

# Abstract

This PEP defines a hierarchy of Abstract Base Classes (ABCs, PEP 3119) for classes that behave like numbers. The hierarchy is `Number :> Complex :> Real :> Rational :> Integral`, where `A :> B` means "A is a supertype of B". Its shape follows Scheme's numeric tower [#schemetower]_.

# Motivation

A function that accepts numbers cannot currently ask what kind of number it was given, except by testing for concrete types. Consider a function that computes a binomial coefficient and must reject non-integers:

    def choose(n, k):
        if not isinstance(n, (int, long)):
            raise TypeError("n must be an integer")
        ...

This test rejects an integer type from a third-party library, such as an arbitrary-precision integer wrapper, even when that type supports every operation `choose` uses. The author of the wrapper cannot fix this, because `isinstance` only knows the classes listed. The function author cannot fix it either without knowing every integer type in advance.

PEP 3119 gives Python a way to state such requirements as abstract classes that other types can register with. This PEP applies that mechanism to numbers. With it, the test above becomes `isinstance(n, Integral)`, and a third-party integer type passes it by registering with `Integral` or inheriting from it.

The same need appears wherever code depends on the algebraic properties of its inputs: whether values can be ordered, whether `/` is exact, whether a value has a real and an imaginary part. # Specification

The module `numbers` defines five ABCs. Each ABC lists the operations a conforming class must provide. Each level adds operations to the level above it; none removes any.

## Number

`Number` is the root. It declares no operations. Its purpose is to let code ask "is this a number at all?", for example to decide whether `x` should be formatted as a number or passed to `repr()`. A class can be a `Number` without fitting any lower level. [TODO: give an example of such a class, if the author has one in mind.]

## Complex

`Complex` describes values that support the field operations of the complex numbers. A subclass of `Complex` must implement:

1. `__add__`, `__radd__`, `__sub__`, `__rsub__`, `__mul__`, `__rmul__`, `__truediv__`, `__rtruediv__`, `__pow__` and `__rpow__`.
2. `__neg__`, `__pos__` and `__abs__`, where `abs()` returns a `Real`.
3. `__eq__` and `__ne__`. `Complex` does not define ordering, since the complex numbers have no ordering compatible with their arithmetic.
4. The properties `real` and `imag`, each returning a `Real`, and the method `conjugate()`.
5. `__complex__`, which converts the value to the builtin `complex`.

The builtin `complex` is registered as a `Complex`.

## Real

`Real` adds what holds for the real numbers but not for the complex ones: a total order and the operations that depend on it. A subclass of `Real` must implement, in addition:

1. `__lt__` and `__le__` (and, through the usual reflection, `>` and `>=`).
2. `__float__`.
3. `__trunc__`, `__floor__`, `__ceil__` and `__round__`, each returning an `Integral` when called with no precision argument.
4. `__divmod__`, `__floordiv__` and `__mod__`, with their reflected forms.

`Real` provides default implementations of the `Complex` members that are trivial for a real value: `real` returns the value itself, `imag` returns `0`, `conjugate()` returns the value, and `__complex__` returns `complex(float(self))`.

The builtin `float` is registered as a `Real`.

## Rational

`Rational` adds an exact representation as a ratio of integers. A subclass must provide the properties `numerator` and `denominator`, each an `Integral`, with the denominator positive and the fraction in lowest terms. [TODO: confirm that lowest terms is required. Requiring it lets two equal rationals be compared by their components, but it forces every implementation to normalize after each operation.]

`Rational` provides a default `__float__` that divides the numerator by the denominator.

## Integral

`Integral` adds the operations that only make sense for integers. A subclass must implement, in addition:

1. `__index__` (PEP 357), so that integral values can be used as sequence indices.
2. The bitwise operations `<<`, `>>`, `&`, `^`, `|` and `~`, with their reflected forms, defined as on two's-complement integers of unbounded width.
3. A three-argument `__pow__(base, exp, mod)`.

`Integral` provides defaults for the `Rational` members: `numerator` returns the value and `denominator` returns `1`.

The builtin `int` is registered as an `Integral`.

# Implementing arithmetic across types

The ABCs say what operations exist, but not how a type should behave when its operand is a different numeric type. Without a convention, the hierarchy invites a specific failure. Suppose `MyRational` and `YourRational` are both registered as `Rational` and neither knows about the other. `MyRational(1, 2) + YourRational(1, 3)` should still produce a correct value, because both sides expose `numerator` and `denominator`.

This PEP recommends the following pattern for `__add__` and its relatives. In a binary method of class `A`, with operand `b`:

1. If `b` is an instance of a type `A` knows how to combine with exactly, compute the result directly.
2. Otherwise, return `NotImplemented`, so that Python tries `b.__radd__`.

In the reflected method `__radd__` of class `B`, with operand `a`:

1. If `a` is a type `B` knows, compute the result directly.
2. Otherwise, if both operands are `Rational`, compute the result from their numerators and denominators.
3. Otherwise, if both are `Real`, convert both to `float`; if both are `Complex`, convert both to `complex`.
4. Otherwise, return `NotImplemented`.

The order of steps 2 and 3 means that two unrelated exact types combine exactly, and that precision is lost only when one operand is inexact. The cost is that every numeric class must write this ladder by hand. # Rationale

## Why a hierarchy follows Scheme's tower

Each level of the tower is a subset, in the mathematical sense, of the level above: every integer is rational, every rational is real, every real is complex. Making each ABC a subclass of the one above means that `isinstance(x, Real)` is true for every `Integral`, which matches what a reader of `isinstance(x, Real)` expects. Scheme's numeric tower [#schemetower]_ uses the same inclusion chain, so the shape is familiar to people who have used Scheme. ## Exactness

Scheme also marks each number as exact or inexact, independently of its level in the tower. An inexact rational and an exact one are both rationals in Scheme. This PEP does not include that distinction. [TODO: record whether an `Exact`/`Inexact` axis was considered and why it was left out. One possible reason, to be confirmed: `float` is the only common inexact type, and adding a second axis would double the number of ABCs a class must choose between.]

As a consequence, `float` is registered as `Real` but not as `Rational`, even though every finite float is a ratio of integers. Registering it as `Rational` would let a function that requires exact arithmetic accept a value that carries rounding error.

## Why ABCs rather than requiring inheritance

Registration under PEP 3119 lets existing types, including `int`, `float` and types from extension modules, join the hierarchy without changing their base classes. A design that required inheritance would exclude any type whose author does not update it, which is the problem the motivation describes. The cost is that registration is a promise the ABC cannot check: a class registered as `Integral` that lacks `__index__` will fail only when something calls it.
