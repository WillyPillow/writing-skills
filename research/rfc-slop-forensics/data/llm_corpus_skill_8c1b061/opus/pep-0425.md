# PEP 425: Compatibility tags for built distributions

## Abstract

This PEP specifies a set of tags that say which versions of Python a built, or binary, distribution is compatible with. Three tags say which Python implementation and language version, which ABI, and which platform the distribution requires. The tags are short, because they are part of distribution filenames.

## Motivation

A source distribution can be built on the machine where it is installed, so it does not need to say where it runs. A built distribution has already been compiled. It may contain bytecode for a specific Python version, extension modules linked against a specific C API, or machine code for one operating system and processor. An installer that picks a built distribution has to know whether it will work on the target interpreter before downloading and unpacking it.

The information has to be readable from the filename. An installer searching a package index sees a list of filenames, and fetching the metadata for each candidate would mean downloading each one. ## Overview

A built distribution's filename ends with three tags, joined by hyphens:

```
{python tag}-{abi tag}-{platform tag}
```

For example, `example-1.0-cp33-cp33m-linux_x86_64.whl` requires CPython 3.3, the `cp33m` ABI, and Linux on x86-64.

## The three tags

### Python tag

The Python tag names the implementation and the language version. It is an abbreviation of the implementation followed by the version with the dot removed:

| Abbreviation | Implementation  |
|--------------|-----------------|
| `py`         | Generic Python  |
| `cp`         | CPython         |
| `ip`         | IronPython      |
| `pp`         | PyPy            |
| `jy`         | Jython          |

`cp33` means CPython 3.3. `py3` means any Python 3 implementation, and `py27` means any implementation of the Python 2.7 language. A pure-Python distribution that uses no implementation-specific features uses a `py` tag.

### ABI tag

The ABI tag names the binary interface that extension modules in the distribution are compiled against. For CPython, this is `cp` followed by the version and by the build flags that change the ABI, such as `m` for pymalloc and `d` for debug builds. ### Platform tag

The platform tag is the value of `distutils.util.get_platform()` with every hyphen and period replaced by an underscore. On 64-bit Linux this gives `linux_x86_64`. On 32-bit Windows it gives `win32`. A distribution that runs on any platform uses `any`.

The replacements keep the tag free of the characters used as separators in the filename. [TODO: confirm the macOS platform string format, which includes a minimum OS version, and how compatibility across macOS versions is decided.]

## Compressed tag sets

A distribution may work with more than one value of a tag. A pure-Python package may support both Python 2 and Python 3. To avoid publishing identical files under several names, any tag may contain several values separated by periods:

```
example-1.0-py2.py3-none-any.whl
```

This file is compatible with any Python 2 or Python 3 interpreter, with no ABI requirement, on any platform. An installer expands a compressed tag set into the cross product of its values, and treats the file as compatible if any combination is supported.

The period is the separator because it cannot appear in a tag after the platform replacement rule above. [TODO: confirm that no Python tag or ABI tag contains a period.]

## Use by installers

### Supported tags

An installer builds a list of the tag triples that the running interpreter supports, ordered from most preferred to least. For CPython 3.3 on 64-bit Linux, the list starts:

1. `cp33-cp33m-linux_x86_64`
2. `cp33-abi3-linux_x86_64` [TODO: if `abi3` is in scope]
3. `cp33-none-linux_x86_64`
4. `py33-none-linux_x86_64`
5. `py33-none-any`
6. `py3-none-any`

The order puts the most specific match first. A distribution built for this exact interpreter is assumed to be better than a generic one, because a generic distribution of a package with optional extension modules is often the pure-Python fallback.

### Choosing a file

Given several built distributions of one release, the installer picks the one whose tags appear earliest in its supported list. If no file matches, it falls back to the source distribution.

An installer may let the user override the supported list, for example to download distributions for another machine. [TODO: decide whether this PEP specifies a format for such overrides.]

## What the tags do not say

The tags say nothing about dependencies on libraries outside Python. A `linux_x86_64` distribution may be linked against a C library version that the target system lacks. The platform tag only says that the operating system and processor match. [TODO: decide whether this limitation is accepted for now, and whether a later PEP should address it.]

The tags also do not say which Python micro versions are excluded, or which features of a minor version are required. A distribution author who needs such a constraint has to state it in the distribution's metadata, outside the filename.

## Rationale

The tags are terse because filenames are limited in length on some systems and are read by people as well as tools. A three-part tag of a few characters each keeps the full filename short enough to read in a directory listing. [TODO: give any specific filename length limit that influenced the design.]
