# PEP 504: Using the system RNG by default

## Abstract

The module-level functions of the `random` module, such as `random.random()`, `random.choice()` and `random.randint()`, draw from a deterministic Mersenne Twister generator. Users doing security-sensitive work are expected to know that they should instead use `os.urandom`, `random.SystemRandom`, or a third-party library such as `cryptography`. This PEP proposes that the module-level functions use the system random number generator by default, so that code written without that knowledge is no longer exposed by it. Code that needs a reproducible sequence keeps one by seeding the generator explicitly.

## Background

The `random` module offers two kinds of generator. The default is a Mersenne Twister instance shared by the module-level functions. It is fast and its output can be reproduced from a seed, which is what simulations, tests and games need. `random.SystemRandom` reads from the operating system's cryptographically secure source, the same one `os.urandom` uses. It cannot be seeded, and an observer who sees part of its output cannot predict the rest.

The Mersenne Twister is not suitable for secrets, because its internal state can be recovered from a sufficient number of consecutive outputs, after which every later output is predictable. [TODO: citation for the state-recovery result, and the number of outputs it needs.]

## The problem

The current design asks every developer to classify their own code as security-sensitive or not, and to pick the right API on that basis. Developers who do not recognise that they are doing security-sensitive work use the module-level functions, because those are the documented, shortest path. Typical cases are generating password reset tokens, session identifiers or temporary passwords. The problem is chronic rather than acute. No single bug of this kind is likely to be catastrophic across the ecosystem, but the pattern recurs. Experience does not correct it well, because a weak token is usually exploited long after it is written, if it is ever exploited at all. The developer who wrote it rarely learns that it was a mistake, so the next project repeats it.

## Goals

- Code that calls the module-level functions of `random` without seeding them receives output from the system random number generator.
- Code that seeds the module-level generator and depends on a reproducible sequence produces the same sequence as before.
- A developer who needs the deterministic generator for performance can still use it, by an explicit and documented call.

## Proposal

### Default generator

The module-level functions delegate to a module-level generator object. This PEP changes that object to an instance of `random.SystemRandom` when the module is first imported.

### Seeding

Today, `random.seed(n)` followed by calls to the module-level functions produces a sequence that is the same on every run. Simulations, test suites and procedural generators depend on this property, and `SystemRandom` cannot provide it, because it ignores seeds.

This PEP proposes that a call to `random.seed()`, `random.setstate()` or `random.getstate()` switches the module-level functions to a Mersenne Twister instance. After the switch, the module behaves exactly as it does today. Code that seeds before it draws therefore sees no change.

## Rationale

The proposal changes the default rather than adding another warning, because the affected developers are the ones who do not read warnings that they do not think apply to them. A safe default protects them without any action on their part. A developer who needs the deterministic generator already knows that they need it, because reproducibility is a property they rely on, and they can opt into it.

## Costs and drawbacks

### Performance

Reading from the operating system's generator involves a system call and costs more per value than computing the next Mersenne Twister output. Code that calls the module-level functions in a tight loop without seeding will run slower. [TODO: benchmark numbers for `random.random()` under both generators on the main platforms. ### Availability

The system generator depends on the operating system. On some platforms, reading from it early in boot may block until the kernel has gathered enough entropy, which can delay programs started by init systems. ### Changed guarantees

Programs that never seed, but whose tests depend on the module-level functions' current behaviour in other ways, may notice the change. For example, a test that patches the module-level generator object, or that pickles its state with `getstate()`, will now trigger the switch to the deterministic generator at a different point. ## Backwards compatibility

Under the seeding rule above, programs that seed before drawing produce the same output as before. Programs that do not seed get different numbers, but no program could rely on those numbers, since the current default seed comes from the system time or from the operating system. ## Security implications

This PEP reduces the harm from one common misuse of the `random` module. It does not make code that seeds the module-level generator safe, and a program that seeds with a predictable value and then generates secrets remains as weak as it is today. The documentation must continue to say that the module-level functions are not the right interface for secrets, even with the new default, because any code that calls `seed()` anywhere in the same process changes what they return.
