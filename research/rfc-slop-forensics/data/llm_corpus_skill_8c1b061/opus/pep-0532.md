# PEP 532: A circuit breaking protocol and binary operators

## Abstract

Python has three expressions that decide whether to evaluate an operand based on the truth value of another: the conditional expression `LHS if COND else RHS`, `LHS and RHS`, and `LHS or RHS`. All three call `bool()` on one value and then either return a value or evaluate a second one. None of them lets the type of the tested value influence what is returned. PEP 335, PEP 505 and PEP 531 each proposed a way to change some part of that behaviour, and PEP 535 proposes a rich comparison chaining model that needs the same hook.

This PEP proposes one protocol for all of these cases. A type can define `__then__` and `__else__`, which are called on the branch taken after the truth test. An object whose type defines them is called a circuit breaker. The existing conditional expression, `and` and `or` are redefined in terms of the protocol, with defaults that keep their current results. The PEP 505 None-aware operators and the PEP 535 comparison chains can then be specified as uses of the protocol rather than as separate special cases.

With the protocol in place, this PEP also proposes that `if` and `else` become usable on their own as binary short-circuiting operators:

- `LHS if RHS`, which is right-associative;
- `LHS else RHS`, which is left-associative.

Finally, it proposes a change to logical inversion (`not EXPR`) so that inverting a circuit breaker is consistent with the operators above. [TODO: the details of the `not` change; see "Logical inversion" below.]

## The protocol

### Evaluation of the conditional expression

Under this proposal, `LHS if COND else RHS` evaluates as follows:

1. Evaluate `COND` once, and call the result `cb`.
2. Call `bool(cb)`.
3. If the result is true, evaluate `LHS` and return `type(cb).__then__(cb, LHS)`.
4. Otherwise, evaluate `RHS` and return `type(cb).__else__(cb, RHS)`.

As today, only one of `LHS` and `RHS` is evaluated. The protocol changes what is returned on each branch, not which operand is evaluated.

When `type(cb)` defines neither method, the interpreter behaves as if `__then__` and `__else__` each returned their second argument. The result is then the same as the current conditional expression. ### `and` and `or` in terms of the protocol

Both boolean operators can be written as conditional expressions in which the tested value appears twice but is evaluated once:

- `LHS and RHS` is `RHS if LHS else LHS`;
- `LHS or RHS` is `LHS if LHS else RHS`.

Under the protocol, `cb` is the value of `LHS` in both cases. For `and`, a false `cb` returns `type(cb).__else__(cb, cb)`, and a true `cb` returns `type(cb).__then__(cb, RHS)`. For `or`, a true `cb` returns `type(cb).__then__(cb, cb)`, and a false `cb` returns `type(cb).__else__(cb, RHS)`. With the default methods, both operators return exactly what they return today.

Defining all three expressions through one protocol is the main point of the proposal. A type author who wants to customise short-circuiting implements two methods, and the change is visible consistently in conditional expressions, `and`, `or`, and the new binary operators.

### The new binary operators

Once `if` and `else` dispatch through the circuit breaker, each keyword is useful on its own. This PEP proposes two new expressions:

- `LHS if RHS` evaluates `RHS` first as `cb`. If `cb` is true, it evaluates `LHS` and returns `type(cb).__then__(cb, LHS)`. Otherwise it returns `type(cb).__else__(cb, cb)`. For an object that is not a circuit breaker, it gives the same result as `RHS and LHS`.
- `LHS else RHS` evaluates `LHS` first as `cb`. If `cb` is true, it returns `type(cb).__then__(cb, cb)`. Otherwise, it evaluates `RHS` and returns `type(cb).__else__(cb, RHS)`. For an object that is not a circuit breaker, it gives the same result as `LHS or RHS`.

For ordinary objects, the binary forms add only a second spelling of `and` and `or`. They become useful with circuit breakers that unwrap a value. Consider a circuit breaker type, called `exists` here for illustration, that wraps a value, is true when that value is not `None`, and has `__then__` and `__else__` return the wrapped value when given the breaker itself. Then

```python
name = exists(user_name) else "anonymous"
```

returns `user_name` when it is not `None`, and `"anonymous"` otherwise. This is the behaviour PEP 505 proposes for its None-coalescing operator. Similarly,

```python
city = user.address.city if exists(user)
```

returns `None` when `user` is `None`, and evaluates the attribute chain otherwise.

### Associativity and precedence

`LHS else RHS` is left-associative, so `a else b else c` means `(a else b) else c`. This form reads as "the first of these that passes the test", with each operand tested in turn from left to right.

`LHS if RHS` is right-associative, so `a if b if c` means `a if (b if c)`. Read from the right, the innermost condition is tested first, and each further condition is tested only if the one to its right passed.

The existing ternary form must continue to parse as it does today. `LHS if COND else RHS` therefore needs a grammar rule that treats it as a single expression, rather than as `(LHS if COND) else RHS`. Under the protocol, the two parses do not give the same result. With `(LHS if COND) else RHS`, a false `LHS` would lead to evaluation of `RHS` even when `COND` was true.

## Logical inversion

For a circuit breaker to be useful in both directions, `not` must be able to invert it without losing the wrapped value. Otherwise `exists(x)` could be negated only by turning it into a plain `bool`, and its `__then__` and `__else__` methods would no longer be called.

## Rationale

The case for a single protocol rests on the number of proposals it serves. Without it, PEP 505, PEP 531 and PEP 535 would each add their own special-case semantics to the evaluator, and the boolean operators would remain the only operators in the language that a type cannot customise. With it, the evaluator gains one mechanism, and each of those proposals reduces to a type definition, a spelling, or both.

## Objections

A reader is likely to raise three objections.

The first is readability. `LHS if RHS` evaluates its right operand first, which reverses the left-to-right reading order of most Python expressions. ## Backwards compatibility

The default behaviour of `__then__` and `__else__` is chosen so that conditional expressions, `and` and `or` return the same values as before for every type that does not define the new methods.
