# Abstract

This PEP changes how Python writes integers in radixes other than ten, in source code and in strings. The changes target Python 3.0. The parts that do not break existing code are also added to Python 2.6, so that every integer literal valid in 3.0 is also valid in 2.6.

The proposal has three parts:

1. Octal literals are written with a leading `0o` or `0O`, instead of a leading `0`.
2. Binary literals are added, with a leading `0b` or `0B`.
3. String formatting gains a way to write a number in binary.

# Motivation

Python 2 inherits its octal syntax from C. A literal that starts with `0` and has more digits is octal:

```python
>>> 0755
493
>>> 010
8
```

The rule is a frequent surprise for readers who do not know C. In everyday writing a leading zero carries no meaning, so `010` reads as ten. A user who pads numbers with zeros to line them up, for example in a table of dates or codes, gets a different value, or a `SyntaxError` if a digit is 8 or 9:

```python
>>> months = [01, 02, 08, 09]
SyntaxError: invalid token
```

The same rule applies when a string is parsed with `int(s, 0)`, which takes the radix from the prefix, so programs that read numbers from configuration files or user input inherit the same trap.

Hexadecimal has a clearly marked prefix, `0x`. Octal does not, and binary has no literal form at all. A program that works with bit masks, such as flags for hardware registers or file permissions, must write them in hexadecimal or compute them, and must convert to binary by hand to display them. # Specification

## Octal literals

An octal literal is `0o` or `0O` followed by one or more octal digits:

```python
>>> 0o755
493
```

In Python 3.0, a decimal literal with a leading zero followed by more digits is a `SyntaxError`. The literal `0`, and literals made only of zeros such as `00`, remain valid and mean zero.

The old form becomes an error in 3.0, rather than being read as decimal. Reading `0755` as decimal would give existing code a different number without any message. Code that sets file permissions with `os.chmod(path, 0755)` would set the mode to 755 decimal, which is 1363 octal, and the program would run with the wrong permissions. An error makes every affected literal visible the first time the code runs under 3.0. [TODO: confirm this is the reason, and whether reading leading-zero literals as decimal was considered.]

The uppercase form `0O` is accepted for consistency with `0X` and `0B`, but the lowercase form is recommended. In many fonts, the uppercase `O` is hard to tell from the digit `0`, so `0O17` can be misread. ## Binary literals

A binary literal is `0b` or `0B` followed by one or more binary digits:

```python
>>> 0b1010
10
```

With `0x`, `0o` and `0b`, every radix that Python supports in literals has a prefix of the same shape: a zero followed by one letter that names the radix.

## Built-in functions

`int(s, 0)` follows the new literal rules. It accepts `0o` and `0b` prefixes, and in 3.0 rejects a string such as `"0755"` with a leading zero. With an explicit radix, `int` accepts the matching prefix: `int("0o755", 8)` and `int("0b1010", 2)` both succeed, as `int("0x1f", 16)` does today.

`oct()` returns a string with the new prefix in 3.0:

```python
>>> oct(493)
'0o755'
```

A new built-in function `bin()` returns the binary form of an integer, with the `0b` prefix, in the same way as `hex()` and `oct()`:

```python
>>> bin(10)
'0b1010'
```

## String formatting

The format specification used by `str.format` gains a presentation type `b`, which writes an integer in binary. It supports the same options as `o` and `x`, including width, fill, and the `#` flag that adds the prefix:

```python
>>> format(10, 'b')
'1010'
>>> format(10, '#010b')
'0b00001010'
```

# Python 2.6

Python 2.6 adds every part of this proposal that does not break existing code:

1. The `0o` and `0b` literal prefixes.
2. The `bin()` built-in.
3. The `b` format type.
4. Support for the new prefixes in `int(s, 0)`.

Python 2.6 keeps accepting the old octal form, and `oct()` keeps returning a string with a leading `0`, since code may parse its output. [TODO: decide whether 2.6 warns about the old octal form, for example under the `-3` option that warns about 3.0 incompatibilities.]

With these changes, a module that uses only new-style literals compiles under both 2.6 and 3.0 with the same meaning.

# Backwards compatibility

The following code that is valid in Python 2 is affected by Python 3.0:

1. Source code with old-style octal literals fails to compile. The conversion is mechanical: replace a leading `0` with `0o`. [TODO: confirm that the 2to3 tool performs this conversion.]
2. Code that calls `int(s, 0)` on strings with a leading zero raises `ValueError` where it returned an octal value.
3. Code that parses the output of `oct()` and expects a single leading `0` gets `0o` instead.

Case 2 is the hardest to find, because the strings usually come from outside the program, from files or user input, and a source scan cannot find them. [TODO: say how users should find such code, and whether the PEP recommends any tool.]

Code that uses only decimal and hexadecimal literals is not affected.
