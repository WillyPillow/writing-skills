# Abstract

This PEP adds statically nested scoping, also called lexical scoping, to Python. It is the standard behavior in Python 2.2, and an option enabled per module in Python 2.1. Python 2.1 also warns about code whose meaning will change when the feature is enabled.

Python 2.0 resolves names in exactly three namespaces: the local, the global and the built-in namespace. With nested scopes, a name that is not bound in a function is also looked up in the namespaces of the functions that enclose it. The most visible effect is that a lambda, or any nested function, can refer to variables of the function around it.

# Motivation

Under the current rules, this function does not work:

```python
def make_adder(n):
    return lambda x: x + n

add3 = make_adder(3)
add3(4)    # NameError: global name 'n' is not defined
```

The lambda body refers to `n`. `n` is not local to the lambda, so Python looks in the global namespace, then in the built-ins, and finds it in neither. The `n` in `make_adder` is never consulted, though it is visible in the source a few characters away.

The usual workaround passes the value through a default argument:

```python
def make_adder(n):
    return lambda x, n=n: x + n
```

This works because default values are evaluated when the lambda is created, inside `make_adder`, where `n` is local. It has three problems. The lambda now accepts a second argument that callers can pass by mistake. The pattern must be repeated for every name the lambda uses. And a reader must know the trick to see why `n=n` is there.

The same limit applies to functions defined with `def` inside another function, and to callbacks such as those passed to GUI toolkits or to `map` and `filter`. [TODO: add examples from the standard library or from user reports where the default-argument workaround was needed or caused a bug.]

A reader of Python code already expects lexical scoping. Most languages with nested functions resolve names by the structure of the source [TODO: name the languages the author wants to cite, for example Scheme], and the `make_adder` example looks correct to a reader who has used one of them.

# Specification

## Name binding

A name is bound in a block by any of these constructs: assignment to the name, a `def` or `class` statement, an `import` statement, a `for` loop target, an `except` clause target, and a function parameter. The block is a module, a class body or a function body, and a lambda counts as a function.

As today, a name bound anywhere in a function body is local to that function for the whole body, unless it is declared `global`.

## Name resolution

When a name is used in a function and is not local to it, the compiler looks for the nearest enclosing function that binds the name. If one exists, the name refers to that binding. If none exists, the name is global, and is resolved first in the module's namespace and then in the built-ins, as today.

The resolution is done by the compiler, from the text of the program. Whether a name refers to an enclosing function's variable does not depend on what happens at run time.

Class bodies are skipped. A name bound in a class body is not visible to functions nested in it:

```python
class C:
    size = 10
    def f(self):
        return size     # global 'size', not C.size
```

Methods reach class attributes through `self` or the class name, as they do now. If class bodies were enclosing scopes, every method would see the class's attributes as plain names, and a method that used a global with the same name as a class attribute would change meaning. ## Rebinding

A nested function can read a variable of an enclosing function, but cannot assign to it. Assignment in the nested function makes the name local to the nested function, under the existing rule above. `global` declarations still refer only to the module namespace.

## Interaction with `from module import *` and `exec`

Both constructs can bind names that the compiler cannot see. If a function contains `from module import *` or a bare `exec`, the compiler does not know which names are local to it, and therefore cannot tell whether a free name in a nested function refers to it. In Python 2.2, a function that contains either construct and also contains a nested function with free variables is a `SyntaxError`. # Transition

Some code that is valid in Python 2.0 changes meaning under the new rules. The case is a nested function that uses a name bound both in the enclosing function and at module level:

```python
x = "global"

def f():
    x = "local"
    def g():
        return x
    return g()
```

Under the old rules, `f()` returns `"global"`. Under the new rules, it returns `"local"`. [TODO: give an estimate of how common this is, for example from a scan of the standard library.]

The change happens over two releases:

1. In Python 2.1, the old rules remain the default. A module that begins with `from __future__ import nested_scopes` uses the new rules. The compiler issues a warning for each construct whose meaning would change, and for each use of `import *` or `exec` that would become a `SyntaxError`.
2. In Python 2.2, the new rules are the only rules, and the future statement is accepted with no effect.

The warning in 2.1 is issued when a module is compiled, not when the code runs, so a program receives every warning even for code that never executes.

# Implementation

The compiler marks each name in a function as local, global or free. A free name is one that resolves to a variable of an enclosing function. When an enclosing function has a variable that a nested function uses, the variable is stored in a cell object instead of directly in the frame. The nested function receives references to the cells when it is created, and reads the current value through them each time it runs.

Because the nested function holds cells, not values, it sees later assignments made by the enclosing function:

```python
def f():
    x = 1
    def g():
        return x
    x = 2
    return g()    # returns 2
```

This differs from the default-argument workaround, which captures the value at the time the function is created.

Holding cells also keeps the variables alive for as long as the nested function exists, even after the enclosing function returns. The rest of the enclosing frame can be freed. [TODO: state the cost of cell access compared with local access, if it has been measured.]

# Backwards compatibility

Code is affected in three ways:

1. A nested function that uses a name bound in both an enclosing function and the module now refers to the enclosing function's binding.
2. A function that contains `import *` or a bare `exec` and also contains a nested function with free variables no longer compiles.
3. Programs that depended on the default-argument workaround keep working, since default arguments are unchanged.

Code with no nested functions is not affected.
