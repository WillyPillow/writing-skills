# PEP 597: Add optional EncodingWarning

## Abstract

Add a new warning category, `EncodingWarning`. It is emitted when the `encoding` argument to `open()` is omitted and the default, locale-specific encoding is used. The warning is disabled by default. A new `-X warn_default_encoding` command-line option and a new `PYTHONWARNDEFAULTENCODING` environment variable enable it.

Also add `"locale"` as a value for the `encoding` argument. It states explicitly that the locale encoding should be used, and silences the warning.

## Motivation

### The default depends on the machine

When `open()` opens a file in text mode without an `encoding` argument, it uses the encoding returned by `locale.getpreferredencoding(False)`. That value depends on the operating system and the user's settings. On most Linux and macOS systems it is UTF-8. On Windows it is the ANSI code page, such as `cp1252` for Western European languages or `cp932` for Japanese.

A program that reads a UTF-8 file without an `encoding` argument works on one machine and fails on another:

```python
with open("data.json") as f:
    config = json.load(f)
```

On a system with a UTF-8 locale, this reads the file correctly. On a Windows system with code page 1252, a non-ASCII character in the file is decoded as the wrong characters, or decoding raises `UnicodeDecodeError`. ### Omissions are hard to find

The missing argument is invisible in the source. A reviewer reading `open(path)` cannot tell whether the author meant "use the locale encoding" or forgot to choose one. Linters can flag every `open()` call without `encoding`, but they cannot follow calls through wrapper functions that pass an `encoding=None` default down to `open()`. ## Specification

### `EncodingWarning`

`EncodingWarning` is a new built-in warning class, a subclass of `Warning`.

It is emitted when all of the following hold:

1. The `-X warn_default_encoding` option is given, or `PYTHONWARNDEFAULTENCODING` is set to a non-empty string.
2. A text stream is opened by `open()`, `io.open()` or `io.TextIOWrapper`.
3. The `encoding` argument is omitted or `None`.

The warning message names the call. Its stack level points to the caller of `open()`, so the warning shows the line that omitted the argument.

### Enabling the warning

The warning is off by default because most existing code omits `encoding`, and a warning that fires in nearly every program would be ignored. It is intended for developers checking their own code, not for end users of applications. [TODO: confirm that this is the reason for off-by-default.]

The command-line option and the environment variable both set a new flag, `sys.flags.warn_default_encoding`. The `io` module checks this flag when deciding whether to emit the warning.

Once enabled, the warning goes through the normal warnings filter. Developers can use `-W error::EncodingWarning` to turn it into an exception in a test run.

### `encoding="locale"`

`open(path, encoding="locale")` opens the file with the locale encoding, exactly as omitting the argument does today, and does not emit `EncodingWarning`. This gives code that really wants the locale encoding a way to say so.

`"locale"` is not a codec name. It is accepted by `open()`, `io.open()` and `io.TextIOWrapper`, which resolve it to the current locale encoding when the stream is created. Passing `"locale"` to `codecs.lookup()` or `str.encode()` raises `LookupError`. [TODO: decide whether any other function accepts `"locale"`.]

### Wrapper functions

Many libraries define functions that accept `encoding=None` and pass it to `open()`. With the warning enabled, the warning points at the wrapper's call to `open()`, not at the caller who omitted the argument. The library author cannot fix the warning without changing what the default means.

## Backwards compatibility

The warning is disabled by default, so programs that do not enable it see no change. Enabling it does not change any program's behavior unless the warnings filter turns the warning into an error.

Code that passes `encoding="locale"` does not work on Python versions before this change, because `"locale"` is not a codec name there. Libraries that support older versions cannot use `"locale"` until they drop those versions, and need another way to silence the warning in the meantime. ## Drawbacks

The warning finds omissions only in code paths that run while it is enabled. Code that runs rarely, such as an error handler that writes a log file, may never trigger it during testing.

Libraries that wrap `open()` will produce warnings that point at the wrong line until they adopt a helper like the one in "Wrapper functions". Users who enable the warning will see noise from libraries they do not control.

Adding `"locale"` means one more value of `encoding` that behaves differently from a codec name, which developers have to learn.
