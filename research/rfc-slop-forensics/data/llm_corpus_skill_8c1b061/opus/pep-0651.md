PEP: 651
Title: Robust Stack Overflow Handling
Status: Draft
Type: Standards Track

# Abstract

This PEP proposes that Python treat overflow of the machine stack separately from runaway recursion. Programs could then set the maximum recursion depth to whatever their needs require, and the interpreter would guarantee that exhausting the machine stack raises an exception instead of crashing.

If this PEP is accepted, the following program will run to completion:

    sys.setrecursionlimit(1_000_000)
    def f(n):
        if n:
            f(n-1)
    f(500_000)

and the following program will raise `StackOverflow` instead of crashing the virtual machine:

    sys.setrecursionlimit(1_000_000)
    class X:
        def __add__(self, other):
            return self + other
    X() + 1

# Motivation

## One limit, two jobs

CPython has one mechanism, the recursion limit, that guards against two different failures.

The first is runaway recursion in Python code: a function that calls itself without a base case. The recursion limit turns this into a `RecursionError`, which is a reasonable outcome. The program has a bug, and the error shows the traceback.

The second is exhaustion of the machine (C) stack. The interpreter uses C stack space when Python code calls into C and when C code calls back into Python. If the C stack runs out, the process crashes, typically with a segmentation fault, and no Python exception or traceback is produced. The recursion limit protects against this only indirectly: it is set low enough by default that Python recursion stops before the C stack is used up. Because one number does both jobs, a program cannot choose a value that suits it. Consider a program that walks a deeply nested data structure with a recursive Python function. The default limit raises `RecursionError` long before the C stack is at risk. Raising the limit with `sys.setrecursionlimit` lets the walk go deeper, but the documentation can only warn that too high a value may crash the interpreter. The program has no way to know what value is safe on the machine it runs on. [TODO: add a real example from the author, such as a bug report about a crash after raising the recursion limit.]

## The second example

The second program in the abstract shows a case where the recursion limit does not help. `X() + 1` calls `X.__add__`, whose body evaluates `self + other`, which calls `__add__` again. Each level passes through the C implementation of the `+` operator before reaching the Python method. Every level therefore uses C stack as well as a Python frame. With the recursion limit set to one million, the C stack runs out before the limit is reached, and the interpreter crashes. ## The goal

The goal is a pair of guarantees:

1. The recursion limit governs only the depth of Python calls, so a program can set it from what it needs, not from what the C stack can hold.
2. Running out of C stack raises an exception, whatever the recursion limit is set to.

# Specification

## Two limits

The interpreter keeps two separate checks.

The recursion limit, set by `sys.setrecursionlimit`, counts Python frames. Exceeding it raises `RecursionError`, as today.

A new check guards the C stack. Before any operation that may use a significant amount of C stack, the interpreter compares the current stack position with a safety margin below the end of the stack. If the stack is within the margin, the interpreter raises `StackOverflow` instead of continuing. # Backwards compatibility

Programs that never come near either limit see no change.

A program that relied on the recursion limit to stop deep C-level recursion, without hitting a Python frame limit, will now get `StackOverflow` instead of `RecursionError` in that case. Whether existing handlers catch it depends on the hierarchy decision above.

A program that set a high recursion limit and previously crashed will now either complete or raise `StackOverflow`.
