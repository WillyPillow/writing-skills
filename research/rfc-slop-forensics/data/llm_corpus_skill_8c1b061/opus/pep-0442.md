# PEP 442: Safe object finalization

## Abstract

CPython cannot always run an object's finalizer. When an object with a `__del__` method is part of a reference cycle, the cyclic garbage collector leaves the whole cycle uncollected and appends it to `gc.garbage`. This PEP changes the collector so that it can run finalizers for any object, whatever its position in the object graph. Python code does not need to change: objects that already define finalizers benefit automatically.

## Definitions

A reference cycle is a set of objects in which each object can be reached from every other by following references.

A cyclic isolate (CI) is a reference cycle, or a group of cycles, that no object outside the group references. The cyclic collector finds cyclic isolates. Reference counting alone cannot free them, because each object in a CI keeps at least one other alive.

A finalizer is code that runs once when an object is about to be destroyed. At the Python level this is `__del__`. At the C level this PEP adds a new slot, `tp_finalize`, described below.

Resurrection happens when a finalizer stores a new reference to the object, or to another object in its CI, somewhere outside the CI. After resurrection the object is reachable again and must not be freed.

## Motivation

The collector frees a CI by calling `tp_clear` on its objects. `tp_clear` drops each object's references, which brings the reference counts to zero and lets normal deallocation run. If an object in the CI has a `__del__` method, the collector cannot follow this procedure. `tp_clear` runs in an arbitrary order, so by the time an object's `__del__` runs, objects it refers to may already be cleared. A `__del__` that reads `self.file` could find a cleared, half-destroyed object.

To avoid exposing half-destroyed objects, the current collector refuses to collect any CI that contains an object with `__del__`. It moves such cycles to `gc.garbage` and leaves them there. ## Proposal

The proposal separates finalization from destruction. The collector first runs every finalizer in a CI, with all objects in the CI still intact. Only then does it decide whether the CI is still garbage and, if it is, break it with `tp_clear`.

### The `tp_finalize` slot

A new type slot, `tp_finalize`, holds the finalizer for C types and is set for Python classes that define `__del__`. Its signature is:

```c
void tp_finalize(PyObject *self);
```

`tp_finalize` must leave the object in a valid state. It may run arbitrary Python code, including code that resurrects the object.

Each object records whether its finalizer has run. A finalizer runs at most once per object, even if the object is resurrected and later becomes garbage again. ### Reference-counting path

When an object's reference count drops to zero, deallocation calls `tp_finalize` first, if the object has one and it has not run yet. If the finalizer resurrects the object, deallocation stops. Otherwise it proceeds to free the object as before.

### Cyclic collector path

For each collection, the collector performs these steps:

1. Find the cyclic isolates among the objects being collected, as it does now.
2. For each object in the cyclic isolates that has a `tp_finalize` not yet run, call it. All objects in the CIs are still fully intact, so every finalizer sees valid objects.
3. Recompute reachability for the objects in the CIs. A finalizer may have made some of them reachable from outside.
4. Any CI that is no longer isolated is resurrected. The collector leaves its objects alive and does not clear them.
5. For each CI that is still isolated, call `tp_clear` on its objects, as now. Deallocation follows. Because finalizers already ran in step 2, deallocation does not call them again.

Step 3 is the step that makes the procedure safe in the presence of resurrection. Without it the collector would clear objects that a finalizer had just made reachable again, and the program would later see cleared objects through the new reference. ### Order of finalizers

Within a CI, finalizers run in an unspecified order. Every finalizer sees intact objects, but a finalizer may see an object whose own finalizer has already run. An object whose finalizer closes a file may find, when another finalizer calls it, that the file is already closed. Finalizers in a cycle need to tolerate this case.
