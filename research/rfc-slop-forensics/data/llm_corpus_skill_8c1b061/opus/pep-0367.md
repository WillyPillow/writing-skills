# PEP 367: New super

## Abstract

This PEP proposes that the name `super`, used inside a method, refer to a `super` object already bound to the class in which the method was defined and to the instance on which the method is running. For a class method, it is bound to the class object instead of an instance. A call that today reads

```python
super(Foo, self).foo(1, 2)
```

becomes

```python
super.foo(1, 2)
```

The current built-in `super` type is renamed to `__super__`. In Python 3.0, the name `super` stops being a built-in. Assignment to `super` becomes a `SyntaxError`, as assignment to `None` is.

## Motivation

The current spelling asks the programmer to restate two facts that the interpreter already knows at the point of the call: the class that defines the method and the object the method is acting on. Consider a method in a class `Foo`:

```python
class Foo(Base):
    def foo(self, a, b):
        return super(Foo, self).foo(a, b)
```

Both arguments to `super` are fixed by where the call appears. The first argument must name the class whose body contains the method. The second is the method's first parameter. Writing them out by hand creates two ways for the call to go wrong.

The first is renaming. If `Foo` is renamed and the call is not updated, the call refers to whatever object the old name is bound to. If that name is unbound, the call fails with a `NameError` at run time, not at definition time. If it is still bound, for example to a subclass or to an old copy of the class, the call may silently skip a class in the method resolution order.

The second is copying. A method copied from one class to another keeps the old class name in its `super` call. The result is the same as with renaming, and the error is found only when that code path runs.

## Specification

### Meaning of `super` inside a method

Inside a function defined in the body of a class statement, a reference to the name `super` evaluates to the same object that `__super__(C, x)` would return. Here `C` is the class created by the enclosing class statement, and `x` is:

- the method's first argument, for an ordinary method;
- the class object passed as the first argument, for a class method.

Attribute access on the result works as it does today. `super.foo(1, 2)` looks up `foo` in the method resolution order of `type(x)`, starting after `C`, binds it to `x`, and calls it with `1` and `2`.

### The renamed built-in

The existing `super` type remains available as `__super__`, with its current signature and behaviour. Code that needs the explicit form, such as code calling `super` for a class other than the defining one, uses `__super__(C, x)`.

In Python 2.x, the built-in name `super` remains available outside methods, so that existing code continues to run. [TODO: confirm. In Python 3.0, `super` is removed from the built-in namespace.

### Assignment to `super`

Assignment to `super` becomes a `SyntaxError`, in the same way as assignment to `None`. This covers plain assignment, use as a function parameter name, use as the target of a `for` loop, and the other binding forms. The restriction keeps the meaning of `super` fixed within a method. Without it, a module that bound `super` at the top level, or a method with a parameter called `super`, could change what `super.foo(1, 2)` refers to, and the shorter spelling would carry the same hidden dependence on names that the current spelling has.

## Backwards compatibility

In Python 2.x, existing calls of the form `super(Foo, self)` keep working if the built-in name remains available, subject to the open question above. The `SyntaxError` on assignment breaks any code that binds `super`, and needs a deprecation period. [TODO: the planned release for the warning and for the error.]

In Python 3.0, every call of the form `super(Foo, self).foo(...)` must be rewritten either to the new form or to `__super__(Foo, self).foo(...)`. The rewrite is mechanical when the first argument is the defining class and the second is the first parameter.
