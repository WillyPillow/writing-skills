# PEP 400: Deprecate codecs.StreamReader and codecs.StreamWriter

## Abstract

`io.TextIOWrapper` and `codecs.StreamReaderWriter` offer the same API [#f1]_. `TextIOWrapper` has more features and is faster. Keeping both means each bug has to be fixed twice and the two implementations can drift apart in small ways. This PEP proposes to deprecate `codecs.StreamReader`, `codecs.StreamWriter` and `codecs.StreamReaderWriter`, and to direct users to `io.TextIOWrapper` and the `open()` built-in.

## Rationale

### Two implementations of one job

The `codecs` module was added in Python 2.0 by PEP 100. It defined `StreamReader` and `StreamWriter` as the way to read and write text through a codec, and `StreamReaderWriter` to combine the two over one stream. `codecs.open()` returns a `StreamReaderWriter`.

The `io` module was added in Python 2.6 and 3.0 by PEP 3116, and reimplemented in C in Python 2.7 and 3.1. Its `TextIOWrapper` wraps a binary stream and decodes and encodes text through a codec's incremental decoder and encoder. In Python 3, `open()` in text mode returns a `TextIOWrapper`.

Both classes take a byte stream and an encoding, and expose `read()`, `readline()`, `readlines()`, `write()`, `writelines()`, iteration, and `close()`. A program that uses only these methods can switch from one class to the other without other changes. When a decoding bug is found, it has to be found and fixed separately in each class. ### The codec registry

A codec registered with `codecs.register()` returns a `CodecInfo` object. That object has `streamreader` and `streamwriter` attributes, which hold the codec's `StreamReader` and `StreamWriter` classes. `TextIOWrapper` does not use them. It uses the `incrementaldecoder` and `incrementalencoder` attributes instead.

This PEP does not remove the `streamreader` and `streamwriter` attributes. Codecs that define only stream classes and no incremental classes cannot be used with `TextIOWrapper`. ## Backwards compatibility

The change affects three kinds of code.

Code that calls `codecs.open()` and uses only the shared methods gets a `TextIOWrapper` instead of a `StreamReaderWriter`. [TODO: check whether any shared method returns a different result between the two, beyond the differences listed under "Rationale".]

Code that instantiates `StreamReader` or `StreamWriter` directly, or through `codecs.getreader()` and `codecs.getwriter()`, gets a `DeprecationWarning`. The code keeps working until removal. [TODO: decide whether `getreader()` and `getwriter()` are deprecated at the same time.]

Code that subclasses `StreamReader` or `StreamWriter` to implement a codec has to provide incremental classes before removal. This is the group with the most work to do. [TODO: give examples of such codecs, if known.]

`DeprecationWarning` is hidden by default outside of `__main__` and test runners, so end users of applications see no change until removal.

## Migrating existing code

Most uses of the deprecated classes come through `codecs.open()`. In Python 3, the replacement is the built-in `open()` with an `encoding` argument:

```python
# Before
f = codecs.open("notes.txt", "r", encoding="utf-8")

# After
f = open("notes.txt", "r", encoding="utf-8", newline="")
```

The `newline=""` argument keeps line endings as they are in the file, which matches what `codecs.open()` returns today. Code that wants universal newline handling can omit it.

Code that wraps an existing binary stream, such as a socket file or a `BytesIO`, replaces `codecs.getreader(encoding)(stream)` with `io.TextIOWrapper(stream, encoding=encoding)`. One difference needs attention here. `TextIOWrapper` expects a buffered binary stream with `readable()`, `writable()` and `closed`. A plain object that only defines `read()` may work with `StreamReader` but not with `TextIOWrapper`. The `errors` argument is passed through unchanged. Both classes accept the same error handler names.
