PEP: 296
Title: Adding a bytes Object Type
Status: Draft
Type: Standards Track

# Abstract

This PEP proposes a new standard type, `bytes`, with a builtin constructor of the same name. A `bytes` object stores an array of bytes compactly, one byte per element. It differs from the existing types that already hold byte sequences in the characteristics listed under "Specification" below.

# Motivation

Python programs that handle binary data today pick one of several containers, and each was designed for something else.

The `str` type holds 8-bit characters. Programs use it for binary data because file reads, socket reads and `struct.pack` all return `str`. The result is that the same type stands for text in one place and raw octets in another, and nothing in the program says which. When Unicode strings and 8-bit strings are mixed, Python converts the 8-bit string using the default encoding, so binary data can be decoded as text by accident. The `array` module can store bytes with typecode `'b'` or `'B'`. An `array` is a general container of machine numbers, and its byte variant inherits that interface rather than one suited to binary data. The `buffer` object gives a view onto memory owned by another object. It does not own its storage, so its contents can change or become invalid when the owner changes. [TODO: confirm which `buffer` problems the author wants to cite.]

None of these types states, in its interface, "this is a sequence of octets with no text meaning." A dedicated type gives binary data a name, so that a function signature or a docstring can say that it takes or returns bytes, and so that the language can refuse to mix bytes and text silently.

# Specification

## Construction

The builtin `bytes` is both the type and its constructor. It accepts the following arguments:

1. No argument, which returns an empty `bytes` object.
2. An integer `n`, which returns a `bytes` object of length `n` with every byte set to zero.
3. A sequence of integers, each in `range(256)`, which returns a `bytes` object holding those values. A value outside that range raises `ValueError`.
4. An object that supports the buffer interface, which returns a copy of the bytes it exposes.

## Element access

Indexing a `bytes` object returns an `int` in `range(256)`, not a one-character string:

    >>> b = bytes([104, 105])
    >>> b[0]
    104

This is the main point where `bytes` differs from `str`. An element of binary data is a number, and returning a string of length one would keep the text interpretation alive. The cost is that code that moves from `str` to `bytes` must change every place that compares an element to a character literal.

## Mutability

[TODO: decide whether `bytes` objects are mutable. The choice is hard to reverse once code depends on it, so it needs the most justification in this PEP.]

The two options lead to different designs:

- A mutable `bytes` supports item and slice assignment, so it can serve as a buffer for I/O that fills data in place. It cannot be hashed, so it cannot be a dictionary key.
- An immutable `bytes` can be hashed and shared safely, like `str`. Code that builds binary data piece by piece must then use a list or an `array` and convert at the end.

The goal of compact storage constrains this choice only partly. Both options store one byte per element; the difference is whether in-place updates avoid a copy.

## Operations

`bytes` supports `len()`, iteration (yielding integers), `in` with an integer operand, concatenation with `+` and repetition with `*`. Comparison is lexicographic on the unsigned byte values.

# Comparison with existing types

The table below compares `bytes` with the three types it overlaps. Entries marked "open" depend on the decisions above.

| Property                  | `str`     | `array('B')` | `buffer`        | `bytes` |
|---------------------------|-----------|--------------|-----------------|---------|
| Owns its storage          | yes       | yes          | no              | yes     |
| Element type on indexing  | 1-char str| int          | 1-char str      | int     |
| Mutable                   | no        | yes          | depends on owner| open    |

| Mixes silently with text  | yes       | no           | yes             | no      |

# Rationale

## A new type rather than changes to an existing one

[TODO: record whether the author considered changing `array.array('B')` or `buffer` instead of adding a type, and why that was rejected. Do not present either as considered until the author confirms.]

Changing `str` so that it stops serving as a byte container is not part of this PEP. That change would break a large body of code, and it only becomes possible once a replacement type exists. This PEP supplies the replacement; it does not remove anything.

## A builtin rather than a module

Placing `bytes` in the builtins lets library functions return it without asking callers to import a module first. The cost is one more name in the builtin namespace, where it can shadow or be shadowed by user code that already uses the name `bytes` for a variable. [TODO: confirm that the author wants a builtin and not, for example, a type in a `bytes` or `binascii` module.]

# Backwards compatibility

Adding a builtin type changes no existing behavior. A program that already defines a global or local named `bytes` keeps working, because its own binding shadows the builtin. The only programs affected are those that relied on `bytes` raising `NameError`. [TODO: confirm there are no other effects, such as on code that inspects the builtins dictionary.]

No existing function changes its return type under this PEP.

# Open questions

1. Mutability, and with it hashability and the writability of the exported buffer. This is the decision with the most downstream consequences.
2. Whether `bytes` accepts a `str` argument, and what it does with a Unicode string.
3. Whether slices copy or share storage.
4. Which `str` methods `bytes` provides.
5. The form of `repr()`.
6. Whether file and socket methods should return `bytes`, in this PEP or a later one.
