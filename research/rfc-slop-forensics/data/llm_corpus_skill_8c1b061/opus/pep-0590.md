PEP: 590
Title: Vectorcall: a fast calling protocol for CPython
Status: Draft
Type: Standards Track

# Abstract

This PEP adds a C API for calling objects that avoids building a tuple and a dictionary for each call. It defines a new protocol, "vectorcall", and the calling convention that goes with it. The convention is based on "fastcall", which CPython already uses internally. Any extension class, including user-defined ones, can implement the protocol.

Most of the new API is private in CPython 3.8. The plan is to settle its semantics during 3.8 and make it public in 3.9.

This PEP concerns only the Python/C API. It does not change the Python language or the standard library.

# Motivation

## The cost of `tp_call`

The general way to call an object from C is `tp_call`:

    PyObject *tp_call(PyObject *callable, PyObject *args, PyObject *kwargs);

The positional arguments arrive as a tuple and the keyword arguments as a dictionary. A caller that holds its arguments in a C array, which is what the interpreter's evaluation loop has on its value stack, must allocate a tuple and copy the arguments into it before the call. A call with keyword arguments also needs a dictionary. The callee often unpacks the tuple straight back into C variables. [TODO: give the author's measurement of this overhead, for example the time per call for a simple function with and without the tuple, and the benchmark it comes from.]

## Fastcall is internal only

CPython already avoids this cost for some of its own types. Internally it uses a "fastcall" convention, in which the arguments are passed as a C array and a count. Functions defined in Python, builtin functions and method descriptors use fastcall when called from the evaluation loop. [TODO: confirm the list of types that use fastcall in 3.7.]

Fastcall is not available to third-party code. An extension type that defines its own callable objects, such as a Cython function or a function type from another language binding, must implement `tp_call` and pay for the tuple on every call. [TODO: name the extension projects the author has in mind and, if available, their measured overhead.] The interpreter also has to special-case each internal type that uses fastcall, which makes adding a new fast path a change to the core.

The goal of this PEP is a single protocol that the interpreter calls through for every type that supports it, internal or external, so that a third-party callable gets the same treatment as a builtin function.

# Specification

## The vectorcall function

A callable that supports vectorcall provides a function of this type:

    typedef PyObject *(*vectorcallfunc)(PyObject *callable,
                                         PyObject *const *args,
                                         size_t nargsf,
                                         PyObject *kwnames);

The arguments mean:

1. `callable`: the object being called.
2. `args`: a C array holding the positional arguments followed by the values of the keyword arguments.
3. `nargsf`: the number of positional arguments, possibly combined with a flag described below. The macro `PyVectorcall_NARGS(nargsf)` extracts the count.
4. `kwnames`: a tuple of the keyword argument names, or `NULL` if there are none. Its length is the number of keyword values that follow the positional arguments in `args`.

Keyword names are passed as a tuple, not a dictionary, because a call site in Python source has a fixed set of names. The compiler can create that tuple once, as a constant, and reuse it for every execution of the call. [TODO: confirm with the author that this is the reason for a names tuple.]

The callee must not modify `args` or `kwnames`, apart from the use of `args[-1]` described next.

## The offset flag

If the caller sets the flag `PY_VECTORCALL_ARGUMENTS_OFFSET` in `nargsf`, the callee may temporarily overwrite `args[-1]`, provided it restores the value before returning.

The flag addresses bound methods. A bound method receives arguments `a, b` and must call its underlying function with `self, a, b`. Without the flag, it must allocate a new array to prepend `self`. With the flag, it writes `self` into `args[-1]`, calls the function with `args - 1`, and restores the slot afterwards. A caller that has a spare slot before its arguments, can set the flag without allocating anything. [TODO: confirm that the evaluation loop's value stack always has such a slot.]

## Where the function is found

A type that supports vectorcall sets the type flag `Py_TPFLAGS_HAVE_VECTORCALL` and sets `tp_vectorcall_offset` to the byte offset, within each instance, of a `vectorcallfunc` pointer.

The function pointer is stored per instance, not per type. This lets a single type, such as a builtin function type, give different instances different call implementations, for example a specialized one for functions that take no arguments. The cost is one pointer per instance. [TODO: confirm with the author that per-instance storage is the deciding reason, and whether a per-type slot was considered.]

A `NULL` pointer in an instance means that this instance does not support vectorcall, and callers fall back to `tp_call`.

## Calling

Callers use a single function:

    PyObject *_PyObject_Vectorcall(PyObject *callable, PyObject *const *args,
                                   size_t nargsf, PyObject *kwnames);

It checks whether the type supports vectorcall and whether the instance's pointer is non-`NULL`. If both hold, it calls the function. Otherwise it builds a tuple and dictionary from `args` and `kwnames` and calls `tp_call`.

## `tp_call` must stay consistent

A type that implements vectorcall must also implement `tp_call`, with the same behavior, because existing code calls objects through `tp_call` directly. The helper `PyVectorcall_Call` implements `tp_call` in terms of the vectorcall function, so a type can set `tp_call = PyVectorcall_Call` and write the call logic only once.

## Private in 3.8, public in 3.9

In 3.8, `_PyObject_Vectorcall` and the type flag carry a leading underscore and are not part of the stable API. Extension authors can use them, accepting that their names or semantics may change in 3.9. [TODO: list exactly which names are private in 3.8 and which, if any, are public from the start.]
