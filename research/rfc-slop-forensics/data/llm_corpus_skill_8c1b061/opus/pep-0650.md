# PEP 650: Specifying installer requirements for Python projects

## Abstract

Python package installers do not interoperate fully. pip is the most widely used installer and a de facto standard, but others, such as Poetry and Pipenv, are also popular because they offer features suited to particular workflows that pip does not provide in the same way. Each of these tools records a project's dependencies in its own format, and no standard requirements file exists. As a result, installing a project's dependencies requires running the specific tool whose format the project uses, or having that tool export a requirements file, which can lose information the tool relies on.

This PEP proposes that a project declare, in its `pyproject.toml`, which installer manages its dependencies and how to invoke it through a common interface. Any tool that understands the interface, called a universal installer here, can then install the project's dependencies by delegating to the declared installer. ## The problem

Consider a project whose dependencies are managed with Poetry. Its dependency list and lock file are in Poetry's formats. A cloud platform, a continuous integration service or an IDE that wants to install that project's dependencies has three options today:

1. Support Poetry's format directly.
2. Require the project to export a pip requirements file.
3. Require the user to install and run Poetry before the platform does anything else.

The first option scales poorly for the platform. It must add and maintain support for each installer its users choose, and a project using an installer the platform does not know about cannot be installed at all.

The second option loses information. A requirements file can express only what pip's format can express. ## Goals

- A project can declare which installer manages its dependencies, in a file that tools already read.
- A tool that knows only the interface defined here can install the dependencies of any project that makes such a declaration, without knowing the installer's file formats.
- The declared installer keeps full control of its own formats, so no information is lost in translation.

## Non-goals

- This PEP does not define a standard lock file or dependency file format. Each installer keeps its own.
- This PEP does not choose a preferred installer or rank installers.
- This PEP does not change how packages are built or published. [TODO: confirm.]

## Specification

### Declaring the installer

A project adds a table to `pyproject.toml`. This document calls it `[install-system]` [TODO: confirm the table name]. The table has two keys:

- `requires`: a list of requirement strings for the packages needed to run the installer. A universal installer installs these into an isolated environment before invoking the installer.
- `install-backend`: an object reference, in the form `module:object`, naming the Python object that implements the interface below.

For example:

```toml
[install-system]
requires = ["poetry"]
install-backend = "poetry.installer_api"
```

### The installer interface

The backend object provides hooks that a universal installer calls. The minimum is:

```python
def invoke_install(path, *, dependency_group=None, **kwargs) -> int:
    ...
```

`path` is the directory containing `pyproject.toml`. `dependency_group` names an optional subset of dependencies, such as development or test dependencies, when the installer supports such groups. The hook installs the project's dependencies into the current environment and returns a process exit code.

### Behaviour of a universal installer

A universal installer that encounters a project with an `[install-system]` table proceeds as follows:

1. Create an isolated environment.
2. Install the packages listed in `requires` into that environment.
3. Import the object named by `install-backend`.
4. Call `invoke_install` with the project path and any dependency group the user requested.
5. Report the exit code to the user.

If `pyproject.toml` has no `[install-system]` table, the universal installer falls back to its own default behaviour. [TODO: what that default is. The material does not say whether pip would act as the fallback or whether the universal installer must report an error.]

## Rationale

The design separates two questions that are coupled today: which tool knows how to read a project's dependency data, and which tool a platform runs. The project answers the first question in `pyproject.toml`. The platform only has to answer the second, once, by supporting the interface.

An alternative is a common requirements format that all installers read and write. That would solve the information loss problem directly, but each installer's format exists because it records things the others do not. ## Costs and drawbacks

Installers must each implement the backend interface. An installer that does not cannot be used through a universal installer, so the problem remains for projects that use it. [TODO: whether the maintainers of pip, Poetry and Pipenv have agreed to implement the interface.]

Delegating installation means running code from the declared installer, and that code runs before any of the project's dependencies are installed. The security section below covers the consequences.

Each installer keeps its own lock file format, so the PEP does not make a project's dependency data readable by other tools. A security scanner, for example, still cannot read a Poetry lock file without Poetry-specific support.

Once installers and platforms implement the table name and hook signatures, changing them requires a coordinated migration across tools maintained by different groups. These are the parts of the design that need the most review before acceptance.

## Security implications

A universal installer runs whatever backend the project declares. Users who install a project's dependencies through a universal installer are therefore trusting the project's choice of installer, in addition to the dependencies themselves.
