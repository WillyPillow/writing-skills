# PEP 570: Python positional-only parameters

## Abstract

This PEP proposes a new syntax, `/`, for marking parameters as positional-only in Python function definitions. A positional-only parameter has no name that callers can use. When a function with positional-only parameters is called, positional arguments are bound to those parameters by order alone.

Library authors design an API so that callers use it correctly and as intended. Without a way to make parameters positional-only, authors have to choose every parameter name with care, because callers can pass any argument by name. This holds even for required parameters, and for parameters whose names mean nothing to callers.

This PEP covers the history and current semantics of positional-only parameters in Python, the problems caused by their absence in Python-level code, how the new syntax solves those problems, and the grammar and semantics of the change.

## Background

Positional-only parameters already exist in Python, but only for functions written in C. Many built-in functions accept arguments only by position. `len(obj=[1])` raises a `TypeError`, because `len`'s parameter has no usable name. The same is true of many methods of built-in types, such as `list.append` and `dict.get`.

Argument Clinic, the tool CPython uses to generate argument parsing for C functions, marks these parameters with `/` in its input. `help()` and `inspect.signature()` show the same marker: the signature of `divmod` is displayed as `divmod(x, y, /)`. The `inspect` module has had a `Parameter.POSITIONAL_ONLY` kind since Python 3.3. [TODO: confirm the version.] Python code can read this kind, but cannot declare a parameter with it.

Python-level code that wants the same behavior has two options today. It can accept `*args` and unpack it by hand, which hides the real signature from `help()`, from editors and from type checkers. Or it can use names with a leading double underscore, a convention some type checkers recognize, which still lets callers pass the argument by name. ## Problems

### Parameter names become part of the API

Any parameter that can be passed by keyword makes its name part of the function's public interface. If a library renames a parameter, any caller that passed it by name breaks. Consider a function written as:

```python
def distance(a, b):
    ...
```

The names `a` and `b` carry no meaning to callers. Nothing stops a caller from writing `distance(a=p, b=q)`, and once one does, the library cannot rename the parameters to `p1` and `p2` without breaking that caller. The library author has to treat names that were never meant to be public as public.

### Names collide with `**kwargs`

A function that accepts arbitrary keyword arguments cannot also have a named parameter whose name a caller might want to use as a key:

```python
def format_record(template, **fields):
    return template.format(**fields)

format_record("{template}", template="x")  # TypeError
```

The call fails because `template` is bound twice: once by position and once by keyword. A function that forwards keyword arguments, such as a wrapper that passes `**kwargs` to another callable, has this problem with every one of its own parameter names. With positional-only parameters, `template` would not be a keyword the function accepts, and `template="x"` would go into `fields`.

### Pure-Python and C implementations disagree

Some standard library modules have both a C implementation and a pure-Python one, and the Python one is used on implementations without the C accelerator. The C version may accept an argument only by position, while the Python version accepts it by name. Code written and tested against one version can then fail on the other. ## Specification

### Syntax

A `/` in a function's parameter list marks every parameter before it as positional-only:

```python
def f(pos1, pos2, /, pos_or_kw, *, kw_only):
    ...
```

Here `pos1` and `pos2` are positional-only, `pos_or_kw` can be passed either way, and `kw_only` is keyword-only, as defined by PEP 3102.

The rules are:

1. `/` may appear at most once.
2. `/` must come after at least one parameter.
3. `/` must come before `*` or `*args`, if either is present.
4. Positional-only parameters may have default values. As for other parameters, once one parameter has a default, every following parameter before `*` must have one too.

The same syntax applies to `lambda` expressions.

The `/` marker was chosen to match the notation already used by Argument Clinic, `help()` and the documentation. [TODO: confirm that this consistency is the deciding reason, and record other spellings considered, if any.]

### Semantics

When a function is called, positional arguments are bound to positional-only parameters in order, as for other positional parameters. A keyword argument whose name matches a positional-only parameter does not bind to that parameter. If the function has `**kwargs`, the keyword argument goes into `kwargs`. Otherwise the call raises `TypeError`.

```python
def f(a, /, **kwargs):
    return a, kwargs

f(1, a=2)   # returns (1, {'a': 2})
f(a=2)      # TypeError: missing required positional argument
```

## How to teach this

The guidance for users is short. Use `/` when parameter names have no meaning to callers, when the names may change, or when the function also takes `**kwargs`. Use keyword-only parameters, after `*`, when the names are the clearest way to call the function. Leave other parameters as they are.

## Drawbacks

The syntax adds a third parameter kind that users meet in function definitions, not only in documentation. Python already has a fairly involved parameter list, and every addition makes signatures harder to read for beginners.

Once a library marks a parameter positional-only, making it keyword-capable later is a compatible change, but the reverse is not. Authors who overuse `/` lose nothing they cannot recover. Authors who omit it keep the problems described above.
