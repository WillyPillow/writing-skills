# PEP 207: Rich comparisons

## Abstract

This PEP proposes two changes to comparisons in Python:

1. Classes and C extension types can overload each of `<`, `>`, `<=`, `>=`, `==` and `!=` separately.
2. Each of these overloaded operators can return any object, not only a Boolean result.

## Motivation

Today a class customizes comparison through a single method, `__cmp__`, and a C type through a single slot, `tp_compare`. Python evaluates `a < b` by calling `__cmp__(a, b)` and testing whether the result is negative. All six operators go through the same call, and the result is always reduced to an integer, and then to true or false.

This design rules out two kinds of types.

The first is a type for which the six operators are not related in the way `__cmp__` assumes. `__cmp__` describes a total order: for any two values, exactly one of "less", "equal" and "greater" holds. Some types have only a partial order. For sets ordered by inclusion, `{1}` is neither a subset nor a superset of `{2}`, so `{1} < {2}` and `{1} > {2}` should both be false. `__cmp__` cannot express that, because it must return one of the three answers. Other types support equality but no ordering at all, such as complex numbers, and should raise an error for `<` while still answering `==`.

The second is a type for which a comparison should not return a truth value. For an array type, a natural meaning of `a < b` is an array of element-by-element results. A symbolic algebra package may want `x < y` to build an expression object. With `__cmp__`, the result is forced to an integer before the type can return anything else. ## Specification

### New methods

A class may define any of these six methods:

| Operator | Method   | Reflected method |
|----------|----------|------------------|
| `a < b`  | `__lt__` | `__gt__`         |
| `a <= b` | `__le__` | `__ge__`         |
| `a > b`  | `__gt__` | `__lt__`         |
| `a >= b` | `__ge__` | `__le__`         |
| `a == b` | `__eq__` | `__eq__`         |
| `a != b` | `__ne__` | `__ne__`         |

Each method takes the right operand as its single argument and may return any object. The interpreter does not convert the result. If the result is used in a Boolean context, such as an `if` statement, Python calls its truth test as for any object.

A method may return the singleton `NotImplemented` to say that it does not handle the given operand types.

### Evaluation order

To evaluate `a < b`, Python does the following:

1. If `type(a)` defines `__lt__`, call `a.__lt__(b)`. If the result is not `NotImplemented`, use it.
2. If `type(b)` defines `__gt__`, call `b.__gt__(a)`. If the result is not `NotImplemented`, use it.
3. Otherwise, fall back to `__cmp__`, as today.

The reflected method in step 2 is the one that gives the same answer with the operands swapped: `a < b` is the same question as `b > a`. Equality and inequality are their own reflections.

Python does not assume any relation among the six methods. It does not derive `__ne__` from `__eq__`, or `__gt__` from `__le__`. A class that wants these relations defines each method. This rule is what makes partial orders and non-Boolean results possible: any derivation would have to assume a total order or a Boolean result. ### Fallback to `__cmp__`

If neither operand handles a comparison through the new methods, Python uses `__cmp__` exactly as before. A class that defines only `__cmp__` behaves as it does today. A class that defines both uses the rich methods first, and `__cmp__` only for operators it does not define.

### C API

A new type slot, `tp_richcompare`, has this signature:

```c
PyObject *tp_richcompare(PyObject *a, PyObject *b, int op);
```

`op` is one of six constants, `Py_LT`, `Py_LE`, `Py_EQ`, `Py_NE`, `Py_GT` and `Py_GE`. The function returns a new reference to any object, or `Py_NotImplemented`, or `NULL` with an exception set.

A single slot with an operator code, rather than six slots, keeps the type object small and lets a C type share code across operators. [TODO: confirm that this is the reason for one slot.]

A new type flag tells the interpreter that a type has the slot, so that extension modules compiled against older headers keep working. [TODO: name the flag.]

Two new API functions call the full comparison protocol from C:

```c
PyObject *PyObject_RichCompare(PyObject *a, PyObject *b, int op);
int PyObject_RichCompareBool(PyObject *a, PyObject *b, int op);
```

`PyObject_RichCompareBool` returns 1, 0, or -1 on error, and is what the interpreter uses internally where it needs a truth value.

### Chained comparisons

`a < b < c` already means `a < b and b < c`, with `b` evaluated once. This PEP does not change that. With non-Boolean results, the `and` calls the truth test of the result of `a < b`. For an array type whose comparison returns an array, that truth test may be ambiguous, and the array type can raise an exception from it. Chained comparisons then fail for such types, which is the correct outcome when there is no single answer.

## Effect on built-in operations

Several built-in operations compare objects: `in`, `list.index`, `list.sort`, `min`, `max` and dictionary lookup. ## Backwards compatibility

Classes that define only `__cmp__` keep their behavior, because the fallback path is unchanged. C types without the new flag keep using `tp_compare`.
