PEP: 520
Title: Preserving Class Attribute Definition Order
Status: Draft
Type: Standards Track

# Abstract

A class body lists its attributes in an order, and that order is sometimes significant. Python currently discards it when it creates the class. This PEP preserves the order in which attributes are introduced in the class definition body, and stores it on the class in a new attribute, `__definition_order__`. Code that needs the order, such as a class decorator, can then read it without a metaclass and without asking the class author to list the attributes a second time.

# Motivation

## The order exists and is lost

A class body runs top to bottom, so its attributes are created in a definite sequence:

    class Point3D:
        x = Field(float)
        y = Field(float)
        z = Field(float)

Anyone reading this class sees `x`, `y`, `z` in that order. The interpreter runs the body in a namespace that is an ordinary `dict`, then passes that namespace to the metaclass, which copies it into the new class's `__dict__`. If it does, the order exists in memory but is not part of the language guarantee; if it does not, the order is lost when the body finishes.] Either way, code that inspects `Point3D` afterwards has no supported way to recover the order.

## When the order matters

For many classes the order of attributes is only a matter of readability. For some it carries meaning. In the example above, a decorator that generates `__init__` from the `Field` declarations should give it the signature `__init__(self, x, y, z)`. Without the definition order, the decorator cannot know whether `Point3D(1, 2, 3)` means `x=1` or `z=1`.

## The current workarounds

Code that needs the order today has two options.

The first is a metaclass whose `__prepare__` method returns an `OrderedDict`, so the body runs in an ordered namespace, and whose `__new__` records the keys. This works, but it forces a metaclass on every class that needs the order. A class can have only one metaclass, so this approach conflicts with any other metaclass the class or its bases already use.

The second is to ask the class author to repeat the order by hand:

    class Point3D:
        _fields = ("x", "y", "z")
        x = Field(float)
        y = Field(float)
        z = Field(float)

This duplicates information the interpreter already had, and the two lists can drift apart when someone edits one of them.

Since the interpreter sees the order while running the class body, recording it costs the class author nothing. That is the case for making the order available by default.

# Specification

## The attribute

Every class created by `type.__new__` gets a `__definition_order__` attribute. Its value is a tuple of strings: the names bound in the class body, in the order in which each name was first bound.

    >>> class Point3D:
    ...     x = 1
    ...     y = 2
    ...     z = 3
    ...
    >>> Point3D.__definition_order__
    ('x', 'y', 'z')

A name that is bound twice appears once, at the position of its first binding. [TODO: confirm first binding rather than last.]

## Which names are included

The tuple includes names bound by assignment, `def`, `class`, `import` and any other binding statement in the class body.

## Type and mutability

The value is a tuple, not a list, so that it cannot be changed in place. [TODO: decide whether `__definition_order__` can be reassigned or deleted on the class. Attributes added to the class after it is created, for example by `setattr`, do not appear in `__definition_order__`. The attribute records the class definition, not the current state of the class.

## Classes that set the attribute themselves

If the class body binds `__definition_order__` itself, that value is kept and the computed one is not stored. This lets a class author state an order explicitly, for example when attributes are created in a loop and the computed order would not mean anything useful.

# Rationale

## A new attribute rather than an ordered `__dict__`

An alternative is to make the class's `__dict__` itself ordered, so that iterating over it gives the definition order. A separate attribute keeps the definition order stable even when later code adds or removes class attributes, which changes `__dict__` but should not change the record of what the class body contained. [TODO: confirm with the author whether an ordered `__dict__` was considered and whether this is the reason it lost.]

## Why a tuple of names

The tuple stores names, not values. The values are already available through the class, and storing them a second time would keep references that outlive changes to the class.
