# PEP 439: Inclusion of implicit pip bootstrap in Python installation

## Abstract

This PEP proposes that Python installations include a small `pip` bootstrap executable. The first time a user runs `pip`, the bootstrap downloads and installs pip itself, and then runs the user's command with it. Later runs go to the installed pip directly.

The PEP does not add pip's implementation to the standard library. It does not add any package management or installation mechanism beyond those defined by PEP 427 ("The Wheel Binary Package Format 1.0") and [TODO: name and number of the distlib PEP].

## Motivation

A new Python user who wants a third-party module is usually told to run `pip install <name>`. On a fresh Python installation, that command fails, because pip is not installed. The user then has to find installation instructions for pip, which have involved downloading and running a script, or installing `setuptools` first. This step is where new users are most likely to give up or to follow outdated advice. It also makes documentation harder to write: a tutorial that uses a third-party module has to explain installing pip before it can explain installing the module.

Bundling pip in the standard library would remove the step, but would tie pip's release cycle to Python's. pip changes faster than Python, and a pip frozen into a Python release would age while the packaging ecosystem moved on. The bootstrap is the narrower option. It puts a command named `pip` on the user's path from the start, so the instruction "run `pip install <name>`" works. The pip that runs is fetched at that moment, so it is current.

## Specification

### What is installed

The Python installer places a bootstrap script named `pip` in the same directory as other Python scripts, such as `pydoc`. On Windows this directory is `Scripts`. The bootstrap is a small Python module in the standard library, with the script as its entry point. [TODO: name the module.] The module contains only the logic in this section.

### First run

When the user runs `pip` and pip is not installed, the bootstrap does the following:

1. Check whether `pip` can be imported. If it can, hand the command line to it and stop.
2. Find the newest release of pip on the Python Package Index (PyPI), in wheel format.
3. Download the wheel, and the wheel of each of pip's dependencies, if any.
4. Verify the downloads (see "Security").
5. Install the wheels with the wheel installer from [TODO: the distlib PEP]. This installer unpacks a wheel into a target directory as PEP 427 specifies. It does not resolve dependencies or build from source.
6. Import the newly installed pip and run the user's original command line with it.

After the first run, step 1 succeeds and the bootstrap passes control straight to pip. The bootstrap stays on the path. Once pip is installed, the installed `pip` script and the bootstrap script must not compete for the same name. [TODO: decide which script wins, and how the bootstrap is replaced or shadowed.]

### Install location

The bootstrap installs pip into the location where the user can write without elevated privileges:

1. If the Python installation's `site-packages` directory is writable by the user, install there.
2. Otherwise, install into the user site directory defined by PEP 370.

## Security

The bootstrap downloads code and runs it, on the user's machine, with the user's privileges. A network attacker who can substitute the download controls the user's account. This is the hardest part of the design and it needs the most care.

The bootstrap downloads only over HTTPS and verifies the server certificate against the system's certificate store. ## Backwards compatibility

Users who have installed pip already see no difference, because the bootstrap hands control to the installed pip at step 1. [TODO: check what happens when pip is installed in a location the bootstrap does not import from, such as a different user site directory.]

Systems where a distribution package manager provides a `pip` command may get two scripts with the same name. [TODO: consult distribution packagers about whether they want the bootstrap installed, and how they would disable it.]

## Drawbacks

The first `pip` command needs network access and takes longer than later ones. A user without network access gets an error on that first run, which they would not get if pip were bundled.

The design makes the Python installer depend on PyPI being available and serving pip as a wheel. If PyPI is down, new users cannot install pip.

The bootstrap adds a component that has to be kept in step with pip's own installation layout. A change to how pip is packaged may require a change to the bootstrap, which then ships only with the next Python release.

## Open questions

The two decisions that most affect users are whether the bootstrap verifies anything beyond the TLS certificate, and where it installs pip when the system `site-packages` is not writable. Both are open, and the first one needs input from people responsible for PyPI's infrastructure.
