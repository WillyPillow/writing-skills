# PEP 383: Non-decodable bytes in system character interfaces

## Abstract

POSIX defines file names, environment variables and command-line arguments as character data, but its C APIs pass them as arbitrary byte strings, whether or not those bytes are valid in any particular encoding. Python 3 presents these values as `str`. When a value cannot be decoded with the file system encoding, Python must either fail, skip the value, or represent it some other way. This PEP proposes decoding such values so that each byte that cannot be decoded is embedded in the resulting string as a reserved code point, and encoding them back so that the original byte string is recreated exactly.

## The problem

On a POSIX system, a file name is a sequence of bytes that excludes `/` and NUL. The kernel does not check those bytes against any encoding. A directory can contain a file named with Latin-1 bytes alongside files named in UTF-8, for example because the file was created by an older program, copied from another system, or extracted from an archive.

Python 3 decodes such values with the file system encoding to present them as `str`. If the encoding is UTF-8 and a file name contains the byte `0xE9` on its own, decoding fails. The interpreter then has no good choice:

1. Raising an exception makes a whole directory listing fail because of one name.
2. Silently omitting the value makes files invisible. A program that lists a directory and then deletes "every file" would leave the omitted ones.
3. Replacing the byte with U+FFFD produces a string that cannot be encoded back to the original name, so the program can display the file but cannot open, rename or delete it.

The same problem applies to `os.environ` and `sys.argv`. A command-line argument that is not valid in the locale's encoding is a file name the user typed, and the program should be able to pass it to `open()`.

## Goal

Any byte string that the operating system returns through these interfaces can be converted to `str` and back to the identical byte string. A program that works only with `str` can then list, open, rename and delete every file, read every environment variable, and pass every argument on to another process, with no special cases.

A second goal follows from the first. Values that decode correctly must decode exactly as they do today. The new mechanism changes only the values that currently fail.

## Specification

### Decoding

This PEP adds a codec error handler, called `bytesescape` here [TODO: confirm the name]. When decoding with this handler, each byte that the codec cannot decode is replaced by the code point U+DC00 plus the byte's value. The byte `0xE9` becomes U+DCE9. Bytes that decode correctly are decoded normally.

Under this rule, a byte with a value of 128 or more maps into the range U+DC80 to U+DCFF. Bytes below 128 are ASCII. ### Encoding

When encoding with the same handler, each code point in U+DC80 to U+DCFF that the codec cannot encode is replaced by the single byte whose value is the code point minus U+DC00. Encoding the string produced in the example above gives back the byte `0xE9`.

### Why lone surrogates

The code points U+D800 to U+DFFF are surrogates. In UTF-16 they occur only in pairs, high then low, to encode characters outside the Basic Multilingual Plane. A lone low surrogate is not a valid character, and a conforming UTF-8 decoder never produces one. A string produced by correctly decoding valid data therefore never contains one of the code points the handler uses, so the two kinds of content cannot be confused when encoding back.

### Where the handler is used

On POSIX systems, the interpreter uses the new handler whenever it decodes or encodes a value of these kinds with the file system encoding:

- file names returned by `os.listdir` and similar functions, and file names passed to `open()`, `os.stat`, `os.rename` and other functions that accept paths;
- environment variables in `os.environ`, and values written back to it;
- command-line arguments in `sys.argv`.

## Consequences for programs

Strings produced by the new handler contain code points that are not characters. Most string operations handle them without trouble: they can be compared, concatenated, sliced, and used as dictionary keys. Problems appear when such a string leaves the program through a channel that does not use the new handler.

Printing a file name that contains an escaped byte to a UTF-8 terminal with the default strict error handler raises `UnicodeEncodeError`. Writing it into a UTF-8 text file does the same. A program that displays file names must therefore decide how to show the undecodable bytes. [TODO: whether the PEP proposes any change to how `print()` or `sys.stdout` handle these code points.]

Comparing a decoded file name with a string literal works as expected for names that decode correctly. For a name that does not, no literal written in source will match it unless the programmer writes the escaped code points explicitly.

## Costs

The mechanism makes `str` carry values that are not text. Code that assumes every `str` is valid Unicode can fail later and far from the source of the value. For example, a library that encodes strings to UTF-8 for a network protocol can raise `UnicodeEncodeError` on a file name it received from `os.listdir`. Today, the error occurs inside `os.listdir`, or the value is never returned at all.

The behaviour depends on the file system encoding. The same byte string can decode differently on two systems with different locales. This is true today for names that decode successfully, and the PEP does not change it.

## Backwards compatibility

For values that decode successfully, the result is the same as before. For undecodable values, functions that previously raised an exception, omitted the value, or returned a lossy replacement will now return a string with escaped bytes.
