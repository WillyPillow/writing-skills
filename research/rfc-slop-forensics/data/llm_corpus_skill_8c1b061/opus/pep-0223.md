PEP: 223
Title: Change the Meaning of ``\x`` Escapes
Status: Draft
Type: Standards Track

# Abstract

This PEP changes `\x` escapes, in both 8-bit and Unicode string literals, so that each one consumes exactly the two hex digits that follow it. The current rule is treated here as a design flaw. The change makes string literals easier to read, gives Unicode literals a consistent set of escapes, brings `\x` closer to Perl's regular expression syntax, and carries a small risk to existing code.

# The current rule

Today a `\x` escape consumes every hexadecimal digit that follows it, however many there are. [TODO: confirm how the resulting value is reduced to fit the string's character size, for example by keeping only the low 8 bits in an 8-bit string and the low 16 bits in a Unicode string.]

This rule came from C, where `\x` is also greedy. The following literals show what it does in practice:

    "\x41"        one character, 'A'
    "\x41BC"      one character: the escape consumes "41BC", not "41"
    "\x41" "BC"   three characters, 'A', 'B', 'C'

The second literal is the problem. A programmer who writes an escaped byte followed by text that happens to begin with a hex digit (any of `0-9`, `a-f`, `A-F`) gets one character instead of several, and no error tells them so. The usual workaround is the third form, splitting the literal so that the escape ends where the literal ends. # Proposal

A `\x` escape consumes exactly two hexadecimal digits. The escape `\xhh` denotes the character with ordinal `0xhh`.

    "\x41BC"      three characters, 'A', 'B', 'C'
    u"\x41BC"     three characters, u'A', u'B', u'C'

If fewer than two hexadecimal digits follow `\x`, the literal is invalid and the compiler raises an error. [TODO: decide whether this is `SyntaxError` or `ValueError`, and whether the error message gives the position of the escape.]

    "\x4"         error
    "\x4G"        error

In Unicode literals, characters above `0xFF` are written with the existing `\uXXXX` escape, which consumes exactly four digits. `\x` in a Unicode literal therefore covers the range `0x00` to `0xFF` only.

The change applies to string literals in source code and to the `unicode-escape` and `string-escape` codecs, so that a string read with `eval` and a string decoded by the codec agree. # Rationale

## Readability

Under the proposed rule, a reader can find the end of every `\x` escape by counting two characters. Under the current rule, the reader must scan forward until the first non-hex character, and must know which letters are hex digits. In `"\xffee"` the current rule produces one character; in `"\xffgg"` it produces three. The two literals look alike but differ in length.

## A consistent set of escapes in Unicode literals

Unicode literals currently have two escapes for character codes. `\uXXXX` takes exactly four digits, and `\x` takes any number. A reader who knows `\u` will expect `\x` to have a fixed width as well. Making `\x` a fixed width of two gives both escapes the same kind of rule, differing only in width: `\x` for codes up to `0xFF` and `\u` for codes up to `0xFFFF`.

The current rule also produces different values for the same literal in the two string types. Under the truncation rule described above, `"\x0141"` and `u"\x0141"` keep different numbers of low bits and so denote different characters. ## Perl regular expressions

Python's `re` module follows Perl's regular expression syntax closely. In a Perl regular expression, `\x` takes at most two hex digits, and a longer code is written `\x{...}`. A Python string literal holding a regular expression copied from Perl may contain `\x` escapes followed by hex-digit characters, and today Python reads those escapes differently from Perl.

# Risk to existing code

The change alters the meaning of a literal only when a `\x` escape is followed by three or more hex digits. A literal with exactly two digits after each `\x` means the same thing before and after.

Code that writes `\x` with one digit, such as `"\x0"`, becomes invalid. Such code fails at compile time, so it cannot change behavior silently.

Code that writes `\x` with three or more digits changes meaning silently. This is the case that matters. Such literals are of two kinds:

1. Literals where the writer intended a two-digit escape followed by text. These are bugs today, and the change fixes them.
2. Literals where the writer relied on the greedy rule, such as `"\x000041"` meaning `'A'`. These change meaning.
