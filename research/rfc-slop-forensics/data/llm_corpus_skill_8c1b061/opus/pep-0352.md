# Abstract

In Python 2.4 and earlier, any classic class, or instance of one, can be raised as an exception. Python 2.5 was planned to allow new-style classes as well. That would let any class or instance at all be raised, so no code could rely on any attribute or method of a caught exception.

This PEP proposes a new built-in class, `BaseException`, and requires every raised object to be an instance of it. The requirement gives exceptions a standard interface that code can rely on, and a single hierarchy that all exceptions belong to.

# Motivation

Consider a logging helper that records any exception passed to it:

```python
def log_failure(exc):
    log.error("failed: %s (%r)", exc, exc.args)
```

The helper assumes that `exc` has an `args` attribute. For built-in exceptions that holds, because they all inherit from `Exception`. For a user-defined classic class that does not inherit from `Exception`, it does not:

```python
class Abort:
    pass

try:
    raise Abort
except Abort, e:
    log_failure(e)    # AttributeError: Abort instance has no attribute 'args'
```

Python accepts `raise Abort` today because `Abort` is a class. If new-style classes become raisable without further restriction, `raise object()` and `raise SomeUnrelatedType()` would be accepted too. A handler written as `except:` or as a catch-all at the top of a program then receives an object about which it can assume nothing. Error-reporting code in frameworks and in the standard library must either check each attribute with `hasattr` or risk raising a second exception while handling the first.

The language already treats exceptions as a separate kind of object. They are raised and caught by special statements, they carry a traceback, and handlers select them by class. Requiring them to share a base class makes that distinction part of the type system, where code can check it with `isinstance`.

One might counter that requiring a specific base class for an interface is unPythonic, since Python code usually relies on duck typing. # Specification

## The new base class

A new built-in class `BaseException` is added. It is a new-style class. Its interface is:

```python
class BaseException(object):
    def __init__(self, *args):
        self.args = args

    def __str__(self):
        ...

    def __repr__(self):
        ...
```

`args` is the tuple of arguments passed to the constructor. `str()` of an exception returns the empty string when `args` is empty, `str(args[0])` when `args` has one element, and `str(args)` otherwise. This matches what `Exception` does today, so existing exception classes keep their string form. `repr()` returns the class name followed by the `args` tuple.

## The raise rule

`raise X` and `raise X, value` succeed only when `X` is a subclass or an instance of `BaseException`. Raising anything else raises `TypeError` instead. The same rule applies to the throw method of generators.

`except` clauses are not changed by this rule. An `except C:` clause still matches when the raised object is an instance of `C` or one of its subclasses. Since every raised object is now a `BaseException`, `except BaseException:` catches everything that a bare `except:` catches.

## The hierarchy

`Exception` becomes a subclass of `BaseException`. All existing built-in exceptions remain subclasses of `Exception`, except `KeyboardInterrupt` and `SystemExit`, which become direct subclasses of `BaseException`.

```text
BaseException
 +-- KeyboardInterrupt
 +-- SystemExit
 +-- Exception
      +-- (all other built-in exceptions, unchanged)
```

The two classes move because a program raises them to stop, not to report an error. Code that writes `except Exception:` to handle "any error" should not prevent the user from interrupting the program with Ctrl-C, or prevent `sys.exit()` from exiting. Under the current hierarchy, both are caught by `except Exception:`, and the only way to avoid that is to list them in an earlier clause. After the move, `except Exception:` handles errors, and `except BaseException:` or a bare `except:` handles everything.

User-defined exceptions should inherit from `Exception`, not from `BaseException`. `BaseException` is meant for the few classes that a normal `except Exception:` handler should let through. The documentation for both classes says so.

# Transition plan

The rule cannot be enforced at once, because existing code raises classic classes that do not inherit from `Exception`, and some code still raises strings. The transition runs over several releases:

1. Python 2.5 adds `BaseException`, makes `Exception` its subclass, and moves `KeyboardInterrupt` and `SystemExit`. New-style classes may be raised only if they inherit from `BaseException`. Raising a classic class that does not inherit from `BaseException` still works.

3. Python 3.0 enforces the rule. Raising any object that is not a `BaseException` raises `TypeError`, and string exceptions are removed.

# Backwards compatibility

Three kinds of existing code are affected.

Code that raises a classic class not derived from `Exception` keeps working in 2.5, warns in a later 2.x release, and fails in 3.0. The fix is to add `Exception` to the class's bases.

Code that writes `except Exception:` and relies on it to catch `KeyboardInterrupt` or `SystemExit` changes behavior in 2.5. Such code now lets those two exceptions propagate. Code that intends to catch them must name them, or use `except BaseException:`. Code that inspects the hierarchy, for example by testing `issubclass(KeyboardInterrupt, Exception)`, gets a different answer.

Code that only raises and catches subclasses of `Exception` is not affected by the new rule or by the move.
