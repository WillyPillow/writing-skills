# PEP 346: User defined ("`with`") statements

## Abstract

PEP 310 proposed a statement that pairs an acquire step with a release step, so that a resource is always released when a block of code exits. PEP 340 proposed anonymous block statements, in which a generator controls the execution of a block and can run code before and after it. This PEP combines the two. It keeps the one-shot acquire/release structure of PEP 310 and adds the ability, taken from PEP 340, to write the acquire and release code as a single generator. It borrows smaller pieces from other PEPs where they are needed, and is written to stand on its own, so that a reader need not consult PEP 310 or PEP 340 to understand it.

## Motivation

A common pattern in Python is to acquire a resource, use it, and release it, with the release guaranteed even if the use raises an exception. Today this is written with `try`/`finally`:

```python
lock.acquire()
try:
    update_shared_state()
finally:
    lock.release()
```

The pattern is correct but verbose, and the boilerplate is the same each time. The acquire call must be placed before the `try` and not inside it, or a failed acquire leads to a release of a lock that was never held. Each use repeats that detail, and each repetition is a chance to get it wrong. [TODO: instances of this mistake in real code, if the author has them.]

Some resources need more than a pair of calls. A database transaction must commit if the block succeeds and roll back if it raises. With `try`/`finally` alone, the code must catch the exception, roll back, and re-raise, and the logic is again repeated at every use.

A user-defined statement lets the author of a resource write the pattern once, and lets each user of the resource write only the block.

### Semantics

The statement

```python
with EXPR as VAR:
    BLOCK
```

is executed as follows:

1. Evaluate `EXPR` to obtain an object, called the manager.
2. Call the manager's `__enter__()` method. If the `as` clause is present, assign the result to `VAR`.
3. Execute `BLOCK`.
4. Call the manager's `__exit__()` method, however `BLOCK` was left: normally, by an exception, or by `break`, `continue` or `return`.

If `BLOCK` raised an exception, `__exit__()` receives the exception type, value and traceback. Otherwise it receives three `None` arguments. If `__enter__()` raises an exception, `BLOCK` is not executed and `__exit__()` is not called. This matches the `try`/`finally` pattern above, in which a failed acquire is not followed by a release.

The block runs once. Unlike the anonymous block statement of PEP 340, this statement is not a loop. ### Generator-based managers

Writing a class with `__enter__()` and `__exit__()` methods for every resource is itself boilerplate. Following PEP 340, this PEP allows a manager to be written as a generator that yields exactly once:

```python
@statement_template
def locked(lock):
    lock.acquire()
    try:
        yield
    finally:
        lock.release()
```

The decorator wraps the generator in a manager object. `__enter__()` advances the generator to its `yield` and returns the yielded value. `__exit__()` resumes the generator. If the block raised an exception, the exception is raised inside the generator at the point of the `yield`, so the generator's own `try`/`finally` or `try`/`except` handles it. With this manager, the lock example becomes:

```python
with locked(lock):

```

The transaction example can be written as one generator that commits after the `yield` and rolls back in an `except` clause around it. The author of the transaction manager writes the commit/rollback logic once, and each use is a two-line `with` statement.

## Rationale

The main design question is how much of PEP 340 to keep. PEP 340's block statement is general: a generator can run the block once, many times, or not at all. That generality makes the statement useful for more than resource management, but it also makes a reader of a block unable to tell, without reading the generator, whether the code inside runs once. [TODO: the author's reason for limiting the statement to one execution. The paragraph above gives a cost of the general form, but whether it was the deciding reason must come from the author.]

The second question is whether to support classes, generators, or both as managers. Classes give full control and need no new generator machinery. Generators let a resource be described in the order a reader expects: set up, run the block, tear down. This PEP supports both, with generators converted to the class protocol by a decorator, so that the statement itself sees only one protocol.

## Costs
