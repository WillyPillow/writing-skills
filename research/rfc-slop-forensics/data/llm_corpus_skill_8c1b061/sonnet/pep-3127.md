# PEP 3127: Integer Literal Support and Syntax

## Abstract

This PEP proposes changes to the Python core to make the handling of integer literals in different radices (bases) consistent. The changes target Python 3.0. The backward-compatible parts should also go into Python 2.6, so that every valid 3.0 integer literal is also valid in 2.6. The proposal has three parts:

a) Octal literals are written with a leading `0o` or `0O` instead of a leading `0`.
b) Binary literals are supported through a leading `0b` or `0B`.
c) String formatting gains support for binary numbers.

## Motivation

Python has literal forms for decimal, octal and hexadecimal integers. Decimal has no prefix, hexadecimal has `0x` or `0X`, and octal has a leading `0`. Compare the three:

```python
255      # decimal
0xff     # hexadecimal
0377     # octal
```

The first two are distinguished by a letter. The third differs from a decimal literal only by a leading zero, with no marker that a different radix is in use. A reader sees `0377` and can easily take it as 377. A programmer who pads a column of decimal numbers with zeros to line them up changes their value without any error:

```python
a = 10
b = 010   # this is 8, not 10
```

The second line is valid and means eight. If the digits `8` or `9` appear, as in `089`, the literal is a syntax error, which at least reveals the problem, but `010` hides it.

The title of the PEP and its first sentence describe the aim as "rationalizing" the treatment of radices. The relevant point is that two of three literal forms have a prefix that names the radix, and the third does not. Giving octal a prefix removes the exception.

## Specification

### Octal

An octal literal starts with `0o` or `0O`, followed by one or more octal digits (0 to 7). A literal such as `0o377` has the value 255. A leading `0` without the `o` is no longer valid as an octal literal in Python 3.0. [TODO: the abstract says octal literals "must now be specified with" the new prefix. ### Binary

A binary literal starts with `0b` or `0B`, followed by one or more binary digits (0 and 1). `0b1010` has the value 10.

## Compatibility with Python 2.6

The abstract divides the changes into two groups. The backward-compatible parts go into 2.6, and the rest go only into 3.0. The stated aim is that "all valid 3.0 integer literals will also be valid in 2.6."

This aim has a precise reading. Every literal that a 3.0 program can contain must also parse in 2.6. The new octal prefix `0o377` and the binary prefix `0b1010` are new syntax in 2.6, and they are accepted in addition to the old forms. The old leading-zero form stays valid in 2.6 and is rejected in 3.0. A program that uses only the new forms therefore runs on both versions, as far as literals go.

The practical consequence is a migration path. A project can switch to `0o` literals while it is still on 2.6, before moving to 3.0. A tool that converts 2.x code to 3.x can rewrite leading-zero literals mechanically. [TODO: the abstract does not mention a conversion tool. The incompatible part is the removal of the old octal form in 3.0. Code that contains a literal such as `0644`, for example a file-permission mode, is affected. ## Rationale

The abstract's rationale is consistency. A reader should be able to tell the radix of an integer literal from its first two characters.

The case against the change is that it breaks existing source in 3.0, in exchange for removing a trap whose frequency the PEP does not measure. The PEP's answer is that 3.0 is the release in which incompatible changes are expected, and that 2.6 lets code migrate in advance.

## Summary of the decision

The PEP asks for two syntax changes, and one library change. The new octal prefix removes the exception among the three radix forms, and the cost is the breakage of leading-zero octal literals in 3.0. The binary literal adds a form that did not exist. The material supports the consistency argument and supplies no measurement of how often the old form causes bugs or how much code it would break.
