# PEP 504: Using the System RNG by default

## Abstract

The module-level functions of Python's `random` module, such as `random.random()` and `random.choice()`, use the Mersenne Twister generator, which is deterministic and not cryptographically secure. Code that needs unpredictable values for security must instead call `os.urandom`, use `random.SystemRandom`, or use a third-party library such as `cryptography`. Developers who do not know their work is security sensitive use the default functions and expose their users to risk.

This PEP proposes to change the default behavior of the module-level API so that the safe choice is the one that needs no knowledge. The deterministic generator stays available for code that wants reproducible sequences. ## Problem

The `random` module serves two groups of users who want opposite properties. Simulations, games, tests and sampling want a fast generator that gives the same sequence for the same seed. Security code, such as session tokens, password reset links and nonces, wants values an attacker cannot predict even after seeing earlier outputs.

Mersenne Twister meets the first need and fails the second. Its internal state can be reconstructed from observed output. [TODO: add a citation for the state-recovery property, supplied by the author.] An attacker who recovers the state can predict every later value.

Python's answer today is documentation: the `random` module page warns that it should not be used for security purposes and points to `os.urandom` and `random.SystemRandom`. The remedy depends on the developer knowing that their work is security sensitive and reading that warning.

This is the gap the PEP targets. A developer writing a function that generates a password reset token may not think of it as "security sensitive work". The function looks like string handling. The developer reaches for `random.choice` over an alphabet, because it is the most visible tool, and the result is a predictable token.

## Why this is a chronic problem

The PEP describes the problem as chronic, not acute. No single failure is urgent. The flaw sits quietly in working code, and exploitation can come long after the flaw was introduced.

That delay matters for how developers learn. A bug that crashes on the first run teaches the developer at once. A predictable token produces correct output on every test. No feedback arrives until an attacker uses the weakness, which may be years later and may be reported to someone other than the original author. The developer cannot learn from experience, because the experience never reaches them.

This argues against relying on education alone. More documentation helps those who read it. It does not help those who have no reason to look.

The design has to answer one question first: what should an unqualified call to `random.random()` do? Two answers are possible.

1. Keep the call fast and deterministic, and make it hard to use for security by accident. Methods include a warning on security-looking use, or a separate, explicitly named API for secure values.
2. Make the unqualified call secure, and require an explicit opt-in, such as constructing a `random.Random` instance, for the deterministic generator.

## Decisions and their costs

### Changing the default instead of documenting harder

The force is that developers do not know their code is security sensitive, so documentation they have not read cannot protect them. Changing the default protects them regardless. The cost falls on the users who wanted determinism, who must now say so. [TODO: ask the author what else was considered, for example a new `secrets`-style module promoted more heavily. ### Keeping the deterministic generator available

Reproducible simulation and testing are legitimate and common uses. Removing the deterministic generator would break them with no safe replacement. The PEP therefore keeps it, behind an explicit choice. Reversibility is high for this decision, since adding the explicit API is additive.

### The default-change itself

This decision is expensive to undo. Once a release has shipped code that relies on secure defaults, changing back would silently reintroduce the flaw. It deserves the most review. [TODO: ask the author whether a deprecation period with warnings is part of the plan, and for how long.]

## Security considerations

The proposal reduces one class of mistake: choosing a predictable generator for unpredictable data. It does not make Python code secure. A developer who writes a bad protocol using good random numbers is still unsafe. It also does not change third-party libraries that carry their own generators.
