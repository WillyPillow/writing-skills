# PEP 400: Deprecate codecs.StreamReader and codecs.StreamWriter

## Abstract

`io.TextIOWrapper` and `codecs.StreamReaderWriter` offer the same API [1]. `TextIOWrapper` has more features and is faster than `StreamReaderWriter`. Duplicate code means that bugs should be fixed twice and that we may have subtle differences between the two implementations. The `codecs` module was introduced in Python 2.0 (see PEP 100). The `io` module was introduced in Python 2.6 and 3.0 (see PEP 3116), and reimplemented in C in Python 2.7 and 3.1.

This PEP proposes to deprecate `codecs.StreamReader` and `codecs.StreamWriter`, and to document that `io.TextIOWrapper` is the supported way to read and write encoded text streams.

## Motivation

Python has two classes that wrap a binary stream and present a text stream with an encoding. One lives in `codecs` and is built from `StreamReader` and `StreamWriter`. The other lives in `io` and is `TextIOWrapper`. A user who opens a file with `open()` in text mode gets a `TextIOWrapper`. A user who calls `codecs.open()` gets a `StreamReaderWriter`.

The two classes answer the same need. They were written at different times. `codecs` came first, in Python 2.0. The `io` module arrived with Python 2.6 and 3.0, and its text layer is the one that `open()` uses. In Python 2.7 and 3.1 `io` was reimplemented in C.

Two classes with one job cost the project in three ways.

1. A bug in the shared behavior has to be fixed in both places. A fix that lands in one and not the other leaves a difference that users discover later.
2. The two implementations drift. Where they differ, a user who switches from one to the other gets a different result for the same input, and the difference is not documented as a choice.
3. The `codecs` classes are slower. [TODO: the abstract states that `TextIOWrapper` is faster but gives no measurement; add the benchmark and its conditions, or reduce this to a statement that the difference was observed by the author.]

## Rationale

The aim is one supported class for the job. Between the two, `TextIOWrapper` is the one `open()` already returns, it has the faster implementation, and it has the larger feature set. Keeping `StreamReaderWriter` alive adds maintenance work and gives users a worse tool.

Deprecation is a smaller step than removal. It tells users to move, and it leaves existing programs running. That fits a class that may have users the project cannot see. [TODO: ask the author whether any survey of use in the wild, such as a code search, was done.]

## Specification

### What is deprecated

The following become deprecated:

- `codecs.StreamReader`
- `codecs.StreamWriter`
- `codecs.StreamReaderWriter`
- `codecs.open()`, which constructs a `StreamReaderWriter`

### How deprecation shows

The deprecated names emit a `DeprecationWarning` when used. Python hides this warning by default outside of `__main__` and test runners, so most end users of a library will not see it, while the developer who runs the test suite will.

The codecs themselves stay. The functions that look up and register codecs, and the `encode` and `decode` functions of each codec, are not touched. ## Alternatives

**Leave both classes in place.** This is the status quo. It keeps duplicate code and the repeated-fix burden described above. The author's reason to reject it is the maintenance cost.

**Make `StreamReaderWriter` a thin wrapper around `TextIOWrapper`.** This would remove the duplicate code without telling users to change. It would only work if the behavior of the two matched, and the PEP records that they have subtle differences. [TODO: ask the author whether this option was considered. **Remove the classes outright.** This is the cheapest in maintenance and the most disruptive. [TODO: ask the author whether removal was considered and whether any release window was discussed.]
