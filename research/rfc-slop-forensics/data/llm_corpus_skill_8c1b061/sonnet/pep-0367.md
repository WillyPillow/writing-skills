# PEP 367: New Super

## Abstract

This PEP proposes syntax that lets a method call its parent's implementation without naming its own class or its instance. The proposed form is:

```python
super.foo(1, 2)
```

It replaces the current form:

```python
super(Foo, self).foo(1, 2)
```

The existing `super` type stays available under the name `__super__`. The name `super` in the builtin namespace is to be removed in Python 3.0, so that `super` refers to the new construct. Assigning to `super` becomes a `SyntaxError`, as assignment to `None` already is.

## Motivation

A method that extends its parent's behavior must reach the parent's version. Python spells that call with the `super` type, and the call takes two arguments: the class in which the method is defined, and the object (or class, for a classmethod) on which it acts.

```python
class Foo(Base):
    def foo(self, a, b):
        return super(Foo, self).foo(a, b)
```

Both arguments are already known where the call is written. The method sits inside the body of `Foo`, and `self` is its first parameter. The programmer restates facts the compiler can see.

That restatement causes three kinds of trouble.

1. The class name appears inside its own methods. Renaming the class means editing every `super(Foo, self)` call. A missed edit leaves a call that names the wrong class, which may still run and bind to a different parent.
2. Copying a method into another class carries the old class name with it. The call then looks up the parent of the original class, not of the new one. [TODO: add one real incident or code-review example from the author's material. Without it, this point rests on the reader's own experience.]
3. The call is long, and it breaks the reading flow of the method it appears in. [TODO: this is a style claim. State it as the author's judgment, or support it with the author's survey of existing code.]

The PEP proposes that the compiler supply the two arguments.

## Specification

### The new form

Inside a method, the expression `super` evaluates to a super object bound to two things:

* the class in which the method was defined, and
* the instance on which the method is running, or the class object when the method is a classmethod.

An attribute access on that object, such as `super.foo`, finds `foo` on the parents of the defining class, in method resolution order, and binds it to the instance. A call to the result behaves as `super(Foo, self).foo(...)` does today.

So `super.foo(1, 2)` means the same as `super(Foo, self).foo(1, 2)` when written in a method of `Foo`.

### Which class is "defined in"

The binding uses the class whose body contains the method definition, not the class of the instance. This is the same distinction the two-argument form already makes, and it is what makes cooperative multiple inheritance work: each class in the chain calls the next one after itself, not after the instance's own class. ### Assignment

Assignment to `super` is a `SyntaxError`, the same rule that applies to `None`. The reason is that `super` is no longer an ordinary name that code can rebind, because the compiler gives it special meaning inside methods. ## Rationale

### Why syntax and not a library function

A library function, such as a helper that inspects the call stack to find the caller's class and instance, is possible without a language change. Stack inspection is slower than a direct reference, and it breaks when a method is wrapped by a decorator that changes the frame. The compiler is the one place that reliably knows the defining class. ### Why not keep the old name for the old form

If `super` kept its current meaning, the new form would need a different name. The PEP instead reuses `super` and moves the old type to `__super__`. ### Why `super.foo` and not `super().foo`

Using an attribute directly on the name looks like a lookup on the parent class. A call form, `super()`, would read as constructing an object and would suggest the same two-argument form with arguments omitted. ## Costs

The proposal removes a builtin name and changes the meaning of the same name. Python 2 programs using `super(Foo, self)` must change when they move to 3.0. In exchange, new programs get a form with no class name in it.

The compiler must track the defining class for every method, which adds a hidden reference to each function. [TODO: measure or estimate the memory cost on a large codebase. No figure is available, so the PEP makes no performance claim.]

Making `super` special also adds a rule to the language that learners must meet: the name looks like a plain object but behaves like syntax. A reader who has not seen the PEP may expect `super` to be an ordinary class they can pass around, and will find that it cannot be assigned or used outside a method in the same way.

## Reversibility

The `SyntaxError` on assignment and the removal of the builtin are the hardest parts to reverse. Once programs depend on `super` meaning the new construct, restoring the old meaning would break them in the opposite direction. The added `__super__` alias is easy to keep or drop.
