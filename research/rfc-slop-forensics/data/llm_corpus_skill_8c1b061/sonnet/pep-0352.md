# PEP 352: Required Superclass for Exceptions

## Abstract

In Python 2.4 and before, any classic class can be raised as an exception. The plan for 2.5 was to also allow new-style classes. That plan makes the situation worse, because any class or instance could then be raised. This PEP proposes a new superclass that every raised object must inherit from. With that restriction, exceptions can have a standard interface that code can rely on, and a known hierarchy.

## Motivation

Consider code that catches an exception and wants to report it:

```python
try:
    run()
except:
    log(sys.exc_info()[1])
```

The handler receives some object. What can it do with that object? In Python 2.4 the answer is almost nothing. `raise "oops"` raises a string. `raise 42` is an error today, but `class Spam: pass` followed by `raise Spam()` works, because classic instances can be raised. Each of these has a different set of attributes. A string has no `args`, no `__str__` beyond itself and no traceback link. An instance of an arbitrary class may have any attributes at all.

So the handler cannot assume that `str(exc)` is a message, that `exc.args` exists, or that the object belongs to any family of exception types. A library that wants to add a standard attribute to all exceptions, for example one that records the cause, cannot do so, since nothing says which objects it would add the attribute to.

The plan for 2.5 was to allow new-style classes as exceptions. A new-style class inherits from `object`, and `object` is the base of every class, so the plan lets any class or instance be raised. This widens the set of raisable objects when what the language needs is a narrower set with a guaranteed interface.

## The proposal in outline

Introduce a base class, `BaseException`, with a defined interface. Make the existing exception base class, `Exception`, a subclass of it. Over time, require that every object passed to `raise` be an instance of a class that inherits from `BaseException`. The restriction is introduced in stages so that existing code has time to move.

### The hierarchy

The abstract states that the change "leads to a known hierarchy for all exceptions to adhere to." A hierarchy matters because of the way `except` clauses work. An `except Exception:` clause today catches most errors, but it also catches things that a program may want to let through, such as a request to exit. A single known root allows the standard library to place such cases deliberately in the tree.

The rule is that the object given to `raise` must be an instance of a class that derives from `BaseException`, or such a class itself. ## Rationale

The case for a required superclass rests on a stated goal: guarantees about the interface of what is caught. A guarantee of this kind needs the set of raisable objects to be described by something the interpreter can check. Inheritance from a specific class is the mechanism Python already has for that.

The abstract anticipates an objection: that requiring a particular base class for an interface goes against how Python usually works. Python tends to follow duck typing, which accepts any object that provides the methods needed and does not check what class the object comes from. The abstract replies that, for exceptions, "there's a good reason." The text of the abstract is cut off at that point and the reason is not in the material.

## Summary of the decision

The PEP asks for one change: require that every raised object inherit from a single base class. It gives a reason that rests on a stated goal, a standard exception interface, and the consequence is a known hierarchy. The cost is that code which raises strings or arbitrary classes must be changed. The size of that cost is not established in this document.
