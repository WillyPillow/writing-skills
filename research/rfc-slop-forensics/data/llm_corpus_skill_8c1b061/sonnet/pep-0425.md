# PEP 425: Compatibility Tags for Built Distributions

## Abstract

This PEP specifies a tagging system to indicate with which versions of Python a built or binary distribution is compatible. A set of three tags indicates which Python implementation and language version, ABI, and platform a built distribution requires. The tags are terse because they will be included in filenames.

## Motivation

A source distribution of a Python project works on any interpreter that can run its setup code, and the build happens on the user's machine. A built distribution has already been compiled or assembled, so it works only with interpreters that match how it was built. An installer that finds several built distributions of one project needs to know which of them, if any, it can use.

Without a machine-readable answer, the installer has two bad choices. It can try each distribution and see which fails, or it can rely on the project author's prose. Neither can be done before download. [TODO: ask the author whether the PEP is written against a specific existing situation, such as installers guessing from filenames, and what that situation is.]

The answer has to be available before the file is fetched, so it belongs in the filename. A tool that lists available files from an index can then pick the best match from the names alone. The size of the tags therefore matters: a filename that carries a long description of the build is unwieldy, and the abstract says that the tags are terse for that reason.

## Specification

### The three tags

A tag set has three parts:

1. The Python tag, which names the implementation and the language version.
2. The ABI tag, which names the application binary interface the compiled code expects.
3. The platform tag, which names the operating system and architecture.

A built distribution carries one value of each, or a set of values for each when it works in several configurations.

## Rationale

Three tags, instead of one, let the installer match each dimension independently. A distribution built for a specific implementation of Python on one platform still runs on any compatible ABI there, and the three tags let the installer tell which of the three conditions fails when a distribution does not match.

The tags are terse by design because filenames have length limits on some systems and are read by people. The cost of terseness is that a person reading a filename has to learn the abbreviations. [TODO: ask the author whether longer, self-describing tags were rejected and why.]

## Alternatives

**Put the compatibility information in a metadata file inside the archive.** This allows richer descriptions. The installer has to download the archive to read it, which defeats the purpose of choosing before download. [TODO: ask the author whether this was considered.]

**Use a single combined tag.** One tag would be shorter than three. It would give up independent matching of the three dimensions. [TODO: ask the author.]

**Leave naming to each project's convention.** This is the status quo for projects that publish several builds. Tools then need a rule per project. [TODO: ask the author.]
