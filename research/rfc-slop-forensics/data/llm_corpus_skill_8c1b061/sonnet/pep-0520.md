# PEP 520: Preserving Class Attribute Definition Order

## Abstract

The class definition syntax is ordered by its nature: attributes are written one after another in the class body. Aside from readability, that order is sometimes significant. If it were available outside the class definition, programs could use it without extra boilerplate such as metaclasses or manual enumeration of the attributes. The information already exists while the body runs, so access to it is a reasonable expectation. Python currently does not preserve the order after the class is created.

This PEP preserves the order in which attributes are introduced in the class definition body. The order is stored in a `__definition_order__` attribute on the class. ## Motivation

Some programs need to know the order in which a class body defined its attributes. A serialization library may want to write fields in the order the programmer declared them. A command-line framework may want to show options in declaration order. A table-definition tool may want columns in the order written. The material gives none of them by name, and they are listed here as plausible illustrations, not as documented demand.]

Today a program that needs the order has two choices. It can write a metaclass whose `__prepare__` method returns an ordered mapping, so that the class body records the order as it runs. Or it can ask the programmer to list the names again in a separate sequence, such as a `fields = ["a", "b"]` attribute. The first choice requires every class that wants the order to use a particular metaclass, and it conflicts with other metaclasses in the same hierarchy. The second makes the programmer state each name twice, and the two statements can drift apart. [TODO: the author's evidence, such as libraries that do this. No library is named in the material.]

The abstract's point is that the interpreter has the order at the moment it executes the body and then throws it away. Recording it costs little relative to the effort programs spend recovering it. ### Introspection

The attribute lets code read the original order from the class object. For a class `C`, the sequence `C.__definition_order__` lists the names in the order written. A tool can then iterate the names and fetch each value with `getattr`.

## Rationale

The PEP puts the order on the class instead of offering it through a hook or a helper function. The advantage of an attribute is that it is available to any code that holds the class, including code that did not write the class and cannot change its metaclass. [TODO: author to confirm this was the reasoning, and to state whether a helper function or an opt-in decorator was considered.]

The PEP does not ask the programmer to do anything. A class defined with no special syntax gets the attribute. That is the point of the proposal, and it is also its cost: every class carries the attribute whether or not anything reads it.

### Alternatives

The status quo is the baseline. Programs keep using metaclasses with ordered namespaces or repeat the names by hand. The PEP exists because these workarounds are, by the abstract's account, boilerplate.
