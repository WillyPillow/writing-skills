# PEP 383: Non-decodable Bytes in System Character Interfaces

## Abstract

POSIX defines file names, environment variables and command line arguments as character data. The C APIs for them accept arbitrary bytes, whether or not those bytes are valid in the user's locale encoding. A Python program that decodes such bytes into `str` can fail on a name it cannot decode, or lose information when it replaces undecodable bytes. This PEP proposes to embed each undecodable byte in the resulting character string in a way that lets the original byte string be recreated exactly.

## Motivation

Python 3 makes `str` the type for text. The standard library's file name functions, `os.listdir`, `os.getcwd`, `os.environ` and `sys.argv`, return `str` when given `str`. To produce a `str` from the bytes the operating system returns, the interpreter decodes them with the locale's encoding.

POSIX describes these values as characters, but the kernel does not enforce an encoding. A file system stores a file name as bytes without any check. A file created under a Latin-1 locale and listed under a UTF-8 locale yields bytes that are not valid UTF-8. Archive extraction and removable media can create the same mismatch. When decoding fails, a program has three choices today, none of them good.

1. Raise `UnicodeDecodeError`. A directory listing then fails because one entry is bad, and the program cannot reach the other entries.
2. Replace the bad bytes with a placeholder character. The program continues, but the name no longer refers to a file, so `open(name)` fails or opens a different file.
3. Skip the entry. The program continues, but the file is invisible to it.

All three break a requirement that file handling often has: a name read from the system must be usable to get back to the same file. The PEP states that requirement as the design goal. A name decoded and re-encoded must produce the original bytes.

* For every byte string the system returns, decoding produces a `str`, and encoding that `str` with the same procedure yields the original bytes.

## Specification

### The mapping

The PEP defines a decoding with an error handler that maps each undecodable byte to a single code point in a reserved range, and an encoding that maps those code points back to the original bytes. ## Rationale

### Why embedding rather than a second type

An alternative is to return `bytes` for names that cannot be decoded. That makes the return type depend on the content of the name, so every caller must handle two types. The embedding keeps one return type.

### Why map to code points that cannot occur in well-formed text

Mapping to ordinary characters would make a decoded undecodable byte indistinguishable from a legitimate character, and the encoder could not tell which bytes to restore. A reserved range solves this because no valid decoded text contains those code points. [TODO: this reasoning is the likely one, but the author's own justification is not in the available material. ## Consequences

### Accepted costs

A `str` produced this way may contain code points that are not valid in text. Encoding such a string with a normal codec such as UTF-8 raises an error. Programs that decode a name from the system, then write it to a UTF-8 file or send it over a network, will meet this error. The handler guarantees a round trip only when encoding goes back through the system interface. ### Reversibility

## Compatibility

Names that decode cleanly are unaffected. Names that fail to decode today raise an exception or are replaced. After the change, they decode to strings that contain mapped code points. A program that caught `UnicodeDecodeError` from a directory listing will no longer see that error. [TODO: the author should state whether any known code depends on the exception.
