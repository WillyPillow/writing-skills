# PEP 227: Statically Nested Scopes

## Abstract

This PEP adds statically nested scoping, also called lexical scoping, to Python 2.2, and as a source-level option to Python 2.1. In addition, Python 2.1 will issue warnings about constructs whose meaning may change when the feature is enabled.

## Background: the three namespaces

The language definition for Python 2.0 and before has exactly three namespaces for resolving names: local, global and built-in. A name used in a function is looked up first in the function's local namespace, then in the module's global namespace, then in the built-in namespace. No other namespace takes part. In particular, a function defined inside another function cannot see the enclosing function's local names.

## The problem

Nested scopes change what the following code means. Consider a function that returns a function:

```python
def make_adder(n):
    def add(x):
        return x + n
    return add
```

Under the three-namespace rule, `n` inside `add` is not local to `add` and not global, so the lookup fails with a `NameError` when `add` runs. The enclosing function's `n` is invisible.

The usual workaround is to bind the value through a default argument:

```python
def make_adder(n):
    def add(x, n=n):
        return x + n
    return add
```

The abstract notes this for lambdas: "Currently, lambdas must often use default arguments to explicitly creating bindings in the lambda's namespace." The same applies to any nested function. The default argument has side effects that the programmer did not intend. It adds a parameter to the signature, so the caller can overwrite the binding by passing a second argument, and the code has to repeat the name on both sides of `n=n`.

## The proposal

The proposal allows the resolution of names that are not local to go through the namespaces of the enclosing functions before it reaches the global namespace. After the change, the first example works: `n` is found in the namespace of `make_adder`.

The abstract describes the most visible consequence: lambdas, and other nested functions, can refer to variables defined in the surrounding namespace. The default-argument idiom is then unnecessary for the purpose of reading an outer variable, though code that uses it continues to run. [TODO: confirm that code using the idiom is not broken. The abstract does not say, and a nested function with a default argument of the same name as an outer variable is the case in point.]

The word "statically" in the title matters. The enclosing scopes are determined by where the function appears in the source text, not by the call stack at run time. A reader can tell which `n` is meant by looking at the nesting of `def` statements. This is the opposite of dynamic scoping, where the answer depends on who called the function.

## Transition: Python 2.1 and 2.2

The abstract states a two-step plan.

In Python 2.2 the feature is on. In Python 2.1 it is available as a source-level option, which means a module has to ask for it explicitly. [TODO: the abstract does not name the mechanism. The author should name it, for instance a `from __future__` statement, and describe its syntax.]

The reason for the option in 2.1 is that the feature changes the meaning of some existing programs. Consider this code:

```python
x = "global"

def f():
    x_value = "unused"
    def g():
        return x
    return g()
```

Under the old rules, `g` returns the global `x`. If `f` also had a local variable called `x`, `g` would return the enclosing function's `x` under the new rules, and its result would differ. The meaning of `g` changed without any edit to `g`. [This example is the writer's illustration of the kind of change the abstract refers to, and is not from the author's material.]

For these cases, Python 2.1 will warn. The abstract says it "will issue warnings about constructs whose meaning may change when this feature is enabled." A programmer therefore has a release in which to find and rename the affected variables before the behaviour changes in 2.2.

## Rationale

The case for the change rests on the workaround's cost: a default argument is a binding written for the interpreter's benefit, not the reader's. A nested function that mentions an outer variable by name is easier to read than one that copies the variable through its parameter list.

The case against it is that existing programs may mean something different after the change. The PEP answers this concern with the warning period and the source-level option. It does not remove the concern: code that is not touched during 2.1 and 2.2 can change meaning silently when the feature becomes the default.
