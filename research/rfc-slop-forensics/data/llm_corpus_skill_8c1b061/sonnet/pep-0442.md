# PEP 442: Safe object finalization

## Abstract

This PEP proposes to deal with the current limitations of object finalization. The goal is to be able to define and run finalizers for any object, regardless of their position in the object graph.

This PEP doesn't call for any change in Python code. Objects with existing finalizers will benefit automatically.

## Motivation

A finalizer is code that runs when an object is about to be destroyed. In CPython, a class defines one with the `__del__` method, and a C type defines one with a slot on the type object. Finalizers let an object release something it holds, such as a file or a lock, when nothing refers to it any more.

The difficulty arises when objects refer to each other in a cycle. CPython frees most objects by reference counting, and it uses a cycle detector for groups of objects that refer to each other and are otherwise unreachable. The detector must destroy such a group. If one object in the group has a finalizer, the order matters: a finalizer may use the other objects in the group, and those may already be gone. The current rule gives up on this case for objects with finalizers that sit in a cycle, and the group is left alive instead of destroyed. The effect is a leak. An object with a finalizer that takes part in a cycle is never finalized and never freed. Two consequences follow for programs.

1. Memory held by the group stays held for the life of the process.
2. The resource the finalizer would have released stays held too.

The goal of this PEP is that any object can have a finalizer, and that the finalizer runs once the object is found to be unreachable, whatever the object refers to or is referred to by.

## Rationale

Allowing finalizers anywhere in the graph is simpler to explain than the current rule. A user does not need to know whether an object is in a cycle in order to know that its finalizer runs.

The alternative of forbidding finalizers on objects that may take part in cycles would not be enforceable, because cycles form at runtime through ordinary assignment. [TODO: ask the author whether this reasoning matches the discussion at the time.]

## Alternatives

**Keep the current behavior and document the leak.** Users avoid `__del__` in cyclic structures and use context managers or explicit close methods. This works for code the user controls and does nothing for code that already has finalizers. [TODO: ask the author whether this was weighed.]

**Use weak-reference callbacks in place of finalizers.** A weak-reference callback runs when its referent dies and avoids the ordering problem, because the callback does not receive the dead object. It cannot see the object's state, so it fits some finalizers and not others. [TODO: ask the author.]
