# PEP 532: A circuit breaking protocol and binary operators

## Abstract

Python's conditional expression, `and`, `or`, and the proposed None-aware operators each decide whether to evaluate their right-hand side. Each does so with its own hard-coded rule. This PEP proposes one protocol, with the methods `__then__` and `__else__`, that an object uses to say whether evaluation continues. The protocol covers:

* conditional expressions: `LHS if COND else RHS`
* logical conjunction: `LHS and RHS`
* logical disjunction: `LHS or RHS`
* the None-aware operators proposed in PEP 505
* the rich comparison chaining model proposed in PEP 535

With the protocol in place, the PEP also proposes that `if` and `else` become general short-circuiting binary operators:

* right-associative: `LHS if RHS`
* left-associative: `LHS else RHS`

## Motivation

Python has several constructs that skip their right operand. `and` skips it when the left operand is falsey, and `or` skips it when the left operand is truthy. A conditional expression evaluates exactly one of its two branches. PEP 505 proposes more operators of the same kind, which test for `None` instead of truthiness.

Each of these tests a different property of the left operand, and none lets an object change the test. PEP 335 tried to open up `and` and `or` by making them overloadable. PEP 531 and PEP 535 raised related requests: PEP 531 for existence checking, and PEP 535 for chained comparisons whose results are not booleans. The common need is that the operand, not the interpreter, decides whether evaluation continues. A NumPy-style array cannot answer "is this truthy?" with a single bool. An optional-value type may want "continue only if I hold a value". A comparison result may want "continue only if the first comparison held". Today each case needs its own language change, because the decision is fixed inside each operator.

### The new binary operators

The PEP proposes `LHS if RHS` and `LHS else RHS` as binary operators. `LHS if RHS` associates to the right, and `LHS else RHS` associates to the left. In both, `RHS` is evaluated only when the protocol says so.

For example, `x if y if z` groups as `x if (y if z)`, and `x else y else z` groups as `(x else y) else z`. [TODO: show what each of these evaluates to for ordinary booleans, and what value `LHS if RHS` yields when the condition fails.]

## Rationale

### Why one protocol rather than one per operator

PEP 335 overloaded `and` and `or` alone. That solves the array case, but PEP 505 and PEP 535 then each need another mechanism for the same underlying question. One protocol means a type author implements two methods and every continuing-or-stopping operator uses them. [TODO: record the objections raised against PEP 335 and how this design answers each.]

## Costs and risks

The change adds two special methods to the data model and two new binary operators to the grammar. Every Python implementation that parses the language must handle the new forms. Tools such as linters, formatters and syntax highlighters need updates. [TODO: confirm the list of affected tools with the author.]

The behavior of `and` and `or` becomes harder to reason about locally. Today `a and b` can be understood without knowing the type of `a`. Under this PEP, the type of `a` can change what runs.
