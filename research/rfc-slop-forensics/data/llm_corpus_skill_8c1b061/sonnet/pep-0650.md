# PEP 650: Specifying Installer Requirements for Python Projects

## Abstract

Python package installers do not interoperate completely. pip is the most widely used installer and a de facto standard. Poetry and Pipenv are also popular, because each offers features suited to certain workflows that do not match how pip operates. Many installers help users with specific needs, but the lack of interoperability makes it hard for other tools to support all of them.

The specific gap is that no standard requirements file declares dependencies. Each tool must be used explicitly to install dependencies written in its own format. Otherwise a tool emits a requirements file for the installer, which loses information and adds an extra step. [TODO: the available text is cut off here. ## Motivation

Consider a hosted build service that receives a repository and must set up its dependencies. A project that uses Poetry has a `poetry.lock`. A project that uses Pipenv has a `Pipfile.lock`. A project that uses pip has a `requirements.txt`. The service must know about each format, or it must ask the project's authors to run their tool in a prescribed way.

A service that supports only pip cannot install a Poetry project directly. It can ask Poetry to export a `requirements.txt` and then run pip on that file. The export step discards what the lock file held and the requirements file cannot express. The same problem affects other kinds of tool: a deployment pipeline, an IDE that offers to set up an environment, a continuous integration system, a platform-as-a-service. Each must implement one code path per installer, or support a single installer and exclude the rest.

The cost grows with the number of installers and the number of consumers. With I installers and C consumers that each want to support all of them, the ecosystem needs I times C integrations. A shared interface reduces the figure to I plus C. [TODO: ask whether the author wants this arithmetic in the PEP. It is general reasoning, not a finding from the author's data.]

## Goals

* A tool that wants to install a project's dependencies can do so without knowing the name of the installer.
* The project author chooses the installer, and the choice is recorded in the project, not in the instructions for the person who builds it.

### Declaring the installer

The project names its installer in a file that tools can read without running project code. The existing `pyproject.toml` is the natural place, since build-system requirements already live there. [TODO: ask the author whether `pyproject.toml` is the chosen location and what table or key is used.]

### Interface of an installer

An installer that supports the PEP provides a way for a consumer to call it to install dependencies into a target environment. The interface must define:

1. how the consumer finds the installer's entry point,
2. which operations it supports, for example installing the declared dependencies and installing the project itself,
3. how options such as the target directory or the Python interpreter are passed,
4. how errors are returned.

## Rationale

### Why a declaration and not a common file format

A single requirements format would let every consumer read dependencies directly. It would also force Poetry and Pipenv to reduce their features to what the format can express, or the format would grow until it contained all of them. The PEP instead lets each installer keep its format and defines how to call it. [TODO: the author has not supplied the reasoning for this choice. Confirm or replace this paragraph. ### Why not make pip the only standard

## Costs

Every installer that wants to take part must implement the interface. Poetry, Pipenv and pip each have a maintenance burden to add and keep it. [TODO: ask whether maintainers of these tools have commented on the proposal, and record their position. No material is supplied, so the PEP makes no claim about their support.]

Consumers gain one code path. They also take on a new failure mode: a project that names an installer that is missing, broken, or does not follow the interface.

The decision with the highest cost to reverse is the interface itself. Once installers ship against it, changes need versioning. [TODO: state how the PEP versions the interface.]

## Security considerations

A consumer that follows the declaration will download and run the installer named by the project. This is the same trust as running any project's build backend. A project can name any package as its installer, so a consumer processing untrusted repositories should treat the declaration as untrusted input.
