# PEP 346: User Defined ("`with`") Statements

## Abstract

This PEP combines the "Reliable Acquisition/Release Pairs" of PEP 310 with the "Anonymous Block Statements" of PEP 340. It keeps the parts of PEP 340 that work, takes parts of PEP 310, and arranges them into one proposal. It borrows from other PEPs so that it can be read without them.

## Motivation

Many resources must be released after use: files, locks, database transactions, temporary state. The release must run whether the code in between returns normally, raises, or exits through `return` or `break`. Python code today writes this with `try`/`finally`:

```python
lock.acquire()
try:
    do_work()
finally:
    lock.release()
```

The pattern has three weaknesses.

1. The acquire and release sit at opposite ends of the block, and a reader must match them by eye.
2. The `try`/`finally` is boilerplate that each use repeats, and a developer who forgets it gets code that works until the first error.
3. It cannot be factored into a function, because the block of code that runs in the middle belongs to the caller, not to the function.

PEP 310 addressed the first two by proposing a `with` statement that calls a method when entering the block and another when leaving it. PEP 340 addressed the third by proposing anonymous block statements, which let a function control the execution of a block passed to it, using the generator mechanism. ### The statement

A `with` statement takes an expression and runs a block:

```python
with EXPR as VAR:
    BLOCK
```

`EXPR` evaluates to an object that supports the protocol described below. If `as VAR` is given, the value produced on entry is bound to `VAR`. The block runs. When it finishes by any route, the object is told so.

### The protocol

An object takes part by providing methods for entry and for exit. The exit method receives information about any exception that ended the block, and it may say whether the exception is handled. ### Defining a resource with a generator

To allow a function to define the resource without a class, the PEP provides a decorator that turns a generator into an object with the protocol. The generator runs up to its single `yield` on entry, hands the yielded value to the block, and resumes after the `yield` on exit:

```python
@contextmanager
def locked(lock):
    lock.acquire()
    try:
        yield lock
    finally:
        lock.release()
```

This gives the factoring PEP 340 aimed for, with a narrower scope: the block runs exactly once, so `with` cannot be used to build loops.

## Rationale

### Why combine instead of choosing one

A reader may ask why not simply accept PEP 310 or PEP 340 as written. PEP 310 alone requires a class for every resource, which is a heavy burden for one-off cases. PEP 340 alone puts the whole block under the control of the called function, which makes it possible to skip or repeat the block, and that is more than the resource problem needs. The combination keeps one mechanism for classes and one for generators. [TODO: this reasoning is inferred from the descriptions.
