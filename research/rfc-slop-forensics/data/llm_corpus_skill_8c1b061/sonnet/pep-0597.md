# PEP 597: Add optional EncodingWarning

## Abstract

Add a new warning category `EncodingWarning`. It is emitted when the `encoding` argument to `open()` is omitted and the default locale-specific encoding is used.

The warning is disabled by default. A new `-X warn_default_encoding` command-line option and a new `PYTHONWARNDEFAULTENCODING` environment variable can be used to enable it.

A `"locale"` argument value for `encoding` is added too. It explicitly specifies that the locale encoding should be used, silencing the warning.

## Motivation

When a program calls `open()` in text mode without an `encoding` argument, Python picks one from the locale of the machine. The same program can then decode the same file differently on two machines. A file written as UTF-8 on one system and read on a system whose locale encoding is something else may be misread, or raise a decoding error, and the program has no line that says so. [TODO: ask the author for a concrete reported case, such as a bug report where a program worked on one operating system and failed on another because of this default. No instance is supplied.]

The omission is easy to make because it is the shortest way to write a call, and it works on the author's machine. The problem appears on someone else's machine, later.

A warning could point at each such call. The difficulty is that omitting `encoding` is common and often harmless, for instance when a program reads a file it just wrote on the same machine. A warning on by default would produce a flood of reports about correct code, so the PEP makes it opt-in. An opt-in warning gives developers a way to find the calls in their own code and in their dependencies, at a time of their choosing, without changing what any program does by default.

## Specification

### The warning category

A new built-in category, `EncodingWarning`, is added. It is a subclass of `Warning`. [TODO: confirm the base class.]

### When it is raised

`EncodingWarning` is emitted when `open()` is called in text mode, `encoding` is not given, and the locale encoding is used as a result. The same applies to other functions that wrap `open()` and pass the omission through. [TODO: ask the author which standard library functions are covered, for example whether `io.TextIOWrapper` created directly is included. The abstract names only `open()`.]

The warning is not emitted when `encoding` is given, when the file is opened in binary mode, or when `encoding` has the value `"locale"`.

### How to enable it

Two switches turn it on:

1. The command-line option `-X warn_default_encoding`.
2. The environment variable `PYTHONWARNDEFAULTENCODING`.

[TODO: specify what values of the environment variable count as set. The abstract does not say whether an empty value counts.]

When neither is set, the warning is off.

Because it is an ordinary warning, the existing warning filters apply. A developer can turn it into an error to find every call in a test run. [TODO: confirm that no special interaction with `-W` is intended.]

### The `"locale"` value

The `encoding` argument accepts the new value `"locale"`. It selects the locale encoding explicitly. Code that wants the locale encoding on purpose, such as a program that reads a file produced by a tool that follows the locale, can say so and no longer triggers the warning.

```python
with open("notes.txt", encoding="locale") as f:
    text = f.read()
```

The value gives the same result as omitting the argument. The difference is that it is explicit, so a reader of the code, and the warning machinery, can tell that the choice was deliberate.

## Rationale

The warning is optional because the cost of a default warning falls on users who cannot act on it. A user who runs a script from a third-party package sees a warning about a call in code they did not write. [TODO: confirm this is the author's reasoning.]

The `"locale"` value exists so that there is a way to silence the warning that is not a change in behavior. Without it, a developer who wants the locale encoding on purpose would have to look up the encoding name for the current system and hard-code it, which is a change in behavior on other systems.

## Backward compatibility

With the warning off, no program changes. The new value `"locale"` is not accepted by older interpreters, so code that uses it does not run on them. [TODO: ask the author whether a fallback is recommended for code that must support older versions.]

A program run with the option or variable enabled may emit new warnings from code that was previously silent. If the warning filters turn warnings into errors, such a program fails. This is a consequence of enabling the option, and the PEP states it. [TODO: the abstract gives no data on how the standard library fares under the option. ## Alternatives

**Warn by default.** This reaches everyone. It also warns on harmless calls, as the motivation section describes. [TODO: ask the author whether a default warning was discussed with a later date.]

**Change the default encoding to UTF-8.** This would remove the machine dependence at the root. It changes the behavior of every program that relies on the current default, which is a larger change than this PEP makes.
