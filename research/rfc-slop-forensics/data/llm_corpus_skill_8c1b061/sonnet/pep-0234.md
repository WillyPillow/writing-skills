# PEP 234: Iterators

## Abstract

This PEP proposes an iteration interface that an object can provide to control how a `for` loop runs over it. An object provides a method that returns an iterator. The iterator has a *get next value* operation, which returns the next item on each call and raises an exception when no items remain. The PEP also proposes specific iterators over the keys of a dictionary and over the lines of a file, and the spelling `key in dict` as an alternative to `dict.has_key(key)`.

This PEP is an almost complete rewrite by the second author. It describes the implementation checked into the trunk of the Python 2.2 CVS tree, and it remains open for discussion. ## Motivation

A `for` loop in Python before this proposal works by sequence indexing. The loop calls the object's item lookup with 0, 1, 2 and so on until the lookup raises `IndexError`. This works for lists and tuples. It has three limits.

1. An object that is not indexed by integers cannot be looped over without faking integer indexes. A dictionary is the main example, since its keys are arbitrary.
2. A loop over an object with an expensive item lookup repeats the work of each lookup from the start, because the protocol has no place to keep position.
3. A file's lines can be read only through a method such as `readlines()`, which reads the whole file, or `xreadlines()`, a separate helper. [TODO: confirm that these are the pre-2.2 idioms the author means. These two names come from general knowledge of Python 2.1 and are not in the supplied material.]

The aim is to let any object say how it is looped over, and to let the loop keep state between steps without the object having to store it.

## Specification

### The two methods

An object that supports iteration provides `__iter__()`, which takes no arguments and returns an iterator object. A `for` loop calls `__iter__()` once at the start.

An iterator provides `next()`, which takes no arguments. Each call returns the next item. When no items remain, the call raises `StopIteration`. After it has raised `StopIteration`, later calls must keep raising it. [TODO: confirm the last rule against the text of the final PEP.]

An iterator also provides `__iter__()`, which returns the iterator itself. This lets a `for` loop accept an iterator wherever it accepts an iterable. [TODO: confirm.]

Written out, the loop

```python
for x in obj:
    body(x)
```

behaves as follows:

```python
it = iter(obj)
while True:
    try:
        x = it.next()
    except StopIteration:
        break
    body(x)
```

The built-in function `iter(obj)` returns `obj.__iter__()`. [TODO: confirm that the PEP defines the two-argument `iter(callable, sentinel)` form, and give its semantics if so.]

### Fallback to the sequence protocol

An object without `__iter__()` that supports sequence indexing keeps working in `for` loops. `iter(obj)` then returns an iterator that indexes from 0 and stops on `IndexError`. This keeps all existing sequence-like classes working. [TODO: confirm that this is part of the PEP and where it is implemented.]

A dictionary provides an iterator over its keys. The loop

## Rationale

### Why a method that returns an iterator, and not a method on the object itself

If the object held its own position, only one loop at a time could run over it. Two nested loops over the same list would share state and interfere. Returning a fresh iterator from each `__iter__()` call separates the state. This is the central design point, and it explains why the PEP has two methods and not one.

[TODO: ask the author which alternatives were considered and rejected. The text does not say. A single-method design with a reset operation, and an index-passing design, are the two obvious candidates, and neither can be presented as considered without confirmation.]

### Why an exception to signal the end

`next()` returns any object as an item, including `None` and `0`. No return value is left over to mean "done". An exception avoids reserving one. The cost is that a loop pays the price of raising and catching one exception at the end. [TODO: add measurements if the author has them. No figure is available here.]

### Why only keys for dictionaries

A dictionary has keys, values and items, and a loop can visit only one of them by default. Keys match what `in` tests. Values and items are reachable with methods that return their own iterators. [TODO: confirm the names of these methods in the 2.2 implementation, for example `iteritems`.]

## Costs

The change adds two special methods and one built-in function to the language, and changes the meaning of `for` over a dictionary and over a file. Each is a visible addition to the data model.

The sequence fallback keeps old classes working but means two paths exist for looping, with different speeds. [TODO: if the author has timing for the two paths, give them.]
