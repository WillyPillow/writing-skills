# PEP 327: Decimal Data Type

## Abstract

This PEP proposes a `Decimal` data type for every use where decimal numbers are needed and binary floating point is too inexact. The type supports Python's standard functions and operations and must comply with the decimal arithmetic standard ANSI X3.274-1996. `Decimal` is floating point, not fixed point, and has bounded precision: the precision is the upper limit on the number of significant digits in a result. The user can set the precision. The type keeps significant trailing zeroes, so fixed-point usage is also possible.

The work is based on code and test functions by Eric Price, Aahz and Tim Peters. Just before Python 2.4a1, the `decimal.py` reference implementation was moved into the standard library. ## Motivation

Binary floating point cannot represent most decimal fractions exactly. The value 0.1 has no finite binary expansion, so the stored value is the nearest representable number. Arithmetic on such values produces results that differ from what a person doing the same sum by hand expects:

```python
>>> 0.1 + 0.2
0.30000000000000004
```

For many calculations the error is harmless. For some it is not. Programs that handle money, tax, or measurements recorded in decimal digits want a result that matches decimal arithmetic, including the number of digits shown and the way rounding is done. A total that is off by a cent is a visible defect, and a comparison `a + b == c` that holds on paper and fails in code is a source of bugs.

* Arithmetic on `Decimal` values gives results that match decimal arithmetic taught to people, for the operations the standard defines.

## Specification

### Floating point with bounded precision

The type stores a sign, a string of digits, and an exponent. The value is the signed integer formed by the digits, multiplied by ten to the exponent. Because the exponent is stored, the decimal point floats.

Precision limits the number of significant digits in a result. If the exact result needs more digits, it is rounded to the precision. With a precision of 5, the sum of 12345 and 0.678 rounds to 12346. [TODO: check this example against the reference implementation before it goes into the PEP.]

The value 1.20 keeps its two decimal places, so a program that reports amounts to the cent can print `1.20`, not `1.2`. ## Rationale

### Why follow a standard

A standard gives an answer to every design question about rounding and edge cases, and an implementation that follows it can be compared with others. Programs written for money often have to match another system's results. Following ANSI X3.274-1996 means Python's answers agree with theirs. [TODO: ask the author whether other candidate standards were examined, and why this one was chosen.]

### Why floating point and not fixed point

A fixed-point type holds a set number of places after the decimal point. That works for currency. It handles poorly any program that mixes values of very different scale, such as a calculation involving a billion and a thousandth. A floating-point type handles both, and keeping the trailing zeroes lets it behave like fixed point where wanted. The cost is that the programmer must manage precision, and the result of an operation may be rounded without a visible sign. [TODO: confirm the reasoning with the author.]

### Why bounded precision

Without a bound, division such as 1/3 has no finite exact result. An unbounded type would either fail or loop. A bound makes every operation finish and gives the user control. The user must choose a precision large enough for their results.

## Costs

The type adds a new numeric tower member that does not mix freely with `float`. Programmers must learn when to use each. The implementation, written in Python at the time of the move to the standard library, is slower than the C-based `float`.
