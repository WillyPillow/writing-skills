# PEP 439: Inclusion of implicit pip bootstrap in Python installation

## Abstract

This PEP proposes the inclusion of a pip bootstrap executable in the Python installation to simplify the use of third-party modules by Python users.

This PEP does not propose to include the pip implementation in the Python standard library. Nor does it propose to implement any package management or installation mechanisms beyond those provided by PEP 427 ("The Wheel Binary Package Format 1.0") and [TODO: distlib PEP; the abstract leaves this reference unresolved].

## Motivation

A new Python user who wants a third-party module has to install an installer first. Python ships without `pip`, so the user must find the `pip` project, download it, and run its installer before the first module can be installed. Each of those steps is a place for a beginner to stop. [TODO: ask the author for evidence of this, such as user reports or support questions. The abstract says the goal is to "simplify" use and gives no data.]

The user who has `pip` already does not meet this problem. The affected user is the one who has just installed Python and has nothing else on the machine.

The PEP proposes to close that gap with a small executable that ships with Python. The executable is named `pip`. When a user runs it for the first time, it downloads the real `pip` implementation, installs it, and then runs the user's command. On later runs the real implementation is already present, and the executable passes the command on to it.

This design means Python's own distribution does not contain the `pip` code. The standard library stays as it is. The only item added to the installation is the bootstrap.

## Specification

### The bootstrap executable

The installation includes an executable called `pip` in the same directory as the other scripts of the installation. [TODO: ask the author where the executable lives on each platform and whether the name carries the Python version, such as a name with a version suffix.]

On each run, the bootstrap does the following:

1. Check whether the real `pip` is installed for this Python.
2. If it is, run it with the user's arguments.
3. If it is not, download it, install it, and then run it with the user's arguments.

### What the bootstrap does not do

The bootstrap does not contain the `pip` implementation and does not become part of the standard library. It also does not add any installation logic of its own. After the first run, installing a package is done by `pip` using the mechanisms that already exist, which include the wheel format described in PEP 427.

## Rationale

The approach separates two concerns that would otherwise be tied. Python's release schedule is slow, and `pip` changes faster. If `pip` lived inside the standard library, each user would get whatever `pip` shipped with their Python until they upgraded. With a bootstrap, the user gets the current `pip` at first use, because the download happens then. [TODO: confirm this is the author's reasoning; the abstract states the non-goal of keeping `pip` out of the standard library, but not the reason.]

A bootstrap executable is smaller than a bundled `pip` and does not change the contents of the standard library.

## Security considerations

A program that downloads and runs code at first use is a place where an attacker can intervene. The attacker could substitute a malicious download, or could block the download and leave the user with a failed command. [TODO: this section has nothing from the author. ## Alternatives

**Ship `pip` inside the standard library.** Users would have `pip` from the start. The abstract rules this out without giving the reason. [TODO: ask the author why. Possible reasons include the size of the library and the mismatch of release schedules, but the author has to say which applied.]

**Keep the status quo.** Users install `pip` by hand. This is simple for Python's maintainers and leaves the problem described above in place.

**Ship a copy of `pip` in the installer but outside the standard library.** The installer would place a fixed `pip` next to Python. This avoids the first-use download. It also fixes the `pip` version at the installer's release. [TODO: ask the author whether this was considered.]
