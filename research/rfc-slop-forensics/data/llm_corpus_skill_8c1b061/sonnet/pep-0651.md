# PEP 651: Robust Stack Overflow Handling

## Abstract

This PEP proposes that Python treat machine stack overflow differently from runaway recursion. The recursion limit could then be set to fit a program's needs, and the interpreter would give additional safety guarantees.

If the PEP is accepted, the following program runs safely to completion:

```python
sys.setrecursionlimit(1_000_000)

def f(n):
    if n:
        f(n-1)

f(500_000)
```

The following program raises a `StackOverflow` exception and does not crash the virtual machine:

```python
sys.setrecursionlimit(1_000_000)

class X:
    def __add__(self, other):
        return self + other

X() + 1
```

## Motivation

Python has one mechanism, the recursion limit, that serves two purposes. It stops infinite recursion in Python code, and it keeps the C stack from overflowing. These are different problems, and the two examples in the abstract separate them.

In the first program, the recursion is deep but finite. A depth of 500,000 is legitimate for a program whose author knows it will end. The recursion limit has been set to a million to allow it. The PEP wants this program to succeed. [TODO: author to say whether it succeeds today. In the second program, the recursion goes through a C-level call. The method `__add__` is invoked by the interpreter on behalf of the `+` operator, and the interpreter's C code calls back into Python. With a high recursion limit, the chain of C frames can exhaust the machine stack before the Python-level counter reaches the limit. The result is a crash of the process, not an exception. The PEP wants this program to raise `StackOverflow`. [TODO: author to confirm the crash behavior for this case.]

The tension is that one number cannot serve both programs. A low limit protects the stack and rejects the first program. A high limit admits the first program and exposes the process to a crash in the second. The PEP's proposal is to track the two limits independently.

## Rationale

The PEP separates two failures that look alike from Python code, because they have different causes and different fixes. A program can choose a recursion limit based on its own logic, such as the depth it expects. A program cannot choose the machine stack size so easily, and should not crash when it guesses wrong.

## Backwards Compatibility

The change adds a new exception and changes what happens at high recursion limits. A program that sets a limit higher than its stack can hold today may crash. After the change it gets `StackOverflow`. Code that depends on a crash does not exist in any sensible form, but code that depends on the existing exception type at the recursion limit may behave differently if the types differ.
