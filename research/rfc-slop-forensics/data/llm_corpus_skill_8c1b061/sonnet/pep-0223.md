# PEP 223: Change the Meaning of `\x` Escapes

## Abstract

This PEP changes `\x` escapes, in both 8-bit and Unicode strings, so that each consumes exactly the two hex digits that follow it. The PEP treats the current behavior as an original design flaw. The change gives clearer expression in every kind of string, a cleaner Unicode story, and better agreement with Perl regular expressions. The author judges the risk to existing code to be minimal. ## Motivation

A `\x` escape in a string literal writes a character by its hexadecimal code. The question is how many hex digits it reads. [TODO: author to state the current rule for each string kind. The abstract implies the digit count is not fixed today, and that 8-bit and Unicode strings may differ. The PEP cannot be reviewed until the current rule is written down precisely.]

An escape that reads a variable number of digits has an ambiguity. Suppose a programmer wants the character with code `0x41` followed by the letter `B`. Written as `"\x41B"`, the literal could mean the code `0x41` followed by `B`, or the code `0x41B` (which is out of range for an 8-bit string). A reader must know the rule to decide, and a rule that depends on what follows is easy to misapply. With a fixed width of two digits, `"\x41B"` always means `A` followed by `B`, and the programmer who wants a longer code uses a different escape.

## Specification

In a string literal, `\x` is followed by exactly two hex digits. The two digits are consumed and give the code of one character.

1. In an 8-bit string, the result is one byte with that value.
2. In a Unicode string, the result is the code point with that value.

If fewer than two hex digits follow `\x`, the literal is malformed. [TODO: the error type, and whether the error is raised at compile time. This is a decision the author must make: the alternative is to keep the old behavior for short escapes.]

If more than two hex digits follow, the extra digits are ordinary characters.

## Rationale

The PEP calls the old behavior a design flaw in the original. The reasoning in this document uses only what the abstract states.

A fixed width makes the literal's meaning local. A reader can decode `\x41` by reading four characters, with no need to look at the next character. This is the property the PEP wants, and it is the same property that other Python escapes of fixed width already have. [TODO: confirm this about the other escapes.]

The PEP could have kept the variable-width rule and documented it. [TODO: author to say whether that option was considered. If so, state why documentation was not enough.]
