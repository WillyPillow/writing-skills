# PEP 207: Rich Comparisons

## Abstract

This PEP proposes several new features for comparisons:

- Allow separate overloading of `<`, `>`, `<=`, `>=`, `==` and `!=`, both in classes and in C extensions.
- Allow any of those overloaded operators to return something else besides a Boolean result.

## Motivation

Python currently routes all six comparison operators through one hook. A class or C type supplies a single comparison function that returns a negative number, zero or a positive number. The interpreter turns that three-way answer into the result of whichever operator the program used. [TODO: confirm that this is the current mechanism for both classes and C types; the abstract describes only the proposed change.]

This arrangement forces two limits on the types that define comparisons.

First, the six operators cannot differ in meaning. A type whose `==` should mean something other than "the three-way result is zero" has no way to say so. Some types have equality without an order: two objects can be equal or unequal and have no "less than" relation at all. Under a single hook, such a type must either invent an order or raise an error for the ordering operators and for equality alike. [TODO: ask the author for a concrete type from the language or the extension ecosystem that suffers from this.]

Second, the result is always a Boolean. An operator applied to two containers of numbers could reasonably produce a container of results, one per element. A user of an array type, for example, may want `a < b` to give an array of truth values, so the result can be used to select elements. With the current rule, the array type can only collapse the comparison to one value. [TODO: the abstract does not name the array case. Ask the author which types motivated the second feature.]

The proposal answers both limits with the same change: let each operator call its own hook, and let the hook return any object.

A comparison method may return any object. The interpreter returns that object as the value of the expression. If the operator appears in a context that needs a truth value, such as an `if` statement, the usual truth test applies to the returned object. ### An example

Consider a class `Version` that orders by release number. Under the proposal, it defines `<` and `==` separately:

```python
class Version:
    def __init__(self, n):
        self.n = n
    def __lt__(self, other):
        return self.n < other.n
    def __eq__(self, other):
        return self.n == other.n
```

## Rationale

The two features are proposed together because the second depends on the first. A non-Boolean result is hard to define under a single three-way hook, since the hook returns a number whose sign decides the operator's result. Once each operator has its own hook, there is no reason to restrict what the hook returns.

The alternative of keeping the single hook and adding a separate hook only for `==` and `!=` would serve types with equality but no order, and would leave the array case unsolved. [TODO: ask the author whether this narrower option was proposed or discussed.]

## Alternatives

**Leave comparisons as they are.** Types that need different operators use named methods instead, such as an `equals` method or an `elementwise_less` method. This works and costs no language change. It also means users cannot write `a < b` for those types. The author's case is that operator syntax matters for numeric and array code. [TODO: ask the author for the supporting argument.]

**Add only the non-Boolean result.** The hook would stay single, with a flag that says whether to return a Boolean. This is simpler in the type structure and does not allow the operators to differ. [TODO: ask the author.]
