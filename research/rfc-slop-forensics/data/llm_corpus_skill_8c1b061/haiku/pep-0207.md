## Abstract

This PEP proposes two new features for comparisons. The first lets each of the six comparison operators be overloaded separately, in classes and in C extensions. The second lets any of those overloaded operators return a value that is not a Boolean.

## Proposal

Each of the six operators, less than, greater than, less than or equal, greater than or equal, equal, and not equal, can be overloaded separately. A class defines the operator it needs without having to define the others. [TODO: confirm whether a class that defines only some operators falls back to any default, and what that default is.]

## Decisions

The first decision is to let each operator be overloaded separately. The force is the need for types to control each comparison independently. The alternative of keeping the operators tied together would force a class to supply behavior it does not want. [TODO: confirm this alternative was considered and why it lost.]

The second decision is to allow a non-Boolean result. The reason is that a comparison may carry information beyond yes or no. The cost is that the result cannot always be read as a Boolean. Code that tests a comparison has to know what it is testing. [TODO: state how the conversion rule in the design answers this cost.]

The cost of both decisions falls on code that expects a comparison to return a Boolean. Such code can receive a value it does not handle.

Reversibility: the comparison operators are part of the language's behavior. Once a result type is allowed, programs can depend on it. Removing the freedom later would break those programs. This is the decision with the highest cost to reverse.
