# PEP 651: Robust Stack Overflow Handling

## Abstract

This PEP proposes that Python treat machine stack overflow differently from runaway recursion. The change would let a program set the maximum recursion depth to fit its needs, and it would give additional safety guarantees. Two programs illustrate the intended behavior. The first sets the recursion limit to 1,000,000 and calls a recursive function to depth 500,000. Under the proposal it runs to completion. The second defines a class whose `__add__` method calls `self + other`, and then evaluates `X() + 1`. Under the proposal it raises `StackOverflow` without crashing the virtual machine. ## Motivation

Python limits the depth of recursion with a single setting. A program that needs deep recursion must raise the limit, and a program that does not must leave it low enough to protect the machine. The two needs are both legitimate, but the current design cannot serve both. [TODO: give one real program that needs deep recursion, and state the depth it reaches.]

The obstacle is that the recursion limit does not measure the resource that actually runs out. Python-level recursion and the machine's own stack are separate, and the interpreter can exhaust the machine stack before it reaches the configured limit. When that happens, the process can crash rather than raise an error. [TODO: state how often this happens in practice, and the platform on which it was observed.]

A program that wants to run safely needs a guarantee that a runaway recursion is reported as an error. Without it, the program cannot recover from the failure. [TODO: give one case in which a crash rather than an error caused a loss of data or service.]

## Rationale

The chosen design treats the two conditions as different events, because they have different causes and different remedies. A program that exceeds the recursion limit has a bug or a limit that is too low. A program that exhausts the machine stack has hit a resource boundary.
