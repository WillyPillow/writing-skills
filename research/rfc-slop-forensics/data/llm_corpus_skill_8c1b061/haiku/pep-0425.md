## Abstract

This PEP specifies a tagging system that states which versions of Python a built or binary distribution is compatible with. A set of three tags gives the Python implementation and language version, the application binary interface (ABI), and the platform that the distribution requires. The tags are short because they are included in filenames.

## Motivation

A built distribution is compiled for a particular combination of interpreter, version, and platform. An installer that picks up a file must be able to tell, before it downloads or opens the file, whether the file can run on the machine in front of it. ## Proposal

Each built distribution carries three tags. The first tag names the Python implementation and the language version. The second names the ABI. The third names the platform. ## Goals and non-goals

Goal: an installer can decide whether a built distribution is compatible with the current environment from its filename. We would know this goal was met if the installer makes the decision without opening the file. [TODO: confirm this test.]

Non-goal: a complete description of the environment. The three tags state what the distribution needs, and they do not describe every property of the machine. [TODO: confirm this non-goal and name any property the author considered and left out.]

## Design

The design defines three tags and a rule for combining them. The installer compares each tag against the environment. A distribution is compatible when all three match. The three tags separate concerns that change at different rates. The implementation and version change with each release, the ABI changes less often, and the platform changes least. ## Decisions

The first decision is to use three tags. The force is the need to state the requirement of a distribution in a few parts that an installer can compare. A single tag would combine parts that change at different rates, so a change in one would force a new tag for all. [TODO: confirm whether a single combined tag was considered, and why it lost.]

The second decision is to keep the tags terse. The reason is that they appear in filenames. The cost is that a terse tag is harder to read for someone who has not seen the scheme. [TODO: state how a reader can learn the tag values, and whether a human-readable reference is planned.]

The cost of the terse tags falls on people who read filenames by eye. It does not fall on installers, which compare the tags as text.

Reversibility: the tag format appears in filenames that are already published. A change to the format would leave existing files with a scheme that installers may not understand. This is the decision with the highest cost to reverse, so the format needs the most care before it is fixed.
