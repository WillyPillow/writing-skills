## Abstract

This PEP adds a new warning category, `EncodingWarning`. The warning is emitted when the `encoding` argument of `open()` is omitted and the default locale-specific encoding is used. The warning is disabled by default. It can be turned on with the `-X warn_default_encoding` command-line option, or with the `PYTHONWARNDEFAULTENCODING` environment variable. The PEP also adds a `"locale"` value for the `encoding` argument, which says explicitly that the locale encoding should be used and which silences the warning.

## Motivation

When `open()` is called without an encoding, the file is read and written with the encoding of the current locale. The same call can therefore behave differently on two machines with different locale settings. ## Proposal

The new warning category is `EncodingWarning`. It is emitted at the point where `open()` falls back to the locale encoding because no encoding was given. [TODO: confirm the exact condition under which the warning is emitted, and whether text and binary modes are both covered.]

The warning is disabled by default. A program that does not enable it sees no change in behavior. [TODO: confirm this claim against the default configuration of each interpreter build.]

The warning can be enabled in two ways. The first is the `-X warn_default_encoding` command-line option. The second is the `PYTHONWARNDEFAULTENCODING` environment variable. [TODO: state which of the two takes precedence if both are set, and whether the variable accepts a specific value.]

The `"locale"` value for `encoding` tells `open()` that the locale encoding is intended. A call that passes this value does not emit the warning. [TODO: confirm that the value selects the same encoding that an omitted argument selects today.]

Goal: a developer can find the calls that depend on the locale encoding, and can make the dependence explicit. ## Design

The design adds the warning category, the two ways to enable it, and the `"locale"` value. The warning is a standard warning, so existing warning filters apply to it. [TODO: confirm that the existing filters apply and state how a developer would filter the new category.]

The design keeps the default behavior of `open()`. Only the reporting changes. [TODO: confirm that no call returns a different result when the warning is enabled.]

## Decisions

The first decision is to make the warning opt-in. The force is that many existing programs omit the argument, and a warning on by default would reach all of them at once. [TODO: confirm this reason and whether a default-on warning was considered, with the reason it lost.]

The second decision is to add a `"locale"` value. The reason is that a developer who wants the locale encoding has no way to say so, other than to omit the argument, and the warning would then flag the call. [TODO: confirm this reason.]

The cost of the first decision is that the warning reaches only the developers who turn it on. [TODO: state how the author expects the warning to reach developers who do not turn it on.]

The cost of the second decision is that developers who want the locale encoding must edit their code to say so, which is a change at each call site.

Reversibility: the warning category and the `"locale"` value become public once released. Removing the value would break code that passes it. The enabling options are cheap to change, since they only control reporting. [TODO: confirm whether the author expects either option to change.]
