## Motivation

Programs that handle binary data need a container for sequences of bytes. Examples include file contents, network messages, image data and encoded records. Today a program holds such data in one of two places. It can use a text string, which attaches a character interpretation the data does not have. Or it can use an array of integers, which spends a full element on each value that needs only eight bits. [TODO: confirm with the author which workaround the motivating use cases rely on, and point to code or issues that show it.]

Neither choice gives binary data its own type. Code that receives a value cannot tell from its type alone whether the value is text or raw bytes. Operations meant for text can therefore run on binary data without any error, and the mistake may surface only later, when the data is written out or compared with something else.

The problem has two parts. The first is storage: a byte held in a general container takes more space than a byte. The second is type confusion: a value that carries no mark for its contents invites mixing text and binary data. The two parts pull in different directions for a single container design, which is why a separate type is proposed.
