# PEP 508: Dependency specification for Python Software Packages

| Field | Value |
|---|---|
| PEP | 508 |
| Title | Dependency specification for Python Software Packages |
| Type | Standards Track |
| Status | Final |
| Created | 2015 |
| Python-Version | 2.7, 3.4 |

## Abstract

This PEP specifies the language used to describe dependencies for packages. It draws a border at the edge of describing a single dependency. The different sorts of dependencies and when they should be installed is a higher level problem. The intent is to provide a building block for higher layer specifications.

The job of a dependency is to enable tools like pip to find the right package to install. Sometimes this is very loose, just specifying a name, and sometimes very specific, referring to a specific file to install. Sometimes dependencies are only relevant on one platform, or only some versions are acceptable, so the language permits describing all these cases. The language defined is a compact line based format which is already in widespread use in pip requirements files.

## Motivation

Packages in the Python ecosystem declare their dependencies in several places. Setup scripts, requirements files, metadata files, and command line tools each have their own way of describing what a package needs. Before this specification, these forms were not standardized, and each tool interpreted them in slightly different ways. A requirement that one tool accepted might be rejected by another, and there was no shared definition of what a version constraint meant.

The pip requirements file format had become the de facto standard for expressing dependencies, and many tools had adopted its syntax informally. However, that syntax was defined by the implementation rather than by a document, so its edge cases were not clear. Writing a parser that agreed with pip required reading pip's source code. The authors wanted a written specification that other tools could implement without that dependency.

A second motivation is the need to express environment markers. A package may need one library on Windows and another on Linux, or may need an older version of a library on an old interpreter. Markers allow such conditions to be stated inside the dependency itself, so that a single declaration serves all platforms. Without a standard form for markers, each tool would invent its own, and packages that used them would be portable only to tools that agreed.

## Specification

A dependency is written as a name, optionally followed by extras in square brackets, then either a version specifier or a direct reference to a URL, and then optionally a semicolon and an environment marker. The name must match a defined pattern of letters, digits, hyphens, underscores, and periods, and it begins and ends with a letter or digit. Names are compared in a normalized form in which case is ignored and runs of hyphens, underscores, and periods are treated as equivalent.

Extras are a comma separated list of names inside square brackets. They request optional features of the package, and a tool installs the additional dependencies that those features declare. Extras do not change the identity of the package, so a request for a package with extras is also a request for the package without them.

A version specifier is a comma separated list of clauses. Each clause has an operator and a version. The operators include comparison operators such as greater than or equal to, a compatible release operator that allows later releases within the same leading components, an equality operator that allows wildcards, and an arbitrary equality operator that compares strings. A specifier is satisfied by a version only if every clause is satisfied.

A direct reference uses the at sign followed by a URL. It names a location from which the package can be obtained, and it is appropriate when the package is not published to an index. The URL must be a valid URL with a scheme that the tool supports. Direct references may not be combined with version specifiers, since the URL already identifies a single artifact.

An environment marker is an expression that evaluates to true or false in the context of the installing interpreter. Markers compare named variables such as the operating system name, the Python version, the platform machine type, and the implementation name against string or version literals. They may be combined with the boolean operators and and or, and grouped with parentheses. The set of variables is fixed by the specification, so that markers evaluate the same way in any compliant tool.

## Rationale

The specification deliberately stops at describing one dependency. It does not say when a dependency should be installed, whether it is required or optional, or how conflicting requirements should be resolved. These are the concerns of resolvers and of higher layer formats, and the authors wanted a small building block that those higher layers could reuse.

The line based format was chosen because it is already familiar to users and tools. Requiring a new syntax would have imposed a migration cost on every project, and the existing syntax was sufficient to express the cases that mattered. The specification therefore formalizes the existing practice rather than inventing a new one.

The use of a semicolon to introduce markers, rather than a keyword, keeps the common case short. A dependency without markers reads exactly as it did before the specification, so existing requirements files remain valid.

Normalization of names was specified so that a project that writes a name in one form can be found by a tool that searches for it in another. Without normalization, the same project could appear to be two different packages, which would cause confusion in resolution and in reporting.

## Backwards Compatibility

Most dependencies written before this specification are valid under it without change. The specification adds rules for cases that were previously ambiguous, and some tools accepted forms that the specification now rejects. The authors recommend that tools emit a warning for such forms during a transition period and then reject them.

## Reference Implementation

A reference parser was written alongside the specification. It accepts a dependency string and produces a structured representation containing the name, extras, specifier, URL, and marker. The parser also evaluates markers against a supplied environment. The implementation serves as a test suite, and tools can compare their behavior against it on a large set of examples.

## Security Considerations

The direct reference form allows a dependency to name an arbitrary URL. A tool that installs such a dependency must be careful about where it fetches from, since a malicious or compromised reference could install unexpected code. The specification does not define trust policy, but it notes that tools should make direct references visible to users and should consider restricting them in automated environments.

## Open Issues

The authors identified several questions for future work. One is whether the arbitrary equality operator should be restricted further, since its string comparison can be surprising. Another is whether markers should gain additional variables for newer platform properties. The authors chose to leave these open so that the first version could be finalized without waiting for consensus on every detail.
