# PEP 618: Add Optional Length-Checking To zip

| Field | Value |
|---|---|
| PEP | 618 |
| Title | Add Optional Length-Checking To zip |
| Status | Final |
| Type | Standards Track |
| Created | 2020 |
| Python-Version | 3.10 |

## Abstract

This PEP proposes adding an optional keyword argument, `strict`, to the built-in `zip` function. When the argument is true, `zip` checks that all of its iterable arguments are exhausted at the same time. If one iterable is exhausted before the others, a `ValueError` is raised. When the argument is false or absent, the existing behavior is preserved, and `zip` stops as soon as the shortest iterable is exhausted.

## Motivation

The `zip` function is one of the most frequently used tools in Python for processing sequences together. It takes several iterables and produces tuples of their corresponding elements. The function stops when the shortest input runs out, and this behavior is convenient in many cases where the inputs are intended to be truncated to a common length.

In many other cases, however, the inputs are expected to have the same length, and a difference in length indicates a bug. A common example is the pairing of a list of keys with a list of values, where a missing value would silently drop the last key. Another example is the combination of coordinates with labels, or of columns with headers, where a mismatch can cause wrong results without any visible error.

Programmers currently handle this case in several ways. Some check the lengths before calling `zip`, which requires that the iterables be sized and can require materializing them if they are generators. Others use `itertools.zip_longest` and check for a sentinel value, which is awkward and can hide the situation that the check is meant to catch. Some omit the check entirely and accept the risk. None of these options is satisfactory for the case where the programmer simply wants an error when the lengths differ.

The proposal is to make this check available directly in the built-in, so that the common case can be expressed concisely and without the cost of an extra pass or the complexity of a sentinel.

## Rationale

The chosen design adds a keyword-only argument to `zip`, rather than a separate function. A separate function would duplicate the existing behavior and would require users to learn a new name for a small variation. A keyword argument keeps the interface consistent with other built-ins that offer optional behavior.

The argument is named `strict` because the purpose is to enforce a stricter contract on the inputs. The name was chosen after considering alternatives such as `check` and `equal_length`, which were judged either too vague or too specific. The name `strict` also fits the convention used in other parts of the standard library, where it indicates that an operation will reject inputs it cannot handle exactly.

The check is performed when the iterator is advanced, rather than when `zip` is created, because the iterables may be generators whose lengths are not known in advance. This means that the error is raised at the moment the mismatch is discovered, which may be after some tuples have already been produced. The PEP considers this acceptable, because the alternative would require consuming the iterables in advance.

The implementation raises the error only when one iterable has been exhausted and another still produces a value. If all iterables are exhausted together, the iteration ends normally. This means that a `strict` zip over equal-length inputs behaves exactly like an ordinary zip.

## Specification

The signature of `zip` becomes `zip(*iterables, strict=False)`. The argument `strict` is keyword-only, and it must be a boolean value. Passing any other value is permitted only to the extent that the value is converted to a boolean in the usual way.

When `strict` is false, the function behaves as it did before this change. It stops producing tuples as soon as any of its inputs is exhausted, and it does not look at the remaining inputs.

When `strict` is true, the function produces tuples as long as every input yields a value. When the first input is exhausted, the function checks each of the remaining inputs. If any of them yields a value, the function raises a `ValueError` whose message indicates that the iterables have different lengths. If all of them are also exhausted, the function ends normally.

The check is performed on each call to the iterator, and the error is raised at the first point where the mismatch can be detected. Because the function reads one element from each remaining input in order to perform the check, the check may consume an element from an input that is not exhausted. This consumption is part of the specified behavior, and it is documented so that users are not surprised by it.

The function does not attempt to determine the lengths of the inputs in advance, and it does not require that the inputs support the length protocol. This allows the strict behavior to be used with any iterable.

## Examples

The following example shows the intended use of the argument.

```python
keys = ["a", "b", "c"]
values = [1, 2]

for key, value in zip(keys, values, strict=True):
    print(key, value)
```

In this case the function produces two tuples and then raises a `ValueError`, because the second input is exhausted while the first still has an element. Without the argument, the loop would simply stop after two iterations and the missing key would not be reported.

## Backwards Compatibility

The change is backwards compatible in the sense that calls without the argument behave exactly as before. Code that passes an unexpected keyword argument to `zip` would previously have received a `TypeError`, and it will continue to receive one for any keyword other than `strict`.

Subclasses or wrappers around `zip` are not affected, unless they forward arbitrary keyword arguments in a way that changes meaning. Such wrappers would need to be updated to pass the argument through, and the PEP recommends that library authors do so when they wish to offer the same behavior.

## Performance

The additional check adds a small cost to each iteration when `strict` is true, because the function must look at the other inputs when the first is exhausted. This cost occurs only once per call, at the end of iteration, and it does not affect the per-element work in the common case. When `strict` is false, no additional work is performed.

## Reference Implementation

The reference implementation modifies the internal iterator for `zip` to accept the new argument and to perform the check when the first input is exhausted. It includes tests for equal lengths, for unequal lengths in both directions, for inputs that are generators, and for the non-strict behavior. The tests also check that the error message is informative enough to identify the mismatch.

## Rejected alternatives

A separate function named `zip_strict` was considered, but rejected because it would duplicate the signature of `zip` and would make the feature harder to discover. A proposal to make the strict behavior the default was rejected because it would break a large amount of existing code that relies on truncation.

An alternative that checks the lengths of sized inputs before iteration was considered and rejected. This approach would give a different error timing for sized and unsized inputs, which is confusing, and it would not help with generators.
