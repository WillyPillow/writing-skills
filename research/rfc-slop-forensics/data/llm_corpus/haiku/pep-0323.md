## Abstract

This PEP suggests that some iterator types should support shallow copies of their instances by exposing a `__copy__` method which meets some specific requirements, and indicates how code using an iterator might exploit such a `__copy__` method when present.

## Motivation

An iterator is an object that produces a sequence of values one at a time through its `next()` method, and signals exhaustion by raising `StopIteration`. Most iterators in the standard library are designed around a single forward pass. Once an iterator has been advanced, the values it has already produced are gone, and the iterator itself carries no record of where it was before the advance.

This design is usually the right one, but it creates a practical problem. Consider a parser that wants to try one interpretation of the upcoming input, fail partway through, and then retry with a different interpretation. The natural approach is to remember the position, advance, and rewind on failure. With a plain iterator there is no way to rewind. The author must either buffer everything produced so far in a list, which costs memory proportional to the input, or restructure the code so that no backtracking is needed.

Some iterators can be cloned cheaply because their state is small and fully described by a few values. A file-like iterator over a list, for example, needs only an index. If such an iterator could be copied, the copy would begin where the original currently stands, and the two could then proceed independently. This would allow a consumer to take a snapshot of the position, look ahead on the copy, and discard the copy if the lookahead was not useful, all without disturbing the original.

Python already has a convention for this kind of operation. The `copy` module recognizes a `__copy__` method on an object and calls it to produce a shallow copy. Iterators that define `__copy__` would therefore integrate with existing code that uses `copy.copy()`, and no new protocol would be needed at the level of the copy module itself.

## Specification

An iterator type MAY define a `__copy__` method. When it does, the method MUST take no arguments beyond `self` and MUST return a new iterator object. The returned object MUST be independent of the original in the following sense: advancing the copy with `next()` MUST NOT change the values later produced by the original, and advancing the original MUST NOT change the values later produced by the copy.

The copy MUST reflect the state of the original at the moment `__copy__` was called. If the original has already produced three values, the copy's first value MUST be the fourth value of the original's sequence, assuming the original has not been changed by other means.

The method is a shallow copy. Any mutable state that the iterator shares with other objects, such as a list being iterated over, MAY remain shared. An iterator that wishes to offer a deep copy may define a separate method for that purpose, but this PEP does not specify one.

An iterator that cannot provide a meaningful copy, because its underlying source is a one-shot stream such as a socket or a generator frame that cannot be duplicated, SHOULD NOT define `__copy__`. Code that calls `copy.copy()` on such an object will then fall back to the default behavior of the `copy` module, which for most objects is to raise an error or to return the object unchanged, depending on the type. Consumers MUST NOT assume that a missing `__copy__` implies the iterator is cheap to rewind.

## Usage Guidance

Code that wishes to exploit a copyable iterator can use the following pattern. The consumer takes a copy before attempting a speculative operation. If the operation succeeds, the consumer continues with the original. If it fails, the consumer discards the original and continues with the copy, which is positioned at the point where the speculation began.

A typical example is a tokenizer that needs to decide whether a run of characters forms a keyword or an identifier. The tokenizer copies the character iterator, reads ahead on the copy to match the keyword, and either adopts the copy or drops it. Because the copy is independent, the tokenizer never has to store characters it has already seen in a separate buffer.

The PEP recommends that consumers check for the presence of `__copy__` with `hasattr` or by catching the error raised by `copy.copy()`, and that they fall back to buffering when copying is unavailable. Libraries should document whether a function returns copyable iterators so that callers can rely on the behavior.

## Rationale

The choice of a shallow copy follows from the fact that most iterators reference their data rather than owning it. A list iterator references the list; copying the iterator need not copy the list. Requiring a deep copy would force every copy to duplicate potentially large sources, which would defeat the purpose of cheap lookahead.

The choice to make `__copy__` optional reflects the reality that many useful iterators cannot be copied. Generators in particular keep their execution state in a frame, and that frame cannot be cloned without a substantial change to the interpreter. A required `__copy__` would have excluded generators from the protocol entirely, which the author considered too restrictive given how common generators are as a source of values.

The proposal intentionally avoids introducing new syntax or a new built-in function. The existing `copy.copy()` entry point already expresses the intent, and adding a separate name would split the concept across two APIs.

## Backwards Compatibility

Adding `__copy__` to an existing iterator type does not change its behavior for code that does not call `copy.copy()`. Code that already calls `copy.copy()` on iterators will observe a change only if the iterator type gains a `__copy__` method, in which case the call will now return a copy rather than the default result. Such code is unlikely to depend on the default behavior, but the author recommends that the change be introduced gradually and mentioned in the release notes.

## Reference Implementation

A sequence iterator over a list can implement the protocol by constructing a new iterator object over the same list and setting its index to the current index of the original. The copy then shares the list but tracks its own position. The implementation requires only a few lines and no changes to the interpreter core.

## Open Issues

The proposal leaves open whether standard library iterators such as those returned by `iter()` on built-in sequences should all gain `__copy__` at once, or whether the change should be limited to types where the benefit is clearest. The author suggests the latter, beginning with sequence and range-like iterators, and extending the protocol as experience accumulates.

A second open question concerns thread safety. If the original iterator is being advanced by another thread at the moment `__copy__` is called, the copy may observe an inconsistent state. The author proposes that `__copy__` be documented as requiring external synchronization when the iterator is shared, and leaves stronger guarantees to a later revision.
