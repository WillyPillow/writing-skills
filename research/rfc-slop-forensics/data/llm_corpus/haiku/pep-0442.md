PEP: 442
Title: Safe object finalization
Author: Antoine Pitrou
Status: Final
Type: Standards Track
Content-Type: text/x-rst
Created: 2013-05-18
Python-Version: 3.4

Abstract
========

This PEP proposes a way to deal with the current limitations of object finalization. The goal is to be able to define and run finalizers for any object, regardless of its position in the object graph. The PEP does not call for any change in Python code. Objects with existing finalizers will benefit automatically.

Rationale
=========

Python objects may define a finalizer, a method that runs when the object is about to be destroyed. In CPython, most objects are freed through reference counting, so the finalizer runs as soon as the last reference disappears. Cyclic garbage is handled by a separate collector, and the collector historically could not safely call finalizers on the objects it found in a cycle. The reason is that the finalizer might access other objects in the cycle that had already been cleared, or that were in an undefined state.

Before this PEP, an object that took part in a reference cycle and that defined a finalizer was placed in a list of uncollectable objects. The garbage collector would not free such objects, and the program would leak their memory for the rest of its lifetime. This behavior is surprising, and it is a common source of unexpected memory growth. Users who wrote classes with a `__del__` method were often advised to avoid cycles, which is difficult in larger programs.

The goal of this PEP is to remove the special case. A finalizer should run for every object that the collector decides to destroy, and the collector should be able to free the objects in the cycle after the finalizers have run.

Specification
=============

The garbage collector is changed so that it proceeds in phases when it finds unreachable objects. In the first phase, it determines the set of unreachable objects, including those in cycles. In the second phase, it calls the finalizer of each object in that set that has one, in an order that does not depend on the internal layout of the collector. During finalization, the objects are not yet freed, so the finalizer may safely access any object that it can reach. If a finalizer resurrects an object by storing a new reference to it, the collector detects the resurrection and does not free the object in that pass.

After all finalizers have run, the collector checks again whether the unreachable objects are still unreachable. Objects that are still unreachable are freed. Objects that were resurrected remain alive and are handled normally in subsequent collections. The finalizer of an object is called at most once for each reachability cycle, so that the mechanism does not loop indefinitely.

The mechanism is implemented in the C-level garbage collector. The Python-level interface does not change. Code that defines `__del__` continues to work, and objects that were previously uncollectable are now collected.

A new C API function is added for extension authors who want to participate in the protocol. The function allows an extension type to request that its finalizer be called in the same safe context as Python-level finalizers. Existing extension types that already define a finalizer are not required to change.

Backwards Compatibility
=======================

Most code will see no difference. Programs that depended on the old behavior of leaking cyclic objects with finalizers may observe that their memory is reclaimed, and that finalizers run at a different time. The PEP argues that this change is a fix, not a regression. Programs that relied on the leak would have been depending on a bug.

Finalizers may now run during a collection that was previously unable to free their objects, so code that performs expensive work in a finalizer may see a change in timing. The PEP recommends that such code be reviewed.

Reference Implementation
========================

The reference implementation modifies the cycle collector in the core interpreter. It introduces a phase that identifies finalizable objects, a phase that invokes their finalizers, and a phase that checks for resurrection before freeing memory. The implementation was tested against the existing test suite and against a set of programs with cyclic data structures that define finalizers.

Discussion
==========

Some participants asked whether finalizers should be called in a deterministic order. The PEP does not promise an order, because the collector is not required to be deterministic with respect to object layout. Authors who need ordering should use explicit resource management, such as context managers, rather than relying on finalizers.

Others asked whether the change would make the collector significantly slower. The reference implementation adds a small amount of work for each collection that finds finalizable objects, and the cost is proportional to the number of such objects. Collections that find none are unaffected.
