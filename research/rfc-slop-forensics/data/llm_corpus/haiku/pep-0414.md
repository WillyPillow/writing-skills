# PEP 414: Explicit Unicode Literal for Python 3.3

**Type:** Standards Track
**Status:** Draft
**Topic:** Language, Porting

## Abstract

This document proposes that Python 3.3 accept the prefix `u` before string literals, restoring the explicit Unicode literal that Python 2.x provided. The prefix has no effect on the value of the literal in Python 3, where all string literals are already Unicode. Its purpose is to reduce the number of edits needed when a program that was written for Python 2 and handles Unicode text is ported to Python 3. The prefix is accepted in Python 3.3 and later and is silently ignored in its meaning, so that code that uses it runs on both lines of the language with the same results.

## Motivation

Python 2 distinguished between byte strings and Unicode strings through two kinds of literal. An ordinary literal produced a byte string, and a literal with the prefix `u` produced a Unicode string. Many programs written for that version use the prefix throughout, both because it made the intent clear and because the default type was not always the one the author wanted.

Python 3 changed the default. Ordinary string literals are now Unicode, and byte strings have their own prefix `b`. The change was correct, but it created a porting problem. A program that uses `u` prefixes is no longer valid Python 3 when the prefix is removed without thought, and it is no longer correct when the prefix is kept, because Python 3.0 through 3.2 rejected it as a syntax error.

The result was that large Python 2 codebases had to be edited to remove a prefix that carried no meaning for the port, or to be edited in a more careful way that would not depend on the presence of the prefix. Both options add work. The first creates a large diff that touches many lines without changing behavior. The second requires tooling that understands the source well enough to decide which literals are text.

## Rationale

The proposal reintroduces the prefix because it lets code be ported in stages. A maintainer can run the same source file under Python 2 and Python 3 without rewriting every string literal, which is valuable when the two versions must be supported at the same time. The prefix becomes a marker that the author chose a Unicode string, and it has the same meaning under both versions.

The alternative of reading the prefix as a no-op in Python 3 was chosen over reading it as a marker for something else, because no other meaning was proposed. Making it a no-op keeps the semantics of the language simple. The literal is still a string, and it is still Unicode. The prefix is accepted for compatibility and for the convenience of readers.

The change also makes the Python 2 and Python 3 forms of common code closer to each other. Code that a library author wants to share between the two versions can use the same literals, and the differences that matter, such as the handling of bytes, can be concentrated in the places where they actually occur.

## Specification

A string literal may be preceded by the letter `u`, in either case. The prefix may be combined with no other prefix, since a literal cannot be both Unicode and bytes. The prefix is valid for ordinary string literals and for triple-quoted strings. It is not valid for byte literals.

A literal with the prefix has exactly the same value as the same literal without it. Escape sequences are processed in the same way, and the result is a Unicode string. The prefix does not change the type of the literal or any other property of it.

The prefix is accepted by the parser and by the compiler in every context where an ordinary string literal is accepted. This includes docstrings, arguments to functions, and parts of implicit string concatenation. Within a single concatenation, the prefix may appear on some of the pieces, and the result is the same as if it were absent.

The raw prefix is not affected by this proposal. A literal with the prefixes `ur` is not accepted, because the raw form has never been combined with the Unicode prefix in Python 3.

## Backwards Compatibility

The proposal is additive. Programs that did not use the prefix are unaffected. Programs that used it in Python 3.0 through 3.2 were rejected with a syntax error, and after this change they are accepted. No valid program changes meaning.

Tools that analyze source code may need to be updated to recognize the new form. Linters and syntax highlighters that treat the prefix as an error should be changed to treat it as valid, and documentation that describes the set of valid prefixes should be revised.

Some code that was written for Python 3 may use the prefix by accident, because it was copied from Python 2 code. After this change such code runs without error, so the prefix would be harmless. Style checkers may choose to flag it as redundant, but the proposal does not require this.

## Discussion

Some people argued that the prefix would encourage the continued use of Python 2 idioms and would make the eventual removal of Python 2 support harder. The proposal responds that the prefix is cheap to remove, that it is most useful during the porting period, and that a tool can strip it automatically once the porting is complete.

Others argued that the change adds a feature that has no purpose in Python 3, and that it complicates the grammar for the sake of a transitional convenience. This is a fair point, and the proposal accepts the cost on the grounds that the benefit to porting is large and that the grammar change is small.

## Implementation

The implementation is a small change to the tokenizer and the grammar. The tokenizer recognizes the prefix and treats the literal as an ordinary string. The grammar accepts it in the same positions as an ordinary literal. The change has been tested against the existing test suite and against a set of ported programs that rely on the prefix.

## Open issues

The proposal leaves open how long the prefix should be supported. One view is that it should remain indefinitely, since removing it would break code that is correct under both versions. Another is that a future version should deprecate it. The proposal takes no position on the removal, beyond stating that the prefix is harmless to keep.
