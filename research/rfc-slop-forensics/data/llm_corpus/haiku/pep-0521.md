# PEP 521: Keeping process-wide state scoped inside generators and coroutines

- **Type:** Standards Track
- **Status:** Draft
- **Requires:** 343, 3152

## Abstract

Most designers of Python libraries try to avoid global state, but a small number of situations make it the sensible choice. A common pattern in the standard library and in third-party code is to keep the state in a global or thread-local slot and to change it only inside a `with` block, so that the change ends exactly when the block ends. The standard library's `warnings.catch_warnings` and `decimal.localcontext` follow this pattern, as do NumPy's `numpy.errstate`, which controls the floating point error handling defined by IEEE 754, and the request or logging context that many server frameworks maintain for each incoming request.

The pattern works well for ordinary functions. It does not work cleanly for generators and coroutines. A `with` block inside a generator can stay open across a `yield`, and while the generator is suspended the caller continues to run with the modified global state still in effect. This proposal describes a protocol that lets a context manager state how its global changes should be detached when a generator suspends and reattached when it resumes. It leaves the existing `with` statement syntax unchanged.

## Motivation

Consider a generator that needs decimal arithmetic at a higher precision than the rest of the program. The natural code wraps the body in `decimal.localcontext`:

```python
def running_totals(values):
    with localcontext() as ctx:
        ctx.prec = 50
        total = Decimal(0)
        for value in values:
            total += value
            yield total
```

When the generator yields, the caller receives a value and then runs its own code. That code now sees a precision of 50 digits, because the `with` block has not exited. The generator has leaked its setting into unrelated code. Developers usually discover this only after a subtle numerical difference appears in some distant module.

The workarounds are unsatisfying. The generator can restore the old context before each `yield` and reinstate the new one after it, but that duplicates logic and is easy to get wrong when an exception is raised in the middle. Some authors move the whole computation into a list, which defeats the point of a generator. Others rely on thread-local storage plus a separate thread per generator, which is expensive and does not compose with asynchronous code.

Coroutines have the same problem with more consequences. An event loop switches between many coroutines in a single thread, so a context set by one coroutine can affect every other one that happens to run before it returns control. Frameworks that store request context in a global variable have had to build complicated machinery to keep it sorted out.

## Specification

This proposal adds two optional special methods that a context manager object may define. A context manager that defines neither method behaves exactly as it does today.

`__suspend__(self)` is called when the generator or coroutine that holds the `with` block is about to suspend. It must undo whatever global change `__enter__` made, and it should return an opaque token that describes the state it removed. The return value is passed to the next call.

`__resume__(self, token)` is called when the generator or coroutine is resumed. It must reinstate the global state described by the token. Its return value is ignored.

The interpreter calls `__suspend__` on every active context manager in reverse order of entry, and calls `__resume__` on them in the order of entry. Ordinary `__enter__` and `__exit__` continue to be called exactly once each, as before. The two new methods only add hooks around suspension points.

A context manager that does not define the new methods inside a generator should be treated as a plain context manager. Interpreters are not required to warn about this, but a linting tool may do so.

## Rationale

Tying the hooks to suspension rather than to entry and exit keeps the common case simple. Authors of ordinary context managers do not need to change anything. Only those who manage global state in a way that must follow the control flow of a generator need to implement the new methods.

The reverse-order suspend and forward-order resume match the nesting of the `with` blocks. An inner block may depend on state installed by an outer block, so it must be removed first and restored last. Keeping the order consistent makes the behaviour predictable when several managers are active at once.

Returning a token from `__suspend__` avoids forcing context managers to store their saved state on the instance. A single context manager object may be used by several generators at the same time, and the token keeps each suspension separate.

## Backwards Compatibility

The proposal is additive. Existing code that does not define `__suspend__` or `__resume__` behaves exactly as before. The only observable change is for code that defines these names for some other purpose, which is expected to be rare.

## Reference Implementation

A prototype can be written in pure Python by wrapping the generator frame and inspecting the active `with` blocks. This is slow and fragile, so the proposal calls for changes in the interpreter's handling of `YIELD_VALUE` and `SEND` so that the hooks are called from the eval loop directly. The prototype is useful mainly to test the protocol against real frameworks.

## Open Issues

Several questions remain open. The first is whether `__suspend__` should be allowed to raise an exception. The current draft says that an exception stops the suspension and propagates into the generator, which matches the way `__exit__` behaves, but it complicates the eval loop. The second is how the protocol should interact with asynchronous generators, which may suspend many times while awaiting I/O. The third is whether a standard helper should be added to the standard library, so that libraries such as `decimal` and `warnings` can adopt the protocol without repeating the same code.

## Discussion

Early reactions suggested that the feature is useful but that the name of the hooks should be clearer. Some participants proposed alternatives that describe the effect rather than the timing, but the timing-based names were kept because they match the points in the control flow where the interpreter calls them.

Several framework authors reported that they already maintain a version of this logic in their own code. They welcomed a standard protocol because it would let them remove that code. Others were concerned that the extra hooks would slow down generators that do not use them. The draft addresses this by checking for the methods once, when the `with` block is entered, and recording the result so that the cost in the common case is a single flag test.

## Summary

This proposal allows a `with` block to manage global state correctly across the suspension points of generators and coroutines. It adds two optional methods, keeps existing code working, and gives library authors a single protocol in place of many ad hoc workarounds.
