Title: Adding an ordered dictionary to collections

Abstract
========

This PEP proposes an ordered dictionary as a new data structure for the ``collections`` module, called "OrderedDict" in this PEP. The proposed API incorporates the experience gained from similar implementations that exist in various real-world applications and in other programming languages.

Motivation
==========

Python's built-in dictionary does not record the order in which keys were inserted. Iteration produces keys in an order that depends on their hash values and on the history of the table, and the order is not something a program can rely on. For most uses this is acceptable. For others it is a serious limitation.

Programs that produce output from a mapping often need the output to follow the order in which the data was given. A configuration file that lists settings in a particular sequence, a report whose columns follow the order of the input, or a serialized object whose fields must be written in a stable order all depend on insertion order. Programmers have worked around the limitation by keeping a separate list of keys alongside the dictionary, which is error-prone because the two can fall out of step.

Several third-party implementations of ordered dictionaries exist, each with its own choices about the API and its own performance characteristics. Some are based on a dictionary with an auxiliary linked list, and others use a list of pairs with an index. These implementations have proven useful, and their experience shows what an ordered dictionary should do. A standard version in the library gives programmers a shared tool and avoids the need to choose among competing packages.

Rationale
=========

An ordered dictionary should behave like a dictionary in every respect that matters for ordinary use, and it should add a clear rule for iteration order. The rule chosen is that keys are iterated in the order in which they were first inserted. Reinserting an existing key does not change its position. Deleting a key removes it from the order, and inserting it again places it at the end.

The API should be a superset of the dictionary API, so that code written for a dictionary works with an ordered dictionary without change. Methods that return views of the keys, values, and items should follow the order. Equality comparison between two ordered dictionaries should take the order into account, since two mappings with the same contents but different orders are, for this purpose, different. Comparison with an ordinary dictionary should continue to ignore order, so that existing code that compares mappings is not affected.

The design also includes a method to move a key to either end of the order, which is useful for implementing caches and least-recently-used policies. Popping an item from either end is also provided. These operations are common enough in practice that they justify inclusion in the standard type.

Specification
=============

The new type is defined in the ``collections`` module. It is a subclass of the built-in dictionary type, and it keeps an additional structure that records the order of the keys. The constructor accepts the same arguments as the dictionary constructor, and when given a sequence of pairs, it records the keys in the order of the pairs.

Iteration over the keys, values, and items follows the insertion order. The methods that return views, such as the keys and items methods, return views that reflect the same order. Assignment to an existing key does not change its position, while assignment to a new key appends it.

The type provides a method that removes and returns an item from either end of the order. A caller chooses the end by passing a flag. The type also provides a method that moves an existing key to one end of the order, which raises an error if the key is absent.

The representation of the object, returned by the repr function, lists the items in order. This allows the output of a program to show the order in which the items are held, which helps when debugging.

Equality between two ordered dictionaries requires both the contents and the order to match. Equality between an ordered dictionary and an ordinary dictionary compares only the contents, as the built-in type does.

Implementation Notes
====================

A reference implementation is written in Python and is also available in a form that uses the C implementation of the dictionary for storage, with an additional linked list to record order. The design allows the ordering to be maintained with constant-time insertion and deletion. Memory use is higher than that of an ordinary dictionary, because of the additional links, and this should be stated in the documentation.

Pickling and copying preserve the order. The object must support the protocols used by these operations, so that a restored copy has the same keys in the same sequence.

Backwards Compatibility
=======================

The new type does not change the built-in dictionary, so existing programs are unaffected. Code that relies on dictionaries having no particular order continues to work, because ordinary dictionaries retain their present behavior. The ordered dictionary is a separate type that a program must choose to use.

Alternatives
============

One alternative is to change the built-in dictionary so that it preserves insertion order. This would be a much larger change, with effects on memory use, performance, and the expectations of existing code. The PEP does not propose it, because the benefits can be obtained from a separate type without disturbing the existing one.

Another alternative is to provide an ordering through a function that wraps a dictionary and returns its keys sorted by insertion time. This requires the wrapper to record that time, which is the same work as the proposed type, but without the integration with the mapping protocol that users expect.

A third alternative is to leave the matter to third-party packages. This was not chosen, because the need is widespread and a standard type gives programmers a common choice.

Open Issues
===========

The exact performance characteristics of the reference implementation should be measured against the third-party designs before the PEP is finalized. The treatment of the ordering in the presence of concurrent modification is not fully specified and may need clarification. The name of the type, and whether it should be placed in a different module, may be revisited in review.
