PEP: 403
Title: General purpose decorator clause (aka "@in" clause)
Author: Alyssa Coghlan
Status: Deferred
Type: Standards Track
Content-Type: text/x-rst
Created: 2012-02-17
Python-Version: 3.3

Abstract
========

This PEP proposes the addition of a new ``@in`` decorator clause that makes it possible to override the name binding step of a function or class definition. The new clause accepts a single simple statement that may make a forward reference to the decorated function or class. The clause is intended for the case where a "one-shot" function or class is needed, and where placing the definition before the statement that uses it makes the code harder to read. The new name is visible only to the statement in the ``@in`` clause, so it does not shadow names in the surrounding scope.

The proposal is based heavily on the ideas in PEP 3150, which describes statement local namespaces, and some of the rationale will be familiar to readers of that PEP.

Motivation
==========

Python code often defines a small helper function or class and then uses it exactly once. The usual layout places the definition first and the use second. For short helpers this layout is clear. For longer helpers, however, the reader must scroll past a large definition to find the code that actually matters, and the purpose of the definition is revealed only at the end.

Decorators already allow a function to be transformed after it is defined. A decorator that receives a function and returns a new value can express many common patterns. But the function must still be given a name before the decorator is applied, and that name then remains in the enclosing scope. The PEP asks whether the name binding itself could be controlled, so that the function can be defined, used, and discarded in a single construct.

Several existing idioms show the need. Property definitions, registration callbacks, and small adapters are often written as a def followed by an immediate call. The names involved are rarely reused, but they still clutter the namespace and invite accidental reuse.

Proposal
========

The ``@in`` clause is written after the decorators of a function or class definition. It takes the form of a keyword followed by a single simple statement. The statement may refer to the name of the decorated object, which is bound only within the statement. Once the statement completes, the name is removed, and the enclosing scope is unchanged.

A simple example illustrates the intent::

    @in print(render(report))
    def render(data):
        return format_lines(data)

In this example, the function ``render`` is defined and called in the same construct. Its name does not persist after the statement. The reader sees the use before the definition, which matches the order in which the code is meant to be understood.

The statement in the clause must be a single simple statement. Compound statements are not allowed, because they would make the scoping rules difficult to state clearly. The clause may not contain another ``@in`` clause.

Semantics
=========

The decorated definition is first evaluated in a temporary namespace. The statement in the ``@in`` clause is then executed in a namespace that contains the defined name and the names of the enclosing scope. After the statement completes, the defined name is discarded. The value of the definition is not stored in the enclosing scope unless the statement itself stores it, for example by assignment to a global.

Decorators are applied in the usual order before the statement runs, so that the object visible to the statement is the decorated object.

Alternatives
============

Several alternatives were considered. One is to introduce a new block construct that groups the definition and the statement. This is more general, but it adds a new kind of block to the grammar and raises questions about indentation and scoping that the ``@in`` clause avoids.

Another alternative is to use a lambda expression wherever possible. Lambdas are limited to a single expression and cannot contain a def or a class, so they do not cover the cases the PEP addresses.

A third alternative is to rely on conventions, such as naming temporary helpers with a leading underscore and deleting them explicitly. This is a workable style, but it does not make the scoping rules visible to the interpreter or to tools.

Concerns
========

Some reviewers were concerned that the clause would be used to hide complicated logic in a position that is easy to overlook. The PEP answers that the clause is limited to a single simple statement, which keeps the logic visible. Others were concerned about the interaction between the clause and existing decorator syntax, and the PEP proposes a precise ordering to address this.

The main objection raised during discussion is that the feature is not needed often enough to justify new syntax. The author agrees that the case is narrow, and this is one reason the PEP is deferred rather than accepted.

Reference Implementation
========================

No reference implementation was completed at the time of writing. A prototype in the compiler demonstrated that the scoping rules could be implemented without changing the bytecode for ordinary definitions.
