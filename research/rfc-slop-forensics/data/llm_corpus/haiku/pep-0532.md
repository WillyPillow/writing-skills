# PEP 532: A circuit breaking protocol and binary operators

- **Type:** Standards Track
- **Status:** Draft

## Abstract

Several proposals in recent years have tried to add new operators or new forms of conditional expression to Python. Each one would have needed its own definition of how short-circuiting works, and each would have duplicated similar logic. This proposal defines a single circuit breaking protocol, based on two special method names, `__then__` and `__else__`. The protocol gives a common foundation for conditional expressions, logical conjunction and disjunction, the None-aware operators, and chained comparisons.

Building on the protocol, the proposal also allows `if` and `else` to be used as general purpose short-circuiting binary operators, with the right-associative and left-associative forms defined in terms of the protocol. It further proposes a consistent treatment of logical inversion, so that `not` follows the same model.

## Motivation

Python already has several short-circuiting constructs. The expression `a and b` returns `a` when `a` is falsy and otherwise returns `b`. The expression `a or b` does the opposite. The conditional expression `x if cond else y` evaluates only one of its branches. Each of these has special rules hard-wired into the interpreter.

Proposals for further operators keep arriving. One proposal would add a way to test for `None` and use the other operand when the first is `None`. Another would make chained comparisons short-circuit in a particular way. Each proposal needs the interpreter to evaluate one operand, decide whether to evaluate the next, and produce a result. Implementing each one separately produces duplicated code and slightly different edge-case behaviour.

A common protocol would allow each of these operators to be described once. An object would decide how it participates in short-circuiting, and the operators would be defined in terms of that decision. New operators could then be added without changing the core rules.

## The circuit breaking protocol

An object takes part in short-circuiting by defining one or both of two special methods.

`__then__(self, if_true)` is called when the object is the left operand of a construct that continues when the left value is true. It receives a callable that evaluates the right operand when needed. The return value of `__then__` becomes the result of the whole expression.

`__else__(self, if_false)` is called in the matching case for falsy values. It receives a callable that evaluates the other operand when needed.

The callable passed to each method is created by the interpreter. Calling it evaluates the right-hand expression exactly once and returns its value. If the method does not call it, the right-hand expression is never evaluated, which is the essence of short-circuiting.

Objects that do not define either method fall back to the truth value protocol that Python already uses for `and`, `or`, and `if`. This keeps the behaviour of all existing types unchanged.

## Conditional expressions

The conditional expression `LHS if COND else RHS` already has well-defined semantics. Under this proposal it is rewritten in terms of the protocol. `COND` is tested with `__then__` when it defines that method, and the chosen branch is evaluated lazily through the callable. The observable behaviour for existing types does not change.

## Logical operators

`LHS and RHS` and `LHS or RHS` are defined in the same way. The left operand decides whether the right operand is evaluated, and the value returned is the object produced by the chosen method. Types that want a different result from a conjunction, such as a symbolic expression type, can return their own object rather than a bool.

## Binary short-circuiting operators

The proposal also allows two new forms of the conditional keyword pair to be used as binary operators. `LHS if RHS` is right-associative and returns `LHS` when `RHS` is true, and otherwise returns a sentinel result defined by the left operand. `LHS else RHS` is left-associative and returns `LHS` when it is true, and otherwise evaluates `RHS`.

These forms are deliberately restricted. The right-associative form only makes sense when the left operand can represent the absence of a value, so the proposal requires that the left operand define `__then__`. The left-associative form is the mirror image, and requires `__else__`. Objects that do not define the required method raise a `TypeError` when the operator is used with them.

Chaining these operators requires care because of associativity. Writing a sequence of right-associative forms reads naturally from left to right, and the proposal shows several examples in which a series of fallback values is tried until one succeeds.

## Logical inversion

The unary operator `not EXPR` is made consistent with the protocol by allowing an object to define `__not__`. If the method is absent, the interpreter applies the usual truth test. This is a small change, but it means that symbolic and array types can give their own meaning to negation in a boolean context without the interpreter needing to know about them.

## Chained comparisons

The rich comparison chain `a < b < c` is currently written as two comparisons joined by `and`. The protocol allows the chain to be expressed as a sequence of circuit breaking calls. Each comparison result is passed to `__then__` of the next, so array types that return element-wise results can keep the whole chain in their own representation.

## Rationale

Using two method names instead of one keeps the two branches of a construct clearly separated. A single method that receives a flag would make the code at each call site harder to read, and it would hide the fact that one branch is lazy.

The callable passed to the methods is a deliberate choice. Passing the right operand as a value would require evaluating it eagerly, which would defeat the purpose. Passing a callable keeps evaluation under the control of the object, while the interpreter still guarantees at most one evaluation.

The restriction on the binary forms is intended to keep the operators predictable. Without it, programmers would be able to write expressions whose meaning depends on the type of an operand in ways that are hard to see when reading the code.

## Backwards Compatibility

Existing code is unaffected, because the protocol falls back to truth testing for types that do not define the new methods. The only new syntax is the binary use of `if` and `else` outside a conditional expression, which was a syntax error before and so cannot break working programs.

## Open Issues

The proposal leaves open how the sentinel result of the right-associative form should be chosen when the left operand does not supply one. It also leaves open whether `__not__` should be a separate method or should be derived from `__then__` and `__else__`. Several reviewers argued that deriving it would be simpler, but the draft keeps a separate method so that the default behaviour is explicit.

## Summary

This proposal defines one circuit breaking protocol, based on `__then__` and `__else__`, and uses it to describe conditional expressions, logical operators, None-aware operators, and comparison chains. It adds two binary forms of the conditional keywords defined in terms of the same protocol. Existing behaviour is preserved, and future operators can be added without new interpreter rules.
