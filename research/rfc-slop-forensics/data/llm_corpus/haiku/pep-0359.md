PEP: 359
Title: The "make" Statement
Author: Steven Bethard
Status: Withdrawn
Type: Standards Track
Created: 2004-02-28
Python-Version: 2.5
Post-History: 2004-03-01

Abstract

This PEP proposes a generalization of the class definition syntax, called the make statement. The proposed syntax and semantics parallel the syntax for class definition, so that the statement has the form:

    make <callable> <name> <tuple>:
        <block>

This is translated into the assignment:

    <name> = <callable>("<name>", <tuple>, <namespace>)

where <namespace> is the dictionary produced by executing <block>. The statement is mostly syntactic sugar for a class definition that sets a metaclass explicitly. Its purpose is to express more clearly the intent of creating something other than a class, while keeping a strong parallel to the existing class statement.

Motivation

Python programmers often want to create objects whose behavior is defined by a block of attribute assignments and method definitions, but whose type is not a class in the usual sense. Examples include named records, configuration objects, and small domain-specific structures. At present they use a class statement for this purpose, which carries the implication that a class is being created, and which requires a metaclass to be set in the body in order to change what is produced.

The class statement is easy to read for ordinary classes. When something other than a class is wanted, the reader is misled by the keyword and must look at the body to discover the real intent. A dedicated statement would state the intent at the start of the block.

The proposal also aims to make the connection between classes and metaclasses easier to learn. A programmer who understands how a class statement invokes a metaclass should be able to understand the make statement by analogy, and the make statement shows the mechanism directly, since the callable is named in the header.

Rationale

The design keeps the shape of the class statement so that readers already familiar with it can recognize the new form. The name of the new object is passed as the first argument to the callable, the tuple of bases or parameters is passed as the second, and the namespace produced by the block is passed as the third. These are the same three pieces that a metaclass receives when a class is created.

Using the same argument order as a metaclass call means that any callable which already acts as a metaclass can be used with the make statement without modification. This is a convenience, not a requirement, and callables that do not follow the metaclass convention may still be used if they accept the three arguments.

The statement does not introduce any new runtime machinery beyond the call. It is intended to be a clearer surface syntax for a pattern that already exists.

Specification

The make statement consists of the keyword make, a callable expression, a name, a tuple expression, and a block. The block is executed in a new namespace, which is then passed to the callable together with the name and the tuple. The result of the call is bound to the name in the enclosing scope.

The name is a string in the call, and it is also the target of the assignment. The tuple may be empty. The namespace is a dictionary, and the block may define functions, assign values, and perform other operations that a class body may perform.

Scoping inside the block follows the same rules as a class body. Names assigned in the block are placed in the namespace, and names that are read are looked up in the enclosing scope if they are not found locally.

Examples

A record-like object might be created as follows, with a callable that builds a new type from the namespace:

    make make_record Point ():
        x = 0
        y = 0

The result is a new object bound to Point. The reader sees immediately that the statement creates a record, and does not need to inspect a metaclass declaration to learn this.

Discussion

Some readers objected that the statement adds a new keyword, which increases the size of the language for a benefit that could be obtained with a helper function. The author responded that a function cannot capture the namespace produced by a block in the same way, and that the block syntax is the reason the statement is worth having.

Others argued that the metaclass mechanism already covers most of these cases and that a new statement should be justified by examples that cannot be written cleanly otherwise. The discussion did not converge on a list of such examples, and this was one factor in the decision to withdraw the proposal.

Reasons for Withdrawal

The PEP was withdrawn because the community did not agree that a new statement was warranted. The existing class statement, combined with metaclasses and helper functions, was judged sufficient for the cases that motivated the proposal. The author acknowledged that the syntax was not a clear improvement over those alternatives, and that the cost of a new keyword was significant.

The ideas in the proposal remain useful as a description of how class creation can be understood, and the discussion recorded in the mailing list is a reasonable reference for readers interested in the design space.
