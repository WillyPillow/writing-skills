Title: Improving License Clarity with Better Package Metadata

Abstract

This PEP defines how the licenses of Python projects are documented, so that license information is simpler and less ambiguous for package authors to write, for end users to understand, and for tools to process automatically. To achieve this, it:

- Adopts the SPDX license expression syntax as the means of expressing the license of a Python project.
- Defines how license files are included in source distributions and built distributions.
- Specifies the changes needed in the core metadata and in the corresponding keys of the project metadata table in pyproject.toml.
- Describes the changes needed in the source distribution standard, the built distribution standard, and the installed project standard.

The changes update the Core Metadata specification to version 2.4. The result is a license declaration that a machine can read without guessing, and that a human can check against a published standard.

Motivation

Python packages are licensed in many ways, and the metadata that describes those licenses has grown inconsistent over time. Some packages state their license in a free-text field, some use a classifier from a fixed list, and some provide a license file without any structured statement at all. The variety makes it difficult for tools to determine what a package permits, and it makes it difficult for downstream users to audit their dependencies.

Free-text fields are the most troublesome. Two packages may state the same license with different spellings, and a tool that tries to compare them must guess whether the strings refer to the same terms. Classifiers are more structured, but they do not express combinations of licenses, and they cannot describe a package that is available under a choice between two licenses.

The SPDX license expression syntax was designed for exactly this purpose. It names licenses with stable identifiers, it allows combinations with operators, and it is already used by many ecosystems and by many compliance tools. Adopting it gives Python packages a shared vocabulary.

Rationale

The PEP takes the SPDX syntax as given rather than inventing a new one. Authors who already know SPDX can use it directly, and tools that already parse it can read Python metadata without a special case.

The PEP does not require that every license be expressed as a single identifier. A package may use a compound expression, and it may use a custom identifier for a license that has no SPDX name, provided that the custom identifier is clearly marked.

License files are treated as first-class content. The PEP requires that the license text be included in distributions where the license requires it, and it provides a standard place for the files so that tools can locate them.

The deprecated license classifiers are not removed immediately. The PEP sets out a transition in which both the new expression and the old classifiers may appear, with the expression taking precedence where the two disagree, and a later revision removes the classifiers once the transition is complete.

Specification

The core metadata gains a license expression field and a license files field. The license expression field holds a single SPDX expression. The license files field lists paths to license files included in the distribution. A tool reading the metadata must treat the expression as the authoritative statement of the project's license.

In the pyproject.toml file, the project table gains a corresponding key for the license expression and a key for the list of license files. The values follow the same rules as the core metadata. Build backends are required to validate the expression and to reject values that are not valid SPDX.

The source distribution must include each license file listed in the metadata. The built distribution must include the same files in a dedicated location, and the installed project must make the files available to tools that inspect installed packages.

The PEP requires that tools accept a license expression that uses only identifiers from the SPDX list of licenses and exceptions, together with the operators and the reference to a custom license identifier. Other values are rejected with a clear error.

Backwards Compatibility

The PEP does not break existing packages. A package that uses the old fields continues to install, and a tool that does not understand the new fields continues to read the old ones. The transition is designed so that a package can publish both forms during the period when tools are updated.

Tools that compare licenses must be updated to use the new expression. Until they are, they may misreport the license of a package that uses the new fields only, and the PEP recommends that package authors continue to supply the old classifiers during the transition.

Security Implications

The license expression is not a security mechanism, and the PEP does not claim that it protects users from malicious packages. Its value lies in making license information accurate, which supports auditing and compliance work.

Reference Implementation

A reference implementation of the parser and validator is provided in a separate project. It checks the expression against the SPDX list and reports errors with the position of the problem in the input.

Rejected Ideas

One suggestion was to define a Python-specific license vocabulary. This was rejected because it would duplicate work already done by SPDX and would make Python packages harder to audit with existing tools.

Another suggestion was to allow free text alongside the expression. This was rejected because it would reintroduce the ambiguity that the PEP aims to remove.

Open Issues

The exact handling of license files for projects that are built from several sources is left to the build backend. The PEP recommends that backends document their behavior clearly, and that they follow the principle that the metadata should match the files in the distribution.
