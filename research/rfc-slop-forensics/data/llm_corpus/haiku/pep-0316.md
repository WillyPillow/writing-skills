# PEP 316: Programming by Contract for Python

| Field | Value |
|---|---|
| PEP | 316 |
| Title | Programming by Contract for Python |
| Status | Deferred |
| Type | Informational |
| Created | 2003 |

## Abstract

This document describes a proposal for adding programming by contract to Python. Design by Contract, a method made popular by the Eiffel language, lets a programmer state the conditions that a routine expects on entry and guarantees on exit, along with invariants that hold for the objects of a class. The proposal extends Python with syntax for invariant expressions on classes and modules, and for precondition and postcondition expressions on functions and methods. The expressions are checked at run time, usually only while debugging.

## Motivation

Assertions are a familiar tool. A programmer writes a statement that must be true at some point, and the program stops if it is not. Assertions are useful, but they are scattered through the code, and they say little about the contract between a function and its callers. A reader of a function must reconstruct from its body what the caller is required to provide and what the caller can rely on.

Contracts make these obligations explicit. A precondition states what the caller must establish before calling the function. A postcondition states what the function promises to establish when it returns. An invariant states a property that every instance of a class maintains between calls. Together they describe the design of the code in a form that can be checked.

Contracts are also useful as documentation. A contract that appears next to a function signature tells the reader more than a comment, because the statement is executable and can be verified. Tools can extract contracts from the source and present them in reference documentation, and they can use them to generate test cases.

Python has no built-in support for this style. The usual practice is to write assertions at the start of a function, or to document the requirements in a docstring and hope that they are respected. The proposal is intended to provide a standard form for the common case, so that programmers who want contracts do not each invent their own notation.

## Rationale

The design follows the general outline of Eiffel's approach while adapting it to Python's conventions. Expressions in contracts are ordinary Python expressions, so that programmers do not need to learn a new language for them. The language of the contract is the same as the language of the code, which keeps the notation small.

The proposal places contracts in the source as declarations attached to a function or class. A decorator is the natural form for this in Python, because it can be applied without changing the syntax of the language. The decorator records the expressions and wraps the function so that they are checked when the function is called. When checking is disabled, the wrapper is not installed, and the function runs at its normal speed.

The proposal distinguishes contracts from assertions. An assertion is a statement inside the body of a function that checks an internal condition. A contract is a declaration about the interface of the function. Keeping the two separate makes it possible to disable contract checking without affecting the internal checks of the implementation, and it makes it possible to read the interface without reading the body.

A design goal is that contracts should be inexpensive to write. A programmer who wants to add a single precondition should not have to write a large amount of boilerplate. The notation should also be easy to read, so that the contract can serve as documentation for someone who does not wish to run it.

## Specification

A function may be decorated with a contract declaration that takes one or more precondition expressions and one or more postcondition expressions. A precondition is evaluated with the arguments of the call bound to their parameter names. If any precondition evaluates to a false value, the call is rejected with an exception that identifies the contract and the function. A postcondition is evaluated after the function returns, with the names of the parameters and the special name for the return value bound. If any postcondition is false, an exception is raised that identifies the failure.

A class may have an invariant expression. The invariant is evaluated after the constructor completes and after each public method returns. It is evaluated with the instance bound to the name `self`. If the invariant is false, an exception is raised. The invariant is not checked during the execution of a method, because the object may be temporarily inconsistent while the method runs.

A module may also have an invariant, which is checked when the module is imported and after each function defined in the module returns. Module-level invariants are intended for global state that must remain consistent across calls.

Contract expressions are evaluated in the environment of the function or class in which they are declared. They may refer to names that are visible at that point, but they should not have side effects. The PEP does not enforce this restriction, but it recommends that contracts be pure, because a contract with side effects changes the behavior of the program when it is checked.

Contract checking can be controlled by a global setting. When checking is disabled, the contract expressions are not evaluated, and the decorated function is called directly. This allows the same code to run with contracts during development and without them in production.

## Inheritance

When a method overrides a method in a base class, the preconditions of the overriding method may be weakened but not strengthened, and the postconditions may be strengthened but not weakened. This rule follows from the requirement that a subclass must be usable wherever the base class is expected. A subclass that demands more of its callers than the base class demanded would violate the expectations of code written against the base.

The implementation of this rule is that the checks for a method include the checks inherited from the overridden method. A precondition in the base class must hold in addition to the preconditions of the subclass, and the postconditions of the base class must hold in addition to those of the subclass. The combination ensures that the effective contract is the conjunction of the contracts along the inheritance chain.

## Examples

The following example shows how a contract might be written for a function that computes an index into a sequence.

```python
@require(lambda seq, index: 0 <= index < len(seq))
@ensure(lambda result, seq, index: result == seq[index])
def element_at(seq, index):
    return seq[index]
```

The precondition states that the index must be in range. The postcondition states that the result is the element at that index. A caller who passes an index outside the range receives an error that names the precondition, which is more informative than the generic index error that the sequence would raise.

## Backwards Compatibility

The proposal is additive. Code that does not use contracts is not affected. The decorators are ordinary functions, and they do not change the behavior of any existing construct.

Contracts that are written in a style that depends on evaluation order, or that rely on side effects, may behave differently when checking is enabled or disabled. The PEP recommends against such contracts and notes that the difference is a consequence of the contract being checked rather than a defect of the mechanism.

## Performance

When contract checking is enabled, every call to a decorated function incurs the cost of evaluating its contracts. For functions with cheap contracts the cost is small, but for contracts that traverse large data structures the cost can be significant. The PEP leaves the decision about which contracts to enable to the programmer, and it recommends that expensive contracts be used mainly in tests.

## Open Issues

Several questions remain open. The first concerns how to report contract failures in a way that is useful to the user without exposing the internal state of the program. The second concerns the interaction with generators, whose postconditions are not straightforward to define because the function does not return a single value. The third concerns the exact form of the contract syntax, which may be better expressed as decorators, as comments that are processed by a tool, or as a new statement in the language.

The PEP does not settle these questions. It proposes the general approach so that the community can discuss the design and decide which details are most important.
