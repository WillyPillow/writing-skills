# PEP 499: Making `python -m foo` also bind `foo` in `sys.modules`

- **Type:** Informational
- **Status:** Rejected

## Abstract

When a module is run as a program with the `-m` option, as in `python -m package.module`, the interpreter executes it as `__main__`. The module object is bound to `sys.modules['__main__']`, and its `__name__` attribute is set to `'__main__'`. This makes the familiar guard `if __name__ == '__main__'` work, but it leaves the module's official name unbound. If the program later imports that name, the module is loaded a second time under a separate identity.

This document describes the problem in detail and proposes that the interpreter also bind the module under its real name in `sys.modules` for the duration of the run. The effect is that a later import finds the module already present and does not execute it again.

## Motivation

Consider a package with a module that defines a class and also contains a small command line entry point. A developer runs the module with `python -m package.module`, and the entry point creates an instance of the class. The class is defined once in the `__main__` namespace. If the entry point imports `package.module` to reach a helper function, Python executes the file a second time, and the second execution defines a second copy of the class.

The consequences can be subtle. An `isinstance` check against the class from one copy fails for an object created by the other. A registry keyed by class identity contains two entries for what the programmer thinks is one class. Module-level state is initialised twice, which may cause files to be opened twice or connections to be made twice.

Programmers encounter these problems regularly, and they are often confused by them, because the source appears to be imported only once. The behaviour is correct under the current rules, but it does not match what most people expect.

## Specification

The proposal changes the `-m` handling so that, in addition to binding the module as `__main__`, the interpreter also records the module under its official name in `sys.modules`. The module object is the same object in both places. Its `__name__` remains `'__main__'` so that the guard continues to work.

When a later import asks for the official name, the import system finds the entry and returns the existing module without executing it again. Imports of other names are not affected.

The entry is created before the module body runs, so that a circular import during execution of the module also finds the same object. The entry is removed only when the process exits, and it is not removed by the normal import machinery.

If the module is a package's `__init__`, the proposal binds the package name, and the behaviour is the same.

## Rationale

The change keeps the single identity that programmers expect. Once the module is running, it is the module, and any later import of its name should refer to that same object. The guard is still based on `__name__`, so no existing programs need to change how they test whether they are the main program.

Binding the module under its real name is a narrow change. The interpreter already has the module object and the name at the point where `-m` is handled, so the additional step is small. The proposal avoids changing any other part of the import system.

The proposal leaves `__name__` as `'__main__'` because changing it would break the guard, which is one of the most widely used idioms in Python.

## Problems raised in discussion

The most common objection was that the proposed behaviour is surprising in a different way. A programmer who writes code inside the module might expect `__name__` to equal the module's official name, and might be confused when it does not. The proposal's answer was that the guard idiom is more important than the name's value, and that documentation can explain the situation.

A second objection concerned the case where the module is run with `-m` but its official name refers to a different file, for example because the package was installed in an unusual way. In that case the proposal would bind the wrong module, and the discussion proposed that the interpreter check that the file it runs matches the path found for the name, and warn when it does not.

A third objection was that the change would hide the double import problem rather than solve it. Some participants preferred that the interpreter warn the user, so that the programmer knows the module is being loaded twice and can restructure the code. The proposal replied that warnings are often ignored and that the correct behaviour should be the default.

Other participants pointed out that the problem can already be avoided by moving shared code into a separate module, and that this is the recommended practice. They argued that changing the interpreter would encourage programmers to continue writing modules that are both programs and libraries, which the proposal authors did not dispute, but they regarded the change as a practical safety net.

## Backwards Compatibility

Programs that run modules with `-m` and do not import them by name are not affected. Programs that rely on the second execution of the module are unusual, and the proposal argues that they are likely to be buggy. The change would therefore alter the behaviour of a small number of programs, and in most of those cases the new behaviour would be the one the authors intended.

The proposal recommends a deprecation period in which the interpreter emits a warning when a module that is run with `-m` is imported again under its official name, so that affected programs can be identified.

## Reference Implementation

A patch to the interpreter's startup code was written. It binds the module under its official name immediately after the module object is created and before the code is executed. The patch was tested against the standard library test suite, and a small number of tests that depended on the double import were updated.

## Status

The proposal was rejected. The main reasons were that the change would alter the behaviour of a basic command line feature for a problem that is better solved by restructuring code, and that the proposed warning would not address the root cause. The decision was recorded as a rejection rather than a deferral, so the behaviour of `-m` remains as it was.

Documentation was updated to explain the double import problem and to recommend the pattern of keeping the entry point small and importing the rest of the code from a regular module. This has been the recommended practice ever since.

## Summary

Running a module with `-m` binds it as `__main__`, but a later import of its real name executes it again and creates a second copy of its contents. This document proposed that the interpreter bind the module under its official name as well, so that the two identities coincide. The idea was rejected in favour of documentation and of restructuring code, but the problem it describes remains a common source of confusion among Python programmers.
