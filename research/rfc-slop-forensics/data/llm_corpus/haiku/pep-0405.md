Abstract
========

This PEP proposes a lightweight mechanism for creating virtual environments in Python. A virtual environment is a directory containing its own Python executable and its own site directories, where third-party packages can be installed without affecting the system-wide installation. The environment shares the standard library with the base interpreter. It can optionally be isolated from the system site directories, so that only packages installed inside the environment are visible. The mechanism is designed to be small, to require no privileges, and to work on all platforms that Python supports.

Motivation
==========

Python developers frequently need to run several projects that depend on incompatible versions of the same library. The usual response is to install packages into the system or user site directory and hope the versions do not clash. That approach fails as soon as two projects need different versions of a package, and it makes it hard to reproduce an environment on another machine.

Third-party tools have filled the gap. Several popular packages create isolated environments by copying or symbolically linking the interpreter and adjusting the search path. Each tool implements its own conventions, and users must learn a different tool for each platform or distribution. The standard library has no equivalent, and the lack of one forces every tutorial to explain the same workaround.

This PEP asks for a single, supported way to create such environments. It does not attempt to manage package versions, resolve dependencies, or fetch packages from a repository. Those tasks belong to installers, which can operate on any environment that the core mechanism provides. The core goal is narrow: to make an isolated site directory available to a Python process, with a predictable layout and a minimal amount of setup.

Specification
=============

A virtual environment is created by running the ``venv`` module of the base interpreter with a target directory as its argument. The module creates a configuration file at the top of the directory. The file records the location of the base interpreter and whether the environment should include the system site directories. The configuration file is the key input for the new behavior, and the interpreter reads it at startup.

When the interpreter starts, it looks for a configuration file in the directory that contains the executable, and then in its parent. If the file exists, the interpreter sets the ``sys.prefix`` and ``sys.exec_prefix`` values to the environment directory, but it keeps the base prefix available in ``sys.base_prefix`` so that the standard library can still be found. The site directories of the environment are added to the search path. Unless the configuration requests otherwise, the system site directories are not added.

The environment contains a ``bin`` directory on POSIX systems, or a ``Scripts`` directory on Windows, holding the interpreter and an activation script for common shells. The activation script is a convenience and is not required. Running the interpreter directly from the environment's directory gives the same result.

Installers install packages into the environment's site directory. Because the directory is on the search path only for that interpreter, the packages cannot be imported from another interpreter by accident.

Isolation
---------

The default setting excludes system site directories. A user may request inclusion through a command-line option, which is useful for environments that need a system package that is difficult to install into an isolated directory. The option is recorded in the configuration file so that the choice remains stable over time.

The isolation applies to ``sys.path`` only. It does not restrict the environment from reading files elsewhere on the filesystem, and it does not change the behavior of the operating system. The PEP does not claim to be a security boundary.

Backwards Compatibility
=======================

Existing installations are unaffected. The configuration file is looked for only in the directory of the executable and its parent, and a normal installation does not contain one. Programs that inspect ``sys.prefix`` will see a different value only inside a virtual environment, and the new ``sys.base_prefix`` attribute allows code to find the original installation when it needs to.

Tools that previously assumed that ``sys.prefix`` was constant may need adjustment. The PEP recommends that such tools use ``sys.base_prefix`` when they need the installation location and ``sys.prefix`` when they need the environment location.

Rationale
=========

The design relies on a configuration file rather than a copied interpreter because a copy is fragile. Copying the executable and its shared libraries requires knowledge of the platform, and it breaks when the base installation is upgraded. A configuration file that points back to the base interpreter has no such dependency. The environment remains small and can be recreated quickly.

The decision to keep the standard library shared also follows from a practical concern. Copying the library would multiply the size of every environment and would make upgrades difficult. Sharing it means that a single security fix in the base installation applies to all environments built on it.

Alternatives that rely on rewriting the search path through environment variables were considered and rejected. Environment variables are inherited by child processes, which makes it easy for one environment to leak into another, and they are awkward to inspect. A file on disk is visible, versioned, and tied to a specific directory.

Reference Implementation
========================

The reference implementation adds a ``venv`` module to the standard library and modifies the startup sequence of the interpreter to read the configuration file. The changes to the interpreter are confined to the site initialization code. The module provides a command-line entry point and a programmatic interface that installers can call.

Discussion
==========

Several contributors asked whether environments should be relocatable, so that a directory could be moved without breaking it. The draft does not require this, because the configuration file records absolute paths. A later revision may make the recorded path relative, but the present design favors simplicity.
