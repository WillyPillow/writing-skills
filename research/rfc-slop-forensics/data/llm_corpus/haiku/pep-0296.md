PEP: 296
Title: Adding a bytes object type

Status: Draft
Type: Standards Track
Created: (to be assigned)
Python-Version: 2.x

Abstract
========

This PEP proposes a new standard type and built-in constructor named ``bytes``. A ``bytes`` object is a compact, mutable-or-immutable sequence of small integers in the range 0 through 255, designed for raw binary data. Python's existing ``str`` type is a sequence of characters, and the current treatment of binary data relies on strings whose elements are used as bytes. That arrangement works, but it blurs the line between text and binary content, invites subtle encoding bugs, and makes it hard for tools to tell which values should be decoded. A dedicated type removes that ambiguity.

Motivation
==========

Python programmers routinely handle data that is not text: network packets, file formats, cryptographic digests, compressed streams, and images. Today these values are stored in ``str`` objects whose characters happen to lie in the byte range. The Python 2 ``str`` type plays two roles at once. It holds character data in an unspecified encoding and it holds raw bytes. A function that receives such a value cannot determine which role it is playing without outside information.

The problem grows with the Unicode work in progress. As text becomes more prominent, the implicit conversions between a byte-oriented string and a character string produce errors that appear far from their cause. A program that reads a binary file and concatenates the result with a Unicode literal may fail only on certain inputs. A distinct byte type makes such mixing an explicit operation, which can be checked and reported at the point of error.

There is also a performance argument. A bytes object can store its contents in a plain C array with no per-character overhead, and it can offer the operations that binary code needs, such as slicing, searching, and conversion to and from integers, without pretending that the data is text.

Specification
=============

The new type is called ``bytes``. Its instances are sequences of integers in the range 0 to 255. The type supports indexing, slicing, concatenation, repetition, membership testing, and iteration. Indexing returns an integer, not a one-character object, which matches the behavior that binary code expects.

The built-in constructor ``bytes`` accepts several forms. Called with no arguments, it returns an empty object. Called with an integer, it returns a zero-filled object of that length. Called with an iterable of integers, it builds an object from those values, and each value must be in range. Called with a string and an encoding name, it encodes the string. The explicit encoding argument is required when a string is passed, so that no hidden conversion takes place.

Methods mirror those of ``str`` where the operation makes sense for binary data. These include ``find``, ``split``, ``replace``, ``strip``, ``startswith``, and ``endswith``. Methods that only make sense for text, such as case conversion for non-ASCII characters, are omitted. The ``decode`` method converts a bytes object into a string using a named encoding.

A mutable companion type, ``bytearray``, is also proposed. It shares the same interface but can be modified in place. The two types are designed so that a function accepting either can treat both as a read-only buffer.

Interaction with str
--------------------

Implicit mixing of bytes and text is an error in the proposed design. Concatenating a bytes object with a string raises ``TypeError``. Comparison between the two returns false rather than raising, so that membership tests in mixed collections behave predictably. Printing a bytes object shows its representation with escape sequences for non-printable values, so that the contents are never mistaken for decoded text.

Backwards Compatibility
=======================

Existing code that relies on the byte-string behavior of ``str`` will break in some cases. The transition plan keeps ``str`` as the default literal type for the first releases. A future ``-b`` flag warns when bytes and text are mixed, so that developers can find affected code before the default changes. The migration is expected to take several releases, and it is described in a separate document.

Rationale
=========

Several alternatives were considered. One was to introduce a binary-only module that wraps the existing string type. That approach keeps the confusion in the core language and merely moves it elsewhere. Another was to rely on the array module, which stores typed values but is not well integrated with string operations and lacks the literal syntax that binary code needs. A third was to extend the buffer protocol without a new type. The buffer protocol remains important and this PEP does not replace it, but a buffer alone does not give the type its own identity, its own literal form, or its own methods.

The chosen design favors explicitness. A programmer who wants to convert between text and bytes must say so, and the encoding must be named. This costs a few extra characters in code that does conversion, and it prevents a large class of defects.

Implementation Notes
====================

The implementation stores the contents in a contiguous buffer with a length field, and it caches a hash value for immutable instances. The C API provides functions that create bytes objects from buffers without copying, where the caller can guarantee that the buffer remains valid. Literal syntax uses a ``b`` prefix before a quoted string, and the escape rules for such literals are restricted to the byte range.

Open Questions
==============

The proposal leaves open whether ``bytes`` should support the ``%`` formatting operator. Some respondents argued that binary protocols need it for building headers, while others considered it a source of confusion. The reference implementation omits it in the first version. A later PEP may add it once the need is clearer.

It is also unsettled whether the default encoding for the string constructor should be ASCII or the locale encoding. The draft requires an explicit encoding, which avoids the question for new code, but it leaves older call patterns to be settled during the transition.
