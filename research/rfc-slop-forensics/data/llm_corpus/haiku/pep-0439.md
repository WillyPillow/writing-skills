# PEP 439: Inclusion of implicit pip bootstrap in Python installation

**Type:** Standards Track
**Status:** Draft
**Topic:** Packaging, Installation

## Abstract

This PEP proposes that every Python installation ship a small bootstrap executable whose job is to install the pip package manager into the interpreter's own environment. The pip implementation itself is not added to the standard library. The bootstrap uses a wheel that is bundled with the installation, so it does not depend on network access at install time. The proposal does not introduce any package management features beyond those already defined by the wheel binary format (PEP 427) and the installer requirements that follow from it.

## Motivation

Most people who write Python code eventually need a third-party library, and the step that gets them there is installing that library. For a new user, that step involves several pieces of knowledge that are not obvious: that a package installer exists, that it is named pip, that it must be matched to a specific interpreter, and that it may not be present at all on a given system. Each of these is a point where a beginner can stop.

The situation has been uneven across platforms and distributions. Some operating system packages install pip alongside the interpreter and others leave it out, because they treat it as a separate package. Python installers for Windows and macOS have historically offered it as an optional component. A virtual environment created with the standard `venv` tooling has no installer at all until one is added. In each case the user must discover the gap and repair it by hand.

The usual repair has been to download a script from the network and run it with the interpreter. That works, but it creates two problems. First, it makes a basic installation depend on a live connection and on the availability of a remote host. Second, it asks the user to run code fetched from an address they have to trust without any local way to check what they are getting. A bootstrap that carries its own wheel removes both problems, because the code that is run was delivered with the interpreter and can be verified when the interpreter was built.

## Rationale

The aim is a single, predictable answer to the question "how do I get a package installer for this Python?" The answer should be the same whether the interpreter came from a python.org installer, a distribution package, or a build from source. It should also work inside a freshly created virtual environment.

Keeping pip out of the standard library is deliberate. The pip project releases on its own schedule and needs to fix bugs and adapt to packaging changes without waiting for interpreter releases. Folding it into the standard library would tie those cycles together and would turn the standard library into a maintenance obligation for a large and fast-moving codebase. A bootstrap that installs pip from a bundled wheel keeps the two projects independent while still making pip available by default.

The bootstrap should also be small. It should not contain installation logic of its own beyond what is needed to unpack a wheel and hand it to the installer. Anything more complicated belongs in pip.

## Specification

The installation gains a module that can be run as a program, which this PEP calls the bootstrap. Running it with the interpreter causes the following steps to occur:

1. The bootstrap locates the wheel for pip that was placed in a known directory when the interpreter was built or packaged. The wheel's file name identifies the pip version it contains.
2. The bootstrap checks whether pip is already importable from the interpreter's active environment. If it is, and its version is at least as new as the bundled one, the bootstrap exits without changes.
3. Otherwise the bootstrap installs the bundled wheel into the active environment's site-packages directory. It uses only the standard library to do so, so it can run before any other package is available.
4. The bootstrap reports what it did and exits with a status code that indicates success or failure.

The bootstrap installs into the environment that is active when it runs. Inside a virtual environment, this is the environment's own site-packages. Outside one, it is the interpreter's default location. It never writes to a system-wide location that the current user does not already control, and it does not require administrator rights for a per-user installation.

Re-running the bootstrap must be safe. Installing an older bundled pip over a newer one would be a regression, so the bootstrap compares versions first. A user who has deliberately installed a newer pip keeps it. An option to force reinstallation is provided for users who need to repair a broken installation.

The bundled wheel is produced during the build of the interpreter, and its hash is recorded in a manifest that ships alongside it. The bootstrap verifies the hash before installing. A mismatch causes it to stop with an error and to leave the environment unchanged.

## Security Considerations

The main benefit of bundling is that the bootstrap never needs to reach the network. A user who runs it offline gets the same result as one who runs it on a fast connection, and no remote code is executed. The hash check guards against accidental corruption and against tampering with the wheel after it has been placed on disk, although it does not protect against an attacker who can replace both the wheel and the manifest. Distributors who need stronger guarantees can sign the manifest using their existing package signing process.

The bootstrap does not change how pip itself resolves or downloads packages. Once pip is installed, its normal index configuration and its normal trust model apply.

## Backwards Compatibility

Existing programs are not affected. The bootstrap is a new entry point, and nothing in the interpreter runs it automatically. Users who already have pip installed will see no change in behavior unless they choose to run the bootstrap. Distributions that already package pip separately may keep doing so. They can disable the bundled wheel at build time, in which case the bootstrap reports that no bundled copy is present and exits without error.

The module adds no import-time side effects, so importing the standard library is not slowed down and no new files appear unless the bootstrap is executed.

## Alternatives Considered

Downloading a bootstrap script at install time was the traditional approach. It was rejected for the reasons given above, namely the network dependency and the difficulty of verifying a script fetched on demand.

Including the full pip implementation in the standard library was rejected because of the coupling it would create between release cycles and the maintenance cost it would place on core developers.

Leaving the matter to distributions was rejected because it would keep the current inconsistency in place. Distributions remain free to make their own choices, and this proposal does not prevent them from doing so.

## Open Issues

Several questions remain open. Distributions that split the interpreter into many small packages will need to decide where the bundled wheel lives so that the bootstrap can find it. The manifest format needs to be fixed before the first release that includes the bootstrap. The bootstrap's behavior when the bundled wheel is older than a pip installed in a parent environment should be specified more precisely, since virtual environments can see packages from their parent in some configurations.

## Reference Implementation

A prototype of the bootstrap exists as a short module of a few hundred lines. It locates the bundled wheel, verifies the manifest, compares versions using the same rules as pip, and performs the installation by invoking the wheel installer. The prototype has been tested on Linux, macOS and Windows against fresh virtual environments and against interpreters with pip removed.
