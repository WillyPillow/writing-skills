# PEP 3153: Asynchronous IO support

| Field | Value |
|---|---|
| PEP | 3153 |
| Title | Asynchronous IO support |
| Status | Deferred |
| Type | Standards Track |
| Created | 2011 |
| Python-Version | 3.4 |

## Abstract

This PEP describes an abstraction of asynchronous input and output for the Python standard library. The aim is to define a set of interfaces that can be implemented by many different asynchronous IO backends, so that a library author can write code that runs unchanged on top of more than one event loop. The abstraction describes what an asynchronous transport and protocol look like, and it leaves the mechanism of waiting for readiness to the backend.

## Motivation

Python programs that handle many connections at once have several choices of event loop. The standard library at the time of writing contained a selector-based module and a set of socket utilities, while third-party projects provided their own loops with different conventions for callbacks, futures, and error handling. A library that wants to offer network functionality must either pick one of these loops or write a separate version for each.

The result is that network code is hard to share. A protocol implementation written against one loop cannot easily be used with another, and users who want to move from one loop to another must rewrite their code. This has been a source of friction in the community for some time, and it creates a barrier for library authors who want their code to be used widely.

The purpose of this PEP is to provide a common vocabulary. It does not require that any one loop be used, and it does not attempt to replace the existing low-level modules. It describes the interfaces that a loop must provide for protocols and transports to be written against them, and it leaves room for each backend to optimize its own internal machinery.

## Rationale

The design is based on the observation that most asynchronous network code is organized around two concepts. A transport represents a connection that can send and receive bytes. A protocol represents the logic that decides what to send and how to interpret what is received. The transport notifies the protocol when data arrives, when the connection is made, and when it is lost. The protocol calls methods on the transport to write data and to close the connection.

Separating these two concepts makes it possible for the same protocol to run over different transports, such as a TCP connection, a Unix domain socket, or a pipe. It also makes it possible for the same transport to be used with different protocols. Each side of the split can be tested independently, and each can be replaced without affecting the other.

The abstraction is deliberately callback-based. Callbacks are less convenient than coroutines for many programmers, but they map naturally onto the event loops that the backends already implement, and they do not force a particular style of programming onto users who do not want it. A higher-level interface built on coroutines can be provided separately, and this PEP does not preclude it.

## Specification

A backend provides a loop object. The loop has methods for creating a connection to a remote address, for creating a server that listens for connections, and for scheduling callbacks to run at a given time. The loop is responsible for calling the protocol methods at the correct moments and for ensuring that they are called from a single thread of control.

A protocol is an object with methods that are called by the transport. The method for a new connection receives the transport as an argument. The method for received data receives a bytes object. The method for a lost connection receives an optional exception that explains why the connection ended. Protocols may also implement a method that is called when the write buffer has been drained, which allows them to apply flow control.

A transport is an object with methods for writing data, for pausing and resuming reading, for closing the connection, and for querying information about the connection such as the peer address. Writes are buffered by the transport. A protocol that writes faster than the peer can read is notified through the flow-control methods, and it is expected to stop producing data until it is told to resume.

Errors are reported through the protocol rather than raised in the caller's context. An error during a write is delivered as a notification to the protocol, and the transport is closed. This avoids the situation in which an exception is raised at an arbitrary point in the application code, far from the place where the connection was used.

Backends are free to implement these interfaces in any way that satisfies the stated behavior. A backend based on the operating system's readiness notifications, a backend based on completion ports, and a backend that emulates asynchronous behavior with threads are all compatible with the abstraction, provided that they preserve the ordering and threading guarantees described above.

## Threading model

All callbacks are invoked from the thread that runs the loop. A protocol implementation does not need to lock its own state against concurrent callbacks, because the loop serializes them. Code that needs to interact with the loop from another thread must use a documented thread-safe method on the loop, which schedules the work to run in the loop's thread.

This model is simple to reason about and matches the behavior of the common backends. It also makes it possible to write protocols that are free of locks, which is a significant advantage for code that is maintained by many people.

## Backwards Compatibility

The PEP is additive. It does not change the behavior of existing modules, and it does not require any existing code to be modified. Code that uses the lower-level socket and selector modules directly will continue to work unchanged.

The names chosen for the interfaces are intended to avoid collisions with existing names in the standard library. Where a collision is possible, the PEP recommends that the new names be placed in a separate module, so that existing code can import them explicitly.

## Implementation

A reference implementation is proposed as a module in the standard library that provides the core loop and the basic transports and protocols. The reference implementation is expected to be small enough to read and review, and it is intended to serve as an example for third-party backends. Test cases are written against the abstract interfaces so that they can be run against any conforming backend.

## Open Issues

Several questions remain. The most important concerns the handling of errors that occur after a connection has been closed by the application, which the abstraction must define precisely to avoid races. A second concerns the interaction with signal handling, which differs between platforms and is difficult to make uniform. A third concerns whether the abstraction should include a standard way to represent datagram transports, or whether this should be deferred to a later version.

The community also needs to decide whether a coroutine-based interface should be part of the standard library at the same time as the callback interface, or whether it should be developed separately once the callback interface has been tested in practice.
