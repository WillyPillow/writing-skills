PEP: 445
Title: Add new APIs to customize Python memory allocators
Author: Victor Stinner <victor.stinner@gmail.com>
Status: Final
Type: Standards Track
Content-Type: text/x-rst
Created: 2013-06-25
Python-Version: 3.4

Abstract
========

This PEP proposes new application programming interfaces (APIs) for customizing
the memory allocators used by Python. The only implementation required to
conform to this PEP is CPython. Other implementations may choose to be
compatible with it, or to reuse a similar scheme for their own allocators.

Rationale
=========

CPython allocates memory through a small set of functions. Some of these
functions are thin wrappers around the system allocator, while others are
specialized for small objects, which are the most common allocations in a
running program. Developers who need to debug memory problems, measure
allocation behavior, or run Python in an unusual environment currently have to
modify the source code of the interpreter to change how memory is obtained.
That is a barrier to experimentation and to deployment in constrained settings.

Several concrete needs motivate the proposal. Debugging tools need to detect
buffer overflows and use after free errors, which they do by wrapping the
allocator and adding guard bytes or poisoning freed memory. Profilers need to
record every allocation and deallocation to identify where memory is spent.
Embedded and embedding applications may need an allocator that draws from a
fixed pool, or one that integrates with an existing memory manager. Each of
these needs is poorly served by the current design, which offers no hook at
all.

The proposal introduces a small, stable interface that lets a program replace
the allocator for each category of allocation without recompiling the
interpreter. It also provides a way to install wrappers that intercept calls
while leaving the underlying allocator in place.

Specification
=============

Memory allocation in the interpreter is divided into three domains. The raw
domain is used for allocations that may be made without holding the global
interpreter lock, such as those needed by the operating system interface. The
memory domain is used for general purpose allocations made while the lock is
held. The object domain is used for the memory of Python objects. Each domain
has its own set of functions and can be customized independently.

For each domain, the interface defines a structure that holds a context pointer
and four function pointers: one each for allocating a block, allocating a zeroed
array, reallocating a block, and freeing a block. A program installs a new
allocator by filling in this structure and passing it to a function that
selects the domain. The previous allocator is returned by the same function
so that a wrapper can call it.

The domains may be customized before the interpreter is initialized. Changing
an allocator after initialization is permitted only if the new allocator is
compatible with the memory already in use, which means that blocks allocated
by the old allocator must be freed by functions that know how to handle them.
The documentation for each domain states the rules that apply.

A debug mode is provided that wraps the default allocators with checks. When
it is enabled, the interpreter fills newly allocated memory with a known
pattern, fills freed memory with another pattern, and places guard bytes
before and after each block. These checks detect many common errors at the
cost of extra memory and time. The debug mode can be enabled from the command
line or by an environment variable, and it does not require a new build.

The interface also includes a function that reports whether the interpreter is
running under a debugger or profiler that has installed hooks. Code that
depends on this information can adjust its behavior accordingly.

Backwards Compatibility
=======================

The default allocators are unchanged, so programs that do not use the new
interface behave exactly as before. The structures and functions are new
additions, and they do not alter any existing public name. Extension modules
that call the existing allocation functions continue to work, because those
functions remain available and continue to route through the current domains.

A small performance cost is incurred by the indirection through function
pointers. The authors measured this cost on a set of benchmarks and found it
to be within the normal variation of the test machines, so the proposal does
not change the default configuration in a way that would be noticed by most
users.

Reference Implementation
========================

A reference implementation was written in C as a set of changes to the
interpreter's memory handling. It defines the domains, the structures, and the
selection functions. It also includes the debug wrappers and a set of tests
that exercise each domain with a custom allocator. The tests check that
allocations are routed correctly, that the debug checks detect deliberately
introduced errors, and that the default configuration produces the same results
as before.

Rejected Ideas
==============

An early proposal was to allow a single allocator to be chosen for the whole
interpreter, with no distinction between domains. This was rejected because the
raw domain has different requirements, in particular that it must not require the
interpreter lock, and a single allocator could not meet both sets of needs.

Another proposal was to require all allocators to be thread safe. The authors
concluded that this requirement would make the interface harder to use and
would not be necessary for the domains that are only used with the lock held.
The documentation instead states the locking rules for each domain.
