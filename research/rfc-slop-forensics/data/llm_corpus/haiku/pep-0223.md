PEP: 223
Title: Change the Meaning of \x Escapes
Author: Tim Peters
Status: Rejected
Type: Standards Track
Created: 2000
Python-Version: 2.1

Abstract

This PEP proposes that the \x escape sequence in both 8-bit and Unicode string literals consume exactly the two hexadecimal digits that follow it. Under the current behavior, \x consumes as many hexadecimal digits as it can find, which makes some strings ambiguous or surprising to read and write. The change is small, affects few existing programs, and brings Python's string syntax closer to the regular expression dialect that most programmers already know.

Motivation

A Python string literal such as "\x1234" is currently read as a single character with the value 0x1234. Anyone writing a byte string that should contain the byte 0x12 followed by the characters "34" must know that the escape will swallow the trailing digits. Writing "\x12" + "34" is the workaround, and it is easy to forget.

The problem is not only theoretical. In the 8-bit string world, a program that builds a binary protocol message may write "\x0a" and then append characters that happen to be hex digits. The resulting byte string is not what the programmer intended. The reader of the source code has to count characters carefully, and the reader is often not the author.

The Unicode story compounds the problem. Unicode string literals use the same escape syntax, but a longer escape is needed for characters above U+00FF, and the rules for when to stop consuming digits differ from the rules for 8-bit strings. The language has two overlapping conventions for one syntax element, and this makes the lexer harder to explain and harder to implement consistently.

Perl's regular expression engine, and the C family of languages in their more careful forms, read exactly two digits after \x in the common case. Programmers who move between Python and these languages are surprised by the difference. A regular expression written in Python that uses \x41 to match a letter should not behave differently when the same escape appears in a literal string that is passed to a regex engine.

Specification

Under this proposal, the escape sequence \x followed by two hexadecimal digits denotes the character whose code is given by those two digits. The lexer consumes exactly two digits. If fewer than two valid hexadecimal digits follow, the escape is an error. This rule applies to both 8-bit string literals and Unicode string literals.

To express characters beyond the range of two digits, the programmer uses the \u escape in Unicode strings, which consumes four digits, and the \U escape, which consumes eight. Byte strings do not have a Unicode escape, so characters above 0xFF cannot be written in them directly, which is consistent with their definition.

The change affects only strings in which \x is followed by three or more hexadecimal digits. Such strings are rare, and in nearly all of them the old reading was not intended by the author. The proposal therefore expects that most existing code is unaffected.

Transition

Because the change alters the meaning of existing valid programs, a transition period is needed. During the first release that includes the change, the interpreter should emit a warning for any string literal in which \x is followed by more than two hexadecimal digits. The warning gives the source position and the value that the old rule would have produced, so that the author can decide whether to rewrite the literal.

In the following release, the warning becomes an error only for code that the author has explicitly enabled through a compiler option. In the release after that, the new meaning becomes the default. This schedule gives third-party code time to adapt without silently changing behavior in a single step.

The standard library and the test suite should be checked and corrected before the warning is introduced, so that the warning does not appear in code that ships with the interpreter.

Rationale

The chief argument for the change is clarity. A two-digit rule is easy to state, easy to check by eye, and easy to teach. A programmer who reads "\x7f" knows exactly what is meant, without needing to look at the next character.

The second argument is compatibility with neighboring technologies. Programmers who write regular expressions, C code, or Perl scripts already expect two digits, and matching that expectation reduces the number of rules a newcomer must learn.

The third argument concerns the Unicode design. Separating the byte escape from the Unicode escapes gives each string type a clear and distinct set of rules, and it allows the Unicode escapes to be wider without overloading \x.

Alternatives

One alternative is to leave the language unchanged and document the behavior more clearly. This preserves compatibility exactly, but it does not address the source of confusion, and the documentation burden falls on every new programmer.

A second alternative is to require braces for long hexadecimal escapes, for example \x{1234}. This is unambiguous, but it adds a new syntax and does not help the common case of short escapes, which would still need to be read carefully in older code.

A third alternative is to keep the current rule for Unicode strings and change it only for 8-bit strings. This was considered, but it leaves the two string types with different rules, which is the inconsistency the proposal is meant to remove.

Risks

The main risk is that some programs will change behavior silently in the transition period if their authors ignore warnings. The proposal mitigates this by making the warning visible in the normal compilation path and by providing a specific message that names the affected literal.

A second risk is that tools that parse Python source, such as syntax highlighters and code formatters, may need to be updated to match the new rule. The authors of these tools are expected to be notified early.

Implementation

The change is confined to the lexer and to the string-decoding routines. The lexer must count digits after \x and stop after two. The decoding routine for Unicode strings is unaffected, except that it no longer receives longer \x sequences from the lexer. A patch implementing the change, with tests for the boundary cases, should accompany the acceptance of this proposal.
