# PEP 3134: Exception Chaining and Embedded Tracebacks

**Type:** Standards Track
**Status:** Draft
**Topic:** Language Reference

## Abstract

This PEP proposes three standard attributes on exception instances. The first, `__context__`, records an exception that was being handled when another exception was raised, and so provides implicit chaining. The second, `__cause__`, records an exception that the programmer named explicitly as the reason for another, and so provides explicit chaining. The third, `__traceback__`, stores the traceback object so that it travels with the exception rather than existing only in the interpreter's current state. A new form of the `raise` statement, `raise ... from`, sets the `__cause__` attribute.

## Motivation

When an exception is raised while another is being handled, the first exception is frequently the more useful piece of information for diagnosing the failure. In Python 3, however, the original exception is discarded as soon as the handler finishes or raises a new exception. The programmer sees only the final error, and the connection between the two is lost unless the handler happened to save the original.

A common case is a library that catches a low-level error, such as a failed read from a file, and raises a higher-level error that describes the operation in domain terms. The low-level detail matters to the person debugging, but in practice it is often omitted. Another common case is cleanup code. A `finally` block or a context manager's exit method may raise its own error while an earlier error is still propagating. Both errors matter, but the second one tends to hide the first.

Earlier versions of the language relied on the interpreter's internal state to carry this information in some situations. That state was not accessible from ordinary code, could not be attached to an exception that was caught and later re-raised, and did not survive being passed between threads or stored in a container. The proposal makes the relationships explicit by storing them on the exception object.

## Specification

Every exception instance gains three attributes.

The `__context__` attribute is set automatically by the interpreter. When an exception is raised while another exception is being handled, the interpreter stores the handled exception in the new exception's `__context__`. The attribute is `None` when there was no such handled exception. The interpreter does not overwrite an existing value, so an exception keeps the context it was first raised in.

The `__cause__` attribute is set only by explicit request. The statement `raise X from Y` raises `X` after assigning `Y` to `X.__cause__`. The value of `Y` must be an exception instance or `None`. When `Y` is `None`, the statement sets `__cause__` to `None` and also marks that the implicit context should not be displayed. This allows a library to suppress noise from an internal error that the user does not need to see.

The `__traceback__` attribute holds the traceback object that describes where the exception was raised and the frames it passed through. It is set when the exception is raised, and it is updated as the exception propagates outward through further frames. Storing it on the exception makes the traceback available to code that catches the exception and passes it elsewhere, such as a logging system or a worker thread that reports its result to a parent.

When the interpreter prints an unhandled exception, it prints the chain. If `__cause__` is set, the cause is printed first, followed by a line stating that the following exception was the direct result of it. If `__cause__` is absent and `__context__` is set, the context is printed first, followed by a line stating that another exception occurred during the handling. Each exception in the chain is printed with its own traceback. Cycles in the chain are detected so that printing terminates.

## Rationale

The distinction between implicit and explicit chaining reflects two different situations. Implicit chaining records what the interpreter observed, and the programmer does not have to do anything for it to happen. Explicit chaining records a decision the programmer made, and it should take precedence in the display because the programmer has already judged the relationship to be meaningful.

The name `__context__` was chosen to describe the circumstances in which the exception occurred, not to imply that the first exception caused the second. The name `__cause__` is reserved for the explicit case so that the two are not confused. The three attributes use the double-underscore convention because they are maintained by the interpreter and should be read rather than assigned by ordinary code, although assignment is permitted.

Storing the traceback as an attribute is a separate but related change. Keeping it on the exception object means that code which catches an error and needs its location can obtain the location without relying on a global record. This matters most in code that re-raises an error in another context, where the original frames would otherwise be lost.

## Backwards Compatibility

Code that catches exceptions and does not examine these attributes is unaffected. The attributes are additions, and they do not change the meaning of any existing statement other than the new `from` clause. Programs that print tracebacks will show more lines when an exception was raised during handling, and some programs that parse the output of the default traceback printer may need adjustment.

The `raise ... from` syntax is new and does not conflict with any existing construct. Code that previously used `raise` with a single argument behaves as before.

## Performance

Assigning the context requires the interpreter to examine the currently handled exception when an exception is raised. This check is cheap because the interpreter already tracks that information for the handler stack. Storing the traceback as an attribute adds a reference from the exception to its frames, which can keep frames alive longer than before. Tests on representative code showed the overhead to be small, but the effect is worth stating because programs that create large numbers of exceptions may notice it.

## Alternatives Considered

One alternative was to store the context in a wrapper exception rather than as an attribute. This was rejected because it changes the type of the exception that the caller receives and would break handlers that match on the original type.

Another alternative was to use a single attribute that held both the cause and the context, distinguished by a flag. This was rejected because the two relationships are used differently by the printer and by programs, and combining them would make both harder to read.

A third alternative was to leave chaining entirely to the programmer, who would copy the context into a field by hand. This was rejected because the situations that most need the information are the ones where the programmer is least likely to remember to record it.

## Open Issues

The printed form of chained tracebacks is intended as a guide to people reading them. Its exact wording may be adjusted before the final release, but the ordering of the chain and the marking of explicit causes are fixed by this specification.

Some libraries wrap exceptions in ways that produce long chains. The proposal does not limit chain length, although the printer detects cycles. Whether a maximum depth should be imposed is left for a later discussion.

## Reference Implementation

A patch implementing the attributes, the `from` clause and the chained printer has been prepared against the development branch. It includes tests for implicit context, explicit causes, suppression by a `None` cause, and cycle detection in the printer.
