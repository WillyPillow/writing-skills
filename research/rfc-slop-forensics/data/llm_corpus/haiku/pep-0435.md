PEP: 435
Title: Adding an Enum type to the Python standard library
Author: Example Author
Status: Draft
Type: Standards Track
Content-Type: text/x-rst
Created: 2013-02-23
Python-Version: 3.4

Abstract
========

This PEP proposes adding an enumeration type to the Python standard library. An enumeration is a set of symbolic names bound to unique, constant values. Within an enumeration, the values can be compared by identity, and the enumeration itself can be iterated over.

Motivation
==========

Programs often need a fixed set of named constants. A status code, a color, a day of the week, or a mode of operation is naturally expressed as one of several symbolic choices rather than as an arbitrary integer or string. Python has no standard way to express such a set. Authors commonly use module-level integers, such as ``STATUS_OK = 0`` and ``STATUS_ERROR = 1``, or they use strings whose spelling is not checked anywhere.

Integers and strings have several weaknesses for this purpose. Nothing prevents a value outside the intended set from being passed where the set is expected. Integers from different groups may compare equal, so a status code may be mistaken for a color. The names of the constants are not grouped together, so there is no single object that represents the whole set. Printing a value shows a bare number, which is unhelpful when debugging.

Many third-party packages have solved this problem independently, and the resulting variety of designs makes interoperation harder. A library that accepts an enumeration from one package cannot easily accept one from another. A standard type would give libraries a common vocabulary and would let the language itself offer useful behavior, such as readable representations and iteration over members.

Rationale
=========

The central requirement is that members of an enumeration are distinct objects, so that identity comparison is meaningful and so that values from different enumerations never compare equal. Each member has a name, which is a string used for display and for lookup, and a value, which is the constant associated with the name. The value is not required to be unique in general, but the design treats values that are repeated as aliases of the same member.

Iteration is included because the set of members is a natural thing to enumerate. A program that wants to list every color, or to validate that a string names one of the members, benefits from being able to walk the set directly.

The type is designed to be simple. It does not attempt to model flags that combine by bitwise operations, and it does not provide an ordering of members beyond what the definition order gives. These features may be useful, but they add complexity, and they can be proposed separately once the basic type has proven itself.

Specification
=============

An enumeration is defined by subclassing a base class provided in the new module. The body of the class lists the members as assignments of names to values::

    from enum import Enum

    class Color(Enum):
        red = 1
        green = 2
        blue = 3

Each name in the body becomes a member of the enumeration. Accessing ``Color.red`` returns the member object, not the integer. The member has attributes ``name`` and ``value`` that give its name and its value as strings or integers, depending on what was assigned.

Members are singletons. Two accesses to the same member produce the same object, so identity comparison with ``is`` is reliable. Comparing a member with a value from another enumeration gives a result of inequality, even if the underlying values are equal, because the members belong to different types.

Iterating over the enumeration yields its members in the order in which they were defined. The enumeration also supports membership tests and lookup by name or by value. Aliases, which are names that share a value with an earlier name, refer to the same member and do not appear twice during iteration.

Subclassing an enumeration that already has members is an error, since that would allow the set of members to change after the fact. An enumeration may, however, define methods and properties, which are available on each member. This allows enumerations to carry behavior that depends on the member.

Backwards Compatibility
=======================

The new module introduces no changes to existing code. Programs that define their own enumeration-like classes continue to work. Libraries may adopt the new type gradually, and where a library previously returned integers, a transition period can be arranged in which both forms are accepted.

Reference Implementation
========================

A reference implementation is available in the form of a module that defines the base class, the member behavior, and the iteration protocol. The implementation keeps member lookup fast by storing members in a mapping, and it validates the class body when the enumeration is created so that errors are reported early.

Alternatives
============

Several alternatives were considered. One is to use a convention of module-level constants, which requires no new type but offers none of the benefits described above. Another is to adopt one of the existing third-party designs as the standard. This would bring a tested implementation, but it would also fix design choices that the community had not agreed on. A third approach is to provide a function that creates an enumeration from a list of names. This is convenient, but it gives up the readability of a class body, and it makes the definition harder to type-check and document.

The proposal chooses a class-based design because it matches the way other class definitions are written, and because it allows enumerations to carry methods and documentation in the usual way.

Open Issues
===========

The treatment of values that are not unique is one open question. The current design treats repeated values as aliases, but some users may expect them to be distinct members. The handling of flags, where members combine with bitwise operators, is left for a later proposal. The exact representation shown by ``repr`` should be settled during review, since it is visible to users in logs and in interactive sessions.
