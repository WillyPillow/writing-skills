## Abstract

This document proposes an iteration interface that objects can provide to control the behaviour of `for` loops. Looping is customized by providing a method that produces an iterator object. The iterator provides a *get next value* operation that produces the next item in the sequence each time it is called, raising an exception when no more items are available.

Two specific iterators are proposed: one over the keys of a dictionary, and one over the lines of a file. A further proposal allows the spelling `key in dict` to replace the older `dict.has_key(key)` method. The proposal is deliberately narrow. It does not introduce generators, comprehensions, or any new syntax beyond what is needed to make `for` loops work over arbitrary objects.

## Motivation

The `for` statement in Python has historically worked only with sequences. A sequence is an object that supports integer indexing from zero upward and raises `IndexError` when the index is out of range. This rule is simple, but it forces several awkward workarounds.

A dictionary is not a sequence, so iterating over it requires calling a method such as `keys()` that builds a complete list of keys in memory before the loop begins. For a large dictionary this is wasteful. A file object has the same problem in a different form: reading a file line by line with `readlines()` loads the whole file into a list, which is unacceptable for files that are larger than available memory.

Objects that model infinite or lazily computed sequences cannot be iterated at all under the current rules, because the protocol requires that the object be indexable at arbitrary positions. An iterator protocol removes this restriction. An object need only be able to hand out its items one at a time, in order.

The protocol also gives users a uniform way to write their own iterable classes. Today a class that wants to support `for` must emulate a sequence, which is an unnatural burden when the class has no notion of indexing at all.

## Specification

Two methods are defined. Any object that wishes to be iterable provides a method named `__iter__()`, which takes no arguments and returns an iterator object. The `for` statement calls this method once, at the start of the loop, to obtain the iterator.

An iterator object provides a method named `next()`, which takes no arguments. Each call returns the next item of the sequence. When the items are exhausted, `next()` raises the `StopIteration` exception. Once an iterator has raised `StopIteration`, subsequent calls should continue to raise it, so that iterators remain well behaved in the presence of repeated calls.

An iterator object should also provide an `__iter__()` method that returns the iterator itself. This allows an iterator to be used directly in a `for` statement, and it allows the same iterator to be passed to functions that expect an iterable.

The `for` statement is then specified as follows. The expression is evaluated and `__iter__()` is called on the result. The resulting iterator's `next()` method is then called repeatedly. Each returned value is assigned to the loop target, and the body of the loop is executed. When `StopIteration` is raised, the loop terminates normally.

For backward compatibility, the old sequence protocol remains in force. If an object does not define `__iter__()` but does support integer indexing, the interpreter constructs a sequence iterator that calls `__getitem__()` with successive indices until `IndexError` is raised. Existing code that depends on the sequence behaviour therefore continues to work unchanged.

## Dictionary Iterators

Dictionaries gain three iterator methods. The method `iterkeys()` returns an iterator over the keys. The method `itervalues()` returns an iterator over the values. The method `iteritems()` returns an iterator over `(key, value)` pairs. Each of these reads entries from the underlying hash table as needed and does not build an intermediate list.

Mutating a dictionary while an iterator over it is active is an error. The iterator records the size of the dictionary when it is created, and if the size changes during iteration the next call to `next()` raises `RuntimeError`. This check is a safeguard rather than a complete guarantee, since replacing a value does not change the size, but it catches the most common mistakes.

The existing methods `keys()`, `values()`, and `items()` are retained with their present behaviour. They return lists and remain the correct choice when the caller needs random access or needs to modify the dictionary during the loop.

## File Iterators

A file object gains the ability to be iterated directly. Each call to `next()` returns the next line of the file, including its trailing newline, and raises `StopIteration` at end of file. A loop such as `for line in open(name):` therefore reads a file one line at a time, with constant memory overhead regardless of the file size.

The file iterator uses the same internal buffer as the existing `readline()` method, so that mixing the two styles of reading does not lose data. The behaviour at end of file for a file opened in text mode follows the behaviour of `readline()` exactly.

## The `in` Operator for Dictionaries

The operator `in` already tests membership for sequences. This proposal extends it so that `key in dict` is equivalent to `dict.has_key(key)`. The implementation is a single entry in the dictionary's containment method, and no new keyword is introduced.

The authors recognize that `has_key()` is a long-standing and widely used method. The proposal does not require its removal. The method stays available, and documentation should present the operator form as the preferred spelling. Code that is written for older versions of Python can continue to use `has_key()` without modification.

## Rationale

The design deliberately separates the act of starting an iteration from the act of advancing it. Calling `__iter__()` returns a fresh iterator, so that two loops over the same container do not interfere with each other. Calling `next()` advances the state held by the iterator, so that the container itself stays simple.

The choice of `StopIteration` as the termination signal reuses the exception mechanism that the language already has. It avoids introducing a sentinel value, which would be easy to confuse with legitimate data. It also keeps the protocol cheap: a loop body that never raises pays nothing for the termination check.

The authors considered making iterators unidirectional and not reusable. This is the intended design. An iterator that has been exhausted stays exhausted, and reiterating requires asking the container for a new iterator. This matches the expectations of most programmers and avoids a class of subtle errors.

## Backward Compatibility

The change is designed to be fully backward compatible. Existing sequence types continue to work because the interpreter falls back to the indexing protocol when `__iter__()` is absent. Existing dictionary code continues to work because the list-returning methods are retained. Existing file code continues to work because `readline()` and `readlines()` are unchanged.

The only observable change for correct programs is that some code which previously raised an error, such as iterating over a user-defined class that defines `__getitem__()` in an unusual way, may now behave differently. The authors judge this risk to be small.

## Reference Implementation

A reference implementation is planned for the trunk of the development tree. It includes the iterator protocol in the core interpreter, the three dictionary iterator methods, the file iterator, and the containment operator for dictionaries. It also includes a set of unit tests that exercise the boundary conditions, such as iteration over an empty container, repeated calls after exhaustion, and modification of a dictionary during iteration.

## Open Issues

Several points remain open for discussion. The name of the advancing method is one. The proposal uses `next()` for consistency with the existing built-in functions of the period, but a different name might read more clearly. The behaviour of a dictionary that is mutated during iteration is another, and the authors are willing to consider stricter enforcement if it proves to cause problems in practice.

The proposal also leaves open whether the iterator protocol should be exposed through a built-in function, so that code can request an iterator explicitly. The authors favour adding such a function only after the protocol has seen real use.
