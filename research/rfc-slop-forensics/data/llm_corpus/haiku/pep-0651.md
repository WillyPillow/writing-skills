PEP: 651
Title: Robust Stack Overflow Handling
Author: Mark Shannon
Status: Rejected
Type: Standards Track
Created: 2020-11-10
Python-Version: 3.10
Post-History: 2020-11-11

Abstract

This PEP proposes that Python treat machine stack overflow differently from runaway recursion. At present, both conditions are signaled with the same exception and governed by the same limit. The proposal separates them. A program would be able to set the maximum recursion depth to suit its needs, and the interpreter would provide additional guarantees that a deep but finite recursion will not crash the virtual machine.

If the PEP were accepted, a program that sets a large recursion limit and then recurses deeply within it would run to completion. A program that recurses without end, through a path that the interpreter cannot track, would raise a dedicated exception rather than crash the process.

Motivation

Python limits the depth of recursion to protect the interpreter from exhausting the machine stack. The limit is a number that programmers can raise, but raising it has been unsafe. A recursion that exceeds the native stack available to the interpreter can crash the process, and the crash gives the programmer no clear diagnostic.

The two conditions the interpreter must distinguish are the Python recursion limit, which counts calls made by Python code, and the native stack, which the interpreter uses when it calls back into C code, such as when a special method is invoked through a slot. A program can reach the native stack limit even when the Python recursion limit has not been reached, because some calls pass through C functions that consume stack space without counting toward the limit.

Users have asked for a way to set a high recursion limit safely. Some algorithms, such as certain tree traversals and parsers written in a recursive style, are clearest when they recurse deeply. Programmers either rewrite them with an explicit stack, which is less readable, or raise the limit and hope the native stack is large enough.

The PEP proposes a design in which the interpreter tracks native stack usage directly. When the usage approaches the available space, the interpreter raises an exception that the program can catch. The Python recursion limit is then a policy setting, and the native stack is protected by its own check.

Rationale

The central observation is that the two limits protect different resources. The Python recursion limit exists to keep programs from consuming unbounded memory through call frames. The native stack limit exists to keep the process from crashing. Treating them as one number forces a compromise, since a value large enough for useful deep recursion may be too large for the native stack in some calls.

By checking the native stack directly, the interpreter can allow a high Python limit without risking a crash, and it can report a clear error when the native stack is nearly exhausted. The check is performed at points where the interpreter already tests for other conditions, so the cost is expected to be small.

The new exception distinguishes a stack exhaustion caused by runaway recursion from an ordinary error. Programs that catch it can recover, for example by reporting the problem and continuing with a smaller input.

Specification

The interpreter maintains a record of native stack usage for each thread. At each call that uses native stack, it compares the current depth with a threshold derived from the stack size reported by the operating system. If the threshold is exceeded, the interpreter raises a new exception, named StackOverflow, which is a subclass of RecursionError.

The Python recursion limit continues to be set with sys.setrecursionlimit and read with sys.getrecursionlimit. Its meaning is unchanged for pure Python calls. A program may set it to a large value, and the interpreter will enforce native stack protection independently of the value.

A program that sets a large limit and recurses within it will run until one of two things happens: the recursion finishes, or the native stack threshold is reached. In the second case, the program receives the StackOverflow exception.

The PEP does not change the behavior of the interpreter for code that never approaches either limit.

Backwards Compatibility

Programs that catch RecursionError continue to work, since the new exception is a subclass of it. Programs that rely on the exact message of the recursion error may need to adjust, since the message for native stack exhaustion differs from the message for the Python limit.

The PEP makes no change to the bytecode or to the semantics of Python-level calls.

Security Implications

Robust stack handling reduces the risk that a crafted input can crash an interpreter through deep recursion. A denial of service that depends on exhausting the native stack would instead raise an exception that the program can handle.

Performance Impact

The native stack check adds a small amount of work to calls that pass through C code. The PEP estimates the cost as low, and it proposes that the implementation be measured against a benchmark suite before acceptance.

Rejected Ideas

One proposal was to run each thread on a separately allocated stack of known size. This was rejected because it would require changes to thread creation that many embedding applications could not accept.

Another was to remove the Python recursion limit entirely and rely only on the native check. This was rejected because the limit serves a useful purpose in bounding memory use, and removing it would change the behavior of many programs.

Outcome

The PEP was rejected. The discussion showed that the native stack check was difficult to make reliable across platforms, and that the cost of tracking stack usage at every relevant call was higher than the benefit for most programs. The author and the steering council agreed that the problem is real, and that a future proposal may revisit it with a narrower design.
