PEP: 650
Title: Specifying Installer Requirements for Python Projects
Author: Example Author <author@example.org>
Discussions-To: https://discuss.python.org/
Status: Draft
Type: Standards Track
Created: 2021-06-01
Post-History: 2021-06-01

Abstract
========

Python package installers are not fully interoperable with one another. Pip is the most widely used installer and is a de facto standard, but other installers such as Poetry and Pipenv are popular because they offer features that suit particular workflows and do not match the way pip operates.

The variety of installers serves end users well, but it makes life hard for the tools that must support all of them. There is no standard file for declaring dependencies in a form that every installer can read. Each tool must therefore be invoked explicitly to install the dependencies written in its own format. Alternatively, a project must emit a requirements file for each tool, which loses information that the originating tool knew and creates a second source of truth that can drift from the first.

This PEP specifies a small, installer-neutral table in the project's ``pyproject.toml`` file. The table records the dependencies a project needs in a form that any installer can translate into its own internal model. It does not replace the lock files of individual tools, and it does not require any installer to change how it resolves versions.

Motivation
==========

Consider a project that is developed with Poetry and deployed in a container that uses pip. The developer maintains a ``pyproject.toml`` with a Poetry-specific section, and the deployment team maintains a ``requirements.txt`` generated from it. When a dependency is added, the developer must regenerate the file, and when the file is out of date the deployment installs a different set of packages from the one the developer tested.

The problem is not limited to Poetry. Any tool that has its own dependency format faces the same choice. Tools that wish to interoperate with others must either adopt a common format or provide an export step, and an export step always loses something. A lock file records exact versions, a constraint file records bounds, and a plain list records only names. Each tool has a notion of these that the others do not share.

A common format for the declared requirements would let each tool read the requirements of the others and make its own decision about how to resolve them. The information that is common to all tools is the set of named requirements with version constraints, the extras that may be requested, and the environment markers that restrict when a requirement applies. A standard that records these items, and leaves resolution to the installer, is the smallest useful step.

Rationale
=========

The design separates the declaration of requirements from the resolution of versions. A declaration says what the project needs. A resolution says which concrete versions satisfy those needs at a given time. The first is a property of the project, and the second is a property of the installer and the moment at which it runs.

This separation keeps the standard small. The format does not need to describe how an installer chooses among compatible versions, which is an area where the installers differ and where the differences are part of their value. It only needs to describe what the project is asking for.

The format lives in ``pyproject.toml`` because the file is already the place where build and project metadata are recorded. A new file would add one more thing to keep in sync. The table is named as a subtable of the existing project metadata so that tools that do not know about it can ignore it without error.

Specification
=============

The table is named ``[project.requirements]``. It contains three keys. The key ``dependencies`` is an array of strings, each in the format of a requirement specifier as defined by the packaging specification. The key ``optional`` is a table whose keys are extra names and whose values are arrays of requirement specifiers. The key ``python`` is a string that gives the range of interpreter versions the project supports.

Each requirement specifier in the arrays must be valid under the existing specification for requirement strings. A tool that reads the table must reject a specifier that it cannot parse, and it must report the location of the error in the file. A tool must not silently drop a requirement it does not understand.

Environment markers are allowed within a requirement specifier, using the existing syntax. A marker that refers to an environment variable or a platform value is evaluated at install time by the installer, not by the author of the file.

The table is optional. A project that does not have it is treated as having no declared requirements through this mechanism, and installers continue to use their existing sources of information. Installers must not treat the absence of the table as an error.

A tool that writes the table must write all three keys, even when some are empty, so that a reader can distinguish an empty list from an absent one. The formatting of the table follows the usual TOML rules for arrays and tables.

Installer behaviour
===================

An installer that supports this PEP reads the table, combines the dependencies with any extras that the user has requested, and resolves them according to its own rules. The installer may also write a lock file in its own format. The lock file is not part of this PEP, and it must not be treated as a substitute for the declared requirements.

An installer that does not support this PEP continues to work as before. A project that uses the table can therefore be installed by tools that do not know about it, provided that those tools have their own way of reading the project's requirements.

Backwards compatibility
=======================

The table is a new addition to ``pyproject.toml``, and it does not change the meaning of any existing key. Tools that validate the file strictly may need to be updated to accept the new table, but the table is designed so that a tool with a permissive reader will ignore it.

No existing installation behaviour changes for a project that does not add the table.

Security implications
=====================

The table records requirements but does not install anything. The security of an installation is still determined by the installer, the index it uses, and the resolution it performs. This PEP does not add a new way for a package to run code during installation.

The table could be used to describe a requirement that points to an unexpected index, if the specifier includes a source URL. Installers should treat such specifiers with the same caution that they apply to any other direct reference, and this PEP does not relax that caution.

Reference implementation
========================

A prototype reader is being developed as a separate library. It parses the table, validates the specifiers, and produces a list of requirements for a given set of extras and a given interpreter version. The library is intended to be used by installers as a common front end, so that each installer does not need to implement the parsing itself.

Open issues
===========

The name of the table is not settled. The choice of a subtable under the project metadata has been proposed, but the final name should be decided after discussion with the packaging community.

The treatment of dependency groups, which are sets of requirements that are not published as extras, needs more discussion. A group may be useful for development and testing, but its relationship to the published metadata is not clear.

It is also unclear whether the table should allow a project to recommend a particular installer. The authors do not propose such a field, because it would turn a neutral format into a preference, but some users have asked for it.
