PEP: 611
Title: The one million limit
Author: Mark Shannon
Status: Draft
Type: Informational
Content-Type: text/x-rst
Created: 2020-02-13

Abstract
========

This PEP proposes a soft limit of one million (1 000 000), and a larger hard limit, for various aspects of Python code and its implementation. The Python language does not specify limits for many of its features. Leaving those features unlimited appears to give programmers freedom, but in practice the CPython virtual machine and other Python implementations have implicit limits, or they must assume that the limits are astronomically large. Assuming large limits is expensive, because it forces implementations to use wider integers, extra checks, or slower data structures. This PEP lists the features that should have a limit of one million, and it sets the hard limit for CPython at eight million (8 000 000).

Motivation
==========

Python programs are rarely written with explicit size limits in mind, and most of the time no limit is reached. However, the interpreter must still be designed so that it behaves correctly in the rare case where a limit is reached. Without a stated limit, implementers choose different values, and programs that work on one implementation may fail on another. Some implementations use fixed-width fields in their internal structures, and the widths were chosen without any documented guarantee.

A documented limit gives implementers a fixed target. It allows the interpreter to use smaller fields where possible, and it allows the authors of tools to reason about worst-case behavior. The number one million is chosen because it is large enough that ordinary programs never approach it, and small enough that it is practical to store in a machine word and to check cheaply.

Limits Proposed
===============

The PEP proposes a soft limit of one million for the following features. Each soft limit is a value beyond which the implementation may emit a warning or a deprecation notice, but it must still operate correctly for values up to the limit.

The number of lines in a single module is limited to one million. Practical source files are far smaller, and the limit allows the compiler to use compact line numbers.

The number of local variables in a function, the number of arguments in a call, and the number of items in a container literal are each limited to one million.

The depth of nested blocks and nested expressions is limited to a value well below one million, with the exact value left to the implementation, because deep nesting is a much more practical concern for the parser and the compiler stack.

The number of branches in a single function, the number of constants in a code object, and the number of names in a module namespace are each limited to one million.

For CPython, the hard limit for each of these features is eight million. A hard limit is one that the implementation enforces with an error. The gap between one million and eight million is reserved so that the implementation can accommodate internal bookkeeping without wrapping around.

Rationale
=========

The soft limit exists to inform programmers and to allow the implementation to make reasonable assumptions. It is not a promise that a program with a million items will run quickly. The hard limit exists so that the interpreter can guarantee that its internal counters do not overflow.

Using a single number for all features is a deliberate simplification. A separate limit for each feature would be harder to remember and harder to document. Where a feature needs a smaller or larger limit, the PEP leaves the choice to the implementation, provided the value is documented.

Implementation
==============

Implementers are asked to document the limits they enforce, and to ensure that the behavior at the limit is well defined. CPython will add checks in the compiler and in the code that creates code objects. Errors produced at the hard limit should name the feature that was exceeded and give the limit that applies.

The PEP does not require any change to the bytecode format. Where the current format uses a fixed-width operand that might overflow at the hard limit, the compiler will emit an extended form or an error.

Open Issues
===========

It is not yet clear whether the depth limit should be expressed as a fixed number or derived from the available stack. Some participants prefer a fixed value because it is predictable. Others argue that a value tied to the stack is more useful in practice.

It is also unresolved whether the soft limit should produce a warning in normal use or only in a development mode. Warnings in normal use are more visible, but they may annoy users who never reach the limit.
