Abstract
========

The idea is to have a Decimal data type, for every use where decimals are needed but binary floating point is too inexact. The Decimal data type will support the Python standard functions and operations, and must comply with the decimal arithmetic ANSI standard X3.274-1996.

Decimal will be floating point, as opposed to fixed point, and will have bounded precision. The precision is the upper limit on the number of significant digits in a result. Precision is user-settable, and a notion of significant trailing zeroes is supported, so that fixed-point usage is also possible.

The work builds on code and test functions written earlier by other contributors. The reference implementation of the module was moved into the standard library shortly before the release of Python 2.4 alpha 1, and this proposal describes the design of that module and the reasons for its shape.

Motivation
==========

Binary floating point cannot represent many decimal fractions exactly. The value 0.1, for example, has no finite binary expansion. Programs that handle money, tax, interest, or measurements recorded in decimal units therefore accumulate small errors that are visible to users and are unacceptable in some domains.

Programmers in these domains commonly work around the problem by storing integer counts of the smallest unit, such as cents, or by using ad hoc classes that are incomplete and inconsistent with each other. A standard type would give all of them a common, well specified tool.

The arithmetic must also be predictable. A user should be able to say how many digits a result carries, and should be able to know what happens when a result needs more digits than that. An arithmetic standard that defines rounding modes and exceptional conditions provides exactly this predictability, and the proposal follows it closely.

Rationale
=========

The Decimal type is floating point with a bounded number of significant digits. This choice is more general than fixed point, because a fixed-point format can be simulated by fixing the exponent. The reverse is not true. The proposal therefore takes the floating point model and adds the means to use it as a fixed-point type when that is wanted.

A value is represented by a sign, a coefficient, and an exponent. The coefficient is an integer of at most the precision number of digits, and the value is the coefficient times ten raised to the exponent. Keeping the exponent explicit allows the type to preserve trailing zeroes. The number 2.00 and the number 2 are different in representation, although they compare equal. This matters when a result is displayed, because the trailing zeroes carry meaning about the precision of the source data.

The module provides a context object that holds the settings for an operation. The context contains the precision, the rounding mode, the emax and emin limits on the exponent, and a set of flags and traps for exceptional conditions. Operations use the current context unless another is given. This design is inherited from the arithmetic standard, and it lets a program change behaviour for a region of code without changing every call.

Rounding modes follow the standard. The default is round half even, which avoids the systematic bias that round half up introduces when many values are summed. Other modes, such as round toward zero and round toward positive infinity, are provided so that the same arithmetic can serve applications with other needs.

Exceptional conditions are signalled in a uniform way. Division by zero, overflow, underflow, invalid operations, and inexact results each have a flag and a trap. A trap raises an exception, and a flag records that the condition occurred without stopping the computation. The defaults trap the most serious conditions and record the rest.

Specification
=============

Decimal instances are created from strings, integers, and tuples. Creation from a float is not permitted by default, because the binary value of a float is not exactly the decimal the user typed, and an implicit conversion would reintroduce the problem the type is meant to solve. A separate conversion function is provided for cases where the exact binary value is wanted.

The standard arithmetic operators and the comparison operators are defined. Mixing a Decimal with an integer is allowed, and the integer is converted exactly. Mixing a Decimal with a float is an error, so that no silent loss of precision occurs.

Methods are provided for the operations defined by the standard, including square root, exponentiation, logarithm, quantize, and the rounding functions to integers. The quantize method is the principal tool for fixed-point use. It sets the exponent of a result to a given value, rounding as required, so that a sum of money can be held to two places after the decimal point.

Hashing is defined so that Decimal values that compare equal hash to the same value, including values that differ only in trailing zeroes and values equal to integers. This keeps Decimal usable as a dictionary key alongside integers.

Design Discussion
=================

Several alternatives were considered. A fixed-point type with a constant scale was rejected because it cannot represent results that need more fractional digits than the scale, and because it does not match the arithmetic standard. A rational type was rejected because the denominators grow quickly and the result is unbounded in size, which conflicts with the goal of predictable cost.

The choice of a context object has been debated. An alternative is to pass the precision and rounding mode as arguments to every operation. This would be verbose and would make it difficult to write code that uses the same settings throughout. The context approach is the one used in the standard, and it is adopted here.

There was discussion about whether the module should provide a numeric type that is also a subclass of the built-in types. The authors decided against it. A Decimal is not a float and should not behave like one, and the explicit rule about mixing types is part of the value of the design.

Backwards Compatibility
=======================

The module is new, so no existing code depends on it. Code that uses floats for money continues to work as before. The proposal does not change the behaviour of the built-in types.

Implementation
==============

The implementation is written in Python and is included in the standard library as a single module. It is tested against the test cases from the arithmetic standard, and it has a large suite of its own tests that check the behaviour of each operation, each rounding mode, and each exceptional condition. A C implementation is considered for later versions, if the performance of the pure Python code proves inadequate.

Open Issues
===========

The naming of some methods was not settled at the time of writing. The list of rounding modes may need to be extended if the standard is revised. The behaviour of the module when used in multiple threads depends on the context mechanism, and the interaction should be documented clearly.

The question of whether the default precision should be changed in later versions was left open. Changing it would alter the results of existing programs, so any change must be made with care.
