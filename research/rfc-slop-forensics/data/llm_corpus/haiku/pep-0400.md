# PEP 400: Deprecate codecs.StreamReader and codecs.StreamWriter

| Field | Value |
|---|---|
| PEP | 400 |
| Title | Deprecate codecs.StreamReader and codecs.StreamWriter |
| Type | Standards Track |
| Status | Withdrawn |
| Python-Version | 3.3 |

## Abstract

`io.TextIOWrapper` and `codecs.StreamReaderWriter` offer the same API. `TextIOWrapper` has more features and is faster than `StreamReaderWriter`. Duplicate code means that bugs should be fixed twice and that we may have subtle differences between the two implementations. This PEP proposes to deprecate the `codecs.StreamReader` and `codecs.StreamWriter` classes, and the `codecs.StreamReaderWriter` class built on them, in favor of the `io` module.

## Motivation

Python has two layers for reading and writing encoded text. The `codecs` module predates the `io` module and provides the lookup of encodings, along with a set of base classes for stream reading and writing. The `io` module was introduced later to provide a complete and consistent model of streams, including text, binary, and raw forms. Its text layer, `TextIOWrapper`, is the interface used by `open()` and by the standard streams.

Over time, the two layers came to overlap. Both offer objects that wrap a byte stream and present a text interface, both handle incremental decoding and encoding, and both expose similar methods for reading lines and writing text. The overlap is not total, and the two differ in their handling of error conditions, buffering, and newline translation.

The duplication has real costs. A bug fixed in one implementation may remain in the other. Developers must learn two similar APIs and choose between them without a clear guide. Maintainers must test both. The `io` implementation is faster, because it is written in C in the form used by the interpreter, and it has received more attention from the core developers in recent releases.

The author argues that the `codecs` stream classes are therefore redundant, and that keeping them as a supported interface offers little benefit. Deprecating them would signal to users that the `io` module is the preferred choice and would give the project room to remove the duplicated code in a later release.

## Rationale

The proposal does not remove the `codecs` module. The lookup functions, the encoder and decoder interfaces, and the registry of encodings are heavily used and are not part of the proposed change. Only the stream reader and writer classes are targeted, since those are where the duplication lies.

The author considered the alternative of making `codecs.StreamReaderWriter` a thin wrapper around `TextIOWrapper`. This would preserve the old names while removing the duplicate implementation. The author noted that the behavior of the two classes differs in subtle ways, and that a wrapper would need to reproduce those differences in order to avoid breaking code that depends on them. The cost of that compatibility layer was judged to be higher than the benefit.

A deprecation period gives users time to migrate. The author suggests that the warning be emitted when the classes are instantiated, and that the documentation point to the corresponding `io` functions and classes. The period should cover at least two release cycles before any removal.

## Specification

The following classes would emit a `DeprecationWarning` when instantiated: `codecs.StreamReader`, `codecs.StreamWriter`, and `codecs.StreamReaderWriter`. The `codecs.StreamRecoder` class, which converts between encodings, would be handled in the same way. The warning would include the name of the replacement, which is `io.TextIOWrapper` for most uses.

The documentation of the `codecs` module would be updated to describe the classes as deprecated, and to give examples that use `io` in their place. The functions for looking up codecs, and the functions that return incremental encoders and decoders, would not be affected.

Existing behavior of the deprecated classes would not change during the deprecation period. Code that uses them would continue to work, and the only visible difference would be the warning, which is hidden by default for most users.

## Migration

For most code, the migration is straightforward. A call that wraps a binary stream in a `StreamReader` can be replaced by opening the stream through `io.TextIOWrapper` with the same encoding and error handler. The author provides examples in the appendix of the draft, and notes that the two classes accept the same arguments for the common cases.

Some code depends on the specific behavior of the `codecs` classes, such as the way they handle partial reads when the stream does not return enough bytes to decode a character. Such code may need to be reviewed, and the author recommends that the change be tested against any codec-heavy application before it is deployed.

## Backwards Compatibility

The change is backwards compatible in the sense that no existing program stops working during the deprecation period. The author recognizes that warnings may be noisy for projects that use the classes heavily, and suggests that the warning be issued only once per location to limit the noise.

## Open Issues

The author raised several points for discussion. The first is whether the deprecation should cover the classes only, or also the methods that return them, such as the stream factory functions in the `codecs` module. The second is whether removal should be scheduled at a specific release, or left to a later decision once the usage data is available.

A third question concerns third-party codecs that subclass the stream classes. The author proposed that these classes be treated as part of the public interface, and that their authors be notified through the release announcements.
