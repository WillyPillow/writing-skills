# PEP 610: Recording the direct URL origin of installed distributions

- **Type:** Standards Track
- **Status:** Draft
- **Requires:** 376, 440, 627

## Abstract

PEP 440 allows a distribution to be identified in one of two ways: by a name and a version, or by a name and a direct URL reference. Installation tools record the name and version in the core metadata of the installed distribution, and the installed-package database defined in PEP 376 lets other tools read that metadata back. The URL that was used to obtain a distribution, however, is not recorded. A tool that inspects an environment cannot tell whether a package came from the index, from a local directory, from a version control checkout at a specific commit, or from an archive at a fixed address.

This proposal adds a single metadata file, `direct_url.json`, to the `.dist-info` directory of every installed distribution that was installed from a direct URL. The file records the URL, a description of the kind of source, and enough detail to reproduce the installation.

## Motivation

Several workflows depend on knowing where a package came from. A developer who has installed a project in editable mode may want to find the source tree again. A build system may need to decide whether an installed copy is stale. An auditing tool may want to report which packages were installed from unreviewed sources. Dependency resolvers may need to know that a package was pinned to a particular commit rather than to a released version.

Today these tools guess. Some inspect the presence of a `.egg-link` file or a `.pth` entry, which depends on the installer. Others compare the version string with what the index reports, which fails when a local build has the same version as a release. None of these approaches is reliable across installers.

Installers already have the information at the moment of installation. The URL is known, the commit hash is known for version control sources, and the choice to install in editable mode is known. The missing step is to write that information down in a form that any tool can read.

## Specification

The file `direct_url.json` is placed in the `.dist-info` directory of the installed distribution. It is only written when the distribution was installed through a direct URL reference. Distributions installed from an index do not receive the file, and its absence means that the origin is the index or is unknown.

The file contains a single JSON object with these keys:

- `url`: a string containing the URL that was used. Credentials embedded in the URL must be removed before the file is written.
- Exactly one of the following keys, describing the kind of source:
  - `archive_info`: an object for archives, such as wheels or source tarballs. It may contain a `hashes` mapping from algorithm name to hex digest.
  - `dir_info`: an object for local directories. It may contain a boolean `editable` key.
  - `vcs_info`: an object for version control checkouts. It must contain a `vcs` key naming the tool, such as `git`, and a `commit_id` key with the full revision identifier. It may contain a `requested_revision` key holding the revision as the user wrote it.

Tools that read the file must ignore keys they do not recognise. This allows future extensions without a new version of the file format. The file also carries a `dir_info` or `archive_info` key whenever the source is a local path or an archive, so that the two cases can be distinguished without reading the URL.

Installers must write the file atomically, so that an interrupted installation does not leave a partial record. Uninstallers must remove it together with the rest of the `.dist-info` directory.

## Security Considerations

Recording URLs can leak secrets. Some index servers embed tokens in the address, and a careless installer would copy them into a file that is often shared, committed to version control, or included in a container image. The specification therefore requires the installer to strip the user information component of the URL before writing it. Tools that read the file should also be prepared to find URLs that still contain credentials from older installers, and should avoid echoing them.

Hash values in `archive_info` make it possible to check that an installed archive matches the one that was originally downloaded. The file does not change how distributions are verified at install time. It is a record only.

## Rationale

The proposal stores the information in a separate JSON file instead of extending the core metadata. Core metadata is shared by all distributions and is part of the published package, so it is the wrong place for facts that depend on how one particular user installed it. A separate file keeps the two concerns apart.

The choice of JSON over the key-value format used by the other metadata files reflects the nested structure of the information. Version control sources need several related fields, and a flat format would require awkward naming conventions.

The three source kinds were chosen to cover the cases that installers actually produce. Other kinds of source can be added later under new keys, and older tools will ignore them.

## Backwards Compatibility

Older installers do not write the file, and older tools do not read it. Nothing about the existing metadata changes. An environment that contains a mixture of old and new installations simply has the file for the packages installed by the new tools.

## Reference Implementation

The reference implementation is a patch to the pip installer that writes the file during installation and removes it during uninstallation. A small module in the standard library's `importlib.metadata` support can read the file and return a parsed object. The patch is intended to be easy to review, because it touches only the code paths that already handle the distribution's metadata.

## Open Issues

The proposal does not say how a tool should behave if the recorded commit no longer exists in the repository. It leaves that to the tool, because the correct response depends on the purpose. A second open question is whether the editable flag should be recorded for projects installed through a build backend that does not support editable installs. The draft currently records the flag only when the installer knows it to be true.

## Summary

Installers know where a distribution came from, but the information disappears once the installation finishes. This proposal writes the direct URL origin into a small JSON file in the distribution's metadata directory, strips secrets before writing, and leaves the rest of the packaging system unchanged. Tools gain a reliable way to answer the question of where a package came from.
