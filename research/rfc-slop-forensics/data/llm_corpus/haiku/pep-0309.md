# PEP 309: Partial function application

- **Type:** Standards Track
- **Status:** Accepted

## Abstract

This proposal adds a way to build a new callable from an existing callable and a partial set of arguments. The arguments may be positional, keyword, or both. The result behaves like the original callable with the supplied arguments already filled in, and it can itself be called with the remaining arguments.

The proposal also suggests a standard library module, called `functional`, to hold useful higher-order functions. The first member of that module would be a `partial` type that implements the idea above. A reference implementation has been written in C and is available for review.

## Motivation

Python programmers often write small wrapper functions whose only purpose is to fix one or two arguments of another function. A callback that must receive a window handle, a sort key that must know a locale, or a formatting function that must always use the same separator are all typical examples. Each wrapper takes several lines and must be repeated in many modules.

The pattern is common enough that most libraries contain their own version. Each one has slightly different behaviour for keyword arguments, for the representation of the result, and for introspection. A single standard implementation would remove the duplication and give everyone the same behaviour.

Partial application is also useful for callbacks in event systems, for building specialised versions of general algorithms, and for passing functions to other functions in a way that is easy to read. Languages with a functional tradition offer it as a basic feature, and Python programmers coming from those languages expect it.

## Specification

The proposal defines a class `partial` that is constructed with a callable and any number of positional and keyword arguments:

```python
p = partial(func, *args, **keywords)
```

When `p` is called with further arguments, the call is made as if `func` had been called with `args` followed by the new positional arguments, and with `keywords` updated by the new keyword arguments. Keyword arguments supplied at call time override those stored in the partial object.

The partial object exposes three read-only attributes. The attribute `func` holds the original callable, `args` holds the stored positional arguments as a tuple, and `keywords` holds the stored keyword arguments as a dictionary. These attributes make it possible for tools to inspect what the partial object will do.

The `__repr__` of a partial object shows the callable and the stored arguments, so that a partial appears in debugging output in a form close to the code that created it. Calling a partial that wraps a callable which is not callable produces the same error that calling the original would produce.

Partial objects are picklable when the wrapped callable is picklable. This allows them to be used with multiprocessing and to be stored in configuration files that are later restored.

## Rationale

The proposal stores the arguments as a tuple and a dictionary rather than as a closure. A closure is opaque, so tools cannot see what it will call. Storing the parts explicitly makes the partial object useful for introspection, for testing, and for serialisation.

Keyword arguments supplied at call time override those stored at construction time. This matches the way ordinary function calls work, where the last value given for a name is the one used. Choosing the opposite rule would make partial objects surprising for people who write a default and then replace it.

The proposal does not add a way to fill arguments by position with gaps. Several proposals suggested placeholder objects for this purpose. They are useful, but they add a new concept to the language and can be introduced later without changing the design described here.

## Implementation

A reference implementation written in C is attached to the proposal. It stores the callable and the arguments in the object and calls the wrapped function through the normal call protocol. The C implementation avoids the overhead of a Python-level wrapper, which matters when partial objects are used in tight loops.

A pure Python version is also provided as a fallback for implementations that do not use C. It defines the same attributes and the same behaviour, and it is used for testing the specification.

## The functional module

The proposal suggests placing `partial` in a new module, `functional`, along with a small set of other higher-order helpers. Candidates mentioned in the discussion include functions for composing callables, for applying a function to each element of a sequence, and for memoising results. The proposal does not commit to a full list. It asks only that the module be created, so that the choice of other members can be made separately.

A dedicated module keeps the built-in namespace small. It also gives a clear home for future functional tools, so that they are not added piecemeal to unrelated modules.

## Alternatives

One alternative is to add a lambda-based helper with a shorter name. Lambdas cannot be pickled and cannot be inspected in the same way, so this was rejected.

A second alternative is to rely on closures written by hand. This is the status quo, and it is the reason the proposal exists. It is simple but repetitive, and the result is opaque.

A third alternative is to use the `functools` naming style for the whole module, but the proposal argues that the name `functional` is clearer for newcomers and better describes the purpose of the module.

## Backwards Compatibility

The proposal adds a new module and a new type. It does not change the behaviour of existing functions, so there is no compatibility issue.

## Open Issues

Discussion has not settled whether the partial object should compare equal to another partial with the same function and arguments. Equality would be useful for testing, but it requires comparing the stored arguments, which may not be comparable. The draft leaves equality as identity for now.

Another open question is whether partial objects should support being used as methods. When a partial is stored as a class attribute, the usual descriptor protocol does not apply to it unless the type defines one. The reference implementation does not define it, and the proposal asks for comment.

## Summary

The proposal adds a `partial` type that fixes some arguments of a callable and returns a new callable for the rest. Its state is stored in explicit attributes so that it can be inspected, printed, and pickled. It proposes a new `functional` module to hold this and similar tools. The change is small, it removes a common source of boilerplate, and it does not affect existing code.
