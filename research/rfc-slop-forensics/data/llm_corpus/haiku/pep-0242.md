# PEP 242: Numeric Kinds

| Field | Value |
|---|---|
| PEP | 242 |
| Title | Numeric Kinds |
| Status | Withdrawn |
| Type | Standards Track |
| Created | 2001 |
| Python-Version | 2.2 |

## Abstract

This proposal gives programmers optional control over the precision and range of numeric computations. A computation that is written once should be able to run on any platform that provides at least the precision and range the programmer requires. The proposal introduces the notion of a numeric kind, which describes a set of numeric values with stated properties, and it allows a programmer to request a kind for a computation. The change is backward compatible with existing code, and it clarifies the meaning of decimal literals.

## Motivation

Python's numeric types are designed for convenience. An integer is an arbitrary precision value, and a floating point number is usually the double precision type of the host platform. These choices suit most programs, but they leave some programmers without a way to say what they need. A scientific program may depend on the precision of a double, while a financial program may need exact decimal arithmetic. A program written with the assumption of a particular range may behave differently on a platform where that range is not available.

At present, the programmer who needs control must either accept the platform default or use a library that provides a different type. Because these libraries are not part of the core language, code that mixes them with ordinary numbers has to be written with care, and the results may differ in subtle ways from code that uses the built-in types.

A second problem concerns literals. A decimal literal such as `0.1` is interpreted as a floating point number of the platform's default kind. Programmers who write such a literal often expect it to represent the exact value they typed, but the platform's representation may differ. The meaning of the literal is therefore unclear, and the proposal aims to make it clear.

The goal is to give the programmer a way to say what precision and range are needed, and to let the implementation choose a representation that satisfies the request. The programmer does not need to know how the representation is achieved.

## Rationale

The proposal is built around the idea of a kind, which is a specification of the properties a number must have. A kind may specify a minimum number of digits of precision, a range of exponents, or both. Two kinds are compatible when one is at least as strong as the other in each respect. A computation performed with a stronger kind can be expected to produce results that satisfy the requirements of a weaker kind.

The design avoids specifying an exact representation. A specification that named a particular bit layout would tie the language to a platform and would prevent the implementation from choosing a better one when it becomes available. Stating requirements in terms of precision and range leaves the implementation free to choose, while still giving the programmer a guarantee.

The proposal also treats the existing types as kinds. The built-in integer type and the built-in floating point type are the default kinds, and any code that does not specify a kind continues to use them. This keeps the change backward compatible and means that the programmer who does not care about the issue does not need to know that it exists.

## Specification

A kind is requested by an expression that names the required precision and range. The exact syntax is left to a separate discussion, but the proposal describes the semantics. A request for a kind yields a value whose kind is at least as strong as the request. If no representation available on the platform satisfies the request, the request fails with an error at the time it is made, rather than producing a value that silently fails to meet the requirement.

Arithmetic between values of different kinds produces a result whose kind is the stronger of the two. The proposal does not define a single rule for every operation, but it requires that the result be at least as precise as either operand, so that no information is silently lost in mixed computations.

Literals receive a kind that depends on their form. An integer literal has the default integer kind unless it is marked otherwise. A decimal literal is interpreted with a kind that is at least as precise as the digits written, which means that a literal written with many digits is not truncated to the platform default. The proposal states that the meaning of `0.1` is the value closest to one tenth in the requested kind, and that the programmer who wants the exact decimal value must request a decimal kind explicitly.

Conversions from a weaker kind to a stronger kind are always permitted and do not change the value. Conversions in the other direction are permitted only when they are requested explicitly, and they may round or truncate. The result of such a conversion records the kind to which it was converted, so that subsequent operations use the correct precision.

## Backward Compatibility

The proposal does not change the meaning of any existing program. Code that does not request a kind receives the default kinds, which are the same as the types used before the proposal. Literals in existing code are interpreted as before, except that the proposal clarifies the meaning of decimal literals in a way that is consistent with the default kind on most platforms.

The clarification of decimal literals may change the output of programs that print the value of a literal on platforms where the default representation is not the closest value to the decimal number. The proposal considers this an acceptable change, because the new behavior is more predictable, and it notes that such platforms are rare.

## Examples

A scientific program might request a double precision kind for a computation that accumulates many small terms.

```python
total = sum(values, kind(precision=15))
```

A financial program might request a decimal kind for values that must be exact in base ten.

```python
price = 19.99 as decimal
tax = price * rate
```

These examples are illustrative only. The concrete syntax is not part of the proposal, and the names shown here are placeholders for the mechanism described in the specification.

## Implementation

The implementation adds a registry of kinds, which records the properties of each representation available on the platform. A request for a kind consults the registry and selects the representation that best satisfies the request. The registry is populated at startup from the platform's description of its numeric types, and it may be extended by extension modules that provide additional representations.

The implementation of literal interpretation is limited to the parser and the constructor for the default kinds. Other kinds are constructed by the library that provides them, so the core language does not need to know their internal representation.

## Open Issues

Several questions remain. The first concerns the syntax for requesting a kind, which the proposal deliberately does not fix. The second concerns the rules for mixed arithmetic between kinds that are incomparable, where neither is stronger than the other. The third concerns whether the default kinds should be documented as the minimum guaranteed by the language, or whether they should continue to depend on the platform.

The proposal also raises the question of whether the registry of kinds should be extensible by the user, or whether it should be fixed by the implementation. The author expects that this will be decided once the basic mechanism has been tested with real programs.
