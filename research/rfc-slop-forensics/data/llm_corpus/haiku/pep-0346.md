# PEP 346: User Defined ("with") Statements

| Field | Value |
|---|---|
| PEP | 346 |
| Title | User Defined ("with") Statements |
| Status | Withdrawn |
| Type | Standards Track |
| Created | 2005 |
| Python-Version | 2.5 |

## Abstract

This PEP proposes a general mechanism for managing resources that must be acquired before a block of code runs and released after it finishes. It combines two earlier proposals. The first is the idea of reliable acquisition and release pairs, which ensures that a resource is released even when an exception occurs. The second is the idea of anonymous block statements, which allows a block of code to be passed to a function that controls its execution. The result is a statement, spelled `with`, whose behavior is defined by an object supplied by the programmer.

## Motivation

Many programs need to acquire a resource, use it, and then release it. Files must be closed, locks must be released, and database transactions must be committed or rolled back. The release must happen even when the code between acquisition and release raises an exception, because otherwise the resource leaks or remains locked.

The common Python idiom for this is the `try` statement with a `finally` clause. The idiom is correct but verbose, and it is easy to get wrong. A programmer who writes the acquisition inside the `try` block, or who forgets the `finally` clause, introduces a subtle bug that appears only when an error occurs. Code that performs the same pattern in many places becomes repetitive, and the intent of the code is obscured by the boilerplate.

The proposal aims to capture the pattern in a single construct. The programmer states what is acquired and what is released, and the language guarantees that the release occurs. The construct also makes it possible for libraries to offer resource management as an ordinary object, which can be reused across many programs.

## Rationale

The proposal takes its structure from two sources. The first source is a design in which the statement is defined in terms of two methods on an object, one that runs at entry and one that runs at exit. This approach is simple and explicit, and it gives the programmer full control over what happens at each point. The second source is a design in which a block of code is turned into a function that is passed to a controlling function. This approach is more flexible, because the controlling function can choose how to call the block, but it is harder to explain and it changes the meaning of control flow statements inside the block.

The proposal favors the first approach as the basis of the statement, and it allows the second to be expressed through generators in a limited way. The reason for this choice is that the object-based form is easier to read and easier to reason about, and it does not require that the block be treated as a function. The language keeps the semantics of `return`, `break` and `continue` inside the block unchanged, which avoids a class of surprises.

The name `with` was chosen because it reads naturally in the common case. A statement such as `with open(name) as f:` describes the activity in a way that is close to the English meaning, and it signals that the body of the block is executed in the context established by the object.

## Specification

A `with` statement takes an expression that evaluates to a context manager, which is an object that provides an entry method and an exit method. The statement first evaluates the expression, then calls the entry method. The value returned by the entry method may be bound to a name in the optional `as` clause. The body of the statement is then executed.

When the body finishes, whether normally or because of an exception, the exit method is called. If the body raised an exception, the exit method receives the details of the exception. The exit method may suppress the exception by returning a true value, in which case execution continues after the statement. If it returns a false value, the exception is propagated as usual.

Control flow statements inside the body behave as they do elsewhere. A `return` inside a `with` block causes the exit method to run before the function returns. A `break` or `continue` inside a loop causes the exit method to run before control leaves the block. This guarantee is what makes the statement useful for resource management.

Multiple context managers may be listed in one statement. They are entered in order and exited in reverse order. This matches the common case in which one resource depends on another, and it ensures that the inner resource is released before the outer one.

## Generators as context managers

The proposal allows a generator function to be wrapped so that it can act as a context manager. The generator runs until its first yield, and the value yielded is the value bound by the `as` clause. The body of the block then runs, and when it finishes the generator is resumed. If the body raised an exception, the exception is thrown into the generator at the point of the yield, which gives the generator the opportunity to clean up or to handle the exception.

This form is convenient for writing simple context managers, because the cleanup code appears in the same function as the acquisition code. It avoids the need to define a class with two methods, and it keeps the logic of the resource management in one place.

## Examples

A common example is the management of a lock.

```python
with lock:
    shared_counter += 1
```

The lock is acquired before the body runs and released afterward, even if the increment raises an exception. A programmer who reads this code can see at a glance that the lock protects the body.

A second example is a transaction, in which the entry method begins a transaction and the exit method commits it if no exception occurred and rolls it back otherwise. Such a context manager lets the programmer write the transaction boundaries in the same place as the work they enclose.

## Backwards Compatibility

The statement introduces a new keyword. Programs that use `with` as an identifier will need to be changed. The proposal addresses this by specifying a transition period in which the keyword is available only under a future import, so that existing code continues to work until the programmer chooses to enable the new behavior.

No other existing construct is affected. The statement is additive, and it does not change the meaning of `try` and `finally`, which remain available for cases that do not fit the context manager model.

## Implementation

The implementation adds the statement to the parser and the compiler, and it defines the entry and exit protocol in terms of special method lookups. The compiler generates code that calls the entry method, sets up an exception handler that calls the exit method, and ensures that the exit method runs on every path out of the block. The implementation includes tests for normal exit, exception exit, suppression of exceptions, and control flow statements inside the block.

## Discussion

The proposal was discussed at length. Some participants argued that the object-based form was sufficient and that the generator form added complexity without enough benefit. Others argued that the generator form was essential for writing simple resource management code without defining classes. The final design includes both, with the generator form implemented as a library feature rather than as a change to the statement itself.

Some participants raised concerns about the interaction between the statement and generators that yield inside the block. These concerns led to a more careful specification of when the exit method runs, in order to avoid resource leaks that depend on the timing of garbage collection.

## Rejected alternatives

A design in which the block is always converted into a function was considered and rejected, because it changes the meaning of control flow in ways that were judged confusing. A design that requires the programmer to name the exit action explicitly was also rejected, because it reintroduces the repetition that the statement is meant to remove.
