PEP: 246
Title: Object Adaptation
Author: A. M. Kuchling, and others (draft)
Status: Draft
Type: Standards Track
Created: 2001
Python-Version: 2.5

Abstract

This proposal puts forth an extensible, cooperative mechanism for adapting an incoming object to a context that expects an object supporting a specific protocol. A protocol here may be a concrete type, a class, or an interface. The proposal introduces a built-in function, `adapt`, which for any object X and any protocol Y asks the Python environment for a version of X that complies with Y.

Behind the scenes, the mechanism works in two directions. It first asks the object X: "Are you now, or do you know how to wrap yourself to provide, a supporter of protocol Y?" If that request fails, the function then asks the protocol Y: "Does object X support you, or do you know how to wrap it to obtain such a supporter?" The two-way structure is intentional. Protocols can be developed after the objects they will be applied to, and objects can be written before anyone has thought of a protocol they might later satisfy. Allowing either side to take the initiative makes the scheme work in both situations.

Motivation

Python programs routinely pass objects into code that expects a particular interface. A function that wants a sequence of lines, a mapping, or a file-like object may receive something that behaves similarly but is not formally related to the expected type. Today the programmer resolves this by hand: they wrap the object, convert it, or check it with `isinstance` and branch. Each library ends up with its own convention, and the conventions do not compose well.

Several existing approaches address parts of this problem. Type checks by `isinstance` only work when the expected class is known and when the object is in fact an instance of it. Duck typing works when the object simply has the required methods, but it provides no way to request a conversion when the methods are absent. Explicit conversion functions require the caller to know which conversion is needed. The proposal aims at a general mechanism that lets a library state what it needs and lets an object or a protocol supply the bridge.

The proposal also draws on work in other communities that studied similar problems under the name "interface adaptation." The central observation from that work is that adaptation is most useful when it is decentralized: no single registry needs to know every pairing of object and protocol in advance.

Specification

The proposal adds a function `adapt(obj, protocol, alternate=None)` to the built-in namespace. The function returns an object that supports the protocol, or raises a `TypeError` if no adaptation can be found. If the optional `alternate` argument is supplied, it is returned instead of raising when adaptation fails.

Adaptation proceeds in the following order.

1. If the object is already an instance of the protocol, which is checked by ordinary type or class membership, it is returned unchanged.

2. The function looks for a method on the object named `__conform__`. If present, it is called with the protocol as its argument. The method may return the object itself, a wrapper that supports the protocol, or `None` to indicate that it does not know how to adapt to the protocol.

3. If `__conform__` is absent or returns `None`, the function looks for a method on the protocol named `__adapt__`. If present, it is called with the object as its argument, under the same return conventions.

4. If neither method produces a result, the optional alternate value is returned, if one was given. Otherwise, a `TypeError` is raised.

The order matters. Objects are given the first opportunity to adapt themselves, because they are usually the best judges of their own capabilities. Protocols are consulted second, since they can provide adapters for objects that were written without knowledge of the protocol.

The proposal does not require that adaptation be symmetric, and it does not require that the result be a new object. An implementation may return the original object when it already supports the protocol, which keeps identity semantics intact in the common case.

Protocols

A protocol is any Python object that can be checked for membership. The proposal explicitly allows classes, abstract base classes, and interface objects to serve as protocols. It does not introduce a new formal kind of protocol type. This choice keeps the mechanism compatible with existing code, since any class already has the necessary behavior.

Rationale

The two-way design is the central rationale. A purely object-driven scheme would require every object to anticipate every protocol, which is impossible for a language whose libraries are developed independently. A purely protocol-driven scheme would require protocols to know every object, which is equally impractical. Using both directions allows the adaptation to be distributed across the two sides of each pairing.

The name `adapt` is chosen for clarity and brevity. The names `__conform__` and `__adapt__` were chosen to make the two hooks easy to remember and to avoid collisions with existing special methods.

Backward compatibility

The proposal adds a new built-in name, so existing code that defines a function or variable named `adapt` will be shadowed in the module where it is defined. This is a small but real compatibility cost, and the proposal recommends that the name be introduced with a warning in the first release that contains it.

Existing code is otherwise unaffected. Objects and protocols that do not define the new hook methods behave as they do today, and the only observable change is the availability of the new function.

Reference implementation

A prototype implementation was written as a pure Python module that defines the function and the search order described above. It has been used in small experiments but is not yet integrated into the interpreter. The authors expect that a C implementation will be needed for acceptance, since `adapt` is intended to be called frequently in library code and should not add significant overhead to ordinary attribute and type operations.

Open issues

Several questions remain open. The first is how adaptation interacts with inheritance: if a class inherits a `__conform__` method, it is not yet specified whether the subclass's protocol should be checked first. The second is whether the protocol side should be consulted only when the object side fails, or whether there are cases where it should take precedence. The third is whether the `alternate` argument should be allowed to be a callable that is invoked lazily.

The authors also note that caching of adaptation results is possible but would require careful definition of when a cached adapter becomes stale. This is deferred to a later revision.

Discussion

Commentators have raised concerns that the mechanism might encourage implicit conversions that are hard to trace. The proposal responds that explicit calls to `adapt` are required, so that conversions do not happen silently, and that the search order is simple enough to be explained in a few sentences.

Other commentators have asked whether the mechanism duplicates the work of `isinstance` and of abstract base classes. The authors reply that the two serve different purposes. An abstract base class describes what a class is. Adaptation describes what an object can be made to do, and it allows the conversion to be provided by code that is not part of the object's class.

Conclusion

The proposal offers a small, general mechanism for requesting that an object satisfy a protocol. It keeps the decision about how to adapt in the hands of either the object or the protocol, which allows independently developed code to interoperate without a central registry. The authors recommend that the mechanism be discussed further, that the open questions be resolved in a revision, and that a C implementation be prepared before any acceptance decision is made.
