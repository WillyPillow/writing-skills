PEP: 510
Title: Specialize functions with guards
Author: Victor Stinner
Status: Deferred
Type: Standards Track
Created: 2016
Python-Version: 3.6

Abstract

This PEP adds functions to the Python C API that specialize pure Python functions by attaching specialized code objects that run under guards. A specialized code object is a version of a function's code that the interpreter may run instead of the generic code, provided that a set of guards holds at call time. The guards check properties of the arguments and of the global environment that the specialized code depends on. If every guard passes, the specialized code runs. If any guard fails, the generic code runs. The mechanism lets a static optimizer apply transformations that are valid only under certain assumptions, while preserving the semantics of Python.

Motivation

Python's dynamic nature makes many optimizations difficult. A call to a function may refer to a global name that another module rebinds at any time, and the types of arguments may change from one call to the next. An optimizer that wants to remove the overhead of these checks must prove that the assumptions hold, which is often impossible in general. Some useful optimizations, however, are valid for the common case, where the assumptions do hold, and they are safe as long as the program checks the assumptions before running the optimized code.

Guards provide that check. An optimizer can produce a version of a function specialized for, say, integer arguments, and attach a guard that verifies the arguments are integers before running the specialized code. The check is cheap compared to the work the specialization saves, and when the guard fails, the program falls back to the generic version without any change in behavior.

The approach is useful for static optimizers, which analyze a program ahead of time or in a separate tool and produce the specialized code. The PEP does not define a particular optimizer, but it provides the interface that such an optimizer needs to install its results into the interpreter.

Rationale

The design places the mechanism in the C API rather than in the language. A Python program does not write guards directly, and it does not observe the specialization. The interface is for tools that extend the interpreter, and it keeps the language's semantics unchanged, which is a central requirement.

The guards must be pure, meaning they must not have side effects and must not depend on state that the function could change while it runs. A guard that performs an arbitrary check could change the behavior of the program, and the PEP restricts guards to checks that the interpreter can evaluate safely.

The specialized code must produce the same results as the generic code whenever the guards pass. This is a requirement on the optimizer, not on the interpreter, and the interpreter cannot verify it. The PEP places responsibility for correctness with the tool that produces the specialization.

Specification

The PEP adds a set of functions to the C API. One function registers a specialized code object for a given Python function, together with a list of guard functions. Each guard function receives the arguments of the call and returns a value indicating whether the specialized code may run. A second function removes specializations, and a third lists the specializations currently attached to a function.

When the interpreter calls a function that has specializations, it evaluates the guards in the order they were registered. If all guards pass, the interpreter runs the first specialized code whose guards passed. If none pass, it runs the generic code. The guards are evaluated before any argument conversion, so that the check reflects the values the caller provided.

The specialized code object must have the same signature as the generic code, and it must accept the same arguments. The interpreter does not check that the specialized code is equivalent to the generic code, only that it can be called with the same arguments.

Guards may refer to the global namespace. The PEP requires that the interpreter invalidate a specialization when a global name that a guard depends on is rebound, so that the guard does not pass on stale information. The mechanism for this invalidation is described in the reference implementation and is not part of the interface.

Performance

The cost of a call to a specialized function is the cost of the guard checks plus the cost of the specialized code. For the optimizations the PEP has in mind, the guard checks are expected to be much cheaper than the work they allow the interpreter to skip. When a guard fails, the cost of the call increases by the time spent evaluating the guard, which the PEP expects to be small.

The PEP does not give benchmark results, because the mechanism is intended for optimizers that do not yet exist in the form the PEP describes. The authors argue that the design should be judged by its ability to support optimization, and that the performance of a particular optimizer is a question for that optimizer's authors.

Backward compatibility

Programs that do not use the new functions are unaffected. The interface adds new functions to the C API and does not change existing behavior. The semantics of Python code do not change, since specializations run only when they are explicitly installed and only when their guards pass.

Alternatives

One alternative is to build specialization into the interpreter itself, so that it observes types at run time and produces specialized code automatically. This is a valid approach, and later versions of the interpreter pursued it. The PEP takes a different path because it wants to support static optimizers, which can use analysis that a run-time system cannot afford.

A second alternative is to keep the optimizations outside the interpreter entirely, for example by transforming the source code before it is compiled. This avoids changes to the interpreter, but the transformation must preserve every detail of the program's behavior, and the interpreter cannot check that it does. Guards allow the check to happen at run time, where it is cheap and reliable.

Open issues

The PEP leaves open the question of how invalidation should be triggered for guards that depend on the state of modules other than the one that defines the function. The reference implementation handles the common cases, but the complete rules require more study. The PEP also does not settle the naming of the new C API functions, which may change during review.
