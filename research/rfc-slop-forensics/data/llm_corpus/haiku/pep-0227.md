PEP: 227
Title: Statically Nested Scopes
Author: Jeremy Hylton
Status: Final
Type: Standards Track
Created: 2000
Python-Version: 2.2
Post-History:

Abstract

This PEP describes the addition of statically nested scoping, also known as lexical scoping, to Python. It is introduced in Python 2.2 and, as a source-level option, in Python 2.1. In addition, Python 2.1 issues warnings about constructs whose meaning changes when the feature is enabled.

The old language definition, in versions 2.0 and earlier, defines exactly three namespaces that are used to resolve names: the local namespace of a function, the global namespace of a module, and the built-in namespace. A name that is not bound locally is looked up in the global namespace and then in the built-ins. The change described here adds a fourth step. A name that is not bound locally may be resolved in the namespaces of the functions that lexically enclose the current function, in order from the innermost outward.

The most visible consequence is that nested functions, including lambda expressions, can refer to variables defined in the surrounding function. Currently, a lambda or inner function that needs a value from its enclosing scope must receive it through a default argument, which creates a binding in the nested function's own namespace. The default argument idiom works, but it is awkward, it can be surprising when the default is evaluated at the wrong time, and it hides the actual dependency of the function on its environment.

Motivation

Programmers coming to Python from languages with lexical scoping find the existing rules limiting. A typical case is a function that builds and returns a closure, or a callback that should read a value from the function that created it. Under the old rules these cases require either a class with explicit state, a default argument, or a mutable container used as a cell. Each of these works, but each is more code than the programmer should need to write.

The default argument idiom has a further problem. Because the default is evaluated once, when the function is defined, it captures the value of the outer variable at that moment. If the outer variable is later changed, the nested function does not see the change. Programmers who expect the nested function to observe the current value are surprised, and the resulting bugs can be subtle. Lexical scoping removes the need for the idiom and gives the expected behavior.

Specification

Under the proposed rules, a name reference inside a function is resolved using the following procedure. If the name is bound in the function's local scope, the local binding is used. Otherwise, if the name is bound in one of the enclosing function scopes, the innermost such binding is used. Otherwise, the global namespace is consulted, followed by the built-in namespace. The determination is made statically, when the code is compiled, and not at run time, so the search does not depend on the order in which functions are called.

Assignment to a name creates a local binding unless a declaration says otherwise. The proposal retains this rule, so that an assignment in a nested function does not change a variable of the enclosing function by accident. A new declaration, which is written as a statement at the top of the function body, allows a nested function to assign to a variable of an enclosing function. This declaration is introduced in a later revision and is not part of the core change described here.

The compiler must be able to determine, for every name reference, which scope provides the binding. This requires that the compiler analyze each function body and record the names that are local, the names that are free, and the scope from which each free name is taken. The information is stored with the code object so that the run-time lookup can use fast access paths.

Compatibility

The change alters the meaning of some existing programs. A program that defines a variable in an enclosing function and also uses a global variable of the same name inside a nested function will see different behavior, because the nested reference now resolves to the enclosing binding instead of the global one. Such programs are uncommon, but they exist.

To help programmers find these cases, the proposal introduces a source-level option that enables the new rules in Python 2.1 ahead of their default adoption in 2.2. When the option is enabled, the interpreter issues a warning for any construct whose meaning would change. The warning identifies the line and the name involved, so that the programmer can review the code and decide whether the change is intended.

The warnings are designed to be silenced once the programmer has checked the code. The proposal recommends that the warnings be issued only when the option is enabled, so that programs that do not opt in see no new messages.

Implementation

The implementation extends the compiler's symbol table pass. During this pass, each scope records its bound names and the names it refers to. A second pass then resolves each free reference to a scope, and the code generator emits instructions that access the enclosing binding through a cell object. A cell is a small container that holds the current value of a variable shared between a function and its nested functions.

Using cells means that a nested function sees updates to the enclosing variable, which is the behavior the proposal aims to provide. It also means that variables which are referenced by nested functions are stored in cells even within their own function, which has a small cost in speed. The authors measured this cost and found it acceptable for typical programs, and they note that it is paid only for variables that are actually shared.

Interaction with exceptions and generators

The proposal considers how the new rules interact with exception handling and with generators, which were introduced in a closely related release. A variable captured by a nested function remains alive for as long as the function does, so that a closure can outlive the call that created it. The proposal states that this behavior is intended and that it follows from the lexical model.

For generators, the proposal specifies that a generator body is a function scope like any other, so that names used inside a generator and defined in an enclosing function resolve in the same way.

Rationale

The authors considered two alternatives to lexical scoping. The first was to extend the default argument idiom with a syntax that makes the captured binding explicit. This would remove some of the awkwardness but would leave the underlying model unchanged and would still surprise programmers who expect closures to see current values. The second alternative was to introduce a new keyword for capturing variables. The proposal rejects this because it would add syntax without changing the semantics for the common case.

The static resolution of names was chosen because it is predictable and because it allows the compiler to produce efficient code. A dynamic scheme, in which the enclosing scope is searched at run time, would be more flexible but would be slower and would make the meaning of a program harder to determine by reading it.

Open questions

The proposal leaves a few points for future discussion. The first is whether the assignment declaration should be introduced in the same release as the read-only behavior or in a later one. The second is whether the warnings should be issued by default in the transitional release or only on request. The third concerns the treatment of names used in class bodies, which do not form closures in the same way as functions and which are therefore handled as a special case.

Conclusion

Statically nested scopes give Python the lexical scoping that many programmers expect, and they remove the need for default argument tricks in closures and inner functions. The change is backward-incompatible in a small number of cases, which the transitional warnings are designed to surface. The authors recommend the change, with the transitional plan described above, as the way to improve the clarity of Python programs without sacrificing predictability.
