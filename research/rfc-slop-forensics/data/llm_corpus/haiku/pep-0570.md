# PEP 570: Python Positional-Only Parameters

**Type:** Standards Track
**Status:** Draft
**Topic:** Language

## Abstract

This PEP introduces a new syntax, a bare slash `/` in a function's parameter list, that marks the parameters before it as positional-only. A positional-only parameter has no name that a caller can use as a keyword argument. When such a function is called, positional arguments are bound to these parameters solely by their order. The proposal lets library authors choose parameter names freely, including names that would otherwise collide with keyword arguments that callers want to pass, and it makes the intended calling convention visible in the signature.

## Motivation

When a library author designs a function, the parameter names become part of the public interface. Callers can pass a value by name, and the author cannot rename the parameter later without breaking those callers. This is usually the right behavior. Named arguments make calls readable and allow optional arguments to be skipped.

For some parameters, however, the name has no meaning to the caller. Consider a function whose first argument is a value to be processed, or a method whose first argument is a receiver. A caller who writes the value as a keyword argument is relying on a name that was chosen for internal convenience. The author has to be careful to choose a name that will never be needed as a keyword elsewhere, and the name then tends to be obscure, such as an underscore-prefixed word, or it has to be kept forever.

The problem is sharper when a function accepts arbitrary keyword arguments. If the signature includes a required parameter with an ordinary name, a caller who passes a keyword argument with the same name receives an error about the duplicate, even though the caller intended the keyword to be stored in the extra arguments. Authors work around this by naming the required parameter in an unusual way, which hurts readability.

Positional-only parameters address both problems. The author can name the parameter whatever is clearest in the body of the function, and the caller cannot use that name as a keyword. The signature states exactly how the function is meant to be called.

## Current practice

Python already has positional-only parameters, but only in C-implemented functions. Many built-in functions accept arguments by position alone, and their documentation says so with a marker. Python code has had no way to express the same thing. Authors who wanted the behavior had to write functions that accept `*args` and then unpack the first arguments by hand, which loses the signature information that tools and readers depend on.

## Specification

A function definition may include a bare slash in its parameter list. Every parameter that appears before the slash is positional-only. The slash itself is not a parameter and does not bind a value. Parameters after the slash remain usable by position or by keyword, as is the case for ordinary parameters.

The slash may follow parameters that have default values. Positional-only parameters with defaults are allowed, and the defaults apply when fewer positional arguments are passed. A parameter that is positional-only and has no default may not follow one that has a default, which is the same rule that applies to ordinary parameters.

Positional-only parameters may be combined with the existing forms of parameter. A function may have positional-only parameters, then ordinary parameters, then a variable-positional parameter and keyword-only parameters, in that order. The slash must appear before the star that introduces keyword-only parameters.

When a function with positional-only parameters is called, the interpreter binds positional arguments to the positional-only parameters first. If a keyword argument has the same name as a positional-only parameter, the keyword is not matched to that parameter. If the function has a variable-keyword parameter, the keyword is collected there instead. Without such a parameter, the call is an error because the keyword does not correspond to any parameter.

Lambda expressions accept the slash in the same way.

## Rationale

The bare slash was chosen as the marker because it reads as a boundary and because it is not already used in parameter lists. It mirrors the bare star that already marks the start of keyword-only parameters. The two markers together describe the three ways a parameter can be passed: by position only, by either position or name, and by name only.

The rule that positional-only parameters are bound first means that a keyword argument never conflicts with a positional-only parameter. This is the property that makes the feature useful for functions that accept arbitrary keywords, because the name of the positional-only parameter can be reused as a keyword without ambiguity.

The proposal does not add a way to declare a parameter as positional-only without a slash, nor does it change the handling of existing functions. Introducing a new marker keeps the syntax of current code unchanged.

## Backwards Compatibility

Existing code that does not use the slash is unaffected. The slash is a new token in a position that was previously a syntax error, so no valid program changes meaning.

Some code may be able to adopt positional-only parameters without any change in behavior for callers that use positional arguments. Callers that currently pass the affected parameters by keyword will receive an error after the change, so authors who adopt the feature should check for such calls before releasing a new version.

Tools that inspect signatures will need to be updated to report positional-only parameters. The reflection interface for function signatures can represent this kind of parameter, so the change is additive for code that reads signatures.

## Problems not solved

The proposal does not address every case in which a parameter name is awkward. It does not allow a parameter to be made positional-only after the fact, and it does not add a decorator that enforces the convention on existing functions. Those are left to other proposals if the need is shown.

The feature also does not change how methods bind their receiver. The receiver is an ordinary positional parameter that happens to be the first argument, and the same rules apply.

## Alternatives

One alternative was to use a naming convention, such as a double underscore prefix, to mark parameters as positional-only. This was rejected because naming conventions are not enforced, they are not visible in the signature, and they conflict with the name-mangling rules that already apply to double underscores in classes.

A second alternative was to use a decorator that rewrites the function to accept positional arguments only. This would keep the syntax unchanged but would hide the signature from tools and would add overhead to every call.

A third alternative was to require all parameters before the star to be positional-only. This would have been a simpler rule but would have removed the ability to pass ordinary arguments by keyword, which is the normal behavior and must stay.

## Open issues

The interaction between the slash and some forms of argument unpacking in calls needs to be reviewed against the implementation, particularly where a keyword argument is supplied through a mapping and the mapping contains a key that matches a positional-only parameter. The specification says such a key is collected by a variable-keyword parameter when one is present. The implementation must agree with this in all cases.

The documentation should explain the convention in a way that helps authors decide when to use it. The PEP suggests that authors use positional-only parameters for the first arguments of functions whose names carry no meaning for callers, and for parameters that a function accepts alongside arbitrary keywords.

## Reference implementation

A prototype of the parser and the call binding has been written and tested against the existing test suite. The prototype includes tests for defaults, for combination with variable and keyword-only parameters, and for keyword arguments that collide with positional-only names.
