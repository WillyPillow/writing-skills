Title: Function Signature Object
Author: Brett Cannon, Jiwon Seo, Yury Selivanov
Status: Final
Type: Standards Track

Abstract
========

Python has long supported introspection of functions and methods. By examining
a function object a program can reconstruct its signature, but the information
is stored in an inconvenient way. It is spread across several deeply nested
attributes, and extracting a complete picture of the parameters requires
knowledge of how those attributes relate to one another. This PEP proposes a
new representation for function signatures. The representation holds all of the
information about a function and its parameters, and it makes introspection
straightforward. The new object does not replace the existing function metadata,
which the interpreter itself uses to call functions. It exists to make
introspection easier for Python programmers.

In this PEP, "function" refers to both plain functions and methods unless
otherwise stated.

Motivation
==========

Tools that work with Python code often need to know what arguments a function
accepts. Documentation generators list parameters and defaults. Testing
frameworks inspect callables to decide how to supply fixtures. Decorators that
wrap functions must preserve the signature of the original so that callers
see the same interface. Each of these tools currently reimplements the logic
that interprets the attributes of a function object, and each implementation
must handle the cases of bound methods, keyword-only parameters, and variable
argument lists separately.

The attributes involved include the names of the arguments, their default
values, the names of the variable positional and keyword parameters, and the
annotations, which were added later. Reading them correctly requires an
understanding of how the code object's variable names are laid out, and of how
the number of defaults applies to the trailing parameters. Small mistakes are
common, and they are hard to notice because most functions do not exercise the
unusual cases.

A single object that describes a signature would replace this scattered logic.
It would give each tool the same view of a function, and it would reduce the
amount of code that must be written and maintained for introspection.

Specification
=============

The proposal adds a new class to the inspection module that represents a
function signature. An instance is created by passing a callable to a function
in the same module. The instance has an ordered mapping of parameter objects,
keyed by name, and a return annotation. The mapping preserves the declaration
order of the parameters.

Each parameter object records the parameter's name, its kind, its default value
if there is one, and its annotation if there is one. The kind is one of a small
set of constants that correspond to the forms of parameter that the language
supports: positional-only, positional-or-keyword, variable positional,
keyword-only, and variable keyword.

The signature object provides a method that binds a set of positional and
keyword arguments to the parameters. The method returns a bound object that
maps each parameter name to the value that would be assigned to it. If the
arguments do not match the signature, the method raises a type error with a
message that describes the mismatch. The binding method does not call the
function, so it can be used to validate arguments before a call is made.

A bound object also supports applying defaults, which fills in the values of
parameters that were not supplied and that have defaults. This makes it easy to
present the complete set of arguments that a call would use.

Signature objects compare equal when their parameters and return annotations
are equal. They may be converted to a string that reproduces the signature in
the form used by the language, which is useful for display and for generating
documentation.

For methods, the signature of the bound method omits the first parameter, so
that the object reflects the arguments that a caller supplies. A separate option
allows the unbound form to be requested when it is needed.

Rationale
=========

The design separates the description of a signature from the act of calling a
function. This separation keeps the new object simple and free of side effects.
It also means that the signature can be computed once and reused, and that it
can be compared, stored, or transmitted without invoking the function.

The parameter kinds are represented explicitly rather than inferred from the
presence of particular attributes. Explicit kinds make the object self-describing
and remove the need for tools to know the internal layout of code objects.

The binding method reproduces the rules that the interpreter applies, so that a
tool can predict whether a call will succeed without making the call. The
authors tested the method against a wide range of signatures to ensure that its
results match those of the interpreter.

Backwards Compatibility
=======================

The new object is an addition, and it does not change any existing attribute of
a function. Code that reads the old attributes continues to work exactly as it
did. The interpreter does not use the signature object internally, so calls to
functions are unaffected.

Reference Implementation
========================

A reference implementation was written in Python and included with the proposal.
It defines the signature, parameter, and bound classes, and it includes a set of
tests that compare the results of binding against the results of actual calls for
many combinations of parameter kinds. The implementation handles bound methods,
callable objects with a call method, and functions that have been wrapped by
decorators that follow the wrapping convention.

Rejected Ideas
==============

One proposal was to add the signature as a new attribute on every function. This
was rejected because it would increase the memory used by every function object,
and because most functions are never introspected.

Another proposal was to represent the signature as a tuple of tuples. This would
be compact, but it would be difficult to read and extend, and it would give users
no methods for binding or formatting.
