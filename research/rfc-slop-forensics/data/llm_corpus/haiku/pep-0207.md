PEP: 207
Title: Rich Comparisons
Author: Guido van Rossum, David Ascher
Status: Final
Type: Standards Track
Content-Type: text/x-rst
Created: 1998-07-17
Python-Version: 2.1

Abstract
========

This PEP proposes several new features for comparisons. It allows the six comparison operators, ``<``, ``>``, ``<=``, ``>=``, ``==``, and ``!=``, to be overloaded separately, both in classes written in Python and in C extension types. It also allows any of these overloaded operators to return a value other than a Boolean result. The proposal keeps the existing behavior for ordinary objects, so that code which depends on the current comparison semantics continues to work.

Motivation
==========

In the Python of this period, a class could define the ``__cmp__`` method to support comparisons. That method returned an integer that indicated the ordering of the two operands. The design worked for simple cases, but it had two serious limitations. First, a single method could not express all six operators efficiently, because the caller had to derive the result of each operator from one three-way answer. Second, the three-way answer could not express a comparison that has no natural ordering, such as the element-wise comparison of two arrays.

Numerical libraries were the most important users affected by these limitations. An array comparison should produce an array of Boolean results, one for each element, rather than a single truth value. The current design forced such libraries into awkward workarounds, and the results were often surprising to their users.

Rationale
=========

The proposal separates the six operators so that each can be defined independently. A class that only needs equality can define ``__eq__`` and ``__ne__``. A class that defines an ordering can define the four ordering methods. A class that needs all six can define them all, and it is not forced to derive the results from a shared helper.

Allowing a non-Boolean result is equally important. When a comparison returns an object, the interpreter passes that object through without converting it to a truth value. The caller decides whether to convert it. In a conditional expression, the truth value is computed as usual, so ordinary code continues to behave the same way.

The reflected operators are kept. If the left operand does not define the comparison, or returns a special marker indicating that it does not apply, the interpreter tries the reflected comparison on the right operand. The reflected form of ``<`` is ``>``, and the reflected form of ``==`` is ``==``.

Specification
=============

Each comparison operator is looked up as a method on the left operand. The method names are ``__lt__``, ``__le__``, ``__eq__``, ``__ne__``, ``__gt__``, and ``__ge__``. If the left operand does not provide the method, or if the method returns the special value ``NotImplemented``, the interpreter tries the reflected method on the right operand. If that also fails, the interpreter falls back to the existing behavior, which for equality compares identity and for ordering raises an error.

The result of a comparison is the object returned by the method. The interpreter does not convert it to a Boolean. Code that uses the result in a conditional context converts it at that point, using the usual truth-value rules.

For backwards compatibility, the ``__cmp__`` method continues to be honored. If a class defines ``__cmp__`` and does not define the rich comparison methods, the interpreter uses ``__cmp__`` to derive the results as it did before.

Backwards Compatibility
=======================

Most programs will see no change. Classes that define ``__cmp__`` continue to work. Classes that define no comparison methods keep the default identity behavior for equality. The one visible difference is that code which assumed a comparison always returns a Boolean may encounter an object instead, particularly when it uses comparisons on values from a library that adopts the new protocol.

The PEP recommends that library authors who return non-Boolean results document the fact clearly, so that callers know to convert the result explicitly where a Boolean is needed.

Implementation Notes
====================

The implementation adds the six method slots to the type object structure and changes the comparison code in the interpreter to consult them before falling back to ``__cmp__``. The change to the C API is additive. Extension types can set the new slots, and existing extensions continue to function without change.

Open Issues
===========

The PEP leaves open whether the reflected operator should be tried before or after the left operand's method when both operands are instances of unrelated classes. The proposal follows the convention used for arithmetic operators, in which the left operand is tried first.

It also leaves open whether a standard library should be provided for common comparison helpers, such as a function that derives the four ordering methods from ``__eq__`` and one ordering method. Such a helper would be convenient, but it is not required by the core proposal.
