PEP: 520
Title: Preserving Class Attribute Definition Order
Author: Eric Snow
Status: Final
Type: Standards Track
Created: 2016
Python-Version: 3.6

Abstract

The class definition syntax is ordered by its very nature. The attributes defined in a class body therefore have an order, and that order is sometimes significant. If the order were available outside the class body, programs could use it without extra boilerplate, such as metaclasses or manually maintained lists of names. Currently, Python does not preserve the order in which attributes are introduced in a class body. This PEP changes that. The order in which attributes are introduced in the body is recorded and made available on the class through a new attribute, __definition_order__, which allows introspection of the original definition order.

Motivation

A class body is executed as a sequence of statements. Each statement that binds a name adds an entry to the class namespace, and the sequence of these bindings is a natural ordering. Many programs depend on it. Serialization libraries need to write fields in a stable order. Command-line tools built from class definitions need to present options in the order the author wrote them. Enumerations and schema definitions often rely on the position of each member.

At present, the namespace is a dictionary that records only the final value of each name. Before Python 3.6, the dictionary did not guarantee any order, so the information was lost. Even with the ordering that the interpreter now provides for dictionaries, the class's __dict__ does not give a reliable account of the definition order, because it reflects insertions and deletions in a way that the author did not necessarily intend. Attributes may be rebound, deleted, or set by a decorator after the body has run, and these operations change the mapping without changing the definition.

Programmers have worked around this for years. The usual approaches are to write a metaclass that records the order in a separate structure, or to maintain a list of names by hand alongside the class. Both approaches add code that is easy to get wrong, and both repeat information the language already has.

Rationale

The definition order is recorded at the moment each name is bound during execution of the class body. This recording is cheap, and it reflects exactly what the author wrote. The proposal therefore stores the order directly, rather than inferring it later from the dictionary.

The proposal records only names that are bound in the body. Attributes added to the class after its creation, through assignment on the class object, are not included in the definition order. This keeps the meaning of the attribute tied to the definition, which is what the name suggests.

The name __definition_order__ was chosen to be explicit about its purpose. The double underscores mark it as a special attribute, consistent with other attributes the interpreter provides for classes and modules, and the word "definition" distinguishes it from the existing namespace.

Specification

When a class statement executes, the interpreter records, for each name bound in the class body, the position of its first binding. The result is a tuple of names in the order of first binding. This tuple is stored in the __definition_order__ attribute of the class.

If a name is bound more than once in the body, it appears in the tuple at the position of its first binding. If a name is deleted and later rebound, it keeps its original position. Names that are bound only through mechanisms outside the class body, such as a decorator that sets an attribute, are not added to the tuple, because they are not part of the definition as written.

The attribute is read-only from the perspective of ordinary code. Assignment to __definition_order__ on the class is permitted for compatibility with metaclass machinery, but the interpreter does not use a modified value when it computes the order of later definitions.

Subclasses have their own __definition_order__, which records only the names bound in their own bodies. The attribute does not include inherited names, since the order of the base class is a separate fact that the subclass author did not write.

Backward compatibility

The change adds one attribute to every class created by a class statement. Programs that do not look for the attribute are unaffected. Programs that define their own attribute with the same name may be affected, but such conflicts are unlikely given the special form of the name.

The cost of the change is a small amount of memory for each class and a small amount of time during class creation. The PEP argues that this cost is acceptable, given how frequently classes are created in typical programs and how little work the recording requires.

Introspection

The new attribute lets a program walk the attributes of a class in definition order. For example, a function that prints the fields of a dataclass-like object can iterate over __definition_order__ and look up each value in the class namespace. The function does not need to know how the class was defined or whether a metaclass was involved.

The attribute also helps tools that generate documentation or help text. A documentation generator can present members in the order the author chose, which is often the most sensible order for a reader.

Alternatives

One alternative is to rely on the dictionary order of the class namespace. This is what the interpreter provides, but it reflects operations after the body has run, as discussed above, so it does not capture the definition order reliably.

A second alternative is to require metaclasses to be used for ordered attributes. This is the status quo for those who need the feature, and it has the disadvantage that the metaclass must be part of every class in a hierarchy that needs the order. The metaclass approach also adds complexity to the class's type, which can conflict with other metaclasses.

A third alternative is to record the order in the namespace itself, for example by storing the sequence under a reserved key. This was rejected because it would place an extra entry in every namespace and would affect code that iterates over the namespace.

Open issues

The PEP does not decide whether the attribute should also be provided for functions defined in a class body, or for modules. These extensions may be considered later if the need becomes clear. The name of the attribute may be revisited if a conflict arises with a widely used library.
