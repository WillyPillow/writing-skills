# PEP 504: Using the system random number generator by default

- **Type:** Standards Track
- **Status:** Withdrawn

## Abstract

The module-level functions in the `random` module are backed by the Mersenne Twister, a deterministic generator. This is appropriate for simulation and testing, where repeatable sequences are valuable, but it is not appropriate for security sensitive work such as generating tokens, keys, or nonces. Programmers who need secure randomness are expected to switch to `os.urandom`, to `random.SystemRandom`, or to a third-party library. Many do not know that they should.

This proposal changes the module-level functions so that they use the operating system's random number source by default. Users who need repeatable sequences would call a function that explicitly creates a seeded generator. The change is intended to make the secure choice the default one.

## Motivation

The problem is not that the Mersenne Twister is broken for its intended purpose. It is that its default use is easy to misjudge. A developer who writes `random.choice` to pick a temporary password is making a security decision without realising it. The Mersenne Twister's output can be predicted from a small number of observed values, and that makes it unsuitable for any secret.

Incidents of this kind have appeared repeatedly in published software. The pattern is consistent: a developer used the convenient module-level function in a place that needed unpredictability, and the flaw was found years later. The delay between introduction and exploitation makes the lesson hard to learn from experience, because the developer who made the mistake is seldom the one who finds out about it.

A safer default would remove the lesson entirely. Code written by people who do not think about security would then be secure by default, and people who want predictable sequences would ask for them explicitly. The cost of asking is small, and the benefit is that the common mistake becomes much harder to make.

## Specification

The proposal makes the following changes. The module-level functions such as `random`, `randint`, `choice`, `shuffle`, and `sample` would obtain their randomness from an instance of `SystemRandom`, which reads from the operating system. Where the operating system provides no secure source, the module would fall back to the Mersenne Twister and emit a warning.

A new function, `random.seeded_instance(seed)`, would return a new generator based on the Mersenne Twister, initialised with the given seed. Scripts that depend on reproducible output would call this function and use the returned object's methods in place of the module-level functions.

The `seed` function would continue to exist, but calling it would switch the module-level functions to the deterministic generator and emit a deprecation warning. This gives existing reproducible scripts a migration path.

The change does not alter the behaviour of `SystemRandom` itself, and it does not change the API of the `Random` class.

## Performance

Reading from the operating system is slower than running the Mersenne Twister. The proposal measured the cost on several platforms and found that it is significant for programs that draw very large numbers of values, such as Monte Carlo simulations. For most other uses the difference is too small to matter.

The proposal argues that the cost is acceptable because the programs most affected are the ones that can afford it, and because the alternative is a steady stream of security flaws. Programs that need speed for simulation can use the seeded generator, which keeps the old performance.

## Rationale

The main argument is that defaults shape behaviour. A function that most people use without thinking should be safe to use without thinking. The security cost of the current default falls on people who did not choose it, which is the wrong way round.

Keeping the seeded generator as an explicit choice preserves the reproducibility that many scientific and testing workflows rely on. The proposal does not try to take away a capability. It asks only that the capability be requested.

Using the operating system's source rather than a new generator was chosen because that source is already audited and widely trusted. Inventing a new secure generator would introduce a new and unproven component.

## Backwards Compatibility

This change is not backwards compatible in the strict sense. Code that relies on `random.seed` and then expects the same sequence will produce different output. The deprecation warning helps programmers find this code, and the proposal suggests a transition period of several releases before the old behaviour is removed.

Code that uses the module-level functions for non-security purposes will continue to work, but its output will no longer be reproducible unless it is changed to use a seeded instance. Test suites are the most likely to be affected.

## Discussion

The proposal received strong support from people who had seen security problems caused by the default. It also received substantial criticism. Several core developers argued that the change would break a large body of existing code and that the warning mechanism would not reach most affected programmers in time. Others argued that the performance cost would be unacceptable in scientific code, and that the seeded-instance function would not be discovered by people who need it.

A recurring point was that the problem is better addressed by documentation and by static analysis tools than by changing behaviour. Tools can warn about the use of `random` in a function whose name suggests security, such as one that creates a password. Supporters replied that documentation has not solved the problem over many years and that tools do not reach code that never runs through them.

Some participants suggested a middle course, in which the module-level functions remain as they are and a new module provides a secure default. This would avoid breakage, but it would leave the original problem in place for anyone who did not switch.

## Status

The proposal was withdrawn after review. The authors concluded that the breakage would be too large for the benefit, and that the best course was to improve documentation and to encourage the use of the secrets-oriented functions for security work. A later module was added to the standard library to provide convenient access to secure random values, which addresses the most common use case without changing the behaviour of the existing module.

## Summary

The proposal asked that the module-level random functions use the operating system's secure source by default and that reproducible sequences be requested explicitly. It was motivated by the repeated misuse of a deterministic generator in security-sensitive code. Because of the compatibility cost and the performance trade-off, the proposal was withdrawn, but the discussion shaped later guidance and tooling.
