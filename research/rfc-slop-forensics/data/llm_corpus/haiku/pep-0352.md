PEP: 352
Title: Required Superclass for Exceptions
Author: Brett Cannon, Christian Heimes
Status: Final
Type: Standards Track
Content-Type: text/x-rst
Created: 2006-08-24
Python-Version: 2.5

Abstract
========

Before Python 2.5, any classic class could be raised as an exception. The plan
for Python 2.5 was to allow new-style classes as exceptions as well, but that
would make the problem worse, since it would mean that any class or instance
could be raised. This is a problem because it prevents any guarantees from being
made about the interface of exceptions. This PEP proposes a new superclass that
every raised object must inherit from. Requiring this superclass allows a
standard interface for exceptions to exist that can be relied upon, and it gives
the exception hierarchy a single known root.

Motivation
==========

Exception handling in Python is driven by the class of the raised object. A
handler names the classes it wishes to catch, and the interpreter checks whether
the object being propagated is an instance of one of them. Code that catches
exceptions, and code that inspects them, relies on a set of common attributes
and methods, such as the message, the arguments, and the traceback. Those common
attributes have never been guaranteed, because any class could be raised.

The consequence is that the exception interface is defined by convention rather
than by the language. A library that wants to attach extra information to an
error must decide for itself how to present that information, and a tool that
wants to format errors must handle many shapes of object. The lack of a common
root also makes it hard to write a handler that catches every error without also
catching system signals or other control flow objects.

One might argue that requiring a particular base class for a specific interface
is unpythonic. In the case of exceptions, however, there is a good reason. An
exception is a signal to the caller that something has gone wrong, and the caller
needs to be able to rely on the signal having a predictable form. Duck typing
serves well for most data, but it is a poor match for error propagation, where
the interpreter itself must make decisions about how to unwind the stack.

Rationale
=========

The proposal introduces a root class for all raised objects. The root is a
direct subclass of the object type and carries the attributes that every exception
should have. A second class derives from the root and serves as the base for the
ordinary exceptions that programs raise and catch. Control flow exceptions, such
as those used to exit a program or to stop iteration, derive from the root but not
from the ordinary base, so that a generic handler does not catch them by accident.

The split between the two classes is the most important design choice. A program
that wants to catch every ordinary error can name the ordinary base. A program that
wants to catch absolutely everything, including control flow signals, can name the
root. Both options are available, and each has a clear meaning.

Existing exception classes in the standard library are rearranged to fit the new
hierarchy. Their names and their behavior are unchanged, but their positions in the
tree move so that they derive from the appropriate base. This rearrangement is the
largest part of the implementation effort, and it is the part most likely to surface
subtle differences.

Specification
=============

The interpreter requires that any object raised as an exception be an instance of the
root class. An attempt to raise an object that is not an instance of the root class
results in a type error. The check is made at the point where the exception is raised,
so that the error is reported close to its source.

The root class provides the attributes that are common to all exceptions. These
include the arguments passed to the constructor, a string representation, and the
ability to be compared for equality with other exceptions of the same type.

The ordinary base class provides the same attributes, together with any behavior that
is specific to ordinary errors. Programs written as subclasses of the ordinary base
continue to work without change.

String exceptions, which were an older mechanism that raised a string instead of an
object, are deprecated. A warning is issued when such an exception is raised. The
mechanism is expected to be removed in a later release, once the deprecation period has
passed.

Backwards Compatibility
=======================

Most programs are not affected, because they raise and catch subclasses of the ordinary
base, and that base continues to exist with the same name. Programs that catch a
specific exception class by name are also unaffected, because the class names are
preserved.

Programs that raise objects which are not exceptions will break. Such programs were
already unusual, and the deprecation period gives their authors time to adjust. Programs
that rely on catching a bare exception clause to intercept every raised object will see
a change in behavior when control flow signals are involved, and the documentation
describes this change so that authors can review their code.

Reference Implementation
========================

A reference implementation modified the interpreter's exception machinery to enforce the
requirement and to define the new classes. It also rearranged the standard exception
classes and updated the tests that depend on the hierarchy. The changes were reviewed
against the documentation and tested across the standard library.

Rejected Ideas
==============

One proposal was to allow any object to be raised but to require that objects used for
errors provide a set of methods. This would preserve flexibility but would not give any
guarantee, because the methods could be missing or behave differently in each case.

Another proposal was to make the root class an interface defined by an abstract base
mechanism rather than a concrete class. This was rejected because the interpreter needs a
concrete type to check at raise time, and because the abstract mechanism was not yet
available in the form needed.
