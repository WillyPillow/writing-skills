# PEP 525: Asynchronous Generators

| Field | Value |
|---|---|
| PEP | 525 |
| Title | Asynchronous Generators |
| Type | Standards Track |
| Status | Final |
| Requires | 492 |
| Created | 2016 |
| Python-Version | 3.6 |

## Abstract

PEP 492 introduced support for native coroutines and `async`/`await` syntax to Python 3.5. It is proposed here to extend Python's asynchronous capabilities by adding support for *asynchronous generators*.

## Motivation

Python generators provide a concise way to produce a sequence of values lazily. A function containing `yield` returns an iterator, and the consumer drives the production one value at a time. Native coroutines introduced by PEP 492 allow asynchronous code to be written in a straight-line style using `await`, but they do not provide a way to produce a stream of values asynchronously in the same manner.

Before this proposal, a developer who wanted to iterate over data that arrives asynchronously had to choose between awkward alternatives. One option was to write a class implementing `__aiter__` and `__anext__` by hand, which requires managing state explicitly and quickly becomes verbose. Another was to build the stream from a coroutine that returns a list, which defeats the purpose of streaming when the data set is large or unbounded. A third was to combine a generator with callbacks, which obscures control flow.

Real-world examples abound. A client reading rows from a database cursor, a websocket delivering messages, or a paginated HTTP API that fetches one page at a time all naturally produce values asynchronously. Expressing them as asynchronous generators would let the code look like ordinary generator code, with `yield` marking each value and `await` marking each point where the event loop may switch tasks.

## Specification

A function that contains both `async def` and `yield` is an asynchronous generator function. Calling it returns an asynchronous generator object. The object implements the asynchronous iterator protocol, which means it provides `__aiter__` returning itself and `__anext__` returning an awaitable. Each awaitable resolves to the next yielded value, or raises `StopAsyncIteration` when the function returns.

Inside an asynchronous generator, the `await` expression is permitted and suspends the generator until the awaited object completes. The `yield` expression produces a value to the consumer. The combination of the two lets the body perform asynchronous I/O between yielded values.

Consumers iterate over an asynchronous generator with `async for`. The loop calls `__anext__`, awaits the result, binds the value, and runs the body. An `async for` statement is permitted only inside an `async def` function, consistent with the rule that `await` requires a coroutine context.

A `return` statement with a value is a syntax error inside an asynchronous generator, because the protocol has no channel for delivering a final return value. A bare `return` is permitted and ends the iteration.

The proposal also defines asynchronous comprehensions, which allow `async for` clauses inside list, set, dictionary, and generator expressions. These comprehensions may be used only inside asynchronous functions, and they consume asynchronous iterables by awaiting each step.

## Finalization

A generator that is not run to completion holds resources in its frame. For synchronous generators, Python calls `close()` when the object is garbage collected, which raises `GeneratorExit` inside the frame so that `finally` blocks run. The author extends this behavior to asynchronous generators, which need a way to perform asynchronous cleanup. Because cleanup may itself need to await, the interpreter cannot simply call a method from the garbage collector.

The proposal addresses this with an asynchronous generator finalizer hook. When an asynchronous generator is first iterated, the event loop may register a finalizer that the interpreter calls when the generator is about to be collected. The finalizer schedules the generator's `aclose()` method as a task on the loop, which runs the cleanup code asynchronously. The `sys.set_asyncgen_hooks` function lets the event loop install these hooks, and the standard `asyncio` event loop does so automatically.

The method `aclose()` returns an awaitable. Awaiting it raises `GeneratorExit` at the suspended `yield`, permitting cleanup to run. If the cleanup itself awaits, that await is honored, because the close operation runs as a coroutine. This gives asynchronous generators the same guarantee of deterministic cleanup that synchronous generators already have, at least when the event loop cooperates.

## Rationale

The design mirrors synchronous generators as closely as possible, so that developers who know one form can read the other without retraining. The `async` prefix on the function signals that the body may suspend for asynchronous reasons, and the protocol names follow the pattern established by PEP 492.

A separate protocol for asynchronous iteration, with `__aiter__` and `__anext__`, was chosen over reusing `__iter__` and `__next__`. Reuse would have produced ambiguous behavior, since an object might be iterable both synchronously and asynchronously, and the two protocols need different calling conventions. Keeping them distinct makes the intent of each loop explicit.

The author considered letting `yield` produce an awaitable directly, but rejected it because it would blur the distinction between a value and a pending operation. Keeping `yield` for values and `await` for suspension keeps each construct doing one job.

## Performance

The author measured the overhead of asynchronous generators against hand-written asynchronous iterators and found the generator form to be faster, since the interpreter needs less bookkeeping per step. The measurements were taken on a microbenchmark that yields a large number of values without performing I/O, and the author notes that real workloads will be dominated by the I/O itself.

## Backwards Compatibility

The proposal adds new syntax only in contexts that were previously errors, so existing programs are unaffected. The new keywords do not become reserved; `async` and `await` were already reserved by PEP 492 for the current release line.

## Reference Implementation

The implementation extends the compiler to generate a distinct code object for asynchronous generator functions and adds a new object type to the interpreter. The finalizer hooks are implemented as a pair of functions stored in the interpreter state. The changes were merged in the release cycle that followed acceptance.

## Open Issues

The author lists several questions for future consideration. One is whether asynchronous generators should support a `yield from` form delegating to another asynchronous iterable; this was deferred because the semantics of delegation across await points needed more study. Another is whether the finalizer hook should be mandatory for event loops, or whether a loop that does not install it should fall back to dropping the generator without cleanup. The author recommends documenting the behavior in the library reference and leaving the choice to implementers.
