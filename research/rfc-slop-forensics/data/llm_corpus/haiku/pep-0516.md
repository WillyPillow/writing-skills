Abstract
========

This PEP specifies a programmatic interface that pip and other distribution or installation tools use when they work with Python source trees. A source tree may be a developer's checkout, such as a git repository, or an unpacked source distribution. The interface allows pip to be decoupled from its current hard dependency on setuptools.

The decoupling serves two purposes. First, it enables new build systems that may be much easier to use, without requiring them to appear to be setuptools. Second, it allows setuptools to change its user interface without breaking pip, which gives the two projects a looser coupling. The interface also lets pip install the build time requirements of a package, which is an important step toward giving pip full feature parity with the installation components of the setuptools stack.

Motivation
==========

Installing a package from source requires running code that the package's author wrote. In the current arrangement, pip always runs setuptools to perform this step. The arrangement works, but it has two costs that have grown over time.

The first cost is that pip cannot use any build tool other than setuptools without that tool pretending to be setuptools. A project that wants to use a different build system must provide a compatibility shim, and users must understand why the shim exists. The shim is a source of confusion and a place where bugs hide.

The second cost is that setuptools is the only tool that pip can rely on to know how to build a source tree. Setuptools must therefore keep its interface stable for pip, even when it would prefer to change it. Any change that breaks pip's assumptions must be coordinated across both projects, and this coordination slows the development of both.

Other installation tools, such as conda, face the same problem. They need to build packages from source, and they need to know which dependencies must be present before the build can begin. A shared interface would let them use the same build systems as pip without duplicating the work.

Rationale
=========

The design places a small, stable interface between the installer and the build system. The installer asks the build system to perform a fixed set of operations. The build system answers in a documented form. Neither side needs to know how the other is implemented.

The key idea is that the build system is declared by the project itself. A project states, in a file at the root of its source tree, which build system it uses and which packages that build system needs. The installer reads this declaration and uses it to set up an isolated environment for the build. The installer does not need to know in advance which build tool the project uses.

The file chosen is ``pyproject.toml``. It is a neutral location that is not specific to any build tool, and it can be read by a program without executing any code. Reading the declaration before the build begins is important because it allows the installer to install the build requirements first, and to do so without running the build system itself.

The interface is expressed as a Python module that the build system provides. The installer imports this module in a fresh environment and calls the functions it defines. The functions cover building a wheel, building a source distribution, and reporting the requirements that a build needs at a particular point. The set of functions is kept small on purpose.

Specification
=============

A source tree that uses this PEP contains a file named ``pyproject.toml`` at its root. The file has a table named ``[build-system]``. The table has a key named ``requires``, which is an array of requirement specifiers that must be installed before the build begins. It has a key named ``build-backend``, which is a string naming the Python object that provides the build interface. An optional key named ``backend-path`` gives a list of directories that are added to the import path when the backend is loaded.

If the table is absent, the installer must assume a default. The default is the setuptools build system, with the requirement that a version of setuptools that supports the legacy interface is installed. This default preserves the behaviour of existing source trees, which do not have the table.

The installer creates an isolated environment, installs the requirements listed in the table into it, and imports the backend. It then calls the functions of the backend. The functions take a directory argument in which to place the result, and they return the name of the file that was created.

The backend must not assume that its functions are called in any particular order, other than the one that the installer documents. The installer must not assume that the backend writes any file other than the one it reports.

Requirements for the build
==========================

The backend can report additional requirements that are needed only for a particular kind of build. A function that reports these requirements returns a list of requirement specifiers. The installer installs them into the isolated environment before calling the build function that needs them. This allows a backend to declare, for example, that a wheel build needs a compiler helper package that a source distribution build does not.

Security implications
=====================

The interface runs code from the source tree, and so it has the same security properties as the existing setup script mechanism. A user who installs a package from source trusts the author of the package to the same degree as before. The isolated environment reduces the risk that the build modifies the user's own environment, but it does not prevent a malicious backend from doing harm within the build process.

The declaration of the build system is read before any code runs, which means that the list of requirements can be inspected by a tool that does not trust the source tree. This is a useful property for auditing, and tools may take advantage of it.

Backwards compatibility
=======================

Existing source trees that have no ``pyproject.toml`` continue to be built with setuptools, as before. Existing setup scripts continue to work through the legacy interface, which the default backend provides. No change is required for projects that do not wish to adopt the new interface.

Projects that adopt the table can choose a build system that differs from setuptools. Users with older installers, which do not understand the table, will continue to use setuptools for these projects. This is a limitation, and it is one that the ecosystem must work through over time.

Reference implementation
========================

A reference implementation of the installer side is provided as part of pip. It reads the declaration, creates the isolated environment, installs the requirements, and calls the backend functions. A reference implementation of a backend is provided as a minimal example, so that other authors can see how to write one.

Rejected alternatives
=====================

One alternative was to require each build system to provide a command line program, rather than a Python module. This would allow any language to implement a backend, but it would make the interface slower and harder to test. The module interface was preferred because the installer runs in Python and because a module can be imported without starting a new process.

Another alternative was to let the installer read the build requirements from the existing setup file. This would avoid a new file, but it would require the installer to run code before knowing the requirements, which defeats the purpose of the declaration.

Open issues
===========

The exact list of functions in the interface may need to grow as build systems evolve. The authors have kept it small, and they expect that any addition will be made through a later PEP.

The treatment of editable installs, which allow a developer to use a source tree directly without copying it, needs more discussion. The interface must provide a function for this case, and the details should be settled with the build system authors.
