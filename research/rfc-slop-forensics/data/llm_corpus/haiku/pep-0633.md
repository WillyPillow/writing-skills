PEP: 633
Title: Dependency specification in pyproject.toml using an exploded TOML table
Author: Brett Cannon, and others
Discussions-To: packaging discussion list
Status: Rejected
Type: Standards Track
Created: 2020
Post-History: 2020

Abstract

This PEP specifies how a project's dependencies may be written in a `pyproject.toml` file, using the fields defined in PEP 621, as an alternative to the approach based on PEP 508 strings defined in PEP 631. The alternative represents each dependency as a table with named keys, rather than as a single string. The proposal is intended for tools that consume the file, so that they can read dependency information without parsing a requirement string, and for authors who prefer a structured form over a compact one.

Motivation

PEP 621 standardized the core metadata of a project in `pyproject.toml`, including the list of dependencies. Under that standard, each dependency is a string in the format defined by PEP 508, such as `"requests >= 2.20, < 3"`. The string format is compact and familiar, and it is what most packaging tools already accept. It is also the format that many tools must parse, and parsing requirement strings is non-trivial, particularly when extras, markers, and URLs are involved.

Some tool authors and users have asked for a structured alternative. A table-based representation would make each part of a dependency explicit: the name, the version constraint, the extras, and the environment markers would each be separate values. Editing such a file could be done with simple key updates rather than string manipulation, and validation could be performed by a schema without a custom parser. The proposal responds to this request.

The proposal does not aim to replace PEP 508 for command-line tools or for the internal metadata of built distributions. Its scope is limited to the dependency declarations in `pyproject.toml`.

Specification

Under this proposal, the `dependencies` key in the `[project]` table may be given either as a list of PEP 508 strings, as PEP 621 allows, or as an array of tables in which each table describes one dependency. The two forms are alternatives, and a single file must use one or the other. A tool that reads the file must accept both.

Each dependency table has a required key `name`, which holds the distribution name. It may have the following optional keys:

- `specifier`, a string holding a version specifier in the form defined by PEP 440, such as `">=2.20,<3"`
- `extras`, an array of strings naming the extras requested
- `marker`, a string holding an environment marker in the form defined by PEP 508
- `url`, a string holding a direct reference to an archive or repository, for dependencies that are not taken from an index

The keys `specifier` and `url` are mutually exclusive. A dependency table that specifies both is invalid. A dependency table with neither key is treated as a request for any version of the named distribution.

A tool that receives a table-form dependency must be able to convert it into the equivalent PEP 508 string. The conversion is defined in the proposal so that the two representations have the same meaning. For example, a table with the name `requests`, the specifier `>=2.20,<3`, and the extras `["security"]` corresponds to the string `requests[security] >=2.20,<3`.

Example

```toml
[project]
name = "example-project"
version = "1.0.0"
dependencies = [
    { name = "requests", specifier = ">=2.20,<3", extras = ["security"] },
    { name = "tomli", specifier = ">=1.1", marker = "python_version < '3.11'" },
]
```

Rationale

The table form was chosen because it gives each piece of a dependency a name and a type. A tool that wants to change a version constraint can edit one key without touching the rest of the entry. A tool that wants to check markers can read a single value without splitting a string. The authors believed that this would reduce bugs in tools that edit the file, and that it would make the file easier to validate with generic schema tools.

The proposal considered allowing only the table form, but that would have broken every existing file and every tool that produces the string form. It therefore allows both, with a rule that a file uses one form consistently.

The proposal also considered using inline tables for each dependency rather than an array of tables. The authors preferred the form shown above, because it places each dependency on its own line in a way that is easy to scan.

Backward compatibility

The proposal is additive. Existing files that use strings remain valid, and tools that only understand strings are not required to change for them. A file that uses the table form will be rejected by tools that do not implement this PEP, and the proposal notes that such tools would need to be updated before users could adopt the new form.

Security implications

The proposal does not introduce new mechanisms for installing code, so it does not change the trust model of packaging. However, the `url` key allows direct references, which are already possible through the string form, and the proposal recommends that tools apply the same restrictions to both forms.

Discussion

Commentators raised several concerns during the discussion period. The first was that having two forms for the same information would complicate tools, since every consumer would need to implement both parsers and a conversion between them. The authors acknowledged this cost and argued that the conversion is simple and that the string form would remain the recommended one for most users.

A second concern was that the table form would make files longer and harder to read in the common case. Several participants said they preferred the compact string form for simple projects, and they asked that the table form be restricted to cases where it is needed. The authors agreed that the string form should be the default in documentation.

A third concern was that the proposal duplicated work already done in PEP 631 and that the community should settle on one approach. The authors replied that PEP 631 describes the same information in a different way, and that the choice between them is a matter of taste rather than of technical necessity. This point was not resolved to the satisfaction of all participants.

Reference implementation

A reference implementation was written as a small library that converts between the two forms and validates the table form against the specification. It was used to test the conversion rules and to check that the examples in this document produce the expected strings. The library was not integrated into any major packaging tool during the discussion period.

Outcome

The proposal was discussed at length on the packaging discussion list and in the packaging working group. The community did not reach consensus on adopting two representations for the same field. The PEP was therefore marked as rejected, and the string form defined in PEP 621 remained the standard for dependency specification in `pyproject.toml`. Some of the ideas in the proposal, such as the separation of name, specifier, and marker into named fields, were noted as useful for tool authors who need a structured view of the data, and they were encouraged to implement that view internally.

Conclusion

The proposal sought to offer a structured, table-based way to write dependencies in `pyproject.toml` as an alternative to PEP 508 strings. Its authors argued that this would ease editing and validation for tools. The discussion showed that the cost of supporting two forms outweighed the benefit for most users, and the PEP was rejected in favor of the single string-based standard.
