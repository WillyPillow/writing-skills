PEP: 437
Title: A DSL for specifying signatures, annotations and argument converters
Author: Larry Hastings
Status: Final
Type: Standards Track
Content-Type: text/x-rst
Created: 2013-03-10
Python-Version: 3.4

Abstract
========

The C-API of CPython has no mechanism for describing the signature of a
function, the annotations of its parameters, or the conversion from Python
objects to C values that each parameter needs. Several approaches have been
considered. Cython derives this information from ``cdef`` declarations in
``.pyx`` files. CPython's own C functions, however, often need initialization
and cleanup code that cannot be expressed in a declaration. PEP 436 proposed a
domain specific language (DSL) written inside C comments, which resembles a
per-parameter configuration file. A preprocessor reads these comments and
emits an argument parsing function, docstrings, and a header for the function
that uses the parsed results. That function is called the *implementation
function*.

This PEP refines the design of that DSL. It describes the syntax, the
semantics of converters, and the way the preprocessor is integrated into the
build. The goal is to remove the hand-written parsing boilerplate that
accounts for a large fraction of the C code in the interpreter, while keeping
the generated code readable enough to review.

Rationale
=========

Writing an argument parser for a C function by hand is repetitive and error
prone. The programmer must unpack a tuple or a set of keyword arguments,
check the number of arguments, convert each one to the expected C type, and
report a helpful error when a conversion fails. Each step is simple, but
omitting one of them produces a bug that may not surface until a rarely used
code path is exercised. Documentation for the same function must be kept in
sync with the parser, which is a second source of divergence.

A declarative description avoids both problems. If the function's parameters,
defaults, and converters are written once, the parser, the docstring, and the
argument checking can all be derived from that description. The description
also serves as a compact summary of the function's interface that a reader can
check at a glance.

The DSL described here is deliberately limited. It is not a general purpose
language, and it does not attempt to express arbitrary C code. Anything that
cannot be captured by a converter is left to the implementation function, which
remains ordinary C.

Specification
=============

A block of DSL text begins with a line containing ``/*[`` followed by the
name of the DSL, and ends with a line containing ``]*/``. Within the block,
the first non-empty line names the function and its return type. Each
following line describes one parameter, using the form of the parameter name,
followed by a colon, a converter name, and optionally a default value and a
set of flags.

For example, a function that takes an optional string and an integer might be
described as follows.

::

    /*[dsl]
    module.function
        name: str(defaultvalue="")
        count: int = 1
    [dsl]*/

The preprocessor reads this block and generates a static function that parses
the arguments into C variables, applies the converters, and then calls the
implementation function with the converted values. It also generates a
docstring that lists the parameters and their defaults, and a header that
declares the implementation function with the correct types.

Converters are named in a registry. Each converter specifies the C type of
the variable it produces, the code that performs the conversion, and the code
that releases any resources acquired during the conversion. Built-in
converters cover the common scalar and string types. Projects may define
their own converters in the same way, provided that they supply the code for
each of these parts.

Keyword-only parameters are indicated by a marker line. Positional-only
parameters are indicated by a separate marker. Default values are written as
C expressions, which the preprocessor copies into the generated code. The
generated parser checks argument counts and reports errors using the same
messages that the hand-written parsers produce, so that the observable
behavior of existing functions is preserved.

Backwards Compatibility
=======================

Existing functions do not need to change. The preprocessor is applied only to
functions whose authors choose to convert them. Converted functions must
produce the same results and the same exceptions as the hand-written versions
they replace, and the test suite checks this for every converted function.

The generated files are checked into the source tree, so that a build does
not require the preprocessor to be present on every platform. A check in the
build system verifies that the checked-in output matches the output the
preprocessor would produce from the current source, which prevents the two
from drifting apart.

Reference Implementation
========================

A reference implementation consists of a preprocessor written in Python, a
set of built-in converters, and a conversion of several representative
functions to the new form. The preprocessor reads the DSL blocks, validates
them, and writes the generated C code. Errors in the DSL are reported with the
line number of the offending text.

Rejected Ideas
==============

An earlier draft proposed generating the parser directly from Python
annotations on a stub file. That idea was rejected because the stub file would
need to be kept in sync with the C source, and because annotations cannot
express the cleanup code that some converters require.

Another proposal was to use a general purpose code generation framework. The
authors concluded that such a framework would be harder to learn and to debug
than a small, specific DSL, and that the extra generality was not needed for
the functions in the interpreter.
