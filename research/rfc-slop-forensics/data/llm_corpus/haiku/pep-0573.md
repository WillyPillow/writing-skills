PEP: 573
Title: Module State Access from C Extension Methods
Author: Example Author
Status: Draft
Type: Standards Track
Content-Type: text/x-rst
Created: 2016-06-30
Python-Version: 3.9

Abstract
========

This PEP proposes a way for CPython extension methods to access the context in which they are defined, in particular the state of the modules they belong to. This will allow extension methods to use direct pointer dereferences rather than calling ``PyState_FindModule`` to look up module state. This reduces or eliminates the performance cost of keeping state at module scope rather than in process-global variables. The PEP fixes one of the remaining obstacles to the adoption of :pep:`3121` and :pep:`489`. It does not resolve every concern that those PEPs raised. In particular, access to module state from slot methods, such as ``nb_add``, is not addressed.

Motivation
==========

Extension modules written in C have long kept their state in static variables. This is simple, but it has a drawback: a module that is loaded more than once, or that must be cleanly unloaded, cannot have independent state for each instance. The process-global variables tie the module to a single copy for the lifetime of the process.

:pep:`3121` introduced a way to create module objects that carry their own state, and :pep:`489` introduced multi-phase initialization, which allows a module to be created in stages and to be loaded in several interpreters. Both designs depend on storing state in the module object and retrieving it from there when needed. The difficulty is that retrieving the state from a method is not direct. A method defined in C receives its arguments and its ``self`` object, but it does not receive the module that defined it. To find the state, the method must call ``PyState_FindModule``, which searches a table of modules and adds a cost to every call.

For code that runs frequently, such as functions called in tight loops, this cost is significant. Authors who want the benefits of isolated module state are therefore tempted to keep state in globals after all, which undermines the design. The goal of this PEP is to remove the cost so that the isolated design is also the efficient one.

Rationale
=========

The essential idea is to make the defining context available to the method directly. When the method is created for a module, a pointer to the module, or to the state the module holds, is stored alongside the method. The method can then read that pointer without any lookup. This turns a search into a single pointer dereference.

The design must remain compatible with existing extension code. Methods that do not use the new facility should work exactly as before, and the storage needed for the context should be added only where the facility is used. The PEP therefore proposes a new calling convention for methods that declare the need for context, rather than changing the convention for all methods.

The approach is also limited in scope. Slot methods, which implement operators and other protocol functions, are invoked by the interpreter through a different route, and the context is not readily available there. Addressing slots would require a separate change, and it is left for future work.

Specification
=============

A method that needs its defining context declares this in its method table entry. The declaration selects a calling convention that passes the context as an additional argument. The context is a pointer to the module state, which the extension author defines as a structure. The method receives a pointer to this structure, and it can read or write fields directly.

The module object continues to own the state. Its lifetime is tied to the module, and the state is released when the module is finalized, as specified in :pep:`489`. A method that outlives its module must not use the context after finalization. The interpreter does not keep the module alive merely because a method refers to it, so authors must take care with references held across calls.

The new calling convention is available only for methods that are created by the module's initialization code. Methods added later by other means do not receive the context, and they must continue to use the lookup function if they need the state.

Error handling follows the existing conventions. A method that fails returns an error indicator, and the interpreter propagates the exception. The context does not change how exceptions are raised or caught.

Backwards Compatibility
=======================

Existing extension modules are unaffected. The new convention is opt-in, and modules that do not declare it behave exactly as they do now. The method table structure is extended in a way that preserves the layout of existing entries, so that compiled extensions built against earlier headers continue to load.

Authors who wish to adopt the new convention must recompile their extensions against a version of the interpreter that supports it. They may keep older builds for older interpreters by using a conditional compilation check on the version.

Performance Impact
==================

Measurements indicate that the lookup removed by this PEP accounts for a measurable fraction of the time spent in small methods. For methods that do very little work, the saving is a meaningful percentage of the total. For methods that perform substantial work, the saving is smaller, but it is still present. The gain is largest in code that calls many small methods in a loop, where the lookup would otherwise repeat many times.

Alternatives
============

One alternative is to continue using ``PyState_FindModule`` and to optimize the lookup itself, for instance by caching the most recent result. Caching helps in some cases but does not remove the cost in general, and it introduces its own complexity around invalidation. Another alternative is to store state in a per-method closure object. This is workable but adds an allocation for each method and complicates the method table.

The approach chosen here keeps the change small and localized. It reuses the existing module object and state structure, and it adds only the information needed to reach them directly.

Open Issues
===========

The interaction with slot methods remains open, and the PEP does not propose a solution. The question of how to handle methods that are copied to other modules or that are bound to different objects should be settled during review. The documentation for the new convention must also explain the lifetime rules clearly, since errors in this area are easy to make.
