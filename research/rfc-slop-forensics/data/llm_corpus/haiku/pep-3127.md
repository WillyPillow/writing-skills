PEP: 3127
Title: Integer Literal Support and Syntax
Author: Patrick Maupin
Status: Final
Type: Standards Track
Created: 2008
Python-Version: 3.0
Post-History: 2008

Abstract

This PEP proposes changes to the Python core to rationalize the treatment of string literal representations of integers in different radices, or bases. The changes are targeted at Python 3.0. The backward-compatible parts of the changes should also be added to Python 2.6, so that every valid Python 3.0 integer literal is also a valid Python 2.6 integer literal.

The proposal makes three changes. First, octal literals must be written with a leading "0o" or "0O" rather than a bare leading "0". Second, binary literals are supported through a leading "0b" or "0B". Third, provision is made for binary numbers in string formatting.

Motivation

Python has long accepted integer literals written in decimal, hexadecimal, and octal notation. Decimal and hexadecimal are unambiguous: decimal literals have no prefix, and hexadecimal literals begin with "0x". Octal literals, however, begin with a bare zero followed by digits. This choice is confusing in practice. A number such as 010 looks like it means ten, but in Python 2 it means eight. Programmers who are not aware of the rule can introduce subtle bugs when they write numbers that look like decimal values, such as zero-padded file permissions or dates.

The leading zero also interacts poorly with the rest of the language. A literal that begins with zero and contains a digit greater than seven is a syntax error, while a literal that contains only digits zero through seven is a valid octal number. This means that a small change to a number can turn valid code into an error without any obvious reason. The rule is difficult to explain to newcomers and is easy to forget for experienced programmers.

Binary notation is also a common need. Programmers who work with bit flags, hardware registers, or network protocols often write numbers in binary, and the language provided no direct syntax for them. The available alternatives were to write hexadecimal digits, which requires a mental conversion, or to use the built-in conversion function on a string. The proposal adds a direct literal form.

Finally, the string formatting mini-language does not provide a way to format integers in binary, although it provides a way to format them in hexadecimal and octal. Adding binary formatting makes the three radices consistent across the language.

Specification

Under the proposal, an integer literal may begin with one of the following prefixes, which are case-insensitive in the second character:

- "0x" or "0X" for hexadecimal, with digits zero through nine and letters a through f
- "0o" or "0O" for octal, with digits zero through seven
- "0b" or "0B" for binary, with digits zero and one

A literal with no prefix is a decimal number, except that the single digit zero is also written without a prefix. A sequence of digits beginning with zero and containing more than one digit is not a valid integer literal in Python 3. Such a sequence was previously octal in Python 2, and the proposal requires that it be written with the "0o" prefix instead.

Underscores are not part of this proposal, and the specification does not allow them within literals.

The string formatting mini-language gains a binary presentation type, written with the letter "b" in the same position as the existing letters for hexadecimal and octal. Format specifications may also request the prefix, in which case the output includes "0b" at the front of the digits, in the same way the existing presentation types include "0x" and "0o".

Transition

The change to octal literals is incompatible with Python 2 code that uses bare leading zeros. The proposal therefore recommends that the Python 2.6 release accept the "0o" form in addition to the old form, and that it issue a warning when the old form is used. This allows programmers to update their code before the Python 3.0 release removes the old syntax.

The binary literal form is new and therefore does not conflict with existing code in Python 2.6. Adding it to Python 2.6 allows code written for Python 3.0 to run on the earlier release without modification, as long as it does not depend on other Python 3 changes.

The string formatting change is also additive. Existing format specifications continue to behave as they do today, and the new presentation type is accepted only when explicitly requested.

Rationale

The choice of "0o" for octal was made because it is short, it is easy to type, and it does not collide with any existing meaning in the language. The letter "o" is also used in the same position as "x" and "b", which makes the three prefixes visually consistent. The authors considered several other forms, but they judged that consistency with hexadecimal was more important than minimizing the number of characters.

The choice of "0b" for binary follows directly from the same pattern. The letter "b" is the natural choice for binary, and it does not conflict with any existing syntax in the language.

The authors considered keeping the leading-zero octal form in Python 3 and simply adding the new prefixes alongside it. This was rejected because it would leave the confusing rule in place and would make the language harder to teach. Removing it is a clear break, but the transition plan makes the break manageable.

Backward compatibility

Most Python 2 code that uses hexadecimal literals is unaffected. Code that uses octal literals with a leading zero will fail under Python 3, and the proposal expects that many such programs will need small edits. The authors note that tools can automate most of these edits, and that the number of affected programs is expected to be small.

Code that uses the string formatting mini-language is unaffected unless it relies on undefined behavior, which the specification does not allow.

Reference implementation

A reference implementation was written in the tokenizer and in the integer conversion routines of the interpreter. It accepts the new prefixes, rejects the old octal form in the Python 3 branch, and emits a warning for the old form in the Python 2.6 branch. Tests were added to confirm that the new forms produce the same values as the existing forms they replace.

Discussion

Commentators raised concerns about the removal of the old octal syntax. Some programmers pointed out that the old form is familiar to users of C and of Unix tools, and that removing it would cause friction for those users. The authors responded that the "0o" form is also familiar in those communities and that the benefit of removing the ambiguous form outweighs the cost.

Other commentators asked whether underscores should be allowed in literals to make long binary numbers easier to read. The authors agreed that this would be useful but decided to defer it to a separate proposal, so that the present change could be considered on its own merits.

A third group asked whether the binary format type should accept the uppercase letter as well. The authors answered that the format type should be case-consistent with the existing types, and the proposal follows that practice.

Conclusion

The proposal rationalizes the treatment of integer literals in different radices. It replaces the confusing leading-zero octal form with an explicit "0o" prefix, adds a binary literal form with "0b", and adds binary formatting to the string formatting mini-language. The changes are introduced in Python 2.6 where they are backward-compatible, and the remaining changes take effect in Python 3.0. The authors recommend the changes as a clearer and more consistent foundation for numeric literals in the language.
