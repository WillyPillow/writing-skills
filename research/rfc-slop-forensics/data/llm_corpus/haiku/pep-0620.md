# PEP 620: Hide implementation details from the C API

| Field | Value |
|---|---|
| PEP | 620 |
| Title | Hide implementation details from the C API |
| Status | Draft |
| Type | Standards Track |
| Created | 2020 |
| Python-Version | 3.11 |

## Abstract

This PEP proposes a set of changes to the C API of CPython that remove access to implementation details of the interpreter. Public C API users would no longer be able to read or write fields of core object structures directly; they would instead call functions or macros that the interpreter provides. The changes are incompatible with some existing C extensions, so the PEP also defines a process for shrinking the number of extensions that break, and a schedule that paces the work across several releases.

Once most implementation details are hidden, the internals of CPython can change without being constrained by the layout that extension modules depend on. This makes it practical to add new features to the object model and to explore optimizations larger than local micro-optimizations, such as tagged pointers or alternative object headers.

## Motivation

The C API of CPython exposes the layout of its core structures. A type such as `PyObject` has a reference count and a type pointer that extension code can read directly, and many other structures such as `PyListObject`, `PyTupleObject` and `PyFrameObject` have fields that are reachable through macros. This has been convenient for authors of extensions, because direct field access avoids a function call and allows code to be written in a familiar style.

The cost is that the layout becomes part of the interface. Every change to a field, to the size of a structure, or to the meaning of a flag can break compiled extensions that were built against an earlier version. Over time the CPython core has accumulated constraints that come from this promise rather than from any real need of the interpreter. Changing how reference counts are stored, adding a field to a frequently allocated object, or replacing a list representation all require careful thought about binary compatibility.

Experience from other projects shows that the situation can be improved. When the public interface describes what an object can do rather than how it is stored, the implementation can change freely. The purpose of this PEP is to move the C API in that direction without making extension authors rewrite their code all at once.

## Rationale

The guiding idea is that the stable part of the C API should be the set of operations, not the set of fields. Where an extension currently reads `Py_SIZE(op)` or `PyTuple_GET_ITEM(op, i)` directly, the same information can be obtained through a function such as `PyTuple_GetItem`, which the interpreter may implement in any way it likes. Functions carry a cost, but the cost is usually small compared with the work done around a call into the interpreter, and the interpreter can often inline the common cases internally.

The PEP does not propose to remove every macro. Some macros are conveniences that expand to function calls and therefore have no layout dependency. Others expose fields and must become opaque. The distinction matters, because a change that merely renames a macro would be harmless but unhelpful, whereas a change that removes field access is the one that enables future work.

A second rationale concerns the ability to experiment. Several proposals to improve CPython, including changes to reference counting and to the representation of small integers, have been discussed for years and rejected or deferred because they would break too many extensions at once. An incremental approach lets each step be judged on its own merits and lets the interpreter evolve while the ecosystem adjusts.

## Specification

The changes are grouped into phases. Each phase makes one class of implementation detail private and provides a replacement for the parts that extensions need.

The first phase covers structure fields that are accessed in hot paths and that have obvious accessor functions. For these, the PEP requires that the field be removed from the public header, that the accessor be added where it is missing, and that the macro form be kept only if it expands to a call to a public function. Extensions compiled against the old header will fail to compile, which makes the breakage visible at build time rather than as a silent memory corruption at run time.

The second phase covers fields that have no direct replacement. For these the interpreter provides a function that performs the most common operation, and the PEP documents the set of operations that remain supported. Code that needs more than this can use the limited API, or it can ask the core developers for a new function through the normal review process.

The third phase deals with internal headers and the way they are installed. Headers that are meant only for the interpreter are moved to a directory that is not on the default include path. Extensions that include them explicitly will need to change, and a deprecation warning is issued during the transition period.

Throughout the phases, the PEP requires that every removal be accompanied by an entry in the changelog and by a note in the documentation that explains the replacement. Where a removal affects a widely used project, the core developers are expected to contact the maintainers before the change lands.

## Process to reduce the number of broken C extensions

The process is driven by measurement rather than by estimates. Before each phase, the core developers compile a corpus of popular C extensions against the new headers and record which ones fail and why. Projects that fail for a reason that has an easy fix are contacted with a patch or a description of the fix. Projects that rely on a field with no replacement are contacted early, so that the replacement can be designed before the field is removed.

The rhythm of the changes follows from this measurement. A phase is not started until the failures from the previous phase have been reduced to an acceptable number, and a phase is not completed until the documentation and the migration guide are in place. In practice this means that a single change may take one release to prepare, one release to land, and another release for the transition period, which is why the work is expected to span several Python versions.

The process also includes a deprecation period in which the old names continue to work but emit warnings when built with a special flag. This gives authors time to update their code without forcing a release of the extension at the moment the interpreter changes.

## Backwards Compatibility

This PEP is deliberately incompatible with some existing C extensions, and it does not attempt to avoid all breakage. The goal is to make the breakage predictable and to limit it to a known set of fields and functions. Extensions that use only documented functions and the limited API are expected to continue to work without modification.

The effect on performance is expected to be small for most code. Some extensions that depend on direct field access in tight loops may see a slowdown, and the core developers will look for opportunities to offset this by providing better functions or by adding internal inlining. Benchmarks are run before each phase to detect regressions that the process has not anticipated.

## Security Implications

Hiding internal fields does not by itself improve or weaken security, but it reduces the number of ways in which an extension can corrupt interpreter state by writing to a field it should not touch. Accessor functions can validate their arguments, and an opaque structure is harder to misuse. The PEP does not claim these as its main benefit.

## Implementation

The implementation is tracked as a series of changes to the header files and to the test suite. The test suite includes a set of extensions that exercise the public API, and it is run against each phase. Changes that remove a field are required to update the tests so that they use the replacement function, which means the test suite serves as a living example of the migration.

## Open Issues

Several questions remain open. The most important is how to treat extensions that are maintained only in binary form, where the author cannot rebuild the code. The PEP suggests that such extensions should be expected to stop working when the field they depend on is removed, but it acknowledges that this is a real cost. Another open question is the exact list of functions that will be added in the second phase, which depends on the results of the measurements described above.
