# Summary

This RFC proposes the *2017 Rust Roadmap*, written in accordance with RFC 1728. The goal of the roadmap is to set out a vision for where the Rust project should be in a year's time, and to describe the concrete steps that will move it there.

The focus for 2017 is improving Rust's productivity while keeping its emphasis on fast, reliable code. The roadmap sets out a small number of outcomes that the project should achieve by the end of the year, and it explains why each one matters.

By the end of 2017, Rust should:

* have a lower learning curve,
* have a pleasant edit-compile-debug cycle,
* provide a solid, but basic, IDE experience,
* provide easy access to high quality crates,
* be well equipped for writing robust, high-scale servers,
* have 1.0-level crates for essential tasks,
* integrate easily into large build systems, and
* have a community that provides mentoring at all levels.

# Motivation

Rust has reached a stage where its core language is stable and its compiler is reliable. The next challenge is to make the language pleasant to use for a much wider group of programmers. Many people who would benefit from Rust's guarantees find the language hard to approach, and many who try it find the tooling slow or unhelpful.

A roadmap gives the project a shared picture of the year ahead. It helps contributors decide where to spend their time, and it helps the wider community understand what to expect. Without one, work tends to follow the interests of whoever is most active, and important gaps can remain open for years.

The roadmap is also a way to be honest about what Rust is not yet good at. Some of the outcomes listed here describe areas where the language or its libraries fall short today. Naming them makes it easier to plan the work and to measure progress at the end of the year.

# Guide-level explanation

The roadmap is organized around the outcomes listed in the summary. Each outcome has a short statement, a description of why it matters, and a list of the work that is expected to achieve it. The work is described at the level of projects and themes, not individual pull requests, so that the roadmap remains useful even when the details change during the year.

A reader who is new to Rust can use the roadmap to see where the language is headed. A reader who is already experienced can use it to find areas where help is needed. In both cases, the roadmap is a statement of priorities rather than a promise that every item will be completed on a fixed schedule.

Progress is reviewed at intervals during the year. The review asks whether each outcome is on track, whether the work described is still the right work, and whether any new information suggests a change of direction. The roadmap is updated when the answer to any of these questions requires it.

# Reference-level explanation

Each outcome is described in terms of concrete goals. For the learning curve, the goals include improving the error messages produced by the compiler, writing better introductory material, and making common patterns easier to express. For the edit-compile-debug cycle, the goals include reducing compile times for typical projects, improving incremental compilation, and making debugging information more reliable.

For the IDE experience, the goals include a language server that supports the common features programmers expect, such as completion, navigation, and inline diagnostics. The server should be built on the compiler's own analysis so that its results agree with the compiler. A basic experience is the target for this year, and more advanced features are left to later years.

For access to high quality crates, the goals include improving the process for finding and evaluating crates, encouraging authors to document their work, and supporting a set of crates that the project itself recommends for common tasks.

For servers, the goals include stable asynchronous input and output, a shared vocabulary of traits for network code, and good examples of how to structure a service. The goals for 1.0-level crates list the libraries that the project believes are essential, and they describe what it would mean for each one to be considered stable.

For build systems, the goals include making Cargo work well inside larger systems that have their own build tools, and making it easier to vendor dependencies and to control how they are built.

For mentoring, the goals include making it easier for new contributors to find work that suits them, providing clear documentation for the compiler and the standard library, and recognizing the people who help others.

# Drawbacks

A roadmap that lists many outcomes risks spreading the effort too thin. The project must keep the list short enough that each item receives real attention, and it must be willing to drop items that are not progressing. The number of outcomes in this proposal is deliberately modest, but the list is still long.

A roadmap can also set expectations that the project cannot meet. Some outcomes depend on work by people outside the core team, and their progress cannot be fully controlled. The roadmap must say clearly where it depends on others.

Finally, a roadmap is a commitment of attention. Time spent on the roadmap is time not spent on other things, and some useful work will fall outside the list. This is an acceptable cost, because the value of a shared direction is greater than the value of the work that it displaces.

# Rationale and alternatives

The main alternative is to have no roadmap and to rely on the judgement of individual contributors. This has worked for a long time, but it has produced uneven results, and the project has found it hard to coordinate work across teams.

A second alternative is a roadmap with a much longer horizon, covering several years. This would give more room for large projects, but it would also be harder to revise and would be less useful to contributors who need guidance for the next few months. A one-year horizon is a compromise that matches the review cycle of the project.

A third alternative is a roadmap that lists only technical goals, without describing the community outcomes. This would be easier to measure, but it would miss the goal of making Rust accessible to more people. The proposal includes both kinds of outcome because they depend on each other.

# Prior art

Other open source projects have published roadmaps in a variety of forms. Some publish a single list of priorities, and others publish a detailed plan with milestones. The approach here is closer to the first group, with enough description to explain each priority and without a schedule of individual tasks.

The project's own earlier process, described in RFC 1728, sets the framework within which this roadmap is written. The present document follows that process closely, and it is intended to be the first in a series of annual roadmaps.

# Unresolved questions

The exact list of 1.0-level crates is not settled. The list in this proposal is a starting point, and the project should agree on it with the maintainers of the crates concerned.

The metrics for measuring progress on the mentoring outcome are not yet defined. The authors suggest counting the number of contributors who make a first contribution, but this measure may not capture the quality of the experience.

# Future possibilities

The roadmap for 2018 can build on the outcomes of this year, and it can take up the areas that this year's work leaves unfinished. Some of the larger goals, such as a complete IDE experience, will require more than one year, and they should be planned as a sequence.

The process for writing roadmaps could itself be improved, for example by asking the community for input at an earlier stage and by publishing progress reports at regular intervals. These improvements can be considered in future roadmaps.
