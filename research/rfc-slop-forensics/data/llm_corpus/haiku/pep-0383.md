# PEP 383: Non-decodable Bytes in System Character Interfaces

| Field | Value |
|---|---|
| PEP | 383 |
| Title | Non-decodable Bytes in System Character Interfaces |
| Status | Final |
| Type | Standards Track |
| Created | 2009 |
| Python-Version | 3.1 |

## Abstract

On POSIX systems, file names, environment variables and command line arguments are defined as sequences of character data, but the C interfaces that carry them allow any sequence of bytes, whether or not those bytes form valid text in the locale's encoding. This PEP proposes a way for Python to represent such irregular bytes in its string type, so that the original byte sequence can be recovered exactly. The mechanism maps each undecodable byte to a code point in a reserved range, and it applies the mapping only when the interpreter converts system data to and from strings.

## Motivation

Python 3 changed the representation of text so that a string is a sequence of Unicode code points. Interfaces that accept or return file names and other system data must therefore decode bytes into code points, and must encode code points back into bytes. On POSIX, this decoding uses the locale's encoding. When the bytes do not decode correctly, the interpreter must either fail or choose some other behavior.

Failing is unsatisfactory. A directory that contains a file whose name is not valid in the current encoding cannot be listed completely, because the listing function raises an error when it reaches the file. A program that reads its command line arguments may refuse to start simply because one argument is not valid text. These failures are unexpected to users, who have no way to fix the underlying data without first finding it.

Silently replacing invalid bytes with a replacement character is also unsatisfactory, because it loses information. Two different file names may become the same string, and the original name cannot be used to open the file again. A program that depends on round-tripping file names would then fail in ways that are hard to diagnose.

The problem is therefore to find a representation that preserves the bytes, is compatible with the string type, and does not introduce a new failure mode.

## Rationale

The proposal is based on an error handler that the codec machinery already supports. When decoding fails, the handler can choose what to put in the result. The handler proposed here, which this PEP calls the surrogate escape handler, replaces each byte that cannot be decoded with a code point from the low surrogate range, specifically a value that is computed by adding a fixed offset to the byte. Surrogate code points are not valid in a Unicode string that represents text, so none of the code points used for escaping will occur in ordinary text that was decoded correctly.

Because the escape values are distinct from valid characters, the mapping is reversible. When the string is encoded again with the same handler, each escaped code point is turned back into the original byte, and the bytes are reproduced exactly. A file name that was read with escaped bytes can therefore be passed back to the operating system to open the same file.

The choice of surrogates has a second advantage. Ordinary text processing functions treat them as characters that are unusual but valid, so string operations such as slicing and searching continue to work. The escape codes do not need special treatment by most of the code that handles strings.

## Specification

The surrogate escape error handler is defined as follows. When an error handler is asked to decode a sequence of bytes that is invalid in the codec, it examines each byte in the invalid range. For each byte in the range 0x80 through 0xFF, the handler produces a code point in the range U+DC80 through U+DCFF, computed by adding 0xDC00 to the byte value. Bytes that are part of a valid sequence are decoded normally.

When the same handler is asked to encode a string, it examines each code point. Code points in the range U+DC80 through U+DCFF are converted back to the byte that they represent. Other code points are encoded in the normal way for the codec. If a code point in the escape range would otherwise be unencodable, the handler reports an error, because the string was not produced by decoding.

The handler is used by default for the conversion of file names, environment variables and command line arguments on POSIX systems. It is not used for ordinary text conversions, where the traditional strict behavior remains the default. Programs that want a different behavior may choose another error handler for their own conversions.

The PEP does not specify the exact set of codecs to which the handler applies. The requirement is that any codec that can produce an invalid byte sequence must support the handler, and that the handler's output must be reversible for every such sequence.

## Specification of the interfaces

The functions that return file names, such as those that list a directory, use the handler when they produce strings. The functions that accept file names use the handler when they convert strings back to bytes. Environment variables are decoded when the interpreter starts and when they are read, and they are encoded when they are written. Command line arguments are decoded at startup.

On systems where the file system encoding is not UTF-8, the handler is applied in the same way, and the escape range is interpreted relative to the bytes that the file system stores. The PEP does not require that the escape values have any meaning to the file system itself.

## Backwards Compatibility

Programs that previously received an exception when they encountered an undecodable name will now receive a string instead. Code that depends on the exception being raised may need to be changed. Such code is rare, and the change is in the direction of allowing programs to proceed in the presence of unusual data.

Code that writes escaped strings to a text stream encoded in a strict codec will fail when it encounters an escape code point, because the stream cannot encode it. This is intentional, because it prevents the escape code points from leaking into output that is meant to be text.

The representation does not change the behavior of any string that contains only valid text, so the vast majority of programs are not affected.

## Security Implications

Escape code points can appear in file names that users have chosen, and they can be confused with other characters if they are printed. Programs that display file names should be aware that an escaped name may not look like the name that the user expects. The PEP does not attempt to solve this presentation problem, which is the responsibility of the application.

Because the mapping is reversible, the escaped string can be used to access exactly the file that the operating system stores. This avoids the risk of opening a different file because of lossy conversion, which is the more serious concern.

## Reference Implementation

The reference implementation adds the error handler to the codec registry, modifies the system interfaces to use it by default on POSIX, and adds tests that check round trips for every byte value in every supported encoding. The tests include file system operations that create files with invalid names, list them, and remove them.

## Open Issues

The PEP leaves open the question of whether the handler should be the default for all text streams that read from the operating system, or only for the interfaces that carry file names and environment data. The current proposal limits the handler to system interfaces, because changing the default for all streams would affect many more programs.

A second open question concerns Windows, where file names are stored as sequences of 16-bit code units and the problem described here does not arise in the same form. The PEP does not propose any change for Windows at this time.
