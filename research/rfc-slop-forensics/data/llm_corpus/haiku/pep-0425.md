# PEP 425: Compatibility Tags for Built Distributions

**Type:** Standards Track
**Status:** Draft
**Topic:** Packaging

## Abstract

This PEP defines a tagging scheme that states which versions of Python a built distribution supports. A tag set has three parts: the Python implementation and language version, the application binary interface (ABI), and the platform. A built distribution declares one or more combinations of these parts that it can run on, and an installer compares those combinations with the interpreter it is running under. The tags are deliberately short because they appear inside file names, where long names are awkward to read and to type.

## Motivation

A built distribution is a package whose files have already been compiled for a particular target. Compiled extensions depend on the interpreter that built them, on the ABI that interpreter exposes, and on the operating system and processor. Installing a built distribution on an incompatible target can produce a crash rather than a clean error, which is why installers need a reliable way to decide whether a file is suitable before they unpack it.

Before this PEP, the decision was made by convention and by inspecting the name of the package or by trying to import it. Neither approach was dependable. Naming conventions varied between projects and platforms, and a failed import happens after the files have been copied into the environment. The result was a practice of publishing source distributions and asking users to compile them, which imposes the cost of a compiler and of build dependencies on every installation.

A common scheme lets a publisher produce one file for each target and lets the installer pick the right one without guessing. It also allows a single file to declare that it works with several targets, which is useful for pure Python code that runs unchanged on many interpreters and for compiled code that is compatible across a range of versions.

## Specification

A tag is a string made of three components separated by hyphens: the implementation and version, the ABI, and the platform. A complete tag is written as `python-abi-platform`, where each component follows the rules below.

The implementation and version component consists of a short code for the implementation followed by a version number. The code `py` denotes the reference implementation, and other implementations use their own short codes. The version is written with the major and minor numbers joined without a separator, so that Python 3.4 is written `34`. A component may be a range of versions when the code is compatible with several releases of the same major version.

The ABI component names the binary interface the code was built against. A value of `none` means that the file contains no compiled code that depends on the interpreter's binary interface, as is the case for pure Python packages. Other values name a specific interface, and an installer must treat them as matching only when they equal the ABI of the running interpreter.

The platform component names the operating system and processor architecture. It is derived from the platform identifier that the interpreter reports, with punctuation replaced by underscores so that it can appear safely in a file name. A value of `any` indicates that the file does not depend on the platform.

A built distribution may carry several tags, separated by periods within a single component. The file name records every combination it supports. The installer considers the file compatible if at least one of its combinations matches the running interpreter.

## Ordering

When an index offers several compatible files for the same version of a project, the installer must choose one. The PEP defines a priority ordering over tags so that the most specific file is preferred. A file built for a particular platform and ABI ranks above one that declares no ABI, and a file for the current interpreter version ranks above one for an older version. The ordering is designed so that the file most likely to run fastest and most correctly is the one selected.

The ordering is a recommendation to installers rather than a requirement, but it is intended to be consistent across tools so that users see the same choice regardless of which installer they run.

## Filename Format

The file name of a built distribution combines the project name, the version and the tags. The tags appear last, separated from the rest of the name by hyphens. Because the components of a tag may contain underscores, the name is parsed from the right, so that the platform is read first and the ABI and implementation afterwards. Project names and versions may not contain hyphens in the positions that would confuse this parsing, and the normalization rules of the packaging specifications apply.

## Rationale

The tags are short by design. A file name is read by people in directory listings and in error messages, and it is copied into logs and command lines. A long tag would make the name difficult to read and would increase the chance of truncation in systems with limits on name length.

Keeping the three components separate reflects three independent sources of incompatibility. A publisher may build against a new ABI without changing the language version, and a file may be portable across platforms while depending on the interpreter. Treating the parts separately lets each be described precisely.

The use of `none` and `any` as explicit values is intended to make the common case of pure Python code easy to express. Such a file works everywhere and should not need to list every target.

## Backwards Compatibility

This scheme adds information to file names that earlier tools did not produce. Older installers will not recognize the tags and will fall back to their previous behavior, which typically means ignoring the file or treating it as a source distribution. Publishers who want their files to be used by older tools should continue to publish source distributions alongside built ones.

Existing built distributions that use earlier naming conventions remain installable by tools that continue to support them. The PEP does not require their removal.

## Security Implications

Tags are a matter of compatibility, not of trust. An installer that matches a tag has not verified who built a file or that it is free from malicious content. Verification must be handled separately by the index and by the installer's trust policy. The tags reduce the risk of accidental misuse, because a file that claims to be for another target is not selected, but they do not prevent a deliberately mislabeled file from being offered.

## Reference Implementation

A reference implementation of tag generation and matching has been written. It determines the tags supported by the running interpreter in the order defined above, and it compares them with the tags in a file name. The implementation has tests for the common interpreters and platforms, and it has been used to check the ordering against a corpus of published files.

## Open Questions

The list of implementation codes must be maintained, and the process for adding a new code needs to be settled. The treatment of platforms that report unusual identifiers is not fully specified, and the reference implementation falls back to a conservative default in that case. The ranges of versions that a single tag may express should be reviewed once the first implementations of this scheme have been used in practice.
