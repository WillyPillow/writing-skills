Title: Add a __getdescriptor__ method to metaclasses

Abstract
========

Attribute lookup on classes currently works by walking the method resolution order (MRO) and inspecting each class's ``__dict__``. The lookup is implemented in C in two places: ``object.__getattribute__`` and ``super.__getattribute__``. This PEP proposes an optional ``__getdescriptor__`` method that a metaclass may define to take over the per-class part of that search. The default behavior is unchanged, but a metaclass that needs different rules for finding attributes on its instances' classes gains a single, well-defined hook.

Motivation
==========

The MRO walk is simple and fast, but it hard-codes the assumption that a class's attributes live in its ``__dict__``. Several important libraries want to break that assumption. Proxy classes may generate attributes on demand. Classes that mirror a remote schema may want to expose fields that do not exist until first access. Frameworks that implement lazy class construction currently resort to filling the dictionary eagerly, which costs memory and makes the class body harder to reason about.

Another motivation is ``super``. The ``super`` object performs its own MRO walk, starting after a given class. Because it reads ``__dict__`` directly, it cannot see descriptors that a metaclass would like to provide. Making the two lookups consistent requires that both go through the same hook.

The change proposed here is deliberately narrow. It does not alter how instances find attributes, only how classes in the MRO are consulted. It also does not change the data model for ordinary classes, where the default behavior matches the present one exactly.

Specification
=============

When ``_PyType_Lookup`` walks the MRO for a name, it currently checks each class's dictionary in turn. Under this proposal, the loop asks each class for the name through its metaclass. The loop can be written in pseudocode as follows::

    def lookup(mro_list, name):
        for cls in mro_list:
            try:
                return type(cls).__getdescriptor__(cls, name)
            except AttributeError:
                pass
        return NotFound

The same change applies to ``super.__getattribute__``, which uses the same loop starting after the bound class.

The default implementation is provided by ``type`` and reproduces the existing behavior::

    class type:
        def __getdescriptor__(cls, name):
            try:
                return cls.__dict__[name]
            except KeyError:
                raise AttributeError(name) from None

A metaclass may override ``__getdescriptor__`` to return any object it chooses. The object is then treated as if it had been found in the class dictionary, so the usual descriptor protocol applies. If the override raises ``AttributeError``, the search continues with the next class in the MRO.

Lookup on the metaclass itself is not affected. Attributes of the metaclass continue to be found through the metaclass's own MRO, which is unchanged by this PEP.

Performance
-----------

The current loop is a single dictionary probe per class. Under this proposal, the default ``__getdescriptor__`` adds a Python-level call for each class unless the implementation recognizes the default and takes a fast path. The reference implementation therefore checks whether the metaclass uses the default method and, if it does, performs the dictionary probe directly in C. With this optimization, the default case costs the same as before, and only classes that override the method pay the additional cost.

Backwards Compatibility
=======================

Existing code is unaffected. Every metaclass in the standard library and in common third-party packages inherits the default method from ``type``, so their lookups follow the old path. The only observable change occurs in a class that defines its own ``__getdescriptor__``, and such a method has no meaning today, so it cannot conflict with existing behavior.

One subtle point concerns code that inspects ``__dict__`` directly and expects it to match what attribute access returns. That code remains correct for every class that does not override the method. For classes that do override it, the discrepancy is the intended purpose of the feature, and documentation will say so.

Security Implications
=====================

Allowing a metaclass to synthesize attributes does not grant any new capability, because a metaclass already controls class creation and may already install descriptors. The hook does, however, make it easier to write code that hides attributes from ``dir()`` and ``vars()`` while still making them reachable. Tools that audit classes should be aware that ``__dict__`` no longer tells the whole story for such classes.

Rejected Alternatives
=====================

A proposal to add a new keyword argument to ``class`` statements was considered and rejected, because it would require parser changes and would not help classes created by existing metaclasses. A proposal to override ``__getattribute__`` on the metaclass was also considered. It covers the same use cases but applies to every attribute access on the class, including those that never touch the MRO, and it is slower for the common case. The narrower hook here places the extension point exactly where the lookup occurs.

Reference Implementation
========================

A reference implementation adds the ``__getdescriptor__`` slot to ``PyTypeObject``, fills it with the default C function, and modifies ``_PyType_Lookup`` and ``super_getattro`` to call the slot when the metaclass has overridden it. The patch includes tests that exercise the default behavior, an overriding metaclass, and the interaction with ``super``.

Open Issues
===========

It is not yet decided whether ``__getdescriptor__`` should be consulted for the class itself before the MRO walk begins, or only for the classes in the MRO. The current draft chooses the second option to keep the change minimal. A future revision may revisit this question if real use cases require it.
