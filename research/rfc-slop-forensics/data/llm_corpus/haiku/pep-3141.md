Title: A Type Hierarchy for Numbers

Abstract
========

This proposal defines a hierarchy of abstract base classes for number-like types. The hierarchy places ``Number`` at the top, with ``Complex``, ``Real``, ``Rational``, and ``Integral`` as successively more specific refinements. The ordering can be written as ``Number :> Complex :> Real :> Rational :> Integral``, where ``A :> B`` means that A is a supertype of B. The classes are built on the abstract base class machinery of PEP 3119, so they can be checked with ``isinstance`` and extended by user code. The design is modeled on the numeric tower found in the Scheme family of languages, adapted to Python's object model.

Motivation
==========

Python's built-in numeric types, ``int``, ``float``, and ``complex``, were not designed as parts of a single system. Each was added at a different time, and the relationships among them are implicit. A program that wants to accept any real number must either list the concrete types or rely on duck typing. Neither approach expresses the intent clearly, and neither helps a library that wants to offer a new numeric type.

The standard library already contains some numeric types that do not fit neatly into the built-in set. The ``fractions`` module provides exact rational numbers, and the ``decimal`` module provides decimal floating point. Each of them behaves like a number, but there is no shared way to ask whether an object belongs to a particular category. A function that computes a square root, for instance, may want to know whether its argument is real, and today it has no reliable test for that.

An abstract hierarchy addresses these problems. It gives each category a name, specifies the operations that a member must support, and allows a library to register a new type as a member of a category without subclassing. The result is that numeric code can be written against the categories rather than the concrete types, which makes it more general and easier to read.

Specification
=============

The hierarchy has five levels. The top level, ``Number``, has no operations. It exists only to mark the class of numeric values. The second level, ``Complex``, adds the operations that make sense for complex values: addition, subtraction, multiplication, division, negation, absolute value, equality, and conversion to ``complex``. The third level, ``Real``, adds the operations that depend on order: comparison, floor and ceiling, truncation, rounding, and conversion to ``float``. The fourth level, ``Rational``, adds the numerator and denominator properties. The fifth level, ``Integral``, adds integer division, the modulo operation, bitwise operations, and conversion to ``int``.

Each class is an abstract base class, and the concrete types of the standard library are registered with the appropriate class. ``int`` is registered as an ``Integral``, ``fractions.Fraction`` as a ``Rational``, ``float`` as a ``Real``, and ``complex`` as a ``Complex``. Registration does not change the behavior of these types. It only makes them answer positively to ``isinstance`` tests against the abstract classes.

Abstract methods are declared for each operation that a subclass must provide. Some methods have default implementations expressed in terms of others. For example, subtraction may be defined as addition of a negated value, so that a minimal implementation needs to supply only a few operations.

Rationale
---------

The ordering follows the mathematical inclusion of the sets involved. Every integer is rational, every rational is real, and every real is complex. The hierarchy therefore reflects the containment that a mathematician would expect. It also reflects the operations that each level can support. A real number has an order, and a complex number does not, so comparison belongs at the real level and above it only where it makes sense.

Some readers have asked whether floating-point numbers belong in the hierarchy at all, since they are not exact. The draft places ``float`` under ``Real`` because it is the standard representation of real numbers in Python, and because excluding it would make the hierarchy less useful. The documentation will note the inexactness and will recommend the exact types where precision matters.

Backwards Compatibility
=======================

The hierarchy is additive. Existing code that uses the concrete types continues to work without change. The only new behavior is that ``isinstance`` checks against the abstract classes succeed for the standard types, and code that did not previously perform such checks is unaffected.

There is one possible concern. Code that previously tested for a specific type may now find that a more general test also succeeds, and it may behave differently if it assumed the narrower type. Such code is rare, and the effect is confined to the affected checks.

Implementation Notes
====================

The implementation lives in the ``numbers`` module. It defines the five classes, registers the built-in types, and provides the default method implementations. The module imports only the abstract base class machinery, so importing it has little cost. The registrations are performed at import time, which means that a program that never imports the module will not see the new classes.

Alternatives
============

One alternative was to define the hierarchy as a set of protocols, checked structurally rather than by inheritance. This approach was considered attractive for its flexibility, but it would not give users a single place to ask whether an object is real. The abstract base class approach was chosen because it fits the machinery already accepted in PEP 3119.

Another alternative was to omit the ``Rational`` level and place ``Integral`` directly under ``Real``. This would simplify the hierarchy, but it would leave no category for exact fractions, and the ``fractions`` module would have no natural home in the tower. The inclusion of the level reflects the importance of exact rational arithmetic in numerical code.

Open Issues
===========

The exact set of operations required at each level remains open to revision. Contributors have suggested additional methods, such as conjugation at the complex level and the floor division operator at the real level. The draft lists the minimum that a faithful implementation requires, and it leaves richer protocols to later work.
