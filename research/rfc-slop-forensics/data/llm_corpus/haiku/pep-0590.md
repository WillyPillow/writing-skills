PEP: 590
Title: Vectorcall: a fast calling protocol for CPython
Author: Mark Shannon, Jeroen Demeyer
Status: Final
Type: Standards Track
Created: 2018-05-01
Python-Version: 3.8
Post-History: 2018-05-02

Abstract

This PEP introduces a new C API for optimizing calls to callable objects in CPython. It defines a new calling protocol, called "vectorcall", and a corresponding calling convention. The protocol builds on the "fastcall" convention that CPython already uses internally for built-in functions and methods. Extension types written in C may adopt the protocol, and the interpreter will use it when calling those objects.

Most of the new API is private in CPython 3.8. The intention is to finalize its semantics and make it public in Python 3.9, once it has been exercised in practice. This PEP concerns only the Python/C API. It does not change the Python language, the bytecode, or the standard library.

Motivation

Calling a function in CPython has historically required the arguments to be packed into a tuple, and keyword arguments into a dictionary, before the callee unpacks them again. For built-in functions that accept positional arguments only, this packing is pure overhead. Each call allocates a tuple, copies references into it, and then the callee reads them back out.

The fastcall convention removed the tuple for many internal functions by passing a C array of arguments and a count. Keyword arguments were passed as a second array with a tuple of names. This reduced allocation for many common calls, but the convention was not available to extension types, and it was not formalized as a protocol that an object could advertise.

Vectorcall generalizes this approach. It defines a per-object function pointer that accepts arguments in the fastcall form, and it defines how the interpreter discovers that pointer. An object that implements vectorcall can be called without the tuple and dictionary, whether the caller is the interpreter itself or another extension.

The benefit is measurable for functions called frequently in tight loops. Calls to built-in functions and to methods defined in C become faster, and the saving is largest when the call has only positional arguments.

Specification

A type that supports vectorcall sets the Py_TPFLAGS_HAVE_VECTORCALL flag in its type object. Instances of such a type store a pointer to a vectorcall function at a fixed offset given by the type's tp_vectorcall_offset field. The stored pointer has the signature:

    PyObject *vectorcallfunc(PyObject *callable, PyObject *const *args,
                             size_t nargsf, PyObject *kwnames);

The args array holds positional arguments followed by the values of keyword arguments. The count of positional arguments is stored in nargsf, and a flag bit indicates that the caller has allowed the callee to modify the array temporarily. The kwnames argument is a tuple of keyword names, or NULL if there are none. The last entries of args correspond to the names in kwnames, in order.

The function returns a new reference to the result, or NULL with an exception set. The callee must not retain the args array after returning.

A helper, PyVectorcall_Call, lets an object that implements vectorcall still support the older tuple-and-dictionary calling convention. The helper unpacks the tuple and dictionary into the array form and invokes the vectorcall function. Types that implement vectorcall must still implement tp_call, so that code calling through the old protocol continues to work.

The interpreter checks for the vectorcall pointer before falling back to tp_call. When the pointer is present, the interpreter uses it directly, and the tuple is not built.

Backwards Compatibility

The protocol adds new fields and flags to type objects. Existing extension types continue to work without change, since they do not set the new flag and therefore use tp_call as before. No behavior changes for code written in Python.

The private API in Python 3.8 may change before it is made public. Extension authors who use it should expect to update their code when the public version is released.

Rejected Ideas

One proposal was to make vectorcall available only through a single global registry of callable types. This was rejected because it would require every type to be known in advance and would complicate the lookup path.

Another was to remove tp_call entirely and require all callables to implement vectorcall. This was rejected because it would break a large body of existing extension code and would force authors to adopt the new API before they had a reason to.

Implementation

The implementation adds the flag, the offset field, and the helper functions to the C API. It updates the interpreter's call path to check for the vectorcall pointer. Built-in functions, method descriptors, and several standard types are changed to use the protocol. Benchmarks in the implementation show reductions in call overhead for functions that accept only positional arguments, with smaller gains for calls that use keywords.

Open Issues

The semantics of the flag that allows the callee to modify the args array need to be documented precisely before the API is made public. The PEP leaves this to the implementation notes, and the public documentation must describe the rule clearly for extension authors.

It is also unresolved how the protocol should interact with subclasses of types that implement vectorcall. The current proposal states that a subclass inherits the vectorcall pointer only if it does not override the call behavior, and this rule should be confirmed against real examples before finalization.
