# PEP 597: Add optional EncodingWarning

**Type:** Standards Track
**Status:** Draft
**Topic:** Text I/O, Developer tools

## Abstract

This PEP adds a new warning category, `EncodingWarning`. The interpreter emits it when the `encoding` argument of `open()` is omitted and the default locale-specific encoding is used to read or write text. The warning is disabled by default. Developers can enable it with a new command-line option, `-X warn_default_encoding`, or with the environment variable `PYTHONWARNDEFAULTENCODING`. The PEP also adds the string value `"locale"` for the `encoding` argument. Passing it states explicitly that the locale encoding is intended, which silences the warning without changing behavior.

## Motivation

When a program opens a text file in Python without specifying an encoding, the result depends on the platform and on the user's environment. On many systems the default is UTF-8. On Windows, for many years, it was a legacy code page. The same program can therefore read the same file correctly on one machine and produce mojibake or raise an error on another. These failures are difficult to find, because they depend on the environment where the program runs rather than on the code itself.

Developers have been advised for a long time to pass the encoding explicitly. Many do not, either because they are unaware of the issue or because the default has worked for them. The result is a large amount of code that is correct only by accident. Libraries that are used on many platforms are especially exposed, since their authors cannot know how their callers have configured the environment.

A warning can help. If the interpreter reports where the default encoding is used, developers can find the places that depend on it and decide what they want. The warning must be off by default, since many programs intentionally rely on the locale, and a warning that appears for every such call would be noise. Enabling it in tests or in development is the usual path.

## Specification

A new warning class, `EncodingWarning`, is defined as a subclass of `Warning`. It is emitted by the built-in `open()` function and by the related text-file constructors when the `encoding` argument is not supplied and the locale's default encoding is selected for the file. The warning is not emitted when the encoding is supplied, and it is not emitted for binary modes, where no encoding applies.

The warning is disabled by default in the filter list. It may be enabled with the warnings machinery in the usual way. The command-line option `-X warn_default_encoding` enables it for the process. The environment variable `PYTHONWARNDEFAULTENCODING`, when set to a non-empty value, has the same effect. The option takes precedence over the variable when both are given.

A new value, `"locale"`, is accepted for the `encoding` argument. When it is used, the file is opened with the locale's encoding, exactly as the default would do, and no warning is emitted. The value is intended to document the choice in the source code. It is not a new encoding name and does not appear in the codec registry.

The warning message identifies the encoding that was selected, so that the developer can see what the default resolved to on the system where the warning occurred.

## Rationale

A distinct warning category allows the warning to be filtered independently of other warnings. A project that wants to find these calls can turn on this category alone, and a project that does not care can leave it off without affecting its other warnings.

The choice to disable the warning by default follows from the observation that a large number of programs deliberately use the locale encoding, and that they would be flooded with messages if the warning were on. Enabling it is a deliberate act, and the flags make that act easy.

The `"locale"` value exists so that developers who have reviewed a call and decided that the locale is correct have a way to say so. Without it, the only way to silence the warning would be to write code that is less clear, for example by obtaining the locale encoding by a separate call and passing it in. The new value expresses the intent directly.

The name `PYTHONWARNDEFAULTENCODING` follows the existing pattern for warning-related environment variables, and the `-X` option follows the convention for implementation-specific settings.

## Backwards Compatibility

The default behavior of the interpreter does not change. Programs that do not enable the warning see no difference. The `"locale"` value is new, and programs that did not use it are unaffected.

Programs that run with the warning enabled may see new output on standard error. Test suites that treat warnings as errors may fail if they enable the new category, and projects that adopt the option should be aware of this.

## Performance

The check for the warning happens only when the encoding is omitted and the warning category is enabled. When the category is disabled, the cost is a single test of the filter state, which is negligible compared with the cost of opening a file.

## Reference implementation

A patch has been written that adds the category, the command-line option, the environment variable and the `"locale"` value. It includes tests for the warning being emitted when enabled, for it being suppressed when the encoding is supplied, and for the `"locale"` value producing the same result as the default without a warning.

## Open issues

The documentation should advise developers to supply an explicit encoding in new code, and should explain when the `"locale"` value is appropriate. The PEP leaves the question of whether a future version should make the warning default to on for some categories of file to a later discussion, after the current change has been used in practice.

Some modules in the standard library open files without an explicit encoding in places where the locale is intended. The implementation changes these calls to use the new value, so that the library's own tests can be run with the warning enabled without noise.
