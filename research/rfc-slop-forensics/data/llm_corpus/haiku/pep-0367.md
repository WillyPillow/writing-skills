# PEP 367: A new form of `super`

- **Type:** Standards Track
- **Status:** Rejected

## Abstract

The `super` built-in is the usual way for a method to call the implementation it overrides in a base class. Its current form requires the programmer to name the class and the instance explicitly, as in `super(Foo, self).method(...)`. The repetition is tedious, and the name of the class must be updated whenever the class is renamed. This proposal introduces a shorter form, `super.method(...)`, which the interpreter resolves automatically to the class in which the calling method is defined and to the instance or class that the method is acting upon.

The proposal also suggests a related change to the built-in namespace. The existing `super` type would be renamed to a dunder name so that the short form can take its place, and assignment to the name `super` would become a syntax error, in the same way that assignment to `None` is an error.

## Motivation

Object-oriented code in Python frequently calls the overridden method of a base class. A typical example is an initialiser that first calls the initialiser of its parent. The current idiom is clear, but it has three weaknesses. The class name appears twice in each call, once in the call to `super` and once in the definition. The instance name, usually `self`, must be written out. And the repetition is noisy when a class has many such methods.

The repeated class name also creates a maintenance problem. A class that is renamed must have every `super` call updated, and a call that names the wrong class fails in a way that is not always obvious. Programmers who copy a method into a different class sometimes forget to update the call, and the result is a method that calls the wrong implementation.

Other languages have solved this with a keyword that refers to the parent implementation directly. Python does not have such a keyword, and the proposal argues that the built-in function is an awkward substitute.

## Specification

Under this proposal, the expression `super.name` inside a method refers to the attribute `name` of the superclass of the class in which the method is defined. When the method is an ordinary instance method, the attribute is bound to the instance that is the first argument. When the method is a class method, it is bound to the class. The call `super.foo(1, 2)` therefore has the same meaning as the current `super(Foo, self).foo(1, 2)` in the class `Foo`.

The interpreter determines the class at compile time from the enclosing class definition. The short form is valid only inside a function defined in a class body. Using it elsewhere is a syntax error, because there is no class to refer to.

The built-in function `super` would be renamed to `__super__`. The old name would be removed in a later major version of the language, and until then both names would refer to the same object. Assignment to the name `super` would be a syntax error, so that the new meaning of the keyword cannot be shadowed by a local variable.

## Rationale

The proposal uses attribute syntax because the expression reads naturally as a request for a parent member. Users familiar with the current form will recognise the meaning immediately, and the short form makes the common case visible without extra noise.

Resolving the class at compile time avoids a common source of error. The current form depends on the class name being correct at runtime, and the compile-time approach ties the reference to the place where the method is written.

Making assignment to `super` an error is necessary because the short form would otherwise be ambiguous. A local variable called `super` would make the meaning of `super.foo` depend on scope, which is hard to read and hard to implement.

## Problems raised

The main objection was that the proposal adds a special case to the language for a problem that the existing form solves adequately. Critics argued that the explicit form makes the class visible, which helps readers, and that the short form hides which class is being used.

A second objection concerned multiple inheritance. The current `super` follows the method resolution order of the instance's class, and the proposal must preserve this behaviour. Several participants asked whether the compile-time class determined by the short form would give the same answer as the runtime search. The proposal answered that the resolution must still be performed at runtime using the method resolution order, and that only the starting class is fixed at compile time.

A third objection was that renaming the built-in would break code that refers to it by name, and that the migration would be large. The proposal responded that the old name would remain for a long transition, but reviewers noted that the transition would be painful for libraries that wrap `super` in helper functions.

Some participants suggested a different syntax, such as a keyword that makes the intention explicit. These alternatives were discussed but not preferred, because they would add a new keyword to the language, which is a larger change.

## Backwards Compatibility

Existing code that uses the explicit form continues to work during the transition. Code that assigns to a local variable named `super` would break, and the proposal recommends searching for such code before the change is made. The rename of the built-in would affect code that inspects the name directly, which is expected to be rare.

## Reference Implementation

A prototype was written as a change to the compiler. It recognises the attribute form, looks up the enclosing class, and emits code that performs the same lookup as the explicit call. The prototype passed the standard library tests, but it required a number of changes to the test suite where tests depended on the name of the built-in.

## Status

The proposal was rejected. The discussion concluded that the benefit did not justify the added special case, the rename, and the migration cost. The explicit form remained the only way to call a superclass method, and the language kept its current design. Later proposals for simpler superclass access were considered separately and have not yet been adopted.

## Summary

This proposal introduced a shorter form of superclass method call, `super.name`, resolved at compile time to the enclosing class and at runtime to the instance. It also renamed the built-in and made assignment to `super` an error. The change would have removed repetition and a class of maintenance errors, but it was rejected because the existing explicit form was judged adequate and the cost of the change was too high.
