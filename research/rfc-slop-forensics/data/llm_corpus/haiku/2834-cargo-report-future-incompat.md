# Rust RFC 2834: cargo report future-incompat

- Feature Name: `cargo_report_future_incompat`
- Start Date: 2020-02-17
- Status: Accepted

## Summary

This RFC proposes that Cargo report to developers the upstream dependencies in their build graph that emit future-incompatibility warnings. A future-incompatibility warning tells the author of a crate that a construct in their code will become an error in a later release of the compiler. Today such warnings are easy to miss when they come from a dependency, and they are often silenced by lint configuration that hides them even from the people who could act on them. Cargo should list the affected dependencies even when the warnings have been suppressed, and it should offer guidance about what a downstream maintainer can do. This RFC specifies the reporting behavior and the interface. It does not prescribe the particular steps a maintainer must take.

## Motivation

The compiler periodically introduces lints for code that is accepted today but will be rejected in a future version of the language. These lints are designed to give the ecosystem time to adapt. The mechanism works well for the crate that contains the offending code. It works poorly for everyone who depends on that crate.

When the offending code lives in a dependency, the person who builds the final program sees either nothing or a long list of warnings that they cannot fix directly. Many builds suppress warnings from dependencies altogether, either through configuration or through lint attributes that the upstream author added to quiet the output. In either case, the downstream developer has no signal that their build will break at some point. When the breakage arrives, it arrives all at once, and the developer must trace it back through the dependency graph under time pressure.

A consistent report from Cargo would close this gap. It would tell the developer which dependency is responsible, which lint is involved, and how far away the breakage is, so that the developer can plan an update or contact the maintainer while there is still time.

## Guide-level explanation

After a build, if any dependency in the graph has emitted a future-incompatibility warning, Cargo prints a short summary. The summary names each affected package and version, the lint that was triggered, and the release in which the construct is scheduled to become an error. The summary is printed even if warnings from dependencies are otherwise hidden.

The output also includes a suggestion. For most lints the suggestion is to update the dependency to a version that has addressed the problem. If no such version exists, the suggestion is to report the issue to the maintainer, with a link to the tracking location that the compiler provides. The suggestion is advisory. Cargo does not change the build as a result of the report.

A developer can view the full details by running a dedicated command. The command reads the information that the build stored and prints the complete warnings, including those that were suppressed, for each affected package. The command does not rebuild anything.

## Reference-level explanation

When a dependency is compiled, the compiler emits future-incompatibility diagnostics in a structured form that includes the package identifier, the lint name, and the target release. Cargo collects these records during the build and writes them to a file in the build directory. The file is keyed by package so that repeated builds replace the information for packages that were rebuilt and keep it for packages that were not.

Suppressed warnings are included in the record. This is the central change in the proposal. Lint levels set by the upstream author, including those set through a cap on lint levels for dependencies, do not remove the entry from the record. The record notes that the warning was suppressed, so that the report can say so.

At the end of the build, Cargo reads the record and prints the summary if there are any entries for packages in the graph. The summary is printed to standard error, in the same stream as other build messages, and it does not change the exit status of the build.

The dedicated command reads the same record. It accepts an optional package filter, and it prints the full diagnostic text for each matching entry. The command must work offline and must not require a network connection or a registry index update.

Cargo does not interpret the lint or attempt to decide whether the code is actually affected. The information is passed on exactly as the compiler reports it. Tactics for fixing the problem are described in the documentation for the lint and are not generated by Cargo.

## Drawbacks

A new summary adds output to every build that has such warnings, and some developers will find it noisy. The RFC mitigates this by printing a single compact notice rather than repeating the full diagnostics, but the notice still appears. Projects that have many affected dependencies may see a long list.

The record file adds a small amount of state to the build directory. Its format must be kept stable, and its contents must be handled carefully so that a corrupted file does not break the build.

There is also a risk that developers will treat the summary as a reason to update dependencies hastily, possibly to versions that are themselves unstable. The guidance text should discourage this.

## Rationale and alternatives

One alternative is to rely on the compiler to print future-incompatibility warnings from dependencies regardless of suppression. This would reverse the lint configuration that upstream authors have chosen, and it would surprise maintainers who have decided to hide certain warnings for good reason. Cargo instead reports the information without overriding the author's choice about the warnings themselves.

Another alternative is to make the summary a hard error when a breakage is imminent. This would give developers strong pressure to act but would fail builds that are otherwise working, which the project regards as an unacceptable cost for a warning about the future.

A third option is to publish a central database of affected crates. That would be useful, but it requires network access and a maintained service, and it does not help a developer who is working offline. The proposal keeps the information local and derives it from the build itself.

## Prior art

Package managers in several ecosystems report deprecation notices for dependencies, and some offer commands that list them. The most useful of these show the affected package, the reason, and the suggested action, and they avoid changing the build. This proposal follows that model. It differs in that the information comes directly from the compiler's own diagnostics rather than from metadata supplied by the package author.

## Unresolved questions

The RFC does not settle how the summary should be formatted for projects that use alternative output formats, such as structured logs for continuous integration. The implementation will need to choose a representation that is machine readable as well as readable by people.

It is also not decided how long the record should be kept when a package is removed from the graph. A reasonable default is to discard entries for packages that no longer appear, but this may need to be revisited if users find the behavior surprising.

## Future possibilities

Cargo could later offer to open an issue with the upstream maintainer on the developer's behalf, provided the developer agrees and the project's policy allows it. The record could also be shared with continuous integration dashboards, so that teams can track the number of affected dependencies over time. In the longer term, the information could inform decisions about when lints are promoted to errors, by showing how widely a change would affect the ecosystem.
