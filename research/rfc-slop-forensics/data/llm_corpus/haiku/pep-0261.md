PEP: 261
Title: Support for "wide" Unicode characters
Author: Paul Prescod
Status: Final
Type: Standards Track
Created: 2001
Python-Version: 2.2

Abstract

Python 2.1 Unicode characters can have ordinals only up to 2**16 - 1. This range corresponds to a range in Unicode known as the Basic Multilingual Plane. Unicode now defines characters on other planes, and the largest addressable character in Unicode has the ordinal 17 * 2**16 - 1, which is 0x10FFFF. For readability, this PEP calls that maximum value TOPCHAR and calls characters in the range above the Basic Multilingual Plane "wide characters". The PEP proposes a way for a Python build to support wide characters in its Unicode type, while keeping the existing interface for code that does not need them.

Motivation

Most text in common use lies within the Basic Multilingual Plane, and a 16-bit code unit is enough to represent it. Some scripts, historical writing systems, mathematical symbols, and rarely used ideographs are outside the plane. A program that needs to process these characters cannot do so reliably if the interpreter truncates or rejects their ordinals.

The existing Unicode type stores characters as 16-bit values. Strings containing characters outside the Basic Multilingual Plane are not impossible to build, because they can be represented as pairs of surrogate code units, but the interpreter treats each code unit as a separate character. A program that calls len on such a string receives a count that is larger than the number of characters the user sees, and slicing can split a character in two. These behaviors are surprising, and they make correct text processing difficult.

The problem is compounded by platform differences. Some builds of the interpreter were compiled with a wide Unicode type, and others with a narrow one. Code that works on one build may fail on another, because the length and indexing of strings differ. The PEP aims to remove this difference by specifying a single behavior for wide characters.

Specification

This PEP proposes that the Unicode type support characters with ordinals up to TOPCHAR. The internal representation may be either narrow or wide, depending on how the interpreter is built, but the observable behavior of the type must not depend on the build. In particular, len, indexing, and slicing operate on characters rather than on code units, and the ordinal of each character is the value of its Unicode code point.

The builtin function unichr accepts ordinals up to TOPCHAR. On a narrow build, unichr of an ordinal above 0xFFFF produces a two-character string of surrogate pairs, which the interpreter presents as a single character to user code through the wide-aware operations. On a wide build, it produces a single character directly. The PEP asks that the observable result be the same on both builds.

Codecs that read and write Unicode text must also handle wide characters. The UTF-8 and UTF-16 codecs are required to encode and decode the full range. A codec that encounters an unpaired surrogate in input should report an error rather than silently producing a malformed string.

The escape sequences for Unicode literals are extended to accept eight hexadecimal digits, so that a programmer can write any code point in the range. The shorter four-digit form remains for characters in the Basic Multilingual Plane.

Compatibility

The change is designed to keep existing programs working. Programs that use only characters in the Basic Multilingual Plane see no difference in behavior. Programs that handle wide characters on a narrow build will see different results for len and indexing, but these programs were already producing inconsistent results, and the new behavior is the one that a careful author would have expected.

The PEP recognizes that code which depends on the internal representation, such as code that reads the raw buffer of a Unicode object through the C interface, may need to be updated. The C API is extended with functions that report the number of characters independently of the internal width, and these functions should be preferred in new extension modules.

Implementation

The implementation chooses the internal representation at build time. A wide build stores each character in a 32-bit code unit, which is simple and gives constant-time indexing. A narrow build stores characters in 16-bit code units and represents wide characters as surrogate pairs. The narrow build must hide the pairs from the user-visible operations, which requires that len, indexing, and slicing scan for pairs when they encounter them. The cost of this scanning is accepted as the price of keeping the narrow build compatible with its existing memory layout.

The patch that implements these changes touches the Unicode object code, the codecs, and the regular expression engine. The regular expression engine must treat surrogate pairs as single characters when matching, so that a pattern matching a wide character works on both builds.

Alternatives

One alternative is to build the interpreter only in wide mode. This is simple and removes the difference between builds, but it doubles the memory used for ordinary text and was judged too costly for the platforms that depended on narrow strings.

A second alternative is to keep the narrow representation and simply document that wide characters are not supported. This avoids the work, but it leaves the problems described above in place, and it prevents programs from handling text outside the Basic Multilingual Plane.

A third alternative is to introduce a separate type for wide strings. This would avoid changing the existing type, but it would split the language's text model in two, and most library code would need to be written for both types.

Open issues

The PEP leaves some questions for the implementers. The exact set of codecs that must support wide characters at the first release should be decided by the people who maintain them. The behavior of string formatting with wide characters in width calculations is not specified in detail, and it may be settled in a later revision.
