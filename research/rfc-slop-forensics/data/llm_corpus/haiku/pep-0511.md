# PEP 511: An API for code transformers

- **Type:** Standards Track
- **Status:** Rejected

## Abstract

This proposal defines an API that lets third-party code register transformers for Python source code. A transformer can work on the abstract syntax tree before it is compiled, or on the bytecode after compilation. The API is designed so that a transformer can be applied during normal imports, can be enabled and disabled from the command line, and can be used by tools that need to instrument or optimise code without changing the source files.

The proposal also adds a command line option, `-o`, which lets the user select a tag that is included in the names of cached bytecode files. A separate tag allows the user to disable the built-in peephole optimiser for a run. Together these changes make it possible to keep several differently transformed versions of the same module on disk without them overwriting one another.

## Motivation

Python has no official way to change code between the moment it is read and the moment it runs. Projects that need this have built their own mechanisms, usually through import hooks or through custom codecs for source encoding. These mechanisms are fragile. They interact badly with the bytecode cache, they are difficult to combine, and they have no common vocabulary.

Several useful tools would benefit from a standard interface. Coverage measurement needs to insert counters. Contract checking needs to insert assertions. Some research projects want to rewrite arithmetic or to add tracing. Each of these currently depends on private details of the import system, which change between releases.

A standard API would let such tools coexist. It would also make it clear to users when code has been transformed, and would give interpreter developers a stable target to support.

## Specification

A transformer is an object that defines one or both of two methods. The first, `ast_transform(self, tree, filename)`, receives the parsed abstract syntax tree of a module and returns a tree that the compiler will then use. The second, `bytecode_transform(self, code)`, receives a code object and returns a new one. Either method may return its input unchanged.

Transformers are registered by calling `sys.set_code_transformers(list)`. The list is consulted in order, and each transformer receives the output of the previous one. Registration affects only modules imported after the call, and a transformer may be removed by registering a shorter list.

When a module is loaded from source, the import system parses it, runs each AST transformer in order, compiles the result, and runs each bytecode transformer in order. The final code object is then executed and may be written to the cache.

The cache file name includes the tag of the active transformers. A module transformed with one set of transformers is stored under a different name from the same module transformed with another set, or with none. This prevents one configuration from loading the output of another.

The command line option `-o TAG` sets the optimisation tag used in the cache name. The special value `noopt` disables the peephole optimiser for that run. Using `-o` changes only the file names in the cache and does not affect the semantics of the program beyond the optimisation setting.

## Cache behaviour

The cache rule is the most delicate part of the proposal. Bytecode produced by a transformer depends on the transformer, so it must not be loaded by a process that does not have the same transformer. The proposal therefore requires that the cache name include a fingerprint of the transformer set.

A second rule is that a module whose cached code requires a transformer must fail to import if that transformer is absent. This prevents a program from silently running code that was transformed in a way the current process does not understand. The failure is an `ImportError` that names the missing transformer.

These rules mean that the cache remains correct, but they also mean that a project using transformers must install them everywhere the code runs. The proposal argues that this is a reasonable requirement, because running untransformed code in place of transformed code would be a more serious problem.

## Rationale

Choosing two separate hooks, one for the tree and one for the bytecode, reflects the two stages at which tools need to act. Some transformations are simpler on the tree, where the structure of the source is still visible. Others are simpler on the bytecode, where the result of compilation is known.

The decision to apply transformers in registration order keeps the behaviour easy to reason about. Users who combine several transformers can predict the result from the order in which they register them.

The `-o` option was designed to be general. It names a tag rather than a particular optimisation, so that future optimisers can be selected in the same way without new command line flags.

## Security Considerations

A transformer runs with the full privileges of the importing process, so installing one is equivalent to installing arbitrary code. The proposal does not change this, but it makes the risk more visible by requiring explicit registration. It also recommends that tools warn when a transformer is registered from a module that was itself loaded from an untrusted location.

## Backwards Compatibility

The API is new and does not change the behaviour of programs that do not register transformers. The new command line option does not affect existing invocations. The only compatibility concern is that cache file names change when the optimisation tag is used, which may cause one extra compilation the first time a module is imported.

## Reference Implementation

A prototype was developed as a patch to the interpreter. It adds the registration function, invokes transformers during import, and extends the cache naming scheme. A set of example transformers was written to test the design, including one that inserts assertions and one that counts executed branches.

## Discussion and status

The proposal generated a large discussion. Supporters pointed to the many projects that already use import hacks and argued that a standard API would make those projects more reliable. Opponents argued that transformers make code harder to understand, because the program that runs may differ from the program the reader sees. They also worried that transformers would be used to hide behaviour, and that the cache rules would complicate the interpreter.

Some core developers proposed a narrower design that allowed only bytecode transformers, arguing that AST transformers would cause most of the difficulty. Others proposed that the feature be provided by a third-party package instead of the standard library, so that it could evolve more quickly.

The proposal was rejected. The rejection reasons included the cost of the cache rules, the risk that transformers would be used in ways that are hard to debug, and the view that the existing import hooks already cover the important cases well enough for the time being.

## Summary

This proposal would have added a registration API for AST and bytecode transformers, a cache naming scheme that keeps transformed and untransformed code separate, and a command line option for selecting an optimisation tag. The design aimed to give tools a stable place to act on source code. The proposal was rejected, but the problems it addressed remain, and later discussions have revisited parts of the design.
