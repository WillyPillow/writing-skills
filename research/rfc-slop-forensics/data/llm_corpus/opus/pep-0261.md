PEP: 261
Title: Support for "wide" Unicode characters
Author: Paul Prescod
Status: Final
Type: Standards Track
Created: 27-Jun-2001
Python-Version: 2.2

Abstract
========

Python 2.1 Unicode characters can have ordinals only up to ``2**16 - 1``.
That range corresponds to the part of Unicode known as the Basic
Multilingual Plane (BMP).  Unicode now assigns characters on other
"planes".  The largest addressable character in Unicode has the ordinal
``17 * 2**16 - 1`` (``0x10ffff``).  For readability we will call this
value TOPCHAR, and call characters above ``0xffff`` "wide characters".

This PEP proposes a build-time option that makes Python's Unicode
strings able to hold every character up to TOPCHAR as a single element,
and describes how the default ("narrow") build should treat wide
characters in the meantime.


Glossary
========

Character
    An abstract entity with a code point in the Unicode standard.

Code point
    An integer in the range 0 to TOPCHAR that identifies a character.

Code unit
    The integer stored in one element of a Python Unicode string.  In a
    narrow build this is 16 bits wide; in a wide build, 32 bits.

Surrogate pair
    A pair of 16-bit code units in the ranges ``0xD800``-``0xDBFF``
    (high) and ``0xDC00``-``0xDFFF`` (low), used by UTF-16 to encode one
    wide character.

Narrow build
    A Python build whose Unicode strings store 16-bit code units.

Wide build
    A Python build whose Unicode strings store 32-bit code units.


Motivation
==========

When Python's Unicode support was designed, nearly every character in
use lived in the BMP, and Unicode itself was often described as a 16-bit
character set.  That is no longer true.  Unicode 3.1 assigns over 40,000
characters outside the BMP, including large sets of CJK ideographs used
in names and historical texts, mathematical alphanumeric symbols, and
musical notation.  Users in East Asia in particular will need these
characters.

Python 2.1 can already hold wide characters in a Unicode string, but
only as surrogate pairs.  To the programmer this means:

- ``len()`` reports two for a single wide character.
- Indexing and slicing can split a character in half.
- ``unichr()`` refuses arguments above ``0xffff``.
- ``ord()`` of a wide character is not possible, since it is two
  elements long.

In effect, Python exposes UTF-16 code units and calls them characters.
That is workable for code that just passes text through, but not for
code that analyses or transforms text character by character.


Proposed Solution
=================

Add a configure-time option, ``--enable-unicode=ucs4``, that selects a
32-bit code unit for Unicode strings.  In such a wide build:

- Every character from ``0`` to TOPCHAR occupies exactly one element of
  a Unicode string.
- ``len()``, indexing and slicing work in characters.
- ``unichr(i)`` accepts any ``i`` in ``range(0, TOPCHAR + 1)``.
- ``ord(c)`` returns the code point of any single-character string.
- The ``\U`` escape in Unicode literals can name any character.

The default build remains narrow (``--enable-unicode=ucs2``) for this
release.  This keeps memory use unchanged for users who do not need wide
characters, and preserves binary compatibility with extension modules
that assume a 16-bit ``Py_UNICODE``.

A new constant ``sys.maxunicode`` reports the largest code point a
single string element can hold: ``0xffff`` on narrow builds and
``0x10ffff`` on wide builds.  Programs that care can test it at runtime.


Behaviour in Narrow Builds
==========================

Narrow builds continue to store wide characters as surrogate pairs, and
the following rules apply:

- ``unichr(i)`` for ``i > 0xffff`` raises ``ValueError``.  It does not
  return a two-element string, because callers expect a one-element
  result.
- The ``\U`` escape with a value above ``0xffff`` produces a surrogate
  pair.
- Codecs encode surrogate pairs as the wide character they represent
  where the target encoding supports it.  In particular, the UTF-8
  encoder produces a single four-byte sequence for a valid surrogate
  pair, not two three-byte sequences.
- The UTF-8 and UTF-16 decoders produce surrogate pairs for wide
  characters.
- Lone surrogates are permitted in strings, since forbidding them would
  make narrow builds unable to represent some intermediate states.  The
  UTF-8 encoder encodes a lone surrogate as a three-byte sequence.

No attempt is made to make ``len()`` or indexing aware of surrogates in
narrow builds.  Doing so would make these operations O(n) and would
change long-standing behaviour.


Behaviour in Wide Builds
========================

- Surrogate code points ``0xD800`` to ``0xDFFF`` may appear in strings
  as single elements, but they are not combined.  A string containing a
  high surrogate followed by a low surrogate has length two.
- The UTF-16 decoder combines valid surrogate pairs into a single wide
  character.  The UTF-16 encoder splits wide characters into surrogate
  pairs.
- The UTF-8 decoder produces wide characters directly.
- ``unichr(i)`` for ``i > TOPCHAR`` raises ``ValueError``.


C API
=====

``Py_UNICODE`` becomes a 32-bit type in wide builds, typically
``wchar_t`` on platforms where that is four bytes, or ``unsigned long``
otherwise.  The macro ``Py_UNICODE_SIZE`` gives its size in bytes.

Extension modules that hard-code a 16-bit ``Py_UNICODE`` will not work
with wide builds.  To prevent silent memory corruption, the names of
the public Unicode API functions are mangled with the build width, so
that ``PyUnicode_FromUnicode`` is exported as
``PyUnicodeUCS2_FromUnicode`` or ``PyUnicodeUCS4_FromUnicode``.  An
extension compiled against a narrow build will fail to load in a wide
build with a link error, rather than corrupting data.

Functions that convert between ``Py_UNICODE`` arrays and ``wchar_t``
arrays become trivial on platforms where the two types have the same
size.


Rationale
=========

Several approaches were considered.

**Variable-width internal representation.**  Store strings as UTF-16 or
UTF-8 but make indexing operate on characters.  This hides the encoding
from the user but turns indexing into a linear-time operation, or
requires auxiliary index structures.  It also complicates every C
extension that touches string data.  Rejected for this release.

**Always use 32 bits.**  Simplest semantics, but doubles memory for
every Unicode string, which matters for applications holding large
amounts of mostly-BMP text.  We prefer to let the user choose.

**Expose surrogates and do nothing.**  Leaves programmers to handle
UTF-16 details themselves, which most will get wrong.

**Make narrow builds surrogate-aware in ``len()`` and slicing.**
Changes the cost model of basic operations and the meaning of existing
code.

A build-time choice gives users who need wide characters a correct
implementation today, while leaving the default unchanged.  If wide
characters become common, a future release can change the default.


Backward Compatibility
======================

Narrow builds behave exactly as Python 2.1, except that codecs now
handle surrogate pairs correctly and ``sys.maxunicode`` is available.

Wide builds may break Python code that assumes ``unichr()`` fails above
``0xffff`` or that ``len()`` counts surrogates.  Such code is rare.  The
larger compatibility issue is binary extensions, addressed by the name
mangling above.

Pickles and marshal data store Unicode strings as UTF-8, so data written
by one build can be read by the other, subject to surrogate pairs being
combined or split as described.


Open Issues
===========

- Should narrow builds offer a helper module for iterating over
  characters rather than code units?
- Should ``repr()`` of a wide character use ``\U`` escapes in both
  builds, so that output is identical?
- Some platforms have a 16-bit ``wchar_t``; Python on those platforms
  cannot rely on ``wchar_t`` for the wide build and must use its own
  type.
