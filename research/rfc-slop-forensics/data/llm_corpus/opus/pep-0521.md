PEP: 521
Title: Managing global context via 'with' blocks in generators and coroutines
Status: Draft
Type: Standards Track
Created: 2015
Python-Version: 3.6

# Abstract

While we generally try to avoid global state when possible, there are a number of situations where it is agreed to be the best approach. In Python, the standard pattern for handling such cases is to keep the state in global or thread-local storage and to use `with` blocks to confine modifications of that state to a single dynamic scope. Examples include `warnings.catch_warnings` and `decimal.localcontext` in the standard library, `numpy.errstate` (which exposes the IEEE 754 floating point error-handling settings), and the logging or request context used by many web frameworks.

There is currently no ergonomic way to manage such local changes to global state when writing a generator or coroutine. A `with` block inside a generator stays "open" across every `yield`, so the modified state leaks out into whatever code resumes the generator, and the caller's own state changes leak into the generator. This PEP proposes an extension to the context manager protocol that lets a context manager be notified whenever the frame executing its `with` block is suspended or resumed, so that it can save and restore the state it manages.

# Motivation

Consider a generator that wants to compute its results with a particular decimal precision:

```python
from decimal import localcontext

def precise_values(items):
    with localcontext() as ctx:
        ctx.prec = 50
        for item in items:
            yield compute(item)
```

This looks correct, and it is the code most people would write. But `localcontext()` modifies the thread's current decimal context when the `with` block is entered and restores it on exit. Between those two points the generator yields control back to its consumer many times. While the generator is suspended, the consumer runs with a precision of 50, even though the consumer never asked for that. Conversely, if the consumer changes the precision between iterations, the generator will see the consumer's setting on resumption rather than its own.

The same problem appears with `warnings.catch_warnings`, `numpy.errstate`, and any framework that tracks "the current request" or "the current transaction" in thread-local storage. With coroutines it is worse: a single thread may interleave dozens of coroutines, each of which believes it has its own private dynamic scope. The result is that context managers which work flawlessly in ordinary functions silently become incorrect once a `yield` or `await` appears inside the block.

Today the only workaround is to avoid holding a `with` block open across a suspension point, which forces awkward code such as re-entering the context manager around each piece of work and exiting it before every `yield`. In practice nobody does this consistently.

# Specification

## The extended protocol

Two new optional methods are added to the context manager protocol:

- `__suspend__(self)`: called when the frame containing the active `with` block is about to be suspended, i.e. immediately before a `yield` (including `yield from` and `await`) transfers control out of the frame.
- `__resume__(self)`: called when the frame is resumed, immediately after control returns to the frame and before execution of the code following the suspension point.

Both methods take no arguments and their return values are ignored. Both are optional; a context manager that does not define them behaves exactly as it does today.

The intended implementation for state-managing context managers is symmetrical with `__enter__` and `__exit__`:

```python
class localcontext:
    def __enter__(self):
        self._saved = getcontext()
        setcontext(self._new)
        return self._new

    def __suspend__(self):
        setcontext(self._saved)

    def __resume__(self):
        self._saved = getcontext()
        setcontext(self._new)

    def __exit__(self, *exc_info):
        setcontext(self._saved)
```

## Ordering

When a frame has several nested `with` blocks active, `__suspend__` is called on each context manager from the innermost outward, mirroring the order in which `__exit__` methods would run. `__resume__` is called from the outermost inward, mirroring `__enter__`. This preserves the invariant that inner contexts are always established on top of outer ones.

## When the hooks are invoked

The hooks fire only for suspensions of the generator or coroutine frame itself. Calls into ordinary functions from within the `with` block do not trigger them, since those calls already execute within the intended dynamic scope. The hooks are invoked on:

- `yield` and `yield from` in generators,
- `await` in native coroutines (but only when the awaited object actually suspends the frame),
- `yield` inside asynchronous generators.

They are not invoked when a generator is first started, since no `with` block is active yet, nor when the generator is closed: on `close()` or garbage collection the frame is resumed with `GeneratorExit`, `__resume__` runs, and the normal `__exit__` sequence follows.

## Exceptions

If `__suspend__` raises, the exception propagates into the generator frame at the suspension point, as if the `yield` expression itself had raised. If `__resume__` raises, the exception likewise propagates at the point of resumption. Remaining hooks in the chain are not called in either case; the frame's own exception handling and `__exit__` methods take over from there.

## Implementation

The compiler records, for each frame, the stack of context managers whose `with` blocks are currently active. CPython already pushes a block entry for each `with` statement; the entry would be extended to keep a reference to the context manager's bound `__suspend__` and `__resume__` methods, looked up once at `__enter__` time in the same way that `__exit__` is today. The `YIELD_VALUE` and resume paths in the evaluation loop walk this stack only when it is non-empty and at least one entry defines the hooks, so code that does not use the feature pays essentially nothing.

# Rationale

The core insight is that a `with` block in a generator describes a dynamic scope that is not contiguous in time. It covers the stretches when the generator is actually executing and excludes the stretches when it is suspended. The interpreter already knows exactly when those transitions occur, so it is the natural place to notify the context manager.

Alternative designs considered include:

**Changing thread-local storage into "frame-local" storage.** This would mean a new kind of context variable that the interpreter automatically swaps on suspension. It is more powerful but requires every library to migrate its state to a new storage mechanism. The approach in this PEP lets libraries keep their existing storage and adopt the fix incrementally by adding two methods.

**Requiring explicit wrapper decorators.** A decorator could wrap a generator and save and restore specific pieces of state around each `next()` call. This works for a fixed, known set of state but cannot handle context managers entered dynamically within the body, and it puts the burden on every generator author instead of on the much smaller number of context manager authors.

**Doing nothing.** The problem is subtle enough that most affected users never notice it until it causes a hard-to-diagnose bug, often in production under concurrency. Asynchronous frameworks make this increasingly common.

# Backwards Compatibility

The new methods are optional, so existing context managers are unaffected. Code that currently relies on state leaking out of a suspended generator, deliberately or accidentally, would change behaviour once the relevant context manager adopts the hooks. Such reliance is believed to be rare and is almost always a bug. Library authors adopting the protocol should note the change in their release notes.

Objects that happen to define methods named `__suspend__` or `__resume__` for some unrelated purpose would begin to have them called. Dunder names are reserved for the language, so this is not considered a compatibility constraint.

# Performance

The cost for frames with no active `with` blocks is a single check on suspension and resumption. For frames with active `with` blocks whose context managers do not define the hooks, the check can be avoided entirely by caching the lookup result at `__enter__` time. Only context managers that opt in incur the cost of method calls, and for those the cost is the price of correctness.

# Open Questions

- Should `contextlib.contextmanager` provide a way for generator-based context managers to define suspend and resume behaviour, and if so, what should the syntax be?
- Should `ExitStack` forward suspend and resume notifications to the context managers it holds? It seems it should, in the same order as it would invoke `__exit__`.
- How should this interact with any future frame-local or task-local storage mechanism added to the language?
