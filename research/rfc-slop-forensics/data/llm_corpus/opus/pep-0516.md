# PEP 516: Build system abstraction for pip/conda etc

| Field | Value |
|---|---|
| PEP | 516 |
| Title | Build system abstraction for pip/conda etc |
| Status | Draft |
| Type | Standards Track |
| Topic | Packaging |

## Abstract

This PEP specifies a programmatic interface that pip and other distribution and installation tools can use when working with Python source trees, both developer trees (such as a git checkout) and source distributions.

The interface decouples pip from its current hard dependency on setuptools. That matters for two reasons:

1. It allows new build systems that are easier to use and do not need to pretend to be setuptools.
2. It lets setuptools change its own user interface without breaking pip.

The same interface lets pip install a package's build-time requirements before building it, which is an important step towards giving pip feature parity with the installation components of other packaging systems.

## Motivation

To install from source, pip runs `python setup.py egg_info`, `python setup.py bdist_wheel`, `python setup.py install` or `python setup.py develop`. This has several consequences.

**Every project must have a `setup.py` that behaves like setuptools.** Projects that want a different build system (flit, a CMake-based build, a Meson build for a C extension, a custom script) must ship a `setup.py` shim that emulates the setuptools command line, including undocumented options pip passes. Shims are brittle, and each pip release can break them.

**setuptools cannot change.** Because pip drives setuptools through its command line, any change to that command line, even removing a long-deprecated option, risks breaking installation for the whole ecosystem. setuptools is frozen in place by its largest consumer.

**Build requirements cannot be declared.** `setup.py` is executed to discover a project's metadata, including its dependencies. If `setup.py` needs something that is not installed (Cython, numpy headers, a newer setuptools) it fails before it can say what it needs. `setup_requires` exists but is handled by setuptools itself, using `easy_install`, outside pip's control over indexes, caches and certificates.

**Other tools face the same problem.** conda-build, distribution packagers and IDE integrations all have to run `setup.py` and parse its output.

What is needed is a small, documented contract: how to discover what a source tree needs to build, and how to ask it to produce metadata and a wheel.

## Specification

### The build system description file

A source tree declares its build system in a file at its root, `pypa.json`:

```json
{
    "schema": 1,
    "bootstrap_requires": ["flit"],
    "build_command": ["flit"]
}
```

- `schema` is the version of this specification. Tools must refuse files with a schema they do not understand.
- `bootstrap_requires` is a list of PEP 508 requirement strings that must be installed before the build tool can run.
- `build_command` is the command, as an argument list, that invokes the build tool. Subcommands defined below are appended to it.

If `pypa.json` is absent, tools fall back to the existing `setup.py` behaviour, using a built-in adapter that implements the interface below on top of setuptools.

### Subprocess interface

The interface is a command-line protocol rather than an importable Python API. Each operation runs `build_command` plus a subcommand in a fresh subprocess, with the working directory set to the source tree. A subprocess boundary keeps the build tool's imports, global state and Python version requirements separate from the installer's.

All output intended for machine consumption is JSON written to stdout. Human-readable progress goes to stderr. A nonzero exit code signals failure.

#### `metadata`

```
<build_command> metadata --output-dir DIR
```

Writes a `.dist-info` directory describing the project into `DIR` and prints its name as JSON. The directory must contain at least `METADATA`. This lets the installer discover the project's name, version and runtime dependencies without building it.

#### `build_requires`

```
<build_command> build_requires
```

Prints a JSON object `{"build_requires": [...]}` listing additional requirements needed to build a wheel, beyond `bootstrap_requires`. These may depend on the target environment. For example, a project may need a specific numpy only when building its C extension.

#### `wheel`

```
<build_command> wheel -d OUTPUT_DIR
```

Builds a wheel from the source tree and places it in `OUTPUT_DIR`.

#### `develop`

```
<build_command> develop [--prefix PREFIX]
```

Installs the project in development mode, so that changes to the source tree are reflected without reinstalling. This is the equivalent of `setup.py develop`. Supporting it is optional. Tools that cannot support it exit with a distinctive status, and installers report that editable installs are unsupported.

### Installer behaviour

To install a source tree, an installer:

1. Reads `pypa.json`.
2. Creates an isolated build environment.
3. Installs `bootstrap_requires` into it.
4. Runs `build_requires` and installs the result.
5. Runs `wheel`.
6. Installs the resulting wheel into the target environment using its normal wheel installation logic.

Because the installer controls steps 3 and 4, its configuration (index URLs, proxies, caches, constraints) applies to build dependencies, fixing a major limitation of `setup_requires`.

### Environment variables

The installer passes configuration through the environment, using the `PYTHON` variable to name the interpreter that will use the built artifacts. The build tool must build for that interpreter, which may differ from the one running the build tool itself.

## Rationale

### Why a subprocess interface rather than Python hooks?

A command-line interface allows build tools written in any language and running under any Python version. It isolates the installer from crashes and import side effects. It also mirrors how pip already calls `setup.py`, which simplifies migration: the setuptools adapter is little more than argument translation.

An importable API is more convenient for Python-based tools and avoids the overhead of JSON on stdout. A competing proposal takes that approach. The authors consider the isolation and language neutrality of a subprocess boundary more important.

### Why not reuse `setup.cfg` or `setup.py`?

Both are tied to setuptools semantics. A separate, minimal file makes clear that nothing else in the tree has to look like setuptools.

### Why separate `bootstrap_requires` and `build_requires`?

Bootstrap requirements are static and needed simply to run the tool. Build requirements may need computation, such as inspecting the target platform, which requires the tool to already be installed.

## Backwards Compatibility

Source trees without `pypa.json` continue to be built by running `setup.py`, now through an adapter that implements this interface. Existing projects see no change.

Installers that do not implement this PEP will not recognise `pypa.json` and will look for `setup.py`. Projects wanting to support older installers can ship a `setup.py` shim during the transition.

## Rejected Ideas

- **Declaring build tool hooks by Python import path.** See above.
- **Standardising the source tree layout.** Out of scope. Build tools may organise sources however they like.
- **Including a `sdist` operation.** Producing source distributions is a developer task, not an installer task, and can be specified separately.
