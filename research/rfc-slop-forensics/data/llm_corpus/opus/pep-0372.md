PEP: 372
Title: Adding an ordered dictionary to collections
Status: Draft
Type: Standards Track
Python-Version: 2.7, 3.1
Created: 15-Jun-2008

# Abstract

This PEP proposes an ordered dictionary as a new data structure for the `collections` module, called `OrderedDict` in this PEP. The proposed API draws on experience with similar implementations in real-world applications and in other programming languages.

# Rationale

The built-in `dict` does not preserve the order in which keys are inserted. Iterating over a dictionary returns keys in an order that depends on hashing and the history of insertions and deletions. For most uses this is fine. For a substantial minority it is not, and the workarounds are clumsy.

Situations where insertion order matters include:

- **Configuration and serialization.** When a program reads a configuration file or JSON document and writes it back, users expect the keys to stay in the same order. A tool that shuffles the keys of a hand-edited file produces large, meaningless diffs.
- **Object-relational mappers.** ORMs such as those in Django and SQLAlchemy want to record the order in which fields are declared on a model class, so that table columns and forms follow the source order.
- **Metaclasses.** Related to the above: a class body is executed into a `dict`, which loses declaration order. An ordered mapping is needed to capture it.
- **Caches and history.** An LRU cache or a "recently used" list needs to know which entry was added or touched first.
- **Porting code from other languages.** PHP arrays and Ruby hashes (since 1.9) preserve insertion order, and code translated from them often relies on it.

Python developers have written many ordered dictionary implementations to meet these needs: `odict` in various web frameworks, `OrderedDict` in Django's `SortedDict`, recipes in the Python Cookbook, and more. They differ in subtle ways, in performance, and in which `dict` methods they get right. A single implementation in the standard library, with a documented API, would remove the duplication and give library authors something they can depend on.

# Specification

## Behavior

`OrderedDict` is a subclass of `dict` that remembers the order in which keys were first inserted.

```python
>>> from collections import OrderedDict
>>> d = OrderedDict()
>>> d['banana'] = 3
>>> d['apple'] = 4
>>> d['pear'] = 1
>>> list(d)
['banana', 'apple', 'pear']
```

The rules are:

- Inserting a new key appends it at the end.
- Assigning to an existing key changes its value but **does not** move it.
- Deleting a key removes it; if it is reinserted later, it goes to the end.
- Iteration (`__iter__`, `keys()`, `values()`, `items()`) follows insertion order. `reversed()` iterates in reverse insertion order.

## Constructor

The constructor accepts the same arguments as `dict`:

```python
OrderedDict()
OrderedDict([('a', 1), ('b', 2)])
OrderedDict(other_mapping)
OrderedDict(a=1, b=2)
```

When given a sequence of pairs, order is taken from the sequence. When given a regular `dict` or keyword arguments, the resulting order is whatever order those arguments arrive in, which for a plain `dict` and for `**kwargs` is arbitrary. This is documented so users know to pass a list of pairs when order matters.

## Methods

`OrderedDict` supports every method of `dict`. Methods whose results depend on order are defined as follows:

- `keys()`, `values()`, `items()` and their iterator and view forms return results in insertion order.
- `popitem(last=True)` removes and returns a `(key, value)` pair. With `last=True`, the most recently inserted pair is returned (LIFO); with `last=False`, the oldest (FIFO). This makes `OrderedDict` usable as both a stack and a queue of key-value pairs.
- `update()` inserts new keys in the order the argument provides them.
- `copy()` returns an `OrderedDict` with the same order.
- `__repr__` shows the contents as a list of pairs so the order is visible and round-trips: `OrderedDict([('banana', 3), ('apple', 4)])`.

## Equality

Comparing two `OrderedDict` instances is order-sensitive:

```python
>>> OrderedDict([('a', 1), ('b', 2)]) == OrderedDict([('b', 2), ('a', 1)])
False
```

Comparing an `OrderedDict` with a regular `dict` (or any other mapping) is order-insensitive, matching `dict` semantics:

```python
>>> OrderedDict([('a', 1), ('b', 2)]) == {'b': 2, 'a': 1}
True
```

This lets `OrderedDict` be substituted anywhere a `dict` is used without changing the results of existing comparisons, while giving meaningful order-aware comparison between two ordered dictionaries.

## Pickling and copying

`OrderedDict` instances can be pickled, copied with `copy.copy`, and deep-copied with `copy.deepcopy`, preserving order.

## Interaction with other modules

- `json`: the `object_pairs_hook` argument (added alongside this PEP) lets `json.loads(text, object_pairs_hook=OrderedDict)` produce ordered results.
- `configparser`: may accept `dict_type=OrderedDict`, and could adopt it as its default so that files are written back in their original order.
- `collections.namedtuple`: `_asdict()` can return an `OrderedDict` so that field order is preserved.

# Reference Implementation

A pure-Python implementation is provided. It stores a regular `dict` for the key-value mapping and a doubly linked list of keys to track order. A second `dict` maps each key to its link node, so that deletion is O(1):

```python
class OrderedDict(dict):
    def __init__(self, *args, **kwds):
        self.__root = root = _Link()
        root.prev = root.next = root
        self.__map = {}
        self.update(*args, **kwds)

    def __setitem__(self, key, value):
        if key not in self:
            link = _Link()
            last = self.__root.prev
            link.prev, link.next, link.key = last, self.__root, key
            last.next = self.__root.prev = link
            self.__map[key] = link
        dict.__setitem__(self, key, value)

    def __delitem__(self, key):
        dict.__delitem__(self, key)
        link = self.__map.pop(key)
        link.prev.next = link.next
        link.next.prev = link.prev
```

With this design, all of the `dict` operations keep their usual big-O complexity. Lookup is unchanged, since it goes directly to the underlying dictionary. Insertion and deletion add a constant amount of work. Memory use is roughly double that of a `dict` with the same contents, which is acceptable for the intended use cases.

A C implementation may follow later if profiling shows it is needed.

# Alternatives Considered

**A sorted dictionary.** Some requests are for a mapping that keeps keys in *sorted* order rather than insertion order. That is a different data structure, usually implemented with a balanced tree or skip list, and has different performance trade-offs. It is out of scope here, though `OrderedDict` combined with `sorted()` covers simple cases.

**Moving a key to the end on reassignment.** Some implementations treat assignment to an existing key as a reinsertion. That is useful for LRU caches but surprising when loading configuration, where updating a value should not reorder the file. The proposed behavior is the less surprising default; LRU users can delete and reinsert.

**Order-sensitive comparison with `dict`.** Rejected because it would break the Liskov substitution principle: code that compared a mapping with a dict literal would start failing when handed an `OrderedDict`.

**Indexing by position (`d.index(key)`, `d[2]` by position).** Some implementations offer it. Such operations are O(n) with a linked list and blur the line between a mapping and a sequence. Users can write `list(d)[2]` when they need it.

**Making `dict` itself ordered.** This would change the performance characteristics of the most heavily used data structure in Python. It is not proposed here.

# Open Questions

- Whether `OrderedDict` should be the default for `configparser` in Python 3.1.
- Whether a C implementation is necessary before release.
