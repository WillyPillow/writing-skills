PEP: 532
Title: A circuit breaking protocol and binary operators
Status: Draft
Type: Standards Track
Created: 2016
Python-Version: 3.8

# Abstract

Inspired by PEP 335, PEP 505, PEP 531 and the related discussions, this PEP proposes a new circuit breaking protocol, using the method names `__then__` and `__else__`, that provides a common semantic foundation for:

- conditional expressions: `LHS if COND else RHS`
- logical conjunction: `LHS and RHS`
- logical disjunction: `LHS or RHS`
- the None-aware operators proposed in PEP 505
- the rich comparison chaining model proposed in PEP 535

Using the new protocol, it further proposes that conditional expressions be generalised so that `if` and `else` can each be used on their own as short-circuiting binary operators:

- right-associative short-circuiting: `LHS if RHS`
- left-associative short-circuiting: `LHS else RHS`

To keep logical inversion (`not EXPR`) consistent with these changes, it also proposes a new `__not__` protocol method, and a new `operator.not_` behaviour that consults it. Finally, it proposes a small standard library module of circuit breaker types that make the None-aware and existence-checking idioms available without new syntax.

# Motivation

Python has several constructs that evaluate one operand, decide something about it, and then either return it or go on to evaluate another operand. `and`, `or` and the conditional expression all fit this description. Today, each of them is hard-wired to call `bool()` on the deciding operand, and that is the only hook a type gets.

Several past proposals have run into this limitation:

- PEP 335 proposed overloading `and` and `or` so that libraries such as NumPy could make `a and b` produce element-wise results.
- PEP 505 proposed new `??`, `?.` and `?[]` operators for short-circuiting on `None`.
- PEP 531 proposed a more general existence-checking protocol.
- PEP 535 proposed letting chained comparisons such as `a < b < c` work element-wise on arrays.

Each of these is in effect asking for a different test than truthiness at the point where Python decides whether to short-circuit. Rather than adding several unrelated special cases to the language, this PEP proposes one protocol that all of them can be built on.

# Specification

## The circuit breaking protocol

A circuit breaker is an object that carries a value and a decision about whether evaluation should short-circuit. It implements:

- `__bool__(self)`: returns the decision. True means "take the `if` branch".
- `__then__(self, result)`: called when the `if` branch is taken, with the value that branch produced (or `self` when short-circuiting). Returns the final value of the expression.
- `__else__(self, result)`: the same, for the `else` branch.

Most circuit breakers will return the wrapped value from whichever method is called when short-circuiting, and the result unchanged otherwise.

## Revised conditional expression

The expression `LHS if COND else RHS` is redefined as follows:

```python
_cb = COND
_type = type(_cb)
if _cb:
    _result = LHS
    if hasattr(_type, "__then__"):
        _result = _type.__then__(_cb, _result)
else:
    _result = RHS
    if hasattr(_type, "__else__"):
        _result = _type.__else__(_cb, _result)
```

For ordinary objects, which define neither method, behaviour is identical to today.

## New binary operators

Two new binary forms are permitted:

- `LHS if RHS` is equivalent to `LHS if RHS else RHS`, except that `RHS` is evaluated only once. It evaluates and returns `LHS` only when `RHS` is truthy; otherwise it short-circuits and returns `RHS`.
- `LHS else RHS` is equivalent to `LHS if LHS else RHS`, except that `LHS` is evaluated only once. It returns `LHS` when it is truthy, and otherwise evaluates and returns `RHS`.

`if` binds right-associatively and `else` left-associatively, consistent with how they nest in the existing conditional expression.

## Redefining `and` and `or`

With these operators, the existing logical operators can be defined in terms of the protocol:

- `LHS or RHS` becomes `LHS else RHS` after passing `LHS` through `operator.true`.
- `LHS and RHS` becomes `LHS if RHS` style evaluation after passing `LHS` through `operator.false`.

Concretely, `operator.true(obj)` returns `obj` unchanged if it is already a circuit breaker, and otherwise wraps it in a breaker that tests `bool(obj)`. `operator.false` does the same but with the decision inverted. A type that wants to control `and` and `or` can therefore do so by returning a circuit breaker from a `__bool__`-like hook, without needing new dunder methods for each operator.

## Logical inversion

A new optional `__not__` method is added. `not EXPR` calls `type(EXPR).__not__(EXPR)` when it exists, and otherwise falls back to `not bool(EXPR)`. Circuit breakers implement `__not__` by returning a breaker with the opposite decision and swapped `__then__` and `__else__` behaviour. This keeps `not (a and b)` and `(not a) or (not b)` consistent for types that participate.

## Standard circuit breakers

A new `types.CircuitBreaker` class is added, with the signature `CircuitBreaker(value, condition)`. Two factory functions in `operator` construct common breakers:

- `operator.is_sentinel(value, sentinel)`: a breaker whose condition is `value is sentinel`.
- `operator.is_not_sentinel(value, sentinel)`: its inverse.

Building on these, the `exists` and `missing` helpers from PEP 531 become ordinary library functions:

```python
from operator import exists, missing

value = missing(x) else default          # x if x is not None else default
attr  = exists(obj) if obj.attr          # obj.attr if obj is not None else None
```

This gives the semantics of PEP 505's None-aware operators without introducing new punctuation.

## Comparison chaining

PEP 535 proposes that `a < b < c` be defined as `(a < b) and (b < c)` using the circuit breaking protocol, so that a rich comparison returning an array-like circuit breaker can control how the chain combines. That change is left to PEP 535, but the protocol defined here is designed to support it.

# Rationale

## Why a protocol rather than new operators?

Each specific operator proposal improves one case while leaving the others unaddressed. A shared protocol allows the language to stay small: the only syntax change is permitting `if` and `else` as binary operators, and every specialised behaviour moves into the library where it can evolve independently.

## Why `if` and `else` as operators?

They read naturally in English: `value else default` and `attr if obj` say what they do. They reuse existing keywords, so no new tokens are reserved, and they line up exactly with the two halves of the conditional expression, which makes the semantics easy to explain.

## Why not just overload `and` and `or`, as in PEP 335?

PEP 335 required two new methods per operator and still did not cover conditional expressions or None-awareness. Building on the conditional expression covers all cases with one pair of methods.

# Backwards Compatibility

The new binary forms are currently syntax errors, so permitting them breaks no existing code. For objects that do not define `__then__`, `__else__` or `__not__`, the behaviour of `and`, `or`, `not` and conditional expressions is unchanged. The added `hasattr` checks are implemented as type slot lookups in CPython and should have negligible cost.

# Risks and Concerns

The proposal adds conceptual weight to constructs that most Python users regard as simple. Code such as `x else y` may surprise readers who have never seen it. The protocol could also be abused to make `and` and `or` do surprising things. These concerns are real, and the main counterargument is that the alternative of adding several narrower features would add more total complexity.
