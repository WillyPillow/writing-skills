# PEP 234: Iterators

| Field | Value |
|---|---|
| PEP | 234 |
| Title | Iterators |
| Status | Final |
| Type | Standards Track |
| Python-Version | 2.2 |

## Abstract

This document proposes an iteration interface that objects can provide to control the behaviour of `for` loops. An object customizes looping by providing a method that produces an iterator object. The iterator offers a single "get next value" operation that returns the next item in the sequence each time it is called and raises an exception when no items remain.

The PEP also proposes specific iterators over the keys of a dictionary and over the lines of a file, and allows `dict.has_key(key)` to be spelled `key in dict`.

This version of the PEP describes the implementation that has been checked into the Python 2.2 development tree. Discussion is still open, and some of the less central details may change before release.

## Motivation

In Python 2.1 and earlier, the `for` statement works by calling `__getitem__` with the integers 0, 1, 2, and so on until the call raises `IndexError`. This protocol was designed for sequences and fits them well. It fits almost everything else poorly.

Consider the objects people actually want to loop over:

- **Dictionaries.** There is no natural integer index. Users write `for k in d.keys():`, which builds a full list of keys just to walk over it once.
- **Files.** Reading lines lazily requires either `readlines()`, which loads the whole file, or the `xreadlines` module, which is a workaround rather than a design.
- **Generated or infinite sequences.** A class that produces values on demand must pretend to support random access, and must keep track of the "index" it is being asked for, even though the only access pattern that will ever occur is sequential.
- **Tree walks, database cursors, network streams.** None of these have meaningful indices.

The workaround for all of these is to write a class whose `__getitem__` ignores its argument and returns the next value. That works, but it is a lie: the object claims to be a sequence when it is not, and code that legitimately indexes it will behave strangely.

What these cases share is that the loop needs exactly one operation: give me the next item, or tell me you are done. This PEP makes that operation the primary iteration protocol and keeps the old `__getitem__` protocol as a fallback.

## Specification

### The iterator protocol

An *iterator* is an object that implements two methods:

- `next()` returns the next value. When there are no more values it raises `StopIteration`. Once it has raised `StopIteration`, every subsequent call should also raise `StopIteration`.
- `__iter__()` returns the iterator itself. This lets an iterator be used wherever an iterable is expected, which is what makes `for x in it:` work when `it` is already an iterator.

An *iterable* is an object that implements `__iter__()` and returns a fresh iterator from it. Containers are iterables; they are generally not iterators themselves, because a container may need to support several independent loops at the same time.

At the C level, type objects gain two new slots: `tp_iter`, corresponding to `__iter__`, and `tp_iternext`, corresponding to `next`. A `tp_iternext` implementation may signal exhaustion by returning `NULL` without setting an exception, which avoids the cost of creating a `StopIteration` instance in the common case.

### The `iter()` built-in

A new built-in function `iter()` is added with two forms.

`iter(obj)` returns an iterator for `obj`. If `obj` defines `__iter__` (or `tp_iter`), that is called. Otherwise, if `obj` supports the sequence protocol via `__getitem__`, a built-in sequence iterator is returned that calls `__getitem__` with 0, 1, 2, ... and translates `IndexError` into `StopIteration`. Otherwise `TypeError` is raised.

`iter(callable, sentinel)` returns an iterator that calls `callable()` with no arguments on each step and stops when the return value equals `sentinel`. This captures a common idiom:

```python
for line in iter(f.readline, ""):
    process(line)
```

### Changes to the `for` statement

The statement

```python
for x in obj:
    body
```

is now defined as equivalent to

```python
_it = iter(obj)
while 1:
    try:
        x = _it.next()
    except StopIteration:
        break
    body
```

with the usual handling of `else`, `break` and `continue`. Because `iter()` falls back to `__getitem__`, every object that worked in a `for` loop before continues to work.

The same change applies everywhere the interpreter consumes a sequence element by element: unpacking assignment, `map()`, `filter()`, `zip()`, `reduce()`, `list()`, `tuple()`, `min()`, `max()`, `"".join()`, the `in` operator when `__contains__` is absent, and `extend()` on lists.

### Dictionary iterators

Dictionaries implement `__iter__` and return an iterator over their keys. So `for k in d:` iterates over keys without building a list.

Three methods return explicit iterators:

- `d.iterkeys()` — same as `iter(d)`
- `d.itervalues()`
- `d.iteritems()` — yields `(key, value)` tuples

Dictionaries also implement `__contains__`, so `key in d` is equivalent to `d.has_key(key)`. `has_key` is not deprecated by this PEP, but `in` becomes the recommended spelling.

Modifying a dictionary's size while iterating over it is not supported. The implementation detects this case and raises `RuntimeError`, rather than silently skipping or repeating keys. Assigning to existing keys is permitted.

### File iterators

File objects implement `__iter__` and return an iterator over their lines, so

```python
for line in f:
    ...
```

reads the file one line at a time with buffering comparable to `xreadlines`. The file object is its own iterator; there is only one read position, so two simultaneous loops over the same file would interfere in the same way two `readline()` loops would.

## Rationale

### Why a separate iterator object?

An alternative design would put a `next()` method directly on containers. That fails as soon as two loops run over the same container, such as a nested loop computing all pairs. Separating the iterable from the iterator gives each loop its own cursor.

### Why `StopIteration` rather than a sentinel return value?

Any value an iterator might return could be a legitimate element, including `None`. An exception is the only signal that cannot collide with data. Exceptions in Python are cheap enough for an event that happens once per loop, and the C-level `NULL`-without-exception shortcut removes even that cost for built-in types.

### Why name it `next()` and not `__next__()`?

This was the most contested point. The argument for `__next__` is consistency: protocol methods called by the interpreter have double-underscore names. The argument for `next` is that iterators are often called directly by user code (`it.next()`), and the method is the iterator's entire public interface rather than a hook. The current implementation uses `next`. If a future version of Python decides that consistency should win, the rename can be handled with a transition period.

### Why should iterators have `__iter__`?

Without it, a function written to accept "anything iterable" would not accept an iterator, and users would have to check which kind of object they had. Requiring `__iter__` to return `self` makes iterators a subset of iterables, which is the relationship people expect.

### Why `key in dict` means key membership

There was argument over whether `x in d` should test keys, values, or items. Keys win because they are what `d[x]` takes, what `has_key` tests, and what iteration over a dictionary now yields. Testing values would be an O(n) operation hidden behind syntax that is O(1) for every other mapping use.

### Restartable iterators

Some people asked for a way to reset an iterator. This PEP does not provide one. Iterators that can be restarted are better modelled as iterables: call `iter()` again. Adding a `reset()` method would force every iterator to remember its starting state, which is impossible for streams.

## Backwards Compatibility

Every object that could be looped over before can still be looped over, because `iter()` falls back to the sequence protocol.

Classes that define `__iter__` for some unrelated purpose will change behaviour. A search of the standard library and several large third-party code bases found no such uses.

Code that relies on `for` calling `__getitem__` with consecutive integers, and that also defines `__iter__`, will now use `__iter__`. This is the intended effect.

Changing a dictionary's size during iteration used to be impossible because `d.keys()` returned a snapshot. Code that writes `for k in d:` and deletes keys inside the loop will get a `RuntimeError`. Such code should continue to use `for k in d.keys():`.

## Open Issues

- Whether `next` should be renamed `__next__`, as discussed above.
- Whether there should be a standard way for an iterator to report its remaining length. A `__len__` on iterators would be misleading for streams, so this is deferred.
- Whether additional built-in types (for example `xrange` objects and string methods that currently return lists) should grow iterator-returning variants.

## Reference Implementation

The implementation is checked into the 2.2 development tree. It includes the new type slots, the `iter()` built-in, the sequence and callable iterator types, dictionary and file iterators, and the conversion of the interpreter's sequence-consuming operations to the new protocol.
