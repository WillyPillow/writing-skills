# Abstract

The Python C-API has no way to specify function signatures, annotations, or custom argument converters and have the boilerplate generated automatically. The problem can be approached in several ways. Cython generates the needed information from *cdef* definitions in *.pyx* files, but CPython's C-API functions often need initialization and cleanup snippets that would be awkward to express in a *cdef*.

PEP 436 proposes a domain-specific language (DSL), embedded in C comments, that looks a lot like a per-parameter configuration file. A preprocessor reads the comment and emits three things: an argument-parsing function, a docstring, and a header for a function that uses the parsed results. That last function is called the *implementation function* below.

This PEP proposes a different DSL for the same job. It is built around a single, compact, Python-like signature line. Each parameter can carry an annotation that names a converter and gives that converter's options inline. The aim is input that is shorter to write, easier to read, and closer to the Python signature that users will eventually see through `inspect`.

# Rationale

Writing argument-parsing code by hand for every C function in CPython is tedious and error-prone. `PyArg_ParseTuple` format strings are terse and hard to read, the docstring signature is maintained separately and drifts out of date, and introspection (`inspect.signature`) cannot see builtins at all because the information lives only in C.

PEP 436 and this PEP agree on the goal: one source of truth per function, from which the parsing code, the docstring, and the introspection metadata are all generated. They differ on how that source of truth should look.

PEP 436's approach puts each parameter in its own indented block of key/value settings. That is very flexible, but a simple function with three positional parameters takes a dozen lines or more, and the result does not look like a Python signature. Contributors must learn a new format that does not resemble anything they already know.

This PEP starts from what the reader expects to see: a Python `def` line. Information that Python itself cannot express, such as the C type, the converter, and default values that only exist in C, is attached through annotations written in a restricted Python syntax. A simple function needs only a line or two, and complex cases use more annotation detail rather than a different syntax.

# Specification

## Overall structure

A DSL block appears inside a C comment immediately before the implementation function. It is delimited by marker lines:

```c
/*[clinic]
os.stat(path: path_t, *, dir_fd: OS_STAT_DIR_FD_CONVERTER = None,
        follow_symlinks: bool = True) -> os.stat_result

Perform a stat system call on the given path.

  path: Path to be examined; can be string, bytes, or open-file-descriptor int.
  dir_fd: If not None, it should be a file descriptor open to a directory,
          and path should be a relative string; path will then be relative to
          that directory.
  follow_symlinks: If False, and the last element of the path is a symbolic
          link, stat will examine the symbolic link itself instead of the
          file the link points to.
[clinic]*/
```

The block has three parts:

1. **The signature line or lines.** A Python-style function header without the `def` keyword and without the trailing colon. It may continue over several lines inside the parentheses.
2. **The function docstring.** Free text that becomes the body of the generated docstring.
3. **Parameter descriptions.** Optional. Each one is an indented line starting with a parameter name and a colon. These are folded into the generated docstring.

## Signature grammar

The signature follows the grammar of a Python 3 `def`, with three restrictions and one extension.

- The function name must be fully qualified (`module.function` or `module.Class.method`).
- Default values must be literals (numbers, strings, `None`, `True`, `False`) or names declared in the converter registry. Arbitrary expressions are not allowed, because they must be translated into C.
- `*` and `/` have their usual meanings: parameters before `/` are positional-only and parameters after `*` are keyword-only. `/` was not legal Python syntax when this PEP was written, but it is accepted here because many builtins need it.
- **Extension:** an annotation may be a *converter expression* instead of a plain Python expression.

## Converter expressions

A converter expression names a converter and optionally passes it keyword arguments:

```
name: str(encoding='utf-8', nullable=True)
buffer: Py_buffer(writable=True)
fd: int(c_type='int', range=(0, None))
```

The converter name is looked up in a registry kept by the preprocessor. Each converter defines:

- the C type of the variable that receives the parsed value;
- the code that converts a `PyObject *` into that C variable;
- any cleanup code that must run after the implementation function returns, such as `PyBuffer_Release`;
- the annotation, if any, to expose through introspection.

Standard converters correspond to the existing `PyArg_ParseTuple` format units (`int`, `str`, `bytes`, `Py_buffer`, `object`, and so on). Extension modules and CPython subsystems can register their own converters in a Python file read by the preprocessor. A converter can be referred to by a short alias such as `path_t` in the example above.

## Return annotations

The return annotation is optional. If present, it is used only for introspection and documentation; the implementation function still returns `PyObject *`. A future extension might allow return converters that turn a C value into a Python object.

## Generated output

For each block, the preprocessor writes the following directly after the comment:

1. A static docstring constant whose first line is the Python signature, so that `inspect` can recover it.
2. A forward declaration of the implementation function, with one C parameter for each Python parameter and with the C types chosen by the converters.
3. A wrapper function with the usual `PyCFunction` signature that parses `args` and `kwargs`, calls the implementation function, runs cleanup code, and returns the result.
4. A `PyMethodDef` entry macro.

The generated region ends with a checksum line. If someone edits the generated code by hand, the preprocessor refuses to overwrite it and reports the mismatch.

## Implementation function

The developer writes only the body of the implementation function:

```c
static PyObject *
os_stat_impl(PyModuleDef *module, path_t *path, int dir_fd, int follow_symlinks)
{
    /* ... */
}
```

The parameter order matches the Python signature. All parsing, type checking, and cleanup are handled by the generated wrapper.

# Comparison with PEP 436

| Aspect | PEP 436 | This PEP |
|---|---|---|
| Parameter syntax | One block per parameter with key/value lines | Inline Python-like annotations |
| Resemblance to Python | Low | High |
| Lines for a 3-parameter function | 10 to 15 | 1 to 3 |
| Complex converters | Natural fit | Expressed as converter keyword arguments |
| Learning curve | New format | Python signatures plus a converter vocabulary |

Both proposals share the generated output and the general preprocessor model. This PEP is therefore a proposal for an alternative *front end*, and a single preprocessor could support both syntaxes during a transition.

# Backwards Compatibility

The DSL lives inside C comments, so code that does not use it is unaffected. Existing functions can be converted one at a time. The generated wrappers behave exactly like hand-written `PyArg_ParseTupleAndKeywords` code, apart from more consistent error messages.

# Reference Implementation

A prototype preprocessor written in Python is available. It parses the signature line with the `ast` module after a small rewrite step that turns `/` into a marker the parser accepts. Converter expressions are parsed as call expressions, and their keyword arguments are evaluated with `ast.literal_eval`.

# Rejected Ideas

**Plain Python annotations only.** Writing `path: "path_t"` and keeping converter options elsewhere would split the information across places again, which is the problem this work set out to solve.

**Reusing Cython syntax.** As the Abstract notes, *cdef* definitions cannot easily express the setup and cleanup code CPython needs, and CPython does not want a dependency on Cython.

**Full Python expressions for defaults.** These cannot be translated reliably into C. Named constants from the converter registry cover the practical cases.

# Open Issues

- How should parameters with *optional groups*, such as `curses.window.addch`, which accepts several unrelated argument patterns, be expressed?
- Should the preprocessor run as part of the build or be invoked manually by developers?
