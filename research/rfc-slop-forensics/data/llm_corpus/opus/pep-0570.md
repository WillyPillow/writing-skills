# Abstract

This PEP proposes to introduce a new syntax, `/`, for specifying positional-only parameters in Python function definitions.

Positional-only parameters have no externally-usable name. When a function accepting positional-only parameters is called, positional arguments are mapped to these parameters based solely on their order.

When designing APIs, library authors try to ensure correct and intended usage of an API. Without the ability to specify which parameters are positional-only, library authors must be careful when choosing appropriate parameter names. This care must be taken even for required parameters or when the parameters have no external semantic meaning for callers of the API.

In this PEP, we discuss:

- Python's history and current semantics for positional-only parameters
- the problems encountered by not having them
- how these problems are handled without language-intrinsic support
- the benefits of having positional-only parameters

# Motivation

## History and current semantics

Positional-only parameters have existed in Python for a long time, but only for functions implemented in C. Many builtins accept arguments only by position:

```python
>>> len(obj=[1, 2, 3])
TypeError: len() takes no keyword arguments
>>> divmod(a=7, b=2)
TypeError: divmod() takes no keyword arguments
```

The C API makes this the natural default: `PyArg_ParseTuple` parses positional arguments and does not know about names at all. Argument Clinic, introduced for CPython 3.4, provides a `/` marker in its docstring-based signature syntax to indicate where positional-only parameters end, and `inspect.signature` reports such parameters with the kind `Parameter.POSITIONAL_ONLY`. The documentation for many builtins already uses `/` in their signatures, for example `divmod(a, b, /)`.

Pure Python functions, by contrast, have no way to declare a positional-only parameter. Every parameter declared before `*` or `*args` may be passed either positionally or by keyword. PEP 3102 added keyword-only parameters in Python 3.0, filling one gap, but the symmetric feature was never provided.

## Problems without positional-only parameters

**Parameter names become part of the public API.** Once a function is published, callers may pass any of its arguments by keyword. Renaming a parameter, even one whose name means nothing to the caller, is a breaking change. A library author who names a parameter `x` in version 1.0 and wants to call it `value` in 2.0 cannot do so without risking breakage.

**Some names have no meaningful public meaning.** In `def is_even(n)`, the name `n` is an implementation detail. Nobody benefits from writing `is_even(n=4)`, and permitting it only constrains the author.

**Collisions with `**kwargs`.** A function that accepts arbitrary keyword arguments cannot also safely use a named positional parameter, because the caller may want to pass a keyword argument with the same name:

```python
def format_template(template, **fields):
    ...

format_template("{template} {name}", template="x", name="y")
# TypeError: got multiple values for argument 'template'
```

This problem appears throughout the standard library, in functions such as `dict.update`, `str.format`, `collections.namedtuple` factories and `functools.partial`.

**Pure Python and C implementations disagree.** Several modules have both a C accelerator and a pure Python fallback, such as `heapq`, `bisect`, `datetime` and `decimal`. The C version is positional-only; the Python version accepts keywords. Code that works against one may break against the other, and PyPy, which uses the Python versions, behaves differently from CPython.

## Current workarounds

Library authors who need positional-only behaviour today use one of several techniques, each with drawbacks.

They may accept `*args` and unpack manually:

```python
def is_even(*args):
    if len(args) != 1:
        raise TypeError(...)
    (n,) = args
    return n % 2 == 0
```

This loses the signature in `help()` and `inspect`, requires boilerplate error handling, and is slower.

They may use names that callers are unlikely to guess, such as `__n` or `_positional_only_n`. This is a convention, not a guarantee, and it uglifies documentation.

They may simply document that a parameter should not be passed by keyword. Callers ignore documentation.

# Rationale

Providing positional-only parameters in pure Python:

- Lets library authors change parameter names without breaking callers.
- Allows `**kwargs` to accept any keyword without collision.
- Lets pure Python implementations exactly match their C counterparts.
- Makes the signatures already shown in documentation and `inspect` expressible in Python source code.
- Can give a modest performance improvement, because the interpreter need not consult names when binding positional-only arguments.

The `/` syntax is chosen because it is already established: Argument Clinic uses it, `inspect.Signature.__str__` produces it, and the documentation for builtins displays it. Users who have seen `divmod(a, b, /)` will recognize it. It also parallels the existing bare `*` marker for keyword-only parameters, with `/` closing a section on the left as `*` opens one on the right.

# Specification

## Syntax

A `/` in a parameter list marks the end of the positional-only parameters. Parameters before the `/` are positional-only. Parameters after the `/` and before any `*` or `*args` are positional-or-keyword. Parameters after `*` or `*args` are keyword-only.

The general form is:

```python
def name(positional_only_parameters, /, positional_or_keyword_parameters,
         *, keyword_only_parameters):
```

All of the following are valid:

```python
def f(a, b, /, c, d, *, e, f): ...
def f(a, b, /, c, d): ...
def f(a, b, /): ...
def f(a, b=None, /, c=None): ...
def f(a, /, *args, **kwargs): ...
```

The following are invalid:

```python
def f(/, a): ...          # / must follow at least one parameter
def f(a, /, b, /): ...    # only one /
def f(*args, /, a): ...   # / must precede * and *args
def f(a=1, /, b): ...     # non-default follows default, as today
```

The rules about defaults are unchanged: once a parameter has a default, all subsequent positional parameters, whether positional-only or positional-or-keyword, must also have defaults.

The same syntax is accepted in `lambda` expressions:

```python
lambda x, /, y: x + y
```

## Semantics

When a function is called, positional arguments are bound to positional-only parameters first, in order. A keyword argument whose name matches a positional-only parameter is not bound to that parameter. If the function accepts `**kwargs`, such a keyword argument is placed in the `kwargs` dictionary; otherwise, a `TypeError` is raised.

```python
def f(a, /, **kwargs):
    return a, kwargs

f(1, a=2)  # returns (1, {'a': 2})
```

## Introspection

`inspect.signature` reports positional-only parameters with `Parameter.POSITIONAL_ONLY`, as it already does for C functions. Code objects gain a new attribute, `co_posonlyargcount`, giving the number of positional-only parameters. `co_argcount` continues to count all positional parameters, including positional-only ones, so that existing tools that use it remain correct.

# Backwards Compatibility

The syntax is new and was previously a `SyntaxError`, so no existing code changes meaning.

Tools that analyse code objects directly may need updating to account for `co_posonlyargcount`. Tools that construct code objects with `types.CodeType` will need to pass the new argument.

# How to Teach This

A function's parameter list can be read as having up to three sections, separated by `/` and `*`:

```
def f(pos_only, /, standard, *, kw_only):
```

Guidance for authors:

- Use positional-only parameters when the name has no meaning to callers, when the order is the natural way to call the function, or when the function also accepts `**kwargs`.
- Use keyword-only parameters when the name conveys meaning that would be lost positionally, such as boolean flags.
- Use the default positional-or-keyword form otherwise.

# Rejected Ideas

**Do nothing.** The problems above persist.

**Decorators**, such as `@positional_only("a", "b")`. These cannot be checked at compile time, add call overhead, and are not visible in the function's syntax.

**Per-parameter markers**, such as prefixing names with a double underscore, which an earlier PEP proposed. This conflates naming with calling convention and is easily mistaken for name mangling.

**Using a different symbol**, such as `;` or `@`. The `/` notation is already in use in documentation and introspection.
