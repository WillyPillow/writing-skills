Title: General purpose decorator clause (aka "@in" clause)
Author: (draft)
Status: Deferred
Type: Standards Track
Created: 13-Oct-2011
Python-Version: 3.4

# Abstract

This PEP proposes the addition of a new `@in` decorator clause that makes it possible to override the name binding step of a function or class definition.

The new clause accepts a single simple statement that can make a forward reference to the decorated function or class definition.

This new clause is designed to be used whenever a "one-shot" function or class is needed, and placing the function or class definition before the statement that uses it actually makes the code harder to read. It also avoids any name shadowing concerns by making sure the new name is visible only to the statement in the `@in` clause.

This PEP is based heavily on many of the ideas in PEP 3150 (Statement Local Namespaces), so some elements of the rationale will be familiar to readers of that PEP. Both PEPs remain deferred for the time being, primarily due to the lack of compelling real-world use cases in either PEP.

# Basic Examples

Before diving into the rationale, here are a few examples.

A sorting key that is too complex for a lambda:

```python
@in sorted_list = sorted(original, key=f)
def f(item):
    try:
        return item.calc_sort_order()
    except NotSortableError:
        return float('inf')
```

A callback registered with an event system:

```python
@in button.on_click(handler)
def handler(event):
    log.info("Clicked at %s", event.position)
    controller.advance()
```

A one-off class whose instance is all that is needed:

```python
@in _default_config = Config()
class Config:
    host = "localhost"
    port = 8080
```

In each case, the statement after `@in` is executed with the name of the function or class bound to the newly created object. Unlike an ordinary `def`, the name is *not* bound in the containing scope; it exists only for the duration of the `@in` statement.

# Proposal

This PEP proposes the addition of an optional `@in` clause preceding a function or class definition, alongside and before any ordinary decorators:

```python
@in <simple_statement>
@decorator1
@decorator2
def name(...):
    ...
```

The semantics are as follows:

1. The function (or class) is created, and the ordinary decorators are applied, exactly as today.
2. Instead of binding the result to `name` in the current scope, the interpreter creates a new, hidden scope in which `name` refers to the result.
3. The simple statement in the `@in` clause is executed in that hidden scope. Names it references, other than `name`, are resolved in the containing scope as normal. Names it binds are bound in the containing scope.
4. The hidden scope is discarded. `name` is not visible afterwards.

Roughly, then:

```python
@in target = f(name)
def name():
    ...
```

behaves like:

```python
def _hidden():
    def name():
        ...
    return f(name)
target = _hidden()
```

except that assignment, augmented assignment, `return`, `yield`, `raise`, and the other simple statements behave as if written directly in the containing scope rather than in a nested function. In particular, `return` inside an `@in` clause returns from the enclosing function, and assignments bind in the enclosing scope.

## Grammar

```
decorated: in_clause? decorators? (classdef | funcdef)
in_clause: '@' 'in' simple_stmt
```

`in` is already a keyword, so no new keyword is required. The clause must appear before any ordinary decorators, and there may be at most one.

## Restrictions

The `@in` clause may contain only a single simple statement. Compound statements (`if`, `for`, `while`, `try`, `with`, `def`, `class`) are not allowed. This keeps the clause readable on one line and avoids the scoping complexity that sank more ambitious proposals.

A `nonlocal` or `global` statement in the clause is a syntax error, since it would affect the hidden scope in confusing ways.

# Rationale

Python's `lambda` is deliberately limited to a single expression. This is a good default: it keeps simple callbacks simple. When something more complex is needed, Python asks the programmer to write a named function with `def`. The trouble is that `def` must come *before* the statement that uses it, which inverts the natural reading order:

```python
def f(item):
    try:
        return item.calc_sort_order()
    except NotSortableError:
        return float('inf')

sorted_list = sorted(original, key=f)
```

A reader encounters the helper before learning why it exists. In code with several such helpers, it becomes hard to tell which helper serves which statement. The `@in` clause puts the purpose first and the details second, which matches how the code is described in prose: "sort the list, using this key".

Decorators already provide precedent for this ordering. A decorator line is written before the function, executed after it is defined, and receives the function as an argument. The `@in` clause generalizes that pattern from "call this with the function" to "run this statement with the function available by name".

## Name shadowing

The helper name is often throwaway: `f`, `key`, `handler`, `cb`. Defining it with `def` leaks it into the enclosing scope, where it may shadow a module-level name or be accidentally reused later. In a loop, the leaked name is rebound each iteration, a classic source of closure bugs. Making the name visible only to the `@in` statement eliminates this class of problem.

## Relationship to PEP 3150

PEP 3150 proposed a trailing `given` clause that introduced an arbitrary block of statements as a local namespace for a single preceding statement. That proposal was more powerful but raised difficult questions about scoping, about what statements were allowed in the block, and about how the result interacted with class bodies and comprehensions.

This PEP takes a smaller step: it allows exactly one function or class to be referenced by exactly one statement. Most of the motivating cases for PEP 3150 involve a single helper function, and those are handled cleanly here.

# Discussion

## Why the `@` prefix?

Using the decorator syntax signals visually that the line modifies the following definition. It reuses a familiar position in the code and requires no new indentation level.

## Why not just improve `lambda`?

Multi-line lambdas have been proposed repeatedly and rejected because Python's indentation-based syntax makes embedding statement blocks inside expressions awkward. The `@in` clause avoids that by keeping the function as a normal statement-level `def`.

## Is the forward reference confusing?

The `@in` statement names something that has not been defined yet when read top to bottom. However, this is already true for decorators, and experience suggests readers adjust quickly. The `@in` marker makes the forward reference explicit.

## Debugging and introspection

The function retains its `__name__` and `__qualname__`, so tracebacks are as informative as for an ordinary `def`. Its `__qualname__` includes a `<in>` marker to indicate it was defined in an `@in` clause.

# Rejected Ideas

**Allowing compound statements in the clause.** This reintroduces most of the complexity of PEP 3150.

**Using an anonymous placeholder, such as `?`, instead of the name.** This would avoid naming the function at all, but makes tracebacks less useful and introduces a new token for a single purpose.

**Binding the name in the containing scope as well.** This defeats the shadowing protection that is one of the main benefits.

# Deferral

This PEP is deferred. While the syntax is appealing in toy examples, it has proven difficult to find real-world code that becomes clearly better, rather than merely different, when rewritten with `@in`. The proposal may be revisited if compelling use cases emerge.
