# PEP 3153: Asynchronous IO support

| Field | Value |
|---|---|
| PEP | 3153 |
| Title | Asynchronous IO support |
| Status | Draft |
| Type | Standards Track |
| Created | 29-May-2011 |

## Abstract

This PEP describes an abstraction of asynchronous IO for the Python standard library. The goal is an abstraction that many different asynchronous IO backends can implement, and that gives library developers a target for writing code portable across those backends.

## Rationale

Python has several mature frameworks for asynchronous network programming: Twisted, Tornado, gevent, eventlet, and the venerable `asyncore` in the standard library. Each has its own event loop, its own way of representing connections, and its own way of signalling that data has arrived or that an operation has finished.

This fragmentation has a real cost. Someone who writes a protocol implementation, for example a Redis client or an HTTP/1.1 parser, must choose one framework and write against its API. If they want the same code to work elsewhere they must write adapters or maintain several copies. Users choosing a framework are partly choosing which protocol libraries they can use.

Most of the differences between frameworks are not essential. Every one of them has something that waits for readiness or completion events from the operating system, something that represents a byte stream, and something that turns bytes into higher-level messages. The differences are in names and in how these pieces are connected.

`asyncore` was the standard library's attempt to provide this. It has not aged well. It mixes the transport (a socket) with the protocol (the subclass's `handle_read` method), it only supports `select`-style readiness, and it gives no good way to build layered protocols such as TLS on top of TCP. It is not a sound foundation to build on.

This PEP proposes a small set of interfaces that separate these concerns so that protocol code can be written once.

## Communication abstractions

### Transports

A **transport** is responsible for moving bytes between two endpoints. It knows how to send and receive data, but nothing about what the data means. Examples:

- a TCP connection
- a UNIX domain socket
- a pipe to a subprocess
- an SSL/TLS connection, which is itself layered on another transport
- an in-memory pair, useful for testing

A transport exposes a small interface:

- `write(data)`: queue bytes to be sent. Must not block. The transport is responsible for buffering.
- `writelines(iterable)`: convenience for writing a sequence of byte strings.
- `close()`: close the transport after any buffered data has been flushed.
- `abort()`: close immediately, discarding buffered data.
- `pause_reading()` / `resume_reading()`: stop and restart delivery of incoming data, for flow control.
- `get_extra_info(name)`: retrieve transport-specific details such as the peer address or the SSL certificate.

The transport does not have a `read` method. Data is pushed to the protocol when it arrives.

### Protocols

A **protocol** turns a byte stream into meaningful events and back. It receives callbacks from its transport:

- `connection_made(transport)`: the transport is ready. The protocol stores a reference to it.
- `data_received(data)`: some bytes have arrived. The protocol must not assume that data arrives in message-sized chunks; it may get half a message, or several messages at once.
- `eof_received()`: the other side will send no more data.
- `connection_lost(exc)`: the transport has closed, with `exc` set to `None` for a clean close or an exception describing what went wrong.

Protocols write by calling `self.transport.write(...)`.

The crucial property is that a protocol depends only on this interface. An HTTP protocol implementation works the same whether its transport is TCP, TLS, or an in-memory buffer used in a unit test. A TLS implementation can be both a protocol (for the underlying TCP transport) and a transport (for the HTTP protocol above it).

### Producers and consumers

For bulk data, such as streaming a large file, a protocol should not write everything at once and fill memory. The **producer/consumer** pattern addresses this. A consumer (typically a transport) can tell a producer to pause when its buffer passes a high-water mark and to resume when it drains below a low-water mark. Producers implement `pause_producing()`, `resume_producing()` and `stop_producing()`.

## Flow control and error handling

Writes never block, so flow control must be explicit. Transports buffer outgoing data and notify the attached protocol (or registered producer) when the buffer grows too large. Incoming flow control is handled by `pause_reading()`.

Errors are reported to the protocol through `connection_lost()`. Exceptions raised by protocol callbacks are caught by the event loop, logged, and cause the transport to be closed; they must not crash the whole loop.

## Event loops

This PEP deliberately does not prescribe a single event loop implementation. The point is that existing frameworks can implement transports and drive protocols with their own loops. A compliant backend must:

- call protocol callbacks from a single thread at a time, so protocols do not need locking;
- never call a protocol method re-entrantly from within `transport.write()`;
- deliver callbacks in an order consistent with the events on the wire.

A reference event loop for the standard library, providing at least `select`, `poll`, `epoll` and `kqueue` backends on POSIX and an IOCP-based backend on Windows, is a natural follow-up, but should be specified in a separate PEP. Interfaces for scheduling timed calls (`call_later`) and for creating connections and servers belong there too.

## Higher-level interfaces

### Callbacks and futures

Callback-based code becomes hard to read as soon as operations are chained. A future or deferred object representing "a result that will be available later" lets code attach success and error handlers and compose operations. `concurrent.futures.Future` (PEP 3148) already exists in the standard library. Its interface (`add_done_callback`, `result`, `exception`) is a reasonable model, but its blocking `result()` is inappropriate inside an event loop. An event-loop-friendly future with the same method names is proposed for the follow-up PEP.

### Generators as coroutines

With PEP 380 (`yield from`), generators can be used to write asynchronous code in a sequential style, where each `yield from` suspends until a future completes. This is attractive, but it is a layer above transports and protocols. Protocols as defined here work with plain callbacks, with futures, or with coroutines built on top.

## Relationship to existing frameworks

The transport/protocol split is borrowed directly from Twisted, which has used it successfully for over a decade. Tornado's `IOStream` corresponds roughly to a transport with a buffered read API layered on top. Adapting existing frameworks should mostly be a matter of wrapping their connection objects as transports.

Frameworks based on greenlets (gevent, eventlet) take a different approach, presenting blocking-style APIs while switching implicitly. They can still benefit: a protocol written against this PEP can be driven by a greenlet-based loop, and a blocking-style API can be layered on top of a protocol.

## Backwards compatibility

This PEP adds new interfaces and does not change existing modules. `asyncore` and `asynchat` remain available. They may be deprecated once a standard event loop exists, but that is a separate decision.

## Open issues

- Exact names: `data_received` vs. `dataReceived`, following PEP 8 rather than Twisted.
- Whether datagram transports (UDP) share the same interface or have their own, with `datagram_received(data, addr)`.
- Whether the abstract base classes should live in a new package (`async`, `concurrency`) or be added to an existing module.
