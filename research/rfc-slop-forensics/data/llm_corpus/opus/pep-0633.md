# Abstract

This PEP specifies how to write a project's dependencies in a `pyproject.toml` file, for packaging tools to consume, using the `dependencies` and `optional-dependencies` fields defined in PEP 621. It is an alternative to PEP 631, which writes each dependency as a single PEP 508 string. Here, each dependency is a TOML table (or a short string for the simplest case) whose keys spell out the parts of the requirement: version, extras, markers, and an optional direct URL or VCS reference.

# Motivation

PEP 621 standardizes most of a project's core metadata in `pyproject.toml`, but it left the format of the dependency fields to a follow-up PEP. Two formats were proposed. PEP 631 reuses PEP 508 strings:

```toml
dependencies = [
    "requests[security,socks] >= 2.24, < 3; python_version >= '3.6'",
]
```

PEP 508 strings are compact and every tool already parses them. They also have problems when they appear in a hand-edited configuration file.

- **They pack a small language into a string.** Names, extras, version specifiers, URLs and environment markers all share one line with their own punctuation. Users get the syntax wrong, and TOML cannot catch the mistakes, because to TOML it is all one string.
- **Quoting gets awkward.** Markers use quoted string literals, so the TOML string has to use the other quote style or escape them.
- **Tools cannot edit them cleanly.** A tool that wants to add a marker or bump a version has to parse the string, change it and re-serialize it, which loses the user's formatting.
- **They are inconsistent with the rest of the file.** Everything else in `pyproject.toml` is structured TOML. Dependencies would be the one place where structure is hidden inside a string.

Tools that already put dependencies in `pyproject.toml`, notably Poetry and Flit, use tables rather than strings, and their users are familiar with that style. Standardizing on a table format makes it easier for those tools to adopt PEP 621.

# Rationale

The format is designed around three goals.

1. **The common case stays short.** Most dependencies are just a name and a version range. That should take one line.
2. **Every field has a key.** Anything more complex than a version range is written as a separate key, so it can be validated by TOML-aware editors and changed by tools without reparsing.
3. **Nothing is lost.** Every requirement expressible in PEP 508 can be expressed in this format, so tools can convert in both directions.

Dependencies are keyed by name rather than listed in an array. A name can appear only once per table, which removes a class of mistakes where the same package appears twice with conflicting constraints. When different constraints are needed under different markers, an array of tables is allowed for that one name.

# Specification

## The dependencies table

`[project.dependencies]` is a TOML table. Each key is a distribution name, normalized according to PEP 503 for comparison. Each value is one of:

- a **string**, which is a version specifier as defined by PEP 440 (for example `">= 2.24, < 3"`). The empty string means any version.
- a **table** with the keys listed below.
- an **array of tables**, each with the keys listed below, for requirements that differ by environment.

```toml
[project.dependencies]
attrs = ""
requests = ">= 2.24, < 3"
pywin32 = { version = ">= 300", for = "sys_platform == 'win32'" }
```

## Requirement keys

`version` (string)
: A PEP 440 version specifier. Omitted means any version.

`extras` (array of strings)
: Extras of the dependency to install.

`markers` (string)
: A PEP 508 environment marker expression. The requirement applies only when it evaluates to true.

`for` (string)
: An alias for `markers`, provided because it reads naturally. Specifying both is an error.

`url` (string)
: A direct reference URL to a distribution file.

`git`, `hg`, `bzr`, `svn` (string)
: A VCS repository URL. At most one may be present.

`revision` (string)
: Only valid with a VCS key. A commit, tag or branch to check out.

`version` and `url`/VCS keys are mutually exclusive, because PEP 508 does not allow a requirement to have both a specifier and a direct reference.

Unknown keys are an error. Tools must not silently ignore them, so that typos such as `extra` for `extras` are caught.

## Optional dependencies

`[project.optional-dependencies]` is a table whose keys are extra names. Each value is a dependencies table in the same format as above:

```toml
[project.optional-dependencies.socks]
pysocks = ">= 1.5.6, != 1.5.7"

[project.optional-dependencies.tests]
pytest = ">= 6"
pytest-cov = ""
```

## Multiple requirements for one name

```toml
[[project.dependencies.numpy]]
version = ">= 1.19"
for = "python_version >= '3.7'"

[[project.dependencies.numpy]]
version = ">= 1.16, < 1.19"
for = "python_version < '3.7'"
```

Each table produces a separate `Requires-Dist` entry.

## Conversion to core metadata

Each requirement maps to one `Requires-Dist` line. The tool joins the name, the extras in brackets, then either the version specifier or ` @ ` and the URL, then `; ` and the marker if present. For VCS keys, the URL is written as `<vcs>+<url>` with `@<revision>` appended when a revision is given. For optional dependencies, the marker `extra == '<name>'` is combined with any existing marker using `and`, with the existing marker parenthesized.

# Examples

The PEP 631 example from the Motivation becomes:

```toml
[project.dependencies]
requests = { version = ">= 2.24, < 3", extras = ["security", "socks"], for = "python_version >= '3.6'" }
```

or, spread over several lines:

```toml
[project.dependencies.requests]
version = ">= 2.24, < 3"
extras = ["security", "socks"]
for = "python_version >= '3.6'"
```

A VCS dependency:

```toml
[project.dependencies]
mylib = { git = "https://example.com/mylib.git", revision = "v1.2.0" }
```

# Backwards Compatibility

There are no existing tools that read these fields, since PEP 621 is new. Tools that already use a table format, such as Poetry, use different key names and will need a migration path, but the shapes are close enough that the conversion is mechanical.

# Security Implications

None beyond those of PEP 508 and PEP 621. Direct URLs and VCS references have the same risks they have today.

# Rejected Ideas

**An array of tables for all dependencies.** This allows duplicates and makes simple cases longer. It was rejected in favor of keying by name.

**Allowing a full PEP 508 string as a value.** Accepting both forms would make every tool support two formats and would make files inconsistent. It was rejected.

**Separate keys for each marker variable**, such as `python` or `platform`. This would cover most real markers in a friendlier way but cannot express `or` or nested conditions, and would create two ways to write the same thing.

# Open Issues

- Whether `for` should be kept as an alias, or whether only `markers` should exist.
- Whether the empty string or `"*"` should denote "any version".
