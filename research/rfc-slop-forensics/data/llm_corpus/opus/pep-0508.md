# PEP 508: Dependency specification for Python Software Packages

| Field | Value |
|---|---|
| PEP | 508 |
| Title | Dependency specification for Python Software Packages |
| Status | Draft |
| Type | Standards Track |
| Topic | Packaging |

## Abstract

This PEP specifies the language used to describe dependencies for Python packages. It deliberately stops at the description of a single dependency. Questions about the different kinds of dependencies, such as build-time, run-time, test, or optional extras, and about when each should be installed, belong to higher-level specifications. The intent is to provide a building block that those specifications can share.

A dependency exists so that a tool such as pip can find the right thing to install. Sometimes the description is loose, just a project name. Sometimes it is very specific, naming an exact file. Sometimes a dependency only applies on one platform, or only some versions are acceptable. The language defined here can express all of these. It is a compact, line-based format that is already widely used in requirements files and in setuptools metadata, though until now it has not been written down in one place.

## Motivation

Python packaging tools have accumulated several overlapping ways of writing a dependency. `install_requires` in setuptools accepts one form. pip's requirements files accept a superset of it, with extra options. PEP 345 defines `Requires-Dist` metadata with environment markers. PEP 426 proposed a JSON format with yet another structure. Most of these agree on the common cases, such as `requests >= 2.8.1`, but they disagree in the corners: whitespace rules, which characters are allowed in names, how markers are combined, and how URLs are written.

Those disagreements cause real bugs. A dependency that one tool accepts is rejected by another, or parsed differently. Authors of new tools, such as alternative installers and build backends, have to reverse-engineer pip and setuptools to know what to accept.

Writing down one grammar, compatible with what tools already accept in practice, lets everyone parse dependencies the same way. Later PEPs can then refer to this one instead of defining their own syntax.

## Specification

### Examples

```
requests
requests [security,tests] >= 2.8.1, == 2.8.*
pip @ https://github.com/pypa/pip/archive/1.3.1.zip#sha1=da9234ee9982d4bbb3c72346a6de940a148ea686
name; python_version < "3.8"
name [fred,bar] @ http://foo.com ; python_version == "2.7"
```

### Concepts

A dependency specification has:

- A **name**, which identifies a distribution.
- Optional **extras**, which request optional features of that distribution.
- Optionally, **either** a set of **version specifiers** **or** a **URL** pointing at a specific artifact.
- An optional **environment marker**, which limits when the dependency applies.

### Names

Names follow the rules for distribution names: ASCII letters and digits, with `.`, `-`, and `_` allowed in the interior. A name must start and end with a letter or digit. Comparison of names is case-insensitive and treats runs of `.`, `-`, and `_` as equivalent, as specified elsewhere. This grammar does not normalize names itself; it only defines what is valid.

### Extras

Extras are a comma-separated list of names in square brackets following the distribution name. An extra pulls in the additional dependencies that the distribution declares under that name. Requesting an extra that the distribution does not define is not an error; installers should ignore it, perhaps with a warning.

### Versions

Version specifiers follow PEP 440: a comma-separated list of clauses such as `>= 1.0`, `!= 1.3.4`, `~= 2.2`, or `== 1.4.*`. Clauses may optionally be wrapped in parentheses, for compatibility with the syntax used in PEP 345 metadata. A dependency with no specifier accepts any version.

### URLs

A URL is introduced with `@`. It is interpreted according to RFC 3986. Tools may support only certain schemes; at minimum, `https` should be supported. A fragment may carry a hash in the form `#<algorithm>=<value>`, which installers should verify.

A dependency may have version specifiers or a URL, but not both. A URL already identifies a specific artifact, and a version constraint on it would be either redundant or contradictory.

If a URL is followed by an environment marker, there must be whitespace between the URL and the `;`. Otherwise the `;` would be valid as part of the URL.

### Environment markers

A marker is an expression after `;` that evaluates to true or false against the environment in which installation happens. If false, the dependency is ignored.

Markers compare a variable with a string, or two strings, using the PEP 440 version comparison operators, `in`, `not in`, `==`, and `!=`. Expressions are combined with `and` and `or`, with `and` binding more tightly, and may be parenthesized. Strings use either single or double quotes.

The marker variables are:

| Variable | Python equivalent | Example |
|---|---|---|
| `os_name` | `os.name` | `posix` |
| `sys_platform` | `sys.platform` | `linux`, `win32` |
| `platform_machine` | `platform.machine()` | `x86_64` |
| `platform_python_implementation` | `platform.python_implementation()` | `CPython` |
| `platform_release` | `platform.release()` | `5.10.0` |
| `platform_system` | `platform.system()` | `Linux` |
| `platform_version` | `platform.version()` | (free-form) |
| `python_version` | `'.'.join(platform.python_version_tuple()[:2])` | `3.4` |
| `python_full_version` | `platform.python_version()` | `3.4.0` |
| `implementation_name` | `sys.implementation.name` | `cpython` |
| `implementation_version` | derived from `sys.implementation.version` | `3.4.0` |
| `extra` | set by the tool evaluating the marker | `test` |

When both sides of a comparison are valid PEP 440 versions and the operator is a version operator, comparison uses PEP 440 semantics. Otherwise it falls back to Python string comparison. Comparing with an operator that has no meaning for strings, such as `<` between two non-version strings, is an error, and tools should report it rather than guess.

The `extra` variable has no value in a general environment. It is only defined when a tool evaluates the dependencies of a particular extra. Using it outside that context is an error.

### Whitespace

Whitespace between tokens is optional except where noted, and is never significant. Comments, line continuations, and options such as `-e` or `--index-url` are not part of this grammar. Requirements-file syntax is built on top of it.

### Grammar

The complete grammar is given in Parsley notation in the reference implementation. In summary:

```
specification = wsp* ( url_req | name_req ) wsp*
name_req      = name wsp* extras? wsp* versionspec? wsp* quoted_marker?
url_req       = name wsp* extras? wsp* urlspec wsp+ quoted_marker?
quoted_marker = ';' wsp* marker
```

## Backwards Compatibility

Most dependencies accepted by existing tools are valid under this grammar, and they mean the same thing. Some edge cases change:

- PEP 345 allowed version specifiers only in parentheses; this PEP accepts both forms.
- Some tools allowed markers to compare two variables. This PEP permits it.
- The `@` URL form is new as a standardized syntax, though pip supported a similar form through `#egg=` fragments. That fragment form is not part of this specification.

## Rationale

The grammar was chosen to match what was already in use rather than to design something new. A new syntax would have offered little and required every requirements file in existence to be rewritten.

Names, versions, and extras use existing definitions so this PEP does not duplicate them.

## Reference Implementation

A reference parser is provided by the `packaging` library, with a Parsley grammar used as the normative source for testing.
