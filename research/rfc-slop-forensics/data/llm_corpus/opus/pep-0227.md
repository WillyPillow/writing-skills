# Abstract

This PEP adds statically nested scoping, also called lexical scoping, to Python. The feature is enabled by default in Python 2.2 and is available in Python 2.1 through a future statement. Python 2.1 also warns about code whose meaning would change once the feature is on.

Python 2.0 and earlier resolve names in exactly three namespaces: local, global and built-in. With nested scopes, a name that is not bound in the local scope is also looked up in the scopes of any enclosing functions. The most visible effect is that lambdas and other nested functions can refer to variables of the function they are defined in. Today such functions must use default arguments to copy those values into their own namespace.

# Motivation

Consider a function that builds a list of callbacks:

```python
def make_adders(n):
    return [lambda x: x + i for i in range(n)]
```

Under the current rules, `i` inside the lambda is looked up in the lambda's locals, then in the module's globals, then in built-ins. It is not found, so calling any of the adders raises `NameError`. The established workaround is to use a default argument:

```python
def make_scaler(factor):
    return lambda x, factor=factor: x * factor
```

This idiom works, but it has costs.

- It is confusing to newcomers, who expect the lambda to "see" `factor` because it is written right there.
- It changes the function's signature. A caller can pass a second argument and silently override `factor`.
- It is easy to forget. Code that forgets it may still run, if a global with the same name happens to exist, and then do the wrong thing.

Most other languages with nested functions, including Scheme, ML, Pascal and JavaScript, resolve names lexically. Python's three-scope rule was a deliberate simplification, but nested functions and lambdas are now common enough, especially in GUI callbacks and functional-style code, that the simplification has become a hazard.

# Specification

Python is a statically scoped language with block structure, in the tradition of Algol. A code block is a module, a class definition or a function body. Each block introduces a new namespace.

## Name resolution

If a name is bound anywhere in a function body, by assignment, `def`, `class`, `import`, a `for` target or a function parameter, it is local to that function, unless it is declared `global`.

If a name is used in a function but not bound there, the compiler looks for a binding in the nearest enclosing function scope. If one is found, the name refers to that binding. If none is found, the name is global, resolved at runtime in the module namespace and then in built-ins, exactly as today.

Class scopes are skipped during this search. Names bound in a class body are not visible to methods defined in that class. This keeps the existing rule that methods access class attributes through `self` or the class name, and avoids making every method implicitly depend on the class namespace.

```python
def outer():
    x = 1
    class C:
        x = 2
        def method(self):
            return x       # refers to outer's x, which is 1
    return C().method()
```

## Binding and the global statement

A `global` declaration in a function applies only to that function. It does not affect enclosing or nested functions. If a nested function refers to a name that an outer function declares `global`, the nested function sees the global binding, because the outer function has no local binding of that name.

This PEP does not provide a way to rebind a name in an enclosing scope. Assigning to a name in a nested function makes it local to the nested function, as today. Code that needs to mutate shared state can use a mutable container, such as a list or an object attribute. A syntax for rebinding outer names may be proposed separately.

## Restrictions

Two constructs make static resolution impossible, because they can add names to a function's namespace at runtime:

- `from module import *` inside a function.
- A bare `exec` statement inside a function, without an explicit namespace argument.

If either appears in a function that contains nested functions with free variables, or in a nested function itself, the compiler raises `SyntaxError`. Both constructs are already discouraged inside functions, and the error can always be avoided by importing names explicitly or passing a dictionary to `exec`.

## Interaction with locals() and vars()

`locals()` in a nested function returns its local bindings and also the free variables it uses from enclosing scopes. Variables from enclosing scopes that the nested function does not use are not included.

# Compatibility and transition

Some code that is valid today will change meaning. The typical case is a nested function that refers to a name intended as a global, while an enclosing function happens to bind the same name locally:

```python
x = 'global'

def f():
    x = 'local'
    def g():
        return x
    return g()
```

Today `f()` returns `'global'`. With nested scopes it returns `'local'`. Code like this is rare and usually a latent bug, but it exists.

To give users time to find such code, the change is introduced in two steps.

1. **Python 2.1.** Nested scopes are off by default. A module can enable them with `from __future__ import nested_scopes`. Without that line, the compiler issues a `SyntaxWarning` for any name whose resolution would differ under the new rules, and for any use of `import *` or bare `exec` that would become an error.

2. **Python 2.2.** Nested scopes are always on. The future statement is accepted and ignored.

# Implementation

The compiler already computes which names are local to each function. The change extends this pass with a symbol table that records, for each block, the names it binds, the names it uses and the names it declares `global`. A second pass determines, for each free name in a nested function, whether an enclosing function binds it.

Variables that are referenced from a nested scope are stored in *cells*, small heap objects that hold one reference. The enclosing function accesses them through new opcodes `LOAD_DEREF` and `STORE_DEREF`. When a nested function is created, the cells it needs are bundled into a tuple and stored on the function object as its closure. The nested function also uses `LOAD_DEREF` to reach them.

Names that are not used by any nested function keep using the fast local-variable slots, so code without nested functions has no new overhead. Code with nested functions pays one extra indirection on access to shared variables.

Cells also solve the lifetime problem. An enclosing function's frame can be released when it returns, while the cells it shares survive as long as any closure refers to them.

# Rejected alternatives

**Dynamic scoping**, in which a nested function sees the bindings of whoever called it, was rejected. It makes behavior depend on the call path and defeats local reasoning.

**Copying values at definition time**, which is what the default-argument idiom does, was rejected as the official semantics. It would make closures see stale values if the outer variable changes after the inner function is defined, which differs from every other lexically scoped language.

**Including class scopes** in the search was rejected for the reason given above.
