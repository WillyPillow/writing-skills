# PEP 618: Add Optional Length-Checking To zip

| Field | Value |
|---|---|
| PEP | 618 |
| Title | Add Optional Length-Checking To zip |
| Status | Draft |
| Type | Standards Track |
| Created | 01-May-2020 |
| Python-Version | 3.10 |

## Abstract

This PEP proposes adding an optional `strict` boolean keyword parameter to the built-in `zip`. When enabled, a `ValueError` is raised if one of the arguments is exhausted before the others.

## Motivation

`zip` stops as soon as its shortest argument is exhausted. That behaviour is useful when one of the inputs is deliberately infinite or longer than needed:

```python
for i, line in zip(itertools.count(1), lines):
    ...
```

In most real code, however, the arguments to `zip` are expected to have the same length. The programmer is pairing up two lists that were built together, columns of a table, keys and values, or parameters and arguments. In that situation, a length mismatch is a bug, and the silent truncation hides it.

Consider:

```python
def apply_weights(values, weights):
    return sum(v * w for v, w in zip(values, weights))
```

If a caller passes one fewer weight than values, the function returns a plausible but wrong number. Nothing fails. The bug may surface much later, far from its cause, or never be noticed at all.

Bugs like this are common enough that a search of open-source Python code turns up many hand-written guards:

```python
if len(a) != len(b):
    raise ValueError("length mismatch")
for x, y in zip(a, b):
    ...
```

These guards only work for sized inputs. When the arguments are iterators or generators, the check requires materializing them, or writing a custom zip with sentinel values, which is fiddly to get right. Several third-party packages ship such a helper, and the pattern is also a recurring question for newcomers.

The standard library itself contains places where an unequal-length `zip` would indicate a bug, and where today it would pass silently. Examples include code generation tools, `ast` processing, and argument binding helpers.

A simple, built-in way to say "these should be the same length" would catch these bugs at the point where they occur, at almost no cost.

## Rationale

### Why a flag and not a new function?

The alternatives are a new built-in (for example `zip_strict`), a new function in `itertools`, or a flag on `zip`.

A flag keeps the concept in one place. Users already reach for `zip`; they will discover `strict=True` in its documentation and in IDE completion. A separate function in `itertools` is less discoverable, and adding a new built-in for a variation of an existing one seems excessive.

There is precedent for this: `sorted(..., reverse=True)`, `print(..., flush=True)`, and `int(x, base=...)` all modify the behaviour of a built-in through a keyword argument.

### Why raise `ValueError`?

The problem is that the *values* passed in are inconsistent with each other, which matches `ValueError`'s documented purpose. A new exception subclass was considered, but there does not seem to be a use case for catching this error specifically rather than letting it propagate.

### Why not change the default?

Changing `zip` to be strict by default would break existing code that relies on truncation, including the common `zip(count(), ...)` idiom and code that deliberately zips with a longer iterable. That is not acceptable for a built-in used this widely.

## Specification

The signature of `zip` becomes:

```python
zip(*iterables, strict=False)
```

When `strict` is false, behaviour is unchanged.

When `strict` is true, `zip` proceeds as usual. When one of the iterators raises `StopIteration`:

- If it is the first iterator, `zip` checks each remaining iterator by calling `next()` on it. If any of them yields a value, `ValueError` is raised. If all of them are also exhausted, iteration stops normally.
- If it is not the first iterator, then the iterators before it have already produced a value for this round, so the lengths differ, and `ValueError` is raised.

The error message identifies which argument was shorter or longer, for example:

```
ValueError: zip() argument 2 is shorter than argument 1
ValueError: zip() argument 3 is longer than arguments 1-2
```

`strict` must be passed by keyword. It is checked for truthiness like any other boolean flag.

`zip` objects remain pickleable; the `strict` flag is preserved in the pickled state.

### Examples

```python
>>> list(zip([1, 2, 3], "abc", strict=True))
[(1, 'a'), (2, 'b'), (3, 'c')]

>>> list(zip([1, 2, 3], "ab", strict=True))
Traceback (most recent call last):
  ...
ValueError: zip() argument 2 is shorter than argument 1

>>> list(zip(range(3), range(5), strict=True))
Traceback (most recent call last):
  ...
ValueError: zip() argument 2 is longer than argument 1
```

### Side effects on consumed items

When the error is raised, some items may have been consumed from the longer iterators. For example, in the "longer" case, `zip` calls `next()` on the remaining iterators to find out whether they are exhausted, which consumes one item from the first iterator that is not. This is unavoidable without lookahead, and is consistent with how `zip` already consumes an item from earlier iterators before discovering that a later one is exhausted.

## Backward Compatibility

This change is fully backward compatible. The new parameter defaults to `False`, which preserves current behaviour. Code that passes keyword arguments to `zip` currently raises `TypeError`, so no working code can be affected.

## Reference Implementation

The implementation adds a flag to the `zip` object in `Python/bltinmodule.c` and an extra branch in `zip_next()` that runs only when an iterator is exhausted. The common path is unchanged, so performance of `zip` without `strict` is unaffected, and performance with `strict=True` is identical except at the end of iteration.

## Rejected Ideas

### Add `itertools.zip_strict`

Rejected for discoverability, as described above. Having `zip` and `zip_longest` already split across two modules is a minor source of confusion, and a third variant in yet another place would make it worse.

### Add a `mode` parameter

A parameter such as `mode="shortest" | "equal" | "longest"` would unify `zip` and `itertools.zip_longest`. This is attractive in theory, but `zip_longest` needs a `fillvalue` parameter that makes no sense for the other modes, and string-valued mode flags are less idiomatic in Python than booleans. Moving `zip_longest` into `zip` is a larger change than this PEP aims to make.

### Add a method or alternative constructor

Something like `zip.strict(a, b)` was suggested. It reads well but introduces a pattern (class methods on built-in functions-as-types) that is otherwise rare, and it complicates the type of `zip`.

### Raise `AssertionError` or check only in debug mode

Length mismatches are bugs that should be caught in production as well as in testing. Tying the check to `-O` would make it silently disappear in exactly the deployments where bugs are hardest to diagnose.
