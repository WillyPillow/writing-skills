PEP: 435
Title: Adding an Enum type to the Python standard library
Status: Draft
Type: Standards Track
Python-Version: 3.4
Created: 23-Feb-2013

# Abstract

This PEP proposes adding an enumeration type to the Python standard library. An enumeration is a set of symbolic names bound to unique, constant values. Within an enumeration, the values can be compared by identity, and the enumeration itself can be iterated over.

# Motivation

Python code is full of small sets of named constants: HTTP methods, file modes, log levels, colors, states in a state machine. The usual way to write them is module-level integers or strings:

```python
RED = 1
GREEN = 2
BLUE = 3
```

This works, but has several weaknesses:

- **No grouping.** Nothing ties `RED`, `GREEN`, and `BLUE` together. You cannot ask "what are all the colors?" or check that a value is a valid color.
- **Poor debugging output.** When a value shows up in a traceback or log, it prints as `2`, not `GREEN`. The reader has to go find the constant table.
- **Accidental mixing.** `RED == SMALL` might be true if both happen to be `1`, even though they mean entirely different things.
- **No protection against reassignment.** Nothing stops `RED = 7` somewhere else in the program.

Many third-party packages solve this problem: `flufl.enum`, `enum34`-style recipes, and ad hoc classes in Django, Twisted, and elsewhere. They differ in small but annoying ways. A single standard implementation would let libraries agree on one type, and would let the standard library itself replace its own magic integers (`socket.AF_INET`, `signal.SIGINT`, `http.HTTPStatus`-style tables) with something more informative.

# Specification

## Creating an Enum

Enumerations are created with class syntax by subclassing `Enum`:

```python
from enum import Enum

class Color(Enum):
    red = 1
    green = 2
    blue = 3
```

The class `Color` is an *enumeration* (or *enum*). The attributes `Color.red`, `Color.green`, and so on are *enumeration members* (or *members*). Each member has a *name* and a *value*.

```python
>>> Color.red
<Color.red: 1>
>>> print(Color.red)
Color.red
>>> Color.red.name
'red'
>>> Color.red.value
1
>>> type(Color.red)
<enum 'Color'>
>>> isinstance(Color.green, Color)
True
```

Values may be of any type. Integers are typical, but strings, tuples, or arbitrary objects are allowed.

## Iteration

Enumerations support iteration, in definition order:

```python
>>> list(Color)
[<Color.red: 1>, <Color.green: 2>, <Color.blue: 3>]
>>> len(Color)
3
```

## Member identity and comparison

Members are singletons. Each is created once, at class creation time, and the same object is returned every time it is accessed. Members can therefore be compared with `is`:

```python
>>> Color.red is Color.red
True
>>> Color.red is Color.blue
False
```

Equality comparison is also supported and is defined by identity. Members of different enumerations never compare equal, even if their values are equal:

```python
>>> class Shape(Enum):
...     square = 1
...
>>> Shape.square == Color.red
False
```

Comparison with non-enum values is also `False`: `Color.red == 1` is `False`. Ordered comparisons (`<`, `>`) are not supported between plain `Enum` members and raise `TypeError`. Enumerations are not numbers.

## Programmatic access

Members can be looked up by value by calling the enumeration, and by name with item access:

```python
>>> Color(1)
<Color.red: 1>
>>> Color['green']
<Color.green: 2>
```

An unknown value raises `ValueError`; an unknown name raises `KeyError`.

## Duplicate names and values

Defining the same name twice is an error. Defining two names with the same value is allowed; the second name becomes an *alias* for the first member:

```python
class Shape(Enum):
    square = 2
    diamond = 1
    circle = 3
    alias_for_square = 2

>>> Shape.alias_for_square
<Shape.square: 2>
>>> Shape(2)
<Shape.square: 2>
```

Aliases are not included in iteration. A `__members__` mapping, ordered by definition and including aliases, is provided for introspection.

## Immutability

Members cannot be reassigned or deleted, and new members cannot be added after the class is created:

```python
>>> Color.red = 4
AttributeError: Cannot reassign members.
```

## Methods and subclassing

Enumerations are Python classes and may define methods:

```python
class Mood(Enum):
    funky = 1
    happy = 3

    def describe(self):
        return self.name, self.value

    @classmethod
    def favorite(cls):
        return cls.happy
```

Subclassing an enumeration is allowed only if it defines no members. This rule exists because allowing it would break the invariant that every member of an enum is an instance of that enum and enumerated by it. It still permits sharing behavior through a base class with only methods.

## IntEnum

A variant, `IntEnum`, is provided whose members are also integers:

```python
from enum import IntEnum

class Priority(IntEnum):
    low = 1
    high = 2

>>> Priority.high > Priority.low
True
>>> Priority.high == 2
True
```

`IntEnum` exists for compatibility: it can replace integer constants in existing APIs without breaking code that compares or does arithmetic with them. New code should prefer `Enum`, since `IntEnum` gives up the type separation that makes enumerations useful.

## Functional API

For cases where class syntax is inconvenient, the `Enum` class is callable:

```python
>>> Animal = Enum('Animal', 'ant bee cat dog')
>>> Animal.ant
<Animal.ant: 1>
```

The second argument may be a space-separated string of names, a sequence of names, a sequence of `(name, value)` pairs, or a mapping. When only names are given, values start at 1, since 0 is false in a boolean context and members are intended to be truthy.

## Pickling

Members can be pickled and unpickled. Pickling stores a reference to the enumeration class and the member name, so the enumeration must be importable from its module. For functional-API enums, a `module` keyword argument may be supplied to make this possible.

# Rationale

**Why not integers by default?** Making members integers would allow `Color.red == Shape.square`, which defeats the purpose. `IntEnum` is offered for the cases where integer behavior is genuinely needed.

**Why class syntax?** Class syntax is familiar, supports methods and docstrings, and plays well with tools such as IDEs and type checkers. Requiring explicit values avoids surprising renumbering when members are reordered.

**Why are values required?** Some proposals auto-assigned values. That makes the value depend on source order and makes pickled data or databases fragile. Explicit values make the contract visible. A helper for automatic values could be added later if there is demand.

**Why ban subclassing of enums with members?** If `class MoreColor(Color)` could add `pink`, then `MoreColor.pink` would be an instance of `Color` but not appear in `list(Color)`. That breaks the basic model.

# Implementation

The implementation uses a metaclass, `EnumMeta`, which collects the class body's attributes, creates one instance per member, and stores them in an ordered mapping. Member lookup by value uses a dict when values are hashable and falls back to a linear search otherwise.

A reference implementation is available in the `enum` module proposed for Python 3.4. A backport for earlier versions can be distributed on PyPI.

# Rejected ideas

- **Making `Enum` members compare equal to their values.** Rejected for the type-safety reasons described above.
- **Allowing ordered comparisons on `Enum`.** Many enumerations have no natural order. Users who want ordering can define `__lt__` or use `IntEnum`.
- **A new keyword or syntax.** The class-based API needs no language changes.
