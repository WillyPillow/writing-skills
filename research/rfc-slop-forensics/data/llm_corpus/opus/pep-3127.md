# Abstract

This PEP proposes changes to the Python core that rationalize how integer literals and string representations of integers in different bases are handled. The changes target Python 3.0. The parts that are backward compatible should also be added to Python 2.6, so that every valid 3.0 integer literal is also valid in 2.6.

The proposal is:

a) Octal literals must be written with a leading `0o` or `0O`, not a leading `0`.

b) Binary literals are supported, written with a leading `0b` or `0B`.

c) String formatting and the built-in functions gain support for binary output.

# Motivation

Python inherited its integer literal syntax from C. A literal that starts with `0x` is hexadecimal, a literal that starts with `0` followed by more digits is octal, and anything else is decimal. That convention made sense in C in the 1970s, when octal was common for describing machine words and Unix file permissions. Today it is mostly a trap.

## Leading zeros are a surprise

Most people who write `010` do not mean eight. They mean ten, with a leading zero for alignment or because the number came from a source that pads with zeros, like a date or a zip code:

```python
>>> month = 09
SyntaxError: invalid token
>>> month = 010
>>> month
8
```

The first case at least fails loudly. The second is silently wrong. Newcomers, and people who do not come from C, are hit by this regularly, and the error message for `09` does not explain what happened.

The same problem appears in `int()`: `int('010', 0)` is 8 when the base is inferred, which surprises anyone parsing user input with automatic base detection.

## Octal is rare

Searches of large bodies of Python code show that octal literals are used almost exclusively for file permissions passed to `os.chmod`, `os.open` and `os.makedirs`. Those uses are important, but they are few, and they do not justify a syntax that makes every leading zero dangerous.

## Binary has no literal

Binary literals are useful when working with bit masks, hardware registers and network protocols. Python has no way to write them. Programmers use hex and convert in their heads, or call `int('1011', 2)` at runtime. Several other languages and many C compilers already accept `0b` literals.

## Output is inconsistent

`hex()` and `oct()` exist. There is no `bin()`. The `%` formatting operator supports `%x` and `%o` but not binary. Getting a binary string means writing a loop.

# Specification

## Grammar

The integer literal grammar for Python 3.0 is:

```
integer        ::= decimalinteger | octinteger | hexinteger | bininteger
decimalinteger ::= nonzerodigit digit* | "0"+
nonzerodigit   ::= "1"..."9"
octinteger     ::= "0" ("o" | "O") octdigit+
hexinteger     ::= "0" ("x" | "X") hexdigit+
bininteger     ::= "0" ("b" | "B") bindigit+
octdigit       ::= "0"..."7"
hexdigit       ::= digit | "a"..."f" | "A"..."F"
bindigit       ::= "0" | "1"
```

A decimal literal may not have a leading zero, except for zero itself written as one or more `0` characters. `010` is a `SyntaxError` in Python 3.0. It is not reinterpreted as decimal ten, because code that relied on the old meaning would then silently change behavior. A syntax error is the safe outcome.

The `L` suffix for long integers is removed separately by PEP 237 and is not discussed here.

## Choice of prefix letters

`0x` is unchanged. `0b` follows existing practice in other languages. For octal, `0o` was chosen over `0c` and `0q`. Its main drawback is that a lowercase `o` can be confused with zero in some fonts, and `0O` looks worse. The PEP recommends that documentation and style guides use the lowercase form. `0c` was rejected because it does not suggest "octal" to most readers, and `0q` because it looks arbitrary.

## Built-in functions

- `oct(x)` returns a string with the `0o` prefix, for example `oct(8) == '0o10'`.
- A new built-in `bin(x)` returns a string with the `0b` prefix, for example `bin(5) == '0b101'`.
- `hex(x)` is unchanged.

All three accept any integer and produce a string that is a valid literal.

## int() and base inference

`int(s, 0)` infers the base from the prefix, using the same rules as the grammar: `0x`, `0o` and `0b` select base 16, 8 and 2. A leading `0` followed by other digits raises `ValueError`. `int(s, 8)` and `int(s, 2)` accept the corresponding prefix, the same way `int(s, 16)` accepts `0x` today.

`int()` with an explicit base of 10, and with no base, continues to accept leading zeros. `int('010')` is 10. This is string parsing of data, not a literal in source code, and rejecting leading zeros there would break a great deal of code that reads numbers from files.

## String formatting

The `str.format()` mini-language of PEP 3101 gains a `b` presentation type for binary, alongside `o`, `x` and `X`. The `#` flag adds the prefix: `format(5, '#b') == '0b101'` and `format(8, '#o') == '0o10'`.

The `%` operator is not extended with a binary code, since `str.format()` is the preferred interface in 3.0.

# Python 2.6

Python 2.6 will:

- accept `0o` and `0b` literals in addition to existing forms;
- provide `bin()`;
- support `0o` and `0b` prefixes in `int(s, 0)`;
- support the `b` format type in `str.format()`.

Python 2.6 will not reject old-style octal literals and will not change the output of `oct()`, since those would break existing code. When run with the `-3` warning flag, 2.6 will warn about old-style octal literals.

The `2to3` conversion tool will rewrite `0777` to `0o777`.

# Backward Compatibility

Code using old octal literals will fail to compile under 3.0 with a clear `SyntaxError`. The fix is mechanical, and `2to3` applies it. Code that parses the output of `oct()` must accept the new prefix. Code that calls `int(s, 0)` on strings with leading zeros will raise `ValueError` instead of returning an octal value; this is intended.

# Rejected Alternatives

**Remove octal literals entirely** and require `int('777', 8)`. This would make file permission code noticeably worse, and the runtime call cannot be used in all the places a literal can.

**Reinterpret leading zeros as decimal.** Rejected because existing code would silently change meaning.

**A general radix syntax**, such as `16r1F` or `8#777`. This is more flexible but adds bases nobody asked for and syntax nobody would recognize.

**Uppercase-only prefixes** to avoid `0o` looking like `00`. Rejected because it would be the only place where Python requires an uppercase letter in a numeric literal.
