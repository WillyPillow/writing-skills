# PEP 383: Non-decodable Bytes in System Character Interfaces

| Field | Value |
|---|---|
| PEP | 383 |
| Title | Non-decodable Bytes in System Character Interfaces |
| Status | Draft |
| Type | Standards Track |
| Created | 22-Apr-2009 |
| Python-Version | 3.1 |

## Abstract

File names, environment variables, and command line arguments are defined as character data in POSIX, but the C APIs allow passing arbitrary bytes, whether or not they conform to any particular encoding. This PEP proposes a way of handling such irregularities: embedding the bytes in character strings so that the original byte string can be recreated exactly.

## Rationale

Python 3 made a clean separation between text (`str`) and binary data (`bytes`). Operating system interfaces that conceptually deal with text, such as `os.listdir()`, `os.environ`, and `sys.argv`, return `str`. To do that, Python must decode the bytes the OS gives it, using the file system encoding (usually derived from the locale).

On Windows this works well. The native APIs are UTF-16, and Python uses the wide-character variants, so there is nothing to decode.

On POSIX systems the situation is different. The kernel treats a file name as a sequence of bytes, excluding only `/` and NUL. Nothing guarantees that those bytes are valid in the locale's encoding. In practice, invalid names are common:

- files created by a program running under a different locale;
- files copied from another system or extracted from an archive;
- files on removable media formatted elsewhere;
- names created deliberately or by bugs.

Python 3.0 handles this inconsistently. `os.listdir()` with a `str` argument silently omits entries whose names cannot be decoded. `sys.argv` and `os.environ` may fail at startup or drop values. A program that walks a directory tree and deletes files can skip files without any indication. Programs that need to be robust must use the `bytes` variants of the APIs, which are not available everywhere (there is no `bytes` version of `sys.argv` or, at present, `os.environ`), and which force the whole program to deal in bytes.

What is wanted is a way for the `str` interfaces to represent every possible OS value, such that passing the `str` back to the OS produces exactly the original bytes.

## Specification

### The error handler

A new error handler, `surrogateescape`, is added to the codec machinery.

**On decoding**, when a byte cannot be decoded, the handler replaces it with a lone surrogate code point: byte `0xXY` (which is always in the range `0x80`-`0xFF`, since ASCII bytes decode under any ASCII-compatible encoding) becomes `U+DCXY`. For example, decoding `b'caf\xe9'` as UTF-8 produces `'caf\udce9'`.

**On encoding**, when the encoder meets a code point in the range `U+DC80`-`U+DCFF` that it cannot otherwise encode, the handler converts it back to the single byte `0xXY`.

Lone surrogates in this range cannot occur in correctly decoded text from any standard encoding, because a well-formed UTF-8, UTF-16, or single-byte codec never produces an unpaired low surrogate. They therefore act as an unambiguous escape mechanism.

### Where the handler is used

On POSIX systems, the following interfaces decode with the file system encoding and the `surrogateescape` handler, and encode with the same combination:

- file name functions in `os` and `os.path` (`listdir`, `stat`, `open`, `getcwd`, `readlink`, and so on), and the built-in `open()`;
- `os.environ` and `os.getenv`/`os.putenv`;
- `sys.argv`;
- `os.execv` and related functions, and `subprocess` arguments.

On Windows, nothing changes, because these interfaces are not byte-based.

### Round-trip guarantee

For any byte string `b` received from the OS, decoding with `fsencoding` and `surrogateescape` produces a `str` `s` such that encoding `s` the same way produces `b` again. This holds as long as the file system encoding is ASCII-compatible. Python will refuse to start with a non-ASCII-compatible file system encoding on POSIX.

### Convenience functions

`os.fsencode(name)` and `os.fsdecode(name)` perform the conversion explicitly, so that code which needs to switch between representations can do so without spelling out the encoding and error handler. These are a natural addition; their exact names may be chosen during implementation.

## Discussion

### Why not just use bytes?

Bytes APIs remain available and are the right choice for some programs. But most programs are written to treat file names as text: they join them with string literals, display them, and compare them with user input. Forcing all of those programs to use bytes in order to be correct for rare edge cases would undo much of the benefit of Python 3's text model. With this PEP, the simple `str` code is also correct.

### What happens to the escaped strings in other contexts?

A string containing escape surrogates behaves like any other `str` inside Python. Problems arise only when it is encoded with a different codec or error handler. For example, writing it to a UTF-8 text file with the default `strict` handler raises `UnicodeEncodeError`, because lone surrogates are not valid in UTF-8. This is intentional: the program has a value that is not text, and the error tells it so at the point where it matters. Programs that want to display such names can encode with `backslashreplace` or `replace`.

### UTF-8 and surrogates

Python's UTF-8 codec does not encode lone surrogates by default. That remains true. The `surrogateescape` handler only converts surrogates in the range `U+DC80`-`U+DCFF` back to bytes; other lone surrogates still cause an error.

There is one subtle case: if the file system encoding is UTF-8 and a file name on disk is actually the UTF-8-style encoding of a surrogate (the bytes `ED B3 A9`, which strict UTF-8 rejects), then decoding produces three escaped bytes, not a surrogate, and the round trip still works.

### Comparison of names

Two different byte strings always map to two different `str` values. Two equal `str` values always came from the same bytes. The mapping is injective, so dictionary lookups, sets, and equality comparisons on file names behave correctly.

### Locale changes

If a program changes the locale after startup, previously decoded names may no longer round-trip. Python fixes the file system encoding at startup and does not change it afterwards, so this is not an issue for the interfaces listed above.

## Alternatives considered

**Use a private-use area (PUA) mapping.** Mapping invalid bytes to characters in a PUA was rejected because PUA characters can legitimately occur in file names, breaking the injective mapping.

**Use an escape character such as `%` or `\`.** Any printable escape character must itself be escaped when it appears normally, which changes the representation of valid names. That breaks the expectation that valid names decode to themselves.

**Return a special `str` subclass that remembers its bytes.** This preserves the bytes as long as the object is not copied or transformed, but string operations return ordinary `str` objects and lose the information. It also complicates every API that accepts file names.

**Use Latin-1 everywhere.** Decoding everything as Latin-1 round-trips trivially, but valid UTF-8 names would appear as mojibake, which is worse for the common case.

## Backwards compatibility

Programs that previously saw undecodable names silently omitted will now see them, as strings containing surrogates. Programs that previously got exceptions will now get strings. Both are improvements. Code that prints such names with a strict encoder may see a new `UnicodeEncodeError` at output time instead of earlier, at listing time.

## Implementation

The error handler is implemented in the codec registry in C so that it is available during interpreter startup. `PyUnicode_DecodeFSDefault` and `PyUnicode_EncodeFSDefault` use it. The `os` module and the startup code that builds `sys.argv` and `os.environ` are updated to call these functions.
