# Abstract

This PEP proposes an extensible, cooperative mechanism for adapting an incoming object to a context that expects an object supporting a particular protocol, such as a specific type, class or interface.

It adds a built-in function, `adapt(obj, protocol)`. For any object X and protocol Y, `adapt(X, Y)` asks the Python environment for a version of X that complies with Y. Behind the scenes, the function first asks X: "Do you already support Y, or do you know how to wrap yourself so that you do?" If X cannot answer, it then asks Y: "Does X support you, or do you know how to wrap it so that it does?" Both sides get a say. This matters because protocols are often written after the objects that need adapting to them, and objects are often written after the protocols they need to support. Neither side can be expected to know about the other in advance.

# Motivation

Python code relies on duck typing. A function that wants "a file" usually means "something with a `read` method". That works well when the caller and the callee agree on the protocol. It breaks down in three situations.

First, an object may support the protocol in substance but not in form. A socket can be read from, but its method is `recv`, not `read`. Callers then write a wrapper by hand, and every caller writes a slightly different one.

Second, a function may accept several input forms, such as a filename, an open file or a string of data. Today such functions are full of `isinstance` checks, and each new form means editing the function.

Third, frameworks such as Zope, Twisted and PEAK each have their own interface systems and their own adapter registries. Code that wants to interoperate with more than one of them has to learn each one separately. There is no common entry point.

`adapt` addresses all three. The callee states what it wants, `adapt` finds a way to produce it, and the logic for how to produce it lives in the object, in the protocol, or in a registry, rather than in every caller.

# Specification

## The adapt function

```python
def adapt(obj, protocol, alternate=AdaptationError):
    ...
```

The function returns an object that supports `protocol`. The steps are:

1. **Identity.** If `type(obj) is protocol`, return `obj`.

2. **Ask the object.** If `type(obj)` has a method `__conform__`, call `obj.__conform__(protocol)`. If the result is not `None`, return it.

3. **Ask the protocol.** If `protocol` has a method `__adapt__`, call `protocol.__adapt__(obj)`. If the result is not `None`, return it.

4. **Subclass check.** If `protocol` is a class or type and `isinstance(obj, protocol)` is true, return `obj`. This step comes after the two hooks so that a subclass that breaks its base class's contract (a "Liskov violation") can refuse adaptation through `__conform__` by raising `LiskovViolation`.

5. **Registry.** Look up `(type(obj), protocol)` in the global adapter registry. If an adapter factory is registered, return `factory(obj, protocol, alternate)`.

6. **Failure.** If `alternate` is the default, raise `AdaptationError`. Otherwise return `alternate`.

The order puts the most specific knowledge first. An object knows best how to present itself, a protocol knows best what counts as conforming to it, and the registry exists for third parties who own neither.

## The \_\_conform\_\_ and \_\_adapt\_\_ hooks

`__conform__(self, protocol)` is looked up on the type, not the instance, like other special methods. It returns an adapted object, or `None` if it does not know how. It should not raise an exception to mean "no"; raising is reserved for real errors, plus the specific case of `LiskovViolation`.

`__adapt__(cls, obj)` is defined on the protocol object. For a class, it is normally a classmethod. Protocol objects that are not classes, such as interface objects from Zope, define it as an ordinary method. The return rules are the same as for `__conform__`.

## The registry

```python
def register_adapter_factory(objtype, protocol, factory):
    ...
```

The registry is keyed on exact types. It is meant for integration code, where a third party wants to make type A from one library adaptable to protocol B from another library without changing either. It deliberately does not search the MRO of `objtype`. Doing so introduces ordering questions that are better handled in the hooks, where the author can see the whole picture.

## Exceptions

`AdaptationError` is a subclass of `TypeError`. Code that previously raised `TypeError` for bad input can switch to `adapt` without breaking callers that catch `TypeError`.

`LiskovViolation` is a subclass of `AdaptationError`. When `__conform__` raises it, `adapt` stops at step 3 and does not fall back to the `isinstance` check.

# Examples

A protocol class that adapts strings to a stream:

```python
class ReadableStream:
    @classmethod
    def __adapt__(cls, obj):
        if isinstance(obj, str):
            return io.StringIO(obj)
        if hasattr(obj, 'recv'):
            return SocketReader(obj)
        return None
```

An object that knows how to present itself:

```python
class Document:
    def __conform__(self, protocol):
        if protocol is ReadableStream:
            return io.StringIO(self.render())
        return None
```

A function that accepts anything adaptable:

```python
def count_lines(source):
    stream = adapt(source, ReadableStream)
    return sum(1 for _ in stream)
```

`count_lines` does not change when someone adds a new kind of source. The new source supplies `__conform__`, or someone registers an adapter.

# Transitivity

Adaptation is not transitive in this proposal. If X adapts to Y and Y adapts to Z, `adapt(X, Z)` does not chain the two. Automatic chaining can pick surprising paths and can lose information at each step. Authors who want a chain can write an adapter that does it explicitly.

# Relation to interfaces

This PEP does not define interfaces. It works with any protocol object: built-in types, classes, abstract base classes or interface objects from a third-party package. Interface packages are free to implement `__adapt__` on their interface objects and thereby plug into the same mechanism. The goal is a common entry point, not a common interface system.

# Backward compatibility

The change is purely additive. No existing code calls `adapt`, defines `__conform__` or defines `__adapt__` with a different meaning, as far as a survey of the standard library and major frameworks shows. Framework-specific adapter functions can be reimplemented on top of `adapt` at their own pace.

# Reference implementation

A pure-Python implementation of `adapt`, the registry and the two exceptions is about sixty lines and is attached to the tracker issue. A C implementation in `bltinmodule.c` would follow if the PEP is accepted.

# Open issues

- Should the registry be global, or should `adapt` accept an optional registry argument for isolation in tests?
- Should built-in types gain `__adapt__` methods, so that, for example, `adapt(x, int)` behaves like a checked `int(x)`? That raises questions about lossy conversion, and this PEP leaves it out for now.
- Should there be a way to declare that a type supports a protocol without writing a method, analogous to the registry but for identity adaptation?
