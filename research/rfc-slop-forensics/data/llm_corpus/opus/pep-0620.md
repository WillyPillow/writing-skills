# PEP 620: Hide implementation details from the C API

| Field | Value |
|---|---|
| PEP | 620 |
| Title | Hide implementation details from the C API |
| Status | Draft |
| Type | Standards Track |
| Created | 19-Jun-2020 |
| Python-Version | 3.10 |

## Abstract

Introduce C API incompatible changes to hide implementation details. Once most implementation details are hidden, the evolution of CPython internals will be less constrained by C API backward compatibility. Adding new features will become much easier, and it will become possible to experiment with optimizations more ambitious than micro-optimizations, such as tagged pointers.

This PEP also defines a process to reduce the number of C extensions broken by each change. The work is expected to be spread carefully over several Python releases. It started in Python 3.7, and most of the changes are already done. The process for reducing breakage sets the pace.

## Motivation

### The C API leaks the object layout

The public C API was never designed as an abstraction layer. It grew out of the headers CPython itself uses, and for most of CPython's history there was no separation between "what the interpreter needs" and "what third-party code may rely on". As a result, extension modules routinely do things like:

- read `ob_refcnt` and `ob_type` directly through the `PyObject` structure;
- use macros such as `PyTuple_GET_ITEM()` or `PyList_GET_ITEM()` that expand to direct array access into the object;
- access members of `PyTypeObject`, `PyFrameObject`, or `PyThreadState` by name;
- assign to macros used as lvalues, for example `Py_TYPE(obj) = type`.

Each of these ties the extension to the exact memory layout of a CPython object at the moment the extension was compiled. Any change to that layout, however small, is an ABI break, and frequently an API break too.

### The cost to CPython

Because the layout is effectively public, many reasonable internal changes are off the table:

- Changing the representation of integers, strings, or lists to something more compact.
- Moving the reference count out of the object header, or switching to a different memory management scheme.
- Removing the GIL or making parts of the runtime per-interpreter, since global state is reachable through public structures.
- Tagged pointers, where small integers or other values are encoded directly in the pointer and never allocated at all. This is impossible as long as extensions are allowed to dereference any `PyObject*` they receive.

Other Python implementations face the same problem from the opposite side. PyPy, GraalPython and others must emulate CPython's object layout to run C extensions, which is slow and complicated. A C API that does not expose structure members would be far easier to support efficiently.

### The cost to extension maintainers

The limited C API and the stable ABI (PEP 384) already exist, but they are not widely used, partly because they are missing functions that the full API provides through structure access. The goal here is not to force everyone onto the limited API, but to close the gap so that the default API stops depending on internal details.

## Rationale

The C API should be treated as a contract that describes behaviour, not memory layout. Getters and setters (functions or static inline functions) give CPython the freedom to change what happens behind them. A function call is marginally slower than a direct member access in some cases, but static inline functions remove most of that cost while still allowing the implementation to change at the source level.

Removing the ability to access structure members is a breaking change and cannot be done in a single release. This PEP therefore pairs each change with a process, described below, designed to keep the number of broken projects small and to give maintainers time and tools to adapt.

## Specification

### Summary of changes

1. **Move private and internal APIs out of the public headers.** The internal C API lives in `Include/internal/` and requires `Py_BUILD_CORE` to be defined. Private functions prefixed with `_Py` that are not needed by extensions are moved there.

2. **Convert macros to static inline functions.** Macros such as `Py_INCREF()`, `Py_TYPE()`, and `PyTuple_GET_ITEM()` become static inline functions. This gives proper type checking, avoids double evaluation of arguments, and, importantly, makes it an error to use the result as an lvalue.

3. **Make structures opaque where possible.** For structures that extensions do not need to allocate on the stack or embed, the definition is moved into the internal headers and access is provided through functions. Initial candidates include `PyInterpreterState`, `PyThreadState`, `PyFrameObject`, `PyGC_Head`, and eventually `PyTypeObject` (for heap types).

4. **Disallow `Py_TYPE()`, `Py_REFCNT()` and `Py_SIZE()` as lvalues.** New functions `Py_SET_TYPE()`, `Py_SET_REFCNT()` and `Py_SET_SIZE()` replace the assignment idiom.

5. **Add new getter functions** wherever an extension previously needed to read a structure member, for example `PyFrame_GetCode()`, `PyFrame_GetBack()`, `PyThreadState_GetInterpreter()`, and `PyThreadState_GetFrame()`.

6. **Add a "borrowed reference free" path.** Functions returning borrowed references make it hard to change object storage. New APIs return strong references; old ones remain but are discouraged.

### Changes already completed

Since Python 3.7 the following have been done:

- `Include/internal/` was created and populated; many private functions moved there.
- `Include/cpython/` holds the non-limited part of the public API, separating it from the limited API.
- Many macros became static inline functions in 3.8 and 3.9.
- `PyInterpreterState` became opaque in 3.8.
- `Py_SET_TYPE()`, `Py_SET_REFCNT()` and `Py_SET_SIZE()` were added in 3.9.
- Frame and thread state getters were added in 3.9.

### Changes planned

- Python 3.10: `Py_TYPE()`, `Py_REFCNT()` and `Py_SIZE()` can no longer be used as lvalues.
- Make `PyThreadState` and `PyFrameObject` opaque once getters cover the known use cases.
- Deprecate and eventually remove APIs that return borrowed references where a strong-reference replacement exists.
- Investigate making `PyObject` and `PyTypeObject` opaque for code built against the limited API without losing performance.

## Process to reduce the number of broken C extensions

Every incompatible change follows these steps:

1. **Estimate impact.** Before merging, check how many projects use the affected API. The reference set is the most popular packages on PyPI plus a list of well-known extensions (Cython, numpy, pybind11, and others) whose generated or hand-written code is widely copied.
2. **Fix the ecosystem first.** If the change breaks a widely used project, submit fixes upstream before the change lands in CPython. Tools like Cython that generate C code are a priority because one fix repairs many packages.
3. **Provide a compatibility layer.** Ship a header, `pythoncapi_compat.h`, that implements new functions on older Python versions. Extensions can adopt the new API immediately and keep supporting old Pythons. A script can rewrite common patterns automatically.
4. **Document the change** in the "Porting to Python 3.x" section of What's New, with the exact replacement code.
5. **Revert if necessary.** If too many projects break during the alpha and beta phases, the change is reverted and reapplied in a later release after more preparation.

No change should break a large share of the ecosystem at once. The pace of this PEP is set by how quickly extensions can be updated, not by how quickly CPython wants to change.

## Backwards Compatibility

This PEP is explicitly about introducing incompatible changes. Each one is evaluated on its own using the process above. The limited C API and the stable ABI are not affected beyond what is already guaranteed; in practice they gain functions, which makes them easier to adopt.

Code that only uses documented public functions without reaching into structures is not affected. Code that uses macros in the documented way is not affected by their conversion to static inline functions, except where the macro was used as an lvalue or in an unusual expression context.

## Performance

Converting macros to static inline functions has no measurable runtime cost with an optimizing compiler. In debug builds without inlining, some functions become real calls; this is acceptable for debug builds.

Making structures opaque can cost a function call where there used to be a member access. For hot paths inside CPython itself this does not matter, because the internal API still sees the full definitions. For extensions, the cost has proven negligible in the benchmarks run so far. In exchange, CPython gains room for optimizations that are currently impossible.

## Rejected Ideas

**Write a new C API from scratch.** Projects like HPy explore this, and this PEP does not compete with them. A new API needs years before the ecosystem moves to it, while the existing API needs to evolve now. The two efforts complement each other.

**Make all changes in one release.** This would break too many projects at once and stall adoption of the new Python version.

**Keep the API as is.** This leaves CPython permanently unable to make deep changes to its object model.
