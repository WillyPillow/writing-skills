PEP: 610
Title: Recording the Direct URL Origin of installed distributions
Status: Draft
Type: Standards Track
Topic: Packaging
Created: 2019

# Abstract

Following PEP 440, a distribution can be identified by a name and either a version or a direct URL reference. After installation, the name and version are captured in the project metadata, but there is currently no way to recover the URL that was used when the distribution was installed from a direct URL reference. This PEP defines additional metadata, written to the installed distribution by the installation front end, that records this Direct URL Origin for use by tools that inspect the database of installed packages described in PEP 376.

# Motivation

Python installers support installing from locations other than an index: a local directory, a local or remote archive, or a version control repository at a particular commit. For example:

```
pip install "mypkg @ git+https://example.com/mypkg.git@1a2b3c"
pip install ./path/to/project
pip install https://example.com/dist/mypkg-1.0.tar.gz
```

Once installed, the resulting environment contains a `.dist-info` directory with a `METADATA` file that gives the project name and version, but nothing about where the code came from. That loss of information causes real problems:

- **Reproducing environments.** A command such as `pip freeze` is expected to produce a requirements file that recreates the current environment. For a package installed from a VCS commit, it can only emit `mypkg==1.0`, which may not exist on any index, or may refer to entirely different code. Tools have resorted to heuristics such as inspecting the source directory for a `.git` folder, which only works for editable installs.
- **Auditing.** Security and compliance tooling wants to know whether a package came from an index or from somewhere else, and if somewhere else, exactly which commit or archive.
- **Upgrades and reinstalls.** An installer deciding whether a requirement is already satisfied cannot tell whether the installed copy came from the same URL the user is now asking for.

Recording the origin at install time is simple and reliable. Reconstructing it afterwards is not.

# Specification

## The `direct_url.json` file

When an installer installs a distribution from a direct URL reference, it must write a file named `direct_url.json` in the `.dist-info` directory of the installed distribution. The file must be added to the `RECORD` file like any other installed file.

When the distribution is installed from a regular index by name and version specifier, the installer must not write this file. Its presence therefore indicates that the distribution was installed from a direct URL.

The file contains a single UTF-8 encoded JSON object with the following keys.

### `url` (required)

A string containing the URL that was used to obtain the distribution. For local paths, this is a `file://` URL. Installers should strip any credentials (user name and password) from the URL before recording it, except where an environment variable reference such as `${TOKEN}` is used in place of a literal secret, in which case the reference may be kept.

The URL should be the canonical form of what the user requested, resolved to an absolute location. A relative path given on the command line is recorded as an absolute `file://` URL.

### `archive_info`

Present when the URL refers to an archive (a source distribution or wheel). It is an object with an optional `hash` key whose value has the form `<algorithm>=<hexdigest>`, for example `sha256=2dc6b5a4...`. Installers should record a hash whenever they computed or verified one.

### `vcs_info`

Present when the URL refers to a version control repository. It is an object with the following keys:

- `vcs` (required): the name of the version control system, such as `git`, `hg`, `bzr` or `svn`. These match the `<vcs>+` prefixes used in PEP 440 direct references.
- `commit_id` (required): the exact, immutable revision that was installed, for example a full Git commit hash. Installers must resolve branch or tag names to a commit before recording.
- `requested_revision` (optional): the revision exactly as the user requested it, such as a branch name, tag or short hash.

### `dir_info`

Present when the URL refers to a local directory. It is an object with an optional boolean `editable` key, defaulting to false, which is true when the distribution was installed in editable (development) mode.

Exactly one of `archive_info`, `vcs_info` and `dir_info` must be present.

## Additional keys

The URL may carry a `subdirectory` fragment indicating that the project lives in a subdirectory of the repository or archive. In that case the top-level object contains a `subdirectory` key with the relative path. Installers must not add other top-level keys; extension data, if needed, should be proposed in a future revision of this specification.

## Examples

A Git commit:

```json
{
  "url": "https://github.com/example/mypkg.git",
  "vcs_info": {
    "vcs": "git",
    "requested_revision": "v1.0",
    "commit_id": "7921be1537eac1e97bc40179a57f0349c2aee67d"
  }
}
```

A remote archive:

```json
{
  "url": "https://example.com/dist/mypkg-1.0.tar.gz",
  "archive_info": {
    "hash": "sha256=8f3a1c9e..."
  }
}
```

An editable local directory:

```json
{
  "url": "file:///home/user/projects/mypkg",
  "dir_info": {
    "editable": true
  }
}
```

## Reconstructing a requirement

A consumer can turn the recorded information back into a PEP 440 direct reference. For VCS installs it should use `commit_id` rather than `requested_revision`, so that the reference identifies the same code even if a branch has since moved:

```
mypkg @ git+https://github.com/example/mypkg.git@7921be1537eac1e97bc40179a57f0349c2aee67d
```

For archives the URL is used directly, optionally with the recorded hash. For local directories the `file://` URL is used, and an editable install is reported in whatever way the consuming tool represents editable requirements.

# Rationale

**Why a separate file?** The `METADATA` file describes the project itself and is generated by the build backend, often before the installer knows how the distribution will be installed. The origin of an installation is a property of the installation, not the project, so it belongs in a file written by the installer.

**Why JSON?** The structure is nested and contains several optional fields. JSON is in the standard library, easy to parse from any language, and less ambiguous than the email-header format used by `METADATA`.

**Why record the resolved commit?** Branch and tag names are mutable. A record that says "installed from `main`" is useless for reproducibility a week later. The requested revision is still kept because it is useful for display and for tools that want to offer "upgrade to latest on this branch".

**Why strip credentials?** The `.dist-info` directory is often world-readable and may be copied into container images or shared environments. Leaking tokens there would be a serious security problem.

# Backwards Compatibility

This specification adds a new file; it does not change any existing file. Tools that do not know about `direct_url.json` will ignore it. Distributions installed before installers adopt this PEP simply lack the file, and consumers must treat its absence as "origin unknown or installed from an index".

# Security Considerations

Consumers must treat the contents of `direct_url.json` as untrusted input, since any process with write access to the environment could modify it. Installers must take care not to record secrets, as described above. Tools that display or reuse the URL should avoid passing it to a shell without quoting.

# Reference Implementation

A reference implementation is expected in pip, writing the file on installation and using it in `pip freeze` to emit accurate direct references.
