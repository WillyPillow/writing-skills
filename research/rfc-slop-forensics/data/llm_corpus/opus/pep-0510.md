PEP: 510
Title: Specialize functions with guards
Author: Victor Stinner
Status: Draft
Type: Standards Track
Created: 04-Jan-2016
Python-Version: 3.6

Abstract
========

Add functions to the Python C API to specialize pure Python functions:
attach specialized code objects to a function, each protected by a list
of guards.  When the function is called, the first specialized code
whose guards all pass is executed; otherwise the original bytecode runs.
This allows static optimizers to be built that respect Python's dynamic
semantics.


Rationale
=========

Python is hard to optimize ahead of time because almost everything can
change at runtime.  A function that calls ``len(x)`` cannot assume that
``len`` is the builtin, because a module global named ``len`` could be
defined later, or ``builtins.len`` could be replaced.  A function that
reads a module constant cannot fold it, because the module attribute can
be reassigned.

Yet in practice these things almost never change.  An optimizer that
could assume "``len`` is the builtin, and ``DEBUG`` is ``False``" could
inline constants, remove dead branches, unroll loops and call builtins
directly.  What it needs is a cheap way to check, at call time, that its
assumptions still hold, and to fall back to the unoptimized code when
they do not.

Several projects have explored this.  JIT compilers like PyPy and
Pyston perform specialization and deoptimization internally.  Static
optimizers such as the ``fatoptimizer`` project transform the AST ahead
of time but need runtime support to remain correct.  Without support in
CPython, each project must patch the interpreter or give up correctness.

This PEP proposes that minimal runtime support.  It does not include an
optimizer.  It defines how specialized code is attached to a function,
what a guard is, and how the interpreter chooses which code to run.


Example
=======

Consider::

    def func():
        return len("abc")

An optimizer may want to replace the body with ``return 3``.  That is
only valid if, when the function is called, ``len`` still resolves to
``builtins.len``.  With this PEP, the optimizer:

1. Compiles the specialized body ``return 3`` to a code object.
2. Creates a guard that checks the global name ``len`` is not defined in
   the function's globals, and that ``builtins.len`` is the original
   builtin function.
3. Calls ``PyFunction_Specialize(func, code, guards)``.

When ``func()`` is called and nobody has touched ``len``, the guard
passes and ``return 3`` runs.  If someone later writes
``builtins.len = mylen``, the guard fails and the original bytecode
runs, calling ``mylen``.  Behaviour is identical to unoptimized Python.

Specialization also applies to argument types.  A function::

    def scale(x):
        return x * 2

might be specialized for ``int`` arguments with a guard checking
``type(x) is int``, allowing the optimizer to emit code that avoids
generic dispatch.


Python Function Call
====================

Each function object gains an internal list of ``(code, guards)``
entries, initially empty.  When the function is called:

1. For each entry in order, evaluate each guard by calling its
   ``check`` method with the function's arguments.
2. If every guard returns "pass", run that entry's code.
3. If a guard returns "fail", move on to the next entry.
4. If a guard returns "fail forever", remove the entry from the list and
   move on.  This avoids repeatedly checking a guard that can never
   pass again, such as one watching a dictionary key that has been
   deleted.
5. If no entry is selected, run the function's original ``__code__``.

If a guard's ``check`` raises an exception, the call fails with that
exception.

The specialized code may be a Python code object or any callable.  A
code object is run in the function's own frame, with the same globals,
defaults and closure.  A callable is called with the function's
arguments; this allows an optimizer to substitute a built-in function
directly, for example replacing a Python wrapper with ``len``.

Specialized code objects must have the same signature as the original:
the same number and names of arguments, the same keyword-only arguments,
and the same free variables.  ``PyFunction_Specialize`` checks this.

Changing a function's ``__code__`` attribute removes all
specializations, since they were derived from the old code.


Guards
======

A guard is a C object implementing:

``int init(PyObject *guard, PyObject *func)``
    Called once when the guard is attached.  Returns 0 on success, 1 if
    the guard can never pass (so the specialization is discarded), or
    -1 on error.

``int check(PyObject *guard, PyObject **stack, Py_ssize_t na, Py_ssize_t nk)``
    Called on every function call.  Returns 0 if the guard passes, 1 if
    it fails, 2 if it fails forever, or -1 on error with an exception
    set.

Guards must be fast.  A guard that costs as much as the code it
protects is useless.  In particular, checking a dictionary key should
not require a dictionary lookup on every call.  Fast guards depend on
dictionary versioning, as proposed in PEP 509: each dictionary carries a
version number that changes whenever it is modified, so a guard can
detect "nothing changed" with one integer comparison and only perform a
lookup when the version differs.

This PEP does not specify a Python-level API for writing guards.
Guards implemented in Python would usually cost more than the
optimization saves.  An optimizer extension module is expected to
provide its own guard types, for example:

- A guard on a set of keys in a dictionary (globals or builtins), using
  dictionary versions.
- A guard on the type of each positional argument.
- A guard on a function's ``__code__``.


C API
=====

Add to the C API:

``int PyFunction_Specialize(PyObject *func, PyObject *code, PyObject *guards)``
    Append a specialized code or callable with a list of guards to the
    function.  Calls ``init`` on each guard.  Returns 0 on success,
    1 if the specialization was discarded because a guard can never
    pass, or -1 on error.

``PyObject *PyFunction_GetSpecializedCodes(PyObject *func)``
    Return a list of ``(code, guards)`` tuples.

``PyObject *PyFunction_GetSpecializedCode(PyObject *func, PyObject **stack, int na, int nk)``
    Return the code that would run for these arguments, after checking
    guards.  Used by the interpreter and for debugging.

``void PyFunction_RemoveSpecialized(PyObject *func, Py_ssize_t index)``
``void PyFunction_RemoveAllSpecialized(PyObject *func)``
    Remove one or all specializations.

These functions are not part of the stable ABI.


Changes
=======

- ``PyFunctionObject`` gains a field holding the specialization list.
- The call path for Python functions checks the list when it is not
  empty.  When it is empty, the overhead is a single pointer comparison.
- ``function.__code__`` setter clears the list.


Behaviour Changes
=================

None, unless an extension module calls ``PyFunction_Specialize``.  When
specializations are installed, the optimizer is responsible for ensuring
that specialized code has the same observable behaviour as the
original, apart from performance, whenever its guards pass.

Tracebacks and debuggers will show the specialized code when it runs.
Optimizers should preserve line numbers where possible.


Discussion
==========

**Why not let optimizers replace ``__code__``?**  Replacing
``__code__`` loses the original code, and there is no way to fall back
when assumptions break.

**Why in the C API and not Python?**  Guard evaluation is on the hot
call path.  A Python API could be added later on top of the C API.

**Will this slow down Python?**  Benchmarks show no measurable
difference when no function is specialized.

**Is this a JIT?**  No.  It is a mechanism that both ahead-of-time and
just-in-time optimizers can use.  It does not generate machine code.


Prior Art
=========

PyPy and Pyston use guards and deoptimization internally.  The Psyco
project specialized functions on argument types.  JavaScript engines
such as V8 rely on similar "inline caches" with fallback paths.
