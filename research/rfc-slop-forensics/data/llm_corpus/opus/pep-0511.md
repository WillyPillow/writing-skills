PEP: 511
Title: API for code transformers
Status: Draft
Type: Standards Track
Created: 2016
Python-Version: 3.6

# Abstract

This PEP proposes an API to register bytecode and AST transformers. It also adds a `-o OPTIM_TAG` command line option to change the names of `.pyc` files, with `-o noopt` disabling the peephole optimizer. An `ImportError` is raised on import if the `.pyc` file is missing and the code transformers required to produce it are not registered. Code transformers are not needed for code that was transformed ahead of time and is loaded from `.pyc` files.

# Rationale

Several projects want to change how Python source is compiled:

- **Optimizers.** Static optimizers such as constant folding beyond what the peephole optimizer does, function inlining, loop unrolling, or specialisation based on type guards.
- **Language extensions.** Projects that add syntax-like features through macros, for example pattern matching or domain specific languages implemented as AST rewrites.
- **Instrumentation.** Coverage tools, profilers and debuggers that insert hooks into code.
- **Teaching and experimentation.** Tools that rewrite code to make it easier to inspect, or to try out a proposed language feature before it is accepted.

Each of these projects currently has to invent its own way of hooking into compilation. The usual method is a custom import hook that reads the source, parses it with `ast`, transforms it, and compiles the result. This is fragile and limited:

- Import hooks only affect code loaded through the import system. They do not affect code passed to `compile()`, `exec()` or `eval()`, nor the main script, nor the interactive interpreter.
- Multiple projects installing import hooks frequently conflict.
- Transformed code is written to `.pyc` files with the same name as untransformed code, so switching between configurations silently uses stale bytecode.
- There is no standard way to apply transformations ahead of time and ship only the result.

A standard API solves these problems once and makes code transformation a supported, composable feature.

# Proposal

## Code transformer objects

A code transformer is an object with a `name` attribute and one or both of the following methods:

- `ast_transformer(tree, context)`: receives an `ast.Module` (or other top-level AST node) and returns a transformed tree. It may modify the tree in place and return it.
- `code_transformer(code, context)`: receives a code object and returns a transformed code object.

The `context` argument is an object with at least these attributes:

- `filename`: the file name passed to `compile()`,
- `optimize`: the optimization level.

The `name` is a short string used to build the optimizer tag. It must be a valid identifier-like string without dots or dashes.

## Registering transformers

Two new functions are added to the `sys` module:

- `sys.set_code_transformers(transformers)`: set the list of active transformers.
- `sys.get_code_transformers()`: return the current list.

Transformers are applied in list order. All AST transformers run first, after parsing and before compilation to bytecode. Then all bytecode transformers run, after the peephole optimizer.

## The optimizer tag

`sys.implementation.optim_tag` is a new string that identifies the transformation pipeline in effect. By default it is `"opt"`. When transformers are registered, it becomes the dash-separated list of their names, for example `"fat-macro"`.

The tag is included in `.pyc` file names. Today, cached bytecode is stored as `module.cpython-36.pyc`, or with an `opt-1` or `opt-2` suffix for `-O` and `-OO`. With this PEP, the name becomes `module.cpython-36.fat-macro.pyc` when transformers `fat` and `macro` are active. Code compiled with different transformers therefore never shares a cache file.

## The `-o` command line option

A new `-o OPTIM_TAG` option sets `sys.implementation.optim_tag` explicitly. The special value `noopt` disables the built-in peephole optimizer, and produces `.pyc` files tagged `noopt`. This is useful for debuggers and coverage tools that want bytecode which corresponds as closely as possible to source lines.

## Importing with a missing transformer

When the import system looks for a `.pyc` file under the current tag and finds none, it would normally compile the source. If the tag names transformers that are not registered, compiling from source would produce code that differs from what the tag promises. In that case an `ImportError` is raised, with a message naming the missing transformers.

This lets a project ship `.pyc` files produced ahead of time by an optimizer, set the optimizer tag at startup, and run them without the optimizer installed. If a `.pyc` file is missing, the user gets a clear error instead of silently running unoptimized code.

## Scope of application

Registered transformers apply to all code compiled by the interpreter: modules loaded through import, the main script, `compile()`, `exec()`, `eval()`, and the interactive interpreter. `compile()` gains no new arguments; it simply honours the current registration.

# Examples

A transformer that replaces calls to `len()` on string literals with their computed value:

```python
import ast, sys

class FoldLen(ast.NodeTransformer):
    def visit_Call(self, node):
        self.generic_visit(node)
        if (isinstance(node.func, ast.Name) and node.func.id == "len"
                and len(node.args) == 1 and isinstance(node.args[0], ast.Str)):
            return ast.copy_location(ast.Num(len(node.args[0].s)), node)
        return node

class FoldLenTransformer:
    name = "foldlen"
    def ast_transformer(self, tree, context):
        return FoldLen().visit(tree)

sys.set_code_transformers([FoldLenTransformer()])
```

After this call, newly compiled code has the transformation applied, and its bytecode is cached under the `foldlen` tag.

# Alternatives Considered

**Keep using import hooks.** As described above, import hooks do not cover all compiled code, do not compose well, and do not solve cache invalidation.

**A single "AST hook" without bytecode transformers.** Many useful optimizations, such as rewriting jump sequences, are much easier at bytecode level. Supporting both costs little.

**Storing the transformer list inside the `.pyc` header.** This would detect mismatches but would not allow multiple variants of a module's bytecode to coexist. Encoding it in the file name does both.

# Backwards Compatibility

With no transformers registered and no `-o` option, behaviour is unchanged except that the `.pyc` file name for unoptimized code includes an `opt` tag. To preserve existing file names, the default tag is treated specially and omitted from the file name, so `module.cpython-36.pyc` is still used.

Third-party tools that construct `.pyc` paths by hand should use `importlib.util.cache_from_source()`, which will be updated to honour the optimizer tag.

# Security Considerations

Registering a transformer allows arbitrary code to change all subsequently compiled code. This does not introduce a new capability, since any code that can call `sys.set_code_transformers()` can already modify modules directly, but it does make the effect more pervasive. Applications that care should register transformers early and avoid letting untrusted code reach the `sys` module.

# Implementation

A prototype implementation exists, along with an example AST optimizer that uses guards to specialise functions. The changes to CPython are limited to the compiler entry points, the import system's cache path computation, and the command line parser.
