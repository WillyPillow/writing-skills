# Abstract

This PEP specifies how licenses are documented in Python projects. It:

- adopts the SPDX license expression syntax for declaring a project's license;
- defines how license files are included in projects and in their source and built distributions;
- specifies the changes needed to Core Metadata and the corresponding `pyproject.toml` metadata keys;
- describes the changes needed to the source distribution (sdist), built distribution (wheel), and installed project standards.

These changes make license declarations simpler and less ambiguous: easier for package authors to write, for end users to understand, and for tools to process. The Core Metadata specification is updated to version 2.4.

# Goals

- Give package authors one clear, standard way to state their project's license.
- Make that statement machine-readable without heuristics.
- Make sure the full text of the license files ends up in distributions and installed environments.
- Keep backwards compatibility with existing metadata, and give a clear migration path.

Non-goals:

- This PEP doesn't validate whether a license is "correct" for a project or whether its dependencies' licenses are compatible.
- It doesn't define license metadata for individual files within a project.
- It isn't legal advice.

# Motivation

Python packages currently declare their license in up to three ways, none of them well specified:

1. **The `License` field** in Core Metadata (and `license` in `setup()`), a free-text string. Authors fill it with anything: `MIT`, `MIT License`, `BSD`, `BSD-3`, `GPLv3+`, `Apache 2.0`, the whole text of the license, or `UNKNOWN`.
2. **Trove classifiers** such as `License :: OSI Approved :: MIT License`. These are a fixed list, but coarse. `License :: OSI Approved :: BSD License` covers several different licenses, and many common licenses have no classifier at all. They also can't say "MIT or Apache-2.0" in a structured way.
3. **License files** (`LICENSE`, `COPYING`, and so on). Whether these end up in sdists and wheels depends on the build backend and its configuration, and there is no standard metadata field that points at them.

All of this hurts several groups:

- **Organizations** that must audit the licenses of their dependencies, for compliance or before redistributing software, can't automatically tell what license a package uses. They resort to heuristics, manual review, or commercial tools.
- **Linux distributions and other redistributors** have to work out every package's license by hand.
- **Package authors** don't know what to write and get no feedback when they get it wrong.
- **Tools** like PyPI's web interface and license scanners show inconsistent and sometimes misleading information.

The SPDX project, from the Linux Foundation, maintains a list of license identifiers and a small expression language for combining them. Other ecosystems have adopted it widely, including npm, Cargo, Maven, RubyGems, and the Linux kernel. Adopting it for Python fits the wider open-source world.

# Rationale

## Why SPDX?

SPDX identifiers are short, unambiguous, and kept up to date by a neutral body. The expression syntax (`MIT OR Apache-2.0`, `GPL-3.0-or-later WITH Classpath-exception-2.0`) covers dual licensing and exceptions. Tooling to parse and validate expressions already exists in many languages, Python included.

## Why a new field rather than reusing `License`?

The existing `License` field contains years of free text. Reinterpreting it as an SPDX expression would make existing metadata ambiguous, since `MIT` would be valid but `MIT License` would not. A new field lets tools tell legacy and new declarations apart reliably.

## Why record license file paths?

An identifier says which license applies. It doesn't hold the copyright notices, attribution, or modified terms that many license files contain. The license texts must ship with the software, and recording their paths in metadata lets tools find them.

# Specification

## Core Metadata

The Core Metadata version becomes **2.4**. Two fields are added.

### `License-Expression`

```
License-Expression: MIT OR Apache-2.0
```

Optional, appears at most once. The value must be a valid SPDX license expression, made of SPDX license identifiers, `LicenseRef-` custom identifiers, and the operators `AND`, `OR`, `WITH`, and parentheses. Tools should normalize identifiers to their canonical case when building distributions and must treat them case-insensitively when reading.

Custom identifiers of the form `LicenseRef-<name>` are allowed for licenses not on the SPDX list. Build tools should warn if they can't find a matching license file.

### `License-File`

```
License-File: LICENSE
License-File: licenses/NOTICE.txt
```

Optional, may appear more than once. Each value is the path of a license file relative to the `.dist-info/licenses/` directory in a wheel or installed project, or relative to the project root in an sdist. Paths use `/` as the separator and must not contain `..`.

### Deprecations

- If `License-Expression` is present, the `License` field must not be present. Tools reading old metadata should continue to accept `License`.
- `License ::` trove classifiers are deprecated. Build tools should raise an error if a project specifies both `License-Expression` and any `License ::` classifier.

## `pyproject.toml`

In the `[project]` table:

### `license`

The `license` key now accepts a string, which is an SPDX license expression:

```toml
[project]
license = "MIT OR Apache-2.0"
```

The old table form (`license = { file = "LICENSE" }` or `license = { text = "..." }`) is deprecated. Tools must keep accepting it for now and should warn.

### `license-files`

A new key, `license-files`, is an array of glob patterns relative to the directory containing `pyproject.toml`:

```toml
[project]
license-files = ["LICEN[CS]E*", "AUTHORS*", "licenses/*.txt"]
```

Build tools must include every matching file in the sdist and in the wheel, and must record each one in a `License-File` field. A pattern that matches nothing is an error. The glob syntax is limited to `*`, `?`, `**`, and `[...]` character classes.

If `license-files` isn't given, tools may use a default set of patterns (for example `LICEN[CS]E*`, `COPYING*`, `NOTICE*`, `AUTHORS*`), but they must record what they included.

## Source distributions

License files are kept at their original paths. The sdist's `PKG-INFO` lists them in `License-File` fields.

## Wheels

License files are stored under `<name>-<version>.dist-info/licenses/`, keeping their paths relative to the project root. For example, `licenses/NOTICE.txt` in the project becomes `.dist-info/licenses/licenses/NOTICE.txt` in the wheel. Putting them in a subdirectory avoids name clashes with other `.dist-info` files.

## Installed projects

Installers must copy the `licenses/` directory into the installed `.dist-info` directory, so that license texts are present in every environment where the project is installed.

# Backwards Compatibility

Existing distributions are unaffected. Tools that read metadata must accept older versions with the free-text `License` field and with classifiers.

Projects that adopt `License-Expression` produce Metadata 2.4. Older tools that don't recognize the new fields will ignore them. PyPI must accept Metadata 2.4 uploads before projects can publish them.

# Security Implications

License file paths are restricted to relative paths without `..` so that malicious metadata can't make installers write files outside the `.dist-info` directory.

# How to Teach This

Packaging guides should tell authors to:

1. look up their license's SPDX identifier;
2. set `license = "<identifier>"` in `pyproject.toml`;
3. make sure `license-files` matches their license file(s);
4. remove `License ::` classifiers.

A migration table from common classifiers to SPDX identifiers will go in the packaging user guide, with a note that ambiguous classifiers such as the generic BSD one need the author to check which license they actually use.

# Rejected Ideas

- **Mapping classifiers automatically to SPDX.** Many classifiers are ambiguous. Converting them automatically would produce wrong declarations that look authoritative.
- **Embedding license text in metadata.** This makes metadata large and duplicates the files.
- **A custom expression syntax.** Reinventing SPDX gives no benefit and makes Python an outlier.
