# Abstract

When Python looks up an attribute on a class or instance, it walks the class's method resolution order (MRO) and checks each class's `__dict__` directly. Both `object.__getattribute__` and `super.__getattribute__` do this, through the internal function `_PyType_Lookup`. There is no hook between "walk the MRO" and "look in the dictionary."

This PEP adds an optional method, `__getdescriptor__`, that a metaclass can define to take over the per-class part of that lookup. The MRO walk changes from:

```python
def lookup(mro_list, name):
    for cls in mro_list:
        if name in cls.__dict__:
            return cls.__dict__[name]
    return NotFound
```

to:

```python
def lookup(mro_list, name):
    for cls in mro_list:
        try:
            return cls.__getdescriptor__(name)
        except AttributeError:
            pass
    return NotFound
```

The default implementation on `type` reads the class dictionary, so existing code behaves the same:

```python
class type:
    def __getdescriptor__(cls, name):
        try:
            return cls.__dict__[name]
        except KeyError:
            raise AttributeError(name) from None
```

# Motivation

Python already lets a class customize attribute access through `__getattribute__` and `__getattr__`. Those hooks are enough for most purposes, but they have one important gap: `super()` ignores them.

When you write `super().method()`, the `super` object walks the MRO starting after the current class and looks in each class's `__dict__`. It does not call the metaclass's `__getattribute__`, because doing so would start the search from the wrong place and could not stop at the right class. The result is that any class whose attributes are not physically stored in `__dict__` is invisible to `super()`.

That situation is more common than it sounds. Some examples:

- **Bridges to other object systems.** PyObjC exposes Objective-C classes as Python classes. Objective-C methods can be added at runtime, and there are thousands of them across the system frameworks. Copying every method into the Python class's `__dict__` up front is slow and uses a lot of memory, and it would still miss methods added later. PyObjC therefore resolves methods lazily. Today it has to maintain its own copy of `super` to make `super().method()` work, and that copy breaks whenever it is mixed with code that uses the builtin.
- **Lazy loading.** A class could load rarely used methods from a database or a compiled extension only when they are first requested.
- **Case-insensitive or aliased names.** A wrapper around a case-insensitive foreign API might want `obj.GetValue` and `obj.getvalue` to resolve to the same method.

In all of these cases the class can implement a custom `__getattribute__` for ordinary lookups. The problem is cooperative inheritance: once a subclass calls `super()`, the custom lookup is bypassed.

`__getdescriptor__` fixes this by putting the hook at the level where both normal lookup and `super` already meet. Both go through a per-class check, and this PEP lets the metaclass own that check.

# Specification

## The method

`__getdescriptor__(cls, name)` is a method defined on a metaclass. It is called with a class and an attribute name (a `str`). It returns the object that would be found in that class for that name, without invoking the descriptor protocol on it, or raises `AttributeError` if the class does not define the name.

The method looks only at the given class. It must not look at base classes; the caller handles the MRO.

`type.__getdescriptor__` implements the current behavior.

## Where it is called

`_PyType_Lookup` and `super.__getattribute__` call `type(cls).__getdescriptor__(cls, name)` for each class on the MRO, in order, until one does not raise `AttributeError`.

Because `__getdescriptor__` is looked up on the metaclass, it is not affected by anything defined on the class itself. That mirrors how other special methods are looked up.

## C API

A new slot, `tp_getdescriptor`, is added to `PyTypeObject`:

```c
typedef PyObject *(*getdescriptorfunc)(PyTypeObject *, PyObject *);
```

The function returns a new reference, or `NULL` without setting an exception when the name is not found. Not setting an exception on the "not found" path avoids the cost of creating an `AttributeError` for every miss, which matters because most MRO entries miss.

A type with a Python-level `__getdescriptor__` gets a slot wrapper, as with other special methods.

## Method cache

CPython caches the results of `_PyType_Lookup` in a global method cache, keyed by type version tag. The cache relies on the fact that changing a class's `__dict__` invalidates the version tag of that class and its subclasses.

A custom `__getdescriptor__` can return different results without any change to `__dict__`, so the cache cannot be trusted for such classes. The rule is: if any class on the MRO has a metaclass with a non-default `__getdescriptor__`, the type is not given a valid version tag and the cache is bypassed. Metaclasses that know when their results change can call `PyType_Modified` to opt back in to caching. A follow-up could expose a Python-level way to do this.

## Interaction with `__getattribute__`

Nothing changes in the order of operations inside `object.__getattribute__`. It still looks up the name on the type first (now via `__getdescriptor__`), checks for data descriptors, then checks the instance dictionary, then non-data descriptors. Only the "look in each class" step is replaced.

# Example

```python
class LazyMeta(type):
    def __getdescriptor__(cls, name):
        try:
            return cls.__dict__[name]
        except KeyError:
            pass
        loader = cls.__dict__.get("_lazy_loader")
        if loader is not None:
            value = loader(name)
            if value is not None:
                return value
        raise AttributeError(name)

class Base(metaclass=LazyMeta):
    @staticmethod
    def _lazy_loader(name):
        if name == "greet":
            return lambda self: "hello from Base"
        return None

class Child(Base):
    def greet(self):
        return "child, then " + super().greet()

print(Child().greet())   # child, then hello from Base
```

Without this PEP, `super().greet()` raises `AttributeError`, because `greet` is not in `Base.__dict__`.

# Backward compatibility

Classes that do not define `__getdescriptor__` behave exactly as before.

Code that inspects `cls.__dict__` directly, such as `inspect.getattr_static`, will not see attributes provided by a custom `__getdescriptor__`. That is consistent with how such code already treats `__getattr__`. `inspect` could be updated to call `__getdescriptor__`, but changing it is not required.

# Performance

The common path, where every class uses the default `__getdescriptor__`, can be kept as fast as today: `_PyType_Lookup` can check whether the slot is the default implementation and fall back to the existing dictionary probe. Benchmarks of a prototype show no measurable difference on the standard benchmark suite.

Classes with a custom implementation lose the method cache unless they opt in, and pay for a Python-level call per class on the MRO. That is the expected cost for opting into dynamic lookup.

# Alternatives

**Make `super` call `__getattribute__`.** This does not work, because `__getattribute__` resolves against the whole MRO and has no way to start partway through.

**Add a hook to `super` only.** That would fix `super` but leave normal lookup and `super` lookup with different semantics, which is worse than today.

**Make `__dict__` a custom mapping.** Allowing any mapping as a class dictionary would also solve the problem, but CPython relies heavily on the class dictionary being an exact `dict`, and lifting that would be a much larger and slower change.

# Open issues

- Should the Python-level method receive the name as `str` only, or should it also accept other types the way `__dict__` lookup technically does?
- Should there be a Python-level API for re-enabling the method cache?
