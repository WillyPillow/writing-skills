PEP: 573
Title: Module State Access from C Extension Methods
Status: Draft
Type: Standards Track
Python-Version: 3.9
Created: 02-Jun-2016

# Abstract

This PEP proposes a way for CPython extension methods to access context, such as the state of the module they are defined in. Extension methods can then use a direct pointer dereference instead of `PyState_FindModule` to look up module state, which reduces or eliminates the performance cost of using module-scoped state over process-global state.

This removes one of the remaining roadblocks to adopting PEP 3121 (Extension Module Initialization and Finalization) and PEP 489 (Multi-phase Extension Module Initialization). The PEP takes a further step toward solving the problems those PEPs started to address, but it does not resolve all of them. In particular, access to module state from slot methods (`nb_add` and similar) is not solved here.

# Motivation

## Where module state lives today

Most C extension modules keep their state in C static variables: cached type objects, exception classes, interned strings, configuration. This is simple and fast, but it has real costs:

- The module cannot be safely loaded more than once in a process, for example in multiple subinterpreters. All instances share the same globals.
- The module cannot be fully unloaded and reloaded, since static state outlives the module object.
- Per-interpreter isolation, which is a prerequisite for running subinterpreters in parallel, is impossible.

PEP 3121 introduced per-module state: a block of memory attached to the module object, sized by `PyModuleDef.m_size`, retrieved with `PyModule_GetState(module)`. PEP 489 made it possible to create module objects in a way that supports multiple instances. Together they give extension authors the tools to avoid global state.

## Why authors do not use it

The problem is getting from a function to the module state. A module-level function defined with `PyMethodDef` receives the module as its `self` argument, so it can call `PyModule_GetState(self)` directly. But methods of types defined by the module receive an instance of the type as `self`, not the module. Nothing connects that instance back to its module.

The available workaround is `PyState_FindModule(&module_def)`, which looks up the module in a per-interpreter table. It has two problems:

1. It is slower than a pointer dereference: a call, an index lookup, and some checks on every method invocation.
2. It only supports one module instance per interpreter per `PyModuleDef`, which is exactly the limitation PEP 489 set out to remove.

So an author who wants to convert a module to PEP 489 style must either accept a performance hit on every method call or give up multi-instance support. Most choose to keep using static globals.

## Example

Consider a module that defines a type `Point` and a custom exception `PointError`, and caches it in module state. A method on `Point` that raises `PointError` needs to find it:

```c
static PyObject *
Point_validate(PointObject *self, PyObject *Py_UNUSED(ignored))
{
    PyObject *module = PyState_FindModule(&point_module_def);
    point_state *state = PyModule_GetState(module);
    if (self->x < 0) {
        PyErr_SetString(state->PointError, "negative x");
        return NULL;
    }
    Py_RETURN_NONE;
}
```

With this PEP, the method can find its defining class directly and get the module from there.

# Rationale

The core observation is that a method knows which *type* it was defined on, even if `self` is an instance of a subclass. If that type records which *module* created it, then the method can reach module state in two pointer hops.

Heap types (types created with `PyType_FromSpec`) already have room for this; static types do not and cannot, since they are shared across all interpreters. This PEP therefore applies to heap types, which are also what PEP 489-style modules should be using.

The defining class matters, not `type(self)`. If a Python subclass of `Point` calls an inherited C method, `type(self)` is the Python subclass, which has no module state. The method needs the C class where it was defined.

# Specification

## Associating a module with a heap type

A new function creates a heap type and records its module:

```c
PyObject* PyType_FromModuleAndSpec(PyObject *module,
                                   PyType_Spec *spec,
                                   PyObject *bases);
```

It behaves like `PyType_FromSpecWithBases`, and in addition stores a strong reference to `module` in the new type. `module` may be `NULL`, in which case no module is associated.

Two accessors retrieve the module and its state:

```c
PyObject* PyType_GetModule(PyTypeObject *type);
void*     PyType_GetModuleState(PyTypeObject *type);
```

`PyType_GetModule` returns a borrowed reference to the associated module, or sets `TypeError` and returns `NULL` if the type is not a heap type or has no module. `PyType_GetModuleState` returns `PyModule_GetState` of that module, or `NULL` with an exception set on failure.

## Passing the defining class to methods

A new calling convention flag, `METH_METHOD`, is added. It must be combined with `METH_FASTCALL | METH_KEYWORDS`. A method with this flag has the signature:

```c
typedef PyObject *(*PyCMethod)(PyObject *self,
                               PyTypeObject *defining_class,
                               PyObject *const *args,
                               size_t nargsf,
                               PyObject *kwnames);
```

`defining_class` is the type in which this method was defined, regardless of the type of `self`. It is supplied by a new method descriptor type, `PyCMethodObject`, which extends `PyCFunctionObject` with an `mm_class` field. When a type is created with methods using `METH_METHOD`, the type machinery records the class in each method's descriptor.

Rewritten, the earlier example becomes:

```c
static PyObject *
Point_validate(PointObject *self, PyTypeObject *defining_class,
               PyObject *const *args, Py_ssize_t nargs, PyObject *kwnames)
{
    point_state *state = PyType_GetModuleState(defining_class);
    if (state == NULL) {
        return NULL;
    }
    ...
}
```

## Argument Clinic

Argument Clinic gains support for a `defining_class` parameter, declared as:

```text
    cls: defining_class
```

When present, Clinic generates a `METH_METHOD` wrapper and passes the defining class to the implementation function.

## Helper for slot methods (partial)

Slot methods such as `tp_richcompare` and `nb_add` have fixed signatures and cannot receive a defining class. For types that are never subclassed, `Py_TYPE(self)` is the defining class, and `PyType_GetModuleState(Py_TYPE(self))` works. For subclassable types, slot methods remain without a reliable path. A later PEP is expected to address this, for instance with a function that walks the MRO to find the first type whose module was created from a given `PyModuleDef`.

# Backwards Compatibility

All additions are new APIs. Existing extensions continue to work unchanged. `PyCMethodObject` is a subtype of `PyCFunctionObject`, so code that inspects builtin method objects continues to work.

# Implementation

A reference implementation adds the new type slot for the module reference, the `METH_METHOD` flag, `PyCMethodObject`, and the accessors. The `_testmultiphase` module is extended with tests that load a module twice and check that each instance's methods see their own state.

# Rejected Ideas

**Storing the module in every instance.** This costs a pointer per object and does not help functions that receive no instance.

**Using `type(self)` instead of the defining class.** As described above, this fails for subclasses defined in Python.

**Making `PyState_FindModule` faster.** Even an optimized lookup still supports only one instance per definition.
