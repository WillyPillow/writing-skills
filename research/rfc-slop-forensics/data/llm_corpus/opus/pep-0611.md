Title: The one million limit
Author: (draft)

# Abstract

This PEP proposes a soft limit of one million (1 000 000), and a larger hard limit, for various aspects of Python code and its implementation.

The Python language does not specify limits for many of its features. Having no limit on these values seems to enhance programmer freedom, at least superficially. In practice, CPython and other Python virtual machines have implicit limits, or are forced to assume that the limits are astronomical, which is expensive.

This PEP lists a number of features which are to have a limit of one million. For CPython the hard limit will be eight million (8 000 000).

# Motivation

Unbounded quantities are a recurring tax on the implementation of a virtual machine. Every time a value might in principle be arbitrarily large, the implementation must choose between two bad options: use a wide representation everywhere, or use a compact one and add overflow checks — sometimes in hot paths, and sometimes forgotten, leading to crashes or security problems.

Consider a few examples from CPython today:

- **Line numbers** are stored in a compressed table that must handle arbitrarily large deltas, complicating both the encoder and the decoder.
- **Bytecode operands** use `EXTENDED_ARG` prefixes so that jump targets, constant indices, and local variable indices can exceed 255. The interpreter must handle chains of these prefixes, and the compiler must iterate to a fixed point when jump sizes change.
- **Object headers** reserve a full machine word for the reference count. On 64-bit machines, refcounts never come close to needing 64 bits, but nothing in the language promises that they will not.
- **Number of classes.** Implementations that want to specialize on type identity — for example, by storing a small class index in an inline cache — cannot do so safely when the number of classes is unbounded.

Each of these could be simplified, made faster, or made more compact if a reasonable upper bound were part of the language specification. The real-world value of each limit is enormous in human terms: no hand-written program has a million lines in one file, a million local variables in one function, or a million classes. Generated code occasionally pushes boundaries, but it can be restructured.

There is also a security argument. Inputs to the compiler are sometimes untrusted — templating engines, notebooks, and online evaluators routinely compile user-supplied code. Without defined limits, malicious inputs can exhaust memory or trigger pathological behaviour in the compiler. Today this is addressed piecemeal; a uniform limit addresses it consistently.

# Rationale

One million was chosen because it is easy to remember, it is far larger than anything a human writes, and it fits comfortably within 20 bits. That leaves headroom when packing several such values into a single machine word together with flags or tags.

A soft limit and a separate hard limit give implementations flexibility. The soft limit is what the language guarantees: every conforming implementation must support values up to one million. Code that stays within it is portable. The hard limit is what a specific implementation enforces; implementations may support larger values, up to their hard limit, and must raise an exception rather than crash or misbehave if the hard limit is exceeded.

For CPython, the hard limit is eight million (2²³ ≈ 8.4 million), which fits within 23 bits.

# Specification

The following are limited to one million (soft limit):

1. The number of source code lines in a module.
2. The number of bytecode instructions in a code object.
3. The sum of local variables and stack usage for a code object.
4. The number of classes in a running interpreter.
5. The recursion depth of Python code.
6. The number of distinct code objects in a running interpreter.
7. The number of coroutines (including generators and async generators) alive at once.

Exceeding the soft limit is not an error by itself. Implementations may emit a warning, controlled by a new warning category `LimitWarning` (subclass of `RuntimeWarning`) when a soft limit is exceeded.

Exceeding an implementation's hard limit raises an exception:

- During compilation, a `SyntaxError` is raised, with a message indicating which limit was exceeded.
- At runtime, a `MemoryError` or a new subclass `ResourceLimitError` is raised, at the point where the limit is crossed.

In no case may an implementation crash, produce incorrect results, or exhibit undefined behaviour because a limit was exceeded.

## Inspecting limits

A new function, `sys.getlimits()`, returns a named tuple giving the implementation's hard limit for each item above. This allows tools that generate code to check limits programmatically rather than hard-coding values.

## Recursion depth

The recursion limit is special because it already exists, as `sys.setrecursionlimit()`. Under this PEP, `sys.setrecursionlimit()` continues to work but may not be set above the implementation's hard limit. The default remains implementation-defined and much smaller than one million.

# Expected benefits

The following improvements become possible in CPython once the limits are in place. None of them is mandated by this PEP; they illustrate the motivation.

**Line number tables.** With line numbers fitting in 20 bits, the line table can use fixed-width fields or simpler variable-length encoding, speeding up traceback construction and tracing.

**Bytecode.** With fewer than 2²³ instructions in a code object, jump targets fit in a 3-byte operand. A redesigned instruction format could drop `EXTENDED_ARG` chains in favour of a simpler fixed-width encoding.

**Frame layout.** A bounded local-plus-stack size allows frames to be allocated from a contiguous stack with simple bounds checks.

**Class identity.** With fewer than 2²³ classes, a class can be identified by a small integer, enabling compact inline caches for attribute lookup and method calls.

**Object headers.** Combining the class index limit with a bound on reference counts would allow, in principle, a reduced object header. This is a longer-term possibility that would require separate discussion.

# Backwards Compatibility

Code that exceeds the hard limits will no longer work. We are not aware of any human-written code that would be affected. Generated code is more likely to be affected; the most likely case is very large generated modules containing data tables. Such code can be restructured by splitting it across multiple modules or by loading data from files at runtime.

A deprecation period is proposed: in the first release implementing this PEP, exceeding a hard limit raises a `DeprecationWarning` where practical, and becomes an error in the following release.

# Other implementations

PyPy, GraalPython, MicroPython and others are free to choose their own hard limits, provided they are at least the soft limit. MicroPython, which targets very constrained devices, may in practice fail earlier due to memory exhaustion; this is permitted as long as failure is reported cleanly as a `MemoryError`.

# Rejected ideas

**Different limits for each feature.** Choosing an optimal limit per feature would extract a little more benefit, but a single number is far easier to remember, document, and teach.

**No soft limit; only implementation-specific limits.** This would give no portability guarantee. Code that works on CPython could fail on another implementation with no indication of which is wrong.

**Larger limits (for example, 2³¹).** These would provide little practical benefit over the status quo, since 32-bit fields are already widely available. The value comes from limits small enough to allow packing.

# Open Issues

- Which exception type should be raised at runtime when a limit is exceeded?
- Is the limit on the number of live coroutines realistic for heavily concurrent servers? Some high-throughput asyncio applications may approach it.
- Should limits apply per interpreter or per process when subinterpreters are used?
