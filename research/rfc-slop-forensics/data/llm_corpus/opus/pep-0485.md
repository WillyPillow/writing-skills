# PEP 485: A Function for testing approximate equality

| Field | Value |
|---|---|
| PEP | 485 |
| Title | A Function for testing approximate equality |
| Status | Final |
| Type | Standards Track |
| Python-Version | 3.5 |

## Abstract

This PEP proposes adding an `isclose()` function to the standard library `math` module. The function determines whether one value is approximately equal, or "close", to another.

## Rationale

Floating-point values carry limited precision, and many decimal values cannot be represented exactly. Calculations that are mathematically equal often produce slightly different results:

```python
>>> 0.1 + 0.2 == 0.3
False
>>> sum([0.1] * 10) == 1.0
False
```

The standard advice is never to compare floats with `==` and instead to check whether they are close enough. Doing that correctly is surprisingly subtle. Users routinely write something like

```python
abs(a - b) < 1e-9
```

which works only when `a` and `b` are near 1. For values around `1e20` it never succeeds unless they are exactly equal, and for values around `1e-20` it always succeeds even when they differ by orders of magnitude.

A relative comparison fixes the scale problem but introduces others: which value is the reference, what happens near zero, and how infinities and NaNs behave. Every user who needs this ends up rediscovering these issues, and the solutions found online are often wrong.

`unittest` has `assertAlmostEqual`, but it rounds to a number of decimal places, which is an absolute tolerance in disguise, and it is only available in tests. NumPy has `allclose` and `isclose`, but they are asymmetric and pull in a large dependency.

A single, correct, well-documented function in the `math` module would serve the common case and give people a reference for what "close" should mean.

## Proposed Implementation

```python
isclose(a, b, *, rel_tol=1e-09, abs_tol=0.0) -> bool
```

Return `True` if `a` and `b` are close to each other, `False` otherwise.

The test is:

```python
abs(a - b) <= max(rel_tol * max(abs(a), abs(b)), abs_tol)
```

- `rel_tol` is the relative tolerance: the maximum allowed difference, relative to the larger absolute value of `a` and `b`. The default `1e-9` requires the values to agree to about nine significant decimal digits. It must be non-negative.
- `abs_tol` is the minimum absolute tolerance, useful for comparisons near zero. It must be non-negative.

Special cases:

- If `a == b`, the result is `True`. This handles equal infinities.
- If either value is `inf` or `-inf` and they are not equal, the result is `False`. An infinity is not close to any finite number, however large the tolerance.
- If either value is NaN, the result is `False`. NaN is not close to anything, including itself.
- If either tolerance is negative, `ValueError` is raised.

The function accepts any values that can be converted to `float`. A companion `cmath.isclose()` handles complex numbers, using `abs()` of the complex difference.

## Behavior near zero

Relative tolerance is meaningless when one of the values is zero: no nonzero value is within any relative tolerance of zero, because the allowed difference is a fraction of the larger value and the difference *is* the larger value. With the default `abs_tol=0.0`,

```python
>>> isclose(1e-30, 0.0)
False
```

This is deliberate. There is no default absolute tolerance that is right for all problems: `1e-9` is negligible for distances in meters and enormous for masses of electrons. Users comparing against zero must choose an `abs_tol` appropriate to their data. The documentation calls this out explicitly.

## Choice of relative tolerance test

There are several reasonable ways to define relative closeness. Given values `a` and `b` and tolerance `tol`, candidates include:

1. **Asymmetric**: `abs(a - b) <= tol * abs(b)`, treating `b` as the expected value.
2. **Weak symmetric**: `abs(a - b) <= tol * max(abs(a), abs(b))`.
3. **Strong symmetric**: `abs(a - b) <= tol * min(abs(a), abs(b))`.
4. **Average**: `abs(a - b) <= tol * (abs(a) + abs(b)) / 2`.

The asymmetric test has a natural interpretation in testing ("is the computed value within tolerance of the expected one?") but means `isclose(a, b)` and `isclose(b, a)` can differ, which surprises people and is awkward outside of tests.

The three symmetric tests differ only for large tolerances. For tolerances of practical interest, well under 1%, the results are indistinguishable. This PEP chooses the weak test (2) because it is the most permissive symmetric test, is easy to explain, and is what Knuth describes as "approximately equal".

Making the function symmetric matters more than which symmetric test is chosen.

## Default tolerance

The default `rel_tol=1e-9` is roughly half the precision of a double. It is loose enough that the results of a typical short chain of arithmetic operations compare as close, and tight enough that values differing in a meaningful way do not. Any default is a compromise. Users with stronger requirements are expected to pass their own.

## Integers, Decimals and Fractions

The `math` module works on floats, so `math.isclose()` converts its arguments to float. This is fine for `int` and `Fraction` in the common range. For `Decimal`, converting to float loses precision, so users who need decimal accuracy should compute the comparison in `Decimal` directly. Making the function generic over numeric types was considered and rejected as a larger change than this PEP is meant to be.

## Relative difference function

Some reviewers asked for a function returning the relative difference itself, so that users could apply their own threshold. That would be useful but does not remove the need for `isclose()`: the tricky parts are the special cases, which a relative difference function would have to handle just as carefully. It can be added later if there is demand.

## Expected uses

- **Tests.** Checking computed results against expected values. A future change could make `unittest` use `isclose()` in a new assertion method.
- **Convergence checks.** Iterative algorithms stop when successive results are close.
- **Comparing measured data.** Where values come from instruments with known relative precision.

It is not intended to replace careful numerical analysis. Users who need guarantees about error bounds should reason about them explicitly.

## Inappropriate uses

`isclose()` should not be used as a hash-compatible equality: it is not transitive. `a` may be close to `b` and `b` close to `c` while `a` is not close to `c`. It must not be used as a key equality for dictionaries or sets.

## Other approaches

- **Units in the last place (ULPs).** Comparing the number of representable floats between two values is precise but hard for most users to reason about, and it gives counter-intuitive results across powers of two.
- **Adding to `unittest` only.** Floating-point comparisons are needed outside tests.
- **Leaving it to NumPy.** Many users do not use NumPy, and NumPy's asymmetric definition differs from what this PEP recommends.

## Reference Implementation

A pure-Python prototype and a C implementation for the `math` module accompany this PEP, with tests covering the special cases above.
