PEP: 520
Title: Preserving Class Attribute Definition Order
Author: Eric Snow
Status: Final
Type: Standards Track
Created: 07-Jun-2016
Python-Version: 3.6

Abstract
========

The class definition syntax is ordered by nature: statements in a class
body execute top to bottom, and attributes are introduced in that order.
Aside from helping readability, that order is sometimes significant to
the program.  If it were available after the class is created, code
could use it without extra boilerplate such as custom metaclasses or
manually listing attribute names.

The information already exists while the class body runs, so making it
available is a reasonable expectation.  However, Python does not
currently keep it.  This PEP changes that: the order in which attributes
are introduced in a class body will be preserved in a new
``__definition_order__`` attribute on the class.  This enables
introspection of the original definition order, for example by class
decorators.

In addition, the default namespace used to execute a class body
becomes an ordered mapping.


Motivation
==========

Many tools care about the order of things in a class:

- Serialisation libraries and ORMs map class attributes to fields, and
  want the fields to appear in the order the user wrote them, for
  example as columns in a table or members of a struct.
- Command-line and configuration frameworks build options from class
  attributes and want help output in source order.
- Enum-like and record-like helpers want to number members in order.
- Documentation tools want to present members in the order the author
  chose.

Since Python 3.0, metaclasses can provide a ``__prepare__`` method that
returns an ordered mapping, and record the order themselves.  That works,
but it has costs:

- A metaclass is a heavy tool for something so simple.  It must be
  written, documented and understood.
- Metaclasses do not compose.  A class can only have one metaclass, so a
  library that needs ordering conflicts with any other library that
  needs a metaclass.
- Class decorators, which are the lighter-weight and composable
  mechanism, cannot recover the order because by the time they run the
  namespace has been copied into an unordered ``dict``.

The result is that libraries either reimplement the same metaclass,
require users to list attribute names twice, or rely on tricks such as
global creation counters on descriptor instances.

With ``__definition_order__`` available on every class, decorators and
other introspection code can get the order directly.


Specification
=============

Part 1: Ordered class namespace
-------------------------------

``type.__prepare__()`` returns an ``OrderedDict`` (or any mapping that
preserves insertion order).  Thus, by default, the class body is executed
in an ordered namespace.

Metaclasses that define their own ``__prepare__`` are unaffected.

Part 2: ``__definition_order__``
--------------------------------

When ``type.__new__`` creates a class, it sets ``__definition_order__``
on the class, as follows:

- If the class namespace already contains ``__definition_order__``, that
  value is used unchanged.  It must be a tuple of identifier strings or
  ``None``; otherwise ``TypeError`` is raised.  This allows a class body
  or metaclass to override the computed order.

- Otherwise, if the namespace is an ordered mapping, the value is a
  tuple of its keys in insertion order, excluding "dunder" names (those
  that start and end with two underscores).

- Otherwise, the namespace's order is not known, and the value is
  ``None``.

Excluding dunder names avoids reporting ``__module__``, ``__qualname__``,
``__doc__`` and similar entries that the compiler inserts implicitly, and
which are not part of the user's intended "fields".

``__definition_order__`` is a read-only attribute of the class: it is
stored in the type's ``__dict__`` and assignments to it after class
creation raise ``AttributeError``.  Its value is never changed by
setting or deleting other attributes on the class later.

Classes created by the C API, such as built-in types, have a
``__definition_order__`` of ``None``.

Example
-------

::

    class Spam:
        ham = None
        eggs = 5
        def __init__(self):
            pass
        @property
        def size(self):
            return 1

Since ``__init__`` is a dunder name, it is excluded::

    >>> Spam.__definition_order__
    ('ham', 'eggs', 'size')

A class decorator can now rely on the order::

    def fields(cls):
        cls._fields = tuple(
            name for name in cls.__definition_order__
            if not callable(getattr(cls, name)))
        return cls


Why a tuple?
============

A tuple is immutable, which makes it clear that the attribute records a
historical fact about the class body rather than something that tracks
the current namespace.  It is also cheap to store and easy to use.


Why not just make ``__dict__`` ordered?
=======================================

A class's ``__dict__`` is a ``mappingproxy`` over the type's internal
dictionary.  Even if that dictionary preserved insertion order, the
order would change as attributes are added to or removed from the class
after creation, for example by decorators or monkeypatching.  It would
also include dunder names.  ``__definition_order__`` captures the order
as it was in the class body, and is unaffected by later changes.

That said, if the internal dictionary of types becomes ordered in a
future release, ``__dict__`` will provide a useful order too.  The two
features are complementary.


Why exclude dunder names?
=========================

Names like ``__module__`` and ``__qualname__`` are added by the compiler,
not by the user, and their position is an implementation detail.  Other
dunder names such as ``__init__`` and ``__repr__`` are special methods,
which are rarely the "attributes" that order-sensitive tools care about.
Code that wants them can still inspect the namespace directly through a
metaclass.


Backward Compatibility
======================

This PEP adds a new attribute and changes the type of the default class
namespace.  Code that checks ``type(namespace) is dict`` inside a
metaclass ``__new__`` could be affected, but such checks are unusual.

``OrderedDict`` is implemented in C in 3.6, so execution of class bodies
should not become measurably slower.

Classes that already define a ``__definition_order__`` attribute for
their own purposes will continue to see their value, though it must now
be a tuple of strings or ``None``.


Other Python Implementations
============================

Implementations must preserve class body order and set
``__definition_order__`` accordingly.  PyPy already uses an ordered
dictionary for all ``dict`` objects, so the change is straightforward.


Rejected Ideas
==============

Using a list
    A list could be mutated, which would give a false impression that
    it tracks the class.

Making ``__definition_order__`` a property of ``type``
    Computing the order lazily would require keeping the original
    namespace alive.

Including dunder names
    See above.

Requiring an explicit opt-in
    The whole point is to make the order available without boilerplate.


Implementation
==============

A patch is available on the issue tracker.  It changes
``type.__prepare__`` and ``type.__new__`` in ``Objects/typeobject.c``.
