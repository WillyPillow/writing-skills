# Summary

This RFC proposes the 2017 Rust Roadmap, following the process established in RFC 1728. The roadmap sets out where the Rust project should be in a year's time.

**This year's focus is improving Rust's productivity, while keeping its emphasis on fast, reliable code.** By the end of 2017:

- Rust should have a lower learning curve.
- Rust should have a pleasant edit-compile-debug cycle.
- Rust should provide a solid, if basic, IDE experience.
- Rust should provide easy access to high-quality crates.
- Rust should be well equipped for writing robust, high-scale servers.
- Rust should have 1.0-level crates for essential tasks.
- Rust should integrate easily into large build systems.
- Rust's community should provide mentoring at all levels.

In addition, there are two exploratory goals: integrating with other languages, and making progress on usage in embedded systems.

# Motivation

Rust 1.0 shipped more than a year ago. Since then the language has gained production users at companies of every size, a growing crate ecosystem, and a reputation for safety and performance. The 2016 State of Rust survey and conversations with production users point to the same thing: people who succeed with Rust like it a great deal, but getting to that point is harder than it should be, and some people give up on the way.

Survey respondents and production users highlighted:

- **The learning curve.** Ownership and borrowing are new ideas for most programmers. Error messages and documentation have improved, but newcomers still report a period of "fighting the borrow checker" that can last weeks.
- **Compile times.** Slow builds stretch the edit-compile-test loop and erode the productivity benefits of a strong type system.
- **Tooling.** Many developers rely on IDE features such as completion, go-to-definition and inline errors, which Rust offers only in limited form.
- **Library maturity.** Many important crates are pre-1.0, under-documented, or hard to find. It is often unclear which of several crates for a task is the one to use.
- **Server-side use.** Rust's async I/O story is in flux, which makes networked services harder to build than in comparable languages.
- **Integration.** Organizations with existing build systems and codebases find it hard to introduce Rust incrementally.

These are not fundamental limitations of the language. They are gaps in its surroundings that can be closed with focused effort. That makes productivity the right theme for 2017.

# Detailed design

## The goals

### Rust should have a lower learning curve

We want people to reach productivity faster. That means improving:

- **Documentation.** A revised edition of *The Rust Programming Language* that teaches ownership early and with more examples. Better API documentation with examples for every public item in the standard library.
- **Error messages.** Continue the error message overhaul, with explanations focused on what the user should do next.
- **Language ergonomics.** Identify places where the language requires annotations or workarounds that do not add safety, and propose targeted changes. Candidates include non-lexical lifetimes, default binding modes in patterns, and inference of trivial bounds.

Success means that new users report reaching productivity substantially faster in next year's survey.

### Rust should have a pleasant edit-compile-debug cycle

Incremental compilation should be available on stable and should make the common "change one function and rebuild" case much faster. `cargo check` should be widely used to type-check without generating code. Debugger support should improve so that inspecting Rust values in gdb and lldb shows readable output.

### Rust should provide a solid, but basic, IDE experience

The Rust Language Server should reach a usable state, providing completion, go-to-definition, find references, and inline diagnostics in major editors. It does not need to rival mature IDEs for other languages, but it should be reliable enough that people choose to use it.

### Rust should provide easy access to high-quality crates

crates.io should help users find good crates: better search, categories, badges for CI and documentation status, and download trends. We should also identify crates that are de facto standards and help them reach 1.0.

### Rust should be well equipped for writing robust, high-scale servers

The futures and Tokio ecosystem should reach a stable foundation, with documentation and integration with common protocols (HTTP, databases). The goal is that writing an asynchronous network service in Rust is a reasonable choice for an experienced developer.

### Rust should have 1.0-level crates for essential tasks

Working with the community, identify a set of tasks that nearly every application needs (serialization, HTTP clients, logging, command-line parsing, regular expressions, date and time handling) and help the leading crates reach 1.0 quality: stable APIs, documentation, and adherence to the API guidelines, which will themselves be written this year.

### Rust should integrate easily into large build systems

Cargo should work well when embedded in other build systems such as Bazel, Buck, Make or CMake, and when used in organizations that vendor dependencies or work offline. That includes being able to obtain a build plan from Cargo, using source replacement, and building without network access.

### Rust's community should provide mentoring at all levels

Every Rust team should have clear entry points and mentoring for new contributors. We will tag mentored issues, run mentoring programs, and track how many new contributors become regular ones. Mentoring also applies to users: forums, IRC and meetups should welcome newcomers and help them succeed.

## Exploratory goals

### Integration with other languages

Rust should be easy to use alongside C, C++ and higher-level languages. We will investigate improvements to FFI tooling, such as bindgen and helpers for writing Python, Ruby and Node.js extensions, without committing to specific deliverables.

### Usage in resource-constrained environments

Embedded developers are interested in Rust. We will investigate the pain points (target support, `no_std` libraries, tooling for cross-compilation) and set clear goals for 2018.

## Non-goals

Large new language features that do not serve the productivity theme are not a priority this year. Proposals can still be made and accepted, but team bandwidth will favour the goals above.

## Tracking progress

Each goal will have a tracking issue in the rust-lang/rust-roadmap repository with concrete milestones. Teams will report progress quarterly. At the end of the year, the community survey will be used to judge whether the goals were met.

# Drawbacks

Setting a roadmap means saying no, or "not yet", to some worthwhile work. Contributors interested in areas outside the roadmap may feel their work is undervalued. The roadmap is a guide for prioritising team effort, not a restriction on what anyone may work on.

Goals phrased at this level are hard to measure precisely. We have tried to attach observable outcomes where possible, but some judgement will be needed.

# Alternatives

- **Focus on performance or new language features.** Rust already performs well, and new features increase the learning curve. Feedback strongly favours productivity.
- **Fewer goals.** A narrower roadmap would be easier to complete but would leave important gaps unaddressed. Each goal has owners and a plausible plan.

# Unresolved questions

- What exactly counts as "1.0-level" for an ecosystem crate?
- How do we measure the learning curve consistently from year to year?
