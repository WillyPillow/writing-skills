# Abstract

This PEP adds a new C API for calling objects faster. It defines a "vectorcall" protocol and calling convention, based on the "fastcall" convention CPython already uses internally. Any extension class, including user-defined ones, can use the new features.

Most of the new API is private in CPython 3.8. The plan is to settle the semantics and make it public in Python 3.9.

**Note:** This PEP covers only the Python/C API. It does not change the Python language or the standard library.

# Motivation

Calling objects is one of the most frequent things CPython does. A typical program makes millions of calls to functions, methods, builtins, and types. Every call goes through `tp_call`:

```c
PyObject *tp_call(PyObject *callable, PyObject *args, PyObject *kwargs);
```

Here `args` is a tuple and `kwargs` is a dict or `NULL`. That signature made sense in the 1990s. It is slow today, for three reasons:

1. **Tuple allocation.** The caller usually has its arguments on the interpreter's value stack or in a C array. Packing them into a new tuple for each call costs an allocation, reference-count updates, and a deallocation.
2. **Dict allocation for keywords.** Keyword arguments get the same treatment, with a dict built on every call that has them.
3. **Bound methods.** Calling `obj.method(x)` creates a temporary bound-method object, which then unpacks itself to call the function with `obj` prepended. Prepending means copying into another tuple.

CPython has worked around these costs internally for some time. Since 3.6 there has been a "fastcall" convention, `METH_FASTCALL`, in which a C function receives a pointer to an array of arguments and a count, with keywords passed as a separate tuple of names. The interpreter uses it for many builtins and has a special path for calling Python functions without building a tuple. `LOAD_METHOD`/`CALL_METHOD` avoid creating bound methods for ordinary method calls.

These fast paths, though, are hard-coded for specific types: `PyFunction_Type`, `PyCFunction_Type`, method descriptors, and a few others. Third-party extensions can't use them. Cython, for example, generates function types that behave like Python functions but get none of the fast-path treatment. Their calls go through `tp_call`, paying for the tuple and dict, even though the generated code could take arguments in C-array form.

This PEP makes the fast calling convention a protocol that any type can implement.

# Specification

## The vectorcall function pointer

A *vectorcall function* has this signature:

```c
typedef PyObject *(*vectorcallfunc)(PyObject *callable,
                                    PyObject *const *args,
                                    size_t nargsf,
                                    PyObject *kwnames);
```

- `callable` is the object being called.
- `args` is a C array of positional arguments followed by the values of any keyword arguments.
- `nargsf` is the number of positional arguments, possibly OR-ed with the flag `PY_VECTORCALL_ARGUMENTS_OFFSET` (see below). Use `PyVectorcall_NARGS(nargsf)` to get the count.
- `kwnames` is `NULL` if there are no keyword arguments, and otherwise a tuple of keyword names (exact `str` objects). Their values are the last `len(kwnames)` entries of `args`.

The function returns a new reference, or `NULL` with an exception set.

## Opting in

A type opts in by:

1. setting the new flag `Py_TPFLAGS_HAVE_VECTORCALL` in `tp_flags`; and
2. setting the new slot `tp_vectorcall_offset` to the byte offset, within instances, of a `vectorcallfunc` pointer.

Storing the pointer per instance, not per type, lets each instance pick its own implementation. A function object can point at a specialized entry point based on its code object's flags, for example a faster path for functions with no keyword-only arguments or defaults.

If the pointer at that offset is `NULL`, the object falls back to `tp_call`.

Types that set the flag must also implement `tp_call` with the same semantics. CPython provides `PyVectorcall_Call`, which implements `tp_call` on top of vectorcall, so most types can simply set `tp_call = PyVectorcall_Call`.

## Calling an object

The new API function

```c
PyObject *_PyObject_Vectorcall(PyObject *callable, PyObject *const *args,
                               size_t nargsf, PyObject *kwnames);
```

checks whether `callable` supports vectorcall and calls through it directly if so. Otherwise it builds a tuple and dict and calls `tp_call`. Callers with their arguments already in an array should use this function.

## `PY_VECTORCALL_ARGUMENTS_OFFSET`

When this flag is set in `nargsf`, the caller promises that `args[-1]` is valid memory the callee may overwrite temporarily, provided it restores the value before returning.

This makes bound-method calls free. A bound method's vectorcall implementation can write `self` into `args[-1]`, call the underlying function with `args - 1` and `nargs + 1`, then put the old value back. No copying or allocation is needed. The interpreter's call opcodes always leave a spare slot below the arguments on the value stack, so they set the flag.

Callees must not assume the flag is set, and callers must not set it unless they actually own the slot.

## Changes to existing types

In CPython 3.8 these built-in types implement vectorcall:

- `function` (Python functions)
- `builtin_function_or_method`
- `method_descriptor`, `classmethod_descriptor`, `wrapper_descriptor`
- `method` (bound methods), using the offset trick above

`type` objects don't implement it in 3.8 because class instantiation involves `__new__` and `__init__` lookup. Adding vectorcall to specific types such as `range` and `list` is left for later.

## Public and private API

In 3.8, `_PyObject_Vectorcall`, `_Py_TPFLAGS_HAVE_VECTORCALL`, and related macros carry an underscore prefix. Extensions can use them, but they may change in 3.9 based on what people learn. `tp_vectorcall_offset` takes over the slot formerly called `tp_print`, which has been unused since Python 3.0.

The intention is to drop the underscores in Python 3.9, once Cython and other heavy users have had a release cycle to try the API.

# Rationale

## Why a per-instance pointer?

One function pointer per type would be simpler, but every Python function object would then need the same entry point, which would have to check arity, defaults, and flags at the start of every call. A per-instance pointer lets the work be specialized when the function object is created.

## Why the keywords-as-names convention?

Passing keyword names as a tuple, separate from the values, means the names are often constant. The compiler can store the tuple of names among a code object's constants, so a call like `f(a, b=1, c=2)` builds no dict and no new tuple. Only the values go on the stack.

## Why `nargsf` instead of separate parameters?

Packing the offset flag into the high bit of `nargsf` keeps the signature at four arguments, which fit in registers on all common calling conventions.

# Backwards Compatibility

`tp_call` still works. Types that don't opt in behave exactly as before. Code that calls `PyObject_Call` gets the same results, and for types that support vectorcall the call may now go through the new path.

The `tp_print` slot is reused. Extensions that still set `tp_print` (which has done nothing since 3.0) would now have an invalid offset. Since this only matters when `Py_TPFLAGS_HAVE_VECTORCALL` is also set, existing extensions are not affected.

# Performance

Prototype benchmarks show that calls to Cython functions get faster by roughly the gap between `tp_call` and the built-in fast path, around 20–30% in microbenchmarks of short functions. Bound-method calls through generic C code no longer allocate. Built-in functions should perform the same as with existing fastcall, since the change only generalizes code that was already there.

# Reference Implementation

A reference implementation is available as a CPython pull request linked from the PEP discussion thread.

# Rejected Ideas

- **Making fastcall public as-is.** The existing `METH_FASTCALL` covers only `PyCFunction` and has no per-instance entry point or offset trick.
- **A type-level slot (`tp_vectorcall`).** Rejected in favor of per-instance pointers, for the reasons above. A future PEP could add both.
