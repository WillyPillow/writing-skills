PEP: 367
Title: New Super
Status: Draft
Type: Standards Track
Created: 2007
Python-Version: 2.6

# Abstract

This PEP proposes syntactic sugar for using the `super` type that automatically constructs instances of the super type, binding to the class a method was defined in and the instance (or class object, for classmethods) that the method is currently acting on.

The premise of the new usage is as follows:

```python
super.foo(1, 2)
```

to replace the old:

```python
super(Foo, self).foo(1, 2)
```

The current `__builtin__.super` would be aliased to `__builtin__.__super__`, with `__builtin__.super` to be removed in Python 3.0. It is further proposed that assignment to `super` become a `SyntaxError`, similar to the behaviour of `None`.

# Rationale

Calling a method of a parent class is one of the most common operations in object-oriented code. The `super` built-in exists to do this correctly in the presence of multiple inheritance, by following the method resolution order rather than naming a specific base class. But its current spelling has several problems.

**It repeats the class name.** Every call must name the class it appears in. This is redundant, since the compiler knows which class a method is defined in. It also creates a maintenance hazard: if the class is renamed, every `super()` call must be updated, and an outdated name may still refer to some other class and produce subtly incorrect behaviour.

**It repeats `self`.** The instance is always the first argument of the current method, which again the compiler knows.

**It is verbose.** `super(ThisClass, self).method(args)` is long enough that many programmers fall back to calling the base class directly, as in `Base.method(self, args)`. That bypasses the method resolution order and breaks cooperative multiple inheritance, which is precisely the problem `super` was introduced to solve.

**It is error-prone with copy and paste.** Methods copied from one class to another keep the original class name in their `super()` calls. The code continues to run, but calls the wrong method.

Making the correct thing as easy as the incorrect thing will encourage people to use `super` consistently.

# Specification

## Semantics

Within the body of a method defined in a class, the bare name `super` refers to an object equivalent to:

```python
__super__(__this_class__, <first argument of the method>)
```

where `__this_class__` is the class whose body lexically contains the method definition, and `<first argument>` is the value of the method's first positional parameter at the point `super` is evaluated (typically `self` or `cls`).

Thus `super.foo(1, 2)` inside a method of class `Foo` is equivalent to `super(Foo, self).foo(1, 2)` under the current rules.

For classmethods the first argument is the class object, which gives the same behaviour as `super(Foo, cls)`. For staticmethods there is no suitable first argument, and using `super` raises a `TypeError` when it is evaluated.

## How `__this_class__` is obtained

The class object does not exist when the method's function object is created, because the class body is executed before the class is constructed. The compiler therefore treats `__this_class__` as a free variable of every function defined in a class body that uses `super`. The class creation machinery fills in the cell after the class object has been created, in the same step that binds the class name.

Because the cell is filled with the class object itself, rather than by looking up the class's name at call time, renaming the class or rebinding its name does not affect `super`.

## Obtaining the first argument

The compiler emits code that loads the first local variable of the method. If the method has no positional parameters, or the first parameter has been deleted, evaluating `super` raises a `RuntimeError`. Reassigning the first parameter, for example `self = other`, changes what `super` binds to; this mirrors what writing `super(Foo, self)` explicitly would do.

## Reserved name

Assigning to `super`, whether as a local variable, global, attribute target in a `for` loop or function parameter, becomes a `SyntaxError`. This avoids the confusing situation in which code shadows the name and then relies on the new semantics. It is consistent with the handling of `None`.

## The `__super__` built-in

The existing `super` type is made available as `__builtin__.__super__`. Code that needs explicit control, for example calling a method of a class other than the one being defined, or constructing an unbound super object, can use `__super__(cls, obj)` directly.

In Python 2.6, `__builtin__.super` continues to refer to the type, and calling `super(...)` with arguments continues to work as it does today. This is necessary for compatibility. Bare `super` as described above is recognised by the compiler only when it is used without being called directly with arguments. In Python 3.0, calling `super` with arguments is removed in favour of `__super__`.

## Use outside methods

Using `super` at module level, or in a function not defined in a class body, raises a `SyntaxError` at compile time, since there is no enclosing class.

Functions nested inside methods, such as closures and lambdas, see the enclosing method's `__this_class__` but do not have the method's first argument. Within such nested functions, bare `super` raises a `SyntaxError`, and `__super__` must be used explicitly.

# Examples

```python
class Base(object):
    def greet(self, name):
        return "Hello, %s" % name

class Polite(Base):
    def greet(self, name):
        return super.greet(name) + ", nice to meet you"

class Formal(Polite):
    @classmethod
    def create(cls):
        return super.create()   # equivalent to super(Formal, cls).create()
```

# Alternatives Considered

**`super()` with no arguments.** A zero-argument call would achieve a similar effect while keeping `super` a function. It is less of a departure from existing code, but it requires special-casing a call of a built-in by name, which is arguably more magical than special-casing the name itself.

**A keyword.** Making `super` a full keyword would be the cleanest solution syntactically, but would break any code that uses `super` as an identifier, including all existing explicit calls. The proposal in this PEP stops short of that, reserving the name only for assignment.

**Automatically naming `self`.** Some languages make the instance implicitly available. That would be a far larger change to Python and is not proposed.

# Backwards Compatibility

Existing code that calls `super(Class, self)` continues to work in 2.6. Code that assigns to the name `super` becomes a syntax error; a deprecation warning will be issued in 2.6 for such code, with the error introduced in 3.0. The conversion tool for 3.0 can rewrite explicit `super(Class, self).meth()` calls to `super.meth()` when `Class` matches the enclosing class and `self` matches the first parameter.

# Reference Implementation

A prototype implementation using a bytecode hack and a metaclass demonstrates the semantics. A full implementation in the compiler is in progress.
