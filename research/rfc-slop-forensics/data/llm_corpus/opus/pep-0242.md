# PEP 242: Numeric Kinds

| Field | Value |
|---|---|
| PEP | 242 |
| Title | Numeric Kinds |
| Status | Draft |
| Type | Standards Track |
| Created | 17-Mar-2001 |
| Python-Version | 2.2 |

## Abstract

This proposal gives the user optional control over the precision and range of numeric computations, so that a computation can be written once and run anywhere with at least the desired precision and range. It is backward compatible with existing code. The meaning of decimal literals is also clarified.

## Rationale

Python's `float` is whatever the C compiler calls `double`. On almost every platform today, that is an IEEE 754 64-bit binary float, but Python does not promise this, and scientific programmers have long worked on machines where it was not true. More importantly, `double` is the only floating-point precision Python exposes. A program that needs 32-bit floats to save memory, or extended precision to control round-off, cannot ask for them in a portable way.

Integers have a similar, if less pressing, issue. Python `int` is a C `long`, which is 32 bits on some platforms and 64 bits on others. Python's automatic promotion to `long` integers hides overflow, but code that interacts with fixed-size data (binary files, C extensions, array storage) needs to know the size.

Fortran 90 solved this problem with *kinds*. A program does not say "I want a `REAL*8`". It says "I want a real type with at least 12 decimal digits of precision and an exponent range of at least 10^±300", and the compiler picks the smallest type on that machine that satisfies the request. The same source runs correctly on a workstation and on a supercomputer with a different floating-point format. This PEP brings that idea to Python.

## Supported kinds

Each Python implementation supports a finite number of **integer kinds** and **floating-point kinds**. Each kind has a fixed range (and, for floating kinds, precision). At least one integer kind and one floating kind exist: the kinds of the existing `int` and `float` types, called the **default kinds**.

An implementation may support others; for example, CPython might offer integer kinds corresponding to C `signed char`, `short`, `int`, `long` and `long long`, and floating kinds corresponding to `float`, `double`, and `long double` where these differ.

Complex numbers have the same kinds as floating-point numbers; a complex number of a given kind has real and imaginary parts of that floating kind.

## Kind objects

A **kind object** is a callable that converts its argument to a number of that kind:

```python
x = k(3.14)     # x is 3.14 converted to kind k
```

If the value cannot be represented in kind `k`, `OverflowError` is raised. Converting a floating-point value to an integer kind truncates toward zero, as `int()` does. Converting to a floating kind with less precision rounds according to the platform's rules.

Kind objects have attributes describing the kind:

- For integer kinds: `MIN` and `MAX`, the smallest and largest representable values.
- For floating kinds: `MIN` and `MAX` (the smallest and largest positive normalized values), `EPSILON` (the difference between 1 and the next representable number), `DIGITS` (decimal digits of precision), and `MIN_10_EXP` and `MAX_10_EXP`.

Kind objects compare equal if they describe the same kind.

## Kind functions

A new module, `kinds`, provides two functions that select kinds by requirements:

```python
kinds.int_kind(n)
```

returns an integer kind able to represent every integer `i` with `-10**n < i < 10**n`. If several kinds qualify, the one with the smallest range is chosen. If none qualifies, `OverflowError` is raised.

```python
kinds.float_kind(nd, n)
```

returns a floating-point kind with at least `nd` decimal digits of precision and a base-10 exponent range of at least `-n` to `n`. As with integers, the smallest qualifying kind is chosen, and `OverflowError` is raised if none exists.

The module also provides:

- `kinds.default_int_kind`, `kinds.default_long_kind`, `kinds.default_float_kind`, `kinds.default_complex_kind`: the kinds of the existing built-in types.

## Examples

A numerical routine that needs at least 12 digits:

```python
from kinds import float_kind

real = float_kind(12, 100)

def integrate(f, a, b, n):
    a, b = real(a), real(b)
    h = (b - a) / n
    total = real(0)
    for i in range(n):
        total = total + f(a + i * h)
    return total * h
```

On a typical IEEE platform, `real` is the default float kind and this code behaves exactly as it would with plain floats. On a platform whose `double` provides fewer than 12 digits, `real` selects a wider type if one exists, and fails loudly at import time if not. Either way, the programmer's intent is explicit.

A routine that packs data into a compact array:

```python
small = kinds.int_kind(4)        # values up to 9999
counts = [small(0)] * 1_000_000
```

## Arithmetic between kinds

When an arithmetic operation combines numbers of different kinds:

1. If one is an integer kind and the other a floating kind, the result has the floating kind.
2. If both are integer kinds, the result has the kind with the larger range.
3. If both are floating kinds, the result has the kind with the greater precision.

Integer overflow in a non-default integer kind raises `OverflowError`; it does not promote automatically to `long`. Automatic promotion would defeat the purpose of choosing a kind. Default-kind integers keep their existing promotion behaviour.

Mixed operations with complex numbers follow the same rules applied to their component floating kinds.

## Literals

The meaning of a literal does not change. An integer literal produces a number of the default integer kind (or `long` if it does not fit), and a floating literal produces a number of the default float kind.

To get a literal of another kind, call the kind object on it:

```python
third = real(1) / real(3)
```

This raises a subtlety. `real(0.1)` converts the default-kind float closest to 0.1, which is not necessarily the closest value of kind `real` to 0.1. For kinds with more precision than the default, that loses accuracy. To fix this, this PEP clarifies that the **compiler retains the decimal text of floating literals** that appear directly as the argument of a call, and kind objects that receive a literal can convert from that text. In practice the implementation passes a string: `real("0.1")` is always correct and equivalent, and is recommended where precision matters.

## Implementation notes

The simplest implementation adds new numeric types to the interpreter for each supported kind, sharing code with `int` and `float` via C macros or templates. An alternative is to implement kinds in an extension module, building on the existing Numeric package, which already supports several numeric type codes.

The `array` and `struct` modules should accept kind objects in place of type codes, so that kinds can be used to describe storage.

## Rejected suggestions

**Naming kinds by bit size** (`float64`, `int32`). Bit sizes are concrete, but they describe implementation rather than requirement. A program that asks for `float64` on a machine without that format cannot run. A program that asks for 12 digits can.

**Specifying precision in bits instead of decimal digits.** Decimal digits are what most users think in and what Fortran uses. Bit-level precision can be computed from the attributes for those who need it.

**Changing the default float type.** Some suggested that literals should default to the highest available precision. This would slow down all existing code and change results in ways users did not ask for.

## Backward compatibility

No existing code is affected. Programs that do not import `kinds` see no change in behaviour. The default kinds are the existing types.
