# Abstract

This PEP proposes the `make` statement, a generalization of the class-declaration syntax. Its syntax and semantics parallel class definition, so

```
make <callable> <name> <tuple>:
    <block>
```

is translated into the assignment

```
<name> = <callable>("<name>", <tuple>, <namespace>)
```

where `<namespace>` is the dict created by executing `<block>`. This is mostly syntactic sugar for

```
class <name> <tuple>:
    __metaclass__ = <callable>
    <block>
```

and it is meant to say more plainly what the statement does when the thing being created is not a class.

Other syntaxes would work too. Keeping close to the class statement means that anyone who understands classes and metaclasses will also understand the `make` statement.

# Motivation

The class statement does two things. It runs a block of code in a fresh namespace, and it passes that namespace, along with a name and a tuple of bases, to a callable (the metaclass). Running a block to collect a set of named values is useful far beyond defining classes.

Python programmers already know this, and they exploit it by bending the class statement to other ends. Some common cases:

**Properties.** Defining a property with getter, setter, and deleter means either writing three functions at class level and joining them with `property(...)`, which leaves the helpers in the class namespace, or using a class statement with a metaclass that returns a property:

```python
class x:
    __metaclass__ = property_maker
    def fget(self): ...
    def fset(self, value): ...
```

**Namespaces and configuration.** Grouping related constants or settings under a name is often done with a class that is never instantiated:

```python
class Options:
    verbose = True
    retries = 3
```

**Declarative frameworks.** ORMs, form libraries, and schema languages use class statements with custom metaclasses to describe data. Many of the objects they produce behave very little like classes.

**XML and other trees.** Some libraries use nested class statements, with metaclasses that build element objects, to write tree structures that mirror the document.

In each case the class statement works, but it reads wrong. A reader sees `class` and expects a class. Hiding the real target behind `__metaclass__` makes the reader dig to find out what is going on. The `make` statement puts the callable up front:

```python
make property x:
    def fget(self): ...
    def fset(self, value): ...
```

```python
make namespace Options:
    verbose = True
    retries = 3
```

The statement now says what it produces.

# Specification

## Syntax

The grammar gets a new compound statement:

```
make_stmt: 'make' expr NAME ['(' [testlist] ')'] ':' suite
```

`make` becomes a keyword. Since that breaks existing code that uses `make` as an identifier, this PEP proposes enabling it through `from __future__ import make_statement` in Python 2.6, making it a full keyword in a later release.

## Semantics

The statement

```python
make <callable> <name> (<args>):
    <block>
```

is executed as follows:

1. Evaluate `<callable>`.
2. Evaluate the tuple `<args>`, or use `()` if it is absent.
3. Execute `<block>` in a new, empty dict namespace, as for a class body.
4. Call `<callable>("<name>", <args>, <namespace>)`.
5. Bind the result to `<name>` in the enclosing scope.

The block runs with the same scoping rules as a class body: names assigned in it go into the namespace dict, and functions defined in it do not close over the block's names.

## Equivalence to class

With these semantics,

```python
class C(B1, B2):
    <block>
```

is equivalent to

```python
make type C (B1, B2):
    <block>
```

except that the class statement also honors `__metaclass__` in the block and inherits the metaclass from its bases. `make` does no metaclass resolution: the callable is whatever was written.

# Examples

## Properties

```python
def property_maker(name, args, ns):
    return property(ns.get('fget'), ns.get('fset'),
                    ns.get('fdel'), ns.get('__doc__'))

class Circle(object):
    make property_maker radius:
        '''The radius of the circle.'''
        def fget(self):
            return self._radius
        def fset(self, value):
            if value < 0:
                raise ValueError("radius must be non-negative")
            self._radius = value
```

The helper functions don't leak into the class namespace.

## Simple namespaces

```python
def namespace(name, args, ns):
    obj = types.ModuleType(name)
    obj.__dict__.update(ns)
    return obj

make namespace config:
    host = 'localhost'
    port = 8080
```

## Interfaces

Interface libraries can declare an interface directly:

```python
make Interface IReadable:
    def read(size):
        "Read up to size bytes."
```

# Rationale

## Why parallel the class statement?

Several syntaxes are possible, including a keyword after the name (`name = make callable:`), a decorator-style prefix, or a block-producing expression. Mirroring the class statement keeps the mental model small. Programmers who have learned how a class body becomes a namespace, and how the metaclass then receives it, can apply that knowledge directly.

## Why pass the name?

Many objects want to know their own name: functions, classes, modules, and descriptors for error messages. The class statement passes the name for this reason, and `make` does the same.

## Why not just use metaclasses?

Writing `__metaclass__` in a block works, but it puts the most important fact, what kind of object this is, inside the body where it is easy to miss. The pattern also carries metaclass baggage such as inheritance of metaclasses from bases, which has nothing to do with the non-class cases.

# Open Issues

## Keyword choice

`make` is short but commonly used as an identifier, and build tools in particular use it. Alternatives such as `create` or `define` have similar problems. The `__future__` import reduces the breakage.

## Namespace type

Some uses want an ordered namespace, for example to preserve the order of fields in a schema. Letting the callable supply the namespace object, perhaps through a `__make_dict__` attribute, would allow this. It could be added later.

## Should `class` be redefined in terms of `make`?

It is tempting to declare that `class` is just `make` with the metaclass as the callable. The metaclass-resolution rules make the two subtly different, though, and this PEP doesn't attempt to unify them.

# Backwards Compatibility

The only incompatibility is the new keyword. Code that uses `make` as a name keeps working unless it opts into the `__future__` import. A later release that makes `make` a keyword unconditionally will need a deprecation warning period.
