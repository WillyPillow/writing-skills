# Abstract

This PEP proposes the inclusion of a pip bootstrap executable in the Python installation to simplify the use of third-party modules by Python users.

This PEP does not propose to include the pip implementation in the Python standard library. Nor does it propose to implement any package management or installation mechanisms beyond those provided by PEP 427 ("The Wheel Binary Package Format 1.0") and the distlib PEP.

# Rationale

Installing a third-party package is one of the first things a new Python user tries to do, and today it is one of the first places where they get stuck. A fresh CPython installation contains no tool capable of fetching a distribution from the Python Package Index and installing it. The user must first discover that such a tool exists, then work out which of several competing tools is the recommended one, and then install that tool by some out-of-band mechanism: downloading `get-pip.py` or `ez_setup.py`, running a platform package manager, or unpacking a source tarball and running `setup.py install` by hand.

Each of these routes has problems. Script downloads require the user to trust a URL found in documentation or a blog post, and frequently fail behind proxies. Platform package managers often ship old versions of pip, or install it in a way that conflicts with the Python the user actually intends to use. Manual installation from source assumes a familiarity with distutils that most newcomers do not have. The net effect is that the experience of "getting started with packages" differs by platform, by Python version, and by which tutorial the user happened to read.

At the same time, there are good reasons not to put pip itself into the standard library. pip evolves on a much faster cycle than CPython. Security fixes to its network code, changes in PyPI's behaviour, and improvements in dependency handling need to reach users within weeks, not on an eighteen-month release schedule. Freezing a particular version of pip into the standard library would leave users of older Python releases stuck with an installer that could no longer keep pace with the index it talks to.

This PEP takes a middle path. CPython will ship a small, stable bootstrap program named `pip`. When invoked for the first time, the bootstrap locates, downloads, verifies and installs the real pip, then hands control over to it. Subsequent invocations go directly to the installed pip. From the user's point of view, `pip install requests` simply works on a fresh Python installation.

# Proposal

The Python installation will include an executable script, installed alongside `python3` on POSIX systems and in the `Scripts` directory on Windows, with the following names:

- `pip3`
- `pip3.N`, where N is the minor version of the Python installation (for example `pip3.4`)

The unversioned name `pip` is deliberately not installed by default, to avoid colliding with an existing Python 2 installation of pip on the same system. Distributors may choose to provide it.

The bootstrap script is implemented as a module in the standard library, tentatively named `pip_bootstrap`, with the scripts being thin wrappers that call into it. Keeping the logic in a module means it can also be invoked as `python -m pip_bootstrap`, which is useful in environments where the script directory is not on `PATH`.

## Bootstrap behaviour

When the bootstrap script is invoked, it performs the following steps:

1. Attempt to import the `pip` package. If the import succeeds, the bootstrap passes its command-line arguments to pip's main entry point and exits with pip's return code. No further steps are taken.

2. If pip cannot be imported, determine whether the user has requested an operation that requires pip (any operation does, in practice). Print a short message explaining that pip is not yet installed and that it will be fetched from PyPI.

3. Query PyPI for the latest released version of pip and of setuptools, using the simple index API. Only wheel distributions are considered; the bootstrap does not build from source.

4. Download the selected wheels over HTTPS, verifying the server certificate against the system's trusted certificate store.

5. Verify the downloaded files against signatures, as described under "Security" below.

6. Install the wheels using a minimal wheel installer implemented in the bootstrap module. The installation target is the user site-packages directory by default, unless the bootstrap is running with write access to the system site-packages and was invoked with an explicit `--system` option, or is running inside a virtual environment, in which case the environment's site-packages is used.

7. Import the newly installed pip and run the user's original command.

If any step fails, the bootstrap prints a diagnostic message describing what went wrong and how the user can install pip manually, and exits with a non-zero status. It does not leave a partially installed pip behind.

## Why setuptools is also installed

At the time of writing, pip depends on setuptools to install source distributions, which remain the dominant format on PyPI. Installing pip without setuptools would produce a tool that fails on most real-world packages. The bootstrap therefore installs both. As the ecosystem moves toward wheels and the dependency is relaxed, the bootstrap's list of required packages can be reduced without any change to its interface.

## Wheel installation

The bootstrap needs to install wheels without pip being present, which means it needs its own minimal installer. This installer supports only what PEP 427 requires for pure-Python wheels: unpacking into the appropriate scheme directories, writing the `RECORD` file, and generating console script wrappers from the `entry_points.txt` metadata. It does not handle dependency resolution, compiled extensions, uninstallation, or any other feature of a full installer. The intention is that the wheel-handling code is shared with, or derived from, the distlib work so that the standard library does not carry two divergent implementations.

# Security

Downloading and executing code from the network on first run is a sensitive operation, and the bootstrap must not make Python installations less secure than they are today.

All network access uses HTTPS with certificate verification enabled. The bootstrap refuses to proceed if it cannot verify the server certificate, and it does not offer an option to disable verification.

In addition to transport security, the downloaded wheels are checked against detached signatures. The public key used to verify pip and setuptools releases is shipped with the bootstrap module. Releases of pip and setuptools are signed by their maintainers using the corresponding private key, and the signature files are published on PyPI alongside the wheels. A wheel whose signature does not verify is discarded.

Because the key is embedded in the CPython distribution, rotating it requires a CPython release. This is considered acceptable: key rotation is expected to be rare, and a maintenance release of every supported Python branch is already the mechanism by which other security-sensitive changes reach users.

# User experience

A user on a new installation will see something like the following:

```
$ pip3 install requests
pip is not installed; downloading it from https://pypi.python.org/ ...
Installing pip 1.4 and setuptools 0.9 into ~/.local
Collecting requests
...
Successfully installed requests
```

The first-run message is printed once. It tells the user where the code came from and where it was installed, so that they can remove it later if they wish.

Users who prefer that nothing be downloaded can install pip by any of the existing methods. If pip is importable, the bootstrap never touches the network.

# Interaction with distributors

Linux distributions and other redistributors frequently package pip themselves. A redistributor that provides pip as a system package should either arrange for that package to be importable from the Python it ships, in which case the bootstrap is a transparent pass-through, or remove the bootstrap scripts entirely and replace them with their own. This PEP does not require any particular choice.

# Backwards Compatibility

The bootstrap introduces new script names and a new standard library module. Existing installations of pip are unaffected: if pip is already importable, the bootstrap delegates to it immediately.

On systems where a user has previously installed a `pip3` script by another means, the Python installer will overwrite it. In practice the overwritten script and the bootstrap end up invoking the same pip, so this is not expected to cause problems.

# Rejected Alternatives

**Including pip in the standard library.** Rejected for the release-cycle reasons described above.

**Bundling a fixed pip wheel with CPython and installing it at install time.** This avoids network access, but every Python release would then ship with a version of pip that ages from the day of release. It also complicates the installers for every platform. This option may be reconsidered in a future PEP.

**Bootstrapping via `easy_install`.** setuptools is no more present in a fresh installation than pip is, so this merely moves the problem.

# Open Issues

- The exact name of the bootstrap module.
- Whether the bootstrap should install to user site-packages or system site-packages by default when run with sufficient privileges.
- How signing keys are managed by the pip and setuptools projects, and how many keys should be trusted.
