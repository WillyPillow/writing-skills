# PEP 525: Asynchronous Generators

| Field | Value |
|---|---|
| PEP | 525 |
| Title | Asynchronous Generators |
| Status | Draft |
| Type | Standards Track |
| Python-Version | 3.6 |

## Abstract

PEP 492 introduced native coroutines and the `async`/`await` syntax in Python 3.5. This PEP proposes extending Python's asynchronous capabilities with *asynchronous generators*: functions defined with `async def` that contain `yield` expressions. An asynchronous generator produces values lazily, like an ordinary generator, but may `await` between them.

## Rationale and Goals

Ordinary generators made it easy to write iterators. Before generators, a class implementing `__iter__` and `__next__` had to store its state explicitly in attributes and reconstruct its position on each call. A generator lets the interpreter keep that state in a suspended frame, so the author can write a plain loop with `yield` in it.

PEP 492 defined the asynchronous iteration protocol (`__aiter__` and `__anext__`) and the `async for` statement, but it did not provide a generator-style way to implement that protocol. Today, anyone who wants an asynchronous iterator must write a class. Consider a ticker that yields integers with a delay between them:

```python
class Ticker:
    def __init__(self, delay, to):
        self.delay = delay
        self.i = 0
        self.to = to

    def __aiter__(self):
        return self

    async def __anext__(self):
        i = self.i
        if i >= self.to:
            raise StopAsyncIteration
        self.i += 1
        if i:
            await asyncio.sleep(self.delay)
        return i
```

With asynchronous generators, the same thing is:

```python
async def ticker(delay, to):
    for i in range(to):
        yield i
        await asyncio.sleep(delay)
```

The second version is shorter, but more importantly it states the algorithm directly. The class version obscures a simple loop behind manual bookkeeping. In informal measurements, the generator form is also about twice as fast as the class-based iterator, because resuming a suspended frame is cheaper than an attribute lookup and method call on every step.

## Specification

### Definition

A function defined with `async def` that contains at least one `yield` expression is an asynchronous generator function. Calling it returns an asynchronous generator object. The function body does not start running until the object is iterated.

`yield from` is not permitted inside an asynchronous generator. It is a `SyntaxError`. See "Design Considerations" below.

A `return` statement with a value is a `SyntaxError` inside an asynchronous generator. A bare `return` is allowed and ends iteration.

### The asynchronous generator object

The object returned by an asynchronous generator function implements the asynchronous iteration protocol:

- `agen.__aiter__()` returns `agen`.
- `agen.__anext__()` returns an awaitable. Awaiting it runs the generator body until the next `yield`, then returns the yielded value. If the body finishes, the awaitable raises `StopAsyncIteration`.

It also provides the counterparts of the generator methods:

- `agen.asend(value)` returns an awaitable that resumes the generator, sending `value` as the result of the current `yield` expression.
- `agen.athrow(type[, value[, traceback]])` returns an awaitable that raises the given exception at the suspended `yield`.
- `agen.aclose()` returns an awaitable that throws `GeneratorExit` into the generator. If the generator then yields another value, `RuntimeError` is raised. If it exits or raises `GeneratorExit` or `StopAsyncIteration`, the awaitable completes normally.

Each of these methods returns a new awaitable. The generator does not advance until that awaitable is awaited. This mirrors how `__anext__` works and lets an event loop schedule the work.

Asynchronous generators also expose `ag_await`, `ag_frame`, `ag_running`, and `ag_code` attributes, analogous to the `gi_*` attributes on ordinary generators, for debuggers and introspection tools.

### `StopIteration` and `StopAsyncIteration`

If code inside an asynchronous generator raises `StopIteration` or `StopAsyncIteration`, it is converted to a `RuntimeError`, with the original exception attached as `__cause__`. This follows the reasoning in PEP 479: an exception that signals the end of iteration should not silently escape from a nested call and terminate an unrelated loop.

### Finalization

An ordinary generator that is garbage-collected while suspended is closed automatically: the interpreter calls `close()`, which runs any `finally` blocks and `with` exits. Asynchronous generators need the same guarantee, but closing one requires awaiting `aclose()`, and the garbage collector cannot await anything. Only the event loop that the generator was running on can do that.

To solve this, the `sys` module gains two functions:

- `sys.set_asyncgen_hooks(firstiter=None, finalizer=None)`
- `sys.get_asyncgen_hooks()`

Both hooks are stored per thread. When an asynchronous generator is iterated for the first time, the interpreter calls the current `firstiter` hook with the generator as its argument and records the current `finalizer` on the generator. When the generator is about to be garbage-collected without having been fully exhausted or closed, the interpreter calls the stored `finalizer` instead of closing the generator itself. The finalizer is expected to schedule `agen.aclose()` on the appropriate event loop.

The `firstiter` hook lets an event loop keep a weak set of all live asynchronous generators it is running. This set is needed for orderly shutdown.

If no finalizer is set when the generator is garbage-collected, the interpreter behaves as before for ordinary generators: it attempts a synchronous close, which works only if the generator does not `await` in its cleanup code.

### asyncio integration

`asyncio` will install both hooks when an event loop starts running and restore the previous hooks when it stops. Its finalizer schedules `aclose()` as a task on the loop.

A new coroutine method, `loop.shutdown_asyncgens()`, closes every asynchronous generator in the loop's tracking set that has not finished yet. Applications should call it before `loop.close()`:

```python
try:
    loop.run_forever()
finally:
    loop.run_until_complete(loop.shutdown_asyncgens())
    loop.close()
```

Without this step, a generator suspended at a `yield` inside `async with` would never run its cleanup.

### Type and inspection support

`types.AsyncGeneratorType` is added. `inspect.isasyncgenfunction()` and `inspect.isasyncgen()` are added. A new code flag, `CO_ASYNC_GENERATOR`, marks the code objects of asynchronous generator functions. `collections.abc.AsyncGenerator` is added as an abstract base class for objects that implement `asend`, `athrow`, and `aclose` on top of `AsyncIterator`.

## Design Considerations

### Why no `yield from`

Supporting `yield from` inside an asynchronous generator is possible in principle, but it is not obvious what it should delegate to. It could delegate to another asynchronous generator, which would require new opcodes and a new delegation protocol for `asend` and `athrow`. The implementation is substantial, and the common use case is served adequately by an explicit loop:

```python
async for item in other():
    yield item
```

This PEP leaves `yield from` out. A future PEP can add it once there is experience with asynchronous generators in practice.

### Why not use `__del__` on the generator

An earlier idea was to let asynchronous generators be closed from a `__del__`-style mechanism that ran the cleanup synchronously. That would run `await` expressions outside the event loop, which is incorrect for any framework. The hook design puts the decision in the hands of the event loop, which is the only component that knows how to run the cleanup.

### Why per-thread hooks

Event loops are bound to threads. A process running separate loops in separate threads needs each loop to finalize its own generators. Making the hooks global would require loops to coordinate with each other.

## Asynchronous Comprehensions

Asynchronous comprehensions (`[x async for x in agen()]`) are a natural companion to this feature and are proposed in a separate PEP.

## Performance

Benchmarks on the reference implementation show asynchronous generators running roughly twice as fast as an equivalent hand-written asynchronous iterator class. The overhead compared with a plain generator is the cost of creating awaitables for each `__anext__` call.

## Backwards Compatibility

Before this PEP, `yield` inside an `async def` function was a `SyntaxError`. No valid code changes meaning. The new `sys` functions and `inspect` predicates are additions.
