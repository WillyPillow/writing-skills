PEP: 309
Title: Partial Function Application
Status: Draft
Type: Standards Track
Created: 2003
Python-Version: 2.5

# Abstract

This proposal is for a function or callable class that constructs a new callable from an existing callable and a partial argument list, including both positional and keyword arguments. I propose a new standard library module called `functional` to hold useful higher-order functions, starting with the implementation of `partial()`. An implementation has been submitted to SourceForge.

# Motivation

Python programmers frequently need a callable that is just an existing function with some of its arguments already filled in. The need comes up constantly in callback-based code:

- GUI toolkits such as Tkinter expect a zero-argument callable for a button's `command`, but the handler usually needs to know which button was pressed.
- `map()`, `filter()` and `sorted(key=...)` want a one-argument function, but the operation at hand often takes two or three.
- Event and scheduling APIs, thread start functions and signal handlers all take a callable and pass it a fixed set of arguments.

Today the usual answer is a `lambda`:

```python
button = Button(root, text="Save", command=lambda: handle("save"))
```

or a nested function:

```python
def make_handler(name):
    def handler():
        return handle(name)
    return handler
```

Both work, but both have problems. A `lambda` hides the intent behind syntax, and inside a loop it is a well-known trap, because names are looked up when the lambda runs, not when it is created:

```python
for name in ("open", "save", "close"):
    buttons.append(Button(root, text=name, command=lambda: handle(name)))
# every button calls handle("close")
```

The usual fix, `lambda name=name: handle(name)`, abuses default arguments and is confusing to newcomers. A nested factory function is correct but verbose for something conceptually trivial.

Partial application is a well-understood concept with a long history in functional programming. Giving it a name and a standard implementation makes code clearer and removes a common source of bugs.

# Rationale

A partial object captures the function and its arguments at construction time. That is exactly the "freeze the values now" behaviour people usually want, and it reads as what it is:

```python
from functional import partial

for name in ("open", "save", "close"):
    buttons.append(Button(root, text=name, command=partial(handle, name)))
```

The name `partial` was chosen over alternatives such as `curry` because currying, strictly speaking, refers to transforming a function of many arguments into a chain of functions of one argument each. What is proposed here is partial application, and it is better to use the correct term than to propagate a common confusion.

Putting it in a new `functional` module, rather than adding a builtin, keeps the builtin namespace small and gives a home to other higher-order utilities that may be proposed later, such as function composition or `flip`.

# Specification

`functional.partial(func, *args, **kwargs)` returns a callable object. When that object is called with positional arguments `more_args` and keyword arguments `more_kwargs`, it calls:

```python
func(*(args + more_args), **merged_kwargs)
```

where `merged_kwargs` is a copy of `kwargs` updated with `more_kwargs`. Keyword arguments supplied at call time therefore override those given at construction time.

The returned object exposes three read-only attributes:

- `func`: the wrapped callable,
- `args`: the tuple of frozen positional arguments,
- `keywords`: the dictionary of frozen keyword arguments (or `None` if none were given).

These allow introspection and debugging, and let tools that wrap callables see through a partial object to the underlying function.

`partial` objects support a writable `__dict__`, so that frameworks which attach metadata to callables (for example, a `__doc__` or a registration tag) can do so.

If `func` is not callable, `partial` raises `TypeError` at construction time rather than waiting until the object is called.

## Reference implementation in Python

The semantics are captured by this pure Python class:

```python
class partial(object):
    def __init__(*args, **kw):
        self = args[0]
        if len(args) < 2:
            raise TypeError("partial() requires a callable")
        func = args[1]
        if not callable(func):
            raise TypeError("the first argument must be callable")
        self.func = func
        self.args = args[2:]
        self.keywords = kw or None

    def __call__(self, *args, **kw):
        if self.keywords:
            merged = self.keywords.copy()
            merged.update(kw)
        else:
            merged = kw
        return self.func(*(self.args + args), **merged)
```

The odd-looking signature of `__init__` ensures that a keyword argument named `self` or `func` can still be frozen and passed through to the wrapped function.

The submitted patch implements the same behaviour in C, which avoids an extra layer of Python function calls and makes `partial` objects nearly as cheap to call as the function they wrap.

# Examples

Fixing the base of `int()`:

```python
from functional import partial
from_hex = partial(int, base=16)
from_hex("ff")         # 255
```

Building a sort key:

```python
by_field = partial(operator.getitem)   # placeholder for illustration
records.sort(key=partial(lookup, table))
```

Supplying a callback with context:

```python
timer.schedule(5.0, partial(notify, user, "reminder"))
```

# Discussion

## Should partial objects behave as methods?

A plain function stored as a class attribute becomes a bound method when accessed through an instance. A `partial` object, being an instance of a class without `__get__`, does not. This proposal deliberately leaves `partial` as a non-descriptor. Making it bind would create surprising behaviour when it is stored in a class for other reasons, and the cases that need method-like behaviour can wrap the partial in a function explicitly.

## Should arguments be appended on the right?

Some users have asked for a variant that freezes arguments on the right-hand side, leaving the leftmost argument open. This is less commonly needed, and keyword arguments cover most such cases. It can be added later in the `functional` module if demand appears.

## Why not just encourage lambda?

Lambda remains available, and nothing in this proposal discourages it. But for the specific job of fixing arguments, `partial` is shorter, harder to get wrong, and introspectable, which makes it the better default.

# Backwards Compatibility

The proposal adds a new module and changes no existing behaviour.

# Implementation

A patch implementing the `functional` module in C, with tests and documentation, has been submitted to SourceForge.
