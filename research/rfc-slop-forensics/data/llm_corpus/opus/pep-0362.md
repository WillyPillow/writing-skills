# Abstract

Python has always offered strong introspection, including for functions and methods. (In the rest of this PEP, "function" means both functions and methods.) By examining a function object you can reconstruct its whole signature. The trouble is that the information is stored inconveniently, spread across half a dozen deeply nested attributes.

This PEP proposes a new representation for function signatures. It holds everything there is to know about a function and its parameters, and makes introspection simple. It does not replace the existing function metadata, which Python itself uses to execute functions. The new object exists only to make introspection easier for Python programmers.

# Motivation

Suppose you want to know what parameters a function takes. Today you need to consult:

- `func.__code__.co_varnames`, which lists positional and keyword parameter names followed by local variable names;
- `func.__code__.co_argcount` and `co_kwonlyargcount`, to know where the parameters stop and the locals begin;
- `func.__code__.co_flags`, to find out whether `*args` or `**kwargs` is present, with their names at specific offsets in `co_varnames`;
- `func.__defaults__`, a tuple of defaults aligned with the *last* positional parameters;
- `func.__kwdefaults__`, a dict of defaults for keyword-only parameters;
- `func.__annotations__`, a dict of annotations keyed by name, with `'return'` for the return annotation.

Putting this together correctly is surprisingly hard. `inspect.getargspec()` and `inspect.getfullargspec()` help, but they return flat tuples that callers still have to interpret, and they do not handle bound methods, `functools.partial` objects, or callable classes consistently.

Many tools need this information: documentation generators, argument validators, RPC frameworks, decorators that want to preserve or change signatures, IDEs, and test fixture systems. Each of them ends up reimplementing the same fragile logic.

A single, well-defined object representing a signature would remove that duplication and give decorators a standard way to report the signature they expose.

# Signature Object

A `Signature` object represents the call signature of a function and its return annotation. It is immutable. It has the following public attributes and methods:

- **`parameters`**: an ordered mapping from parameter names to `Parameter` objects, in the order they appear in the definition.
- **`return_annotation`**: the return annotation, or `Signature.empty` if there is none.
- **`bind(*args, **kwargs)`**: maps the given arguments to parameters the way a real call would, and returns a `BoundArguments` object. It raises `TypeError` if the arguments do not match the signature.
- **`bind_partial(*args, **kwargs)`**: like `bind()`, but missing required arguments are allowed.
- **`replace(parameters=..., return_annotation=...)`**: returns a new `Signature` with the given fields changed.

`Signature` objects support equality: two signatures are equal if their parameters and return annotations are equal.

`str(sig)` produces a string that looks like the parameter list in a `def` statement, for example `'(a, b=1, *args, c, d=2, **kwargs) -> int'`.

# Parameter Object

Python's parameter syntax is rich: parameters can be positional-only, positional-or-keyword, keyword-only, or variadic. A `Parameter` object represents one of them. It is immutable and has these attributes:

- **`name`**: the parameter's name as a string.
- **`default`**: the default value, or `Parameter.empty` if there is none.
- **`annotation`**: the annotation, or `Parameter.empty`.
- **`kind`**: one of the following constants:
  - `Parameter.POSITIONAL_ONLY`: may only be supplied positionally. Python code cannot define these, but many builtins have them.
  - `Parameter.POSITIONAL_OR_KEYWORD`: the ordinary case.
  - `Parameter.VAR_POSITIONAL`: the `*args` parameter.
  - `Parameter.KEYWORD_ONLY`: a parameter after `*` or `*args`.
  - `Parameter.VAR_KEYWORD`: the `**kwargs` parameter.

and one method:

- **`replace(name=..., kind=..., default=..., annotation=...)`**: returns a new `Parameter` with the given fields changed.

`Parameter` objects can be created directly, which lets tools build signatures from scratch:

```python
from inspect import Parameter, Signature

sig = Signature([
    Parameter('x', Parameter.POSITIONAL_OR_KEYWORD),
    Parameter('y', Parameter.KEYWORD_ONLY, default=0),
])
print(sig)  # (x, *, y=0)
```

The constructor checks that parameters appear in a valid order and that names are unique.

# BoundArguments Object

`Signature.bind()` returns a `BoundArguments` object with these attributes:

- **`arguments`**: an ordered mutable mapping from parameter names to values. It contains only explicitly bound arguments; defaults are not filled in.
- **`args`**: a tuple of positional argument values, computed from `arguments`.
- **`kwargs`**: a dict of keyword argument values, computed from `arguments`.
- **`signature`**: the `Signature` that created it.

`args` and `kwargs` can be used to call the function:

```python
def f(a, b, *, c=3):
    return a + b + c

ba = signature(f).bind(1, 2, c=10)
ba.arguments['a'] = 100
assert f(*ba.args, **ba.kwargs) == 112
```

# The `signature()` Function

A new function, `inspect.signature(callable)`, returns a `Signature` for any callable. Its algorithm:

1. If the object is not callable, raise `TypeError`.
2. If the object has a `__signature__` attribute that is not `None`, return it. This lets decorators and wrappers report a custom signature.
3. If the object is a bound method, compute the signature of the underlying function and drop the first parameter.
4. If the object has a `__wrapped__` attribute (as set by `functools.wraps`), follow it and compute the signature of the wrapped object.
5. If the object is a Python function, build the signature from its code object, defaults, and annotations.
6. If the object is a `functools.partial`, compute the signature of the wrapped function and then remove or adjust the parameters already supplied.
7. If the object is a class, use the signature of its metaclass's `__call__` if user-defined, else its `__new__`, else its `__init__`, dropping the first parameter.
8. If the object is an instance of a class with a `__call__` method, use the signature of that method, bound.
9. Otherwise, raise `ValueError`, since some builtins do not expose signature information.

Signatures are computed lazily, on demand. Function objects do not carry a precomputed signature, so there is no runtime or memory cost for programs that never call `signature()`.

# Visualizing Callable Objects' Signatures

A short example shows the improvement:

```python
from inspect import signature

def greet(name: str, *, punctuation: str = '!') -> str:
    return 'Hello, ' + name + punctuation

sig = signature(greet)
for p in sig.parameters.values():
    print(p.name, p.kind, p.default, p.annotation)
# name POSITIONAL_OR_KEYWORD <class 'inspect._empty'> <class 'str'>
# punctuation KEYWORD_ONLY ! <class 'str'>
print(sig.return_annotation)  # <class 'str'>
```

# Implementation

The implementation adds the `Signature`, `Parameter`, and `BoundArguments` classes and the `signature()` function to the `inspect` module, written in pure Python. It does not change the function object or the interpreter. `inspect.getfullargspec()` can later be reimplemented on top of `signature()`.

# Design Considerations

**No implicit caching on functions.** An earlier draft attached a `__signature__` attribute to every function at creation. That costs memory for every function and raises the question of what happens when `__defaults__` is modified after creation. Computing signatures lazily avoids both problems.

**Immutability.** `Signature` and `Parameter` are immutable so they can be shared and hashed safely. The `replace()` methods make modification easy anyway.

**`empty` sentinels.** `None` is a legitimate default value and a legitimate annotation, so it cannot mean "absent." The dedicated `empty` sentinel removes the ambiguity.

**Positional-only parameters.** Python has no syntax for them, but they are part of the model because builtins need them.
