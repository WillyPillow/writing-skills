# PEP 327: Decimal Data Type

| Field | Value |
|---|---|
| PEP | 327 |
| Title | Decimal Data Type |
| Status | Final |
| Type | Standards Track |
| Python-Version | 2.4 |

## Abstract

This PEP proposes a `Decimal` data type for every use where decimal numbers are needed and binary floating point is too inexact.

`Decimal` supports the standard Python numeric operations and functions and complies with the decimal arithmetic standard ANSI X3.274-1996, as refined in the General Decimal Arithmetic Specification. It is a floating-point type, not a fixed-point type, with bounded precision: the precision is an upper limit on the number of significant digits in a result. Precision is user-settable, and trailing zeros are significant, so fixed-point usage is also possible.

The work builds on code and tests by Eric Price, Aahz and Tim Peters. Shortly before Python 2.4a1 the reference implementation, `decimal.py`, was moved into the standard library.

## Motivation

### Binary floating point surprises people

Python's `float` is an IEEE 754 binary double. It cannot represent most decimal fractions exactly:

```python
>>> 0.1 + 0.1 + 0.1 - 0.3
5.551115123125783e-17
>>> 1.1 * 3
3.3000000000000003
```

For scientific computation this is acceptable and well understood. For many other programs it is a source of bugs. Money is the canonical example. Accounting rules are written in decimal. A total of line items that should be exactly zero comes out as a tiny nonzero number, comparisons fail, and rounding at the last step produces off-by-one-cent errors that auditors notice.

Programmers work around this in several ways, none satisfactory:

- **Integers in the smallest unit.** Store cents as `int`. This works until you need to multiply by a percentage, divide among parties, or handle currencies with different minor units.
- **Rounding everywhere.** Call `round()` after every operation. This is error-prone and still gives wrong answers at boundaries, because `round(2.675, 2)` operates on the binary value nearest 2.675, which is slightly below it.
- **Third-party libraries.** Several exist, with different semantics and different rounding rules.

### Decimal arithmetic is a solved problem

The decimal arithmetic specification, developed largely by Mike Cowlishaw at IBM and adopted in ANSI X3.274 and later IEEE 754-2008, defines precise behaviour for decimal floating point: representation, the result of each operation, rounding modes, exceptional conditions, and special values. It is used in REXX, Java's `BigDecimal` and hardware decimal units. Following it lets Python adopt a well-tested design instead of inventing one.

## Specification

### The data type

A `Decimal` is a triple of sign, coefficient (a non-negative integer of arbitrary length) and exponent. Its value is `(-1)**sign * coefficient * 10**exponent`. Special values are positive and negative infinity, quiet NaN and signaling NaN.

Trailing zeros are preserved. `Decimal("1.20")` and `Decimal("1.2")` compare equal but are distinct values: the first has coefficient 120 and exponent -2, the second coefficient 12 and exponent -1. This preserves the notion of significance, which matters in financial and measurement contexts.

### Construction

`Decimal` can be constructed from:

- **An `int` or `long`.** Exact.
- **A string.** Exact, following the specification's numeric string syntax, including `"Infinity"` and `"NaN"`.
- **Another `Decimal`.** Exact copy.
- **A tuple** `(sign, digits, exponent)`. Exact.

Construction from `float` is **not** supported implicitly. A float like `1.1` is really `1.100000000000000088817841970012523...`; turning that into a `Decimal` silently would either reproduce the binary error with misleading precision or round it in a way that hides what happened. Users who want the exact binary value can request it explicitly through a dedicated class method.

Construction is exact regardless of context precision. Rounding to context happens only when arithmetic is performed. This allows a value to be stored faithfully and then used in calculations at a chosen precision.

### Context

All arithmetic happens within a *context*, an object holding:

- `prec`: precision in significant digits (default 28)
- `rounding`: one of `ROUND_HALF_EVEN` (default), `ROUND_HALF_UP`, `ROUND_HALF_DOWN`, `ROUND_UP`, `ROUND_DOWN`, `ROUND_CEILING`, `ROUND_FLOOR`
- `Emin` and `Emax`: exponent limits
- `traps`: which signals raise exceptions
- `flags`: which signals have occurred

Each thread has its own current context, obtained with `getcontext()` and replaced with `setcontext()`. Contexts can also be used directly: `ctx.add(a, b)`.

Thread-local contexts mean that one library setting precision does not affect another thread's arithmetic.

### Signals

The specification defines exceptional conditions: `Clamped`, `DivisionByZero`, `Inexact`, `InvalidOperation`, `Overflow`, `Rounded`, `Subnormal`, `Underflow`. Each is a subclass of `DecimalException`, which subclasses `ArithmeticError`.

When a condition occurs, its flag is set in the context. If its trap is enabled, the corresponding exception is raised. By default, `InvalidOperation`, `DivisionByZero` and `Overflow` trap, and the rest only set flags. A program that wants to know whether any rounding happened can check `ctx.flags[Inexact]`; a program that must never round can enable the trap.

### Operations

`Decimal` supports `+`, `-`, `*`, `/`, `//`, `%`, `divmod`, `**` with integer exponents, unary minus and plus, `abs`, comparisons, hashing, `int()`, `long()`, `float()`, `str()` and `repr()`.

It also provides methods defined by the specification: `quantize()` to round to a given exponent (the core operation for fixed-point use), `sqrt()`, `to_integral()`, `normalize()`, `max()` and `min()`, and `compare()`.

### Mixing with other types

Arithmetic between `Decimal` and `int` or `long` is allowed, converting the integer exactly.

Arithmetic between `Decimal` and `float` raises `TypeError`. Allowing it would require choosing a conversion, and either choice hides an error the user should see.

Comparisons with `float` follow the same rule in this version.

### Hashing

Values that compare equal must hash equal. `Decimal(5)` must hash the same as `5`, so integral Decimals hash as the corresponding integer. Non-integral values hash on their normalized form.

## Rationale

### Floating point instead of fixed point

A fixed-point type with a set number of decimal places is easy to describe but breaks on multiplication and division, whose results need more places than their inputs. A floating-point decimal with significant trailing zeros and `quantize()` covers both cases.

### Why not a C implementation first

A pure Python implementation is easier to verify against the specification's test suite and easier to maintain. Performance is adequate for its intended uses, which are dominated by I/O and business logic, not numeric loops. A C accelerator can be added later without changing the interface.

### Default precision of 28

Twenty-eight digits is enough for any currency calculation including intermediate products of large amounts and rates, and matches common commercial systems.

## Backwards Compatibility

This PEP adds a new module and changes no existing behaviour.

## Reference Implementation

`decimal.py` is in the standard library as of 2.4a1, along with its test module, which runs the specification's published test cases.
