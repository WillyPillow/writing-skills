PEP: 223
Title: Change the Meaning of ``\x`` Escapes
Author: Tim Peters
Status: Final
Type: Standards Track
Created: 20-Aug-2000
Python-Version: 2.0

Abstract
========

Change ``\x`` escapes, in both 8-bit and Unicode strings, to consume
exactly the two hex digits that follow the ``x``.  Today a ``\x``
escape consumes every hex digit that follows it, and keeps only the
low-order bits of the result.  This PEP treats that behaviour as a
design flaw inherited from C, and replaces it with a fixed-width rule.
The change gives clearer expression in every flavour of string literal,
makes the story for Unicode string literals simpler, brings Python in
line with Perl regular expression syntax, and carries very little risk
for existing code.


Syntax
======

The syntax of ``\x`` escapes in all string literals becomes::

    \xhh

where ``h`` is a hex digit (``0-9``, ``a-f``, ``A-F``).  Exactly two
hex digits are required.  In an 8-bit string the escape produces the
single byte with ordinal ``0xhh``.  In a Unicode string it produces the
Unicode character with ordinal ``0xhh``, that is, a character in the
range U+0000 through U+00FF.

The behaviour of ``\x`` followed by fewer than two hex digits is
discussed under "Semantics" below.


History and Rationale
=====================

The ``\x`` escape in Python was copied from C.  The C standard says a
hex escape continues for as many hex digits as follow, and that the
result is implementation-defined if it does not fit in a ``char``.  The
Python implementation took the same reading: it consumed all following
hex digits and kept the last two (in practice, the value modulo 256).
So in Python 1.5.2::

    >>> "\x123465"
    'e'

because the escape eats ``123465`` and keeps the low byte ``0x65``.

Almost nobody wants this.  The usual effect of the rule is a surprise
when a hex escape is immediately followed by a character that happens
to be a hex digit::

    >>> "\x0aBad"      # intended: newline followed by "Bad"
    '\xad'

The user wanted ``"\n" + "Bad"`` and received a single unrelated byte.
The only workaround is to split the literal, or to use octal escapes,
which have the opposite problem of being limited to three digits but
being hard to read.

C programmers live with this because C compilers will at least warn
about out-of-range values.  Python never did, and quietly discarded
high-order bits.  That is the worst combination: a rule that is easy to
trip over, combined with no diagnostic when you do.

Unicode raises the stakes.  Python 2.0 introduces Unicode string
literals, where ``\uhhhh`` names a character by exactly four hex
digits.  The obvious question is what ``\x`` should mean in a Unicode
literal.  Under the old rule, ``u"\x1234"`` would consume four digits
and, depending on how the truncation was defined, yield either U+1234
or U+0034.  Neither answer is attractive.  If it yields U+1234, then
``\x`` and ``\u`` are two spellings for the same thing with subtly
different digit-consumption rules.  If it yields U+0034, it silently
discards data.  In either case, ``"\x1234"`` and ``u"\x1234"`` would no
longer mean "the same characters" in the two kinds of string, which
undermines the idea that a plain ASCII-range string literal can be
turned into a Unicode literal by adding a ``u`` prefix.

The fixed-width rule makes the answer simple.  ``\xhh`` means the
character with ordinal ``0xhh`` in both kinds of string.  Wider
characters are spelled with ``\uhhhh``.  Each escape has a fixed width,
so the reader can see exactly where it ends.

Finally, Perl's regular expression syntax, which Python's ``re`` module
follows closely, already treats ``\x`` as consuming at most two hex
digits.  Patterns copied from Perl documentation behave differently in
Python today when a hex escape is followed by a hex digit.  After this
change, they behave the same.


Semantics
=========

In an 8-bit string literal:

- ``\x`` followed by two hex digits produces one byte with that value.
  Any further hex digits are ordinary characters.

- ``\x`` followed by fewer than two hex digits raises ``ValueError``
  when the literal is compiled.  Previously, ``"\x"`` with no digits
  was left as the two characters backslash and ``x``; ``"\xa"`` was
  accepted as a single byte.  Both are now errors.  Making the short
  forms an error, rather than guessing, means that no remaining spelling
  has a quiet surprising meaning.

In a Unicode string literal:

- ``\x`` followed by two hex digits produces the character with that
  ordinal, in the range U+0000 to U+00FF.

- ``\x`` followed by fewer than two hex digits is an error, as above.

The same rules apply in ``unicode_escape`` and ``raw_unicode_escape``
codecs where those codecs interpret ``\x`` sequences, and to the
``string-escape`` handling used by ``eval`` of ``repr`` output.  Since
``repr()`` already produces exactly two hex digits after ``\x``, every
string produced by ``repr()`` remains valid input with the same
meaning.

The ``re`` module handles escapes in patterns itself.  Its ``\x``
handling is changed to match: it consumes at most two hex digits.


Example
=======

Before this change::

    >>> "\x41BC"
    '\xbc'

After this change::

    >>> "\x41BC"
    'ABC'

And for Unicode::

    >>> u"\x41BC"
    u'ABC'
    >>> u"ABC"
    u'ABC'


Backward Compatibility
======================

Three kinds of existing code could change behaviour.

1. Code that writes more than two hex digits after ``\x`` on purpose,
   relying on truncation.  This is hard to imagine as intentional.  A
   search of the standard library and a sample of third-party code
   found no instances.

2. Code that writes more than two hex digits after ``\x`` by accident,
   as in the ``"\x0aBad"`` example.  Such code is already broken, and
   this change fixes it.

3. Code that writes ``\x`` followed by zero or one hex digit.  This
   will now fail at compile time with a clear error instead of running.
   An instance of ``"\x"`` meaning a literal backslash-x is plausible,
   for example in strings passed to other tools.  These are easy to
   find and fix by doubling the backslash.

Because the third category produces an error rather than a quiet change
in meaning, any breakage will be visible immediately.  The first two
categories change meaning silently, but the first is vanishingly rare
and the second is a bug fix.

Binary data embedded in strings is usually written with ``repr()``
output or with two-digit escapes, which are unaffected.


Effects on Other Tools
======================

Tools that parse Python source and interpret string escapes, such as
syntax highlighters, ``tokenize``-based utilities and IDEs, may need
updating if they reproduce the escape semantics.  Most tools only need
to know where a literal ends, which is unchanged.

JPython (the Java implementation) should adopt the same rule.  Java's
own string syntax does not have ``\x`` escapes, so there is no
competing convention there.


Alternatives Considered
=======================

Leave ``\x`` alone and only define its meaning in Unicode literals.
This keeps the C-like surprise in 8-bit strings and makes the two
string types disagree on the meaning of the same characters, which is
exactly what we want to avoid.

Make ``\x`` in Unicode literals consume up to four digits.  This
duplicates ``\u``, and still allows a following hex digit to be
absorbed silently.

Issue a warning for the old behaviour for one release before changing
it.  The warnings framework is new in 2.0 and was not available in time
for this change.  Given how rarely the old semantics are relied on, and
that the most common failure mode is a compile-time error, a direct
change was judged acceptable.


Reference Implementation
========================

The change is confined to the string literal parser in
``Python/compile.c``, the Unicode escape decoder in
``Objects/unicodeobject.c``, and the escape handling in ``sre_parse``.
A patch has been checked in to the CVS tree for 2.0.
