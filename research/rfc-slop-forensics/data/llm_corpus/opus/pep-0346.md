# PEP 346: User Defined ("`with`") Statements

| Field | Value |
|---|---|
| PEP | 346 |
| Title | User Defined ("`with`") Statements |
| Status | Draft |
| Type | Standards Track |
| Created | 06-May-2005 |
| Python-Version | 2.5 |

## Abstract

This PEP combines PEP 310's "Reliable Acquisition/Release Pairs" with the "Anonymous Block Statements" of Guido's PEP 340. It aims to take the good parts of PEP 340, blend them with parts of PEP 310, and arrange the result into a coherent whole. It borrows from several other PEPs to give a complete picture, and is intended to stand on its own.

## Author's Note

Much of the discussion on python-dev about PEP 340 concerned two separate ideas that the PEP joined together: a statement that reliably pairs setup with cleanup, and a statement that lets a generator control a loop body. This PEP argues that the first is what most people actually want, that the second introduces a new kind of looping construct with surprising control flow, and that they should be separated. The result is a non-looping `with` statement with generator support provided by a decorator.

## Introduction

Python code is full of patterns like this:

```python
lock.acquire()
try:
    ...
finally:
    lock.release()
```

and:

```python
f = open(path)
try:
    ...
finally:
    f.close()
```

The `try`/`finally` is correct but noisy, and it is easy to get wrong. A common error is to put the acquisition inside the `try`, so that `release()` is called even when `acquire()` failed. Another is to forget the `try` entirely.

PEP 310 proposed a statement that captures this:

```python
with lock:
    ...
```

where the object provides `__enter__` and `__exit__` methods. PEP 340 proposed a more general block statement driven by a generator, which could also express loops, retry logic, and more. This PEP keeps PEP 310's non-looping semantics, adopts the ability to write managers as generators from PEP 340, and adds exception information to `__exit__` so that managers can react to the way the block ended.

## Proposed Semantics

### Syntax

```
with_stmt: 'with' expr ['as' target] ':' suite
```

`with` and `as` become keywords. During a transition period, they produce a warning when used as identifiers.

### Semantics

The statement

```python
with EXPR as VAR:
    BLOCK
```

is translated to:

```python
mgr = (EXPR)
exit = mgr.__exit__      # looked up before entering
value = mgr.__enter__()
exc = True
try:
    try:
        VAR = value      # only if "as VAR" is present
        BLOCK
    except:
        exc = False
        if not exit(*sys.exc_info()):
            raise
finally:
    if exc:
        exit(None, None, None)
```

Key properties:

1. `__exit__` is looked up before `__enter__` is called, so that a manager missing `__exit__` fails before any resource is acquired.
2. If `__enter__` raises, `__exit__` is not called. The resource was never acquired.
3. If the block raises, `__exit__` receives the exception type, value, and traceback. If it returns a true value, the exception is suppressed; otherwise it propagates.
4. If the block completes normally, or exits via `break`, `continue`, or `return`, `__exit__` is called with three `None` arguments.

The `with` statement is not a loop. `break` and `continue` inside the block apply to an enclosing loop, exactly as they would inside a `try` statement. This is the most important difference from PEP 340.

### The manager protocol

A **statement manager** (the term "context manager" is also used in discussion) is any object with:

- `__enter__(self)`: acquire the resource and return the value to bind to `VAR`.
- `__exit__(self, type, value, traceback)`: release the resource. The arguments describe the exception that ended the block, or are all `None`.

Many objects can be their own managers. File objects, for example, return themselves from `__enter__` and close themselves in `__exit__`. Locks acquire in `__enter__` and release in `__exit__`.

## Generators as statement managers

Writing a class with two methods for every pattern is verbose. PEP 340's great idea was that a generator with a single `yield` is a natural way to express setup and teardown:

```python
@statement_template
def opened(path):
    f = open(path)
    try:
        yield f
    finally:
        f.close()
```

A decorator, `statement_template`, turns such a generator function into a factory for managers. Its `__enter__` advances the generator to the `yield` and returns the yielded value. Its `__exit__` resumes the generator:

- normally (as if `next()` were called) if the block ended without an exception;
- by raising the exception inside the generator at the `yield` if the block raised.

If the generator yields a second time, that is an error: a statement template must yield exactly once.

### Raising exceptions into generators

To support this, generators gain a method, `__raise__(type, value=None, traceback=None)`, that raises the given exception at the point where the generator is suspended. If the generator catches it and finishes, `__raise__` raises `StopIteration`. If it re-raises or raises another exception, that exception propagates.

The decorator uses this so that `try`/`except` and `try`/`finally` around the `yield` behave exactly as a reader would expect. An `except` clause in the generator sees the block's exceptions; if it swallows them, the manager's `__exit__` returns true and the exception is suppressed.

### Generator finalization

Generators currently cannot contain a `yield` inside a `try` with a `finally` clause, because there is no guarantee the generator will be resumed. To allow statement templates, this restriction is lifted. Generators gain a `close()` method that raises a `GeneratorExit` exception at the suspension point. `close()` is called when a generator is garbage collected. This guarantees that `finally` clauses in generators eventually run.

These changes are useful independently of the `with` statement and could be accepted separately.

## Examples

A lock:

```python
@statement_template
def locked(lock):
    lock.acquire()
    try:
        yield
    finally:
        lock.release()

with locked(my_lock):
    ...
```

Transactions:

```python
@statement_template
def transaction(db):
    db.begin()
    try:
        yield db
    except:
        db.rollback()
        raise
    else:
        db.commit()
```

Temporarily redirecting `sys.stdout`:

```python
@statement_template
def redirected(stream):
    saved, sys.stdout = sys.stdout, stream
    try:
        yield
    finally:
        sys.stdout = saved
```

Suppressing a particular exception:

```python
@statement_template
def ignored(*exceptions):
    try:
        yield
    except exceptions:
        pass
```

## Rejected Options

### Looping semantics

PEP 340 allowed the generator to yield more than once, re-running the block each time, which made the block statement a loop. That allows retry loops and other constructs to be expressed, but it changes the meaning of `break` and `continue` inside the block and makes it impossible to tell, by reading the statement, whether its body runs once or many times. Most uses only need one execution. Looping can still be written with an ordinary `for` loop over a generator.

### Not passing exception details to `__exit__`

PEP 310 called `__exit__` with no arguments. That is enough for locks and files but not for transactions, where commit and rollback depend on how the block ended. Passing the exception is cheap and makes the protocol much more expressive.

### Using `do`, `block`, or no keyword

Several keywords were considered. `with` reads well in nearly all examples and has precedent in other languages. A keyword-less form (`EXPR: BLOCK`) is too easy to confuse with other syntax.

## Backwards Compatibility

Adding `with` and `as` as keywords breaks code that uses them as identifiers. A `from __future__ import with_statement` import enables the statement in Python 2.5, with warnings for identifiers in the meantime; the keywords become unconditional in 2.6.
