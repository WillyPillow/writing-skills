# Abstract

This PEP proposes three standard attributes on exception instances: the `__context__` attribute for implicitly chained exceptions, the `__cause__` attribute for explicitly chained exceptions, and the `__traceback__` attribute for the traceback. A new `raise ... from` statement sets the `__cause__` attribute.

# Motivation

When an exception is raised while another exception is being handled, the information about the first exception is lost. Consider:

```python
try:
    config = parse(open(path).read())
except ParseError:
    log.write("could not parse %s\n" % path)
    raise
```

If `log.write` itself fails, say because the disk is full, the `IOError` from the logging call propagates and the `ParseError` vanishes. The traceback the programmer sees describes the logging failure and says nothing about the parse error that led to it. Debugging this requires guessing that there was an earlier problem, then reproducing it.

A second, related problem arises when a library deliberately translates one exception into another. A database adapter might catch a socket error and raise its own `OperationalError` so that callers do not need to know about the transport layer. That is good API design, but it hides the underlying cause. Library authors today work around this in ad hoc ways: some store the original exception as an attribute with a name of their own choosing (`original`, `inner`, `wrapped_exc`, `reason`), some format it into the message string, and some keep a copy of `sys.exc_info()`. None of these is understood by the traceback printer or by debugging tools, and each library chooses a different convention.

A third problem is that the traceback of an exception is not attached to the exception object. It lives in `sys.exc_info()` or is passed separately as the third argument to `raise`. Code that wants to store an exception for later re-raising must store a tuple of three values and be careful to keep them together. This is awkward, and the three-argument form of `raise` is one of the more obscure corners of the language.

Other languages have addressed these issues. Java's `Throwable` has a `getCause()` method, and its stack traces print chains of "Caused by:" sections. C# has `InnerException`. Perl 6 and Ruby have related mechanisms. Python is in a position to adopt a cleaner version of the same idea, since Python 3.0 permits changes that would be backward-incompatible in 2.x.

# Rationale

Two distinct situations need to be distinguished.

In the first, an exception occurs unexpectedly while handling another, as in the logging example. The second exception was not intended to replace the first; it is an accident. The traceback should show both, with an indication that the second happened during handling of the first.

In the second, a programmer intentionally raises a new exception to represent the failure at a higher level of abstraction. Here the new exception is the main event, and the original is supporting detail. The programmer is making an explicit statement about causation.

Treating these with one attribute would lose information about intent, and would mean that every exception raised within an `except` block, intended or not, appears as a "cause". This PEP therefore uses two attributes: `__context__` records the implicit situation automatically, and `__cause__` records the explicit one when the programmer asks for it.

Names with double underscores are chosen because these attributes are set by the interpreter and have semantics defined by the language, in the same way as `__class__` or `__dict__`. Using ordinary names such as `cause` would risk colliding with attributes that existing exception subclasses already define.

# Specification

## The `__context__` attribute

Every exception instance has a `__context__` attribute, initially `None`.

When an exception is raised while another exception is being handled, that is, inside an `except` or `finally` clause where `sys.exc_info()` would report an active exception, the interpreter sets the new exception's `__context__` to the exception being handled. This happens automatically and requires no change to user code.

If the new exception already has a `__context__` set, it is overwritten. If setting `__context__` would create a cycle (for instance, re-raising an exception that is already somewhere in the chain), the interpreter breaks the cycle rather than creating it.

## The `__cause__` attribute

Every exception instance has a `__cause__` attribute, initially `None`. It is set by the new `raise ... from` statement:

```python
raise EXCEPTION from CAUSE
```

This is equivalent to:

```python
exc = EXCEPTION
exc.__cause__ = CAUSE
raise exc
```

`CAUSE` must be an exception instance or class; if it is a class, it is instantiated. Any other value raises `TypeError`.

Example:

```python
class DatabaseError(Exception):
    pass

def fetch(query):
    try:
        return connection.execute(query)
    except socket.error as e:
        raise DatabaseError("connection lost") from e
```

Setting `__cause__` does not affect `__context__`. In the example above, the `DatabaseError` will have both attributes pointing at the `socket.error`, since it was raised inside the handler.

## The `__traceback__` attribute

Every exception instance has a `__traceback__` attribute. When an exception is raised, the interpreter sets `__traceback__` to the traceback object for the current frame, and as the exception propagates up the stack the traceback is extended in place, exactly as the third element of `sys.exc_info()` is today.

With the traceback stored on the exception, `sys.exc_info()` becomes equivalent to:

```python
(type(exc), exc, exc.__traceback__)
```

and the three-argument form of `raise` is no longer needed. To re-raise an exception with a particular traceback, one writes:

```python
raise exc.with_traceback(tb)
```

where `with_traceback` sets `__traceback__` and returns the exception. The three-argument `raise` form is removed in Python 3.0.

## Default traceback printing

The default exception display, as implemented in `traceback.print_exception` and used by the interpreter for uncaught exceptions, is changed to print the whole chain. The chain is printed starting from the earliest exception, so that the final line shown is the exception that actually propagated.

For each exception in the chain, the printer examines `__cause__` first. If it is not `None`, the cause is printed, followed by:

```
The above exception was the direct cause of the following exception:
```

Otherwise, if `__context__` is not `None`, the context is printed, followed by:

```
During handling of the above exception, another exception occurred:
```

The printer guards against cycles by tracking which exceptions it has already displayed.

New functions in the `traceback` module accept an optional `chain` argument, defaulting to `True`, so that callers who want only the last exception can request it.

# Reference cycles

Storing the traceback on the exception creates a reference cycle when an exception is bound to a local variable in an `except` clause: the exception refers to the traceback, the traceback refers to the frame, and the frame refers to the local variable holding the exception. Such cycles are collected by the cyclic garbage collector, but they delay the release of resources held by the frame.

To mitigate this, the `except E as name:` clause is changed so that `name` is deleted at the end of the clause, as if by `del name`. Code that needs to retain the exception after the handler must assign it to a different variable explicitly.

# Backwards Compatibility

The new attributes do not conflict with any existing standard exception attributes. Third-party exceptions that happen to define `__cause__`, `__context__` or `__traceback__` are unlikely, since names of that form are reserved for the language.

Removal of three-argument `raise` and the deletion of the `except` target are incompatible changes, appropriate for Python 3.0. The `2to3` tool can translate `raise E, V, T` into `raise E(V).with_traceback(T)`.

# Rejected Ideas

**A single attribute for both kinds of chaining.** Discussed under Rationale.

**Automatically setting `__cause__` instead of `__context__`.** This would mislabel accidental exceptions as intentional.

**A method instead of syntax, such as `raise E.caused_by(e)`.** This is possible with `with_traceback`-style methods, but a keyword form reads more naturally and parallels similar constructs elsewhere. The word `from` is already a keyword, so no new reserved word is needed.

**Printing the chain in reverse order, most recent first.** Python tracebacks already print the most recent call last; printing chains oldest-first keeps the most relevant information nearest the prompt, consistent with existing practice.
