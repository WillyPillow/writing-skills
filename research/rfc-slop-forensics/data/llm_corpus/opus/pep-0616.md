# Abstract

This PEP proposes two new methods, `removeprefix()` and `removesuffix()`, for Python's string types. `s.removeprefix(p)` returns `s` with `p` removed from the start if `s` starts with `p`, and returns `s` unchanged otherwise. `removesuffix()` does the same at the end. The methods are added to `str`, `bytes`, `bytearray`, and `collections.UserString`.

# Motivation

Removing a known prefix or suffix is a very common string operation. Python has no direct method for it, and the two obvious attempts are both wrong or awkward.

The first attempt is usually `lstrip` or `rstrip`:

```python
>>> "test_case.py".rstrip(".py")
'test_case'
>>> "happy.py".rstrip(".py")
'ha'
```

`rstrip` takes a set of characters, not a suffix. It removes any trailing characters that appear in the set, which is almost never what the author meant. This confusion is common enough that it is one of the most frequently reported "bugs" in `str.strip` on the issue tracker and a frequent question on help forums. Because it often works on the test input, the mistake can go unnoticed for a long time.

The correct version is:

```python
if s.endswith(suffix):
    s = s[:-len(suffix)]
```

This has its own trap. If `suffix` is the empty string, `s[:-0]` is `s[:0]`, which is `''`. Code that works for every non-empty suffix silently returns an empty string for an empty one. The fully correct version is:

```python
if suffix and s.endswith(suffix):
    s = s[:-len(suffix)]
```

Few people write this the first time. The prefix version, `s[len(prefix):]`, does not have the empty-string problem, but it still requires spelling out the condition and repeating the prefix, which invites mismatches when one copy is edited and the other is not.

A search of the standard library and of popular packages on PyPI turns up many hand-written versions of these patterns, a number of which have the `rstrip` bug or the empty-suffix bug. A method on the string type would replace them with one obviously correct call.

# Specification

## `str`

```python
def removeprefix(self, prefix, /):
    if self.startswith(prefix):
        return self[len(prefix):]
    else:
        return self[:]

def removesuffix(self, suffix, /):
    # suffix='' should not call self[:-0].
    if suffix and self.endswith(suffix):
        return self[:-len(suffix)]
    else:
        return self[:]
```

Both methods:

- Take exactly one positional-only argument, which must be a `str`. Passing any other type raises `TypeError`.
- Remove at most one copy of the prefix or suffix. `"aaab".removeprefix("a")` is `"aab"`.
- Return a string equal to the original if the prefix or suffix is not present. For `str`, which is immutable, CPython may return the original object rather than a copy; callers must not rely on either behavior.

## `bytes` and `bytearray`

The same methods are added with the same semantics. The argument may be any object supporting the buffer protocol. The return type matches the type of `self`: `bytes.removeprefix` returns `bytes`, and `bytearray.removeprefix` returns a new `bytearray`. The `bytearray` methods do not modify the object in place, consistent with the other methods on `bytearray` that return a modified copy, such as `replace` and `strip`.

## `collections.UserString`

`UserString` gains both methods, delegating to the wrapped string and returning a `UserString`.

# Rationale

## Why methods instead of a function in a module

Prefix and suffix tests are already methods (`startswith` and `endswith`). Users look for the removal operation in the same place. A function in `string` or a recipe in the documentation would be harder to find and would not prevent the `rstrip` mistake, because `rstrip` is right there on the object.

## Why one argument, not a tuple

`startswith` and `endswith` accept a tuple of alternatives. It would be natural to allow `removeprefix(("http://", "https://"))`. We decided against it for now. With a tuple, it is not obvious which prefix should be removed if more than one matches. Taking the first match in tuple order is one answer, taking the longest is another, and each has users who would expect it. The single-argument form is unambiguous and covers most uses. A tuple form can be added later if a clear rule emerges.

## Why not remove repeatedly

Removing all leading copies of a prefix is a different operation, and it is easy to build with a loop. The common case is a single known prefix, such as a URL scheme, a file extension, or a namespace prefix on an identifier.

## Naming

Alternatives considered included `strip_prefix`, `trimprefix`, `cutprefix`, `lchop`, and `without_prefix`.

- Names containing `strip` were rejected because they suggest a close relationship to `strip`, `lstrip`, and `rstrip`, whose different behavior is the source of the confusion this PEP is trying to fix.
- `cut` and `chop` are used in other languages with differing meanings.
- `removeprefix` describes exactly what the method does and follows the existing all-lowercase, no-underscore style of `str` methods such as `startswith`.

## Why not return a flag

Some callers want to know whether the prefix was present. They can check `startswith` themselves, or compare the result's length with the original. Returning a tuple would make the common case clumsy.

# Backward compatibility

The new methods do not conflict with any existing names on the affected types. Subclasses of `str` that already define methods with these names will continue to use their own definitions. A search of PyPI found no packages defining methods with exactly these names on string subclasses.

# How to teach this

The documentation for `lstrip` and `rstrip` will be updated to mention the new methods, with an example showing the difference:

```python
>>> "Arthur: three!".lstrip("Arthur: ")
'ee!'
>>> "Arthur: three!".removeprefix("Arthur: ")
'three!'
```

The tutorial section on strings will introduce `removeprefix` and `removesuffix` alongside `startswith` and `endswith`.

# Reference implementation

An implementation for `str`, `bytes`, `bytearray`, and `UserString`, with tests and documentation, is available as a pull request against CPython.
