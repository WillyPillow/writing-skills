# Abstract

This PEP proposes a new built-in type, `bytes`, with a constructor of the same name. A `bytes` object is a mutable, fixed-length, efficiently stored array of 8-bit values. It differs from the existing types that can hold binary data (`str`, `array.array('B')`, and `buffer`) in a few specific ways: it is never confused with text, its memory can be shared safely with C code, and its size cannot change after creation, so pointers into it stay valid.

# Motivation

Python programs handle binary data all the time: file contents, network packets, image buffers, the output of `struct.pack`. Today the usual container is `str`, because that is what `read()` returns and what `socket.recv()` returns. Using `str` for binary data has three problems.

**`str` means text.** The same type is used for "a sequence of characters" and "a sequence of octets." That ambiguity is already causing trouble as Unicode becomes more common: functions cannot tell whether a `str` argument should be decoded, and `str + unicode` silently decodes using the default encoding, which is wrong for binary data and fails on non-ASCII bytes.

**`str` is immutable.** Code that builds or modifies binary data must create a new string for every change. Reading a large file into a preallocated buffer, or filling a buffer from a C library, is not possible without copying.

**The alternatives each fall short.**

- `array.array('B')` is mutable and stores bytes efficiently, but it can be resized. A C extension that takes a pointer to its data via the buffer interface may find that pointer invalid after Python code appends to the array. This is a real source of crashes.
- The `buffer` object exposes memory from another object, but it inherits the same problem: if the underlying object reallocates, the buffer's pointer dangles. The `buffer` type is also poorly documented and rarely used correctly.
- `mmap` objects are fixed-size and mutable but are tied to files and operating system mappings.

What is missing is a simple type with these properties: mutable contents, fixed length, contiguous storage, and a stable address for the lifetime of the object. That is the `bytes` type.

# Specification

## Construction

```python
bytes()                  # empty, length 0
bytes(n)                 # length n, all zeros
bytes(iterable)          # from an iterable of ints in range(256)
bytes(str_object)        # copy the 8-bit contents of a str
bytes(buffer_object)     # copy from any object supporting the buffer interface
```

Passing a `unicode` object raises `TypeError`. Converting text to bytes requires an explicit encoding step: `bytes(u.encode('utf-8'))`. This is deliberate. The point of the type is to keep text and binary data apart.

## Elements

Indexing returns an `int` in the range 0 to 255:

```python
>>> b = bytes([1, 2, 3])
>>> b[0]
1
>>> b[0] = 255
>>> b[0] = 256
ValueError: byte must be in range(0, 256)
```

Slicing returns a new `bytes` object containing a copy of the selected range. Slice assignment is allowed only when it does not change the length:

```python
>>> b[0:2] = bytes([9, 9])     # fine
>>> b[0:2] = bytes([9])        # ValueError: cannot resize bytes
```

`del b[i]` raises `TypeError`.

## Operations

`bytes` supports `len()`, iteration, `in` (with an integer or a `bytes` operand), comparison (lexicographic, by unsigned value), and concatenation and repetition (`+`, `*`), which return new objects. It also supports `hash()` raising `TypeError`, since the object is mutable.

The following methods are provided:

- `b.find(sub[, start[, end]])`, `b.index(...)`, `b.count(...)` search for a sub-sequence.
- `b.tostring()` returns a `str` with the same 8-bit contents.
- `b.hex()` returns a `str` of hexadecimal digits; `bytes.fromhex(s)` is the inverse.

String methods that only make sense for text (`upper`, `split` on whitespace, `strip`, formatting with `%`) are deliberately left out. Users who need them can convert to `str`.

## Representation

`repr(b)` produces `bytes([1, 2, 3])` style output for short objects. For long objects the output is still valid but long; truncating it would break the property that `eval(repr(x)) == x`.

## Buffer interface

`bytes` implements the read and write buffer interface with a single segment. Because the length can never change, the pointer returned by `bf_getwritebuffer` remains valid for as long as the object is alive. C extensions may hold onto it as long as they also hold a reference to the object.

## Memory layout

The data is stored in a separate allocation pointed to by the object header, not inline. This makes it possible, in the future, to create `bytes` objects that wrap memory owned by someone else (a C library or a memory-mapped region) without copying. That constructor is not part of this PEP but the layout keeps the option open.

The allocator aligns the data on a boundary suitable for any C type, so extensions can treat it as an array of `double` or a C struct without alignment faults.

## Pickling

`bytes` objects pickle and unpickle as their contents. A new pickle opcode is not required; the default reduction through `tostring()` and the constructor is sufficient.

## File and socket integration

This PEP does not change what `file.read()` or `socket.recv()` return. They continue to return `str`. Two additions are proposed:

- `file.readinto(b)` already exists in a limited form; it will be documented as accepting a `bytes` object and filling it in place.
- `socket.recv_into(b[, nbytes])` is added, filling an existing `bytes` object.

These let programs reuse buffers instead of allocating a new string per read.

# Rationale

**Why fixed length?** It is the property that makes the type safe to share with C. Every other mutable type in Python that holds raw memory can be resized, and every one of them has the dangling-pointer problem. Programs that need growable binary buffers can use a list of chunks or `array.array`, and copy into a `bytes` object when the final size is known.

**Why mutable?** An immutable bytes type would mostly duplicate `str`. Mutability allows in-place I/O and in-place modification, which is where the performance benefit comes from.

**Why integers, not one-character strings?** Indexing a `str` returns a `str` of length 1, which is a text-oriented answer. For binary data the natural element is a small integer. This also makes arithmetic on elements (`b[i] ^ key`) direct.

**Why not just fix `array`?** `array.array('B')` already has a resizing API used by existing code. Removing it would break that code, and adding a "frozen length" flag would make the type harder to reason about.

# Backward compatibility

`bytes` is a new name in the built-in namespace. Programs that already use `bytes` as a variable name continue to work, because local and global names shadow built-ins. No existing behavior changes.

# Open issues

- Should there be a literal syntax, such as `b"..."`? This PEP does not propose one. It can be added later once the type has seen use.
- Should `str` methods like `split` and `replace` be added, restricted to byte operands?
- Should a future version of Python change `file.read()` in binary mode to return `bytes`? That would be the natural end point but is a large compatibility change and is out of scope here.

# Reference implementation

A reference implementation as a C extension module is available and will be moved into `Objects/bytesobject.c` if this PEP is accepted.
