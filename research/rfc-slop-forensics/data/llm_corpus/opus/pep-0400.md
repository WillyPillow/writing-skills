# PEP 400: Deprecate codecs.StreamReader and codecs.StreamWriter

| Field | Value |
|---|---|
| PEP | 400 |
| Title | Deprecate codecs.StreamReader and codecs.StreamWriter |
| Status | Draft |
| Type | Standards Track |
| Python-Version | 3.3 |

## Abstract

`io.TextIOWrapper` and `codecs.StreamReaderWriter` offer the same API. `TextIOWrapper` has more features and is faster than `StreamReaderWriter`. Having two implementations means that bugs must be fixed twice, and the two can drift apart in subtle ways.

The `codecs` module was introduced in Python 2.0 (PEP 100). The `io` module was introduced in Python 2.6 and 3.0 (PEP 3116) and reimplemented in C in Python 2.7 and 3.1. This PEP proposes deprecating `codecs.StreamReader`, `codecs.StreamWriter`, and `codecs.StreamReaderWriter` and making `codecs.open()` a thin alias for the built-in `open()`.

## Motivation

### Two ways to read text

There are two ways in the standard library to wrap a binary stream and decode it as text:

```python
import codecs
f = codecs.open("data.txt", "r", encoding="utf-8")
```

and

```python
f = open("data.txt", "r", encoding="utf-8")
```

The first returns a `codecs.StreamReaderWriter`, which wraps a binary file and a pair of codec-specific `StreamReader` and `StreamWriter` objects. The second returns an `io.TextIOWrapper` wrapping a buffered binary file.

For most users, these behave the same. Both have `read()`, `readline()`, `readlines()`, `write()`, `writelines()`, iteration, and context manager support. That is the problem: two objects with the same interface, maintained separately, with nearly identical documentation, and no clear guidance about when to use one or the other.

### `TextIOWrapper` is the better implementation

`TextIOWrapper` is the implementation that the language itself uses. `open()` returns it. `sys.stdin`, `sys.stdout`, and `sys.stderr` are instances of it. Every improvement to text I/O since Python 3.0 has gone into it.

Compared with `StreamReaderWriter`, `TextIOWrapper`:

- Handles universal newlines correctly. `StreamReader` has its own newline handling, which differs in edge cases such as a `\r\n` pair split across two reads.
- Supports `tell()` and `seek()` on text streams with a stateful decoder, using opaque cookies that encode the decoder state. `StreamReader` has `seek()` that resets the codec but cannot return to an arbitrary position in the middle of a multibyte sequence.
- Supports the `errors` and `newline` arguments consistently, and allows `reconfigure`-style changes.
- Uses incremental decoders, which every codec in the standard library already provides.
- Is implemented in C and is substantially faster. Micro-benchmarks reading a UTF-8 file line by line show `TextIOWrapper` several times faster than `StreamReader`, and the gap is larger for writing.

### Duplicated bugs

Over the years, bugs have been reported against `StreamReader` that were already fixed, or never present, in `TextIOWrapper`. Examples include incorrect behaviour of `readline()` when called with a size argument, incorrect handling of BOMs for UTF-16 when reading after a seek, and `readlines()` behaving differently from repeated `readline()` calls. Each fix requires someone who understands the old code, and there are few such people. Each unfixed bug is a trap for users who chose `codecs.open()` because older documentation recommended it.

### Codec authors carry the burden

Every codec registered with the `codecs` module is supposed to provide `StreamReader` and `StreamWriter` classes in addition to its encoder, decoder, incremental encoder, and incremental decoder. For codecs implemented in the standard library, most of these stream classes are trivial subclasses that add nothing. Third-party codec authors must still write them. If `StreamReader` and `StreamWriter` are no longer needed, the codec interface can shrink to the parts that are actually used.

## Specification

1. `codecs.StreamReader`, `codecs.StreamWriter`, `codecs.StreamReaderWriter`, and `codecs.StreamRecoder` emit `DeprecationWarning` when instantiated.
2. `codecs.open()` is changed to call the built-in `open()` and return an `io.TextIOWrapper` (or a binary file object, when no encoding is given). The existing signature, `codecs.open(filename, mode='r', encoding=None, errors='strict', buffering=-1)`, is preserved. Its documentation will state that `open()` is preferred.
3. `codecs.getreader()` and `codecs.getwriter()` emit `DeprecationWarning`. Code that needs to wrap an existing binary stream should use `io.TextIOWrapper(stream, encoding=...)` instead.
4. `codecs.CodecInfo` keeps its `streamreader` and `streamwriter` attributes for compatibility. New codecs may leave them as `None`. Tools that look them up should handle `None`.
5. The standard library is updated to stop using the deprecated classes internally.
6. The classes are removed no earlier than two feature releases after the deprecation.

## Backwards Compatibility

### Differences in behaviour

Switching `codecs.open()` to return a `TextIOWrapper` changes behaviour in a few places that existing code may depend on:

- **Newlines.** `codecs.open()` historically opened the underlying file in binary mode and did no newline translation, so a Windows file read through it kept its `\r\n` endings. `TextIOWrapper` translates newlines by default. To preserve the old behaviour, `codecs.open()` will pass `newline=''`, which disables translation on reading and writing.
- **Mode strings.** `codecs.open()` forced binary mode on the underlying file by appending `b` to the mode. The new implementation will strip `b` from the mode it passes to `open()` when an encoding is given.
- **`readline(size)` and `read(size, chars)`.** `StreamReader.read()` has an extra `chars` argument that `TextIOWrapper.read()` does not. The `chars` argument is rarely used. Calls that pass it will fail. This is noted in the documentation.
- **Codec-specific stream subclasses.** A few codecs, such as the UTF-16 and UTF-32 codecs, have stream classes that handle the byte-order mark. `TextIOWrapper` achieves the same effect using incremental codecs, which already handle the BOM.

### Third-party code

Code that subclasses `StreamReader` or `StreamWriter` directly will see deprecation warnings and, eventually, breakage. A search of public packages finds such subclasses mostly in codec packages that also provide incremental decoders. Those packages can simply stop providing stream classes.

## Alternatives

### Keep both, fix bugs in `StreamReader`

This preserves compatibility but leaves the maintenance burden in place, and the two implementations will continue to diverge.

### Reimplement `StreamReader` on top of `TextIOWrapper`

`StreamReader` could become a subclass or wrapper of `TextIOWrapper`, preserving its constructor while using the newer machinery. This was considered, but the APIs differ enough (`read(size, chars, firstline)`, `reset()`, codec-specific overrides) that a faithful wrapper would itself be a nontrivial amount of code to maintain, for an API we would rather users leave.

### Only change the documentation

Recommending `open()` in the documentation, without deprecation, has been the de facto policy. It has not stopped new code from using `codecs.open()`, in part because many tutorials still recommend it for Python 2 compatibility.

## Open Issues

- Whether the deprecation period should be extended, given how widely `codecs.open()` appears in code that supports both Python 2 and 3.
- Whether `codecs.open()` itself should eventually be deprecated, or kept indefinitely as an alias.
