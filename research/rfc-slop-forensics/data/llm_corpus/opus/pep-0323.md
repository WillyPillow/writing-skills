# PEP 323: Copyable Iterators

| Field | Value |
|---|---|
| PEP | 323 |
| Title | Copyable Iterators |
| Status | Draft |
| Type | Standards Track |
| Python-Version | 2.5 |

## Abstract

This PEP proposes that some iterator types should support shallow copying of their instances by exposing a `__copy__` method that meets a specific set of requirements. It also describes how code that consumes an iterator can take advantage of such a method when one is present, and fall back gracefully when it is not.

## Motivation

The iterator protocol is deliberately minimal. An iterator has a `__next__` method (spelled `next` in older versions) that returns the next item or raises `StopIteration`, and an `__iter__` method that returns the iterator itself. This minimalism is a strength: almost anything that produces a sequence of values can be expressed as an iterator, including infinite streams, values read from a socket, and lazily computed results.

The cost of that minimalism is that an iterator, once advanced, cannot be rewound or forked. Code that needs to look at a stream twice, or needs to remember a position and return to it later, has two options today:

1. Materialize the remaining items into a list and iterate over the list as many times as needed. This works, but it consumes memory proportional to the remaining length of the stream, and it is impossible for infinite iterators.
2. Use `itertools.tee`, which splits one iterator into several independent iterators. `tee` buffers every item that has been consumed by the leading iterator but not yet by the trailing ones. When the consumers stay close to each other this is cheap. When one runs far ahead, the buffer grows without bound.

Both approaches treat the source iterator as a black box. Yet many iterators in the standard library are not black boxes at all. An iterator over a list is a reference to the list plus an integer index. An iterator over a `range` is a few integers. An iterator returned by `dict.items()` is a reference to the dictionary plus a position in its internal table. For these iterators, producing an independent copy that resumes from the same point is trivial and costs a constant amount of memory. There is simply no standard way to ask for it.

This PEP supplies that way.

## Specification

### The `__copy__` protocol for iterators

An iterator type MAY define a `__copy__` method. If it does, calling `copy.copy(it)` on an instance `it` MUST return a new iterator `it2` such that:

- `it2` is a distinct object from `it` (`it2 is not it`).
- Advancing `it2` does not affect the items subsequently produced by `it`, and vice versa.
- Assuming the underlying data is not mutated, `it` and `it2` produce the same sequence of items from the point of the copy onward.

The copy is shallow. The items produced by the two iterators are the same objects, not copies of them. Likewise, the underlying container is shared, not duplicated. If the underlying container is mutated after the copy is made, both iterators observe the mutation in whatever way a single iterator over that container would have observed it.

An iterator type that cannot meet these requirements cheaply MUST NOT define `__copy__`. In particular, an iterator over an external resource such as a file or a network connection should not attempt to emulate copying by buffering, since that would defeat the purpose of the protocol: callers who see `__copy__` are entitled to assume it is inexpensive.

### Standard library iterators

The following built-in iterator types will gain a `__copy__` method:

- Iterators over sequences produced by the default `iter()` fallback that uses `__getitem__`.
- `list_iterator`, `tuple_iterator`, and their reversed counterparts.
- `range_iterator`.
- Dictionary key, value, and item iterators.
- `itertools.count` and `itertools.repeat`.
- `enumerate`, when the wrapped iterator is itself copyable.
- `itertools` combinators such as `islice`, `chain`, `takewhile`, `dropwhile`, `starmap`, and `zip`, when every iterator they wrap is copyable.

Combinators that wrap other iterators expose `__copy__` conditionally. Calling `copy.copy` on such a combinator copies each wrapped iterator in turn. If any wrapped iterator is not copyable, the combinator's `__copy__` raises `TypeError`. Because a type cannot easily remove a method on a per-instance basis, callers that need to test copyability ahead of time should use the helper described below rather than `hasattr`.

Generator objects will not be copyable. A generator's state includes its frame, local variables, and the position of its instruction pointer. Copying that frame shallowly would produce two generators that share mutable local objects, which violates the independence requirement in ways that are hard to predict and harder to debug. Deep copying the frame is expensive and semantically dubious for frames holding references to external resources.

File objects will not be copyable, for the reasons given above.

### Using copyable iterators

Code that wants to fork an iterator should try `copy.copy` first and fall back to `itertools.tee`:

```python
import copy
import itertools

def fork(it):
    try:
        return it, copy.copy(it)
    except TypeError:
        return itertools.tee(it)
```

To make this pattern the default, `itertools.tee` will itself be changed to check for a copyable iterator. When `tee` is called on an iterator that supports `__copy__`, it returns the original iterator plus copies of it, without allocating a shared buffer. When the iterator does not support copying, `tee` behaves exactly as it does today. Existing callers of `tee` therefore get the memory benefit automatically.

One subtlety: `tee` currently guarantees that the source iterator should not be used after the call, since advancing it would cause the tee'd iterators to miss items. Under the new behaviour this restriction is still documented, even though in the copyable case using the original would happen to work. Keeping the documented contract unchanged avoids making callers depend on an implementation detail.

## Rationale

### Why `__copy__` rather than a new method

The `copy` module already defines a protocol for making shallow copies, and that protocol already means the right thing: an independent object that shares references to its contents. Introducing a separate `__fork__` or `clone` method would give two names to the same idea. Reusing `__copy__` also means that any third-party iterator class that has already implemented `__copy__` sensibly will interoperate with the new `tee` behaviour without changes.

There is a risk that some existing class defines `__copy__` in a way that does not satisfy the independence requirement. The authors are not aware of any such iterator in widespread use, and the requirement is the natural reading of what "copy" means for an iterator. A class whose `__copy__` returns the same object, for example, would already be surprising to users of `copy.copy`.

### Why not make every iterator copyable

It was suggested that every iterator could be made copyable by falling back to a buffering strategy similar to `tee`. That would make `__copy__` universally available but would hide large and unpredictable memory costs behind an operation that looks cheap. The value of this proposal comes from the guarantee that copying is inexpensive. Iterators that cannot keep that guarantee are better served by explicit buffering through `tee`, where the cost is documented.

### Why not deep copies

A deep copy of an iterator would copy the underlying container as well. That is occasionally useful, but it is already available through `copy.deepcopy(list(it))` and similar idioms, and it is not what callers who want to "remember a position" are asking for. Deep copying iterators is left unspecified by this PEP.

## Backwards Compatibility

Adding a method to built-in iterator types does not affect code that does not call it. Code that previously called `copy.copy` on a built-in iterator received a `TypeError` or an object that did not behave independently; such code was already broken and is unlikely to exist in practice.

The change to `itertools.tee` alters its memory profile but not its observable output, provided callers follow the documented rule of not touching the source iterator after calling `tee`. Callers who violate that rule may see different results in the copyable case than before. This is considered acceptable because the rule has always been part of the documentation.

## Reference Implementation

A reference implementation adds `__copy__` to the iterator types listed above and modifies `tee` to attempt a copy before allocating its buffer. Most of the work consists of short C functions that allocate a new iterator object and copy the index and container reference. For combinators, the implementation calls `copy.copy` on each wrapped iterator and builds a new combinator around the results.

## Open Issues

- Whether dictionary iterators should be copyable given that a dictionary resized during iteration raises `RuntimeError`. The proposal is that a copied dictionary iterator raises in the same circumstances as the original, which seems consistent.
- Whether a separate predicate, such as `itertools.iscopyable(it)`, should be added so that callers can check copyability of combinators without triggering an exception.
