# Abstract

This PEP specifies a tagging system to indicate with which versions of Python a built or binary distribution is compatible. A set of three tags indicate which Python implementation and language version, ABI, and platform a built distribution requires. The tags are terse because they will be included in filenames.

# Rationale

Today's built distributions do not carry enough information to tell an installer whether they will work on a given system. The existing `bdist_*` commands encode some platform information in filenames, but the conventions are inconsistent and incomplete. An egg named `foo-1.0-py2.7-linux-x86_64.egg` says it targets CPython 2.7 on 64-bit Linux, but it cannot express that it is pure Python and works on any 2.x interpreter, nor that it needs a particular ABI variant such as a debug build or a UCS-4 Unicode build. Nor can it say anything about alternative implementations such as PyPy or Jython.

As the community moves toward a common binary format (see PEP 427, the wheel format), installers need a reliable way to answer one question: given the interpreter I am running, which of the available archives can I install? This PEP provides the vocabulary for that answer. It defines the tags; it does not define the archive format that carries them.

# Overview

A compatibility tag consists of three parts, separated by hyphens:

```
{python tag}-{abi tag}-{platform tag}
```

For example:

```
cp33-cp33m-linux_x86_64
py27-none-any
pp20-pypy_20-macosx_10_6_intel
```

A distribution's filename includes this triple after the name and version, as specified by the archive format.

## Python tag

The Python tag indicates the implementation and version required. It is formed from an abbreviation of the implementation followed by the version number with the dot removed.

The following abbreviations are defined:

| Implementation | Abbreviation |
|----------------|--------------|
| Generic Python | `py`         |
| CPython        | `cp`         |
| IronPython     | `ip`         |
| PyPy           | `pp`         |
| Jython         | `jy`         |

Other implementations should register an abbreviation by amending this PEP.

The version is `sys.version_info[0]` followed by `sys.version_info[1]`, with no separator. Thus CPython 3.3 is `cp33`. A version consisting of the major version alone, as in `py2` or `py3`, indicates any release in that major series.

The generic `py` prefix is used for distributions that rely only on the Python language and not on any implementation-specific behaviour. A pure-Python package that supports all of Python 2 is tagged `py2`, not `cp27`.

For implementations other than CPython the version is the implementation's own version, not the version of Python it is compatible with. PyPy 2.0 is `pp20`. This allows tags to distinguish between PyPy releases that offer different extension module support, even if they implement the same language version.

## ABI tag

The ABI tag indicates which Python ABI is required by any included extension modules. For CPython, it is formed from the implementation and version, followed by flags indicating build options that affect the ABI:

- `d` for a debug build (`--with-pydebug`)
- `m` for pymalloc (`--with-pymalloc`)
- `u` for a wide Unicode build (`--with-wide-unicode`, Python 3.2 and earlier)

So a standard CPython 3.3 build has ABI tag `cp33m`, while a debug build of 3.3 is `cp33dm`.

The special value `none` means the distribution contains no extension modules and does not depend on any particular ABI. The tag `abi3` designates the CPython stable ABI defined in PEP 384; a distribution tagged `abi3` works with any CPython that implements the stable ABI at or above the version given in its Python tag.

Implementations other than CPython should define their ABI tags in a way that distinguishes incompatible builds. Where an implementation exposes `sysconfig.get_config_var('SOABI')`, the ABI tag is derived from that value by replacing hyphens and periods with underscores.

## Platform tag

The platform tag is the value of `distutils.util.get_platform()` with all hyphens and periods replaced by underscores. For example:

- `win32`
- `win_amd64`
- `linux_i386`
- `linux_x86_64`
- `macosx_10_8_x86_64`

The special value `any` means the distribution runs on any platform.

# Use

## Building

A tool that builds a distribution determines its tags as follows:

- If the distribution is pure Python and does not depend on implementation details, its tags are `py{major}{minor}-none-any` or, if it works across a whole major series, `py{major}-none-any`.
- If it contains extension modules, it uses the tags of the interpreter that built it.

The builder may override these defaults when the author knows better, for instance when an extension module is built against the stable ABI.

## Installing

An installer determines the list of tags supported by the running interpreter, in order of preference. When choosing among several available distributions for a project, it selects the one whose tags appear earliest in this list.

For CPython 3.3 on 64-bit Linux, the supported list would begin:

1. `cp33-cp33m-linux_x86_64`
2. `cp33-abi3-linux_x86_64`
3. `cp3-abi3-linux_x86_64`
4. `cp33-none-linux_x86_64`
5. `cp3-none-linux_x86_64`
6. `py33-none-linux_x86_64`
7. `py3-none-linux_x86_64`
8. `cp33-none-any`
9. `cp3-none-any`
10. `py33-none-any`
11. `py3-none-any`
12. `py32-none-any`
13. `py31-none-any`
14. `py30-none-any`

The ordering expresses a preference for the most specific match. A build compiled for exactly this interpreter is likely to be the fastest and best tested; a generic pure-Python build is the fallback.

An installer must not install a distribution whose tags do not appear in the supported list. Installers may let users add or remove tags, for example to accept builds for an older OS X version that are known to be compatible.

The list of supported tags is necessarily implementation-specific. This PEP describes how CPython's list should be constructed; other implementations should document theirs.

## Compressed tag sets

A single distribution may be compatible with several tag triples. To avoid producing many identical files that differ only in name, each tag component may contain multiple values separated by periods. For example, a pure-Python package that supports Python 2 and 3 may be tagged:

```
py2.py3-none-any
```

The set of tags for such a file is the Cartesian product of its components. An installer expands the compressed set and checks whether any member appears in its supported list.

# FAQ

**Why not use the full platform names?** Filenames are visible in indexes, URLs and command lines. Short, regular tags keep them readable and avoid characters that are awkward in filenames on some systems.

**What about Linux distributions?** The `linux_x86_64` tag says nothing about which C library or other system libraries are present. In practice, binaries built on one Linux distribution often fail on another. This PEP does not try to solve that problem. Indexes such as PyPI may choose not to accept Linux binaries until a more precise tag is defined in a future PEP.

**Why is the implementation version, not the language version, used for PyPy?** Because extension compatibility depends on the implementation's internals, which change between PyPy releases even when the language version does not.

**Can I tag a distribution as compatible with a version that does not yet exist?** Yes, if you are confident. Installers will treat the tag as written.
