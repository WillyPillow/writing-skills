# Abstract

This PEP adds built-in support for lightweight virtual environments. A virtual environment is a directory containing a Python executable and its own `site-packages`. Packages installed into it are invisible to the base Python installation and to other environments. By default the environment is also isolated from the base installation's `site-packages`, though that can be turned off. The standard library is shared with the base installation rather than copied.

The PEP specifies a small change to interpreter startup, so that a Python binary can recognize that it is running inside a virtual environment, and a new standard library module, `venv`, for creating environments.

# Motivation

Isolated per-project package sets are now standard practice in Python development. They let different projects depend on incompatible versions of the same package, let a developer install packages without administrator rights, and make it possible to reproduce a deployment exactly.

The third-party `virtualenv` tool has filled this role for years and is very widely used. It works, but it has to work around the interpreter rather than with it:

- It copies or symlinks a selection of standard library modules into each environment, because `site.py` and the modules it imports must be found before `sys.prefix` is set correctly. The list of modules to copy changes between Python versions, and every new release risks breaking `virtualenv`.
- It ships its own modified `site.py`, which must be kept in sync with the real one.
- Tools that inspect `sys.prefix` to find the installation get the environment's directory, with no reliable way to find the base installation. Some parts of `distutils` and `sysconfig` give wrong answers inside an environment as a result.

All of these problems come from the same source: the interpreter has no idea that it is running in an environment. If the interpreter knew, at startup, that it should use one prefix for the standard library and another for site packages, most of the workarounds would disappear.

# Specification

## The `pyvenv.cfg` file

When the Python binary starts, before importing `site`, it looks for a file called `pyvenv.cfg`, first in the directory containing the executable and then in that directory's parent. If the file is found, the interpreter is running in a virtual environment.

The file is a simple `key = value` format. The keys defined by this PEP are:

- `home`: the directory containing the base Python executable. The interpreter uses it to find the standard library, in the same way it would if it had been started from that directory.
- `include-system-site-packages`: `true` or `false`. Defaults to `false`.
- `version`: the version of the base Python, for informational use by tools.

Unknown keys are ignored, so tools can store their own settings.

## Effect on `sys`

Inside a virtual environment:

- `sys.prefix` and `sys.exec_prefix` point to the environment directory.
- New attributes `sys.base_prefix` and `sys.base_exec_prefix` point to the base installation. Outside an environment they equal `sys.prefix` and `sys.exec_prefix`.

A program can tell whether it is in a virtual environment by checking `sys.prefix != sys.base_prefix`.

The standard library is located through `sys.base_prefix`. Site directories are located through `sys.prefix`.

## Effect on `site`

`site.py` computes site-packages directories from `sys.prefix`, so inside an environment it adds the environment's `site-packages`. If `include-system-site-packages` is `true`, it also adds the base installation's site-packages after the environment's, so packages installed in the environment take precedence.

User site-packages (`~/.local/lib/pythonX.Y/site-packages`) are not added inside an environment unless system site-packages are included. An isolated environment should not depend on what happens to be in the user's home directory.

## Effect on `sysconfig` and `distutils`

`sysconfig` install schemes use `sys.prefix` for the paths where packages are installed (`purelib`, `platlib`, `scripts`, `data`) and `sys.base_prefix` for the paths of the standard library and headers (`stdlib`, `platstdlib`, `include`). As a result, `python setup.py install` and any installer built on these schemes install into the environment with no configuration.

## Directory layout

On POSIX systems an environment looks like this:

```
env/
    pyvenv.cfg
    bin/
        python  -> /usr/bin/python3.3   (symlink or copy)
        activate
    include/
    lib/
        python3.3/
            site-packages/
```

On Windows, `bin` is named `Scripts` and `lib/python3.3/site-packages` is `Lib\site-packages`, matching the layout of a normal Windows installation.

Symlinks are used for the executable by default on platforms where they work reliably. On Windows, where symlinks need special privileges, the executable and its DLL are copied.

## The `venv` module

A new module, `venv`, creates environments:

```
python3 -m venv /path/to/env
```

Options:

- `--system-site-packages`: set `include-system-site-packages = true`.
- `--symlinks` / `--copies`: choose how the executable is placed.
- `--clear`: delete the contents of an existing environment first.
- `--upgrade`: update an existing environment to the running Python, for use after the base Python is upgraded in place.

The module exposes an `EnvBuilder` class with methods for each step (create directories, write config, set up the executable, install scripts). Third-party tools can subclass it, for example to install a package installer into every new environment, without reimplementing the basic steps.

## Activation scripts

`venv` installs shell scripts (`activate` for bash and compatible shells, `activate.csh`, `activate.fish`, `activate.bat` and `Activate.ps1` on Windows) that put the environment's `bin` directory at the front of `PATH` and set the `VIRTUAL_ENV` environment variable. Activation is a convenience only. Running `env/bin/python` directly gives the same result without activation, which is the recommended approach for scripts and services.

# Rationale

**Why a config file next to the binary, rather than an environment variable?** An environment variable has to be set by whoever runs the interpreter, and it leaks into child processes that may be running a different Python. A file next to the binary means the binary alone determines its environment. Running `/path/to/env/bin/python` always gives the environment, regardless of how it is invoked.

**Why share the standard library?** Copying it would make each environment large and slow to create, and it would freeze each environment at whatever patch release it was created with. Sharing means a security fix to the base installation applies to all environments. The cost is that upgrading the base Python's minor version breaks environments built on it, which is already true of `virtualenv` and is acceptable.

**Why isolate by default?** The main use of environments is reproducibility. An environment that silently sees system packages may work on one machine and fail on another.

# Backward compatibility

Interpreters started outside a virtual environment behave exactly as before. The only visible change is the new `sys.base_prefix` and `sys.base_exec_prefix` attributes.

Code that uses `sys.prefix` to locate the standard library will get the wrong answer inside an environment and should switch to `sys.base_prefix` or `sysconfig`. Such code already fails under `virtualenv`, so in practice this is rare.

`virtualenv` can continue to work as it does today. It can also adopt the built-in mechanism on Python versions that support it and drop most of its workarounds.

# Open questions

- Should `venv` install a package installer into new environments by default? This depends on whether one is bundled with Python, which is outside the scope of this PEP.
- Should there be a way to relocate an environment after creation? The absolute path in `home` and in installed scripts makes this hard; this PEP does not try to solve it.

# Reference implementation

A reference implementation is available as a branch of CPython, including tests and documentation.
