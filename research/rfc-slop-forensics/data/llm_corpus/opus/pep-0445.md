# Abstract

This PEP proposes new Application Programming Interfaces (APIs) for customizing Python's memory allocators. CPython is the only implementation required to conform to this PEP. Other implementations may choose to be compatible or to reuse a similar scheme.

# Rationale

CPython allocates memory through three families of functions:

- the **raw** functions, `PyMem_RawMalloc()` and friends, which are thin wrappers around the C library's `malloc()` and can be called without holding the GIL;
- the **memory** functions, `PyMem_Malloc()` and friends, intended for general-purpose buffers;
- the **object** functions, `PyObject_Malloc()` and friends, which use `pymalloc`, an allocator tuned for the many small, short-lived objects a Python program creates.

These functions are fixed at compile time. Changing them requires recompiling Python, which rules it out for most users and for any application that embeds a stock Python. There are several common reasons to want to change them.

**Embedding Python in an application with its own memory management.** Game engines, databases, and scientific applications often have custom allocators. They want Python's allocations to come out of their own pools, so that memory can be budgeted, tracked, and released as a unit.

**Memory profiling and debugging.** Tools that measure who allocated how much memory need to intercept every allocation. Today they rely on `LD_PRELOAD` tricks or a patched interpreter. A hook API would let such a tool be written as an ordinary extension module.

**Debugging allocator misuse.** CPython has debug hooks that detect buffer overflows and calls to the wrong deallocation function, but they are only available in debug builds. Being able to install them at runtime in a release build would make it far easier to find bugs in C extensions.

**Using a different underlying allocator.** Some users want to replace `malloc()` with jemalloc or tcmalloc for Python only, or want to disable `pymalloc` in favor of the system allocator to let tools like Valgrind see every allocation.

# Proposal

## New functions and structures

A new structure describes an allocator:

```c
typedef struct {
    /* user context passed as the first argument to the 4 functions */
    void *ctx;

    /* allocate a memory block */
    void* (*malloc) (void *ctx, size_t size);

    /* allocate a memory block initialized by zeros */
    void* (*calloc) (void *ctx, size_t nelem, size_t elsize);

    /* allocate or resize a memory block */
    void* (*realloc) (void *ctx, void *ptr, size_t new_size);

    /* release a memory block */
    void (*free) (void *ctx, void *ptr);
} PyMemAllocator;
```

The `ctx` field lets one set of functions serve several allocators, and lets a hook carry a pointer to the allocator it wraps.

A new enumeration identifies the three domains:

```c
typedef enum {
    PYMEM_DOMAIN_RAW,  /* PyMem_RawMalloc(), PyMem_RawRealloc(), ... */
    PYMEM_DOMAIN_MEM,  /* PyMem_Malloc(), PyMem_Realloc(), ... */
    PYMEM_DOMAIN_OBJ   /* PyObject_Malloc(), PyObject_Realloc(), ... */
} PyMemAllocatorDomain;
```

Two new functions get and set the allocator of a domain:

```c
void PyMem_GetAllocator(PyMemAllocatorDomain domain, PyMemAllocator *allocator);
void PyMem_SetAllocator(PyMemAllocatorDomain domain, PyMemAllocator *allocator);
```

`pymalloc` itself sits underneath `PyObject_Malloc()` and gets its memory from the operating system in large chunks called *arenas*. A separate structure and pair of functions control how arenas are obtained:

```c
typedef struct {
    void *ctx;
    void* (*alloc) (void *ctx, size_t size);
    void (*free) (void *ctx, void *ptr, size_t size);
} PyObjectArenaAllocator;

void PyObject_GetArenaAllocator(PyObjectArenaAllocator *allocator);
void PyObject_SetArenaAllocator(PyObjectArenaAllocator *allocator);
```

Finally, a function reinstalls the debug hooks on top of whatever allocators are currently in place:

```c
void PyMem_SetupDebugHooks(void);
```

## Requirements on allocators

A custom allocator must meet these requirements:

- `malloc(ctx, 0)` and `realloc(ctx, ptr, 0)` must return a unique, non-`NULL` pointer when possible, as the current functions do.
- Allocators in the `PYMEM_DOMAIN_RAW` domain must be thread-safe, because they can be called without the GIL.
- Allocators in the other two domains are always called with the GIL held.
- Memory obtained from one domain must be released through the same domain. Mixing domains is a bug, which the debug hooks catch.

## When to set an allocator

`PyMem_SetAllocator()` should be called before Python is initialized (before `Py_Initialize()`), or when no memory obtained from the domain is still live. Replacing the allocator after allocations have been made means existing blocks will be freed with the new allocator's `free`, which will usually crash.

The exception is *hooks*: an allocator that wraps the previous one, gets it with `PyMem_GetAllocator()`, and forwards every call to it. Hooks can be installed at any time, because they do not change which allocator owns each block.

## Example: a hook that counts allocations

```c
typedef struct {
    PyMemAllocator orig;
    size_t count;
} hook_t;

static hook_t hook;

static void* hook_malloc(void *ctx, size_t size)
{
    hook_t *h = ctx;
    h->count++;
    return h->orig.malloc(h->orig.ctx, size);
}

/* hook_calloc, hook_realloc and hook_free are similar */

static void setup_hook(void)
{
    PyMemAllocator alloc;
    PyMem_GetAllocator(PYMEM_DOMAIN_OBJ, &hook.orig);
    alloc.ctx = &hook;
    alloc.malloc = hook_malloc;
    alloc.calloc = hook_calloc;
    alloc.realloc = hook_realloc;
    alloc.free = hook_free;
    PyMem_SetAllocator(PYMEM_DOMAIN_OBJ, &alloc);
}
```

## Changes to existing behavior

- `PyMem_Malloc()` and `PyMem_Realloc()` will go through the `PYMEM_DOMAIN_MEM` allocator instead of calling `malloc()` directly. By default that allocator is the same as the raw one, so nothing observable changes.
- In debug builds, debug hooks are installed by default on all three domains, as today. In release builds, `PyMem_SetupDebugHooks()` can be called explicitly, and the `PYTHONMALLOC` environment variable can be used to select the debug hooks or plain `malloc`.

# Performance

The extra indirect function call adds a small cost to each allocation. Benchmarks on the prototype show a slowdown under 1% on the standard benchmark suite, which is within the noise for most workloads. `pymalloc`'s fast path for small objects is unaffected apart from the indirection.

# Backwards Compatibility

The new APIs are additions. Existing extension modules and embedding applications behave the same unless they call the new functions.

Code that relied on `PyMem_Malloc()` being exactly `malloc()`, for example by freeing its result with `free()`, was already wrong and is now more likely to fail when a custom allocator is installed. The debug hooks will report such mistakes.

# Alternatives

**Compile-time macros only.** Letting users redefine `PyMem_Malloc` and the others through macros would require recompiling Python and every extension, which defeats most of the use cases.

**Hooks without replacement.** Supporting only "observe" hooks, not full replacement, would cover profiling but not embedding.

**A single allocator for all domains.** Simpler, but it would force raw allocations to go through allocators that need the GIL and would prevent replacing `pymalloc` on its own.

**Using `LD_PRELOAD` or similar.** This works only on some platforms and only for the C library's `malloc`, not for `pymalloc`.

# Open Issues

- Should the `calloc` field be included now, given that Python does not yet use `calloc()` internally?
- Should there be a Python-level API for querying which allocator is installed?
