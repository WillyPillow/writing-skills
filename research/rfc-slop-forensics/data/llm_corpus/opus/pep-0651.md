# Abstract

This PEP proposes that Python treat overflow of the machine (C) stack separately from runaway recursion. Programs could then set the maximum recursion depth to whatever they need and still be protected from crashes.

If this PEP is accepted, the following program will run to completion safely:

```python
sys.setrecursionlimit(1_000_000)

def f(n):
    if n:
        f(n-1)

f(500_000)
```

and the following program will raise `StackOverflow` and not crash the VM:

```python
sys.setrecursionlimit(1_000_000)

class X:
    def __add__(self, other):
        return self + other

X() + 1
```

# Motivation

CPython uses one counter, the recursion depth, for two jobs:

1. **Catching runaway recursion in Python code.** A function that calls itself without end is almost always a bug. Raising `RecursionError` after some number of calls gives a clear, recoverable error.
2. **Protecting the C stack.** Each Python-level call has traditionally taken a C stack frame in the interpreter loop. Some C-level operations also recurse on the C stack: calling `__add__` from C, `repr` of nested containers, pickling, comparing deeply nested structures. If the C stack overflows the process segfaults, and nothing can recover.

The recursion limit defaults to 1000, a value chosen to keep the C stack safe on common platforms. It is a poor fit for both jobs.

**It is too low for Python code.** Many legitimate algorithms recurse deeply: tree traversal, recursive-descent parsers, divide-and-conquer. Programmers raise the limit with `sys.setrecursionlimit`, and the documentation warns that doing so may crash the interpreter.

**It doesn't protect the C stack.** The amount of C stack a Python call uses depends on the call path. A call through a C extension, a slot wrapper, or a nested `__getattr__` may use far more stack than a plain Python-to-Python call. Some C code doesn't increment the counter at all. With a high limit, or with a deep enough chain of C-level recursion, CPython crashes.

The two needs are different and should be handled separately.

# Rationale

As CPython 3.11 and later evolve, Python-to-Python calls are being changed so they no longer use C stack: the interpreter pushes a new frame and keeps going in the same C loop. Once that happens, Python recursion depth and C stack use are largely unrelated. Pure Python recursion is limited only by heap memory, and the recursion limit becomes a policy choice. C recursion still needs a hard safety limit.

Separating the two checks lets each be set correctly:

- The **recursion limit** stays a user-configurable bound on Python call depth, mostly as a bug-catching aid, and it can safely be set high.
- A new **C stack limit** protects the process. It is checked on entry to recursive C functions and can't be raised past what the platform can actually support.

# Specification

## `StackOverflow` exception

A new exception, `StackOverflow`, is added. It is a subclass of `RecursionError`, so existing code that catches `RecursionError` keeps working:

```
BaseException
 └── Exception
      └── RuntimeError
           └── RecursionError
                └── StackOverflow
```

`StackOverflow` is raised when the interpreter detects that continuing would overflow the C stack. `RecursionError` (but not `StackOverflow`) is raised when the Python recursion limit is exceeded.

## Recursion limit

`sys.setrecursionlimit()` and `sys.getrecursionlimit()` keep their current names and signatures. The limit now counts only Python-level frames. Setting it to a large value is safe: exceeding the C stack will raise `StackOverflow`, never crash.

The default stays at 1000 for compatibility. A future release may raise it.

## C stack checks

The interpreter tracks C stack usage directly and doesn't rely on a call count. At startup it records the address of a local variable in the main thread, and on new threads at thread start. It works out a safe limit from the thread's stack size, using platform APIs where they exist (`pthread_getattr_np` on Linux, `pthread_get_stacksize_np` on macOS, `GetCurrentThreadStackLimits` on Windows) and otherwise a conservative default. It keeps a safety margin for the code that raises the exception.

`Py_EnterRecursiveCall()` keeps its name but changes meaning. Instead of incrementing a counter, it compares the current stack pointer against the limit and raises `StackOverflow` if the remaining stack is below the margin.

A new C API function is added:

```c
int Py_CheckStackDepth(const char *where);
```

It does the check without changing any counter. Extension modules that recurse in C, such as serializers and tree walkers, should call it.

## Handling after overflow

When `StackOverflow` is raised, the interpreter temporarily allows a small amount of extra stack so that exception handlers and `finally` blocks can run. If the extra allowance is also used up, a fatal error is reported with a clear message rather than a segfault. This behavior mirrors how `RecursionError` handling works today.

## Interaction with `sys.setrecursionlimit` warnings

The documentation will be updated to remove the warning that a high recursion limit may crash the interpreter, since that will no longer be true.

# Backwards Compatibility

- Code that catches `RecursionError` also catches `StackOverflow`.
- Code that relied on a low recursion limit to stop deep C-level recursion is now protected by the stack check, which is more reliable.
- Some programs that hit the C stack limit indirectly may now see `StackOverflow` at a different depth than they used to see `RecursionError`. The depth at which the error is raised was never specified, so this isn't considered a compatibility break.
- Extension modules that call `Py_EnterRecursiveCall` keep working, and are better protected.

# Security Implications

Today, untrusted input that causes deep recursion in a C extension (deeply nested JSON, pickles, or regular expressions, for example) can crash the interpreter, a denial-of-service vector. Reliable stack checks turn those crashes into catchable exceptions.

# Performance Impact

Comparing the stack pointer against a limit costs about the same as incrementing and comparing a counter. No measurable slowdown is expected. Removing the counter from Python-to-Python calls, which no longer need it for safety once they don't use C stack, may be a small speedup.

# Implementation

A prototype implementation exists and passes the test suite on Linux, macOS, and Windows. The most delicate part is getting a reliable stack size for threads created by foreign code. In that case the implementation assumes a conservative default and lets embedders override it.

# Rejected Ideas

## Just raise the default recursion limit

That makes crashes more likely, not less, as long as C stack use isn't checked.

## Grow the C stack on demand

Segmented or growable stacks aren't portable, and they interact badly with C extensions and signal handlers.

## Catch `SIGSEGV`

Recovering from a segfault caused by stack overflow is unreliable and platform-specific, and state may already be corrupted.

# Open Issues

- Should `StackOverflow` be a builtin name or only reachable as an attribute of some module?
- What should the default safety margin be, and should it be adjustable?
