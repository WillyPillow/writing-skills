# Abstract

This PEP proposes several new features for comparisons:

- Allow separately overloading `<`, `>`, `<=`, `>=`, `==`, and `!=`, both in classes and in C extensions.
- Allow any of those overloaded operators to return something other than a Boolean result.

# Motivation

The current comparison mechanism in Python is built around a single method, `__cmp__`, and its C-level counterpart, the `tp_compare` slot. When the interpreter evaluates `a < b`, it calls `cmp(a, b)`, which must return a negative integer, zero, or a positive integer, and then compares the result against zero. All six comparison operators are derived from this one three-way result.

This design works well for numbers and strings, where a total order exists, but it is too restrictive for several important cases.

**Numeric arrays.** Users of Numerical Python want `A < B`, where `A` and `B` are arrays, to produce an array of Booleans, one per element. This is the natural, expected behaviour in array languages such as APL, Matlab and IDL. Under `__cmp__`, `A < B` can only produce a single truth value, which is useless for arrays. Today, NumPy users must write `less(A, B)` instead, which reads poorly and is inconsistent with the arithmetic operators, which already work elementwise.

**Partial orders.** Some types have meaningful `<` and `>` relations that are not total. Sets ordered by inclusion are the classic example: `{1}` is neither less than, greater than, nor equal to `{2}`. A three-way `__cmp__` cannot express "none of the above". Complex numbers are another case: equality is meaningful but ordering is not, and there is no way to support `==` while rejecting `<`.

**Equality distinct from ordering.** For many types, testing equality is much cheaper than determining order, or ordering is undefined but equality is not. Requiring every equality test to go through a full three-way comparison wastes work and forces authors to invent an arbitrary order.

**Symbolic and deferred computation.** Libraries that build expression trees — for query languages, constraint solvers, or symbolic algebra — want `x < 5` to produce an expression object rather than evaluate immediately. This is impossible if the comparison must return an integer.

# Proposal

## New special methods

Six new special methods are introduced, one per operator:

| Operator | Method   | Reflected |
|----------|----------|-----------|
| `<`      | `__lt__` | `__gt__`  |
| `<=`     | `__le__` | `__ge__`  |
| `==`     | `__eq__` | `__eq__`  |
| `!=`     | `__ne__` | `__ne__`  |
| `>`      | `__gt__` | `__lt__`  |
| `>=`     | `__ge__` | `__le__`  |

Each takes two arguments, `self` and `other`, and may return any object. The result is not required to be a Boolean, and the interpreter does not coerce it. When the result is used in a Boolean context — an `if` statement, `while` condition, or the operand of `not`, `and`, or `or` — its truth value is determined in the usual way.

## Dispatch

When evaluating `a < b`:

1. If `a` has `__lt__`, call `a.__lt__(b)`. If the result is not `NotImplemented`, use it.
2. Otherwise, if `b` has `__gt__`, call `b.__gt__(a)`. If the result is not `NotImplemented`, use it.
3. Otherwise, fall back to `__cmp__` as today.

The reflected operation for `<` is `>`, not `>=`: if `a < b` cannot be determined by `a`, the question `b > a` is equivalent. There is no assumption that `<` is the negation of `>=`, or that `==` is the negation of `!=`. Those relationships hold for total orders but not in general, and the purpose of this PEP is to stop assuming them.

The singleton `NotImplemented` is introduced (or reused, if already present for numeric coercion) to mean "this type does not know how to perform this comparison with that operand". It allows the other operand's method a chance to handle the operation.

## C API

A new type slot, `tp_richcompare`, is added:

```c
PyObject *(*richcmpfunc)(PyObject *a, PyObject *b, int op);
```

where `op` is one of the new constants `Py_LT`, `Py_LE`, `Py_EQ`, `Py_NE`, `Py_GT`, `Py_GE`. The function returns a new reference to the result, `Py_NotImplemented` to indicate the comparison is not supported, or `NULL` with an exception set on error.

A single slot with an operation code, rather than six separate slots, keeps the type object small and allows extension types to share implementation logic across operators.

New API functions are provided:

```c
PyObject *PyObject_RichCompare(PyObject *a, PyObject *b, int op);
int PyObject_RichCompareBool(PyObject *a, PyObject *b, int op);
```

The first returns the result object; the second converts it to a C integer (1, 0, or -1 on error).

A type flag, `Py_TPFLAGS_HAVE_RICHCOMPARE`, indicates that the slot is present, preserving binary compatibility with extensions compiled against older headers.

## Chained comparisons

Python allows chained comparisons: `a < b < c` means `a < b and b < c`, with `b` evaluated once. This continues to hold. Because `and` uses truth values, if `a < b` returns an array, the chain will attempt to take its truth value. For NumPy arrays, that is ambiguous and may raise an exception; this is considered the array library's decision, not the interpreter's.

## Built-in functions

`cmp(a, b)` continues to return an integer. If neither object defines `__cmp__` but both support rich comparisons, `cmp` will try `==`, then `<`, then `>` and derive a three-way result from those that succeed with Boolean results.

Built-in operations that need a Boolean — such as `list.sort()`, `in` for lists, and dictionary key lookup — call the relevant rich comparison and take the truth value of the result.

# Rationale

## Why not keep a single `__cmp__` and add flags?

Extending `__cmp__` to return special values such as "unordered" would handle partial orders but not elementwise arrays or symbolic expressions, both of which need to return arbitrary objects.

## Why six methods instead of two?

One could define only `__lt__` and `__eq__` and derive the rest. That would again assume a total order. Some types, such as floating-point numbers with NaN, violate the usual identities: `x < y` and `x >= y` can both be false. Giving each operator its own method lets types implement the semantics they actually have.

## Why allow non-Boolean results?

The NumPy use case is the primary driver and was the motivation for this proposal. Restricting results to Booleans would solve only half the problem.

# Backwards Compatibility

Classes that define only `__cmp__` behave exactly as before, since the interpreter falls back to it when no rich comparison method is present. Extension types without the new flag are unaffected.

Code that assumes `a < b` returns 0 or 1 may break when given objects that return other values. Since such objects do not exist today, existing code is unaffected until it is used with new types.

# Open Issues

- Whether `__cmp__` should eventually be deprecated in favour of rich comparisons.
- Whether `list.sort()` should be specified to use only `<`, which would simplify implementing sortable types.
