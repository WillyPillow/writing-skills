# Abstract

Add a new warning category `EncodingWarning`. It is emitted when the `encoding` argument to `open()` is omitted and the default locale-specific encoding is used.

The warning is disabled by default. A new `-X warn_default_encoding` command-line option and a new `PYTHONWARNDEFAULTENCODING` environment variable can be used to enable it.

A `"locale"` argument value for `encoding` is added too. It explicitly specifies that the locale encoding should be used, silencing the warning.

# Motivation

## Using the default encoding is a common mistake

When a text file is opened without an explicit `encoding`, Python uses the encoding returned by `locale.getpreferredencoding(False)`. On most Linux and macOS systems, this is UTF-8. On Windows, it is the ANSI code page, such as cp1252 in Western Europe or cp932 in Japan.

Developers who work on Linux or macOS frequently write code like this:

```python
with open("config.json") as f:
    config = json.load(f)
```

It works on their machine and in their CI. It works on most of their users' machines. Then a Windows user tries to read a file containing a non-ASCII character, and the program fails with a `UnicodeDecodeError`, or, worse, silently reads mojibake.

This is not a rare edge case. JSON, TOML, YAML, Markdown and most configuration and source files used in modern software are UTF-8 by convention or by specification. Reading them with a locale encoding is almost always wrong. Yet `open()` without `encoding` is the shortest, most obvious way to open a file, and it is what tutorials show.

Searching popular open source projects turns up a large number of `open()` calls in text mode with no encoding argument. Many of these are bugs that only manifest on Windows. Bug trackers for well-known packages contain reports of installation failures on Windows caused by `setup.py` reading a `README` that contains a non-ASCII character.

## Changing the default is hard

The long-term fix may be to make UTF-8 the default encoding for text files on all platforms. However, changing the default would break code that relies on the locale encoding today, for example code that reads files written by other Windows applications in the ANSI code page. Such a change requires a long deprecation period, and a deprecation period requires a way to find affected code.

That is what this PEP provides. It does not change any defaults. It gives developers a tool to find places where they are relying on the default encoding, so that they can decide, call by call, whether they meant UTF-8 or the locale encoding, and say so explicitly.

## Explicitly using the locale encoding is awkward

Today, a developer who genuinely wants the locale encoding has to write:

```python
open(path, encoding=locale.getpreferredencoding(False))
```

This is verbose, requires an import, and is easy to get wrong: `locale.getpreferredencoding()` with no argument may call `setlocale()`, which is not thread-safe. Moreover it is subtly different from the default behaviour in UTF-8 mode (PEP 540), where the default encoding is UTF-8 regardless of locale.

Developers need a short, correct way to say "use the same encoding that the default would use, and I mean it."

# Specification

## `EncodingWarning`

A new warning category, `EncodingWarning`, is added as a builtin. It is a subclass of `Warning`.

## Enabling the warning

The warning is emitted only when one of the following is set:

- The `-X warn_default_encoding` command-line option.
- The `PYTHONWARNDEFAULTENCODING` environment variable, set to a non-empty string.

The setting is exposed as `sys.flags.warn_default_encoding`.

When neither is set, no `EncodingWarning` is emitted, and there is no performance cost beyond a flag check. The warning is opt-in because emitting it by default would produce a large volume of warnings from third-party code that the user cannot fix, and would be noisy in applications that legitimately depend on the locale encoding.

## When the warning is emitted

When the option is enabled, `EncodingWarning` is emitted when `encoding=None` is passed, explicitly or by default, to:

- `open()` and `io.open()` in text mode
- `io.TextIOWrapper`
- `pathlib.Path.open()`, `read_text()` and `write_text()`
- Other standard library functions that open text files with a default encoding, such as `subprocess.Popen` with `text=True`, `fileinput.input`, and `configparser.ConfigParser.read`.

The warning's `stacklevel` is set so that it points at the caller of the function that defaulted the encoding. For example, a warning from `pathlib.Path.read_text()` points at the line that called `read_text()`, not at the `open()` call inside `pathlib`.

## `encoding="locale"`

`io.TextIOWrapper` accepts `"locale"` as a value for `encoding`. It means "use the locale encoding", and is resolved as follows:

- In UTF-8 mode, it means UTF-8, as `encoding=None` does today.
- Otherwise, it means `locale.getpreferredencoding(False)`.

Because `open()` passes `encoding` through to `TextIOWrapper`, `open(path, encoding="locale")` works as well, and so do the other functions listed above. Passing `"locale"` does not emit `EncodingWarning`.

`"locale"` is not a codec name. `codecs.lookup("locale")` will fail. It is special-cased only where text streams are constructed.

## `io.text_encoding()`

Library functions that accept an `encoding` argument and pass it through to `open()` would, without help, emit the warning inside the library, where the user cannot see which call site is responsible. To support such functions, a helper is added:

```python
io.text_encoding(encoding, stacklevel=2)
```

If `encoding` is not `None`, it is returned unchanged. If it is `None`, the function returns `"locale"` (or `"utf-8"` in UTF-8 mode), and, if the warning is enabled, emits `EncodingWarning` at the given stack level.

A library function written as:

```python
def read_config(path, encoding=None):
    encoding = io.text_encoding(encoding)
    with open(path, encoding=encoding) as f:
        ...
```

will report the warning at the caller of `read_config`, and its internal `open()` call will not warn because `encoding` is no longer `None`.

# Rationale

Making the warning opt-in lets the developers who care about portability find bugs without imposing any cost on anyone else. Developers can enable it in CI or during testing. Library maintainers can enable it to make sure their own code is clean, and the `stacklevel` handling ensures they see warnings for their own calls rather than for the standard library's.

Adding `"locale"` allows every `open()` call to be explicit about its intent, so that when the warning is enabled, a clean run means every text file in the program has a deliberate encoding.

# Backwards Compatibility

No default behaviour changes. `EncodingWarning` is a new builtin name, which could shadow nothing in the builtins namespace but might coincide with a global name in user code. User-defined globals take precedence over builtins, so such code is unaffected.

Code that passes `encoding="locale"` will not run on older Python versions. Code that needs to support those can use `locale.getpreferredencoding(False)`.

# How to Teach This

For new code: always pass `encoding` when opening text files. Use `encoding="utf-8"` for files whose format is UTF-8, which is most of them. Use `encoding="locale"` only when you specifically want the platform's legacy encoding, for example when reading files produced by other local programs.

To find places that need fixing, run your tests with `python -X warn_default_encoding -W error::EncodingWarning`.

# Rejected Ideas

**Emitting the warning by default.** Too noisy, and unfixable by users for third-party code.

**Using `DeprecationWarning` or `ResourceWarning`.** Neither describes the problem, and filtering would interfere with unrelated warnings.

**Changing the default to UTF-8 now.** Out of scope; this PEP is a prerequisite for considering it.
