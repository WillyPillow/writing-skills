PEP: 499
Title: `python -m foo` should also bind `'foo'` in `sys.modules`
Status: Draft
Type: Standards Track
Created: 2015
Python-Version: 3.6

# Abstract

When a module is used as a main program on the Python command line, for example by:

```
python -m module.name ...
```

it is easy to accidentally end up with two independent instances of the module if the module is imported again within the program. This PEP proposes a way to fix this.

When a module is run with the `-m` option, it is bound to `sys.modules['__main__']` and its `__name__` attribute is set to `'__main__'`. This enables the standard "main program" boilerplate at the bottom of many modules:

```python
if __name__ == '__main__':
    sys.exit(main(sys.argv))
```

However, with the command above it is natural to assume that the module has been imported under its official name, `module.name`, and therefore that if the program imports that name again it will get the same module object. It does not. This PEP proposes that `sys.modules['module.name']` also refer to the main module.

# Motivation

Consider a module `tool/cli.py` that defines some state and a main function:

```python
# tool/cli.py
_registry = {}

def register(name):
    def deco(func):
        _registry[name] = func
        return func
    return deco

def main(argv):
    import tool.plugins   # registers handlers via tool.cli.register
    ...
    print(sorted(_registry))

if __name__ == '__main__':
    main(sys.argv)
```

Running `python -m tool.cli` executes `cli.py` as `__main__`. When `tool.plugins` executes `from tool.cli import register`, the import system finds no `tool.cli` in `sys.modules`, so it executes `cli.py` a second time and creates a separate module object. The plugins register their handlers in the second module's `_registry`, while `main()` in the first module reads its own empty `_registry`. The program prints an empty list.

This class of bug is confusing because nothing looks wrong. Both copies have the same source and the same function names; the problem only shows up as missing state, duplicated side effects, or `isinstance()` checks failing because a class has been defined twice. Experienced developers have learned to avoid putting state in modules that are run as scripts, but newcomers keep rediscovering the problem.

The `-m` switch makes the issue more common, because it is the documented and recommended way to run a module inside a package. Users reasonably think of `python -m tool.cli` as "import `tool.cli` and run it".

# Proposal

When the interpreter runs a module with `-m`, the module object it creates is placed into `sys.modules` under both `'__main__'` and the module's real name. In the example above, after startup:

```python
sys.modules['__main__'] is sys.modules['tool.cli']
```

The module's `__name__` remains `'__main__'`, so the `if __name__ == '__main__'` idiom continues to work. Its `__spec__.name` already records the real name, `'tool.cli'`, as specified by PEP 451, and is unchanged.

Any later `import tool.cli` finds the existing entry in `sys.modules` and returns the main module, rather than executing the file a second time.

## Implementation

The change is localised to `runpy._run_module_as_main()`, which is the function the interpreter uses to implement `-m`. After creating the `__main__` module and before executing its code, it adds:

```python
sys.modules[mod_spec.name] = main_module
```

For a package run with `-m`, the module executed is the package's `__main__` submodule, so the alias is `'package.__main__'`, not `'package'`. The package itself is imported normally as part of locating `__main__`, and is already in `sys.modules` under its own name.

When the main module finishes running, the interpreter does not remove either entry; this matches existing behaviour for `'__main__'`.

## Running scripts by path

This PEP does not change the behaviour of `python path/to/script.py`. A script run by path has no canonical module name, and inferring one from `sys.path` would be guesswork. Running a module by path that is also importable under a package name remains a way to get two copies, and the documentation should continue to recommend `-m` for modules in packages.

# Rationale

## Why not set `__name__` to the real name?

That would break the overwhelmingly common `__main__` check, which is the reason `-m` sets `__name__` the way it does. Keeping `__name__` as `'__main__'` and adding an alias under the real name gives both behaviours.

## Why not warn instead of aliasing?

A warning when a module running as `__main__` is imported again would at least make the problem visible. But in almost every case the user's intent is clearly to share one module, and the fix is mechanical. Doing the right thing is better than telling the user they did the wrong thing.

## Pickling

Objects defined in the main module currently pickle with a module reference of `'__main__'`. That is unchanged, because the pickling machinery uses `__module__`, which is derived from `__name__`. Separately, PEP 451's `__spec__.name` gives tools the information they need to pickle under the real name if they choose.

# Backwards Compatibility

Programs that depend on getting a second, independent copy of the main module when importing it by name will change behaviour. This is believed to be rare. The most plausible case is a module that deliberately does different things when imported than when run, and whose run-mode code imports itself expecting the import-mode behaviour. Such a module now receives the already-running `__main__` module, whose top-level code may not have finished executing. This is the same situation as any circular import, and the same workarounds apply: move the shared code into a separate module.

A related subtlety is that the import of `tool.cli` during execution of `tool/cli.py` will return a partially initialised module, since the main module's top level is still running. Again, this is ordinary circular import behaviour, and is arguably better than the current situation of silently running the whole module twice.

Tools that inspect `sys.modules` and assume every entry has a `__name__` equal to its key will see one exception. This assumption is already invalid for other cases, such as modules aliased by `sys.modules` manipulation in third-party code.

# Reference Implementation

A patch to `runpy` implementing the change, with tests for modules, packages, and the circular import case, is available on the issue tracker.

# Open Questions

- Should the alias also be added when the main module is run with `runpy.run_module()` and `alter_sys=True`? For consistency it probably should.
- Should there be an opt-out for the unusual programs that rely on the current behaviour?
