# PEP 316: Programming by Contract for Python

## Abstract

This submission describes programming by contract for Python. Eiffel's Design By Contract(tm) is perhaps the most popular use of programming contracts. Programming contracts extend the language to include invariant expressions for classes and modules, and pre- and post-condition expressions for functions and methods.

These expressions (contracts) are similar to assertions: they must be true or the program is stopped, and run-time checking of contracts is typically enabled only while debugging. Contracts are higher-level than plain assertions and are typically included in documentation.

## Motivation

Python already has `assert`. Why add anything?

Assertions are statements in the body of a function. They are written where it is convenient for the implementer, mixed in with the code, and are invisible to someone reading the function's documentation. They say nothing about who is responsible when they fail.

Contracts make that responsibility explicit:

- A **precondition** states what must be true when a function is called. If it fails, the caller has a bug.
- A **postcondition** states what the function guarantees when it returns. If it fails, the function has a bug.
- An **invariant** states what is always true of an object (or module) between calls to its public methods. If it fails, the class has a bug.

This distinction pays off in several ways:

1. **Documentation.** The contract is part of the interface. Users of a function can read exactly what is required and what is promised, in a precise form, without reading the implementation.
2. **Debugging.** When a contract fails, the error message tells you which side of the interface is at fault. That narrows the search immediately.
3. **Subclassing.** Contracts give a precise meaning to "a subclass may be used wherever its base class is expected". Subclasses may weaken preconditions and strengthen postconditions, but not the reverse, and this can be checked automatically.
4. **Testing.** Postconditions and invariants act as oracles. Random or exhaustive tests can call functions with any arguments that satisfy preconditions, and every call checks itself.

Python's dynamic typing makes the case stronger. Without static types, the most basic facts about a function's arguments are often only stated in prose. Contracts give a checkable place to state them.

## Specification

### Where contracts live

Contracts are written in docstrings. This keeps them next to the prose documentation, does not require any new syntax, and allows them to be ignored entirely when contract checking is not enabled. A tool or an import hook parses the docstrings and wraps functions and classes with checking code.

Within a docstring, contracts are introduced by keywords at the start of a line, followed by a colon, followed by an indented block of Python expressions, one per line:

```python
def sqrt(x):
    """Return the square root of x.

    pre: x >= 0
    post[]:
        __return__ >= 0
        abs(__return__ * __return__ - x) < 1e-9 * max(x, 1)
    """
```

The recognized keywords are:

- `pre:` for preconditions
- `post:` for postconditions
- `inv:` for invariants (in class and module docstrings)

Each expression must evaluate to a true value. All expressions in a block are checked, in order.

### Preconditions

Preconditions are evaluated after the arguments are bound and before the function body runs. They may refer to the function's parameters and to any name visible in the function's global scope.

### Postconditions

Postconditions are evaluated after the function returns, normally. If the function raises an exception, postconditions are not checked.

Two special names are available:

- `__return__` refers to the return value.
- `__old__` refers to an object holding copies of values as they were on entry. `__old__.x` is the value of `x` on entry.

Because copying is expensive, values are only saved if they are named in the postcondition's bracket list. `post[]:` means no values need to be saved; `post[self, items]:` means `self` and `items` are copied (with `copy.deepcopy`) on entry:

```python
def append(self, item):
    """Append item to the end of the list.

    post[self]:
        len(self) == len(__old__.self) + 1
        self[-1] is item
    """
```

The bracket list also documents which of the function's arguments it may modify. A postcondition with `post[]` on a method that mutates `self` is a warning sign.

### Invariants

Invariants appear in class docstrings and in module docstrings.

Class invariants are checked after `__init__` returns and before and after every call to a public method (one whose name does not begin with an underscore). They are not checked around calls to private methods, since those are allowed to leave the object temporarily inconsistent.

```python
class Range:
    """A half-open integer interval.

    inv:
        self.start <= self.stop
    """
```

Module invariants are checked after the module is imported and around every call to a public module-level function.

### Inheritance

When a method overrides a base-class method:

- its effective precondition is the logical **or** of its own precondition and those of the methods it overrides;
- its effective postcondition is the logical **and** of its own and the overridden methods' postconditions.

A class's effective invariant is the **and** of its own invariant and those of all its bases.

These rules mean a subclass cannot demand more from callers than its base class does, nor promise less. The checking machinery enforces this automatically, so a subclass that tries to strengthen a precondition simply finds that the base class's weaker precondition is still accepted.

### Exceptions

A failed precondition raises `PreconditionViolationError`. A failed postcondition raises `PostconditionViolationError`. A failed invariant raises `InvariantViolationError`. All three are subclasses of a new `ContractViolationError`, which is a subclass of `AssertionError`, so existing code that catches assertion failures behaves sensibly.

The error message includes the failing expression's text, the function, and the values of its parameters where they can be represented.

### Enabling checking

Contract checking is off by default. It can be enabled:

- for the whole program with a command line switch, or
- for selected modules through a `contracts` module providing `checkmod(module)` and an import hook.

When checking is off, contracts have no run-time cost at all: they are just text in docstrings.

## Reference Implementation

A pure-Python reference implementation provides a `contracts` module that parses docstrings, compiles each expression once, and wraps functions and methods in checking wrappers. It handles inheritance by walking the MRO at class creation time. It runs on unmodified Python and needs no interpreter changes.

## Examples

A sorted insertion function:

```python
def insort(a, x):
    """Insert x into sorted list a, keeping it sorted.

    pre:
        all(a[i] <= a[i+1] for i in range(len(a) - 1))
    post[a]:
        len(a) == len(__old__.a) + 1
        x in a
        all(a[i] <= a[i+1] for i in range(len(a) - 1))
    """
```

Note that the contract alone describes nearly everything a caller needs to know.

## Rejected Alternatives

**New syntax.** Adding `pre`, `post` and `inv` as keywords would make contracts first-class but would break existing code using these names, and would force contract overhead on every run unless the compiler learned to drop them. Docstrings avoid both problems.

**Decorators.** Decorator-based contracts are possible, but they place the contract outside the docstring, where documentation tools do not see it, and they make the inheritance rules harder to apply uniformly.

**Plain `assert`.** As described in the motivation, assertions do not carry the information about responsibility or inheritance that makes contracts useful.

## Open Issues

- Should contract checking be available in the standard library, or remain a third-party module with this PEP as its specification?
- How should contracts interact with generators, where the "return" happens incrementally?
- Is `copy.deepcopy` the right default for `__old__`, or should users be able to choose shallow copies?
