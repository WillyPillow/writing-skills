PEP: 504
Title: Using the System RNG by default
Status: Draft
Type: Standards Track
Created: 2015
Python-Version: 3.6

# Abstract

Python currently defaults to the deterministic Mersenne Twister random number generator for the module level APIs in the `random` module. Users are expected to know that, for "security sensitive" work, they should instead use the cryptographically secure `os.urandom` or `random.SystemRandom` interfaces, or a third-party library such as `cryptography`.

In practice this has led to a situation where developers who don't realise they are doing security sensitive work use the default module level APIs and expose their users to unnecessary risk. This is not an acute problem, but it is a chronic one, and the long delay between introducing a flaw and seeing it exploited means developers rarely learn from experience.

To provide an eventually pervasive solution, this PEP proposes that the module level functions in `random` switch to using the system random number generator by default, while preserving deterministic behaviour for any program that explicitly asks for it by seeding the generator or saving and restoring its state.

# Motivation

The `random` module is the first place most Python developers look when they need random values. Its documentation includes a warning that it is unsuitable for security purposes, but warnings in documentation are easy to miss and are often not consulted at all. Searching public code turns up many uses of `random.choice`, `random.randint` and `random.random` to generate:

- password reset tokens,
- session identifiers,
- API keys and temporary passwords,
- nonces and salts.

The Mersenne Twister's output is predictable once an attacker has observed enough of it. For a web application that generates tokens on request, that is often entirely practical. The resulting vulnerabilities are rarely discovered by the developers who introduced them.

Education alone has not fixed this. The `secrets` module, being proposed in parallel, will help developers who know to look for it, but it does nothing for the code written by people who don't. Changing the default reaches everyone.

At the same time, there are entirely legitimate uses of deterministic random numbers: simulations, games, procedural content generation, test data, and reproducible scientific experiments. These uses must continue to work, and their performance must not be harmed.

# Proposal

## Default behaviour

The module level functions of `random` (`random()`, `randint()`, `choice()`, `shuffle()`, `sample()` and so on) are currently bound methods of a hidden `random.Random` instance. This PEP proposes replacing that hidden instance with a new object that starts out delegating to `random.SystemRandom`, which draws from `os.urandom()`.

## Switching to deterministic mode

The hidden instance switches permanently to a seeded Mersenne Twister the first time any of the following module level functions is called:

- `random.seed()`
- `random.getstate()`
- `random.setstate()`

These are exactly the operations that only make sense for a deterministic generator. A program that calls `random.seed(42)` is plainly asking for reproducible results, and it gets them, exactly as today. Code that never calls these functions gets the secure generator.

## Warning on implicit switch

To help library authors find code that relies on the old behaviour in a shared, process-wide way, a `RandomWarning` is emitted when the switch to deterministic mode happens after the system RNG has already been used to produce values. In that situation earlier and later values come from different generators, which is probably not what the program intended. Applications that want deterministic behaviour from the very start can avoid the warning by calling `random.seed()` before using any other function.

## Explicit APIs

Two new module level names make the choice explicit:

- `random.ensure_repeatable()`: switches to deterministic mode if not already in it, without reseeding. Intended for applications that want to opt in to the old behaviour unconditionally.
- `random.system_random`: a module level `SystemRandom` instance for code that wants a guaranteed secure source regardless of mode.

Instances of `random.Random` that programs create explicitly are entirely unaffected. Only the module level convenience API changes.

# Rationale

## Why not deprecate the module level API?

The module level functions are used in enormous amounts of code, much of it in teaching material and scripts where security is irrelevant. Deprecating them would cause churn out of proportion to the benefit. Changing what they do underneath, in a way that most callers cannot observe, achieves the security goal with far less disruption.

## Why use `seed()` as the signal?

A deterministic generator is only useful if its output is reproducible, and reproducibility requires either a known seed or saved state. Programs that rely on determinism must therefore already call `seed()` or `setstate()`, or they get a time-based seed and are not reproducible anyway. Using these calls as the trigger means the change is invisible to every program that actually depends on deterministic behaviour.

## Performance

`SystemRandom` is slower than the Mersenne Twister, because each call may involve a system call. Benchmarks suggest the difference is a small constant factor per call. For the typical use of the module level API, generating a modest number of values, the difference is negligible. Performance-sensitive code that generates large quantities of random numbers should already be using its own `Random` instance or NumPy's generators, and can call `random.seed()` or `ensure_repeatable()` to restore the old performance.

## Why not just add `secrets`?

The `secrets` module is a good idea and this PEP supports it. But it only helps people who know they need it. The problem this PEP addresses is precisely the people who don't know.

# Backwards Compatibility

Programs that never seed the generator will see different values, which is fine because those values were never reproducible.

Programs that seed the generator see identical behaviour.

Programs that use the generator before seeding it, and then seed it, see the same values after seeding as before, plus a `RandomWarning`.

Libraries that call `random.seed()` at import time would switch the entire process into deterministic mode. This is already a questionable practice, since it affects other code sharing the module level generator, and the warning helps identify it.

Code that pickles or inspects the hidden `random._inst` object directly will need updating. This is a private name and not covered by compatibility guarantees.

# Transition Plan

1. In Python 3.6, add `ensure_repeatable()`, `system_random` and `RandomWarning`, and emit a `DeprecationWarning` when module level functions are used without first seeding, informing users the default will change.
2. In a later release, switch the default as described.

# Open Questions

- Should `ensure_repeatable()` be triggered by an environment variable or command-line option, for applications that cannot easily be modified?
- Is the warning on implicit switching too noisy for test suites that seed per test?
