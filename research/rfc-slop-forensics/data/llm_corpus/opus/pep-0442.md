# Abstract

This PEP proposes to deal with the current limitations of object finalization. The goal is to be able to define and run finalizers for any object, regardless of its position in the object graph. In particular, objects with a `__del__` method that are part of a reference cycle will be collected rather than being left in `gc.garbage`.

This PEP does not call for any change in Python code. Objects with existing finalizers benefit automatically.

# Definitions

**Reference** — A directional link from one object to another. The target of a reference is kept alive by it as long as the source is alive and the reference exists.

**Weak reference** — A reference that does not keep its target alive. Weak references may have callbacks that run when the target is about to be destroyed.

**Reference cycle** — A cyclic subgraph of references. An object in a reference cycle cannot be freed by reference counting alone, because its count never drops to zero.

**Cyclic isolate (CI)** — A reference cycle, or set of interconnected cycles, with no references from outside. Its objects are unreachable from the rest of the program and are candidates for cyclic garbage collection.

**Cyclic garbage collector (GC)** — The `gc` module's collector, which identifies cyclic isolates and breaks them.

**Finalizer** — A function or method called when an object is about to be destroyed. For Python classes, this is `__del__`; for C extension types, this PEP introduces the `tp_finalize` slot.

**Clearing** — Breaking the references held by an object so that its referents can be freed. For C types this is done through `tp_clear`.

**Resurrection** — The situation where a finalizer creates a new strong reference to the object being finalized, or to another object in the same isolate, causing it to become reachable again.

# Rationale

Under CPython's current rules, the cyclic garbage collector refuses to collect a cyclic isolate if any object in it has a `__del__` method. The objects are instead appended to `gc.garbage` and kept alive forever, unless the program inspects that list and breaks the cycles itself. The reason is ordering: if objects A and B reference each other and both have finalizers, there is no safe order in which to call them. Whichever runs second might see an object whose state has already been torn down.

In practice, this rule causes several problems:

- **Memory leaks.** Cycles involving finalizers are surprisingly common. A file-like wrapper that references its parent object, which in turn holds a list of wrappers, is enough. Programs leak memory silently unless someone checks `gc.garbage`.
- **Generators.** A generator suspended inside a `try`/`finally` block has an implicit finalizer: closing it runs the `finally` clause. Generators in cycles therefore end up in `gc.garbage`, which is surprising for code that never defined `__del__`.
- **Workarounds pollute library design.** Library authors avoid `__del__` and resort to weak references and callbacks to implement cleanup, which is both more complex and more error-prone.
- **C extensions.** Types implemented in C that need cleanup logic have no hook that the GC can call safely. They do their cleanup in `tp_dealloc`, which runs too late — after references may already have been cleared — and cannot safely execute arbitrary Python code.

The ordering concern is real, but it rests on an assumption that does not have to hold: that finalization and clearing are a single step. If all finalizers in an isolate are called *before* anything is cleared, then every finalizer sees a fully intact object graph. No finalizer can observe a torn-down object, because nothing has been torn down yet.

# Proposal

## Separating finalization from deallocation

A new slot, `tp_finalize`, is added to type objects. It is a function with signature `void tp_finalize(PyObject *self)`. For Python classes, the slot is filled with a wrapper that calls `__del__`. Its contract:

- It is called at most once per object, by the interpreter, before the object is destroyed.
- It is called while the object is still fully intact; all of its references are valid.
- It may execute arbitrary Python code, including code that resurrects the object.
- Exceptions raised from it are reported through `PyErr_WriteUnraisable` and otherwise ignored.

A flag in the object's GC header records whether the finalizer has been called. This ensures that a resurrected object is not finalized a second time when it eventually dies again.

## Reference-counting path

When an object's reference count drops to zero and it is not part of a cycle, the deallocator calls `tp_finalize` first (if present and not yet called), then checks whether the object was resurrected. If it was, deallocation stops. Otherwise, deallocation proceeds as before.

## Cyclic garbage collection path

The GC's handling of a cyclic isolate becomes:

1. **Identify** the cyclic isolate as today.
2. **Finalize.** Call `tp_finalize` on every object in the isolate whose finalizer has not yet run, and mark it as finalized. Weak-reference callbacks are handled at this stage as well.
3. **Check for resurrection.** Recompute reference counts within the isolate. If any object in it is now referenced from outside — that is, a finalizer resurrected something — abort collection of this isolate. The objects survive. Because their finalizers are now marked as having run, they will not be finalized again; the next time they become unreachable, the GC proceeds directly to clearing.
4. **Clear.** If the isolate is still isolated, call `tp_clear` on its objects to break the cycles. Reference counting then frees them.

The key property is that finalizers run against an intact graph. A finalizer on object A may safely access object B, even if B is in the same cycle and has a finalizer of its own, because B has not been cleared.

## Legacy finalizers

C types that implement cleanup in `tp_del` (the existing, unsafe slot) keep the old behaviour: isolates containing such objects are still placed in `gc.garbage`. This retains compatibility with extensions that cannot handle the new protocol. Python classes with `__del__` move entirely to the new mechanism.

## Generators

Generators gain a `tp_finalize` that closes them. As a result, suspended generators in reference cycles are collected and their `finally` blocks run, rather than being left in `gc.garbage`.

# Impact

Python code needs no changes. Classes with `__del__` that previously leaked in cycles will be collected. Programs that relied on finding such objects in `gc.garbage` will see an empty list in cases where it previously had entries; this is considered a fix, not a regression.

C extension authors are encouraged to move cleanup logic that executes Python code from `tp_dealloc` or `tp_del` into `tp_finalize`. Types that do so must set the `Py_TPFLAGS_HAVE_FINALIZE` flag. The `PyObject_CallFinalizerFromDealloc()` helper is provided for types that need to call the finalizer from their deallocator in the non-cyclic case.

# Discussion

## Order of finalizer calls

Within an isolate, finalizers are called in an unspecified order. Since none of them see a cleared object, the order matters only if finalizers interact with one another's state, which programs should not rely on.

## Resurrection and repeated finalization

Calling a finalizer only once is a deliberate choice. If a resurrected object were finalized again on its next death, a finalizer that always resurrects its object would prevent it from ever being collected and could run indefinitely. Calling it once matches the behaviour of Java and the .NET runtime, which also guarantee at most one finalization per object.

## Cost

The new flag fits in existing padding in the GC header on common platforms, so there is no memory overhead. The extra pass over the isolate to call finalizers and recompute reference counts is proportional to the size of the isolate and only occurs for isolates containing finalizable objects.

# Reference Implementation

A reference implementation is available in a branch of the CPython repository. It passes the existing test suite and adds tests for finalization in cycles, resurrection, and generator collection.
