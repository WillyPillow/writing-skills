Title: Explicit Unicode Literal for Python 3.3

# Abstract

This document proposes the reintegration of an explicit unicode literal from Python 2.x to the Python 3.x language specification, in order to reduce the volume of changes needed when porting Unicode-aware Python 2 applications to Python 3.

# Proposal

This PEP proposes that Python 3.3 restore support for the `u` prefix on string literals. In Python 3.3 and later, the following will be valid and equivalent:

```python
'text'
u'text'
U'text'
```

All three produce an object of type `str`. The `u` prefix has no semantic effect; it exists purely so that source code written for Python 2 with explicit unicode literals is also valid Python 3.

The prefix is accepted in combination with triple quoting (`u'''...'''`, `u"""..."""`). It is not accepted in combination with the `r` prefix (`ur'...'`); see "Raw unicode literals" below.

No change is made to the `b` prefix or to bytes literals.

# Rationale

When Python 3.0 was designed, the core developers expected most projects to migrate in one of two ways: either by converting their source tree once using `2to3` and then maintaining Python 3 code thereafter, or by maintaining a Python 2 tree and running `2to3` at build time to generate Python 3 code. Under either model, the removal of the `u` prefix was harmless, because `2to3` simply stripped it.

Experience over the subsequent years has shown that a third model has become dominant, especially for libraries and frameworks: maintaining a single code base that runs unmodified on both Python 2.6 or 2.7 and Python 3.x. This approach avoids the slow, opaque build step that `2to3` imposes, means tracebacks point at the code the developer actually wrote, and lets the same tests run directly on every supported version. Libraries such as `six` exist to support it.

The single-source approach works well for most language changes. Print can be handled with `from __future__ import print_function`. Exception syntax `except E as e` is valid on 2.6 and later. Most library renames can be handled with conditional imports. But string literals remain a serious obstacle.

## The string literal problem

In Python 2, `'text'` is a byte string and `u'text'` is a Unicode string. In Python 3, `'text'` is a Unicode string, `b'text'` is a byte string, and `u'text'` is a syntax error.

An application that handles text correctly in Python 2 will have been written with care to mark Unicode strings with `u`, because mixing bytes and Unicode is precisely the source of bugs that such applications have learned to avoid. Web frameworks, templating engines, internationalisation libraries and anything processing human-language text tend to use the `u` prefix pervasively. In a typical such project, a large fraction of all string literals carry it.

To make this code run on Python 3, the developer has three options today:

1. **`from __future__ import unicode_literals`.** This makes unprefixed literals Unicode on Python 2. But it changes the meaning of every literal in the module, including those that genuinely need to be native strings: names passed to `__import__`, `__name__` comparisons, WSGI header values, keyword argument names in `**kwargs` on older 2.x, `str()` results passed to APIs that check `isinstance(x, str)`. Each of these must then be found and wrapped, and the errors are often subtle and only detected at run time.

2. **A wrapper function**, such as `six.u('text')`. Every literal becomes a function call. This is noisy, slower, cannot be used in all contexts where a literal can, such as docstrings, and is easily forgotten.

3. **Removing the prefix and accepting that literals change type.** This is correct only if the application never needs to distinguish text from bytes on Python 2, which is not the case for the applications this PEP is concerned with.

All three require touching a large number of lines, and each touch is an opportunity to introduce a bug. The diffs obscure the actual porting changes that matter. Code review becomes harder. In discussions with maintainers of major web frameworks, the string literal issue has repeatedly been cited as the single biggest mechanical burden in porting.

## Three kinds of string

It is useful to think of Python code that supports both 2 and 3 as dealing with three kinds of string:

- **Text**, which is `unicode` on Python 2 and `str` on Python 3.
- **Bytes**, which is `str` on Python 2 and `bytes` on Python 3.
- **Native strings**, which are `str` on both, meaning bytes on 2 and text on 3. These are required by interfaces such as WSGI, by attribute names, and by many standard library functions.

With this PEP, all three can be written naturally in single-source code: `u'...'` for text, `b'...'` for bytes, and `'...'` for native strings. Without it, there is no literal syntax for text that works on both versions.

# Raw unicode literals

Python 2 supports `ur'...'`, a raw Unicode literal. However, its semantics differ subtly from Python 3's raw strings: in Python 2, `\u` and `\U` escapes are still processed inside `ur` literals. Accepting `ur` in Python 3 with Python 3's raw semantics would silently change the meaning of such literals. Accepting it with Python 2's semantics would introduce an inconsistency into Python 3.

This PEP therefore leaves `ur` unsupported. Raw Unicode literals are much less common than plain ones, and code that uses them can be adjusted by hand.

# Impact on tooling

The tokenizer and parser need a trivial change to accept the prefix. `2to3` will continue to remove the `u` prefix, since the result is correct on all Python 3 versions. Tools that parse Python source, including syntax highlighters and linters, will need to accept `u` when targeting 3.3 and later.

Code that wishes to support Python 3.2 or earlier as well as 3.3 cannot use the prefix. An import hook or a small preprocessing tool can strip the prefix on those versions. Since 3.0 and 3.1 have very few users and 3.2 is expected to be quickly superseded, we expect most single-source projects to target 2.6 or 2.7 plus 3.3 and later.

# Objections

**"This undoes a deliberate design decision."** The removal of `u` was part of making the text model in Python 3 clean, and that model is unchanged. Unprefixed literals are still text. `u` becomes a harmless redundancy, not a reversal.

**"It will encourage people to keep writing Python 2 style code."** Some new Python 3 code may use `u` needlessly. That is a style matter, readily addressed by linters, and of trivial cost compared to the benefit of making ports easier.

**"People should use `2to3`."** Many maintainers have tried this and abandoned it. The language should support the approach the community has found to work.

**"Use `unicode_literals`."** As discussed, this changes the meaning of literals that should remain native strings and does not reduce the volume of edits so much as move them.

# Backwards Compatibility

The change is purely additive. Code that is valid Python 3.2 remains valid with the same meaning.
