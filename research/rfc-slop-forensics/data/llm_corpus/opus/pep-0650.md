# PEP 650: Specifying Installer Requirements for Python Projects

| Field | Value |
|---|---|
| PEP | 650 |
| Title | Specifying Installer Requirements for Python Projects |
| Status | Draft |
| Type | Standards Track |
| Topic | Packaging |

## Abstract

Python package installers are not fully interoperable. pip is the most widely used installer and a de facto standard, but others, such as Poetry and Pipenv, are popular because they offer features suited to particular workflows. Having several installers is good for users with specific needs. The lack of interoperability between them makes it hard for other tools to support all of them.

In particular, there is no standard way to declare a project's dependencies for installation. Each tool must be invoked directly to install from its own format, or must export a `requirements.txt`, which loses information.

This PEP specifies a way for a project to declare which installer it uses, and a minimal API through which any *universal installer* (such as a cloud platform's build step or an IDE) can ask that installer to install the project's dependencies, without knowing anything about its file format.

## Motivation

Consider a hosting platform that deploys Python applications. A user pushes a repository. The platform needs to install its dependencies. Today the platform has to guess:

- Is there a `requirements.txt`? Run `pip install -r requirements.txt`.
- Is there a `Pipfile.lock`? Install Pipenv and run `pipenv install --deploy`.
- Is there a `poetry.lock`? Install Poetry and run `poetry install`.
- Is there something else? Unsupported.

Every platform, CI provider and editor reimplements this detection, and each supports a different subset of tools. New installers cannot gain adoption without convincing every platform to add a special case. Users of less common installers are told to export a `requirements.txt`, which:

- loses hashes, sources, environment markers or groups that the native lock file recorded,
- must be kept in sync by hand or with a hook,
- and means the platform installs something subtly different from what the developer tested.

This is the same problem that build backends had before PEP 517: pip could only build projects that looked like setuptools. PEP 517 solved it by letting a project declare its build backend in `pyproject.toml` and defining a small API that frontends call. This PEP applies the same idea to installation.

## Terminology

**Installer backend.** The tool that knows how to read a project's dependency specification and install it, such as pip, Poetry or Pipenv, exposing the API defined here.

**Universal installer.** A tool that wants to install a project's dependencies without caring which installer backend the project uses: a deployment platform, a CI system, an editor, or a generic command-line wrapper.

## Specification

### Declaring the installer backend

A project declares its installer backend in `pyproject.toml`:

```toml
[installer]
requires = ["poetry-core>=1.0"]
backend = "poetry.installer_api"
```

- `requires` is a list of PEP 508 requirement strings needed to run the backend.
- `backend` is an object reference, in the same `module:attribute` form used by PEP 517, naming the module or object that provides the hooks.

If the table is absent, universal installers may fall back to their existing behaviour. This PEP does not define a default.

### The backend API

The backend must provide one mandatory hook and may provide optional ones.

#### `invoke_install` (mandatory)

```python
def invoke_install(path, *, dependency_group=None, **kwargs) -> int:
    ...
```

Installs the dependencies of the project at `path` into the current environment. `dependency_group` selects a named group, such as `"dev"` or `"docs"`, where the backend supports groups. `None` means the default set. Returns 0 on success and nonzero on failure.

`**kwargs` lets backends accept tool-specific options. Universal installers must not pass options they do not know the backend supports.

#### `invoke_uninstall` (optional)

```python
def invoke_uninstall(path, *, dependency_group=None, **kwargs) -> int:
    ...
```

Removes the dependencies previously installed for `path`.

#### `get_dependencies_to_install` (optional)

```python
def get_dependencies_to_install(path, *, dependency_group=None, **kwargs) -> list[str]:
    ...
```

Returns the list of PEP 508 requirements that `invoke_install` would install, without installing them. This lets a universal installer inspect, audit or cache dependencies.

#### `get_dependency_groups` (optional)

```python
def get_dependency_groups(path, **kwargs) -> set[str]:
    ...
```

Returns the names of the dependency groups the project defines.

#### `update_dependencies` (optional)

```python
def update_dependencies(path, *, dependency_group=None, **kwargs) -> int:
    ...
```

Updates the project's locked dependencies to newer versions allowed by its constraints.

### Execution environment

The universal installer:

1. Reads `[installer]` from `pyproject.toml`.
2. Creates or selects the target environment.
3. Installs the packages in `requires` into an isolated environment from which the backend can run, but which is distinct from the target environment where possible.
4. Imports `backend` and calls the hook, with the target environment active, meaning `sys.executable` and the relevant environment variables point at it.

Hooks run in a subprocess so that a failing or misbehaving backend cannot corrupt the universal installer's own process. Output on stdout and stderr is passed through to the user.

### Errors

Hooks report failure through their return value. An uncaught exception is treated as failure, with its traceback shown to the user.

## Rationale

### Why not standardise a lock file format?

A shared lock file format would be the ideal long-term answer and would remove the need for many of these hooks. It is also a much larger effort with many competing designs. This PEP is deliberately smaller: it lets the existing formats interoperate today, and remains useful afterwards for installers with features beyond what a standard lock file captures.

### Why mirror PEP 517?

Tool authors and platforms already implement PEP 517. Reusing its shape (declaration in `pyproject.toml`, an object reference, isolated requirements, simple function hooks) reduces the cost of adoption and avoids inventing a second mechanism.

### Why so few mandatory hooks?

The only universal need is "install this project's dependencies". Everything else is useful to some universal installers but not all, and not every backend can implement it. Keeping the mandatory surface to one hook makes it easy for an installer to become compliant.

## Backwards Compatibility

The `[installer]` table is new. Tools that do not understand it ignore it. Projects that do not declare it are unaffected.

## Security Implications

Calling a backend runs arbitrary code from the packages listed in `requires`. This is the same trust model as PEP 517 build backends and as running an installer manually. Universal installers that process untrusted repositories should sandbox the subprocess.

## Rejected Ideas

- **Command-line interface instead of a Python API.** Command-line interfaces vary in argument conventions and output parsing. A Python API is easier to specify precisely.
- **Requiring all hooks.** This would exclude simpler installers.

## Open Issues

- Whether the target environment should be passed explicitly as an argument rather than through the active interpreter.
- How dependency group names should be normalised across backends.
