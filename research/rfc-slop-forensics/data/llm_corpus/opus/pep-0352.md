# Abstract

In Python 2.4 and earlier, any classic class can be raised as an exception. The plan for 2.5 was to allow new-style classes as well, but that makes the problem worse: it would mean *any* class, or any instance, could be raised. That rules out any guarantee about the interface of exceptions.

This PEP proposes a new superclass that every raised object must inherit from. With that restriction in place, there can be a standard interface for exceptions that code can rely on, and all exceptions fit into a known hierarchy.

One might object that requiring a particular base class for an interface is unpythonic. Exceptions are a special case, though, and there is good reason for it: exceptions are almost always handled far from where they are raised, by code that knows nothing about their concrete type. That code needs to be able to depend on some minimal behavior.

# Requiring a Common Superclass

This PEP introduces a new built-in class, `BaseException`, at the root of the exception hierarchy. Starting in a future version of Python, `raise` will accept only `BaseException` instances and subclasses. Raising anything else will be a `TypeError`.

`BaseException` defines the interface every exception is guaranteed to have:

```python
class BaseException(object):
    """Superclass representing the base of the exception hierarchy."""

    def __init__(self, *args):
        self.args = args

    def __str__(self):
        if len(self.args) == 1:
            return str(self.args[0])
        return str(self.args)

    def __repr__(self):
        return '%s%r' % (self.__class__.__name__, self.args)

    def __getitem__(self, index):
        """Deprecated; use self.args[index] instead."""
        return self.args[index]
```

The interface is deliberately minimal:

- **`args`**: a tuple of the arguments passed to the constructor. Code that handles an exception it does not know anything about can still display or log these.
- **`__str__`**: a readable rendering of the exception. With a single argument it returns `str()` of that argument, which matches the common usage `raise ValueError("bad input")`. With no arguments it returns an empty string, and with several it returns `str()` of the tuple.
- **`__repr__`**: an unambiguous rendering suitable for debugging.

`__getitem__` is kept only for backward compatibility with code that indexes exceptions directly, such as `e[0]`. It is deprecated.

## Should `message` be added?

An earlier version of this proposal added a `message` attribute holding the first argument. In practice it confuses things: exceptions with several arguments have no obvious "message," and `args` already provides the information. This PEP does not add it.

# Exception Hierarchy Changes

Introducing `BaseException` also means reorganizing the top of the hierarchy. The aim is that the common idiom `except Exception:` catches errors a program might reasonably recover from, and does not catch exceptions that signal the program should stop.

The new top of the hierarchy is:

```
BaseException
 +-- KeyboardInterrupt
 +-- SystemExit
 +-- GeneratorExit
 +-- Exception
      +-- (all other current built-in exceptions)
```

`KeyboardInterrupt` and `SystemExit` currently inherit from `Exception`. As a result, a bare `except Exception:` written to log and continue after errors will also swallow Ctrl-C and calls to `sys.exit()`. That is almost never what the programmer wants, and it is a frequent source of programs that cannot be interrupted.

After this change:

- `except Exception:` catches errors but lets `KeyboardInterrupt`, `SystemExit`, and `GeneratorExit` propagate.
- `except BaseException:` catches everything, for the rare code that really wants to, such as a top-level handler that cleans up and re-raises.
- A bare `except:` continues to catch everything, but it is discouraged.

User-defined exceptions should continue to inherit from `Exception`, not from `BaseException`. `BaseException` exists to sit above everything, not as the default base for new exceptions.

# Transition Plan

Changing what may be raised breaks code, so the transition happens in stages.

## Python 2.5

- Add `BaseException` and make `Exception` inherit from it.
- Move `KeyboardInterrupt` and `SystemExit` to inherit directly from `BaseException`.
- Make all built-in exceptions new-style classes.
- Allow new-style classes to be raised, provided they inherit from `BaseException`.
- Continue to allow classic classes and their instances to be raised.
- Continue to allow string exceptions, with a `DeprecationWarning`.

## Python 2.6

- Issue a `DeprecationWarning` when raising a classic class that does not inherit from `BaseException`.
- Issue a `DeprecationWarning` when using `__getitem__` on an exception.

## Python 2.7

- Make string exceptions an error.

## Python 3.0

- Require all raised objects to be instances of a `BaseException` subclass. Classic classes no longer exist.
- Remove `__getitem__` from `BaseException`.
- A bare `except:` remains legal, and catches only `BaseException` subclasses, which by then is everything that can be raised.

# Implementation

The implementation changes `Objects/exceptions.c` (or the equivalent module that defines the built-in exceptions) to add `BaseException`, reparents the affected exceptions, and updates the `raise` statement in `Python/ceval.c` to check the type of the raised object according to the transition schedule.

`isinstance(e, BaseException)` will hold for every exception that can be caught by code written for Python 3.0. Tools such as loggers and test runners can use that check to identify exceptions without special-casing old-style classes or strings.

# Rationale

## Why a required base class?

Python normally favors duck typing over inheritance checks. Exceptions differ because they are designed to travel through layers of code that know nothing about them. A logging framework, a test runner, or the interpreter's top-level handler must be able to do *something* sensible with any exception it receives. Duck typing would require each of these to guard every attribute access defensively, for a benefit (raising arbitrary objects) that no one actually needs.

Requiring a base class also brings the language in line with Java, C#, and other languages where exceptions share a common root. It also makes the hierarchy easier to document and to teach.

## Why not make `Exception` the root?

Making `Exception` the root would leave nowhere to put `KeyboardInterrupt` and `SystemExit` such that `except Exception:` skips them. A new class above `Exception` solves the problem with the least disruption to existing code, since `except Exception:` keeps its meaning for everything that is actually an error.

# Rejected Ideas

**Allowing any object to be raised.** As explained above, this makes it impossible to rely on any exception interface.

**A `TerminatingException` intermediate class** to group `KeyboardInterrupt` and `SystemExit`. Nobody showed a real need to catch only those two, and the extra class would complicate the hierarchy.

**Deprecating bare `except:` immediately.** It is too widely used for that. Encouraging `except Exception:` instead is enough.
