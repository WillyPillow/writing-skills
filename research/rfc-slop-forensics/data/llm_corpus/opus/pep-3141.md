# Abstract

This PEP defines a set of abstract base classes (ABCs), using the mechanism from PEP 3119, that describe number-like types. The hierarchy is

```
Number :> Complex :> Real :> Rational :> Integral
```

where `A :> B` means "A is a supertype of B." It is modeled on Scheme's numeric tower. The ABCs live in a new module, `numbers`. The built-in types `int`, `float`, `complex`, and the standard library's `fractions.Fraction` and `decimal.Decimal` are registered at the appropriate levels.

# Rationale

Functions that work on numbers often need to ask what kind of number they have been given. A function that computes a floor might accept anything real but reject complex numbers. A function that indexes a sequence needs an integer, and should accept a NumPy integer or a user-defined integer type as readily as an `int`.

Today the only tool for these checks is `isinstance` against concrete types, as in `isinstance(x, (int, float))`. This rejects every number type the author did not think of, including many that behave correctly. The alternative, duck typing, gives no useful way to tell "a real number" from "a complex number," because both support `+`, `*`, and the rest.

PEP 3119 introduced abstract base classes so that a type can declare, or be registered as, an implementation of an interface. This PEP uses that mechanism for numbers. A function can then write `isinstance(x, numbers.Real)` and accept any type that promises to behave like a real number, whether built in or not.

The tower also documents the operations each kind of number is expected to support, which helps people writing new numeric types.

# Specification

All ABCs are defined in the `numbers` module. Each one lists the methods a concrete subclass must provide. Where an operation can be implemented in terms of others, the ABC provides a default.

## `Number`

```python
class Number(metaclass=ABCMeta):
    __hash__ = None
```

`Number` is the root. It defines no operations. Its purpose is to let a type say "I am a number" without committing to anything else, and to let code check for that.

## `Complex`

`Complex` describes the operations defined on complex numbers:

- Conversion: `__complex__`.
- Components: abstract properties `real` and `imag`.
- Arithmetic: `__add__`, `__radd__`, `__neg__`, `__pos__`, `__sub__`, `__rsub__`, `__mul__`, `__rmul__`, `__truediv__`, `__rtruediv__`, `__pow__`, `__rpow__`.
- `__abs__`, returning a `Real`.
- `conjugate()`.
- `__eq__` and `__ne__`.

`__sub__` and `__rsub__` have default implementations in terms of addition and negation. Ordering comparisons are not part of `Complex`, since complex numbers are not ordered.

## `Real`

`Real` adds the operations that make sense on the real line:

- Conversion: `__float__`.
- Rounding: `__trunc__`, `__floor__`, `__ceil__`, and `__round__(self, ndigits=None)`. With `ndigits` omitted, rounding returns an `Integral`. With `ndigits` given, it returns a value of the same type as `self`.
- `__divmod__`, `__rdivmod__`, `__floordiv__`, `__rfloordiv__`, `__mod__`, `__rmod__`.
- Ordering: `__lt__`, `__le__`.

`Real` provides defaults for the `Complex` operations that follow from being real: `real` returns `+self`, `imag` returns `0`, `conjugate()` returns `+self`, and `__complex__` returns `complex(float(self))`. `__divmod__` defaults to `(self // other, self % other)`.

## `Rational`

`Rational` adds the abstract properties `numerator` and `denominator`, which must be `Integral` values in lowest terms with a positive denominator. It provides a default `__float__` computed as `numerator / denominator`.

## `Integral`

`Integral` adds:

- `__int__` and `__index__`.
- `__pow__(self, exponent, modulus=None)`, supporting three-argument `pow`.
- Bitwise operations: `__lshift__`, `__rshift__`, `__and__`, `__xor__`, `__or__`, their reflected forms, and `__invert__`.

It provides `numerator` (returns `+self`) and `denominator` (returns `1`) by default, and `__index__` defaults to `int(self)`.

## Registration of built-in types

```python
Complex.register(complex)
Real.register(float)
Integral.register(int)
```

`bool` is a subclass of `int` and so is `Integral`. `fractions.Fraction` subclasses `Rational`.

`decimal.Decimal` is registered only as a `Number`, not as `Real`. Decimal does not interoperate with `float` in the way `Real` implies (mixing them raises `TypeError`, by design, to avoid silent loss of precision), and its rounding methods follow the decimal context rather than the rules above. Registering it lower in the tower would make promises it does not keep.

# Implementing the arithmetic operations

Mixed-type arithmetic is the hard part. Suppose `A` and `B` are both subclasses of `Rational` from different libraries. `a + b` must give a sensible answer even though neither author knew about the other.

The recommended pattern for a binary operation is:

1. In `A.__add__(self, other)`: if `other` is an instance of a type `A` knows how to handle exactly (for example, `A` itself or `int`), compute the result. Otherwise return `NotImplemented`.
2. In `A.__radd__(self, other)`: if `other` is a type `A` knows, compute the result. Otherwise, if `other` is an instance of `Rational`, convert both to a common representation (for example, using `numerator` and `denominator`) and compute. Otherwise, if `other` is `Real`, convert to `float`. If `other` is `Complex`, convert to `complex`. Otherwise return `NotImplemented`.

The idea is that the forward method only handles cases it is sure of, and the reverse method falls back to the most specific ABC both operands share. This keeps results as precise as possible and lets any two implementations interoperate, while still allowing a type that knows about another to do something better.

# Notes for type implementors

Implementations should make equal values hash equal, even across types. `hash(Fraction(1, 2))` must equal `hash(0.5)`, because `Fraction(1, 2) == 0.5`. This PEP does not specify a hashing algorithm; it notes the requirement.

New ABCs below the tower, such as one for modular integers, are fine. Adding new ABCs between existing levels is discouraged, because it makes the relationships harder for users to follow.

# Rejected alternatives

**A finer hierarchy based on algebra.** An earlier draft defined groups, rings, and fields as ABCs. That is mathematically tidy, but most Python programmers do not think in those terms, and the extra levels added complexity for few practical uses. The Scheme-style tower captures what code usually wants to ask.

**Including exactness.** Scheme distinguishes exact and inexact numbers along a separate axis. We considered `Exact` and `Inexact` ABCs. In practice `float` is the only common inexact type, the property is hard to define precisely for user types, and code that cares can check for `Rational`.

**Making `Decimal` a `Real`.** Discussed above.
