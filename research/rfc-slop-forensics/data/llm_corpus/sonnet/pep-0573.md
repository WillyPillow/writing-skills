# PEP 573: Module State Access from C Extension Methods

- Status: Draft
- Type: Standards Track
- Python-Version: 3.9

## Abstract

This PEP proposes to add a way for CPython extension methods to access context, such as the state of the modules they are defined in. This will allow extension methods to use direct pointer dereferences rather than `PyState_FindModule` for looking up module state, reducing or eliminating the performance cost of using module-scoped state over process global state. This fixes one of the remaining roadblocks for adoption of PEP 3121 (Extension module initialization and finalization) and PEP 489 (Multi-phase extension module initialization). While this PEP takes an additional step towards fully solving the problems that PEP 3121 and PEP 489 started tackling, it does not attempt to resolve *all* remaining concerns. In particular, access to the module state from slot methods (`nb_add`, etc) is not solved.

## Motivation

Historically, C extension modules kept their state in static C variables. This is simple and fast, but it ties the state to the process: there is exactly one copy no matter how many times the module is imported. This breaks down in several situations:

* **Subinterpreters.** Each interpreter should have its own module state, so that objects do not leak between interpreters.
* **Reloading and re-initialization.** A module that is imported, deleted from `sys.modules` and imported again should start with fresh state.
* **Embedding.** An application that initializes and finalizes Python more than once will find stale global state from the previous run.
* **Multiple module objects from one binary.** PEP 489 allows the same shared library to create several independent module objects, each of which ought to have its own state.

PEP 3121 introduced per-module state: a block of memory of `m_size` bytes, allocated with the module object and retrieved with `PyModule_GetState`. PEP 489 added multi-phase initialization, which makes the creation of module objects more flexible. Together they provide the necessary tools, but extension authors have been slow to adopt them. A principal reason is that, in a method of a type defined by the extension, there is no obvious way to find the module object whose state is needed.

The function method signature is `PyObject *meth(PyObject *self, PyObject *args)`. For a function defined at module level, `self` is the module object, and `PyModule_GetState(self)` gives the state. For a method of a class, `self` is an instance of that class, which has no pointer to the module that defined it. The only means available is `PyState_FindModule(&moduledef)`, which looks up the module by definition in a per-interpreter list.

`PyState_FindModule` has serious drawbacks. It requires a lookup in an array indexed by the module's `m_index`, which costs a function call and several memory accesses compared with a static variable. It does not work for modules with multiple instances, since it returns only one per definition. It also does not work for modules created with PEP 489 multi-phase initialization unless the module defines `m_size >= 0`, and in particular modules created from a spec without being added to `sys.modules`, such as `importlib.util.module_from_spec` results, are not registered at all.

Because of this cost and unreliability, many authors keep global state even though they know it is incorrect. The goal of this PEP is to make correct code as convenient and as fast as global state.

## Rationale

The module state is needed from three kinds of places:

1. Module-level functions. Already solved: `self` is the module.
2. Methods of extension types, called through `tp_methods`.
3. Slot functions of extension types, such as `tp_new`, `tp_richcompare` and `nb_add`.

This PEP addresses the second case. The slot case is more difficult because slot signatures have no spare argument through which to pass a context, and because several slots may be reached via lookups that do not have access to the defining type, as with binary operations where either operand's slot may be invoked.

The central idea is to let a method find the *class* that defines it, since the class can be given a reference to its module. In Python, a method defined in a class already has some notion of its defining class, used for `super()`. This PEP introduces an analogous facility for C methods.

## Specification

### Defining class

A new method flag, `METH_METHOD`, indicates that a C function wishes to receive the defining class. A function with this flag has the signature:

```c
PyObject *meth(PyObject *self, PyTypeObject *defining_class,
               PyObject *const *args, Py_ssize_t nargs,
               PyObject *kwnames);
```

This is only permitted in combination with `METH_FASTCALL | METH_KEYWORDS`. The `defining_class` argument is the type object on whose `tp_methods` the method was found, which may differ from `type(self)` if `self` is an instance of a subclass.

The corresponding new C type is `PyCMethodObject`, a subclass of `PyCFunctionObject` that adds a field `mm_class`. Methods with `METH_METHOD` set are instantiated as `PyCMethod` objects, and the class is stored in `mm_class` when the method is bound through the descriptor protocol.

### Looking up the module from a class

Heap types created with `PyType_FromModuleAndSpec` store a reference to a module:

```c
PyObject *PyType_FromModuleAndSpec(PyObject *module, PyType_Spec *spec,
                                   PyObject *bases);
PyObject *PyType_GetModule(PyTypeObject *cls);
void *PyType_GetModuleState(PyTypeObject *cls);
```

`PyType_FromModuleAndSpec` is like `PyType_FromSpecWithBases`, but additionally records `module` in the heap type object. `PyType_GetModule` returns the stored module, raising `TypeError` if the type was not created with one. `PyType_GetModuleState` is a shortcut equivalent to calling `PyModule_GetState` on the result.

The module reference is stored in the extended `PyHeapTypeObject` structure as a new field, `ht_module`. This field is traversed and cleared by the garbage collector, so that a reference cycle between the type and the module can be collected.

### Example

An extension with a module-level state struct and a type defined in the module might look like this:

```c
typedef struct {
    PyObject *error;
    long counter;
} mymod_state;

static PyObject *
Counter_incr(PyObject *self, PyTypeObject *cls,
             PyObject *const *args, Py_ssize_t nargs, PyObject *kwnames)
{
    mymod_state *state = PyType_GetModuleState(cls);
    if (state == NULL) {
        return NULL;
    }
    state->counter++;
    return PyLong_FromLong(state->counter);
}

static PyMethodDef Counter_methods[] = {
    {"incr", (PyCFunction)(void(*)(void))Counter_incr,
     METH_METHOD | METH_FASTCALL | METH_KEYWORDS, "Increment."},
    {NULL}
};
```

The cost of finding the state is two pointer dereferences: from the class to the module, and from the module to its state.

### Module state access from `tp_new`, `tp_init` and other slots

The `PyType_GetModule` functions are also available inside slots as long as the caller has a type object. In `tp_new`, the type is the first argument, and in `tp_init` it can be obtained from `Py_TYPE(self)`. These work in the common case, with the caveat that for a subclass defined in Python, `Py_TYPE(self)` is the subclass, whose `ht_module` is not set. For this case, a helper, `PyType_GetModuleByDef(type, def)`, walks the MRO and returns the module of the first base that was created with the given module definition. This is slower, but suitable for these less-frequently called slots.

```c
PyObject *PyType_GetModuleByDef(PyTypeObject *type, struct PyModuleDef *def);
```

### What is not solved

Binary slots, notably `nb_add`, receive two operands with no type argument, and either could be an instance of a class from this module or from another. `Py_TYPE(self)` is the wrong class when `self` is the right operand, and might be a subclass for which `ht_module` is not set. This PEP does not address those cases, and extensions that need module state in such slots must continue to use `PyState_FindModule` or `PyType_GetModuleByDef` with a known operand.

## Backwards compatibility

The change is additive. Existing methods continue to work, and types created with `PyType_FromSpec` simply have no module. Extension authors are not required to change anything.

The size of `PyHeapTypeObject` grows by one pointer, which affects extensions that allocate it manually or rely on its layout; this is not part of the limited API and is considered an acceptable change.

`METH_METHOD` is not part of the stable ABI in its first release. It may be added to the limited API once it is proven.

## Performance

Looking up the state via the defining class involves a pointer load for `mm_class` and another for `ht_module`, followed by the module's state pointer. This is comparable to the cost of accessing a static variable through a pointer and removes the function call and index lookup of `PyState_FindModule`. An informal benchmark of a method that increments a counter shows a speed-up of about 10 to 15 percent over `PyState_FindModule` and parity within noise with a global variable for typical method bodies.

## Reference implementation

A reference implementation is available as a branch of CPython, including tests that define a type with module state inside a test extension, and verify that two module instances created from the same definition keep independent counters.

## Rejected ideas

**Storing the module in `PyTypeObject` itself.** Only heap types can be freed with their modules; static types cannot refer to a module that may disappear. Restricting the feature to heap types avoids lifetime issues.

**Passing the module as `self`.** Changes the meaning of `self` for ordinary methods and defeats the descriptor protocol.

**A thread-local "current module".** Hidden state, error-prone with callbacks, and wrong in the presence of multiple interpreters per thread.
