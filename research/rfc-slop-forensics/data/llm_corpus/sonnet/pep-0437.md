# PEP 437: A DSL for specifying signatures, annotations and argument converters

- Status: Draft
- Type: Standards Track
- Python-Version: 3.4

## Abstract

The Python C-API currently has no mechanism for specifying and auto-generating function signatures, annotations or custom argument converters. There are several possible approaches to the problem.

Cython uses *cdef* definitions in *.pyx* files to generate the required information. However, CPython's C-API functions often require additional initialization and cleanup snippets that would be hard to specify in a *cdef*.

PEP 436 proposes a domain specific language (DSL) enclosed in C comments that largely resembles a per-parameter configuration file. A preprocessor reads the comment and emits an argument parsing function, docstrings and a header for the function that utilizes the results of the parsing step. The latter function is subsequently referred to as the *implementation function*.

This PEP proposes an alternative DSL that looks much closer to a Python function definition, and which makes the signature, the annotations and the converters part of the declaration itself.

## Rationale

Functions implemented in C have traditionally been written with hand-rolled calls to `PyArg_ParseTuple` or `PyArg_ParseTupleAndKeywords`. The format strings used by these calls encode the types of the arguments, but they do not carry parameter names in a form that the interpreter can introspect, and the docstring that describes the signature is written separately by hand. As a consequence:

1. `inspect.signature()` cannot report a signature for most built-in functions.
2. The signature text in a docstring can drift away from the real parameter list.
3. Argument conversion code is repeated, with minor variations, across the code base.
4. Annotations cannot be attached to built-in functions at all.

PEP 436 addresses these points with a preprocessor and a DSL inside a C comment. The DSL there is organized per parameter: each parameter is declared on a line, and its attributes (the converter, default value, flags) are given as indented sub-lines. This has the advantage of being easy to parse. Its disadvantage is that the declaration of a function no longer resembles the Python function that it implements, and that a reader needs to learn a new notation to understand even simple cases.

The DSL proposed here instead takes the position that the declaration of a built-in function should be written as nearly as possible the way a Python programmer would write it. A C function that implements `os.stat(path, *, dir_fd=None, follow_symlinks=True)` should be declared with that line, plus whatever C-specific information is needed to turn Python objects into C values.

## Specification

### Overview

A block of DSL is placed inside a C comment that starts with a distinguishing marker. A preprocessor script, run during the build, reads these blocks and emits C code immediately after each. The emitted code is delimited by checksummed marker comments so that unmodified output can be detected and regenerated, and manual edits can be flagged.

```c
/*[sig]
def os.stat(path: path_t, *, dir_fd: dir_fd = None,
            follow_symlinks: bool = True) -> stat_result
[sig]*/
```

The preprocessor generates, from this block:

- An argument parsing function, which accepts the usual `(self, args, kwargs)` arguments and extracts the values.
- A docstring in the form expected by `inspect.signature()`, i.e. beginning with the textual signature followed by the marker `\n--\n\n`.
- A declaration of the implementation function with C-typed parameters, which the developer then defines.

### Parameters and annotations

Parameters are written as in a Python `def`. The annotation is not a Python expression evaluated at runtime but the *name of a converter*. A converter is a short description, defined in the preprocessor, of how to turn a Python object into one or more C values:

```
def example(count: int, name: str = "x", *, flag: bool = False)
```

Here `int` is the converter that yields a C `int`, `str` yields a `const char *` and a length if requested, and `bool` yields an `int` that is 0 or 1. The set of built-in converters is deliberately small, and corresponds to the most common format units of `PyArg_ParseTuple`.

Converters may take parameters in parentheses:

```
def read(fd: int, n: Py_ssize_t(min=0))
```

Defaults are Python literals or one of a short list of special values. A default that cannot be expressed as a literal can be given as a C expression in backticks:

```
def pad(width: int = `DEFAULT_WIDTH`)
```

### Return annotations

A return annotation, if present, is a hint for the generated documentation and is emitted into the metadata. It does not change the C return type of the implementation function, which is always `PyObject *` unless the return converter says otherwise. A return converter may be specified to allow the implementation to return a C value that the generated wrapper then converts into a Python object:

```
def getpid() -> pid_t
```

### Custom converters

Where the stock converters do not suffice, a developer defines a custom converter in an additional DSL block. A converter definition has four parts: the C declaration of the variables that hold the converted value, the code that performs the conversion, the code that is run on failure, and cleanup code that runs after the implementation function returns.

```
/*[converter]
converter path_t:
    declare: path_t path = PATH_T_INITIALIZE;
    convert: path_converter(arg, &path)
    cleanup: path_cleanup(&path)
[converter]*/
```

This addresses the shortcoming noted above for `cdef` style declarations: initialization and cleanup snippets are first-class parts of a converter.

### Self and class methods

For methods, the first parameter is written as in Python: `self`, or `cls` for class methods. Its type may be given as a C type with the `self` converter. For module-level functions, `module` is the conventional name.

### Output and regeneration

The generated block follows the DSL block and is bracketed by:

```c
/*[sig end generated code: checksum=...]*/
```

On each run, the preprocessor verifies the checksum. If the checksum matches, the block is replaced with freshly generated code. If the checksum does not match, the file has been edited by hand, and the preprocessor stops with an error rather than overwrite the change.

### Build integration

The preprocessor is a standalone Python script, run once by the build system over the relevant files before compilation. It is also run by a developer-facing target that checks that all generated code is current. The generated code is committed to the repository so that building from a source checkout or a release tarball does not require running the preprocessor.

## Comparison with PEP 436

The two proposals have the same goals and generate essentially the same output. They differ in the shape of the input:

- PEP 436 is parameter-oriented, with a line per parameter and indented attributes. The present proposal is function-oriented and uses Python's own declaration syntax.
- This proposal uses annotation syntax to name converters, which makes simple functions short at the expense of requiring a custom parser for the full syntax of defaults and converter arguments. In practice the preprocessor can reuse Python's `ast` module, since the declaration is a valid Python function definition apart from a few extensions.
- PEP 436 can describe obscure options with additional attribute lines. This proposal expresses the same options as converter parameters, which are less discoverable.

Which of the two is preferable is a matter of taste to some extent. The author believes that familiarity matters more, since the audience is C developers who already know Python function syntax.

## Backwards compatibility

The proposal has no effect on existing code. Functions that are not converted continue to work. Conversion can proceed one function at a time, and a module can mix hand-written and generated parsing code.

For built-in functions that are converted, the user-visible changes are that `inspect.signature()` now works, and that the text of `__doc__` begins with a signature in the standard form. Code that parses the first line of a built-in docstring may need to be updated.

## Reference implementation

A prototype of the preprocessor is being developed and will be published once the specification stabilizes. It includes the converters for the common format units and a test suite that compares generated code against the output of hand-written `PyArg_ParseTuple` calls.

## Open issues

- Whether to allow Python 3 style keyword-only markers in the same form as Python or via a flag.
- The exact set of built-in converters and their names.
- How to express groups of optional positional parameters of the kind found in `curses` functions. The author is inclined to specify these via a special `[` `]` notation, as used in documentation, though this does not map onto Python syntax.
- Whether a C expression as a default should be permitted at all.
- How best to share converters across modules.
