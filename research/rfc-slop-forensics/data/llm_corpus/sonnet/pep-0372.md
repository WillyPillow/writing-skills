# PEP 372: Adding an ordered dictionary to collections

- Status: Draft
- Type: Standards Track
- Python-Version: 2.7, 3.1

## Abstract

This PEP proposes an ordered dictionary as a new data structure for the `collections` module, called "OrderedDict" in this PEP. The proposed API incorporates the experiences gained from working with similar implementations that exist in various real-world applications and other programming languages.

## Patch

A working implementation is available as a patch against the `collections` module. It includes the class, a test suite, and documentation, and has been exercised by a number of users of earlier third-party versions.

## Rationale

In current Python versions, the widely used built-in dict type does not specify an order for the key/value pairs stored. This makes it hard to use dictionaries as data storage for some specific use cases.

Some dynamic programming languages like PHP and Ruby 1.9 guarantee a certain order on iteration. In those languages, and existing Python ordered-dict implementations, the ordering of items is defined by the time of insertion of the key. New keys are appended at the end, but keys that are overwritten are not moved to the end.

The following examples show the problem:

```python
>>> d = dict()
>>> d['parrot'] = 'dead'
>>> d['penguin'] = 'exploded'
>>> d.items()
[('penguin', 'exploded'), ('parrot', 'dead')]
>>> d['penguin'] = 'alive'
>>> d.items()
[('penguin', 'alive'), ('parrot', 'dead')]
```

The order of the items is determined by the hash values of the keys and the history of the table, and so is effectively arbitrary. A program that prints a dictionary may produce different output on different platforms or Python versions. For many use cases this is acceptable, but a number of recurring tasks need a predictable order.

### Use cases

* **Configuration files and serialization.** Programs that read an INI-style or XML file and write it back out want to preserve the order of sections and keys so that a round trip does not shuffle the file and produce unhelpful diffs. Programs that emit JSON, YAML or HTTP headers often want to control the order of fields.
* **Form handling and web frameworks.** HTML forms, query strings and database result rows have a meaningful field order, which is lost if a plain dictionary is used as the container.
* **Tabular data.** A mapping from column name to values should iterate in the order the columns were declared.
* **Keyword arguments.** There is repeated demand for a way to keep the order in which keyword arguments are passed, for example to construct an ordered dictionary directly from a call such as `OrderedDict(a=1, b=2)`. At present, such a call cannot preserve order because the arguments arrive as a plain dict.
* **Caches.** Least-recently-used caches can be implemented simply on top of an ordered mapping where an entry can be moved to the end or the oldest entry popped from the front.
* **Sorting by value or by key.** A common recipe is to sort the items of a dictionary and then retain the result in a mapping, which is not possible with a plain dict.

Many programmers have written their own versions to address these needs. Recipes in the Python Cookbook, modules such as `odict`, `ordereddict` and `StableDict`, and implementations inside Django and other frameworks show both the demand and the disagreement over details.

## Specification

The `OrderedDict` class is a subclass of `dict`. It supports all the methods of a dictionary, and the following differences and additions.

### Ordering

Items are iterated in the order in which their keys were first inserted. Overwriting the value for an existing key does not change its position. Deleting a key and inserting it again places it at the end:

```python
>>> from collections import OrderedDict
>>> d = OrderedDict()
>>> d['a'] = 1
>>> d['b'] = 2
>>> d['a'] = 3
>>> d.keys()
['a', 'b']
>>> del d['a']
>>> d['a'] = 4
>>> d.keys()
['b', 'a']
```

The methods `keys()`, `values()`, `items()`, `iterkeys()`, `itervalues()`, `iteritems()` and the iterator returned by `iter(d)` all use this order.

### Construction

`OrderedDict(data)` accepts a sequence of `(key, value)` pairs, in which case the order of the sequence is preserved. It also accepts a mapping, but if that mapping is an unordered dict the resulting order is arbitrary, and a mapping that is itself an `OrderedDict` preserves its own order. A call that supplies keyword arguments, such as `OrderedDict(a=1, b=2)`, has arbitrary order in this version because Python does not preserve the order of keyword arguments; the documentation notes this limitation.

### Updating

`update()` takes the same arguments as the constructor and is equivalent to setting each key in turn. Existing keys keep their position, and new keys are appended.

### Popping

`popitem(last=True)` removes and returns a `(key, value)` pair. With `last=True` (the default) it pops the most recently added item, giving LIFO order. With `last=False` it pops the oldest, giving FIFO order. This allows `OrderedDict` to be used as a stack, a queue, or the basis for a cache.

`pop(key[, default])` works as for `dict`, removing the entry at any position.

### Reordering

A method `move_to_end(key, last=True)` may be added in a later revision of the API to move an existing key to either end. Without this, code must `pop` the key and set it again, which is correct but needs two hash lookups. This is mentioned as an open issue.

### Sorting and reversal

`OrderedDict` has no `sort()` method. To sort, create a new `OrderedDict` from the sorted items:

```python
>>> d = OrderedDict(sorted(d.items(), key=lambda t: t[1]))
```

Iteration in reverse is supported by `reversed(d)`, which yields keys from newest to oldest.

### Equality

Two `OrderedDict` instances compare equal only if their items are equal *and* appear in the same order. An `OrderedDict` compared with a regular `dict` ignores order, so that code that treats both as mappings still works. This asymmetry is deliberate, since the equality relation must remain consistent with the one defined for `dict`, and an `OrderedDict` is used in places where a `dict` is expected.

### Copying and representation

`copy()` returns a new `OrderedDict` with the same order. `repr()` shows items as a list of pairs, so that the order is visible and the output can be evaluated:

```python
>>> OrderedDict([('a', 1), ('b', 2)])
OrderedDict([('a', 1), ('b', 2)])
```

Pickling and deep copy preserve order.

### Subclassing

`OrderedDict` is designed to be subclassed. Methods are written so that overriding `__setitem__` and `__delitem__` is respected by the other methods that modify the dictionary.

## Implementation

The reference implementation is a pure Python class that stores the key order in a doubly linked list, with a regular dict mapping each key to its list node. Insertion, lookup, and deletion are therefore O(1). The list is kept as sentinel-based circular structure, in which each link is a list of `[prev, next, key]`. Since links refer to each other, they form reference cycles; the implementation uses weak references for the back links, or a `__del__`-free cleanup in `clear()`, to avoid leaking memory.

An alternative implementation that stores the keys in a plain list has O(n) deletion and was rejected. A C implementation is possible and may be added later for performance. The pure Python version is intended to be sufficient for the standard library at first.

Memory use is higher than that of a plain dict, by about three pointers per entry for the list node and the sentinel overhead.

## Alternative approaches

**Order by sorted key.** Some libraries (such as `sorteddict` types in other languages) maintain keys in sorted order. This is a different data structure with different complexity guarantees. It could be added separately and is not what most of the use cases above require.

**Making `dict` ordered.** An ordered built-in dict would benefit everyone but would constrain the hash table implementation, increase memory use for all programs, and risk performance regressions. It is not proposed here.

**Position-based API.** Several third-party modules expose index-based access, such as `d.index(key)` or `d.insert(i, key, value)`. This invites O(n) operations on a structure whose main promise is O(1) hash lookup. The PEP omits them. Users who want positional access can use `list(d)`.

**Overwriting moves a key to the end.** Some implementations treat assignment to an existing key as a new insertion. This is surprising and complicates round-trip use cases. The proposal follows PHP, Ruby, and the majority of Python modules.

## Backwards compatibility

This PEP adds a class to an existing module and changes nothing else. There are no compatibility concerns with existing code, apart from possible name clashes for programs that star-import `collections`.

## Open issues

* Whether to include `move_to_end()` in the first release.
* Whether the constructor should accept keyword arguments given the lack of order.
* Whether equality between two `OrderedDict` instances should be order-sensitive, as proposed, or consistent with `dict`.
