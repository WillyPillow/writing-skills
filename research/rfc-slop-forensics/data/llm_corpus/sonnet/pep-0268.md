PEP: 268
Title: Extended HTTP functionality and WebDAV
Status: Rejected
Type: Standards Track
Created: 20-Aug-2001
Python-Version: 2.3

# Abstract

This PEP discusses new modules and extended functionality for Python's HTTP support. Notably, the addition of authenticated requests, proxy support, authenticated proxy usage, and WebDAV capabilities.

# Rationale

Python has supported HTTP since its early days, through the `httplib` module, which provides a thin layer over the protocol, and `urllib`, which provides a convenient function-oriented interface for fetching URLs. Over the years, the web has changed. Sites commonly require authentication; many users sit behind proxies; and protocols layered on HTTP, such as WebDAV, have become widely deployed for remote authoring and file storage.

The existing modules handle the simplest cases well. A script that wants to download a public document can call `urllib.urlopen()` and read the result. Beyond that, Python programmers face a patchwork of limitations:

- `httplib` is a low-level interface. It sends a request and returns a response, and leaves everything else, such as redirects, authentication challenges, and cookies, to the caller.
- `urllib` follows some redirects and supports basic authentication only through a subclass hook (`FancyURLopener.prompt_user_passwd`), which is awkward and tied to interactive prompts.
- Proxy support in `urllib` is limited to reading environment variables, and does not cover proxies that require credentials.
- There is no support for the HTTP methods and headers used by WebDAV, such as `PROPFIND`, `PROPPATCH`, `MKCOL`, `COPY`, `MOVE`, `LOCK`, and `UNLOCK`.

Users who need these features today must write the code themselves, or look to third-party modules of varying quality. Since the standard library is where most Python programmers look first, we believe these capabilities belong there.

# Specification

This PEP proposes changes in three areas: authentication, proxies, and WebDAV.

## Authenticated requests

`httplib` gains the ability to carry credentials with a request. A new optional argument to `HTTPConnection.request()` is not proposed, because it would complicate a method already carrying several optional arguments. Instead, a small helper layer is added that attaches an `Authorization` header derived from a user name and password.

Two schemes are supported:

- **Basic**, as defined by RFC 2617: the user name and password are joined with a colon, base64-encoded, and sent in the header.
- **Digest**, as defined by RFC 2617: the client responds to a `WWW-Authenticate` challenge with a hashed response containing the nonce, URI, method, and credentials.

Basic can be sent preemptively; Digest requires a round trip, since the server's nonce must be obtained first. The helper therefore offers a method, `request_with_auth(method, url, body, headers, credentials)`, which sends the request, inspects a 401 response for a challenge, and retries once with the appropriate header.

A pluggable registry of authentication handlers allows additional schemes to be added by third parties, such as NTLM, without changing the core.

## Proxy support

The following changes are proposed:

1. A `ProxyHandler` configuration object holding the proxy address and, optionally, credentials. It is created explicitly, or built from the conventional environment variables `http_proxy`, `https_proxy`, and `no_proxy`.
2. For proxied plain HTTP requests, the request line uses the absolute URI form, as required by the HTTP specification. The `Host` header is retained.
3. For HTTPS through a proxy, the client issues a `CONNECT` request to establish a tunnel, then performs the TLS handshake over the tunnel.
4. Authenticated proxies, which reply with status 407 and a `Proxy-Authenticate` header, are handled using the same machinery as server authentication, with `Proxy-Authorization` as the response header.

The `no_proxy` variable is interpreted as a comma-separated list of host names or domain suffixes for which the proxy should be bypassed.

## WebDAV

A new module, `davlib`, provides client support for WebDAV, as specified in RFC 2518. It is built on top of `httplib` and shares the authentication and proxy facilities described above.

The module defines a class `DAV`, a subclass of `HTTPConnection`, with one method per WebDAV verb:

```python
class DAV(HTTPConnection):
    def propfind(self, url, body=None, depth=None): ...
    def proppatch(self, url, body): ...
    def mkcol(self, url): ...
    def copy(self, src, dst, overwrite=1, depth=None): ...
    def move(self, src, dst, overwrite=1): ...
    def lock(self, url, owner=None, timeout=None, depth=None): ...
    def unlock(self, url, locktoken): ...
    def delete(self, url): ...
    def put(self, url, data, content_type=None): ...
```

Each method returns an `httplib.HTTPResponse` object. For methods that return XML bodies, namely `PROPFIND`, `PROPPATCH`, and `LOCK`, helper functions parse the multi-status response into Python data structures: a dictionary mapping resource URLs to dictionaries of property names and values.

XML parsing uses the `xml.dom` or `xml.sax` support in the standard library, rather than requiring an external dependency. Property names are returned as `(namespace, name)` tuples to preserve the namespace information that WebDAV properties rely on.

Conditional requests using the `If` header, and the `Destination` and `Overwrite` headers for `COPY` and `MOVE`, are produced by the module from the arguments given.

A convenience interface, resembling a file system, is also contemplated: a class which maps `listdir`, `mkdir`, `rename`, `remove`, `open`, and `stat` onto WebDAV operations. This is optional and may be deferred.

# Backwards Compatibility

All changes are additive. Existing uses of `httplib` and `urllib` are unaffected. The existing `FancyURLopener` is retained and continues to work, although it may delegate to the new machinery for authentication.

The environment-variable handling of proxies already exists in `urllib` via `getproxies()`. The new classes reuse it, so behavior for existing scripts that rely on those variables remains the same.

# Security Considerations

Basic authentication sends credentials in a reversibly encoded form, so it should be used only over a secure transport. Documentation must make this clear, and the helper should refuse to send Basic credentials over plain HTTP unless the caller explicitly asks for it.

Digest authentication using MD5 is weaker than modern alternatives, but is the scheme widely deployed in 2001. Implementations must avoid reusing nonces in ways that open replay vulnerabilities, and should verify the `nextnonce` and `rspauth` values when provided.

Credentials for proxies and servers are distinct and must not be mixed. In particular, credentials given for one host must not be sent to another after a redirect. The helper strips authorization headers when a redirect crosses hosts.

The `CONNECT` method can be abused to reach arbitrary ports through a proxy. This is a concern for the proxy operator, not the client, but the documentation should note it.

# Reference Implementation

A prototype of `davlib` exists as an external module maintained by Greg Stein and has been used with several servers, including Apache `mod_dav`. The authentication and proxy support are not yet implemented; patches adding them to `httplib` are being prepared.

# Rejected Ideas

**A single comprehensive HTTP client module.** Replacing `httplib` and `urllib` with a unified client was considered. It would give a cleaner design but breaks compatibility and requires substantial work. The incremental approach is preferred.

**Leaving everything to third parties.** Third-party libraries can offer these features, and some already do. However, an authentication and proxy layer is needed by many programs, and should be part of the standard distribution.

# Open Issues

- Should cookie handling be included in this PEP or treated separately?
- How should timeouts be specified? The socket layer has recently gained timeout support, and the HTTP layer ought to expose it.
- Whether `davlib` should be included in the standard library or remain a separate package.
