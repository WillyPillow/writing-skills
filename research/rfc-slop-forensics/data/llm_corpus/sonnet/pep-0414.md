# PEP 414: Explicit Unicode Literal for Python 3.3

- **Status:** Draft
- **Type:** Standards Track
- **Created:** 15-Feb-2012
- **Python-Version:** 3.3

## Abstract

This document proposes the reintegration of an explicit unicode literal from Python 2.x to the Python 3.x language specification, in order to reduce the volume of changes needed when porting Unicode-aware Python 2 applications to Python 3.

## BDFL Pronouncement

This PEP is intended to be submitted for the approval of the project leadership. The recommendation is that it be accepted for inclusion in Python 3.3.

## Proposal

This PEP proposes that Python 3.3 restore support for the `u` prefix on string literals. The prefix is accepted, case-insensitively, immediately before the opening quote of a string literal, including triple-quoted strings:

    u"text"
    U'text'
    u"""multi-line
    text"""

The `u` prefix has no effect on the type or value of the literal. In Python 3, the literal `u"abc"` is identical to `"abc"`: both produce an instance of `str`. The prefix is a no-op provided purely for source-level compatibility.

The `u` prefix may not be combined with the `r` prefix: `ur"..."`, which was valid in Python 2 and was removed in Python 3.0 alongside the other changes, remains invalid. The reasoning is that Python 2's `ur` literals had peculiar semantics for backslash-u escapes, and carrying them forward would reintroduce confusion without any benefit for porting. Also, `ur` is rare in practice compared with `u`.

The `u` prefix may not be combined with `b`. The behavior of `bytes` literals is not changed.

## Rationale

### The porting problem

Python 3.0 changed the meaning of unquoted string literals, so that `"abc"` creates text instead of bytes. The change was correct: text should be the default type for textual data. For a program written only for Python 3, the `u` prefix was redundant, and its removal simplified the language.

For programs that must run on both Python 2 and Python 3, the situation is different. In Python 2, unprefixed literals are byte strings; to write text one needs `u"..."`. A program that has been carefully written to handle Unicode correctly under Python 2 will have these prefixes throughout: in templates, in test fixtures, in dictionary keys, and in documentation strings. When such a program is ported to Python 3, all of those prefixes were, until now, syntax errors.

The tool `2to3` removes the prefixes automatically, and it does so well for programs that will be abandoned on the Python 2 side. But many libraries want to support both versions from a single code base for a period of years. For them, the choices have been:

1. Run `2to3` at install time, so that Python 3 users receive translated code. This makes development awkward: tracebacks refer to generated code, debugging is harder, and the build process is more complicated.
2. Maintain separate source trees for each version. This doubles the maintenance burden.
3. Wrap every text literal in a function call, such as `u("text")`, defined to decode on Python 2 and to return the argument on Python 3. This is the approach taken by compatibility libraries. It is workable, but it is noisy, it costs runtime time on every evaluation unless hoisted, and it makes code harder to read.

The third option is the most widely adopted, and is also the most irritating. A web framework might contain thousands of text literals. Replacing each `u"text"` with `u("text")`, or equivalently with `text_type("text")`, adds visual noise and a function call to code that previously needed neither.

### Why now

At the time of writing, Python 2.7 is the dominant version in production, and the pace of migration is limited by the largest libraries and frameworks, which many applications depend on. These projects have repeatedly cited the removal of `u` as their largest remaining obstacle, ahead of more substantial semantic differences, because the differences in semantics can be addressed locally, but the literal syntax affects every file.

If we want these libraries to reach Python 3 sooner, and many users have told us we do, the cost to us is small. The syntax is simple, already familiar to every Python 2 programmer, and has no runtime semantics.

### The objection from purity

A reasonable objection is that Python 3 deliberately removed the prefix, and that restoring it reintroduces redundancy that the language had shed. This PEP agrees that, in a world containing only Python 3, the prefix is redundant. The justification rests on practicality: its presence reduces the barrier to adoption of Python 3 by a substantial part of the community. The redundancy is harmless; the porting barrier is not.

Another worry is that people will write new Python 3 code with `u` prefixes out of habit. This is not a serious concern. Linters can flag it, and style guides can discourage it, in the same way that redundant parentheses and backslash continuations are discouraged but permitted.

## Specification

The lexical analysis section of the language reference is updated so that the grammar for string literal prefixes is:

    stringprefix ::= "r" | "u" | "R" | "U"

with the prefix `b` and its combinations with `r` defined as before. The tokenizer is changed to accept `u` and `U` at the start of a string literal. No other part of the interpreter needs to change, since the AST for the literal is identical.

The `tokenize` module reports the string with its prefix intact, so that tools that round-trip source code, such as code formatters and refactoring tools, do not lose the information.

The `ast` module does not record the prefix; the parsed value is the same.

`repr()` of a string is unchanged: it does not add a `u` prefix.

## Interaction with `__future__` imports

An alternative would be to require `from __future__ import unicode_literals` in Python 2 to make unprefixed literals into text. That approach has real uses, and is orthogonal to this PEP. It changes the meaning of every literal in a module at once, which can produce subtle bugs when the module also interacts with APIs that require byte strings in Python 2. Many projects have found that explicit prefixes are safer, because the intent is visible at each use.

## Backwards Compatibility

Programs written for earlier Python 3 versions are unaffected, since the prefix was previously a syntax error. Any program that contains a name `u` immediately followed by a string literal, such as `u"x"`, was already invalid. Tools that process Python source must be updated to accept the prefix.

`2to3` retains its existing behavior of removing `u` prefixes by default, but a new fixer option allows them to be preserved.

## Reference Implementation

A patch to the tokenizer is a few lines. It is attached to the tracker issue, together with tests for each valid and invalid combination of prefixes and updates to the documentation.

## Alternatives Considered

### Import hooks

A custom import hook could rewrite the source of a module before compilation, stripping the prefixes. This works, but it is invasive, interacts poorly with tools like debuggers and coverage, and requires installation of the hook.

### A new `__future__` feature

A directive could tell Python 3 to accept `u` prefixes. This would require the same source change in every file and would not remove any obstacles for source compatibility; the `from __future__` line would itself be new to Python 2.

### Do nothing

Libraries continue to use `2to3` or wrapper functions. The costs described above continue.
