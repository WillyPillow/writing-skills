# PEP 223: Change the Meaning of `\x` Escapes

- Status: Draft
- Type: Standards Track
- Created: 20-Aug-2000
- Python-Version: 2.0

## Abstract

Change `\x` escapes, in both 8-bit and Unicode strings, to consume exactly the two hex digits following. The proposal views this as correcting an original design flaw, leading to clearer expression in all flavors of string, a cleaner Unicode story, better compatibility with Perl regular expressions, and with minimal risk to existing code.

## Syntax

The syntax of `\x` escapes, in all flavors of non-raw strings, becomes

    \xhh

where `h` is a hex digit (0-9, a-f, A-F). The exact syntax in 1.5.2 is not clearly specified in the Reference Manual; it says

    \xhh...

implying "2 or more" hex digits, but then goes on to say that the escape sequence may consume any number of hex digits. In practice the implementation reads all the hex digits it finds, then keeps only the low-order bits that fit in a single byte.

## Semantics

In an 8-bit non-raw string,

    \xij

expands to the character

    chr(int(ij, 16))

Notes:

1. This is exactly the same as in ANSI C, except that Python's `\x` is not greedy: ANSI C allows any number of hex digits, which makes it awkward to write a hex escape followed by a literal hex digit.
2. In a Unicode string, `\xij` is the same as `\u00ij`, so the two-digit form names a code point in the Latin-1 range.
3. A `\x` escape followed by fewer than two hex digits is a syntax error, rather than being silently accepted.

For example, `"\x4142"` today produces a single character in 1.5.2 (the low byte of 0x4142, namely `"B"`), and under this proposal produces the two characters `"AB"`.

## Backward Compatibility

The proposed change is an incompatible one, but a narrow one. Any code that used `\x` with exactly two hex digits behaves identically. Any code that used `\x` with one digit would now raise a syntax error. Any code that used three or more hex digits would see a changed meaning, from "a single byte determined by the low-order bits" to "a byte followed by literal characters".

We believe such uses are extremely rare. Because the existing behavior silently discarded high-order bits, a program that wrote `\x123` was almost certainly mistaken or confused about what it was getting. To gauge the impact, the Python standard library and a sampling of publicly available third-party code were searched for string literals containing `\x` followed by three or more hex digits. A handful of hits were located, nearly all of them in regular expression literals or test data, and most of those would have been bugs as written.

For the one-digit case, the previous behavior was to accept `\xa` as `chr(10)`. A migration path is simple: write `\x0a` instead. The tokenizer error can mention this in its message.

Raw strings are unaffected, since the backslash is retained verbatim in them.

## Effects on Unicode

The existing situation for Unicode strings is awkward. A Unicode literal `u"\x1234"` consumes four hex digits under the "as many as available" rule and yields what appears to be a Unicode code point, which overlaps in function with `ሴ`. Having two spellings for the same concept in Unicode strings is redundant, and worse, `\x` and `\u` disagree about digit counts, so that moving between them requires care.

Under this proposal, `\x` in a Unicode string always means a code point below 256, and `\u` is the way to name a code point in the Basic Multilingual Plane. The mapping between 8-bit and Unicode strings via the default Latin-1 interpretation is then clean: `\xhh` means the same character in both, and `u"\xe9"` is "e acute", the same as `u"é"`.

This also makes Unicode escapes easier to document. Each escape has a fixed width:

    \xhh      two hex digits
    \uhhhh    four hex digits
    \Uhhhhhhhh    eight hex digits

and none of them depends on what follows in the string.

## Effects on Regular Expressions

Perl, whose regular expression syntax Python's `re` module follows closely, defines `\x` in a regular expression to consume at most two hex digits when written as `\xhh` (and permits `\x{...}` for longer forms). The Python behavior under 1.5.2 differs from Perl, which is a repeated source of confusion for programmers porting patterns. Pattern strings typically pass through the string-literal parser before `re` sees them, unless raw strings are used, so a change to the literal rules also affects what `re` receives.

With the change, a non-raw string literal such as `"\x41B"` yields `"AB"`, as in Perl. Raw strings continue to pass the escape through to `re`, which already treats `\x` as two digits. Aligning the two layers removes a trap in which the same escape would have two different widths depending on whether it was processed by the tokenizer or by the regular expression compiler.

## Rationale

The original design flaw is that `\x` was specified to consume "any number of hex digits", copied from ANSI C. In C, this is tolerable because characters are narrow and the greedy rule rarely matters in practice; where it does, C programmers split the string literal, relying on adjacent literal concatenation, as in `"\x41" "B"`. Python has the same concatenation, but the greedy behavior is more surprising here because the implementation then truncated the result to a byte, a step that C implementations typically report as an out-of-range error.

Silently truncating has no benefit. It converts an apparent mistake into a program that runs and produces the wrong data.

Fixed-width escapes have several advantages:

- **Predictability.** A reader can tell how many characters an escape occupies without examining the neighboring text.
- **Composability.** Writing a hex escape adjacent to hex-looking text, which is common in binary protocols and test fixtures, no longer requires splitting the literal.
- **Consistency.** Every escape in the language that takes hex digits now has a fixed width.

## Alternatives Considered

**Leave things as they are.** This preserves compatibility with the small amount of code that depends on the current rule, but it keeps a known hazard and leaves Unicode strings with duplicate escape spellings.

**Deprecate first.** One could issue a warning for `\x` escapes followed by more than two hex digits for one release, and change the meaning the release after. This is the conservative route. We think it is unnecessary because so little code is affected, and because a warning phase would extend the period in which the meaning of the same text differs between releases.

**Add a new escape for the fixed-width form.** For instance, keep `\x` greedy and introduce something new. This burdens the language with two nearly identical escapes and requires users to learn which is which.

**Make `\x` with more than two digits an error.** This would be safer in the face of ambiguous intent. But the result of `\x41B` is not ambiguous in any real sense once the rule is stated plainly, and rejecting valid text would add friction for users writing hex-looking content after an escape.

## Implementation

The change is confined to the string-literal decoding function in the compiler and the corresponding Unicode-escape decoder. In the 8-bit path, the loop consuming hex digits is replaced with one that reads exactly two, and raises a `ValueError` (reported as a `SyntaxError` for literals) if fewer than two digits are found. In the Unicode path, `\x` is routed through the same logic so that the result is a code point from 0 to 255.

Documentation changes include the Language Reference section on string literals, which will state the exact two-digit rule and remove the sentence implying more digits may be consumed. The tutorial's discussion of escapes will be updated, and the NEWS entry will highlight the incompatibility.

Test cases should cover: two-digit escapes in both kinds of strings; adjacent literal hex digits following an escape; the error for one-digit escapes; raw strings preserving the backslash; and a representative set of regular expressions to confirm agreement with the Perl behavior.

## Open Issues

Whether the diagnostic for a malformed escape should name the offending position and suggest the zero-padded two-digit form remains to be decided. It is also unresolved whether the `codecs` `unicode-escape` and `raw-unicode-escape` codecs should adopt the same rule in the same release; consistency suggests yes, since otherwise the codec and the compiler would disagree about the meaning of the same text.
