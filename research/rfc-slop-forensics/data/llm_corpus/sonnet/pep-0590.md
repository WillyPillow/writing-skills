# PEP 590: Vectorcall: a fast calling protocol for CPython

- Author: Mark Shannon, Jeroen Demeyer
- Status: Draft
- Type: Standards Track
- Created: 29-Mar-2019
- Python-Version: 3.8

## Abstract

This PEP introduces a new C API to optimize calls of objects. It introduces a new "vectorcall" protocol and calling convention. This is based on the "fastcall" convention, which is already used internally by CPython. The new features can be used by any user-defined extension class.

Most of the new API is private in CPython 3.8. The plan is to finalize semantics and make it public in Python 3.9.

**NOTE**: This PEP deals only with the Python/C API, it does not affect the Python language or standard library.

## Motivation

The choice of a calling convention impacts the performance and flexibility of code on either side of the call. Often there is tension between performance and flexibility.

The current `tp_call` calling convention is sufficiently flexible to cover all cases, but its performance is poor. The reason is that it requires every call to build a tuple of positional arguments and a dict of keyword arguments, even when the callee immediately unpacks them again. Allocating and filling these containers is often more expensive than the work done by the callee.

CPython already works around this internally. Built-in functions and methods can be declared with `METH_FASTCALL`, which passes arguments as a C array plus a count, and `METH_FASTCALL | METH_KEYWORDS`, which adds a tuple of keyword names. Python functions use a similar scheme inside the interpreter loop. But the optimization has limits:

- It is specific to a few types, namely built-in function and method objects and Python functions. Other callables, including those defined by extension modules, cannot use it.
- The dispatch is done by `if` chains inside `PyObject_Call` and friends, rather than by a protocol that classes can implement.
- Wrapper callables, such as bound methods, `functools.partial` and Cython's function objects, must either construct a tuple to forward the arguments or reimplement the same special cases.

The result is that extension authors who want speed must imitate built-in types, and the interpreter must know about each fast case.

### Goals

1. Provide a calling convention that avoids creating temporary tuples and dicts.
2. Make it available to any extension type, not just those built into CPython.
3. Keep it simple and small enough that it can be understood and implemented correctly, and allow `PyObject_Call` and its relatives to benefit automatically.
4. Retain backwards compatibility, so existing callables continue to work unchanged.

## Specification

### The vectorcall signature

A callable that supports vectorcall provides a C function with the following signature:

```c
typedef PyObject *(*vectorcallfunc)(PyObject *callable,
                                    PyObject *const *args,
                                    size_t nargsf,
                                    PyObject *kwnames);
```

- `callable` is the object being called.
- `args` is a C array of arguments. The first positional arguments come first, followed by the values of keyword arguments, in the order of `kwnames`.
- `nargsf` is the number of positional arguments, optionally combined with the flag `PY_VECTORCALL_ARGUMENTS_OFFSET`.
- `kwnames` is either `NULL`, or a tuple of keyword names (strings). The number of keyword arguments is the length of that tuple.

The total number of items read from `args` is therefore `PyVectorcall_NARGS(nargsf) + len(kwnames)`.

The caller owns the array and its elements. The callee must not modify them, with one exception described below, and must not keep a pointer to the array after returning.

### The PY_VECTORCALL_ARGUMENTS_OFFSET flag

If the flag `PY_VECTORCALL_ARGUMENTS_OFFSET` is set in `nargsf`, the callee is allowed to temporarily modify `args[-1]`. This is intended for bound-method style objects, which need to prepend `self` to the arguments: instead of allocating a new array, the callee can write `self` into `args[-1]`, call the underlying function with `args - 1`, and restore the previous value before returning.

The flag tells the callee that the slot is writable. A caller that sets it must guarantee that the memory at `args[-1]` is valid and may be restored. A callee that does not wish to use it must ignore the flag and must not pass it on unchanged to a further callee unless it has left `args[-1]` in its original state.

### Opting in: tp_vectorcall_offset and Py_TPFLAGS_HAVE_VECTORCALL

A type opts in to vectorcall as follows:

1. The type sets the flag `Py_TPFLAGS_HAVE_VECTORCALL` in `tp_flags`.
2. The type's `tp_vectorcall_offset` slot holds the byte offset, within each instance, of a `vectorcallfunc` pointer.
3. Instances store the function pointer in that location when created.

Because the function pointer lives in the instance, different instances of the same type may use different implementations. This is how built-in functions can have a specialized entry for each `METH_*` signature.

A type that sets the flag must also provide a `tp_call` slot. This keeps behaviour consistent when the object is called through a code path that does not know about vectorcall. The two slots must be semantically equivalent. A helper, `PyVectorcall_Call`, is provided to implement `tp_call` in terms of the vectorcall function by converting the tuple and dict to an array and a names tuple.

The flag is inherited by subclasses only if they do not override `__call__` and do not define `tp_call`, since otherwise the vectorcall function would be bypassing the overridden behaviour. Heap types defined in Python never inherit the flag.

### Public and private API

The following functions are added:

```c
PyObject *_PyObject_Vectorcall(PyObject *callable, PyObject *const *args,
                               size_t nargsf, PyObject *kwnames);

PyObject *_PyObject_FastCallDict(PyObject *callable, PyObject *const *args,
                                 size_t nargsf, PyObject *kwargs);

PyObject *_PyVectorcall_Call(PyObject *callable, PyObject *tuple, PyObject *dict);

size_t PyVectorcall_NARGS(size_t nargsf);
```

`_PyObject_Vectorcall` calls the object using vectorcall if available and otherwise falls back to `tp_call` after building a tuple and dict. `_PyObject_FastCallDict` takes keywords as a dict, for callers that already have one. In 3.8, the leading underscore marks these as private. The intent is to drop the underscores in 3.9 after experience with the API.

### Interaction with existing conventions

`METH_FASTCALL` and `METH_FASTCALL | METH_KEYWORDS` are unchanged for authors of C functions. Internally, built-in function objects and method descriptors now use vectorcall, so a call to `len(x)` goes through a single protocol.

Python function objects get a vectorcall entry that sets up a frame directly from the array without intermediate containers. Bound methods use `PY_VECTORCALL_ARGUMENTS_OFFSET` to prepend `self`.

`type.__call__` is not itself vectorcall in this PEP, although types with fast constructors, such as `list`, `dict` and `range`, may provide a vectorcall implementation on the type object itself in a follow-up.

## Backwards Compatibility

The change is purely additive. Existing extensions keep working with no modification. Types that do not set `Py_TPFLAGS_HAVE_VECTORCALL` are called through `tp_call`. The new flag takes a previously unused bit in `tp_flags`. The private names are explicitly unstable.

One subtle difference is for classes that set the flag but later have `__call__` overridden in a subclass. As described above, the flag is cleared for such subclasses, so the overriding `__call__` is honored.

## Performance

Benchmarks on the CPython performance suite show modest but consistent improvements for call-heavy code. Microbenchmarks of calling built-in functions with one to three positional arguments are 10 to 30 percent faster, because the tuple allocation is gone. Calls through `functools.partial` and bound methods of extension types are measurably faster as well, because they avoid copying. No benchmark in the suite shows a significant regression, and memory usage is unchanged except for the extra pointer per instance of types that opt in.

## Reference Implementation

A reference implementation is available as a pull request against CPython. It converts built-in functions, method descriptors, bound methods, Python functions and `functools.partial` to use vectorcall, and adds a test type to the test extension module exercising all paths.

## Rejected Ideas

### A single flat array including keyword values with a separate length

An earlier version of the proposal used a struct describing arguments. It was dropped because it required callers to build the struct and offered no speed advantage over the `(args, nargsf, kwnames)` triple.

### Putting the function pointer in the type

Storing `vectorcallfunc` in the type object, like most slots, would save memory per instance but prevent per-instance specialization. Built-in function objects, which share one type but differ in signature, would need an extra layer of dispatch, which is what we are trying to remove.

### Making the API public immediately

Given the short time until the 3.8 feature freeze, there was concern that the semantics around `PY_VECTORCALL_ARGUMENTS_OFFSET` and inheritance were not yet fully tested outside CPython. Delaying the public API until 3.9 allows third parties such as Cython to try it first.
