# PEP 639: Improving License Clarity with Better Package Metadata

- Author: Philippe Ombredanne, C.A.M. Gerlach, Karolina Surma
- Status: Draft
- Type: Standards Track
- Topic: Packaging
- Created: 15-Aug-2019
- Post-History: Discourse threads on the Packaging forum

## Abstract

This PEP defines a specification for how licenses are documented in Python projects.

To achieve that, it:

- Adopts the [SPDX license expression syntax](https://spdx.github.io/spdx-spec/v2.3/SPDX-license-expressions/) as a means of expressing the license for a Python project.
- Defines how to include license files within the projects, source and built distributions.
- Specifies the necessary changes to Core Metadata and the corresponding Pyproject Metadata keys.
- Describes the necessary changes to the source distribution (sdist), built distribution (wheel) and installed project standards.

This will make license declaration simpler and less ambiguous for package authors to create, end users to understand, and tools to programmatically process.

The changes will update the Core Metadata specification to version 2.4.

## Goals

The main goal of this PEP is to make it easier for users to understand, and for tools to process, the license that applies to a Python package. In particular:

1. Provide a clear, unambiguous way to declare the license of a project in `pyproject.toml` and in the metadata of built distributions.
2. Make the license machine-readable, so that tools can audit dependencies for compliance, without resorting to guessing from free text or classifiers.
3. Ensure that the full text of licenses, and notices such as copyright statements, travel with the code, as many licenses require.
4. Keep the change backwards compatible, with a gradual deprecation of the ambiguous mechanisms in use today.
5. Avoid imposing unnecessary burden on authors, whose most common need is to state a single common license such as MIT or Apache-2.0.

## Motivation

Python packages today can declare a license in at least three places, and the three often disagree.

**The `License` field in Core Metadata.** This is a free-form string intended for a short name. In practice it holds anything from `MIT` to a full multi-paragraph license text. Because the content is unconstrained, a tool cannot tell whether `BSD` means the 2-clause or 3-clause variant, or whether `GPL` includes version 2 only or any later version.

**License classifiers.** Trove classifiers such as `License :: OSI Approved :: MIT License` are structured, but the list is limited, includes ambiguous entries (`License :: OSI Approved :: BSD License`), and cannot express combinations or exceptions. It also cannot carry licenses that are not on the list.

**The `license` key in `pyproject.toml`**, as defined by PEP 621, which is a table accepting either a `file` or a `text` key. This inherits the ambiguity of the Core Metadata field.

In addition, there is no standard for including license files in distributions. Setuptools, Flit, Hatch and others each have their own default patterns, and some include nothing. Wheels have generally put files in unspecified places. Downstream redistributors, such as Linux distributions and conda-forge, end up reading license files out of sdists by hand.

The consequences are tangible. Organizations that must comply with open source licenses cannot reliably determine which licenses apply to their dependency trees. Distributors repeatedly file the same bugs. Authors who want to be correct find that no single field is authoritative, and authors who do not care get no feedback.

Other ecosystems have addressed the same issue. npm uses SPDX expressions in the `license` field of `package.json`. Cargo uses SPDX in `license`. Maven, Debian (DEP-5) and RPM all have schemes of varying strictness.

## Specification

### SPDX license expression

A new field, `License-Expression`, is added to Core Metadata. Its value is a valid SPDX license expression, as defined by the SPDX specification, using license identifiers from the SPDX License List or the `LicenseRef-` form for custom licenses. Examples:

```
License-Expression: MIT
License-Expression: Apache-2.0 OR MIT
License-Expression: GPL-3.0-or-later WITH GCC-exception-3.1
License-Expression: LicenseRef-Proprietary
```

Tools should validate the expression, normalize the case of identifiers, and reject invalid ones when building distributions. Consumers of metadata should handle unknown identifiers gracefully, since the SPDX list evolves.

The expression describes the license of the distribution as a whole. If the project bundles components under other licenses, the expression should combine them with `AND`.

### In pyproject.toml

The `[project]` table's `license` key becomes a string containing the SPDX expression:

```toml
[project]
name = "example"
license = "MIT"
license-files = ["LICENSE", "NOTICE"]
```

The previous table form (`license = {text = "..."}` or `{file = "..."}`) is deprecated. Build backends should emit a warning and may continue to accept it for a transition period. The two forms must not be combined.

### License files

A new Core Metadata field, `License-File`, may appear multiple times, with each value being a path relative to the license files directory. The corresponding `pyproject.toml` key is `license-files`, a list of glob patterns relative to the project root. If it is absent, backends use a default set of patterns matching `LICEN[CS]E*`, `COPYING*`, `NOTICE*` and `AUTHORS*`.

Patterns follow a restricted glob syntax: `*`, `?`, `[...]` and `**`, with `/` as the only separator. Patterns that match nothing cause an error, since silent omission would defeat the purpose. Absolute paths and paths with `..` are rejected.

Build backends must copy the matched files into the following locations:

- In an sdist, at the root of the distribution, preserving relative paths, and listing them in `PKG-INFO` via `License-File`.
- In a wheel, in the `.dist-info/licenses/` directory, preserving relative paths.
- In an installed project, in the same `.dist-info/licenses/` directory, alongside `METADATA`.

Installers must preserve this directory when installing. Files placed there must not be shadowed by other contents.

### Deprecations

Several mechanisms are deprecated:

- The `License` Core Metadata field. Tools should stop writing it when `License-Expression` is present. For backwards compatibility with older consumers, a backend may continue to write it with the same SPDX string, for a transition period.
- License classifiers. Tools should reject a project that provides both a `License-Expression` and a `License ::` classifier, and warn when only classifiers are present. Classifiers remain valid in older metadata versions.
- The table form of `project.license` in `pyproject.toml`.

PyPI will start accepting and displaying `License-Expression` and stop requiring classifiers. It may deprecate classifier-based display after a grace period.

### Core Metadata 2.4

The Core Metadata version is bumped to 2.4. `License-Expression` and `License-File` are added. The `License` field is retained but marked deprecated. Metadata version 2.4 is required to use the new fields; earlier versions must not.

## Backwards Compatibility

Existing packages continue to work. Old metadata in the wild remains valid. Tools that read metadata and do not know about 2.4 will ignore the new fields as per the standard handling of unknown fields.

The primary compatibility issue is for build backends and for maintainers who currently use the table form of `project.license`. They will see deprecation warnings. Since PEP 621 is relatively recent, many projects still use it, and a long transition is intended: the old form is expected to remain accepted for at least two years after backends adopt the new one.

For consumers that process `License` strings, such as scanners, the transition may create a period where both fields exist. Scanners should prefer `License-Expression` and fall back otherwise.

## Security Implications

The license is not a security-sensitive field, but license files are copied from the user's tree into distributions, and glob patterns could be abused to include unintended files (for example, `../../etc/passwd`). The restrictions on path syntax prevent traversal out of the project root. Tools should also avoid following symlinks outside the project. Validating expressions with a strict parser avoids injection of control characters into metadata files.

## How to Teach This

The simplest guidance for package authors is:

1. Find your license's SPDX identifier on the SPDX License List.
2. Put it in `license = "..."` in `pyproject.toml`.
3. Make sure your license file is named `LICENSE` or listed in `license-files`.
4. Remove license classifiers.

For most projects this takes one line and one deletion. Documentation in the Python Packaging User Guide should include a migration page, with a table of common old classifiers and their SPDX equivalents, and a note on dual licensing with `OR`.

For tool authors, the SPDX expression grammar is small and reference parsers exist in multiple languages. A validation helper such as the `packaging.licenses` module will be provided so that backends need not implement their own.

## Reference Implementation

Support for `License-Expression` and `license-files` has been prototyped in Setuptools, Flit-core, Hatchling and PDM-backend, and a `packaging.licenses` module provides canonicalization of SPDX expressions. PyPI's warehouse has a branch that displays the expression.

## Rejected Ideas

- **Keeping classifiers as the primary mechanism.** The list is too coarse, and maintaining it in step with SPDX would be a large effort.
- **A new license-specific table in `pyproject.toml`.** An extra table would add complexity without benefit over a string and a list.
- **Allowing free-form custom license names.** The `LicenseRef-` syntax already covers this need and keeps the field machine-parseable.
- **Embedding license text in metadata.** Including full license texts in the metadata file balloons its size, and the files directory is a better home.
