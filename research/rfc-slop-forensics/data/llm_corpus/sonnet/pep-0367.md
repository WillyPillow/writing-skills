# Abstract

This PEP proposes syntactic sugar for use of the `super` type to automatically construct instances of the super type binding to the class that a method was defined in, and the instance (or class object for classmethods) that the method is currently acting upon.

The premise of the new super usage suggested is as follows:

```python
super.foo(1, 2)
```

to replace the old:

```python
super(Foo, self).foo(1, 2)
```

and the current `__builtin__.super` be aliased to `__builtin__.__super__` (with `__builtin__.super` to be removed in Python 3.0).

It is further proposed that assignment to `super` become a `SyntaxError`, similar to the behaviour of `None`.

# Motivation

The current usage of `super` requires an explicit passing of both the class and instance it must operate from, requiring a breaking of the DRY (Don't Repeat Yourself) rule. This hinders any change in class name, and is often considered a wart by many.

Consider an ordinary cooperative method:

```python
class Child(Parent):
    def __init__(self, name, age):
        super(Child, self).__init__(name)
        self.age = age
```

The name `Child` appears twice in a few lines: once in the class statement, once in the call to `super`. If the class is renamed, or if the method is copied into another class, the call silently refers to the wrong class. The consequences are unpleasant. With single inheritance, a stale class name merely skips a level of the hierarchy. With multiple inheritance, it can produce infinite recursion or silently bypass a cooperating base.

There is a second, subtler problem. The first argument must be the class in which the method is *defined*, which is not the same as the class of `self`. Beginners frequently write `super(self.__class__, self)`, which appears to work in simple cases and then recurses infinitely as soon as the class is subclassed. The explicit two-argument form invites the error because the correct arguments cannot be derived by looking at the call.

Finally, the verbose form discourages use of `super` altogether. Many programmers continue to call base class methods directly, as in `Parent.__init__(self, name)`, which breaks cooperative multiple inheritance. If the correct idiom were shorter than the incorrect one, adoption would improve.

# Specification

## Overview

Within a method defined in a class body, the name `super` used as an attribute-access prefix refers to the proxy for the next class in the method resolution order after the class in which the method was defined, bound to the method's first argument. The compiler recognises the construct and arranges for the necessary information to be available at runtime.

Concretely, in a method of `Foo`:

* `super.foo(1, 2)` is equivalent to `super(Foo, self).foo(1, 2)`, where `self` is the first positional parameter of the enclosing function.
* In a classmethod, the first parameter is the class object, and the call binds to the class: `super.create()` is equivalent to `super(Foo, cls).create()`.
* In a staticmethod, which has no instance or class parameter to bind, use of the form is an error.

The bare name `super` with no attribute access, for example `x = super`, or `super(Foo, self)` with explicit arguments, retains its existing meaning, provided the aliases below.

## The `__super__` alias

The existing type remains available under a new name, `__builtin__.__super__`, so that code that needs the explicit form can still reach it. Calls such as `__super__(Foo, self).foo()` operate exactly as the old `super(Foo, self).foo()`.

In Python 3.0, `__builtin__.super` as the explicit type is removed; only the new semantic form remains. In the 2.x series, the old form continues to work during a transition period, and a `PendingDeprecationWarning` is issued.

## Making `super` a keyword-like name

To permit the compiler to treat `super` specially, assignment to the name becomes a `SyntaxError`:

```python
super = 1          # SyntaxError
def super(): pass  # SyntaxError
```

This matches the existing treatment of `None`. Any use as an attribute name, such as `obj.super`, is unaffected.

## Implementation notes

The class in which a method is defined is not known until the class statement completes, because the function object is created before the class is. The compiler therefore stores a reference through a hidden cell variable, `__class__`, which is populated when the class is created. A function that uses the new `super` gains a free variable referencing that cell. The first parameter is accessed by position, so a method with no parameters or only varargs signals a `TypeError` at call time.

This design means that the class reference is lexical: a function defined inside a method and using `super` sees the enclosing method's class and first argument, which is correct for nested helpers.

# Examples

```python
class A:
    def greet(self):
        return "A"

class B(A):
    def greet(self):
        return "B" + super.greet()

class C(A):
    def greet(self):
        return "C" + super.greet()

class D(B, C):
    def greet(self):
        return "D" + super.greet()

D().greet()   # "DBCA"
```

The chain follows the method resolution order of `D`: `D`, `B`, `C`, `A`. Each class refers only to `super`, not to any other class name, so inserting a new class in the hierarchy or renaming one requires no further edits.

In a classmethod:

```python
class Base:
    @classmethod
    def make(cls):
        return cls()

class Derived(Base):
    @classmethod
    def make(cls):
        obj = super.make()
        obj.tag = "derived"
        return obj
```

# Rationale and alternatives

**Why attribute syntax and not a call?** Writing `super().foo()` would be closer to existing code, but a zero-argument call leaves no way for the compiler to distinguish the form from a user-defined name and relies on frame inspection at runtime, which is slow and fragile. Using the bare name as an attribute prefix is unambiguous at compile time.

**Why not a keyword?** Making `super` a reserved word would break any existing code that uses the name, which includes code using it as a parameter or variable. The compromise is to restrict assignment but not other uses of the identifier.

**Why raise on staticmethods?** A staticmethod has no receiver, so there is nothing to bind. Silent failure would be worse.

**Frame introspection.** Several recipes in circulation walk the stack to discover the class and instance. These cost performance, interact badly with decorators, and break when functions are copied between classes.

# Compatibility

Code calling `super(Class, self)` continues to work during 2.x. Programs that rebind the name `super` break and must be changed. This is expected to be rare. Tools that analyse code, such as linters and refactoring tools, need to learn the new form.

# Reference implementation

A prototype patch to the compiler and the symbol table pass implements the hidden `__class__` cell and the attribute-prefix recognition. It passes the test suite with minor adjustments.

# Superseded

A different, call-based syntax with zero arguments, `super()`, was ultimately adopted using the same hidden cell mechanism. This PEP is retained for historical interest.
