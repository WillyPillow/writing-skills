# PEP 633: Dependency specification in pyproject.toml using an exploded TOML table

- PEP: 633
- Title: Dependency specification in pyproject.toml using an exploded TOML table
- Status: Draft
- Type: Standards Track
- Topic: Packaging
- Requires: 508, 621
- Created: 02-Mar-2021

## Abstract

This PEP specifies how to write a project's dependencies in a `pyproject.toml` file for packaging-related tools to consume using the fields defined in PEP 621, as an alternative to the PEP 508-based approach defined in PEP 631.

## Motivation

PEP 621 moved project metadata into `pyproject.toml` and left the representation of dependencies open. PEP 631 filled the gap by storing each dependency as a PEP 508 string in a TOML array:

```toml
[project]
dependencies = [
    "requests >= 2.20; python_version >= '3.6'",
    "django[bcrypt] == 3.1.*",
]
```

This is compact, and it matches what `setup.py` and `requirements.txt` already use. But it embeds a second small language, with its own grammar, inside the TOML string. Several problems follow.

First, tools that need to read or modify a dependency must parse the string. A tool that wants to bump a version, add an extra, or switch a package to a different source must use a PEP 508 parser, and then re-serialize the result, taking care to preserve comments and formatting. TOML libraries that preserve formatting can edit a table in place, but they cannot edit a substring of a string value.

Second, the string form is hard to validate with the generic tools that already exist for TOML. Editors and schema validators can check that a table has the keys it should, with the right types. They cannot look inside a string. A typo in a marker, such as `python_vesion`, is only discovered when a packaging tool is run.

Third, the PEP 508 grammar has quoting and whitespace rules that confuse users. Markers contain quotes inside quotes, so a marker in a TOML basic string needs either escaping or single quotes. URL dependencies use `name @ url` syntax, in which the space before `@` is significant for parsing.

Fourth, it is not obvious how to extend the format. Alternative sources such as a git revision with a subdirectory, a local path in a monorepo, or a hash for a specific file, need a place to put their attributes. PEP 508 has only the URL, and tools that wish to add a revision or a subdirectory must invent syntax, usually in the URL fragment.

An exploded table gives each part of a dependency its own key. Users already familiar with the dependency tables of other ecosystems, such as Cargo's `Cargo.toml` and Poetry's `[tool.poetry.dependencies]`, will recognize the shape. This PEP proposes such a form for the `[project]` metadata.

## Rationale

The design principle is that every piece of information that can be separated is separated, so that it can be read, validated and edited by generic TOML tooling. Names become table keys, versions and extras become named fields, and markers stay as the only remaining string in the PEP 508 language. Markers are kept as strings because they are expressions, with boolean operators and comparisons, and breaking those into tables would be more verbose than the problem warrants.

The PEP defines tables, not arrays, so that a dependency name is a key. Duplicate names, which the array form permits and which are always an error unless markers differentiate them, can then be detected by the TOML parser as duplicate keys. Where a project legitimately needs the same package under different markers, the value may be an array of tables.

## Specification

The `[project]` table is extended with a `dependencies` table and an `optional-dependencies` table of tables, replacing the arrays of strings of PEP 631. A project may use one form or the other, but not both in the same file, and tools must reject files that mix them.

### Dependencies

Each key of `[project.dependencies]` is a project name, normalized according to PEP 503 for comparison. The value is either a string or a table.

A string value is a shorthand for a version specifier, as in PEP 440:

```toml
[project.dependencies]
requests = ">=2.20"
numpy = "*"
```

The special value `"*"` means any version.

A table value may contain the following keys:

- `version`: a PEP 440 version specifier string.
- `extras`: an array of strings naming the extras to enable.
- `markers`: a string containing a PEP 508 environment marker expression. The dependency applies only when the expression evaluates to true.
- `url`: a direct URL reference. It must not be combined with `version`.
- `git`, `rev`, `subdirectory`: a git repository URL, and optionally a revision (a branch, tag or commit) and a path within the repository.
- `path`: a path to a local project directory, relative to the file. Package indexes must reject uploaded metadata containing this key.

Example:

```toml
[project.dependencies]
requests = ">=2.20"
django = { version = "==3.1.*", extras = ["bcrypt"] }
pywin32 = { version = ">=300", markers = "sys_platform == 'win32'" }
mylib = { git = "https://example.org/mylib.git", rev = "v1.2" }
```

When the same project is needed under more than one condition, the value is an array of tables, each with its own `markers`:

```toml
[[project.dependencies.numpy]]
version = "<1.20"
markers = "python_version < '3.7'"

[[project.dependencies.numpy]]
version = ">=1.20"
markers = "python_version >= '3.7'"
```

The conditions must be mutually exclusive, or the result of resolving them is determined by a combination of all active entries, as it would be for several lines in a requirements file.

### Optional dependencies

`[project.optional-dependencies]` is a table whose keys are extra names and whose values are tables of the same shape as `[project.dependencies]`:

```toml
[project.optional-dependencies.test]
pytest = ">=6"
coverage = "*"
```

The names of extras are normalized as in PEP 685.

### Conversion to core metadata

Build backends must translate the tables into `Requires-Dist` and `Provides-Extra` fields as defined in the core metadata specification. Each dependency is rendered to a PEP 508 string, and the conversion is mechanical:

- The name and extras form the name part, as in `django[bcrypt]`.
- The `version` field is the specifier.
- The `url` field produces `name @ url`. A `git` field produces a URL of the form `git+URL@rev#subdirectory=...`.
- The `markers` field is appended after a semicolon, combined with `and` with any marker implied by the optional dependency's extra.

The `path` key has no representation in published metadata. Backends must reject it when building a distribution intended for upload, but may accept it for local builds.

### Dynamic

As in PEP 621, if a backend computes dependencies at build time, `dependencies` or `optional-dependencies` is listed in `dynamic` and must not be given statically.

## Backwards compatibility

This PEP does not change the format of built distributions or their metadata, so installers and indexes are unaffected. Tools that read `pyproject.toml` must be updated to accept the new tables. A tool that does not understand them will treat the project as having no dependencies, unless it checks `project.dependencies` for the type. To make that failure loud, tools are required to raise an error on a `dependencies` value that is not of a type they support.

The two forms cannot coexist, so migration is a rewrite of the section. Conversion between them is mechanical, and a tool can offer to do it.

## Security implications

Allowing `path` and `git` keys in the source of a project introduces the same concerns as direct URL references in PEP 508 strings. Installers must follow the policy already established for them, such as the rule that indexes disallow packages with direct URL dependencies. The explicit table makes it easier to detect and audit such dependencies, since a tool can scan for the keys rather than parse strings.

## How to teach this

The exploded table should be introduced as the same list of dependencies that users have in `requirements.txt`, except that each requirement is a line in a TOML table. The tutorial shows the string form of the table first, `name = "version"`, since it handles most cases, and introduces the inline table for extras and markers. A converter and a reference chart relating each PEP 508 construct to its table form will be in the packaging guide.

## Rejected ideas

**Arrays of PEP 508 strings only.** This is PEP 631. It was rejected for this alternative because of the editing and validation problems above, but remains in force as a competing proposal, and the two are not intended to be accepted together.

**An array of tables with a `name` key.** This would preserve ordering and permit duplicates without a special case, but it makes the common case verbose and does not let a TOML parser detect duplicates.

**Splitting markers into tables.** This was considered and rejected for its verbosity and complexity.

## Open issues

Ordering: TOML tables are unordered by specification, whereas dependency order can matter for some resolvers' tie-breaking. This PEP states that order is not significant.

Whether `*` should be a string shorthand or whether an empty table should mean any version is open for discussion.
