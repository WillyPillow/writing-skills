PEP: 611
Title: The one million limit
Status: Draft
Type: Standards Track
Created: 05-Dec-2019
Python-Version: 3.9

# Abstract

This PEP proposes a soft limit of one million (1 000 000), and a larger hard limit for various aspects of Python code and its implementation.

The Python language does not specify limits for many of its features. Not having any limit to these values seems to enhance programmer freedom, at least superficially, but in practice the CPython VM and other Python virtual machines have implicit limits or are forced to assume that the limits are astronomical, which is expensive.

This PEP lists a number of features which are to have a limit of one million. For CPython the hard limit will be eight million (8 000 000).

# Motivation

There are many values that need to be represented in a virtual machine. If no limit is specified for these values, then the representation must either be inefficient or vulnerable to overflow. The CPython virtual machine represents values like line numbers, stack offsets and instruction offsets by 32 bit values. This is inefficient, and potentially unsafe.

It is inefficient because modern processors can handle smaller values more efficiently than larger ones, in terms of both memory use and cache behavior. It is potentially unsafe because, with no stated limit, a conforming program or a malicious input could cause an integer overflow in the interpreter, with undefined consequences in C code.

The limits in this PEP are chosen to be large enough that no sensible program would hit them, and small enough to allow compact and fast representations. Having such limits would make it easier for tools, such as debuggers and profilers, to store data compactly, and for virtual machines other than CPython to make reasonable assumptions.

## Safety

Without explicit limits, many code paths in CPython rely on the assumption that a value will not exceed `INT_MAX`, but nothing enforces this. Past security bugs have been traced to integer overflows in the compiler and in the handling of large inputs. A uniform, documented limit allows checks to be placed once, at the point of creation, rather than scattered throughout the code base.

## Performance

Knowing that a value is small allows more compact encodings. For example, if the number of local variables in a function is below a million, then variable indices can be stored in fewer bits, and instruction formats can be simpler. Similarly, if the number of objects in a class hierarchy is bounded, then type caches can be more compact.

Such reductions may be small individually, but they accumulate across the interpreter, and they matter on devices with limited memory.

## Comprehensibility

Programmers who know the limits of the platform can reason about their programs. Today, the limits that exist in CPython are accidents of implementation. Making them explicit turns them into a documented part of the language, which other implementations can honor.

# Rationale

## Why one million?

One million is a round number that is far larger than any realistic usage. A Python file with more than a million lines is not human-written. A function with a million local variables is a bug. A class with a million subclasses is effectively impossible, since the memory for the class objects alone would be several gigabytes.

At the same time, one million fits comfortably in 20 bits, leaving room in 32 bit words for other data, such as flags and opcodes. The hard limit of eight million fits in 23 bits, so that a 24-bit field with a sign bit, or a 32-bit word with an 8-bit opcode, can hold any such value.

## Soft and hard limits

The soft limit is the limit that the language specifies. Conforming programs must not exceed it. The hard limit is the limit enforced by a particular implementation. A virtual machine may refuse to handle values above the soft limit, but must refuse values above the hard limit. For CPython, the hard limit is eight million.

Between the two limits, behavior is implementation-defined, but implementations are encouraged to raise an exception, rather than to behave incorrectly. This gap gives implementations room for a smooth failure mode, and gives users some slack.

# Specification

The following limits apply. For each, the soft limit is 1 000 000. For CPython, the hard limit is 8 000 000.

- The number of source code lines in a module.
- The number of bytecode instructions in a code object.
- The number of local variables in a function.
- The number of constants in a code object.
- The number of names (globals, attributes, and so on) in a code object.
- The number of classes in a running interpreter.
- The number of direct base classes of a class, and the depth of the class hierarchy.
- The number of attributes of an object.
- The number of nested parentheses in an expression.
- The number of items in a literal of a container type written in source code.
- The number of Python frames on a call stack, subject to the recursion limit, which remains separately configurable and is typically far lower.
- The number of coroutines in a running interpreter.
- The size of the value stack of a frame.

The limit on the *size* of dynamic containers, such as lists, dictionaries and strings created at runtime, is explicitly **not** covered by this PEP. A list may hold billions of elements if the machine has enough memory, and the PEP makes no attempt to change that.

Similarly, the PEP places no limit on the value of integers, the length of identifiers, or the number of threads.

## Behavior on exceeding limits

When a limit is exceeded in source code, the compiler raises `SyntaxError`, or a new subclass, with a message indicating which limit was hit. When a limit is exceeded at runtime, for example during the creation of a class, the interpreter raises `MemoryError` or `RuntimeError`.

# Backwards Compatibility

It is possible that some existing code exceeds these limits. In practice, this should apply only to machine-generated code, such as parsers produced by generator tools, or data tables embedded in source files. A table with more than a million entries written as a literal is unusual; most such data is loaded from files.

Where generated code may exceed the limits, authors can restructure it to load data at runtime, or split it into several modules. The PEP's authors surveyed the top packages on PyPI and found no instance that exceeded the proposed limits, though the survey was necessarily incomplete.

Other implementations of Python are free to adopt stricter limits, or to support larger ones, provided they document them.

# Implementation

The implementation changes can be made incrementally. First, checks are added in the compiler that enforce the limits and produce clear error messages. Second, once the limits are enforced, the internal representation can be narrowed in a subsequent step, without being visible to users. This ordering lets the change be deployed safely and reviewed in small pieces.

Tests will be added to ensure that each limit is enforced and that hitting it produces the expected exception rather than a crash.

# Rejected Ideas

## Larger limits

A limit of a billion or more would not enable any of the compact representations that motivate this PEP. A limit of 2^31 simply matches the current implicit limit.

## Smaller limits

A limit of 65 536 was considered, since it fits in 16 bits. It was rejected as too restrictive: generated code, such as parsers and protocol definitions, can legitimately reach tens of thousands of entries, and the margin would be too small.

## Different limits for different features

A tailored limit for each feature would be more precise, but more complicated to document and remember. A single number is simple, and one million works for all the cases considered.

## No specification

The alternative is the status quo: no limits specified, and each implementation making its own choices. This is the situation that leads to undocumented behavior, security issues, and unnecessary cost.

# Open Issues

- Should the hard limit be configurable at build time?
- How should the limits be exposed to Python code? A possible API is `sys.limits`, a read-only namespace.
- Whether the number of classes in an interpreter should be limited at all, since there is no obvious structural need.
