PEP: 447
Title: Add __getdescriptor__ method to metaclass
Status: Draft
Type: Standards Track
Created: 12-Jun-2013
Python-Version: 3.x

# Abstract

Currently `object.__getattribute__` and `super.__getattribute__` peek in the `__dict__` of classes on the MRO for a class when looking for an attribute. This PEP adds an optional `__getdescriptor__` method to a metaclass that replaces this behavior and gives more control over attribute lookup, especially when using a `super` object.

That is, the MRO walking loop in `_PyType_Lookup` and `super.__getattribute__` gets changed from:

```python
def lookup(mro_list, name):
    for cls in mro_list:
        if name in cls.__dict__:
            return cls.__dict__[name]

    return NotFound
```

to:

```python
def lookup(mro_list, name):
    for cls in mro_list:
        try:
            return cls.__getdescriptor__(name)
        except AttributeError:
            pass

    return NotFound
```

The default implementation of `__getdescriptor__` looks in the class dictionary:

```python
class type:
    def __getdescriptor__(cls, name):
        try:
            return cls.__dict__[name]
        except KeyError:
            raise AttributeError(name) from None
```

# Rationale

It is currently not possible to influence how the `super` class looks up attributes, that is, `super` and the regular attribute machinery always read the `__dict__` of each class in the method resolution order. This is a problem for classes whose attributes are not stored in the class dictionary at all, but are computed or fetched from elsewhere on demand.

The motivating use case is the Objective-C bridge PyObjC. In PyObjC, Python proxies for Objective-C classes expose Objective-C methods as attributes. The set of methods of an Objective-C class is held by the Objective-C runtime and can change while the program runs, for example when a category is loaded from a dynamically linked bundle. Copying all methods into the proxy class's `__dict__` eagerly is both slow and incorrect, because the copy goes stale. PyObjC therefore implements a metaclass with a custom `__getattr__`-style lookup that asks the runtime for a method on demand.

That works for ordinary attribute access on the class or its instances, because the metaclass can intercept the access. It fails for `super`. When a method is invoked through `super().method()`, the lookup walks the MRO of the instance's class starting after the current class, and consults each class's `__dict__` directly. It never calls the metaclass's `__getattribute__` for the classes it passes through. The Objective-C method is not in any `__dict__`, so `super` cannot find it, and the call fails with an `AttributeError`, even though `Class.method` works.

PyObjC has worked around this by shipping its own replacement for `super` and asking users to use it. This is fragile: every library that uses cooperative inheritance through the built-in `super` has to be rewritten, and mixing the two spellings produces confusing errors.

A hook on the metaclass solves the problem at the right level. The metaclass already controls what a class is; it is natural for it to control how attributes are found on the class when walking an inheritance chain.

# Proposal

Add a new optional method to the metaclass, named `__getdescriptor__`, with the signature:

```python
def __getdescriptor__(cls, name):
    ...
```

The method is called with the class on which lookup is being performed (`cls`) and the attribute name (`name`). It should return the raw object stored under that name for that specific class, without invoking the descriptor protocol and without recursing into base classes. If the class has no such attribute, the method raises `AttributeError`.

The two places that walk the MRO are changed to call this method instead of reading `cls.__dict__` directly:

1. `_PyType_Lookup` in the C implementation of `type`, which underlies `object.__getattribute__` and `type.__getattribute__`.
2. `super.__getattribute__`, which walks the MRO starting after a given class.

Everything that follows the lookup is unchanged. Once the raw attribute has been found, the usual descriptor processing is applied: if the object has a `__get__` method it is called with the appropriate instance and owner, and so on.

## The default implementation

`type` provides a default `__getdescriptor__` that reads the class `__dict__`. This keeps the behavior of all existing classes the same. A metaclass that does not override the method behaves exactly as before.

## Interaction with `__getattribute__`

`__getdescriptor__` is deliberately lower level than `__getattribute__`. It is not asked to apply descriptors, to consult instance dictionaries, or to walk bases. Its only job is to answer a narrow question: "does this class itself define something under this name, and if so what is it?" Overriding `__getattribute__` on a metaclass changes what `Class.attr` means; overriding `__getdescriptor__` changes what each link in the inheritance chain contributes.

## Performance

`_PyType_Lookup` is performance critical, and it has a method cache. The cache is consulted before the MRO is walked, and so the hook is not invoked on cache hits. The cache must be invalidated when `__getdescriptor__` itself returns different results over time. For metaclasses that override the method, the type is flagged so that the cache is bypassed or cleared at appropriate times, and the responsibility of calling the invalidation function (as already happens when a class is modified) falls to the metaclass author.

For types that use the default implementation, the C implementation can detect this and keep the existing fast path that reads the dictionary without a Python-level call. Therefore existing code pays no measurable cost.

# Backward Compatibility

The change is backward compatible for classes that do not define `__getdescriptor__`. A metaclass that already defines a method with that name for some other purpose would see it called in a new context. Because double-underscore names are reserved for Python, this is considered acceptable.

There is a minor semantic difference. Code that replaces `__dict__` with a mapping that is not a real dictionary was previously unaffected by the hook; it remains unaffected unless it also defines `__getdescriptor__`.

# Alternatives

**Do nothing.** Projects such as PyObjC continue to ship a replacement `super`. This is the status quo and its drawbacks are described above.

**Make `super` call the metaclass `__getattribute__`.** This would change the semantics of `super` for every metaclass that defines `__getattribute__`, and such methods often assume they are called for a full lookup, including walking bases. Calling them for each class in the MRO would produce repeated and potentially incorrect results.

**Use `__getattr__` on the metaclass.** `__getattr__` is only invoked after normal lookup has failed, so it cannot override attributes that exist in a base class, and `super` does not call it anyway.

**Populate `__dict__` lazily with a custom mapping.** Class dictionaries must be real `dict` instances in CPython, and a lazily populated one would still not know what to return for names that haven't been requested yet.

# Reference Implementation

A patch against the CPython repository implements the proposal. It modifies `_PyType_Lookup` to detect whether the metatype of each class in the MRO overrides `__getdescriptor__`, and modifies `super_getattro` similarly. The default is implemented in C as `type.__getdescriptor__` and is used directly when the metatype is exactly `type` or does not override the method.

# Open Issues

- The name `__getdescriptor__` may be misleading, since the method returns the raw stored object rather than the result of the descriptor protocol. Alternatives such as `__getlocal__` or `__lookup__` have been suggested.
- Whether the method should also be consulted by `dir()` and the `inspect` module is not decided. For now only attribute lookup is affected.
- The precise rules for cache invalidation for metaclasses that override the hook need to be documented.
