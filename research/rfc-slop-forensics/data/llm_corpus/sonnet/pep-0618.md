PEP: 618
Title: Add Optional Length-Checking To zip
Author: Example Author <author@example.org>
Status: Draft
Type: Standards Track
Created: 01-May-2020
Python-Version: 3.10

# Abstract

This PEP proposes adding an optional `strict` boolean keyword parameter to the built-in `zip`. When enabled, a `ValueError` is raised if one of the arguments is exhausted before the others.

# Motivation

Python's `zip` function currently stops when the shortest of its arguments is exhausted, and discards the remaining items of the longer ones without any notice:

```python
>>> list(zip([1, 2, 3], "ab"))
[(1, 'a'), (2, 'b')]
```

This behavior is often convenient. It makes it possible to pair a finite sequence with an infinite iterator such as `itertools.count()`, and it is the usual definition of `zip` in other languages. But there is a large class of programs in which the arguments are expected to have the same length, and a mismatch indicates a bug. Examples include:

- pairing the columns and values of a database row,
- pairing the parameters of a function with the arguments for a call,
- walking two parallel lists, such as labels and data, which were built separately,
- implementing a vector operation, where operands of different dimensions are an error.

In these cases the silent truncation hides the bug. The program produces output that looks plausible but is wrong, and the failure may only be noticed much later, far away from its cause. A survey of code in the standard library found a number of places that call `zip` and need equal lengths, several of which had pre-checks like `assert len(a) == len(b)` and others none. Some of them are likely to contain latent bugs.

## Current workarounds

There are several ways to get checked behavior today, and none of them is pleasant.

**Check lengths first.**

```python
if len(a) != len(b):
    raise ValueError("lengths differ")
for x, y in zip(a, b):
    ...
```

This only works for sequences. It does not work for iterators and generators, which have no length. It also adds a line and, in many programs, a second pass to compute lengths.

**Use `itertools.zip_longest` with a sentinel.**

```python
sentinel = object()
for x, y in zip_longest(a, b, fillvalue=sentinel):
    if x is sentinel or y is sentinel:
        raise ValueError("lengths differ")
```

This works with any iterable, but it is verbose, slower, and easy to get wrong. It is also a recurring recipe: the `more-itertools` package provides `zip_equal`, and the idea appears in many code bases.

**Use a third-party helper.** This requires a dependency and a different name for what is semantically the same operation.

The proposed parameter makes the common case a one-word change.

# Rationale

Experience with the behavior of `zip` in other languages is mixed. Some languages truncate, some raise an error, and some provide both under different names. Python has to keep truncation as the default because the behavior is long established, and a large amount of code depends on it, including code that deliberately uses iterators of different lengths.

Adding a keyword argument is the least disruptive way to add the option. It requires no new name, keeps the discoverability of the feature, and keeps the code readable.

A keyword-only parameter is used so that a call such as `zip(a, b, True)` cannot be mistaken for passing a third iterable. The name `strict` was chosen as it conveys the intent and is already used with a similar meaning elsewhere, for instance in `int.from_bytes`-like APIs and in `pathlib.Path.resolve(strict=...)`.

The default is `False`, which preserves current behavior. The authors considered making the strict mode the default and adding a way to opt out, as it would catch more bugs. This was rejected because it would break working code, and also would require a long deprecation period for little gain.

# Specification

The built-in `zip` accepts a new keyword-only argument:

```python
zip(*iterables, strict=False)
```

When `strict` is false, the behavior is unchanged.

When `strict` is true, `zip` raises a `ValueError` if one iterable is exhausted before the others. The check is made when the iterator is advanced, as follows. On each call to `__next__`, the iterators are advanced in order. If the first one raises `StopIteration`, then the remaining iterators are each advanced once more. If any of them yields a value, a `ValueError` is raised, with a message that identifies which argument is shorter or longer. If all of them raise `StopIteration`, then the `zip` object is exhausted normally. If a later iterator is exhausted before the first one, a `ValueError` is raised at that point.

The error messages are of the form:

```
zip() argument 2 is shorter than argument 1
zip() argument 3 is longer than arguments 1-2
```

An exception other than `StopIteration` raised by an iterator is propagated as usual.

Because the check requires advancing the remaining iterators after the first is exhausted, one extra item may be consumed from the longer iterators before the error is raised. This is unavoidable if there is to be detection at all. Programs that need to preserve every item of the longer iterator should use `zip_longest`.

Examples:

```python
>>> list(zip("abc", range(3), strict=True))
[('a', 0), ('b', 1), ('c', 2)]

>>> list(zip("abc", range(4), strict=True))
Traceback (most recent call last):
  ...
ValueError: zip() argument 2 is longer than argument 1
```

With no iterables, `zip(strict=True)` returns an empty iterator, as `zip()` does.

# Backwards Compatibility

The change is backward compatible. No existing call passes `strict`, because `zip` presently accepts no keyword arguments and raises `TypeError` when given one. Code that relies on this error is not expected to exist.

Third-party tools that inspect the signature of `zip`, such as type stubs, need to be updated. The typeshed stubs have been updated in step with the implementation.

# Performance

When `strict` is false, the extra code path is a single flag test. Benchmarks show no measurable difference. When `strict` is true, there is a small overhead at exhaustion only, because the extra checks occur when an iterator is exhausted rather than at each step.

# Rejected Ideas

**Make `strict` the default.** Discussed above.

**Add a new function.** A separate built-in such as `zip_equal` would work, but adds another name to the namespace and makes the relationship with `zip` less obvious. A new function could also live in `itertools`, where the existing recipe sits, but then it is less discoverable than an argument of `zip`.

**A `mode` string argument.** Something like `zip(a, b, mode="strict")` would allow more options in the future, such as `"longest"`. It would be more verbose and would invite confusion with the existing `zip_longest`. A boolean is simpler and sufficient.

**Check lengths up front where possible.** For sequences, `len` could be used to detect a mismatch before iterating. This would raise errors earlier, but the behavior would then differ between sequences and iterators, and the semantics would be harder to explain.

**Change `map` too.** The `map` built-in with several iterables has the same truncating behavior. It was suggested that it gain a `strict` argument as well. This is left for a separate proposal.

# Reference Implementation

A reference implementation is available as a pull request against CPython. It modifies `bltinmodule.c`, adds the `strict` field to the `zip` object, updates the documentation of the built-in and adds tests that cover equal lengths, each position of the shorter argument, empty arguments, exceptions raised by iterators and pickling of `zip` objects.
