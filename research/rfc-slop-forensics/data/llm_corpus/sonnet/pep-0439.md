# PEP 439: Inclusion of implicit pip bootstrap in Python installation

- **Status:** Draft
- **Type:** Standards Track
- **Created:** 18-Mar-2013
- **Python-Version:** 3.4

## Abstract

This PEP proposes the inclusion of a `pip` bootstrap executable in the Python installation to simplify the use of third-party modules by Python users.

This PEP does not propose to include the `pip` implementation in the Python standard library. Nor does it propose to implement any package management or installation mechanisms beyond those provided by PEP 427 ("The Wheel Binary Package Format 1.0") and the forthcoming distlib PEP.

## Rationale

Installing third-party Python packages is one of the first things a new Python user must learn, and it remains one of the most frequent sources of confusion. A user who has just installed Python and wants to use a library from the Python Package Index (PyPI) currently has to do the following before a single package can be installed:

1. Discover that an installer called `pip` exists, and that it is the recommended tool.
2. Locate the bootstrap instructions for their platform.
3. Download a bootstrap script such as `get-pip.py` over the network, usually with a web browser or `curl`.
4. Run that script, often with elevated privileges, and hope that it chooses the right interpreter.

Every one of these steps is a place where users give up, make a mistake, or end up with a broken installation. Documentation for third-party projects typically begins with the sentence "first, install pip", which pushes the problem onto every project in the ecosystem rather than solving it once.

Other language communities have solved this differently. Ruby ships with `gem`, and Node.js distributions ship with `npm`. A newcomer to those languages can install a dependency immediately after installing the language. Python is, at present, an outlier among popular languages in this respect.

The goal of this PEP is to give Python users a working installer without requiring them to take any step beyond installing Python itself, while avoiding the maintenance and release-cycle problems that would come from adding `pip` to the standard library proper.

### Why not simply bundle pip?

Bundling the full `pip` source in the standard library would tie its release cadence to that of CPython. Packaging tools evolve quickly, and a bug fix in an installer must reach users in weeks, not in the eighteen-month cycle of a language release. Bundling would also make the standard library responsible for the behavior of an installer that frequently changes its dependency resolution, index handling and security posture.

For this reason the PEP proposes a thin bootstrap instead. The bootstrap is small, stable and rarely needs to change. The thing it installs is free to move at its own pace.

## Proposal

Python installations will include an executable named `pip` (together with a versioned form such as `pip3.4`) that is a bootstrap rather than the installer itself.

When the bootstrap is run and a real `pip` is not yet installed for the interpreter, it will:

1. Print a short notice to standard error stating that `pip` is being installed.
2. Download the latest released `pip` from PyPI over HTTPS, verifying the server certificate.
3. Install it, together with its dependencies, into the `site-packages` directory associated with the interpreter, or into the user site directory if the system location is not writable.
4. Replace itself, or hand off execution, so that the original command line is executed by the real `pip`.

On subsequent invocations, the real `pip` is found directly and no network access occurs. The user sees no difference from a conventionally installed `pip`, except for the one-time delay on first use.

### Explicit bootstrap

The same functionality is exposed as a module so that scripts and build systems can request it explicitly:

    python -m ensurepip

An `--upgrade` option will cause the bootstrap to install the latest release even if an older `pip` is present. A `--user` option selects the user site directory. This explicit form is the recommended interface for automated environments, where an implicit network access in the middle of a build would be surprising.

### Installation layout

The bootstrap executable is installed alongside the interpreter in the standard scripts directory. On Windows this is `Scripts`, and on POSIX systems it is the same `bin` directory that contains `python3`. The bootstrap itself is a tiny script, and its only responsibility is to locate the interpreter and run the bootstrap module.

Because the real `pip` is installed into `site-packages` and not into the standard library directory, it can be upgraded, downgraded or removed by the user without interfering with the Python installation proper.

## Security Considerations

Downloading and executing code at the moment of first use deserves careful scrutiny. The proposal relies on the following properties.

- All network access uses HTTPS with certificate verification against the system or interpreter trust store. The bootstrap must refuse to proceed if verification fails, and it must not offer a flag to disable verification.
- Only packages from the canonical PyPI index are fetched, unless the user explicitly overrides the index through the usual configuration mechanisms.
- The bootstrap does not execute arbitrary code from the network before installation. Packages are installed from wheel files in accordance with PEP 427, which means that no `setup.py` is run during bootstrap.

These measures do not make the process immune to compromise of the index or of the user's trust store, but they bring it to parity with the current practice of downloading `get-pip.py` from a web page, and in several respects improve on it, since the user no longer needs to run a script retrieved by an ad hoc command.

Distributors who wish to avoid network access entirely may build the bootstrap against a bundled copy of the wheel files. This option is discussed under Alternatives.

## Backwards Compatibility

The PEP adds new executables and a new module. Existing programs that do not call these are unaffected.

Two compatibility questions deserve attention.

First, systems that already provide `pip` through a distribution package manager will have a name collision. The expectation is that distributors will either omit the bootstrap or arrange for the distribution-supplied `pip` to take precedence. The bootstrap is written so that, if a real `pip` is found, it does nothing but forward the call.

Second, some organizations forbid network access from developer machines. For these, the implicit behavior is a regression in predictability. They can disable it with a build-time option, or simply not use the executable; the explicit `ensurepip` module and the bootstrap are separate entry points.

## Alternatives

### Bundle a wheel inside the installer

An alternative design is to ship a pinned `pip` wheel within the Python distribution and install from it, with no network access. This is attractive in air-gapped settings and removes the security question of first-use downloads. Its drawback is that the bundled `pip` is out of date by the time the interpreter reaches users, which leads to the need to upgrade immediately. The PEP leaves this as a supported mode for distributors, and it may well be a better default in the long run, but the consensus among the packaging community so far has been that a bootstrap that fetches the current release is preferable.

### Do nothing

Continuing to rely on `get-pip.py` leaves the status quo, with all of its friction. The cost falls on the beginner, who is least equipped to deal with it.

### Include pip in the standard library

As discussed under Rationale, this couples release cycles and expands the maintenance burden of the core team. The PEP rejects it.

## Reference Implementation

A reference implementation consists of a `bootstrap` module, the `ensurepip` entry point and the small launcher scripts described above. It has been exercised on Linux, macOS and Windows against the current PyPI. A patch against the development branch will be attached to the tracker issue once the design has been accepted.

## Open Issues

- Whether the implicit first-run behavior should prompt for confirmation when attached to an interactive terminal.
- How virtual environments should interact with the bootstrap. The expectation is that the `venv` module will invoke the explicit form when creating an environment, so that each environment has its own `pip`.
- What the bootstrap should do when the user site directory is not on `sys.path`.
- The final name of the module, and whether to provide a `python -m pip` shortcut that triggers the same behavior.
