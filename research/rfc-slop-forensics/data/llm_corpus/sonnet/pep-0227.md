# PEP 227: Statically Nested Scopes

- PEP: 227
- Title: Statically Nested Scopes
- Status: Final
- Type: Standards Track
- Created: 01-Nov-2000
- Python-Version: 2.1

## Abstract

This PEP describes the addition of statically nested scoping (lexical scoping) for Python 2.2, and as a source level option for python 2.1. In addition, Python 2.1 will issue warnings about constructs whose meaning may change when this feature is enabled.

The old language definition (2.0 and before) defines exactly three namespaces that are used to resolve names -- the local, global, and built-in namespaces. The addition of nested scopes allows resolution of unbound local names in enclosing functions' namespaces.

The most visible consequence of this change is that lambdas (and other nested functions) can reference variables defined in the surrounding namespace. Currently, lambdas must often use default arguments to explicitly creating bindings in the lambda's namespace.

## Introduction

This proposal changes the rules for resolving free variables in Python functions. The new name resolution semantics will take effect with Python 2.2. These semantics will also be available in Python 2.1 by adding "from __future__ import nested_scopes" to the top of a module. (See PEP 236.)

The Python 2.0 definition specifies exactly three namespaces to check for each name -- the local namespace, the global namespace, and the builtin namespace. According to this definition, if a function A is defined within a function B, the names bound in B are not visible in A. The proposal changes the rules so that names bound in B are visible in A (unless A contains a name binding that hides the binding in B).

This specification introduces rules for lexical scoping that are common in Algol-like languages. The combination of lexical scoping and existing support for first-class functions is reminiscent of Scheme.

The changed scoping rules address two problems -- the limited utility of lambda expressions (and nested functions in general), and the frequent confusion of new users familiar with other languages that support nested lexical scopes, e.g. the inability to define recursive functions except at the module level.

The lambda expression yields an unnamed function that evaluates a single expression. It is often used for callback functions. In the example below (written using the Python 2.0 rules), any name used in the body of the lambda must be explicitly passed as a default argument to the lambda.

```python
from Tkinter import *
root = Tk()
Button(root, text="Click here",
       command=lambda root=root: root.test.configure(text="..."))
```

This approach is cumbersome, particularly when there are several names used in the body of the lambda. The long list of default arguments obscures the purpose of the code. The proposed solution, in crude terms, implements the default argument approach automatically. The "root=root" argument can be omitted.

The new name resolution semantics will cause some programs to behave differently than they did under Python 2.0. In some cases, programs will fail to compile. In other cases, names that were previously resolved using the global namespace will be resolved using the local namespace of an enclosing function. In Python 2.1, warnings will be issued for all statements that will behave differently.

## Specification

Python is a statically scoped language with block structure, in the traditional of Algol. A code block or region, such as a module, class definition, or function body, is the basic unit of a program.

Names refer to objects. Names are introduced by name binding operations. Each occurrence of a name in the program text refers to the binding of that name established in the innermost function block containing the use.

The name resolution rules are typical for statically scoped languages, with three primary exceptions:

- Names in class scope are not accessible. Names are resolved in the innermost enclosing function scope. If a class definition occurs in a chain of nested scopes, the resolution process skips class definitions. This rule prevents odd interactions between class attributes and local variable access.
- The global statement short-circuits the normal rules. Names are treated as global if the global statement is used in any block that contains the name, regardless of where the binding takes place.
- Variables are not declared. If a name binding operation occurs anywhere in a function, then that name is treated as local to the function and all references refer to the local binding. If a reference occurs before the name is bound, a NameError is raised.

The specification introduces rules for nested scopes. Given a use of a name within a function F, the name is resolved first in F's local scope. If it is not bound there, it is resolved in the scopes of the functions that enclose F, from the innermost outward. If it is not found in any of them, it is resolved in the global namespace, and then in the builtin namespace.

An example illustrates the rules:

```python
def make_adder(n):
    def adder(x):
        return x + n
    return adder

add5 = make_adder(5)
print(add5(3))    # prints 8
```

Under the old rules, `n` in `adder` would be looked up in the local scope of `adder`, then in the module globals, and the call would fail with a NameError. Under the new rules, `n` is found in the enclosing scope of `make_adder`, and a reference to it is retained for as long as `adder` is alive.

### Rebinding names in enclosing scopes

There are technical issues with rebinding names in enclosing scopes. If a name is bound in a nested function, the name is local to that function, as before. The proposal does not include a mechanism for rebinding a name in an enclosing scope. The `global` statement can only reach the module scope. A user who needs an updatable cell must use a mutable container, such as a list with one element. The question of an additional declaration that would permit rebinding is deferred to a future PEP.

### Interaction with import * and exec

The import * statement and the exec statement without an explicit namespace can bind arbitrary names in a function scope that cannot be determined by examining the source text. This makes static resolution impossible. In a function that contains a nested function with free variables, the use of `import *` or an unqualified `exec` is therefore a SyntaxError. In a function that does not contain nested scopes, these statements keep their existing behavior. A warning is issued in Python 2.1 for code that will become an error.

### Class scope

Names bound in a class body are not visible in methods or nested functions, as before. The rule exists so that a name such as `x` in a method refers to a global or an enclosing function variable and not an attribute with the same name:

```python
x = 'global'
class C:
    x = 'class'
    def method(self):
        return x     # refers to the global, not the class attribute
```

A class defined inside a function can nonetheless see the function's locals, so nested class definitions behave naturally.

## Discussion

The semantics are those of Scheme, Pascal, and many other languages. The rationale for the change is that the lack of nested scopes is surprising to programmers with experience in other languages. It is also an obstacle to functional style, which relies on closures to capture state.

A frequent objection is that the default argument idiom already works, and that the new feature complicates the interpreter. The idiom, however, changes the signature of the function. A lambda that has been given extra parameters can be called with extra arguments by accident, and the intent is obscured. The default argument approach also fails for recursive nested functions, because the function name is not bound when the defaults are evaluated.

Another concern is that nested scopes could make it harder to understand code. The counterargument is that the rule is local and static: a reader can determine where any name is bound by examining the text, without running the program.

## Backwards compatibility

The most significant compatibility concern arises when a name that was previously resolved in the global namespace is now found in an enclosing function. For example:

```python
x = 1
def f():
    x = 2
    def g():
        print x    # 2.0: prints 1; 2.2: prints 2
    g()
```

The compiler in 2.1 detects the cases where the meaning will change, and issues a SyntaxWarning for each of them. It cannot be certain the change was unintended, so the warning is about the possibility. A programmer who wants the old meaning can rename the inner variable.

Other cases that will break are the `import *` and `exec` forms described above. Both are rare in nested functions.

The Python 2.1 implementation compiles modules with the old rules unless the `__future__` statement appears. The `symtable` module and other tools that expose scope information need to be updated, and the `compiler` package has been extended to compute free variables.

## Implementation

The compiler performs a symbol-table pass before code generation. For each function it collects the sets of local, free, and cell variables. A variable is a cell variable if it is bound in the function and referenced by a nested function. A variable is free if it is referenced but bound in an enclosing function. At runtime, a cell is a small object holding a reference to a value. When a nested function is created, the cells of its free variables are packed into a tuple and attached to the function object as `func_closure`. Accesses to cell and free variables use the new opcodes `LOAD_DEREF`, `STORE_DEREF` and `LOAD_CLOSURE`, and the function creation opcode `MAKE_CLOSURE`.

This implementation adds a small cost to function calls that involve closures. Functions without free variables are unaffected. Garbage collection of cells that are part of reference cycles is handled by the cyclic collector.

## Locked down issues

Several design questions were settled during discussion. The rule that class scopes are skipped was chosen over the alternative of making class names visible, because it keeps existing code behaving the same. The name-binding rule within a single function is unchanged. No new keyword is added. Nested scopes are the default from Python 2.2, with no way to disable them.

## Reference implementation

A patch against the Python 2.1 development tree implements the proposal. It includes changes to the compiler, the `symtable` module, the test suite, and the documentation of the language reference.
