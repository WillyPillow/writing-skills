# PEP 651: Robust Stack Overflow Handling

- Author: Mark Shannon
- Status: Rejected
- Type: Standards Track
- Created: 18-Jan-2021
- Python-Version: 3.10

## Abstract

This PEP proposes that Python should treat machine stack overflow differently from runaway recursion.

This would allow programs to set the maximum recursion depth to fit their needs and provide additional safety guarantees.

If this PEP is accepted, then the following program will run safely to completion:

```python
sys.setrecursionlimit(1_000_000)

def f(n):
    if n:
        f(n-1)

f(500_000)
```

and the following program will raise a `StackOverflow`, without causing a VM crash:

```python
sys.setrecursionlimit(1_000_000)

class X:
    def __add__(self, other):
        return self + other

X() + 1
```

## Motivation

CPython uses a single recursion depth counter to prevent both runaway recursion and C stack overflow. However, runaway recursion and growing the C stack are two different things. Counting recursion is a proxy for the thing we really care about, which is not running out of stack.

Using a single counter has several problems.

1. It prevents recursion from reaching depths that would be perfectly safe. The default limit of 1000 is conservative so that even the most stack-hungry call sequences cannot overflow. Programs that recurse deeply on small frames, such as recursive-descent parsers over deeply nested data or algorithms on long linked structures, are forced to raise the limit, and then risk a crash.
2. It cannot guarantee safety. Raising the limit to a large value turns a clean `RecursionError` into a segmentation fault when some call path consumes more C stack per level than expected. The amount of C stack used by one level of Python recursion varies widely: a pure Python function call in the interpreter loop may use a few hundred bytes, while a call through `__add__`, `__getattr__` or a C extension may use several kilobytes.
3. It is platform- and build-dependent. A limit that is safe on Linux with a debug build may crash on Windows with a release build, where stack sizes and frame sizes differ.
4. It conflates two concerns in the same exception. `RecursionError` is raised both when Python code recurses too deeply and when the C stack is nearly exhausted, though the remedies differ.

Because of these issues, the answer to "what should I set the recursion limit to?" is "no one knows", and a large number of bug reports concern crashes caused by `sys.setrecursionlimit`.

### The opportunity

Since the introduction of the new frame model, pure Python-to-Python calls need not consume C stack at all. If the interpreter evaluates a Python function called from a Python function by pushing a new frame onto a heap-allocated stack and continuing in the same C-level loop, the depth of Python recursion is limited only by memory. The C stack is only consumed by calls that pass through C code, for instance a Python function invoked by `sorted(..., key=f)` or by a special method such as `__add__`.

This suggests two separate limits:

- One for the depth of pure Python recursion, which is cheap to allow in large numbers.
- Another for the depth of C recursion, which must be small and strictly policed.

## Rationale

The PEP separates the two limits by introducing a new exception, `StackOverflow`, which is raised when the C stack is about to overflow. `RecursionError` continues to be raised when the recursion limit set via `sys.setrecursionlimit` is exceeded by pure Python calls.

Since a `StackOverflow` indicates exhaustion of a finite machine resource rather than a program error, it is a subclass of `MemoryError`, and `RecursionError` remains a subclass of `RuntimeError`.

The design keeps the user-visible API small: the existing `sys.setrecursionlimit` and `sys.getrecursionlimit` are unchanged in signature, and become simple to reason about, since the limit counts only Python-to-Python frames. The stack overflow protection is automatic and has no user-adjustable setting in the first instance.

## Specification

### Python-to-Python calls

A call from Python code to a Python function, where the call is made from the interpreter loop and the callee is a pure Python function, does not consume C stack. Such calls are counted towards the recursion limit set by `sys.setrecursionlimit`. When the count exceeds the limit, `RecursionError` is raised, as at present.

### C recursion

A call that passes through C code, whether a call to a built-in that calls back into Python, the invocation of a slot function such as `__add__` or `__getitem__`, or a C extension calling `PyObject_Call`, uses the C stack and is counted against a second counter, the C recursion depth. This is bounded by a fixed per-platform limit, chosen to be safely below the stack size of typical threads, with the actual value established at build time and tuned with a safety margin.

When the C recursion limit is exceeded, a `StackOverflow` exception is raised. The check is made in `Py_EnterRecursiveCall`, which is the existing API used by extension authors. The semantic is unchanged for them, but the exception raised will be `StackOverflow`.

### New exception

```
BaseException
 └── Exception
      ├── MemoryError
      │    └── StackOverflow
      └── RuntimeError
           └── RecursionError
```

Code catching `RecursionError` to handle runaway recursion will continue to work for pure Python recursion, but will not catch `StackOverflow`. Code catching `MemoryError` will now also catch `StackOverflow`.

### Changes to the C API

- `Py_EnterRecursiveCall` and `Py_LeaveRecursiveCall` continue to exist and are now related to the C stack counter.
- `PyErr_SetStackOverflow()` is added to raise `StackOverflow`.
- `Py_GetRecursionLimit` and `Py_SetRecursionLimit` remain and relate only to the Python limit.
- A new function `Py_GetCStackLimit()` reports the C limit for diagnostic purposes.

### Interaction with other features

**Generators and coroutines.** Resuming a generator is treated as a Python-to-Python call when done from the interpreter, so deeply nested `yield from` chains count against the Python limit and not the C stack.

**Threads.** Each thread has its own counters. The C limit is determined using the stack size of the thread where possible, since threads created with `threading.stack_size` may have a different size.

**Exception handling during overflow.** When `StackOverflow` is raised, the interpreter has little C stack left. It must be possible to unwind and run `except` and `finally` handlers. The limit incorporates a safety margin for this purpose, and the margin is not available to normal code.

## Backwards Compatibility

The change is mostly compatible, but there are observable differences.

Programs that rely on `RecursionError` being raised at a certain depth continue to see it for pure Python recursion, though the achievable depth is larger if the limit is raised. Programs that handle runaway recursion arising from special methods, such as `__getattr__` defined in terms of itself, formerly saw `RecursionError` and now see `StackOverflow`. Such programs must catch both if they wish to remain compatible with older versions.

Tests that deliberately cause infinite recursion via C code and expect `RecursionError` need updating. The standard library has a few of these.

The default recursion limit may be raised, though this is not part of the PEP. The PEP merely makes it safe to do so.

C extensions calling `Py_EnterRecursiveCall` get the new behaviour without modification. Extensions that implement their own recursion tracking continue to work, but their recursion is unprotected as before.

## Security Implications

The PEP improves security by turning potential crashes into recoverable exceptions. Stack overflow in the interpreter is a denial-of-service vector for programs that handle untrusted input, such as deeply nested JSON. With the existing system, a robust application had to keep the recursion limit low, and still might crash. With this PEP, `StackOverflow` can be caught, and applications can raise the Python limit safely for legitimate uses.

A mistake in setting the C limit could still allow overflow, so conservative defaults are important.

## Performance Impact

Two counters need to be maintained. The Python counter is already incremented per call; the C counter is incremented only on the C recursion path, which is slower anyway. Measurements with the pyperformance suite showed no measurable difference on call-heavy benchmarks. A slight improvement is expected for deep recursion because less C stack is touched.

## Implementation

The implementation depends on the interpreter evaluating Python-to-Python calls without recursion in C, which was introduced in the branch accompanying this PEP. A reference implementation is available as a pull request, passing the test suite with a handful of updated tests.

## Rejected Ideas

- **A single larger default recursion limit.** Raising the default would still crash on some platforms, and does not fix the underlying conflation.
- **Querying the actual stack usage.** Platform-specific APIs could report the remaining stack, but they are unreliable across threads and platforms, and checking on every call would be expensive.
- **A user-settable C limit.** This would let users reintroduce crashes. Keeping it internal preserves the safety guarantee.
- **Making `StackOverflow` a subclass of `RecursionError`.** This would keep old handlers working but would confuse the distinction the PEP is trying to establish.
