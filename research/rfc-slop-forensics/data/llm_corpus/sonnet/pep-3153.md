# Abstract

This PEP describes an abstraction of asynchronous IO for the Python standard library.

The goal is to reach an abstraction that can be implemented by many different asynchronous IO backends and provides a target for library developers to write code portable between those different backends.

# Rationale

People who want to write asynchronous code in Python right now have a few options:

- `asyncore` and `asynchat`
- something bespoke, built on `select` or `poll`
- a third-party framework, such as Twisted or Tornado, or an event library such as gevent or libevent bindings

`asyncore` and `asynchat` are part of the standard library but they are limited. They have a callback style that is hard to compose, they lack timers and a pluggable event loop, and their design predates many common expectations. Third-party frameworks are far more capable, but each provides its own incompatible interface. A protocol written for Twisted cannot be reused in Tornado without a rewrite, even if the protocol itself has nothing to do with either.

The result is duplication. Every framework contains its own HTTP client, its own IRC implementation, its own DNS resolver. A library author who wishes to ship a protocol implementation to the largest audience must either pick a framework and exclude everyone else, or write adapter layers for several of them.

The standard library is the natural place for a shared abstraction. Python's strength comes partly from the fact that common interfaces such as file objects, WSGI and DB-API let different implementations be swapped behind a single protocol. Asynchronous IO has no such interface. This PEP aims to supply one.

# Goals

The abstraction described here has the following goals.

1. It must be implementable by existing backends, with Twisted, Tornado and a select-based reference implementation as the primary targets.
2. It must allow protocol implementations to be independent of any particular event loop.
3. It must be small enough to be understood and implemented without extensive effort.
4. It must not require language changes.
5. It should not prescribe a single programming style, such as callbacks or coroutines, but it should be possible to build either on top of it.

Non-goals include the design of a high-level framework and the replacement of threading for CPU-bound work.

# Design overview

The design separates three concerns: the transport, which moves bytes; the protocol, which interprets them; and the event loop, which drives both.

## Transports

A transport represents a connection to some endpoint. It is responsible for reading bytes from the endpoint and delivering them to a protocol, and for taking bytes from the protocol and writing them out. A transport knows nothing about what the bytes mean. Examples include TCP sockets, UNIX sockets, pipes, SSL-wrapped connections and, in tests, an in-memory buffer.

The transport interface is small:

- `write(data)`: queue bytes for sending. It must not block.
- `writeSequence(iterable)`: queue several byte strings.
- `loseConnection()`: close the connection after all queued data is written.
- `pauseProducing()` and `resumeProducing()`: flow control.
- `getPeer()` and `getHost()`: addresses of the two endpoints.

## Protocols

A protocol is an object that handles the data received on a transport. It has callbacks that the transport calls:

- `connectionMade(transport)`: the connection is established.
- `dataReceived(data)`: some bytes arrived.
- `connectionLost(reason)`: the connection ended, either cleanly or not.

A protocol writes by calling methods on the transport it was given. Because a protocol has no knowledge of the event loop and only talks to a transport, the same protocol class can be used on any backend that supplies compliant transports.

Protocols are created by factories. A server holds a factory and calls it once per incoming connection. A client calls it once per outgoing connection.

## Event loop

The event loop is the object that waits for external events and dispatches them. This PEP specifies only the interface that transports and protocols need from it, rather than a complete reactor API:

- `callLater(delay, callable, *args)`: schedule a call.
- `callSoon(callable, *args)`: schedule a call on the next iteration.
- `run()` and `stop()`.

Backends may offer additional capabilities, such as file descriptor watching, but portable code should use only the capabilities listed here.

## Deferred results

Operations that finish later, such as resolving a name or connecting, need a way of reporting the result. This PEP defines a minimal result object, informally called a future, with these operations:

- `addCallback(fn)` and `addErrback(fn)`
- `cancel()`
- `result()`, valid only after completion

The object is deliberately minimal. Twisted's `Deferred` would be able to implement it, as would a thread-based `Future`.

# Reference implementation

The PEP proposes a reference implementation built on `select`/`poll`/`epoll`/`kqueue`, as available. It is meant primarily as a baseline for testing the specification and as a convenient default; it is not intended to compete with mature frameworks. Adapters for Twisted and Tornado should be written by the maintainers of those projects, who know best how to map their own APIs to this one.

A test suite accompanies the reference implementation. It defines the behaviour of transports and protocols precisely, including edge cases such as writing after `loseConnection()`, receiving data after `pauseProducing()`, and the order of callbacks when a connection fails.

# Interaction with threads and processes

Asynchronous code often needs to call blocking functions. The event loop should offer a method to run a callable in a thread pool and return a future for its result. Calls into the loop from other threads must go through a thread-safe entry point such as `callFromThread`. Subprocess support is out of scope for the first version but the transport interface is designed so that a pipe transport can be added later.

# Error handling

Exceptions raised in protocol callbacks must not terminate the event loop. The transport catches such exceptions, closes the connection, and passes the exception to `connectionLost`. Exceptions in scheduled calls are logged. This matches the behaviour of existing frameworks.

# Rejected alternatives

**Standardize on Twisted.** Twisted is mature, but adopting it wholesale would put a very large code base in the standard library and tie the standard library to its release cycle. It would also leave out users of other frameworks.

**Language-level coroutines first.** A syntax for coroutines would help write straight-line asynchronous code, but it would not solve the problem of incompatible backends. The abstraction proposed here is complementary: coroutine-based libraries can be written on top of transports and protocols later.

**Specify only the protocol layer.** Without a common transport interface, protocols would still need to know about the backend that creates connections, and portability would be lost.

# Open issues

- The exact names of the methods, in particular whether to follow PEP 8 conventions or the naming of existing frameworks.
- Whether the future type should be shared with `concurrent.futures`.
- How to handle timeouts uniformly.
- What guarantees to make about the ordering of callbacks across transports.
- Support for datagram protocols, which have different semantics from stream protocols.

# Backwards compatibility

The proposal adds new modules and does not alter existing ones. `asyncore` and `asynchat` remain unchanged.
