# PEP 359: The "make" Statement

- Author: Steven Bethard
- Status: Withdrawn
- Type: Standards Track
- Created: 05-Apr-2006
- Python-Version: 2.6

## Abstract

This PEP proposes a generalization of the class-declaration syntax, the `make` statement. The proposed syntax and semantics parallel the syntax for class definition, and so:

```
make <callable> <name> <tuple>:
    <block>
```

is translated into the assignment:

```
<name> = <callable>("<name>", <tuple>, <namespace>)
```

where `<namespace>` is the dict created by executing `<block>`. This is mostly syntactic sugar for:

```
class <name> <tuple>:
    __metaclass__ = <callable>
    <block>
```

and is intended to help more clearly express the intent of the statement when something other than a class is being created. Of course, other syntax for such a statement is possible, but it is hoped that by keeping a strong parallel to the class statement, an understanding of how classes and metaclasses work will translate into an understanding of how the make-statement works as well.

The PEP is based on a suggestion by Michele Simionato on the python-dev list.

## Motivation

Class statements provide two nice facilities to Python:

1. They are the standard Python means of creating a namespace. All statements within a class body are executed, and the resulting local name bindings are passed as a dict to the metaclass.
2. They encourage DRY (don't repeat yourself) by allowing the class being created to know the name it is being assigned.

Thus in a simple class statement like:

```python
class C(object):
    x = 1
    def foo(self):
        return 'bar'
```

the metaclass (`type`) gets called with the name `'C'`, the tuple of bases `(object,)` and the dict `{'x': 1, 'foo': <function foo at ...>}`.

The advantage of a class statement over the alternative of calling `type` directly is that the namespace is built with ordinary statement syntax, and the name is written once. The disadvantage is that the same syntax is now used for things that are not classes. A variety of Python programs use classes as containers for building other objects, taking advantage of the namespace semantics while ignoring the object-oriented nature of the result. Several common idioms exist:

### Properties

Properties are often defined with a class-based recipe so that getter, setter and deleter can be written as functions inside a namespace:

```python
class x:
    '''The x property.'''
    def fget(self):
        return self._x
    def fset(self, value):
        self._x = value
    def fdel(self):
        del self._x
    __metaclass__ = lambda name, bases, ns: property(**ns)
```

Here the `class` keyword is misleading, since the result `x` is a property, not a class, and the `__metaclass__` line is a hack that readers must decode.

With the make statement the same code becomes:

```python
make property x:
    '''The x property.'''
    def fget(self):
        return self._x
    def fset(self, value):
        self._x = value
    def fdel(self):
        del self._x
```

### Named tuples, enumerations and records

Similarly, a namespace of names and values can be converted into an enumeration or record:

```python
make Enum Color:
    red = 1
    green = 2
    blue = 3
```

### Hierarchical data

Programs that build XML, configuration files or GUI trees are naturally written as nested blocks. With a suitable callable, a make statement allows:

```python
make element html:
    make element body:
        make element p:
            text = 'Hello'
```

Each nested statement evaluates the inner block, calls the callable with the name and namespace, and binds the result in the enclosing namespace.

### Reading the code

In all of these examples, a reader seeing `class` expects a class, and must read to the end to learn that a different object results. The make statement puts the type of the thing created at the top.

## Specification

Python will translate a make statement:

```
make <callable> <name> <tuple>:
    <block>
```

into the assignment:

```
<name> = <callable>("<name>", <tuple>, <namespace>)
```

where `<namespace>` is the dict created by executing `<block>`. The `<tuple>` expression is optional; if omitted, an empty tuple is assumed. The `<callable>` is any expression, evaluated before the block executes.

The block is executed in a new local namespace, as for a class body. Names assigned in the block become keys of the dict. Special names `__module__` and `__doc__` are set in the same way as for classes, so a docstring in the block appears as `'__doc__'`.

The grammar change is:

```
make_stmt: 'make' test NAME [ '(' [testlist] ')' ] ':' suite
```

and `make` becomes a keyword. To limit the impact, it would be introduced via `from __future__ import make_statement` in Python 2.6 and be unconditional in 2.7 or 3.0.

### Evaluation order

1. The `<callable>` expression is evaluated.
2. The `<tuple>` expression, if given, is evaluated.
3. The block is executed in a fresh namespace.
4. The callable is invoked with `(name, tuple, namespace)`.
5. The result is bound to `<name>` in the current scope.

### Example: a simple callable

The only requirement on the callable is that it accepts three positional arguments. A `namespace` helper could be defined:

```python
class namespace(object):
    def __init__(self, name, args, kwargs):
        self.__dict__.update(kwargs)

make namespace ns:
    x = 1
    y = 2
```

after which `ns.x == 1`.

## Open Issues

Does the ``make`` keyword break too much code? Originally, the make statement used the keyword ``create`` (a suggestion due to Nick Coghlan). However, investigations into the standard library and Zope Subversion repositories suggested that ``create`` was used far more often than ``make``, so a switch was made. It is likely that ``make`` is already used in numerous programs, such as build tools, though most of those uses are in method names or attributes.

Should the make statement allow keyword arguments? The `<tuple>` may be extended to accept keyword arguments, mirroring PEP 3115 for classes in Python 3000. This would make the syntax more flexible but complicate the call.

Should the statement support decorators? A decorator for make statements would be analogous to class decorators but was not part of the original proposal.

Should the callable receive the name and tuple at all? Properties, for example, discard both. A more minimal design would pass only the namespace, but the three-argument form keeps the parallel with metaclasses exact.

## Optional Extensions

### Remove the make keyword

An alternative is to avoid a new keyword by overloading the class statement: `class property x:`. This was rejected because it would be ambiguous with base class lists.

### Allow arbitrary assignment targets

The statement could allow `make property obj.x:` binding to an attribute, or a subscript. This was dropped because the name is used as the first argument, and it is unclear what string should be passed for a dotted target.

### Provide an `__make__` protocol

Rather than calling the callable directly, the interpreter could look for a `__make__` method that receives the namespace, giving the callable more control over ordered execution. For instance, `__prepare__` in PEP 3115 lets a metaclass provide an ordered dict for the block. A comparable hook could allow ordered declarations, which matter for things like XML elements and form fields. This is left for a future PEP.

## Reference Implementation

The reference implementation is a patch to the parser and compiler that treats `make` as a keyword and compiles the statement into the same bytecode used by `class` with the metaclass replaced by the evaluated callable. It reuses `BUILD_CLASS` and adds a minimal grammar rule. The patch is small, about eighty lines of C plus tests.

## Rejected and Withdrawn

The PEP was withdrawn after discussion on python-dev. The principal objections were:

- The benefit is small, since the same effect is available with a class statement and a metaclass, a decorator, or by calling a function with a dictionary.
- A new keyword imposes cost on all code, including the tools that parse Python.
- The cases that motivated it, such as properties, were better served by decorators, which were accepted in Python 2.4 and later gained `@x.setter` in 2.6.
- Domain-specific languages built from nested blocks are better handled by context managers via the `with` statement or by explicit builder objects.

The author concluded that the status quo was acceptable and withdrew the proposal.
