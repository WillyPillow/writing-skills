PEP: 296
Title: Adding a bytes Object Type
Status: Draft
Type: Standards Track
Created: 12-Jul-2002
Python-Version: 2.3

# Abstract

This PEP proposes the creation of a new standard type and builtin constructor called `bytes`. The `bytes` object is an efficiently stored array of bytes with some additional characteristics that set it apart from several implementations that are similar.

# Rationale

Python has no clean way to represent a sequence of raw bytes. Today, programmers use one of several stand-ins, and each has drawbacks.

The `str` type is the traditional choice. A `str` is a sequence of 8-bit characters, and it is the type returned by `file.read()` in binary mode and by `socket.recv()`. But `str` is immutable, so any operation that edits a buffer in place must create a complete copy. It also doubles as the text type, so nothing in the type tells a reader or a tool whether a given value is meant to be text or binary data. When Unicode strings are mixed in, implicit conversions through the default encoding produce confusing errors, or worse, silently succeed on ASCII data and fail later on other data.

The `array` module, using typecode `'B'` or `'c'`, supplies a mutable array of bytes. However, it is not part of the core language, it has no literal syntax, it does not support the string methods that are convenient for binary protocols, and its interaction with other modules, such as `struct` and the file and socket objects, is limited and somewhat inconsistent.

A `list` of small integers is mutable and flexible, but it uses a pointer per element, which is wasteful for large buffers, and it can hold values outside the range 0-255.

The `buffer` object offers a read-only view onto another object's memory and does not own storage. The `mmap` object is a memory-mapped file.

None of these gives a programmer a single, obvious, mutable, compact type that clearly means "bytes." Network code, image and audio processing, file format parsers, cryptography and many extension modules would all benefit from one.

This PEP therefore proposes a new builtin type, `bytes`, whose purpose is to be the standard container for binary data.

# Specification

## Overview

A `bytes` object is a mutable, fixed-or-growable sequence of integers in the range 0 to 255 inclusive. Elements are stored contiguously as C `unsigned char` values, one byte per element, with no per-element object overhead.

Because a `bytes` object is mutable, it cannot be used as a dictionary key and it is not hashable.

## Constructor

The builtin `bytes` is a type and a constructor:

```python
bytes()            # an empty bytes object
bytes(10)          # ten zero bytes
bytes([1, 2, 3])   # from a sequence of integers in range(256)
bytes("abc")       # from a str; each character must have an ordinal < 256
bytes(other)       # from any object supporting the buffer interface
```

Passing a Unicode string is an error unless an encoding is also given:

```python
bytes(u"caf\xe9", "latin-1")
```

This avoids reliance on the system default encoding. A value outside the range 0-255 raises `ValueError`. A non-integer element raises `TypeError`.

## Indexing and slicing

Indexing a `bytes` object returns an integer. This differs from `str`, where indexing returns a one-character string, and is intentional: the elements of a `bytes` object are numbers, not characters.

```python
b = bytes([65, 66, 67])
b[0]       # 65
b[0:2]     # bytes([65, 66])
b[1] = 90  # allowed, object is mutable
```

Slice assignment is supported. Assigning a slice of a different length changes the length of the object, as with lists. Assigning a value outside 0-255 raises `ValueError`.

## Operations

The following operations are supported, with the semantics familiar from `str` and `list`:

- `len(b)`, `b1 + b2`, `b * n`, `x in b`, iteration (yielding integers)
- Comparison with other `bytes` objects, lexicographically by element value
- `append(x)`, `extend(iterable)`, `insert(i, x)`, `pop([i])`, `remove(x)`, `reverse()`
- `del b[i]` and `del b[i:j]`

In addition, a number of methods are borrowed from `str` where their meaning is unambiguous for binary data: `find`, `rfind`, `index`, `count`, `startswith`, `endswith`, `split`, `join`, `replace`, and `strip`. These accept `bytes` arguments only; mixing `bytes` and `str` raises `TypeError`.

Methods that depend on character semantics, such as `upper`, `lower`, `isalpha` and similar, are not provided in this version. They could be added later if a clear use case emerges.

## Conversion

`str(b)` returns a `str` with the same byte values, one character per byte. This is lossless and corresponds to the traditional use of `str` as a byte string. `unicode(b, encoding)` decodes the contents with the given encoding. The method `b.decode(encoding)` is provided as a convenience and `str.encode` and `unicode.encode` should be able to return `bytes` objects when asked.

## Buffer interface

A `bytes` object supports the buffer interface for both reading and writing. This means it can be passed directly to `file.readinto()`, `socket.recv_into()` and similar functions to avoid copying. A `bytes` object must not be resized while a buffer exported from it is in use; attempts to do so raise `BufferError`.

## Literals

This PEP does not propose new literal syntax. A prefix such as `b"abc"` could be introduced in a later PEP, once the type is accepted and its semantics settled.

# Pickling and marshalling

Instances of `bytes` support the pickle protocol. They are not supported by `marshal` in this version.

# Reference Implementation

A prototype is available as an extension module. It stores the contents in a single `malloc`ed block with an over-allocation strategy similar to that used by `list`, so that repeated `append` operations take amortized constant time. Moving it into the core requires adding the type to `Objects/` and registering it in `Python/bltinmodule.c`.

# Backward Compatibility

The name `bytes` is not currently a builtin. Code that already defines a variable or function called `bytes` will continue to work, since module-level names shadow builtins. The one exception is code that uses `from module import *` where the module exports `bytes`; that shadowing continues to apply as before.

No existing behavior of `str`, `unicode` or `array` is changed.

# Open Issues

- Should indexing return an integer or a length-one `bytes`? This PEP chooses integers because they are more useful for arithmetic and for interoperation with `struct`, but this choice breaks the analogy with `str`.
- Should `bytes` be a subclass of `str`? A subclass relationship would make `isinstance(b, str)` true and let existing code accept `bytes` where a string is expected, but at the cost of confusing mutable and immutable semantics. This PEP says no.
- Should `bytes` objects be hashable if frozen? An immutable sibling type could be added later.
- Should the fixed-length and growable cases be different types?

# Rejected Ideas

**Make `array.array('B')` a builtin.** This would be a minimal change, but `array` has a different API and a general design built around typecodes. A purpose-built type can have a cleaner interface.

**Make `str` mutable.** This would break every program that uses strings as dictionary keys.
