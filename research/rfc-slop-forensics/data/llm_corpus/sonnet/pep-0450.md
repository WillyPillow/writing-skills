# Abstract

This PEP proposes the addition of a module for common statistics functions such as mean, median, variance and standard deviation to the Python standard library. See also http://bugs.python.org/issue18606

# Rationale

The proposed statistics module is motivated by the "batteries included" philosophy towards the Python standard library. Raymond Hettinger and other senior developers have said that a quality statistics library that satisfies the needs of a large majority of users is a worthwhile addition to the standard library.

Statistics is not a niche concern. Anyone who processes data, from a teacher averaging grades to an engineer summarising benchmark timings, wants a few basic measures: the mean, the median, a measure of spread. Python's standard library currently has none of these. Users must write them by hand, which is easy to get subtly wrong, install a third-party package, or reach for something much larger than the problem requires.

NumPy and SciPy are excellent, and nothing here is intended to compete with them. But they are heavy dependencies for small scripts, they are not available in every environment, and their design targets arrays of floating point numbers and high performance rather than accuracy over a wide range of numeric types. A user who needs the mean of five `Fraction` values or a hundred `Decimal` amounts is poorly served by tools that convert everything to `float`.

## The cost of getting it wrong

The naive implementations of even the simplest statistics are problematic. The obvious variance formula, the mean of squares minus the square of the mean, suffers catastrophic cancellation when the data have a large mean and small spread, and can return negative values for a quantity that is non-negative by definition. Summation of floats in the obvious order accumulates rounding error. A programmer who is not a numerical analyst will not know to avoid these pitfalls, and the result will be wrong without any visible symptom.

A standard library implementation can invest effort in doing it correctly once.

## Why not just a third-party package?

Several packages exist on PyPI, of varying quality and maintenance. A standard module offers a common vocabulary that other code can rely on, makes examples in documentation and teaching portable, and removes the hurdle of installing a dependency for scripts that are otherwise self-contained. The scope proposed is deliberately small: it should satisfy the common needs of ordinary users and leave advanced work to specialised packages.

# Scope

The module is aimed at the level of a first course in statistics, or a scientific calculator's statistics mode. It will offer:

* averages and measures of central tendency: `mean`, `median` (with `median_low`, `median_high` and `median_grouped` variants), and `mode`;
* measures of spread: `pvariance` and `variance`, `pstdev` and `stdev` for population and sample versions respectively.

It will not offer, at least initially: hypothesis tests, probability distributions, regression, correlation, random sampling, or any multidimensional functionality. These can be added later if there is demand, and several are naturally left to dedicated libraries.

# Design

## Numeric types

The functions accept any iterable of real numbers, including `int`, `float`, `Fraction` and `Decimal`. A key design decision is that the result type follows from the input type: the mean of integers is a float, the mean of `Fraction` values is a `Fraction`, and the mean of `Decimal` values is a `Decimal`. Mixed types are coerced to the widest type present by a defined set of rules, and combinations that cannot be coerced without loss of meaning, such as `Decimal` with `float`, raise `TypeError`.

## Accuracy

Internally, sums are computed exactly using integer ratios, and conversion to the output type happens once at the end. That gives results that are correctly rounded in the common cases and removes dependence on the order of the data. This approach is slower than a plain `sum()` on floats, and the cost is accepted: the module prioritises correctness and simplicity over speed, and documents that faster alternatives exist for large arrays.

## Variance and standard deviation

Variance is calculated with a two-pass algorithm: first the mean, then the sum of squared deviations from it. This avoids cancellation. Both population (`pvariance`, `pstdev`) and sample (`variance`, `stdev`) forms are provided, with names chosen to make the distinction explicit. The sample forms require at least two data points and raise `StatisticsError` otherwise. An optional argument allows the caller to supply a precomputed mean when it is already known, which avoids a redundant pass and permits use with data that arrive in streams only once.

## Empty data and exceptions

Computing a statistic of no data is an error. The module defines `StatisticsError`, a subclass of `ValueError`, for errors of the kind "no data", "no unique mode", or "not enough data". Raising an exception rather than returning `nan` makes mistakes visible.

## Iterators

The functions accept any iterable. Where multiple passes are required, the input is first converted to a list. This is documented, and users with very large datasets are pointed to alternatives.

## Mode

`mode` returns the most common value and works on categorical, non-numeric data as well as numbers. When there is a tie for most frequent value, it raises `StatisticsError` rather than choosing arbitrarily. This behaviour was debated; some users would prefer the first or smallest value. Returning a list of modes was also considered, but it makes the common case, a single mode, awkward.

## Median

For an odd number of values, the median is the middle value; for an even number, it is the mean of the two middle values. This requires the data to support arithmetic. For data that are ordered but not numeric, the `median_low` and `median_high` variants return one of the actual data points. `median_grouped` supports interval data, interpolating within the median class.

# Discussion

## Naming and the module name

The name `statistics` is descriptive and does not collide with anything in the standard library. Several alternatives, such as `stats`, were rejected because the short form is already in common use by third-party projects, and conflicts would cause confusion.

## Namespace

Functions are exposed at module level with no classes. Alternative designs based on a `Dataset` or `Series` object were considered and rejected as more complex than the problem requires.

## Performance

The module is not intended to be fast. A quick benchmark shows it to be considerably slower than NumPy for large arrays and slower than naive pure Python for small ones, since exact arithmetic is used. The documentation says so plainly.

## Relation to other proposals

This proposal does not preclude later additions. The module is intentionally small and conservative so that it can grow in response to real needs, in the manner of other standard modules.

# Backwards compatibility

There are no compatibility concerns, as this is a new module. Third-party code with a module of the same name in an application directory takes precedence over the standard library in the usual way, but because the standard library comes later in the search path, this is only a concern for scripts that are run from the directory containing such a file.

# Reference implementation

A reference implementation, with tests and documentation, has been attached to the tracker issue listed above, written in pure Python and requiring no extension modules.
