# PEP 3127: Integer Literal Support and Syntax

- PEP: 3127
- Title: Integer Literal Support and Syntax
- Status: Final
- Type: Standards Track
- Created: 14-Mar-2007
- Python-Version: 3.0

## Abstract

This PEP proposes changes to the Python core to rationalize the treatment of string literal representations of integers in different radices (bases). These changes are targeted at Python 3.0, but the backward-compatible parts of the changes should be added to Python 2.6, so that all valid 3.0 integer literals will also be valid in 2.6.

The proposal is that:

a) octal literals must now be specified with a leading "0o" or "0O" instead of "0";

b) binary literals are now supported via a leading "0b" or "0B"; and

c) provision will be made for binary numbers in string formatting.

## Motivation

This PEP was motivated by two different issues:

- The default octal representation of integers is silently confusing to people unfamiliar with C-like languages. It is extremely easy to inadvertently create an integer object with the wrong value, because '013' means 'decimal 11', not 'decimal 13', to the Python language itself, which is not the meaning that most humans would assign to this literal.
- Some Python users have a strong desire for binary support in the language.

The first issue is a matter of pure surprise. A programmer who has been taught that leading zeros do not matter in numbers, as in dates and zip codes and every school arithmetic exercise, writes `x = 010` and gets 8. The bug can survive for a long time, since 010 is a legal integer and nothing complains. A particularly nasty form arises with columns of aligned numbers:

```python
values = [
    007,
    010,
    011,
]
```

Here the first element is 7 and the others are 8 and 9, all legal. A change to `08` or `09`, the next numbers a person might type, produces a SyntaxError that appears to have no cause, since those are not valid octal digits. The error message complains about invalid tokens, not about the radix, so users cannot easily find the reason.

The octal prefix is a heritage of C and its predecessors. In C, octal integers were a convenience for machines with 12-, 18- and 36-bit words, where groups of three bits mapped usefully onto words. They remain in use today for Unix file permission modes such as `0644`, but most other uses of octal are historical. Python borrowed the notation in its early days, together with the hexadecimal `0x` prefix, which does not have the same problem because it is unambiguous.

The second issue, binary literals, is a matter of expressiveness. Programmers working with bit fields, hardware registers, network protocols and file formats often wish to write a number as its bit pattern. Currently they must convert by hand to hexadecimal or octal, or call `int('1010', 2)`, which is a function call evaluated at run time and unusable in contexts such as default arguments that need a constant. Many other languages provide a `0b` prefix, including recent versions of C++, Java 7 proposals, Ruby, Perl, and various assemblers. While there is no pressing technical need, a literal form that matches the way programmers think about bit patterns is useful and costs little.

## Specification

### Octal literals

Octal literals are written with a leading "0o" or "0O" followed by one or more octal digits:

```python
>>> 0o17
15
>>> 0O777
511
```

The old form of octal literals, a leading "0" followed by octal digits, is a syntax error in Python 3.0. The tokenizer reports an error that explains the problem and the fix. For example:

```
SyntaxError: leading zeros in decimal integer literals are not permitted;
use an 0o prefix for octal integers
```

The literal "0" by itself, and sequences of zeros such as "00" or "000", remain legal and mean zero. This special case is to avoid breaking the common idiom of a zero constant.

The lowercase form "0o" is recommended, because a capital "O" is easily mistaken for a zero. Style guides should encourage the lowercase form, as they do for the "l" suffix in earlier versions.

### Binary literals

Binary literals are written with a leading "0b" or "0B" followed by one or more binary digits:

```python
>>> 0b1010
10
>>> 0B11111111
255
```

The result is an ordinary integer. As with the other forms, the literal has no sign; a leading "-" is the unary negation operator, so `-0b1` is `-1`.

The literal grammar for integers becomes:

```
integer        ::= decimalinteger | octinteger | hexinteger | bininteger
decimalinteger ::= nonzerodigit digit* | "0"+
octinteger     ::= "0" ("o" | "O") octdigit+
hexinteger     ::= "0" ("x" | "X") hexdigit+
bininteger     ::= "0" ("b" | "B") bindigit+
nonzerodigit   ::= "1"..."9"
octdigit       ::= "0"..."7"
bindigit       ::= "0" | "1"
```

### Built-in functions

The built-in function `oct()` returns a string with the "0o" prefix, so its output is a valid literal in the new syntax. Currently, `oct(8)` returns '010'; under this proposal it returns '0o10'. A new built-in function `bin()` is added, which returns a string with the "0b" prefix: `bin(10)` is '0b1010'. The function `hex()` is unchanged.

The built-in function `int()` accepts strings with a prefix when called with a base of 0, so `int('0o17', 0)` is 15 and `int('0b101', 0)` is 5. With base 0 the old-style '017' is interpreted as a decimal 17 in 3.0 only if there are no leading zeros before nonzero digits; otherwise a ValueError is raised, consistent with the literal syntax. With an explicit base, `int('0b101', 2)` and `int('0o17', 8)` accept the prefix matching the base, as `int('0x1f', 16)` already does.

### String formatting

The format specification of the new `format()` protocol in PEP 3101 gains a type code `b` for binary integers, in addition to `o`, `x` and `X`:

```python
>>> format(10, 'b')
'1010'
>>> '{0:#b}'.format(10)
'0b1010'
```

With the alternate form flag `#`, the output includes the prefix, as it does already for `x` and `o`. The old `%` operator is not extended with a binary code, as it is considered to be frozen. The 2.6 `str.format` method gets the same code as 3.0.

### Python 2.6 and the transition

The new forms of octal and binary literals are added to Python 2.6 in a backwards compatible fashion. In 2.6 the old form of octal literals remains valid, so existing code does not break, but it is deprecated: the `-3` command line switch causes a warning to be emitted for each old-style literal. The new forms are accepted unconditionally, so that code which is intended to work on both 2.6 and 3.0 can use `0o` consistently. The `2to3` tool converts old-style octal literals to the new form, including those in strings passed to `int` with base 0, where it can detect them statically.

The 2.6 `oct()` function keeps the old behavior, returning '010'. A compatibility alternative is offered through `format(x, 'o')`, which produces no prefix and so behaves identically in 2.6 and 3.0. Since `oct()` changes only in 3.0, `2to3` leaves calls to it alone, and a note in the porting guide describes the change in output.

## Rationale

Several alternatives to the `0o` prefix were considered.

One was to leave things alone. This is the zero-cost option, and many Python programmers are comfortable with C-style octal. The objection is the persistent trap for newcomers. Python 3 is an opportunity to remove such things, and the occasion is unlikely to recur.

Another was to use a different prefix, such as "0c" for octal, which has some precedent. The "0o" form is consistent with "0x" and "0b", is used in other languages, including ML, and Perl later added it. A "0c" prefix is not as widely used, and a lowercase "c" is easy to confuse with other characters in some fonts. The capital "0O" is accepted for symmetry, though discouraged.

Others suggested an `o` suffix or a function, `Oct('17')`. Suffixes have been used for long integers in Python 2 and are hard to read; function-style constants are not constant for the compiler.

A broader proposal to allow arbitrary radices through a syntax such as `8r17` was considered, but is more general than needed, and in practice nobody uses radices other than 2, 8, 10 and 16.

As for whether a leading zero in a decimal should be permitted, as in `007` meaning 7, the proposal forbids it. Allowing it would invite the same confusion in the opposite direction, as users reading code from other languages see 010 as 8 or 10. Rejecting the form outright, with an informative message, is clearer for everyone.

## Backwards compatibility

In Python 3.0 the old octal literals are an error. For code that is being ported, this is a visible failure rather than a silent change of value, which is the safer behavior. The `2to3` conversion tool handles the common case. The change to `oct()` affects code that generates literals or parses its output, and must be updated by hand where it matters, as with code that builds file mode strings.

Code that uses `os.chmod(path, 0755)` in the old form is the most common victim; after conversion, `0o755` works in 2.6 and 3.0 alike.

## Reference implementation

A patch for the tokenizer, the `int` conversion, and the formatting module is provided in the tracker. It changes the scanning of numeric literals in `Parser/tokenizer.c`, adds `bin()` to the built-in functions, and extends the `format` specification parser with the `b` code. Tests cover valid and invalid literals in all radices, including edge cases such as `0b`, `0o8` and `0_0`, which are errors.
