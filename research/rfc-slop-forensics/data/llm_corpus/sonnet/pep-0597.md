# PEP 597: Add optional EncodingWarning

- **Status:** Draft
- **Type:** Standards Track
- **Created:** 12-Jun-2019
- **Python-Version:** 3.10

## Abstract

Add a new warning category `EncodingWarning`. It is emitted when the `encoding` argument to `open()` is omitted and the default locale-specific encoding is used.

The warning is disabled by default. A new `-X warn_default_encoding` command-line option and a new `PYTHONWARNDEFAULTENCODING` environment variable can be used to enable it.

A `"locale"` argument value for `encoding` is added too. It explicitly specifies that the locale encoding should be used, silencing the warning.

## Motivation

### Using the default encoding is a common mistake

Developers using macOS or Linux may forget that the default encoding is not always UTF-8. Consider a script that reads a UTF-8 file:

    with open("data.txt") as f:
        text = f.read()

On a developer's machine, where the locale is `en_US.UTF-8`, this works. On a Windows machine, where the default encoding is a legacy ANSI code page such as cp1252 or cp932, it can raise `UnicodeDecodeError` or, worse, silently produce garbled text. The same applies to a Linux container with the `C` or `POSIX` locale. The failure appears far from the cause, often in somebody else's environment.

The Python documentation says that the default encoding is platform dependent, but the call site gives no hint. Static analyzers and linters can flag calls to `open()` without `encoding`, but only for code which they can see. They cannot see the third-party packages in site-packages or code in the standard library that calls `open()` indirectly.

### Changing the default is difficult

It has been suggested that the default encoding be changed to UTF-8 on all platforms. That would be the simplest fix in the long term, and the language is moving that way (see PEP 540 for the UTF-8 mode). However, changing the default suddenly would break programs that rely on the locale encoding, for example those reading files created by other legacy applications on the same system. Before a default can be changed, the developer community needs a way to find all affected call sites.

The opt-in warning offers that: it is a diagnostic tool which makes the dependence visible without changing behavior.

### Why a warning and not a lint rule

A dedicated runtime warning has several advantages.

- It covers all code executed, including third-party packages, generated code and the standard library.
- It reports the actual location of the call by the usual warnings machinery, with `stacklevel` set so the warning points at the line that called `open()`, not at the internals of the `io` module.
- It integrates with the existing filters: `-W error::EncodingWarning` turns the warning into an exception, which is convenient in test suites and continuous integration.

## Specification

### `EncodingWarning`

A new warning category `EncodingWarning` is added to the built-in exceptions. It is a subclass of `Warning`.

### Emitting the warning

When the `encoding` argument is omitted (or is `None`) in a call to one of the following, and the warning is enabled, an `EncodingWarning` is emitted:

- `open()` and `io.open()` in text mode;
- `io.TextIOWrapper`;
- `pathlib.Path.open()`, `read_text()` and `write_text()`;
- `subprocess` functions when text mode is requested without an encoding;
- `locale.getpreferredencoding()` when called with `do_setlocale` and no explicit request.

The warning is not emitted for binary mode, because no encoding is involved. It is not emitted when `encoding` is passed explicitly, including when it is passed as `"utf-8"`, or `"locale"` as defined below.

The message is:

    EncodingWarning: 'encoding' argument not specified

### Enabling the warning

The warning is ignored by default, to avoid noise for users who cannot act on it. It can be enabled in three ways:

- the command-line option `-X warn_default_encoding`;
- the environment variable `PYTHONWARNDEFAULTENCODING`, if set to a non-empty string;
- the standard `-W` machinery and `warnings.simplefilter`, in conjunction with one of the above, since the check is made only when the interpreter has been told to track it. The cost of the check is negligible when the option is off.

The flag is exposed as `sys.flags.warn_default_encoding`, and also in `sys._xoptions`.

### The `"locale"` encoding

A new special encoding name `"locale"` is added. Passing `encoding="locale"` means "use the locale encoding", the same as the default behavior, but without triggering the warning. It tells readers and tools that the author has made a deliberate choice.

    with open("legacy.txt", encoding="locale") as f:
        ...

The name is recognized by `open()`, `io.TextIOWrapper`, and the other functions listed above. It is not registered in the codec registry as a general codec: `"locale".encode(...)` is not a feature, and `codecs.lookup("locale")` raises `LookupError`. This keeps the scope limited. The alias is processed by the text I/O layer, which resolves it to `locale.getpreferredencoding(False)`.

Code that must run on versions of Python without this feature cannot use `"locale"`. For compatibility with older versions, the recommended pattern is to pass `encoding=None` explicitly, which does not trigger the warning, or to use an explicit encoding.

### Stack level

For functions implemented in Python (for example `pathlib`), the warning uses `stacklevel` so that it points to the caller of the public function. For functions implemented in C, the call location is determined from the current frame.

## Backwards Compatibility

The warning is off by default, so existing programs behave identically. Programs that run with `-W error` are unaffected unless the option is enabled as well. Third-party test runners that turn all warnings into errors will see failures only if they also enable the new flag.

The `"locale"` encoding name was previously a `LookupError`, so no valid program changes meaning, except for an unlikely custom codec registered under that name; in that event, the custom codec is shadowed in the text I/O layer.

## Security Implications

None. The warning exposes information only through the standard warnings mechanism. If anything, the PEP improves security by making it easier to find places where untrusted data may be misdecoded.

## How to Teach This

For new users, the guidance is simple: always pass `encoding="utf-8"` to `open()` unless you know otherwise. The documentation of `open()` is updated to say so prominently, and the tutorial's examples are updated to include the argument.

For maintainers of larger code bases, the recommended workflow is:

1. Run the test suite with `python -X warn_default_encoding -W error::EncodingWarning`.
2. Fix each reported call by passing an explicit encoding, or `"locale"` where the platform encoding is intentionally used.
3. Keep the flag enabled in continuous integration to prevent regressions.

## Rejected Ideas

### Enable the warning by default

This would result in a flood of warnings in code that cannot be modified by the user, such as dependencies. A warning that cannot be acted upon trains users to ignore warnings.

### Make UTF-8 the default now

Beyond the compatibility problem noted above, this should be decided separately, after the community has had time to use the warning.

### Emit `DeprecationWarning`

A deprecation warning implies that the behavior will be removed. That has not been decided, and `EncodingWarning` leaves the future open.

### Emit the warning only on Windows

The problem is not unique to Windows. Linux in a minimal container and macOS with unusual locales are affected too.

## Reference Implementation

The implementation changes `Modules/_io`, `Lib/_pyio.py`, `Lib/subprocess.py` and `Lib/pathlib.py`, adds the exception to `Objects/exceptions.c`, and extends the command-line parsing. Tests cover each entry point with the flag on and off.
