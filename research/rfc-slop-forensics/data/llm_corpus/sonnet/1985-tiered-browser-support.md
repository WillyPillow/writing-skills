# RFC 1985: Tiered Browser Support

- Feature Name: `tiered_browser_support`
- Start Date: 2017-05-07
- RFC PR: rust-lang/rfcs#1985
- Rust Issue: N/A

## Summary

Official web content produced by the Rust teams for consumption by Rust users should work in the majority of browsers that Rust users are visiting these sites in. The Rust compiler only supports [a finite number of targets][forge], with varying degrees of support, due to the limits on time, expertise, and testing resources. Similarly, we don't have enough time, expertise and testing resources to be sure that our web content works in every version of every browser. We should have a list of browsers and versions in various tiers of support.

[forge]: https://forge.rust-lang.org/platform-support.html

## Motivation

The Rust project publishes a growing amount of web content: the main website, the documentation books, the API documentation generated by `rustdoc`, the playground, crates.io, and the blog. Each is written and maintained by different people, often volunteers, and each has quietly made its own decisions about which browsers to care about. Those decisions are rarely written down.

This produces predictable problems.

First, contributors cannot tell what is expected of them. A pull request that uses a CSS feature or a JavaScript API may be accepted by one reviewer and challenged by another. When an issue arrives reading "the search box does not work in my browser," the maintainers have no policy to consult, and the answer depends on who happens to read the issue.

Second, users cannot tell what to expect. Someone reading the book on an older tablet, or on a locked-down corporate machine, has no way of knowing whether a broken page is a bug or an unsupported configuration.

Third, the effort is unbounded. Without a defined set of browsers, the only safe goal is "everything," which is unachievable. Some of the browsers still found in use are over a decade old and lack features that modern sites take for granted. Supporting them would hold back the content for everyone else.

The compiler team solved the analogous problem with target tiers: a published list in which each target has a defined level of guarantee. Tier 1 targets are tested on every change and are guaranteed to work. Tier 2 targets are built but not fully tested. Tier 3 targets are accepted but unsupported. The idea transfers directly to browsers.

## Detailed design

### Tiers

This RFC defines three tiers of browser support for official Rust web content.

**Tier 1: Guaranteed to work.** The content must function correctly, including all interactive features, and must look as intended. Regressions in Tier 1 browsers are treated as bugs and may block a release of the affected site. Contributors are expected to test changes in these browsers, and where possible automated tests run against them.

**Tier 2: Expected to work.** The content should be usable and readable, and all essential tasks must be possible. Cosmetic differences are acceptable, and some non-essential interactive features may degrade. Bug reports are accepted and fixed when practical, but they do not block releases.

**Tier 3: Best effort.** The content is not tested against these browsers. Patches that improve compatibility are welcome as long as they do not add significant complexity or harm the experience in higher tiers. Bugs reported only in Tier 3 browsers may be closed with a pointer to this policy.

Browsers that appear in no tier are unsupported. Content is expected to remain readable as plain HTML, since much of it is statically generated, but nothing else is promised.

### Initial lists

The initial lists are proposed below. They are meant as a starting point and are to be revised using the process described in the next section.

Tier 1:

- the current stable release of Firefox, Chrome, Safari, and Edge;
- the current stable release of the default mobile browser on iOS and on Android.

Tier 2:

- the previous two major releases of each Tier 1 browser;
- the Firefox Extended Support Release.

Tier 3:

- Internet Explorer 11;
- other browsers based on the same engines as the Tier 1 browsers, such as Opera and Brave.

Browsers older than the above, including all earlier versions of Internet Explorer, are unsupported.

Each tier is defined in terms of the *current* release, so the list rolls forward automatically as new versions ship. No RFC is needed to move from one Chrome release to the next.

### Content covered

The policy applies to web content that the Rust teams produce and host for Rust users:

- www.rust-lang.org and its subpages;
- the documentation books and the standard library documentation;
- output from `rustdoc` as shipped with the compiler, including its search and its interactive features;
- the playground;
- crates.io and docs.rs;
- the official blog.

It does not apply to third-party sites, to the generated documentation of arbitrary crates beyond what `rustdoc` itself controls, or to experiments clearly labeled as such.

### Progressive enhancement

To keep the cost low, the policy is paired with a recommended technique. Content should be written so that the essential parts work with the least capable browser and the interactive features are layered on top. Reading a page, following links, and copying code should work without scripting at all. Features like search, the playground's run button, and the theme switcher may require JavaScript, and may require a Tier 1 or Tier 2 browser.

Feature detection is preferred over browser detection. Sites should not sniff user agent strings. They should test whether a capability is available and fall back when it is not.

### Measuring and revising

The tiers should be informed by data, not by guesswork. The teams that already collect aggregate, privacy-respecting statistics on visits, such as server logs without personal identifiers, should share the browser share data with the teams responsible for content once per release cycle. A browser or version that makes up more than a small threshold of visits, say five percent, is a candidate for promotion. One that has fallen to a negligible share, say under one percent for two consecutive quarters, is a candidate for demotion.

Changes to the lists, other than the automatic rolling of "current" and "previous" releases, are proposed as pull requests to a document in the forge repository and approved by the relevant teams. They are announced on the internals forum. An RFC is only required if the structure of the tiers themselves is to change.

### Documentation

The policy and the current lists are published alongside the compiler's platform support page. Each site links to the policy from its footer or contributor guide. The issue templates for the web repositories ask reporters to state their browser and version and point out that the answer determines how the issue is triaged.

## Drawbacks

A formal policy creates a document that must be maintained. If it falls out of date, it is worse than having no policy at all, since it misleads contributors and users.

Declaring a browser unsupported can alienate users who have no choice about what they use, such as people on older hardware or in organizations with strict controls. The progressive enhancement guidance is intended to soften this, and the policy does not forbid anyone from fixing a problem for an older browser.

There is a risk that Tier 1 testing requirements discourage drive-by contributors, who may not have access to every listed browser. Automated cross-browser testing and a clear statement that reviewers will test on the contributor's behalf if necessary can reduce this barrier.

## Alternatives

**Do nothing.** Decisions continue to be made ad hoc. This is cheap in the short run and costly in the long run.

**Support only the latest browsers.** This is the simplest policy, and it makes development easier. It leaves out a significant number of users, especially on mobile devices that no longer receive updates.

**Support everything the site has ever supported.** This guarantees there are no regressions but freezes the site's technology at a point many years behind.

**One policy per site.** Each team defines its own list. This respects local differences but gives users an inconsistent experience and multiplies the effort of writing and maintaining policies.

## Unresolved questions

What should the threshold for promotion and demotion be, and is quarterly data enough to measure it? Should accessibility tools, such as screen readers paired with specific browsers, be listed as a separate dimension? How should the policy treat browsers on platforms with unusual constraints, such as text-mode browsers or e-readers? These questions can be settled in the first revision of the lists rather than by this RFC.
