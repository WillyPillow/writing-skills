# Abstract

This PEP proposes the addition of an `isclose()` function to the standard library math module that determines whether one value is approximately equal or "close" to another value.

# Rationale

Floating point values contain limited precision, which results in their being unable to exactly represent some values, and in error accumulating with repeated computation. As a result, it is common advice to only use an equality comparison in very specific situations. Often an inequality comparison fits the bill, but there are times (often in testing) where the programmer wants to determine whether a computed value is "close" to an expected value, without requiring them to be exactly equal. This is common enough, particularly in testing, and not always obvious how to do, so it would be a useful addition to the standard library.

Existing Implementations
------------------------

The standard library contains some approximate comparison facilities already. The `unittest` module has `assertAlmostEqual`, which compares two values by checking that the difference rounded to a given number of decimal places is zero. This is an absolute-tolerance test, expressed in decimal places, and it is awkward when the values being compared are very large or very small.

Outside the standard library, `numpy` provides `allclose()` and `isclose()`, which use a combination of relative and absolute tolerance. Many other projects, including testing frameworks and scientific libraries in a number of languages, have their own implementations, each with slightly different conventions about which value the relative tolerance is measured against and how zero is handled. This diversity is itself a reason for providing a single, carefully specified version.

Proposed Implementation
-----------------------

The proposed function is:

    math.isclose(a, b, *, rel_tol=1e-9, abs_tol=0.0)

It returns `True` if `a` and `b` are close to each other, and `False` otherwise. Closeness is determined by the relative tolerance, the absolute tolerance, or both.

The relative tolerance is the maximum allowed difference between `a` and `b`, relative to the larger of the absolute values of `a` and `b`. For example, to set a tolerance of 5%, pass `rel_tol=0.05`. The default tolerance is `1e-9`, which assures that the two values are the same within about 9 decimal digits. `rel_tol` must be greater than zero.

The absolute tolerance is a minimum absolute tolerance, useful for comparisons near zero. `abs_tol` must be at least zero.

If the difference is less than either tolerance, the values are considered close. In other words:

    abs(a - b) <= max(rel_tol * max(abs(a), abs(b)), abs_tol)

NaN is never close to anything, including itself. Infinity is close only to itself with the same sign. If either tolerance is negative, `ValueError` is raised. The function is symmetric in its two arguments in the sense that `isclose(a, b)` equals `isclose(b, a)`.

Discussion of the Design
------------------------

Which value is the reference?

A relative tolerance must be measured against some value. In many contexts there is a natural "expected" value, and the tolerance is relative to that. For example, "is the computed result within 1% of the known answer?" However, making the function asymmetric has costs. The result would depend on argument order, which is surprising in a function named for a symmetric relationship, and users could not ignore which is which. Using the larger of the two magnitudes makes the test symmetric and slightly more lenient than using the smaller. When the tolerance is small, as it is by default, the difference between the choices is negligible.

Several other definitions were considered:

- Relative to the first argument. Simple, but asymmetric.
- Relative to the smaller magnitude. Symmetric and the strictest option, but it makes the test fail on values that most people would regard as equal at a given tolerance if one of them is slightly smaller.
- Relative to the average. Symmetric, and nearly equal to the max version for close values, but it requires computing a sum that could overflow for large values.
- Relative to the larger magnitude. Symmetric, cheap, and robust against overflow. This is the one chosen.

Zero

By definition no non-zero value is within a relative tolerance of zero: `abs(a - 0) <= rel_tol * max(abs(a), 0)` implies `abs(a) <= rel_tol * abs(a)`, which is false for any `rel_tol < 1`. So, if either value is zero, a relative-only test degenerates to exact equality, which is not useful. This is the reason for the `abs_tol` argument. The default for `abs_tol` is `0.0`, which means that a comparison with zero is exact by default. The alternatives are to choose a nonzero default, or to require the user to choose one. A nonzero default would silently make small numbers equal to zero, which is wrong for computations in units where numbers of order 1e-12 are meaningful. The meaning of "small" depends entirely on the problem, so the function leaves it to the user. The documentation will include a clear explanation of this case.

Default tolerance

The default relative tolerance of `1e-9` is intended to be strict enough to catch real differences while permitting the kind of accumulated rounding error one expects from a modest number of operations on 64-bit floats, which have about 15 to 16 significant decimal digits. It is not a one-size-fits-all choice, and users are encouraged to specify an appropriate value for their problem.

Behaviour on other types

The function is written for floats, but it will accept any numeric type that supports conversion to float, or can be handled by the arithmetic in the formula. In particular, integers are accepted, and `Decimal` and `Fraction` are supported if the tolerances are of a compatible type. Complex numbers are addressed separately: the function is not defined for them in this PEP, and they raise `TypeError`. A `cmath.isclose` version using the magnitude of the difference is a natural extension, and is provided for convenience.

Why not a method of float

A free function in `math` fits the existing library layout and is available for all numeric types.

Why not fold it into `==`

Changing the semantics of `==` for floats is out of the question. It would break existing programs and make equality non-transitive.

Backward compatibility
----------------------

This is a new function and does not affect existing code.

Reference Implementation
------------------------

A pure Python implementation consistent with the above:

    def isclose(a, b, *, rel_tol=1e-9, abs_tol=0.0):
        if rel_tol < 0.0 or abs_tol < 0.0:
            raise ValueError('tolerances must be non-negative')
        if a == b:
            return True
        if math.isinf(a) or math.isinf(b):
            return False
        diff = abs(b - a)
        return (diff <= abs(rel_tol * b) or diff <= abs(rel_tol * a)
                or diff <= abs_tol)

The early test for equality handles infinities of the same sign. NaN fails every comparison and so falls through to a `False` result. The two-sided form of the relative test is equivalent to comparing against the larger magnitude. A C version is provided for speed and to avoid overflow in intermediate values.

Open issues
-----------

- Whether `isclose` should be added to `cmath` in the same change. The consensus so far is to include it.
- Whether the default `abs_tol` should be nonzero. The discussion concluded that zero is the right default given its failure modes.
- Whether to add a related `assertIsClose` to `unittest`. This can be considered later.
