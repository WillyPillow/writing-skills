PEP: 616
Title: String methods to remove prefixes and suffixes
Status: Draft
Type: Standards Track
Created: 19-Mar-2020
Python-Version: 3.9

# Abstract

This is a proposal to add two new methods, `removeprefix()` and `removesuffix()`, to the APIs of Python's various string objects. These methods would remove a prefix or suffix (respectively) from a string, if present, and would be added to Unicode `str` objects, binary `bytes` and `bytearray` objects, and `collections.UserString`.

# Rationale

There have been repeated issues on Python-Ideas, Stack Overflow, and bugs.python.org where users misunderstand `str.lstrip()` and `str.rstrip()`. These methods take a string argument, but interpret it as a set of characters to strip, not a literal prefix or suffix. A user who writes `"example.py".rstrip(".py")` expecting `"example"` instead gets `"example"` only by luck, whereas `"happy.py".rstrip(".py")` returns `"ha"`, since `p`, `y`, and `.` are all in the set and `p` precedes `y` in `"happy"`. This is a well-known source of silent bugs.

Meanwhile, the need to remove a known prefix or suffix is extremely common. Examples include stripping `"https://"` from URLs, removing `.txt` from file names, removing a leading `"test_"` from function names, or dropping a trailing newline marker. The idiom Python programmers actually use is:

```python
if s.startswith(prefix):
    s = s[len(prefix):]
```

This takes two lines and repeats the variable and the prefix. A common bug is to forget the `startswith` check and always slice, silently corrupting strings that don't begin with the prefix. Another is to compute the length by hand with a magic number, which falls out of sync when the prefix changes. For suffixes there is an additional trap: `s[:-len(suffix)]` returns an empty string when `suffix` is empty, instead of `s`.

A single method with a clear name addresses all of these. The proposal is not new in the wider ecosystem: many other languages and libraries provide equivalents, and a large number of Python projects define their own helper function with this behavior. A survey of the standard library found over fifty places where the idiom above was written out by hand, in modules ranging from `ast` to `zipfile`; refactoring these to use the new methods makes each of them shorter and more readable.

# Specification

The builtin `str` class will gain two new methods which will behave as follows when `type(self) is type(prefix) is str`:

```python
def removeprefix(self: str, prefix: str, /) -> str:
    if self.startswith(prefix):
        return self[len(prefix):]
    else:
        return self[:]

def removesuffix(self: str, suffix: str, /) -> str:
    # suffix='' should not call self[:-0].
    if suffix and self.endswith(suffix):
        return self[:-len(suffix)]
    else:
        return self[:]
```

When the arguments are instances of `str` subclasses, the methods should behave as though those arguments were first coerced to base `str` objects, and the return value should always be a base `str`.

Methods with the corresponding semantics will be added to the builtin `bytes` and `bytearray` objects. If `b` is either a `bytes` or `bytearray` object, then `b.removeprefix()` and `b.removesuffix()` will accept any bytes-like object as an argument. The two methods will also be added to `collections.UserString`, with similar behavior.

Both methods return the original string unchanged when the prefix or suffix is absent. Because `str` is immutable, returning `self` (or an equal copy) is permitted; code should not rely on object identity. For `bytearray`, which is mutable, a new `bytearray` is always returned, never the same object.

Passing a tuple of prefixes, as `startswith` allows, is not supported by this proposal. See Rejected Ideas.

# Motivating examples from the Python standard library

The examples below demonstrate how the proposed methods can make code one or two lines shorter and more readable, and in some cases remove latent bugs.

## `find_recursionlimit.py`

Current:

```python
if test_func_name.startswith("test_"):
    print(test_func_name[5:])
else:
    print(test_func_name)
```

Improved:

```python
print(test_func_name.removeprefix("test_"))
```

## `deccheck.py`

This is an interesting case because the author chose to use the `str.replace` method in a place where it is almost always, but not always, correct:

Current:

```python
if funcname.startswith("context."):
    self.funcname = funcname.replace("context.", "")
    self.contextfunc = True
else:
    self.funcname = funcname
    self.contextfunc = False
```

Improved:

```python
self.contextfunc = funcname.startswith("context.")
self.funcname = funcname.removeprefix("context.")
```

The original would also have deleted the substring if it occurred in the middle of the name, which is not the intent.

## `cookiejar.py`

Current:

```python
def strip_quotes(text):
    if text.startswith('"'):
        text = text[1:]
    if text.endswith('"'):
        text = text[:-1]
    return text
```

Improved:

```python
def strip_quotes(text):
    return text.removeprefix('"').removesuffix('"')
```

# Rejected Ideas

## More than one prefix or suffix

Some users suggested accepting a tuple, mirroring `startswith` and `endswith`. When several prefixes match, the choice of which to remove (the longest, the shortest, the first) is ambiguous, and each choice is surprising to someone. Users who need multiple prefixes can compose calls or write a small loop. This could be added later without breaking compatibility.

## Re-using `strip`

Changing `lstrip` and `rstrip` to treat their argument as a prefix or suffix would silently change the behavior of existing programs. It is not possible.

## Other names

Names such as `cutprefix`, `trimprefix` (as in Go), `delprefix`, and `stripprefix` were considered. `removeprefix` was preferred because "remove" is the term used by `list.remove` and `set.remove` and does not suggest character-set semantics the way "strip" or "trim" do, and the existing `remove*` family does not imply in-place mutation of immutable strings any more than `str.replace` does.

## A boolean-returning variant

A variant that also reports whether anything was removed was suggested. It would complicate the common case, and users can compare lengths if they need to know.

# Backwards Compatibility

The proposal adds new methods only. Subclasses of `str`, `bytes` or `bytearray` that already define methods with these names will continue to work, with their own definitions taking precedence. Third-party code that monkey-patches those names onto builtins is not possible because the builtins are immutable.

Code that supports older Python versions must continue to use the slicing idiom or a helper, but the behavior of a helper can be implemented in a few lines, as shown in the specification, and conditionally replaced by the builtin when available.

# Reference Implementation

A reference implementation is available as a pull request against CPython. It adds the methods to `Objects/unicodeobject.c` and `Objects/bytes_methods.c`, along with documentation and tests covering empty arguments, matching and non-matching cases, subclass arguments, and type errors on mixed `str` and `bytes` use.
