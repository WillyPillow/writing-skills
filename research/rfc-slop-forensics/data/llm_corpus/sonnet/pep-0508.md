# PEP 508: Dependency specification for Python Software Packages

- **Status:** Draft
- **Type:** Standards Track
- **Created:** 11-Nov-2015
- **Replaces:** PEP 345 (Requires-Dist)

## Abstract

This PEP specifies the language used to describe dependencies for packages. It draws a border at the edge of describing a single dependency - the different sorts of dependencies and when they should be installed is a higher level problem. The intent is to provide a building block for higher layer specifications.

The job of a dependency is to enable tools like pip [#pip]_ to find the right package to install. Sometimes this is very loose - just specifying a name, and sometimes very specific - referring to a specific file to install. Sometimes dependencies are only relevant in one platform, or only some versions are acceptable, so the language permits describing all these cases.

The language defined is a compact line based format which is already in widespread use in pip requirements files, though we do not specify the command line option handling that those files permit. There is one caveat - the URL reference form, specified in PEP 440 is not actually implemented in pip, but since PEP 440 is accepted, we use that format rather than pip's current native format.

## Motivation

Any tool that installs Python packages needs to understand what a package needs. Over the years several overlapping notations have developed: the `install_requires` argument to setuptools, the `Requires-Dist` metadata field of PEP 345, and the lines of a pip requirements file. They agree on the simple cases (`requests`, `requests>=2.0`) and diverge in the harder ones, such as extras, environment-dependent requirements, and direct references to a URL.

This divergence has practical costs. A tool that reads metadata from a built distribution must parse one flavor; a tool that reads a requirements file must parse another; and a tool that generates metadata has to produce text that every consumer accepts. Edge cases like whitespace, quoting, and operator precedence have been handled differently by each. Bugs filed against one tool are not fixed in another, and users cannot tell what is guaranteed.

A precise grammar settles the matter. With a single reference specification, tools can share parsers, test suites can be shared, and packaging authors can know that what they write will be read the same way everywhere.

## Specification

### Overview

A dependency specification is a single line (a string without newlines) of the following shape:

    name [extras] [version-specifier | @ url] [; marker]

Everything but the name is optional. Examples:

    requests
    requests [security,tests] >= 2.8.1, == 2.8.*
    pip @ https://github.com/pypa/pip/archive/1.3.1.zip
    argparse; python_version < '2.7'

### Names

A name consists of ASCII letters, digits, `-`, `_`, and `.`, beginning and ending with a letter or digit. Names are case-insensitive. Comparison of names SHOULD normalize by lowercasing and replacing any run of `-`, `_`, `.` with a single `-`, as defined by PEP 503.

### Extras

Extras are optional features of a package, each of which may pull in additional dependencies. They are written in square brackets after the name, separated by commas:

    name [fred,bar]

Whitespace around the brackets and commas is ignored. Extra names follow the same character rules as package names. An extra that the package does not define is not an error at the parsing level; a tool decides how to treat it at install time, usually with a warning.

### Versions

Version specifiers follow PEP 440. A version specification is a comma-separated list of clauses, each of which is a comparison operator and a version:

    name >= 1.0, != 1.3.2, < 2

The operators are `<`, `<=`, `!=`, `==`, `>=`, `>`, `~=`, and `===`. All clauses must be satisfied for a version to match; the comma means "and". Parentheses around the entire version specification are permitted for compatibility with the older `Requires-Dist` syntax:

    name (>= 1.0, < 2)

New metadata SHOULD NOT use parentheses; parsers MUST accept them.

### Environment markers

A marker follows a semicolon and states a condition under which the requirement applies:

    name ; python_version < '3.4' and sys_platform == 'win32'

A marker is a boolean expression made from comparisons, `and`, `or`, `not`-free grouping with parentheses, and the following variables:

| Marker                   | Python equivalent                        |
| ------------------------ | ---------------------------------------- |
| `os_name`                | `os.name`                                |
| `sys_platform`           | `sys.platform`                           |
| `platform_machine`       | `platform.machine()`                     |
| `platform_python_implementation` | `platform.python_implementation()` |
| `platform_release`       | `platform.release()`                     |
| `platform_system`        | `platform.system()`                      |
| `platform_version`       | `platform.version()`                     |
| `python_version`         | `'.'.join(platform.python_version_tuple()[:2])` |
| `python_full_version`    | `platform.python_version()`              |
| `implementation_name`    | `sys.implementation.name`                |
| `implementation_version` | derived from `sys.implementation.version` |
| `extra`                  | an extra name being evaluated            |

Comparison operators are the same as for versions, plus `in` and `not in` for substring tests. Strings may be single- or double-quoted. A comparison may place the variable on either side.

Operators on the marker variables `python_version`, `python_full_version`, `implementation_version` use PEP 440 version comparison semantics when both sides parse as versions. For all other variables and in all other cases, comparison is plain string comparison. `and` binds tighter than `or`, and parentheses override.

The `extra` marker is evaluated against the extra being requested. A requirement written

    pytest; extra == 'test'

applies only when the extra `test` of the containing package was asked for. This is how packages express which of their dependencies belong to which extra.

### URL references

A requirement may name a direct reference instead of a version:

    name @ https://example.com/name-1.0.zip

The `@` separates the name from the URL; whitespace around it is optional but required before the URL when followed by a marker, so that the semicolon terminating the URL is unambiguous:

    name @ https://example.com/name-1.0.zip ; python_version >= '3.4'

A URL requirement and a version specifier cannot both appear in one requirement, since the URL already identifies the exact artifact. Tools SHOULD check that the downloaded artifact has the stated name.

### Grammar

The specification is given in a parsing expression grammar, here abridged:

    wsp           = ' ' | '\t'
    letter_or_digit = [A-Za-z0-9]
    identifier    = letter_or_digit ( [-_.]* letter_or_digit )*
    name          = identifier
    extras        = '[' wsp* ( identifier ( wsp* ',' wsp* identifier )* )? wsp* ']'
    version_cmp   = wsp* ( '<=' | '<' | '!=' | '==' | '>=' | '>' | '~=' | '===' )
    version       = wsp* ( letter_or_digit | [-_.*+!] )+
    version_one   = version_cmp version wsp*
    version_many  = version_one ( wsp* ',' version_one )*
    versionspec   = '(' version_many ')' | version_many
    urlspec       = '@' wsp* URI_reference
    marker_op     = version_cmp | 'in' | 'not' wsp+ 'in'
    marker_expr   = marker_var wsp* marker_op wsp* marker_var | '(' wsp* marker wsp* ')'
    marker        = marker_expr ( wsp* ( 'and' | 'or' ) wsp* marker_expr )*
    quoted_marker = ';' wsp* marker
    name_req      = name wsp* extras? wsp* versionspec? wsp* quoted_marker?
    url_req       = name wsp* extras? wsp* urlspec wsp+ quoted_marker?
    specification = wsp* ( url_req | name_req ) wsp*

Parsers MAY accept more than this, but MUST accept everything the grammar produces.

### Evaluating markers

To evaluate a marker, a tool substitutes each variable with its value in the target environment, performs each comparison, and combines the results. For installation the target environment is usually the interpreter in use; for lock file generation it may be a different one. Tools therefore MUST allow the environment to be supplied explicitly.

## Backwards Compatibility

Almost every requirement that was valid under PEP 345 remains valid. The new forms are additions: the `@` URL syntax and the extended set of marker variables. The older marker names, such as `python_implementation`, are not part of this specification, and the new names should be used.

Metadata written with the older parenthesized version syntax remains legal. Requirements that depended on whitespace-sensitive behavior in pip's parser are normalized by the grammar above.

## Rationale

The PEP does not address which requirement lines go in which section of the metadata, whether a dependency is for building, running, or testing, or how a tool should resolve conflicts. Those are higher-level questions, and keeping the scope to a single line leaves room for different answers.

The choice of `@` for URLs mirrors the syntax pip has been moving toward and avoids the ambiguity of putting a URL where a version should be. Use of PEP 440 comparison for version-like marker variables makes `python_version >= '3.10'` behave properly, which a string comparison would not.
