PEP: 499
Title: `python -m foo` should also bind 'foo' in sys.modules
Author: Example Author <author@example.org>
Status: Deferred
Type: Standards Track
Created: 07-Aug-2015
Python-Version: 3.6

# Abstract

When a module is used as a main program on the Python command line, such as by:

    python -m module.name ...

it is easy to accidentally end up with two independent instances of the module if that module is again imported within the program. This PEP proposes a way to fix this problem.

When a module is invoked via Python's `-m` option the module is bound to `sys.modules['__main__']` and its `.__name__` attribute is set to `'__main__'`. This enables the standard "main program" boilerplate code at the bottom of many modules, such as:

```python
if __name__ == '__main__':
    sys.exit(main(sys.argv))
```

However, when the above command line invocation is used it is a natural inference to presume that the module is actually imported under its official name `module.name`, and therefore that if the program again imports that name then it will obtain the same module instance. That actually isn't what happens: the second import creates a fresh module object, executing the module's top level code a second time under the name `module.name`.

# Motivation

Consider a small package with a module `pkg/tool.py`:

```python
# pkg/tool.py
import pkg.plugins

REGISTRY = {}

def register(name):
    def deco(fn):
        REGISTRY[name] = fn
        return fn
    return deco

def main():
    print(sorted(REGISTRY))

if __name__ == "__main__":
    main()
```

and `pkg/plugins.py`, which does `from pkg.tool import register` and uses it as a decorator. Run as `python -m pkg.tool`, execution proceeds as follows. The interpreter runs `pkg/tool.py` as `__main__`. It imports `pkg.plugins`, which in turn imports `pkg.tool`. Since `sys.modules` has no entry named `pkg.tool`, the import system loads the file again, producing a second module with its own `REGISTRY`. The plugin registers itself into that second registry. Control returns to the original `__main__` module, whose `REGISTRY` is empty, and `main()` prints nothing.

The surprise is real and causes confusing bugs. Symptoms include:

* module-level singletons, caches and registries existing twice;
* `isinstance` checks failing between objects created by "the same" class in two copies of the module, as `__main__.Foo` and `module.name.Foo` are distinct classes;
* exceptions defined in the module that cannot be caught because the raising and catching code refer to different copies;
* pickle failures or oddities when instances created in `__main__` are serialised and later loaded by the module's real name;
* top level side effects, such as logging configuration or registration, executing twice.

Experienced developers learn to avoid circular imports of the main module, but the problem is not always obvious, particularly in larger projects where the import path through the main module is indirect.

# Rationale

The cause is that `__main__` is not an alias of the real module name. The module is bound under only one key in `sys.modules`. A import-by-name finds nothing and loads again.

The simplest remedy is to make the same module object visible under both names. After the module has been located and is about to be run as `__main__`, the runner also binds it under its real name:

```python
sys.modules['module.name'] = sys.modules['__main__']
```

Subsequent `import module.name` statements then return the running module. The singleton problem disappears, because there is only one module object.

# Specification

When the interpreter is run with `-m module.name`, the `runpy` machinery that locates and executes the module will, in addition to binding the module object as `sys.modules['__main__']`, bind the same object under `sys.modules['module.name']`, the name resolved by the module spec.

Detailed requirements:

1. The binding is created before the module's code is executed, so that any import of the module during execution, including indirect ones, finds it.
2. The module's `__name__` attribute remains `'__main__'`. Programs rely on this value to distinguish script execution from import. The module's `__spec__.name` continues to hold the real name, as it does now.
3. For a package executed with `python -m package`, which runs `package.__main__`, the module `package.__main__` is bound under that name as well, in addition to `__main__`. The package itself is already imported normally.
4. If the name is already present in `sys.modules` when the binding is attempted, which can occur if a parent package's `__init__` imported the module, the existing entry is not replaced, and a `RuntimeWarning` is issued, as is already done for related situations by `runpy`. In this case the problem of duplicates remains, but the program is informed.
5. Programmatic callers of `runpy.run_module` with `alter_sys=True` get the same behaviour. With `alter_sys=False`, nothing changes.

# Backwards Compatibility

The change is mostly invisible. Programs that previously worked under the duplicate-module behaviour could be affected in the rare case that they depend on getting a fresh copy. An example would be a test script that deliberately re-imports itself to check import-time behaviour. Such a program can be adjusted by removing the entry from `sys.modules` before re-importing.

A more subtle case concerns code that tests `sys.modules.get('module.name')` to detect whether the module has "really been imported". After the change, this would be true when run as a script. Such tests are fragile in any event.

Pickled objects: previously, instances created while running as `__main__` carried `__main__` as their module and would unpickle only in a program running the same script. That is unchanged, since the class's `__module__` stays `'__main__'`. However, classes imported by real name now agree with the running copy, so new objects of those classes have the identity the author intends.

Debuggers and profilers that key on module name see a module with `__name__ == '__main__'` registered under two keys. Tools which iterate over `sys.modules` and process each value may see the module twice. Authors of such tools can deduplicate by identity.

# Alternatives

**Rename `__name__` to the real name and inject `__main__` as an alias.** This would break the very idiom that motivates `-m`: the `if __name__ == '__main__'` guard would fail to fire.

**Warn only.** Detect the second import of a module whose file matches `__main__`'s file, and issue a warning. This helps debugging but does not fix the issue, and in the presence of symlinks and case insensitive file systems, matching files is unreliable.

**Do nothing; document it.** The problem is well known to experienced users. But it is a trap that costs hours, and a fix is cheap.

**Fix only for packages.** Restricting the change to `python -m package` would leave plain modules with the old behaviour, creating inconsistent rules.

# Reference Implementation

A short patch to `runpy._run_module_as_main` and the `_ModifiedArgv0`/`_TempModule` helpers suffices: after the module spec is found, `sys.modules[spec.name]` is set alongside `__main__`, with proper restoration on exit. A test suite should cover the registry example above, packages with `__main__.py`, and the warning in the pre-imported case.

# Status

This PEP is deferred pending agreement on the interaction with the import system's handling of `__main__` and the proposed changes to module spec semantics.
