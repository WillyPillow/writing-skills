# Abstract

This submission describes programming by contract for Python. Eiffel's Design By Contract(tm) is perhaps the most popular use of programming contracts [1]. Programming contracts extends the language to include invariant expressions for classes and modules, and pre- and post-condition expressions for functions and methods.

These expressions (contracts) are similar to assertions: they must be true or the program is stopped, and run-time checking of the contracts is typically only enabled while debugging. Contracts are higher-level than straight assertions and are typically included in documentation.

# Motivation

Python already has the `assert` statement, and many programmers use it to check conditions at function entry and exit. Contracts go further in three ways.

First, contracts are tied to the interface of a function or class, not to the body. A precondition describes what the caller must guarantee. A postcondition describes what the function guarantees in return. An invariant describes what is true of every instance of a class whenever a public method is not running. Writing these as assertions scattered in code leaves the distinction implicit.

Second, contracts are inherited. If a subclass overrides a method, the contract of the base class method still applies: the overriding method may weaken the precondition and may strengthen the postcondition, but not the reverse. This rule, from the Liskov substitution principle, cannot be expressed with plain assertions without discipline and repetition.

Third, contracts are documentation. A contract is part of the interface description. A tool can extract contracts and show them to the user, who can then read the guarantees without reading the code. As the abstract notes, they are typically included in documentation.

Python is dynamically typed and has weak means for describing interfaces. Contracts offer a lightweight way to say what a function expects and promises, and they have been found useful in finding bugs early in other languages.

# Specification

The contracts are written in docstrings, in a form that is understood by a preprocessor and does not require any change to the Python language. This keeps the proposal compatible with all versions of Python and allows contract checking to be disabled at no cost by not running the preprocessor.

## Syntax

A contract is placed in a docstring, after the normal description, in sections introduced by keywords at the beginning of a line.

```python
class Account:
    """A bank account.

    inv:
        self.balance >= 0
    """

    def withdraw(self, amount):
        """Remove money from the account.

        pre:
            amount > 0
            amount <= self.balance

        post:
            self.balance == __old__.self.balance - amount
        """
        self.balance -= amount
```

The keywords are:

- `pre:` followed by one or more expressions that must be true on entry.
- `post:` followed by expressions that must be true on normal return.
- `inv:` followed by expressions that must be true at the start and the end of each public method, and after construction.
- `raise:` followed by exception classes and conditions under which they may be raised, as in `raise: ValueError if amount <= 0`.

Each expression is on its own line and is an ordinary Python expression. All the expressions of a section are combined with `and`. The block is indented under the keyword.

## Special names

Within a postcondition, the name `__old__` refers to a snapshot of the state of the object and arguments at entry, so that the result can be related to the initial values. The snapshot is taken by shallow copy of the attributes named in the postcondition, so there is no cost for attributes that are not mentioned. The name `__return__` refers to the value being returned.

Within invariants and contracts, quantifiers are expressed with the existing generator and `all`/`any` features, for example `all(x > 0 for x in self.items)`.

## Checking

A tool, called the contract preprocessor, reads a module and generates a version in which each method with a contract is wrapped by code that checks the conditions. Evaluation order is as follows. On entry, the invariant and preconditions are checked. After the body completes, the postconditions and then the invariant are checked. A violation raises `PreconditionViolation`, `PostconditionViolation` or `InvariantViolation`, all subclasses of `AssertionError`.

Public methods are those whose name does not begin with an underscore. Private methods are not checked for invariants since invariants may not hold in the midst of an update.

During the evaluation of a contract, further contract checking is disabled, which prevents infinite recursion when a contract expression calls a method that has a contract of its own.

## Inheritance

When a method overrides a method of a base class, the effective precondition is the base precondition `or` the derived precondition, and the effective postcondition is the base postcondition `and` the derived postcondition. Invariants of the base class apply to all derived classes. The preprocessor builds these combinations on class creation by walking the method resolution order.

## Modules

A module docstring may include an `inv:` section. The module invariant is checked at the end of module initialization and at the entry and exit of each public function.

# Rationale

## Why docstrings

Placing contracts in docstrings, rather than adding keywords such as `require` and `ensure` to the language, avoids a grammar change and allows adoption in stages. Existing documentation tools already display docstrings. A later PEP could add syntax if the approach proves successful.

## Why not decorators

Decorators were proposed as an alternative, with functions such as `@pre(lambda self, amount: amount > 0)`. The lambda notation is clumsy for non-trivial expressions, repeats argument names, and does not suit class invariants. Decorators also keep contracts away from the prose of the documentation. Another consideration is that decorator syntax is itself only a proposal at the time of writing.

## Why not just assert

Assertions can express the same checks, but cannot be inherited, cannot be extracted as documentation, and cannot distinguish blame: a failed precondition is the caller's fault, while a failed postcondition is the function's. Distinguishing these cases speeds up debugging.

# Backwards Compatibility

There are no language changes. Existing modules have docstrings that happen to contain words like `pre:` or `post:` at the start of a line. The preprocessor only acts on modules that opt in, for example by a marker line `__contracts__ = True`, so existing code is unaffected.

# Reference Implementation

A prototype preprocessor, written in Python, parses docstrings, generates wrapper code and handles inheritance. It has been used on small programs to find real bugs. It is slow, because it re-evaluates snapshots with each call, and has no support for contracts on properties, class methods, or generators. The contract-checking overhead can be avoided by not running the preprocessor in production.

# Open Issues

- Handling of contracts for generators and coroutines.
- Whether `__old__` should deep copy.
- Thread safety of invariant checks.
- Interaction with `-O`, which removes `assert` statements; contracts could be disabled under the same flag.
- A standard format for extracting contracts for documentation tools.
