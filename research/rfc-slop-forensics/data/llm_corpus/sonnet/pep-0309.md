# Abstract

This proposal is for a function or callable class that allows a new callable to be constructed from a callable and a partial argument list (including positional and keyword arguments).

I propose a standard library module called "functional", to hold useful higher-order functions, including the implementation of partial().

An implementation has been submitted to SourceForge [2].

# Acceptance

Patch #941881 was accepted and applied in 2005 for Py2.5. It is essentially as outlined here, a partial() type constructor binding leftmost positional arguments and any keyword arguments. The partial object has three read-only attributes func, args, and keywords. Calls to the partial object can specify keywords that override those in the object itself.

There is a separate and continuing discussion of whether to support right-curried arguments. That issue is not resolved here.

# Motivation

Functions in Python are first-class objects. A common idiom is to take an existing function and fix some of its arguments, producing a function with a smaller signature that can be handed to code expecting a callable of fewer parameters. GUI toolkits that take callbacks without arguments, sorting keys, threading targets and many other APIs invite this style.

Today there are several ways of doing it, none of them satisfying.

The first is a lambda expression:

```python
callback = lambda: process(item, verbose=True)
```

This works but has a well-known pitfall. The lambda captures variables, not values, so a lambda created in a loop sees the loop variable's final value unless the author uses the default-argument trick:

```python
callbacks = [lambda x=x: f(x) for x in values]
```

That trick pollutes the signature of the callable, which can then be called with an unintended argument, and it is obscure to novices.

The second is a nested function, typically a closure written as a function returning a function. It has the same capture semantics as the lambda, and it needs several lines for each use.

The third is a hand-written class with `__init__` and `__call__`. This is the most explicit, but it is heavy for a one-off need and every project ends up with its own slightly different version.

A standard `partial` would capture values at the time of the call, document what it does by name, and make the intention plain to readers. It is also an instance of a pattern that other languages already include in their standard libraries under names such as "bind" and "curry", although strictly speaking what is proposed here is partial application, not currying.

# Use cases

Callbacks in event-driven code are the most common case:

```python
button.configure(command=partial(handle_click, button_id))
```

Fixing a keyword argument to adapt a function to a protocol:

```python
int_from_binary = partial(int, base=2)
int_from_binary("1011")   # 11
```

Specialising a general function in a table of handlers:

```python
handlers = {
    "json": partial(serialise, format="json"),
    "csv": partial(serialise, format="csv"),
}
```

And supplying constant arguments to `map`, `filter` and `sorted`, where a short function name is clearer than a lambda.

# Specification

The proposal is a new callable type, `partial`, constructed as `partial(func, *args, **keywords)`. When the resulting object is called with positional arguments `a` and keyword arguments `k`, it calls `func(*(args + a), **{**keywords, **k})`. In other words:

* positional arguments given at construction are placed before any given at call time;
* keyword arguments given at call time override those given at construction;
* the result of the underlying call is returned unchanged, and exceptions propagate.

The object has three read-only attributes:

* `func`, the wrapped callable;
* `args`, a tuple of the frozen positional arguments;
* `keywords`, a dictionary of the frozen keyword arguments.

These attributes make a partial object introspectable: tools such as debuggers, serialisers and decorators can inspect what was fixed. The type can be subclassed.

## Module location

The original text of this proposal suggested a new module named `functional` to hold `partial` and other higher-order helpers that might be added later. Whether such a module would acquire further content is uncertain, and creating a module to house one function is poor stewardship of the namespace. The implementation therefore places the type in a module whose subject is higher-order functions, and leaves room to grow it.

## Reference implementation

A pure Python version of the semantics is short:

```python
class partial:
    def __init__(self, func, *args, **keywords):
        if not callable(func):
            raise TypeError("the first argument must be callable")
        self.func = func
        self.args = args
        self.keywords = keywords

    def __call__(self, *args, **keywords):
        kw = self.keywords.copy()
        kw.update(keywords)
        return self.func(*(self.args + args), **kw)
```

The submitted patch implements the same behaviour in C for speed, since partial objects are often called in tight loops.

# Design discussion

## Why not lambda?

Python's lambda is deliberately limited and the community has long argued about its future. Replacing common lambda uses with a named, tested function reduces the pressure on the language. More concretely, `partial` binds argument values at construction, avoiding the late-binding surprise, and gives objects that can be compared by their parts and introspected.

## Why bind only on the left?

Binding leftmost positional arguments covers the vast majority of practical cases and is simple to describe. Supporting arbitrary positions needs a placeholder syntax or an index parameter, either of which complicates the interface. A right-binding variant, or a placeholder form, can be added later without breaking this one, and the question is left open.

## Keywords and overriding

Allowing call-time keywords to override constructor keywords matches the behaviour users expect from default arguments, and enables the "specialise but allow overrides" pattern.

## Naming

Other names were suggested, including `curry`, `bind` and `closure`. "Curry" is rejected because currying transforms a multi-argument function into a chain of single-argument functions, a different operation. "Partial" is accurate and used in the literature on partial application.

## Method binding

A partial object wrapping a function does not bind as a method when stored on a class, because it is not a function object and therefore does not participate in the descriptor protocol. This is consistent with other callables and is documented. Users who want a bound method should use a regular method definition or `types.MethodType`.

# Backwards compatibility

The proposal is purely additive. No existing names are altered. Third-party libraries that define their own `partial` are not affected unless they import the new one.

# Open issues

* Whether partial objects should have a useful `repr`. The reference includes one that shows the wrapped function and arguments.
* Whether nested partial objects should be flattened, so `partial(partial(f, 1), 2)` is stored as `partial(f, 1, 2)`. Doing so would be an optimisation only, visible through the attributes.
* Support for right-curried arguments, as mentioned in the Acceptance section.
