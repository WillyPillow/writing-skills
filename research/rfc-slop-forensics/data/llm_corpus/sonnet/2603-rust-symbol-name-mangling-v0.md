# RFC 2603: Rust Symbol Name Mangling (v0)

- Feature Name: `rust_symbol_name_mangling_v0`
- Start Date: 2018-11-27
- RFC PR: rust-lang/rfcs#2603
- Rust Issue: rust-lang/rust#60705

## Summary

This RFC proposes a new mangling scheme that describes what the symbol names generated by the Rust compiler look like. This new scheme has a number of advantages over the existing one which has grown over time without a clear direction. The new scheme is consistent, depends less on compiler internals, and the information it stores in symbol names can be decoded again which provides an improved experience for users of external tools that work with Rust symbol names. Note that, at this point, the new mangling scheme would not be part of the language specification or the specification of a stable Rust ABI. In the future it could be part of both and it is designed to be stable and extensible, but for the time being it would still be an implementation detail of the compiler.

## Motivation

Rust symbol names are what linkers, debuggers, profilers, and crash reporters see. Every function, static, and monomorphized generic instance in a Rust program ends up as a symbol in an object file, and that symbol has to be a string that the platform's tools can handle.

The current scheme, which this RFC calls "legacy", is an extension of the Itanium C++ ABI mangling with ad hoc modifications. It has several problems.

**Lossy encoding of generics.** The legacy scheme does not encode generic arguments in a structured way. Instead, the compiler appends a 64-bit hash, written like `17h0123456789abcdefE`, to the path of the item. The hash covers the type parameters, the crate disambiguator, and other inputs. Two instances of `Vec<u8>::push` and `Vec<String>::push` differ only in the hash. A debugger or profiler looking at such a name can tell that two symbols are different instances of the same function, but not how they differ.

**Dependence on compiler internals.** The hash is computed from internal data structures. Changes that are invisible to users, such as reordering fields in a compiler-internal type, can alter symbol names. This makes it hard for external tools to reason about symbols, and makes reproducible comparisons of builds noisy.

**Inconsistent handling of impls.** Methods in trait impls appear in the legacy scheme under names like `_$LT$impl$u20$core..fmt..Debug$u20$for$u20$Foo$GT$`, which relies on the `$` escape convention to cover characters that are not valid in symbols. The result is difficult to read, difficult to parse, and not uniquely decodable in every case.

**Limited character set.** Symbols on some platforms may contain only a restricted set of characters. The legacy scheme dodges this with `$`-escapes and `..` for `::`, which is non-standard and makes demangling a bespoke exercise.

**No support for non-ASCII identifiers.** With the stabilization of non-ASCII identifiers on the horizon, the legacy scheme would need to be extended with yet another escape.

A new scheme should be designed so that symbols can be demangled back to a faithful, human-readable path, including generic arguments, without needing access to the compiler.

## Design goals

1. **Unambiguous decoding.** A mangled name must decode to exactly one path.
2. **Platform independence of the character set.** The output uses only `[A-Za-z0-9_]` and the `_R` prefix, so that it is valid on all supported targets without escapes.
3. **Stability.** The encoding of any given item should not change from one compiler version to the next unless the item itself changes. Where hashes are required, they should depend only on documented inputs.
4. **Extensibility.** New kinds of items, such as const generics, can be added without invalidating old encodings.
5. **Compactness.** Repeated components are compressed through back-references, since mangled names can otherwise become very large.

## Detailed design

### Overview

Every symbol in the new scheme begins with the prefix `_R`. This is distinct from the legacy prefix `_ZN`, so tools can tell the schemes apart. After the prefix comes an optional decimal version number, then a *path* naming the item, and optionally an *instantiating crate* suffix.

The grammar is given in a BNF-like notation:

```
<symbol-name> = "_R" [<decimal-number>] <path> [<instantiating-crate>]
```

### Paths

A path is built up from a root and a sequence of nested components.

```
<path> = "C" <identifier>                        // crate root
       | "M" <impl-path> <type>                  // inherent impl
       | "X" <impl-path> <type> <path>           // trait impl
       | "Y" <type> <path>                       // trait definition
       | "N" <namespace> <path> <identifier>     // nested path
       | "I" <path> {<generic-arg>} "E"          // generic application
       | <backref>
```

The namespace character distinguishes categories of names: `v` for values such as functions and statics, `t` for types, and `C` for closures. A closure also carries a disambiguator, since a function can contain many closures with no names.

An impl path records the crate and the disambiguator of the impl block inside its parent. This allows two impls of the same trait for different types to be told apart without relying on a hash of the type.

### Identifiers

Identifiers are written as a decimal length followed by the bytes of the name:

```
<identifier> = [<disambiguator>] <undisambiguated-identifier>
<undisambiguated-identifier> = ["u"] <decimal-number> ["_"] <bytes>
```

The optional `u` flag marks an identifier that contains non-ASCII characters. In that case, the identifier is first encoded with Punycode, using `_` in place of `-` as the delimiter, and the length applies to the encoded form. The extra underscore after the length is added only when the identifier begins with a digit or an underscore, which removes the ambiguity between the length and the name.

The disambiguator, written as `s` followed by a base-62 number, distinguishes multiple items with the same name in the same scope, for instance when different crates with the same name appear in a dependency graph or when macros generate identically named functions.

### Types

Every type that can appear in a generic argument has an encoding. Primitive types use single lowercase letters, for example `a` for `i8`, `h` for `u8`, `l` for `i32`, `j` for `u32`, `b` for `bool`, and `c` for `char`. Compound types use uppercase prefixes: `R` for a shared reference, `Q` for a mutable reference, `P` for a const raw pointer, `O` for a mutable raw pointer, `A` for an array with a length constant, `S` for a slice, and `T` for a tuple.

Types defined by the user are encoded as the path to their definition, followed by generic arguments if any. Function pointer types, trait object types, and `impl Trait` in argument position are handled by dedicated prefixes, with trait objects listing their principal trait and then projection bounds.

### Constants

Because const generics are in development, the scheme includes a `K` prefix for constants. Integer constants are written with their type followed by the value in hexadecimal. Negative values use a leading `n`. Booleans and characters use their type letter and a hexadecimal scalar value. Constants of other types are not yet encodable and use a placeholder.

### Compression

To avoid exponential growth, the scheme supports back-references. A back-reference is written as `B` followed by a base-62 offset, and refers to an earlier position in the same symbol where a path or type begins. Because an offset always points backwards, a decoder can resolve it in a single pass. Compression is mandatory in canonical output, which keeps the mapping from items to symbols deterministic.

### Instantiating crate

Generic functions may be instantiated in a crate other than the one that defines them. Two crates may both instantiate `Vec<u8>::push` and the linker must be able to keep these copies separate or merge them. The `<instantiating-crate>` suffix names the crate performing the instantiation, which lets the compiler avoid collisions in cases where it cannot otherwise guarantee that instances are identical. It is omitted when the instance is shared across crates.

### Example

A function `foo::bar` in crate `mycrate` would appear approximately as:

```
_RNvCs15kBYyAo9fc_7mycrate7foo3bar
```

Reading from left to right: `_R` is the prefix, `Nv` is a nested value path, `C` introduces the crate root, `s15kBYyAo9fc_` is the crate disambiguator, `7mycrate` is the crate name, and `7foo3bar` hold the remaining components.

## Drawbacks

The new scheme is longer than the legacy one for simple, non-generic items because the crate disambiguator and the namespace letters add bytes. Compression recovers much of this for deeply nested or generic code, but not all.

Demanglers and tools must be updated. Existing versions of `c++filt` will not understand `_R` symbols, and tools such as `perf`, `gdb`, `lldb` and `valgrind` require changes. The rollout needs coordination with these projects.

Finally, supporting two schemes concurrently during transition increases complexity in the compiler.

## Rationale and alternatives

**Extending the legacy scheme.** One could fix the individual defects, for instance by adding generic arguments after the path. However, the legacy scheme's escape conventions and hash would have to be retained for compatibility, and the result would still not be self-describing.

**Reusing the Itanium C++ scheme more fully.** This has the advantage that existing demanglers work. The disadvantage is that Rust has concepts with no C++ analogue, such as lifetimes in binder positions, trait objects with associated types, and closures, and the Itanium scheme would need extensions that existing demanglers would not understand anyway.

**Hashing everything.** A scheme that emits only a hash provides compactness and guaranteed uniqueness but gives up all readability. Debugging and profiling would be significantly worse.

## Prior art

The Itanium C++ ABI, the Swift mangling scheme, and the D language mangling scheme each describe their own approach to recoverable names with back-references. The design here draws particularly on Swift's use of substitutions and on D's focus on compactness.

## Unresolved questions

* Should the instantiating-crate suffix be made mandatory? Omission adds a small risk of silent merging of non-identical instances.
* What is the right encoding for const generic values of types other than integers, bool and char?
* How should the scheme handle higher-ranked lifetimes in a way that remains stable if lifetime syntax evolves?

## Future possibilities

If the scheme proves stable, it could be incorporated into the Rust reference and adopted as part of a stable ABI. Tools such as debuggers could demangle it natively, and the compiler could drop the legacy scheme after a transition period of several releases.
