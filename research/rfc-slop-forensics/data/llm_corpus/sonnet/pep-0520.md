# PEP 520: Preserving Class Attribute Definition Order

- Status: Draft
- Type: Standards Track
- Created: 07-Jun-2016
- Python-Version: 3.6

## Abstract

The class definition syntax is ordered by its very nature. Class attributes defined there are thus ordered. Aside from helping with readability, that ordering is sometimes significant. If it were automatically available outside the class definition then the attribute order could be used without the need for extra boilerplate (such as metaclasses or manually enumerating the attribute order). Given that this information already exists, access to the definition order of attributes is a reasonable expectation.

However, currently Python does not preserve the attribute order from the class definition. This PEP changes that by preserving the order in which attributes are introduced in the class definition body. That order will now be preserved in the `__definition_order__` attribute of the class. This allows introspection of the original definition order, e.g. by class decorators.

Additionally, this PEP requires that the default class definition namespace be ordered (e.g. `OrderedDict`) by default. The long-lived, now-obsolete `__prepare__()` workaround that metaclasses used to provide an ordered namespace is no longer required for that purpose.

## Motivation

A number of use cases for ordered class attributes have shown up over the years. They fall into a few families.

**Declarative schemas.** Libraries that describe a record, a form, or a database table with a class body want the fields in the order the author wrote them. Examples include ORMs, serialization frameworks, and enumerations that support explicit ordering. The column order in a `CREATE TABLE` statement, or the order of fields in a rendered form, should match the source.

**Binary layouts.** A class describing a C structure or a wire format must list its members in order, since the position of each field is significant.

**Documentation and introspection.** Tools that generate documentation or help text benefit from presenting members the way the author arranged them rather than alphabetically.

**Testing.** Some frameworks run tests in the order in which they are defined.

At the moment, the standard recipe is to give the class a custom metaclass, define `__prepare__()` to return an `OrderedDict`, and have `__new__()` copy the key order into a class attribute. That is boilerplate: a metaclass is a heavy tool for such a small need, and metaclasses make it difficult to combine libraries since every class has only one metaclass and conflicts arise when two libraries each provide one.

Since the interpreter already evaluates the class body in order, preserving the order costs little.

## Specification

### Ordered class namespace

Beginning in Python 3.6, the namespace object returned by the default `type.__prepare__()` will preserve insertion order. It is an implementation detail whether this is an `OrderedDict` or another mapping type with the same behavior. The interpreter will use that namespace as the local scope while executing the class body.

If a metaclass defines its own `__prepare__()` that returns an unordered mapping, the class body will not have its order preserved, since the interpreter can only record keys in the order the mapping reports them.

### The `__definition_order__` attribute

After the class body completes, `type.__new__()` copies the keys of the namespace into a tuple and stores it on the new class as `__definition_order__`. The tuple contains the names of attributes that were *set* in the class body, in the order they were first introduced:

```python
class Meta(type):
    pass

class Spam(metaclass=Meta):
    ham = None
    eggs = 5

assert Spam.__definition_order__ == ('__module__', '__qualname__', 'ham', 'eggs')
```

Details:

- The tuple includes only names that are put in the class namespace during execution of the class body. It does not include names inherited from base classes, nor does it include attributes added later by assignment on the class object.
- The first time a name is bound establishes its position. Rebinding the same name later in the body does not change its position. Deleting a name with `del` removes it from the tuple.
- Implicit entries such as `__module__` and `__qualname__` are included, as they are really in the namespace. A consumer that does not want them can filter names that begin and end with double underscores.
- `__definition_order__` is a regular class attribute. It is not inherited in a meaningful way: each class has its own, computed from its own body. Reading it on a subclass returns the subclass's tuple.

### Overriding the definition order

A class body may explicitly set `__definition_order__` itself, and in that case the value is preserved as given. This allows a class to hide its order, by setting `__definition_order__ = None`, or to override it with a custom ordering. A class created by calling `type()` directly gets a definition order derived from the order of keys in the supplied namespace mapping, which for a plain `dict` argument on Python 3.6 means insertion order of that dict.

### Types without a class body

For classes created via other means, including extension types and classes created by `type(name, bases, ns)`, the attribute is derived from `ns` where one is available. For built-in and extension types it is `None`, since no definition order was recorded.

## Why a tuple

A tuple is immutable, hashable and has a natural meaning as an ordered sequence of names. A list invites mutation, and an `OrderedDict` would duplicate information already stored in the class namespace. A tuple of names can be turned into any other structure by the consumer.

## Why not a different name

Other candidate names were `__attribute_order__`, `__members__` and `__fields__`. The last two are in use by other libraries with different semantics, for example `enum` already uses `__members__`. The word "definition" reflects that the order is the order of the class body, not the order of arbitrary attribute assignments.

## Alternatives

**Do nothing; keep using metaclasses.** This leaves the boilerplate in place, and prevents ordinary decorators from observing the order.

**Make the class `__dict__` ordered.** This would give access to the order without a new attribute, but class dicts are used for lookups throughout the interpreter and the performance and memory cost of using an ordered mapping at runtime, as opposed to only at class creation, is a concern. It would also mix attributes added later with those from the body, losing the distinction that is important to many use cases.

**Provide the order only to metaclasses via the `__prepare__()` namespace.** This is what exists today.

**Capture order in the compiler.** The compiler could record the order of assignments statically and attach it to the code object. This fails for names defined dynamically, such as via `locals()` or loops in the body.

## Backward Compatibility

Most code should see no effect. The new attribute is additive. A class that already defines `__definition_order__` would now have its own value retained, which is the same as before. Metaclasses that implemented `__prepare__()` to return an `OrderedDict` still work; they are simply no longer required.

Some code that checks `type(namespace) is dict` inside a metaclass `__new__()` or `__prepare__()` will notice a change, since the default namespace is no longer a plain `dict`. Such checks are fragile, and this is considered acceptable.

Pickling is unaffected, since classes are pickled by reference.

## Implementation

The implementation is small. `type.__prepare__()` returns an ordered mapping rather than a `dict`. In `type.__new__()`, after the namespace is copied to the new type's `__dict__`, the keys of the namespace are collected in order and stored under `__definition_order__` unless the namespace already supplies one.

The implementation for the C code lives in `Objects/typeobject.c`, and the language reference gets a new paragraph in the section on class creation. A "What's New" entry describes the feature.

Tests include: ordering of simple attributes; rebinding preserves position; deletion; inheritance; classes created by `type()`; explicit override; and metaclasses with custom `__prepare__()`.

## Open Questions

- Should `__definition_order__` include the implicit `__module__` and `__qualname__` entries, or filter them out?
- Should `dir()` honor definition order?
- Does the decision to use a tuple of strings leave room for later extension to richer attribute metadata?
