PEP: 521
Title: Managing global context via 'with' blocks in generators and coroutines
Author: Example Author <author@example.org>
Status: Draft
Type: Standards Track
Created: 2017-04-27
Python-Version: 3.7

# Abstract

While we generally try to avoid global state when possible, there nonetheless exist a number of situations where it is agreed to be the best approach. In Python, a standard pattern for handling such cases is to store the global state in global or thread-local storage, and then use ``with`` blocks to limit modifications of this global state to a single dynamic scope. Examples where this pattern is used include the standard library's ``warnings.catch_warnings`` and ``decimal.localcontext``, NumPy's ``numpy.errstate`` (which exposes the error-handling settings provided by the IEEE 754 floating point standard), and the handling of logging context or HTTP request context in many server application frameworks.

However, there is currently no ergonomic way to manage such local changes to global state when writing a generator or coroutine. For example, this code:

```python
def f():
    with decimal.localcontext() as ctx:
        ctx.prec = 5
        yield 1 / 3
        yield 2 / 3
```

does not do what its author expects. Between the two ``yield`` statements, the caller is free to run arbitrary code, and that code sees the modified decimal precision, even though it has nothing to do with the generator. Conversely, the generator body may resume under a different context from the one it established.

This PEP proposes to extend the context manager protocol with two new optional methods, ``__suspend__`` and ``__resume__``, which are called when a generator or coroutine suspends or resumes execution while inside a ``with`` block. With these hooks, a context manager can correctly swap its global state in and out as control passes across the suspension boundary.

# Motivation

Python's ``with`` statement is the idiomatic way to establish a temporary change that must be undone reliably. For ordinary functions the semantics are easy to state: the change is in force for exactly the dynamic extent of the block. The dynamic extent of the block is the same as the time during which the frame is executing.

Generators and coroutines break this equivalence. A ``with`` block inside a generator remains "open" while the generator is suspended, but the generator's frame is not executing. Control has returned to the caller, which runs under whatever global state the generator installed. From the point of view of a context manager that manipulates global state, ``__enter__`` has been called and ``__exit__`` has not, so the state remains modified.

This is not merely a theoretical concern. It produces three distinct classes of bug.

*Leaking.* State established inside a generator leaks to the caller between iterations. A consumer iterating over the generator above would compute its own decimal arithmetic at precision 5 without ever having asked for that.

*Dropping.* If the caller changes the global state while the generator is suspended, then on resumption the generator's code runs under the caller's state rather than the one it established. The generator's ``with`` block therefore does not guarantee anything about the code inside it.

*Interleaving.* When several generators, each with its own ``with`` block of the same kind, are advanced in alternation, their modifications overlap in non-nested order. Because ``__exit__`` restores whatever value was saved at ``__enter__``, an interleaved sequence of enters and exits can leave the global state permanently corrupted.

The problem is more acute with the rise of ``async``/``await``. Coroutines suspend far more often than traditional generators, and event loops multiplex thousands of them over a single thread. Thread-local storage no longer identifies the logical flow of execution, so even the standard workaround for the shared-state problem fails.

Today, authors of libraries that depend on context-managed global state have two choices, both unattractive. They can document that the context manager must not be used across a ``yield``, relying on users to read and obey the warning. Or they can invent library-specific mechanisms, such as explicit context arguments, which defeat the purpose of ambient state.

# Rationale

The cleanest fix is to give context managers the opportunity to react when the block they guard is suspended and resumed. A context manager that wants to protect global state can use ``__suspend__`` to save the generator's view of that state and restore the caller's, then use ``__resume__`` to do the inverse.

Alternatives considered are discussed below, but the essential argument for this design is that it keeps the information where it belongs. The context manager knows what state it manages and how to swap it. The interpreter knows when a frame suspends. Connecting the two requires only a notification.

# Specification

## New methods

The context manager protocol is extended with two optional methods:

* ``__suspend__(self)``: called when execution leaves a ``with`` block because the enclosing generator or coroutine is suspended by ``yield``, ``yield from`` or ``await``.
* ``__resume__(self)``: called when execution re-enters the block because the generator or coroutine has been resumed.

Both methods take no arguments and their return values are ignored. If a context manager does not define them, nothing is called, preserving the behaviour of every existing context manager.

## Ordering

For a generator containing nested ``with`` blocks, suspension calls ``__suspend__`` on the context managers from innermost to outermost, mirroring the order in which ``__exit__`` would run. Resumption calls ``__resume__`` from outermost to innermost, mirroring ``__enter__``.

## Exceptions

If ``__suspend__`` raises, the exception propagates out of the ``yield`` expression's suspension point into the generator, as if the ``yield`` itself had raised. If ``__resume__`` raises, the exception is raised inside the generator at the point of resumption. Remaining context managers in the chain are still notified so that the stack stays consistent.

## Interaction with close and throw

When a suspended generator is closed or has an exception thrown into it, ``__resume__`` is called first on all active context managers, after which ``GeneratorExit`` or the thrown exception is raised at the suspension point. The block's ``__exit__`` then runs in the normal state, with the generator's own context restored. This guarantees that ``__exit__`` always observes the same global state as the code in the body did.

## Example

```python
class LocalDecimalContext:
    def __init__(self, **kw):
        self._new = decimal.Context(**kw)

    def __enter__(self):
        self._saved = decimal.getcontext()
        decimal.setcontext(self._new)
        return self._new

    def __exit__(self, *exc):
        decimal.setcontext(self._saved)

    def __suspend__(self):
        self._inner = decimal.getcontext()
        decimal.setcontext(self._saved)

    def __resume__(self):
        self._saved = decimal.getcontext()
        decimal.setcontext(self._inner)
```

With this definition the example generator from the abstract behaves as expected: the caller's arithmetic runs at the caller's precision, and the generator's at precision 5.

## Implementation sketch

For generators, the suspension hooks are driven by the ``with`` block's entry in the frame's block stack. When the frame executes ``YIELD_VALUE`` the interpreter walks the active ``SETUP_WITH`` blocks and invokes ``__suspend__`` where present. On resumption the same walk is performed in the opposite direction. The lookup of the two methods is performed once at ``__enter__`` time and cached on the block entry, so frames whose context managers lack the hooks pay only a pointer comparison on suspension.

# Backwards Compatibility

Existing context managers do not define the new methods and are unaffected. A context manager that happens to define attributes named ``__suspend__`` or ``__resume__`` for unrelated purposes would see unexpected calls, but the double-underscore namespace is reserved for the language, so such use is already unsupported.

The performance cost to generators using ``with`` blocks without hooks is small but nonzero. Benchmarks should be run before acceptance.

# Alternatives

**Do nothing; use explicit context objects.** This is the status quo, and it is why the problem persists. Libraries cannot make ``decimal.localcontext`` safe without a language-level change.

**Contextvars-style storage.** A separate proposal provides storage that follows the logical flow of control instead of the thread. This addresses the interleaving problem for new code but requires every library to migrate, and does not help with state that lives in C extensions or in the process itself, such as floating point error flags or the current working directory.

**Forbid ``yield`` inside ``with``.** Some context managers cannot sensibly span a suspension. A static check could reject them, but ``with open(...)`` inside a generator is both common and correct, so a blanket rule is unacceptable.

# Open Issues

* Whether ``__suspend__`` and ``__resume__`` should receive the suspending frame or generator object, which would allow context managers to key state per generator.
* How asynchronous context managers should integrate, since ``__aenter__`` and ``__aexit__`` are awaitable but a suspension notification must be synchronous.
* Whether an exception in ``__resume__`` during ``close()`` should suppress ``GeneratorExit``.
