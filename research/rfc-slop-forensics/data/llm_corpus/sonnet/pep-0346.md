# Abstract

This PEP is a combination of PEP 310's "Reliable Acquisition/Release Pairs" with the "Anonymous Block Statements" of Guido's PEP 340. This PEP aims to take the good parts of PEP 340, blend them with parts of PEP 310 and rearrange the lot into an elegant whole. It borrows from various other PEPs in order to paint a complete picture, and is intended to stand on its own.

# Author's Note

During the discussion of PEP 340, I made a spectacular blunder by suggesting that "anonymous block statements" could be used to simplify resource management. Having reflected on it, the block-statement idea is more powerful than is needed for that purpose, and the loop-like semantics of PEP 340 cause confusion. This PEP keeps the useful parts: a statement that guarantees cleanup and a way to write the guarded code as a generator.

# Motivation

Resource management in Python is done with `try`/`finally`:

```python
f = open(name)
try:
    process(f)
finally:
    f.close()
```

This works, but it has drawbacks. The acquisition and release are separated by the body, so a reader must scan to the end to find the release. The pattern must be repeated each time. It is easy to forget, and mistakes show up as leaked file handles, forgotten locks or unfinished transactions.

Other languages offer constructs for this: C# has `using`, C++ has destructors with scoped objects, Java 7 is expected to have something similar. CPython's reference counting makes `f = open(name)` followed by exit from the scope release the file promptly, but this is an implementation detail and not part of the language, and Jython and IronPython do not behave this way.

The same pattern appears beyond resources: lock acquisition, transaction commit and rollback, temporarily changing a global such as the decimal context or the current directory, redirecting standard output, and so on. All consist of a setup step, a body, and a teardown step that must always run.

# Specification

## The with statement

A new statement is added:

```
with_stmt: "with" expression ["as" target] ":" suite
```

The expression is evaluated to produce an object, the *resource*, which must provide two methods, `__enter__` and `__exit__`. The semantics are equivalent to:

```python
resource = expression
value = resource.__enter__()
try:
    target = value          # only if "as target" is present
    suite
except:
    if not resource.__exit__(*sys.exc_info()):
        raise
else:
    resource.__exit__(None, None, None)
```

`__enter__` is called with no arguments. Its return value is bound to the target, if any. If `__enter__` raises an exception, the body and `__exit__` are not executed.

`__exit__` receives the exception type, value and traceback if the body raised an exception, or three `None` values otherwise. If it returns a true value after an exception, the exception is suppressed. Otherwise the exception propagates. Suppression is something the author of a resource opts into; most resources return `None` and let exceptions through.

A `return`, `break` or `continue` in the body also causes the exit method to be called, with three `None` values, as with `finally`.

Files, locks and similar standard objects gain `__enter__` and `__exit__`. For files, `__enter__` returns the file and `__exit__` closes it, so the example becomes:

```python
with open(name) as f:
    process(f)
```

## Defining resources with generators

Writing a class with two methods for each resource is heavy. To make it light, a decorator turns a generator with a single `yield` into a resource:

```python
@contextmanager
def locked(lock):
    lock.acquire()
    try:
        yield
    finally:
        lock.release()

with locked(mylock):
    update_shared_state()
```

The decorator creates an object whose `__enter__` runs the generator up to the `yield` and returns the yielded value, and whose `__exit__` resumes the generator. If the body raised an exception, `__exit__` throws it into the generator at the `yield` point, using the `throw()` method of generators proposed in PEP 342. If the generator lets the exception propagate, it is re-raised after the `with` statement. If the generator catches it and returns normally, the exception is suppressed. If the generator yields a second time, a `RuntimeError` is raised, since the generator is expected to finish.

This feature depends on PEP 342, which adds `send()` and `throw()` to generators, and on the allowing of `yield` inside `try`/`finally`, which is also part of that PEP.

## Differences from PEP 340

PEP 340 proposed a block statement, in which the body was run as a "block" invoked by an iterator, with the body potentially executing multiple times. Because of this, the `break` and `continue` statements within the body had to be given new meanings, and the construct resembled a loop. This PEP does not do that. The `with` statement runs its body exactly once. This means that `break` and `continue` retain their usual meaning, referring to the enclosing loop.

PEP 340 also allowed a block iterator to swallow control-flow exceptions, to implement features like retrying. The `with` statement cannot loop. Use cases for retrying are left to ordinary loops with `try`/`except`.

## Differences from PEP 310

PEP 310 proposed a statement of the form `with expression [as target]:`, with `__enter__` and `__exit__` methods, but without the exception information passed to `__exit__` or the generator-based helpers. This PEP adds exception details, so that a resource such as a transaction can decide whether to commit or roll back, and the helper decorator.

# Examples

**Transactions.**

```python
@contextmanager
def transaction(db):
    db.begin()
    try:
        yield db
    except:
        db.rollback()
        raise
    else:
        db.commit()

with transaction(db) as conn:
    conn.execute(...)
```

**Temporarily changing a setting.**

```python
@contextmanager
def decimal_precision(n):
    ctx = decimal.getcontext()
    saved = ctx.prec
    ctx.prec = n
    try:
        yield
    finally:
        ctx.prec = saved
```

**Redirecting output.**

```python
@contextmanager
def redirected(stream):
    old = sys.stdout
    sys.stdout = stream
    try:
        yield stream
    finally:
        sys.stdout = old
```

**Closing.** An object with only a `close()` method can be wrapped:

```python
with closing(urllib.urlopen(url)) as page:
    data = page.read()
```

# Backwards Compatibility

`with` and `as` become reserved words. In Python 2.5 the statement is available through `from __future__ import with_statement`, so that code using these names as identifiers continues to work until the following release.

# Rejected Alternatives

**Using `__del__`-like finalization.** Relying on the garbage collector to release resources is not reliable on all implementations.

**Calling the exit method with separate arguments for each outcome.** Using different method names for success and failure, as in `__commit__` and `__abort__`, was considered but a single method with exception details is simpler and more general.

**Making generators themselves resources.** Adding `__enter__` and `__exit__` to generator objects directly would be confusing, since most generators are not resources; the decorator makes the intention explicit.

# Reference Implementation

A patch against the Python 2.5 development branch implements the statement in the compiler and the new opcodes, adds the methods to file objects, locks and condition variables, and adds the `contextmanager` decorator to a new library module along with tests.
