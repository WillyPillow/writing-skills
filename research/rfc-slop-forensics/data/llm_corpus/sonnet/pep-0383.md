Title: Non-decodable Bytes in System Character Interfaces

# Abstract

File names, environment variables, and command line arguments are defined as being character data in POSIX; the C APIs however allow passing arbitrary bytes - whether these conform to a certain encoding or not. This PEP proposes a means of dealing with such irregularities by embedding the bytes in character strings in such a way that allows recreation of the original byte string.

# Rationale

The C char type is a data type that is commonly used to represent both character data and bytes. Certain POSIX interfaces are specified and widely understood as operating on character data, however, the system call interfaces make no assumption on the encoding of these data, and pass them on as-is. With Python 3, character strings use a Unicode-based internal representation, making it difficult to ignore the encoding of byte strings in the same way that C code can.

On the other hand, Python 3 offers `bytes` as well as `str`, so a program that wants exact control can use the `bytes` forms of the APIs. The majority of programs, however, deal with file names as text, and expect `os.listdir()`, `sys.argv`, `os.environ` and so on to return `str` values.

The difficulty arises when the bytes do not conform to the expected encoding. This happens in practice:

- A user moves files created on a system with a different locale, for example an archive of Latin-1 file names unpacked on a UTF-8 system.
- A file name is created by a program that writes arbitrary bytes.
- The locale is set incorrectly, so that the declared encoding does not match the real one.

In each of these cases, decoding the name with the file system encoding fails with a `UnicodeDecodeError`. Unless this case is dealt with, a simple directory listing may raise an exception, and the program cannot access files in that directory. A program written to do something harmless, such as copying a tree, would fail on the first unusual name. The user has no way to rename the files from within Python, since the old name cannot be represented as a string.

Three approaches were considered:

1. Let the decoding fail, and require callers to catch the error and use bytes interfaces.
2. Replace undecodable bytes with a placeholder such as U+FFFD. This loses information: different byte strings map to the same string, and the original name cannot be recovered. Operations on the file would refer to a name that doesn't exist.
3. Map each undecodable byte to a distinct code point, in a way that can be reversed.

This PEP adopts the third approach.

# Specification

## Error handler

On POSIX systems, Python currently applies the locale's encoding to convert file names to and from Unicode. This PEP proposes to change the conversion to use an error handler, called `surrogateescape`, which operates as follows.

When decoding, each byte that cannot be decoded is mapped to a lone low surrogate code point. A byte in the range 0x80 to 0xFF is represented as U+DC80 to U+DCFF respectively. In other words, the byte `b` becomes the code point `0xDC00 + b`.

When encoding, a lone surrogate in the range U+DC80 to U+DCFF is converted back to the single byte `code point - 0xDC00`. A character outside this range that cannot be encoded raises `UnicodeEncodeError` as usual.

For example, with UTF-8 as the file system encoding, the byte string `b'abc\xff'` decodes to `'abc\udcff'`, and encoding that string yields `b'abc\xff'` again.

The round trip property is central: for every byte string `b`, `encode(decode(b)) == b`, provided that the decoder uses this handler.

## Where it applies

The handler is used by the file system encoding conversions in the following interfaces:

- `os.listdir()`, `os.walk()`, `glob.glob()`, and other functions returning file names as `str`
- File names passed to `open()`, `os.stat()`, `os.rename()` and similar functions as `str`
- `sys.argv`
- `os.environ`, `os.getenv()`, `os.putenv()`
- `os.readlink()`, `os.getcwd()`

Calls that accept `bytes` are unchanged, and pass the bytes directly.

On Windows, file names are already stored as Unicode by the operating system, so no change is needed there.

## The handler as a general facility

The handler is registered with the codecs machinery under the name `surrogateescape` and can be used by any program, for example `data.decode('utf-8', 'surrogateescape')`. This allows applications that wish to process mostly-text input with occasional stray bytes to do so without data loss.

## Interaction with UTF-8 and other encodings

For UTF-8, a byte sequence is undecodable if it is not well-formed. Each byte that is part of an ill-formed sequence is escaped individually. The decoder does not try to find the longest valid prefix, so that behaviour is simple to specify and implement. The valid parts of the string decode normally.

For single-byte encodings, such as Latin-1 or ASCII, only bytes with no mapping are escaped. With ASCII, all bytes of 0x80 and above are escaped.

For multi-byte encodings, the handler works on the same basis as for UTF-8: an invalid byte is escaped and decoding continues at the next byte.

## Lone surrogates in input

The scheme has an ambiguity. A genuine string can contain a lone surrogate in the range U+DC80 to U+DCFF, for instance if it was produced by user code. When such a string is encoded with the handler it becomes a byte. In the other direction, a file name containing the UTF-8 encoding of a lone surrogate (the three bytes `ED B2 BF`, for instance) is ill-formed in strict UTF-8 and is also decoded byte by byte, so no ambiguity arises from that source. The only ambiguity is that a program constructing a string with such a lone surrogate gets the corresponding byte when it passes the string to the operating system. This is considered acceptable, and is arguably the intended behaviour, since it is how such a string was likely produced.

## Output of such strings

A string containing escaped bytes cannot be encoded by the usual strict codec. If a program prints it to a terminal with a strict encoding, an error occurs. The standard streams use the `backslashreplace` error handler for output by default to avoid failures, so the offending bytes appear as `\udcff` and similar. This keeps the program working but loses the exact bytes in the output. Programs that need exact output can write bytes to `sys.stdout.buffer`.

# Backwards compatibility

For file names that decode correctly, nothing changes. For names that previously raised `UnicodeDecodeError`, the new behaviour returns a `str` containing surrogates. Code that relied on catching the exception will no longer see it, and code that processes the string further may meet surrogates in unexpected places, for example when writing to a database or an XML file with a strict encoding. Such code was previously unable to work with these file names at all, so the change turns a crash into a possibly-detectable problem later.

The `os.listdir()` function currently returns `bytes` entries when passed a `bytes` argument and `str` entries otherwise; this behaviour is kept.

# Alternatives considered

**Use private-use code points.** Mapping bytes to a range of private-use characters, for example U+F780 to U+F7FF, has a similar effect and was proposed in earlier discussions. It has the disadvantage that private-use characters can occur in legitimate text, so the round trip is ambiguous in a more common case. Lone surrogates are not valid text in any standard encoding, so the ambiguity is far less likely.

**Use a subclass of str.** A special string type could carry the original bytes. It would not interoperate well with existing code and doubles memory use.

**Return bytes when decoding fails.** Mixing `str` and `bytes` in the same list would make program logic complex, and most code would not handle the case.

**Use a placeholder.** As noted above, loses the original bytes.

# Reference implementation

A patch adds the `surrogateescape` handler to the `codecs` registry, and updates `os`, `sys` and the startup code to use it for file system conversions on POSIX. The patch includes tests for round trips with UTF-8, ASCII and Latin-1 locales, for `os.listdir()` on directories with undecodable names and for the command line.
