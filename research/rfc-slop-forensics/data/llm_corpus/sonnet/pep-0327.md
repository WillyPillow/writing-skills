# Abstract

The idea is to have a Decimal data type, for every use where decimals are needed but binary floating point is too inexact.

The Decimal data type will support the Python standard functions and operations, and must comply with the decimal arithmetic ANSI standard X3.274-1996 [1]. Decimal will be floating point (as opposed to fixed point) and will have bounded precision (the precision is the upper limit on the number of significant digits in a result). However, precision is user-settable, and a notion of significant trailing zeroes is supported so that fixed-point usage is also possible.

This work is based on code and test functions written by Eric Price, Aahz and Tim Peters. Just before Python 2.4a1, the decimal.py reference implementation was moved into the standard library; along with the documentation and the test suite, this was the work of many contributors.

# Motivation

Binary floating point, the type that Python calls `float`, represents numbers as a sum of powers of two. Most decimal fractions cannot be represented exactly in this form. The familiar example is

    >>> 1.1 + 2.2
    3.3000000000000003

Programmers who write financial, accounting or billing code expect `0.1 + 0.2 == 0.3`. They are often taught to work around the problem by using integers of cents, or by rounding at every step, but these approaches are error-prone and push the burden of numeric correctness onto each application.

There are several reasons to prefer decimal arithmetic in these domains:

- Humans think in base ten. Inputs arrive as decimal strings and outputs are read as decimal strings. A decimal type avoids the conversion error entirely.
- Many legal and commercial rules, such as rounding of taxes and interest, are defined in terms of decimal arithmetic with a specific rounding mode. Reproducing them with binary floats is at best awkward.
- Decimal numbers preserve the number of significant digits. `1.20` and `1.2` are numerically equal but carry different information, such as the precision to which a measurement was made. Binary floats cannot represent this distinction.
- Other languages and databases, such as Java's `BigDecimal`, REXX, and SQL's `DECIMAL`, provide it, and Python programs that exchange data with them should be able to do so without loss.

Python already offers some of this through ad-hoc third-party modules, but they differ in interface and semantics. A standard type removes the need to choose among them and gives users a single well-specified behaviour.

# Rationale

## Why follow a standard

The ANSI standard X3.274-1996, and the closely related General Decimal Arithmetic Specification by Mike Cowlishaw, define a floating-point decimal system with exact specification of results for each operation, including rounding, overflow, underflow and exceptional conditions. Adopting a published specification has these advantages: it settles questions of detail without long debate, it gives users a reference to consult, and it allows test suites to be shared with other implementations.

## Why floating point rather than fixed point

A fixed-point type, with a set number of digits after the decimal point, is simpler. It is also less general. Floating-point decimals can represent both very large and very small magnitudes, and a user who wants fixed-point behaviour can obtain it by quantizing results to a chosen exponent. The reverse is not true. A floating-point type with significant trailing zeros can therefore emulate fixed point; a fixed-point type cannot emulate floating point.

## Bounded precision

Unbounded precision would make some operations, such as division of `1` by `3`, impossible, since the exact result has infinitely many digits. Bounded precision also keeps the cost of operations predictable. Precision is a property of the context and defaults to 28 digits, which is enough for nearly all applications while still being cheap. It can be raised or lowered.

# Specification

## The Decimal class

A `Decimal` instance represents a sign, a coefficient, which is a non-negative integer, and an exponent. The value is `(-1)**sign * coefficient * 10**exponent`. Special values, namely infinities, quiet NaN and signalling NaN, are supported.

Construction:

    Decimal(value)

where `value` may be an integer, a string, a tuple `(sign, digits, exponent)`, or another `Decimal`. Construction from a `float` is deliberately not allowed in the initial implementation, because the conversion would silently inherit the binary rounding error that the type is meant to avoid. A classmethod or function may be offered for explicit conversion, and doing arithmetic that mixes a `Decimal` with a `float` raises `TypeError`. Construction from a string is exact and unaffected by the context's precision; the context is applied only when the result of an arithmetic operation is produced.

## Arithmetic

All the standard operators are supported: `+`, `-`, `*`, `/`, `//`, `%`, `**`, unary `-` and `+`, `abs()`, comparisons, `divmod()`, `round()`, `int()` and `float()` (with the latter two being explicit and lossy). Mixed arithmetic with Python integers is allowed, because an integer converts to a `Decimal` exactly. The result of an operation is rounded to the context's precision, and any condition that arises is signalled.

Comparisons are exact: `Decimal("1.0") == Decimal("1.00")` is true, although the two have different representations. Hashing is consistent with equality.

## Context

The arithmetic environment is carried in a `Context` object, which has:

- `prec`, the precision;
- `rounding`, one of several rounding modes (round-half-even is the default, matching the standard; round-half-up, round-down, round-up, round-floor and round-ceiling are also provided);
- `Emin` and `Emax`, the minimum and maximum exponent;
- `traps`, a set of conditions that raise exceptions;
- `flags`, a record of conditions that have occurred;
- `capitals`, controlling the case of the exponent character in string output.

There is one current context per thread. `getcontext()` returns it and `setcontext()` replaces it. A helper `localcontext()` may be used, in a `with` block, to apply a temporary context. Each operation also has a method form that accepts an explicit context, for programmers who prefer to avoid thread-local state.

## Signals and exceptions

The conditions defined by the standard are: Clamped, DivisionByZero, Inexact, InvalidOperation, Overflow, Rounded, Subnormal and Underflow. Each is a subclass of `ArithmeticError` (a new class `DecimalException` is the common base). By default, DivisionByZero, InvalidOperation and Overflow are trapped, which means they raise exceptions; the others only set flags. Users may change this per context.

## Quantization and fixed-point usage

The `quantize()` method rounds a number to the exponent of another, which provides the usual way of obtaining a fixed number of decimal places:

    >>> Decimal("2.675").quantize(Decimal("0.01"))
    Decimal("2.68")

Since trailing zeros are significant, a result such as `Decimal("1.10") * 2` yields `Decimal("2.20")`, retaining the two decimal places. This is what financial users usually want.

## String conversion

`str()` returns a string in the scientific notation defined by the standard when that is shorter and a plain decimal notation otherwise. `repr()` returns an expression that can be passed back to the constructor. Conversion is exact. The formatted output of the number is not locale-dependent.

# Reference Implementation

The reference implementation is a pure-Python module, `decimal.py`, with an extensive test suite derived from the test cases published by Mike Cowlishaw. It is not fast, but is complete, and it is suitable for the standard library. A faster implementation in C may follow as a separate effort and must pass the same tests.

# Backwards Compatibility

The proposal adds a new module and a new type; no existing code is affected. Because `Decimal` does not mix with `float`, existing code that handles floats will not unexpectedly produce `Decimal` results.

# Open Issues and Discussion

- *Float interoperability.* There was long discussion over whether `Decimal(1.1)` should be allowed. The proposal is conservative: disallow it for now, and revisit when real-world usage provides evidence. Whether comparisons between `Decimal` and `float` should be permitted is similarly deferred.
- *Literals.* A literal syntax such as `1.1d` has been suggested. It is not part of this PEP; the constructor with a string is sufficient and avoids a language change.
- *Performance.* Pure Python arithmetic is slower by orders of magnitude than hardware floats. For the intended uses, where correctness matters more than speed, this is acceptable.
- *A fixed-point type.* Users who need a restricted fixed-point type can build one on top of `Decimal`.
