# Abstract

Python package installers are not completely interoperable with each other. While pip is the most widely used installer and a de facto standard, other installers such as Poetry or Pipenv are popular as well due to offering unique features which are optimal for certain workflows and not directly in line with how pip operates.

While the abundance of installer options is good for end-users with specific needs, the lack of interoperability between them makes it hard to support all potential installers. Specifically, the lack of a standard requirements file for declaring dependencies means that each tool must be explicitly used in order to install dependencies specified with their respective format. Otherwise tools must emit a requirements file which leads to potential information loss for the installer as well as an added export step in the workflow.

This PEP proposes a standardized API that a third-party installer can implement to be used by tools that want to install the dependencies of a project, without being tied to a particular installer. The API is declared in `pyproject.toml`, in the same spirit as PEP 517, and consists of a small set of commands that the installer must expose in a Python module.

# Motivation

Consider a hosted service that builds a Python project, for example a platform-as-a-service, a continuous integration product, or an editor that sets up a development environment. Such a service needs to install the project's dependencies. Today it can do so only for formats it already knows about: a `requirements.txt` file for pip, a `Pipfile.lock` for Pipenv, a `poetry.lock` for Poetry. Every time a new installer becomes popular, every service must add explicit support. Every time an installer changes its file format or command line, every service must adapt.

For installer authors the situation is symmetrical. A new installer has no way to be recognized by existing services unless each of them adds custom logic. This acts as a barrier to innovation and entrenches the incumbent.

For users, the cost is paid in friction. A project that uses Poetry on a developer's machine may need to export a `requirements.txt` for deployment. The export loses information such as markers and hashes in some cases, and the file can go stale relative to the lock file. Projects with multiple installers in use among their contributors face even more confusion.

PEP 517 and PEP 518 solved an analogous problem for *building* packages: a project declares in `pyproject.toml` which build backend to use and tools call a standard interface. This PEP does the same for *installing the dependencies of a project*.

# Rationale

The core idea is to let a project name the installer it prefers and describe how to invoke it through a stable programmatic interface. A tool that wants to install the project's dependencies reads `pyproject.toml`, installs the declared installer into an isolated environment, and calls the interface with the project directory. It does not need to know what format the installer reads, or whether it uses a lock file.

The interface is deliberately small. It covers three cases:

1. installing the dependencies needed to run the project in production;
2. installing the dependencies needed for development, which may include test and documentation tooling;
3. asking the installer which dependencies it would install, in a form the calling tool can display or audit.

It does not attempt to standardize lock-file formats, resolution algorithms or the command-line interface of installers. Those remain the business of the installers.

# Specification

## Declaring the installer

A new top-level table, `[dependency-installer]`, is added to `pyproject.toml`. To avoid colliding with the `[project]` table of PEP 621, it is kept separate from it. It has the following keys:

- `requires`: a list of PEP 508 strings naming the packages needed to run the installer. This is the equivalent of `build-system.requires`.
- `installer-path`: a string giving a `module` or `module:object` reference to the API entry point. The semantics mirror `build-backend` in PEP 517.

Example:

```toml
[dependency-installer]
requires = ["poetry-installer-api>=1.0"]
installer-path = "poetry_installer_api"
```

If the table is absent, tools are free to fall back to existing behaviours, such as looking for `requirements.txt`. No installer is assumed by this PEP.

## The API

The entry point must expose the following callables. All path arguments are `pathlib.Path` objects, or strings in the case of subprocess-style invocation, and refer to the project source tree.

### `invoke_install(path, *, dependency_group=None, **kwargs)`

Install the dependencies of the project at `path` into the currently active environment. `dependency_group` selects a named group if the installer supports them. The function returns `0` on success and a non-zero exit code on failure, mirroring a process exit status. It may write progress information to standard output and error. Unknown keyword arguments must be ignored, to permit forward compatibility.

### `invoke_uninstall(path, *, dependency_group=None, **kwargs)`

Remove the dependencies of the project previously installed by `invoke_install`. Behaves analogously. Uninstallation of a shared dependency that other installed packages require is installer-defined, though installers should avoid breaking unrelated packages.

### `get_dependencies_to_install(path, *, dependency_group=None, **kwargs)`

Return a mapping with keys `"dependencies"`, a list of PEP 508 strings, and `"extras"`, a list of strings naming extras, describing what would be installed. The values may be incomplete when the installer cannot compute them without network access, in which case it must raise `NotImplementedError`.

### `get_dependency_groups(path)`

Return the names of the dependency groups defined by the project.

### `update_dependencies(path, *, dependency_group=None, **kwargs)`

Re-resolve and update the lock file, if the installer uses one. Installers without lock files may no-op.

## Environment and isolation

The calling tool is responsible for creating an isolated environment, installing `requires`, and then invoking the entry point either in-process or in a subprocess. Because the installer must act on the *target* environment rather than its own, the calling tool tells it where that is by setting the `VIRTUAL_ENV` environment variable, or, for system installs, by running the entry point with the target interpreter. The installer must install into the interpreter that runs it, unless explicitly configured otherwise.

## Errors

Failures are reported by non-zero return codes or by raising an exception. Tools should treat any exception as a failure and surface its message to the user. The installer may print to standard error for diagnostics.

## Backwards compatibility with pip

pip is expected to provide an API shim, in a separate distribution, that reads a `requirements.txt` file located at the root of the project or a path configured under `[tool.pip]`. This allows the large number of existing projects to remain valid under the new scheme without changes, and allows services to treat the absence of the table as an implicit request for the pip shim.

# Backwards Compatibility

This PEP is additive. Projects without the new table are unaffected. Tools that do not understand it ignore it, as is the rule for unknown top-level tables in `pyproject.toml`.

# Security Implications

Executing a project-selected installer means executing code fetched from a package index chosen by the project author. This is the same trust model as PEP 517 build backends, but with a notable difference: installation of dependencies generally happens in contexts where the project is trusted by the user. A tool that installs dependencies for untrusted projects must sandbox the installer exactly as it would a build backend. Services should also pin or restrict the index used to install `requires`.

# Reference Implementation

A reference implementation of the calling side exists as a small library, together with a prototype API shim for pip. Prototype adapters for other installers are being developed with the cooperation of their maintainers.

# Rejected Ideas

**A new requirements file format.** A standard declarative file listing dependencies would be simpler but would not accommodate lock files, hash-checking or resolution strategies, which installers differ on, and which is the reason they exist.

**Command-line interface rather than Python API.** A subprocess interface with standardized flags would be easier to implement in non-Python tools, but cannot easily be extended and has no clean way to return structured data.

**Reuse of the PEP 517 table.** Installers and build backends are different roles, and a project may legitimately use setuptools to build and Poetry to install.

# Open Issues

- Naming of the table and entry-point keys.
- Whether dependency groups should be standardized before this PEP.
- How to express that an installer supports only some of the commands.
