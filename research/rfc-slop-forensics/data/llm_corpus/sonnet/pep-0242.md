# Abstract

This proposal gives the user optional control over the precision and range of numeric computations so that a computation can be written once and run anywhere with at least the desired precision and range. It is backward compatible with existing code. The meaning of decimal literals is clarified.

# Rationale

Currently it is impossible in every language except Fortran 90 to write a program in a portable way that uses floating point and gets roughly the same answer regardless of platform -- or refuses to compile if that is not possible. Python, like most languages, takes the types of its numbers from the machine. A Python `float` is a C `double` on the host, an `int` is a C `long`, and the range and precision follow from whatever the hardware and compiler provide.

For many applications this is fine. For numerical programmers, it is a serious problem. A program that works on a machine with 64-bit doubles may produce a different answer or a lower accuracy on a machine on which the equivalent type is shorter. A program written for a Cray, where the single precision type is 64 bits, might silently lose accuracy on a workstation. Conversely, a program written on a workstation may assume that `long` is 32 bits and overflow on a machine where it is 64, or the reverse.

Fortran 90 solved this by introducing *kinds*. Instead of asking for `double precision`, a programmer asks for a real with at least 12 decimal digits and a decimal exponent range of at least 100, via `selected_real_kind(12, 100)`. The compiler returns a kind that satisfies this on the target machine, or an error value if none does. The same program then gets at least the same quality of results everywhere, and fails clearly where this cannot be achieved.

This PEP proposes a comparable facility for Python.

# Specification

## Kinds

A *kind* is an integer-valued handle that identifies a numeric type with certain guaranteed properties. The kind is obtained from a function in a new module, here called `kinds`, and is used to create numbers of that type.

```python
import kinds

k = kinds.float_kind(digits=12, exponent=100)
x = k(1.5)
```

The `kinds` module provides the following functions.

**`kinds.int_kind(digits)`**
Returns a kind for integers that can represent every integer with at most `digits` decimal digits, in magnitude. If no such type exists, raises `KindError`.

**`kinds.float_kind(digits, exponent)`**
Returns a kind for floating point numbers with at least `digits` decimal digits of precision and a decimal exponent range of at least `exponent`, i.e. that can represent magnitudes from `10**-exponent` to `10**exponent`. If no such type exists, raises `KindError`.

**`kinds.complex_kind(digits, exponent)`**
Likewise for complex numbers, where each part satisfies the stated requirements.

Each kind is a callable that converts its argument to the corresponding type. Two kinds are equal if they denote the same underlying type. On a typical machine, `float_kind(6, 30)` yields the single precision type and `float_kind(12, 100)` yields double.

## Properties of kinds

The module also provides introspection:

- `kinds.precision(k)`: the number of decimal digits guaranteed for kind `k`.
- `kinds.range(k)`: the guaranteed exponent range.
- `kinds.default_float_kind`, `kinds.default_int_kind`: the kinds of the built-in `float` and `int` on this platform.
- `kinds.max_float_kind`, `kinds.max_int_kind`: the highest-quality kinds available.

## Operations on mixed kinds

When numbers of different kinds are combined, the result has the kind of the operand with greater precision, as with existing coercion rules. For two numbers of the same kind, the result has that kind.

## Literals

The meaning of numeric literals is clarified. A literal without a suffix has the default kind of its category: `1` is of `default_int_kind`, `1.0` is of `default_float_kind`. A new literal form is proposed that attaches a kind to a literal by means of a suffix, as in `1.5_k`, where `k` is the name of a kind bound in scope, following the Fortran notation. A decimal literal with more digits than the default kind can represent is rounded to the nearest representable value of the default kind, as it is today. The new literal is optional and could be left out of an initial implementation, since `k(1.5)` is equivalent, apart from a rounding step through the default float.

This last point is important. The expression `k(1.1)` first converts the text `1.1` to a default float and then converts it to `k`. If `k` has greater precision than the default float, the extra digits are lost. The suffix form, or alternatively `k("1.1")`, would avoid this. The PEP therefore proposes that kinds accept strings, converting directly from the decimal representation.

## Arrays and interfaces to C

Extensions such as Numeric Python store elements of a given C type. The proposal would let these packages accept kinds in their constructors. For example `array([1, 2, 3], kind=k)`. This aids portable programs, but is outside the scope of the core language change.

# Example

A portable numerical routine:

```python
import kinds

wp = kinds.float_kind(digits=12, exponent=100)   # working precision

def mean(values):
    total = wp(0)
    for v in values:
        total = total + wp(v)
    return total / wp(len(values))
```

On a machine with 64-bit doubles, this behaves as an ordinary double computation. On a machine that offers a longer type, it runs at higher precision where the hardware makes it cheap. On a machine that cannot provide 12 digits, importing the module or calling `float_kind` raises an error that explains why.

# Backward Compatibility

The proposal adds a module and a literal suffix. No existing programs are affected. `int`, `float` and `complex` keep their present meaning, and become the default kinds. The suffix form `1.5_k` is currently a syntax error, so adding it breaks no code.

# Implementation

The `kinds` module can be written in Python for a first version, probing the platform's types using `sys.maxint`, the floating point parameters from the C `float.h`, and, where available, extension types such as those from the GNU multiple precision library for kinds above the machine range. The literal suffix needs a change to the tokenizer and the compiler. The interaction with the proposed rational and decimal types is left open; they might be exposed as additional kinds.

# Discussion

Critics have argued that Python programmers rarely care about the exact precision of floats and that the facility would add complexity for little gain. Others point out that the audience for Python in scientific computing is growing and these users are the ones who most often hit portability issues. A related objection is that the need for kinds disappears if Python guarantees IEEE 754 doubles. This is difficult to guarantee on all platforms, since some lack hardware support.

There is also disagreement on whether the specification should use decimal digits or binary bits. Decimal digits, as in Fortran, are easier to reason about for users, while bits are closer to the hardware. The PEP follows Fortran, but permits bit-based queries as extras.
