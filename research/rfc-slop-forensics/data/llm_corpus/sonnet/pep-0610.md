PEP: 610
Title: Recording the Direct URL Origin of installed distributions
Author: Example Author <author@example.org>
Status: Draft
Type: Standards Track
Topic: Packaging
Created: 21-Apr-2019

# Abstract

Following PEP 440, a distribution can be identified by a name and either a version, or a direct URL reference (see PEP 440 Direct References). After installation, the name and version are captured in the project metadata, but currently there is no way to obtain details of the URL used when the distribution was identified by a direct URL reference. This proposal defines additional metadata, to be added to the installed distribution by the installation front end, which records the Direct URL Origin for use by consumers which introspect the database of installed packages (see PEP 376).

# Motivation

Installing from an index is the common case: a user asks for `name==1.0`, a front end resolves it against an index, and the installed distribution records `name` and `1.0` in its `.dist-info` directory. Anyone inspecting the environment later can reproduce the installation by asking the index again.

Direct references break this. A user may install a package from a version control repository, a local directory, or an archive at an arbitrary URL:

```
pip install "name @ git+https://example.org/project.git@v1.0"
pip install ./local/checkout
pip install https://example.org/dist/name-1.0.tar.gz
```

After the install, the installed metadata says only that version `1.0` of `name` is present. Nothing says that it came from a Git repository at a particular commit, or from a directory that may since have been edited. Tools that need this information have to guess or give up.

Several use cases motivate recording the origin:

* **Freezing environments.** A `freeze` command emits requirements that reproduce the environment. For a package installed from a Git URL, emitting `name==1.0` is wrong, since that version may not exist on any index, or may refer to a different build. The tool should emit the original direct reference, pinned to a commit.
* **Listing and diagnostics.** Tools that show installed packages benefit from showing where each came from, particularly for editable installs, where the source directory is the thing that matters.
* **Upgrade logic.** A front end deciding whether a requirement is already satisfied should know that an installed `name 1.0` came from a local checkout and is not interchangeable with the index release of the same version.
* **Editable detection.** Tools frequently want to know whether a distribution is installed in editable mode, and at what path. Today this is detected through ad hoc conventions, such as finding a `.egg-link` file.

Each tool currently implements its own heuristics, and they disagree.

# Specification

## The direct_url.json file

A front end installing a distribution from a direct URL reference MUST create a file named `direct_url.json` in the distribution's `.dist-info` directory. The file contains a single JSON object encoded as UTF-8.

A front end installing a distribution by any other means, for example by resolving a name and version against an index, MUST NOT create this file. Consumers MUST treat the absence of the file as meaning the distribution was not installed from a direct URL. Front ends SHOULD remove a stale file when a distribution is reinstalled or upgraded by other means.

The file is listed in the `RECORD` file like any other file in the `.dist-info` directory, and it is not covered by the installer-specific files that can be omitted from `RECORD`. It is considered part of the installer's output and is not to be modified by other tools.

## Top-level structure

The JSON object has the following keys:

* `url` (string, REQUIRED): the URL of the source, with credentials removed. See Security below.
* Exactly one of `archive_info`, `vcs_info` or `dir_info` (object, REQUIRED): information specific to the kind of source.

Additional keys MAY be present and MUST be ignored by consumers that do not recognise them.

## Archive

For a source archive or wheel at a URL, the object `archive_info` contains:

* `hash` (string, OPTIONAL): the hash of the archive in the form `<algorithm>=<hexdigest>`. The algorithm MUST be one listed in `hashlib.algorithms_guaranteed`. When a hash was supplied in the URL fragment of the original requirement, it is recorded here and removed from `url`.

Example:

```json
{
  "url": "https://example.org/dist/name-1.0.tar.gz",
  "archive_info": {"hash": "sha256=3a5f..."}
}
```

## Version control

For a source obtained from a version control system, `vcs_info` contains:

* `vcs` (string, REQUIRED): the VCS command, such as `git`, `hg`, `bzr` or `svn`.
* `commit_id` (string, REQUIRED): the exact revision that was installed, as an unambiguous identifier. For Git this is the full commit hash.
* `requested_revision` (string, OPTIONAL): the branch, tag or revision named by the user. It is informative only, since the branch or tag may have moved by the time the file is read.

The `url` is the repository URL without the `vcs+` prefix and without the revision suffix. A consumer reconstructing a requirement should join them: `<vcs>+<url>@<commit_id>`.

Example:

```json
{
  "url": "https://example.org/project.git",
  "vcs_info": {
    "vcs": "git",
    "requested_revision": "v1.0",
    "commit_id": "1f2e3d4c5b6a79880123456789abcdef01234567"
  }
}
```

## Local directory

For a source in a local directory, `dir_info` contains:

* `editable` (boolean, OPTIONAL): true if the distribution was installed in editable mode. If absent, consumers MUST treat it as false.

The `url` is a `file://` URL naming the directory. Because directories change, the metadata describes where the installation came from, not its content.

Example:

```json
{
  "url": "file:///home/user/checkout",
  "dir_info": {"editable": true}
}
```

## Registered requirement conversion

A front end that wishes to emit a requirement for the installed distribution from this file SHOULD use the following form: for VCS, `name @ vcs+url@commit_id`; for archives, `name @ url#hash`; for directories, `name @ url`. For editable directory installs, tools producing a requirements file MAY emit `-e url` in whatever syntax they support.

# Security considerations

URLs may contain credentials in the userinfo component or in the query string. Recording them in a file readable by every user of the environment would leak secrets. A front end MUST therefore strip a password from the URL before writing it. A username MAY be retained if it is not a secret; specifically, the common case of `git` in `ssh://git@host/path` SHOULD be preserved because it is part of how the repository is addressed. Where the URL contains an environment variable reference, such as `https://${TOKEN}@host/path`, the reference SHOULD be preserved in unexpanded form so that no secret is written.

Consumers must treat the content of the file as untrusted input, as with any file in a site-packages directory, and must not execute or fetch the URL merely because the file is present.

# Backwards compatibility

The change is purely additive. The file lives in a directory whose contents are defined by PEP 376 and that tools already handle by ignoring unknown names. Distributions installed before this PEP lack the file, and consumers handle that case as "not from a direct URL", which may be inaccurate for those distributions but is the same information they have today.

# Rejected ideas

**Embedding the information in METADATA.** The core metadata file describes the distribution as built by its author. The origin is a fact about one installation, not about the distribution. Mixing them would make rebuilding or comparing metadata unreliable.

**Reusing the `INSTALLER` or `REQUESTED` files.** These are single-purpose marker files with plain text contents. The origin data is structured, and JSON allows extension without parsing changes.

**Recording index information for non-direct installs.** Index installs are reproducible from name and version, and recording the index URL would capture private mirrors. This could be a later proposal.

# Reference implementation

The behaviour described here has been prototyped in pip, whose `freeze` and `list` commands consume the file and whose installation code produces it for VCS, archive and directory requirements.
