# PEP 3134: Exception Chaining and Embedded Tracebacks

- **Status:** Draft
- **Type:** Standards Track
- **Created:** 12-May-2005
- **Python-Version:** 3.0

## Abstract

This PEP proposes three standard attributes on exception instances: the `__context__` attribute for implicitly chained exceptions, the `__cause__` attribute for explicitly chained exceptions, and the `__traceback__` attribute for the traceback. A new `raise ... from` statement sets the `__cause__` attribute.

## Motivation

During the handling of one exception (exception A), it is possible that another exception (exception B) may occur. In today's Python (version 2.4), if this happens, exception B is propagated outward and exception A is lost. In order to debug the problem, it is useful to know about both exceptions. The `__context__` attribute retains this information automatically.

Sometimes it can be useful for an exception handler to intentionally re-raise an exception, either to provide extra information or to translate an exception to another type. The `__cause__` attribute provides an explicit way to record the direct cause of an exception.

In today's Python implementation, exceptions are composed of three parts: the type, the value, and the traceback. The `sys` module exposes the current exception in three parallel variables, `exc_type`, `exc_value`, and `exc_traceback`, the `sys.exc_info()` function returns a tuple of these three parts, and the `raise` statement has a three-argument form accepting these three parts. Manipulating exceptions often requires passing these three things in parallel, which can be tedious and error-prone. Additionally, the `except` statement can only provide access to the value, not the traceback. Adding the `__traceback__` attribute to exception values makes all the exception information accessible from a single place.

## History

Raymond Hettinger [1] raised the issue of masked exceptions on Python-Dev in January 2003 and proposed a `PyErr_FormatAppend()` function that C modules could use to augment the currently active exception with more information. Brett Cannon [2] brought up chained exceptions again in June 2003, prompting a long discussion.

Greg Ewing [3] identified the case of an exception occurring in a `finally` block during unwinding triggered by an original exception, as distinct from the case of an exception occurring in an `except` block that is handling the original exception.

Greg Ewing [4] and Guido van Rossum [5], and probably others, have previously mentioned adding a traceback attribute to Exception instances. This is noted in PEP 3000.

This PEP was motivated by yet another recent Python-Dev reposting of the same ideas [6] [7].

## Rationale

The Python-Dev discussions revealed interest in two different ways of chaining exceptions.

1. **Implicit chaining.** When an exception is raised while another is being handled, the new exception should record the one that was being handled.
2. **Explicit chaining.** A programmer who deliberately raises a new exception in response to a caught one should be able to say so, and to distinguish this from an accidental secondary failure.

The two are different in intent, and a traceback should be able to say which occurred. In the first case, the message is "while handling this, something else went wrong"; in the second, "this exception was the direct consequence of that one". Collapsing them into a single mechanism loses information that matters when reading a report at three in the morning.

Embedding the traceback in the exception object has a related justification. Once an exception is chained to another, the chain must carry the traceback of each link, or the information that chaining exists to preserve would be incomplete. Attaching the traceback to the instance also makes it possible to pass exceptions around without the three-valued tuple.

## Specification

### Implicit exception chaining

Here is an example to illustrate the `__context__` attribute:

    def compute(a, b):
        try:
            a / b
        except Exception as exc:
            log(exc)

    def log(exc):
        file = open('logfile.txt')   # oops, forgot the 'w'
        print(exc, file=file)
        file.close()

Calling `compute(1, 0)` raises a `ZeroDivisionError`. The exception is caught by the `except` clause in `compute`, but then a second exception occurs in `log`: an `IOError` because the file is not writable. In today's Python, the `ZeroDivisionError` is lost. With this proposal, the `IOError` instance has an attribute `__context__` that refers to the `ZeroDivisionError`, and the traceback printed shows both.

The `__context__` attribute is set when a new exception is raised while another is being handled. It is `None` when no exception was being handled. It is set by the interpreter at the moment of the raise, and only if the attribute is not already set explicitly.

### Explicit exception chaining

The `__cause__` attribute on exception objects is always initialized to `None`. It is set by a new form of the `raise` statement:

    raise EXCEPTION from CAUSE

which is equivalent to:

    exc = EXCEPTION
    exc.__cause__ = CAUSE
    raise exc

In the following example, a database provides implementations for a few different kinds of storage, with file storage as one kind. The database designer wants errors to propagate as `DatabaseError` objects so that the client does not have to be aware of the storage-specific details, but does not want to lose the underlying error information.

    class DatabaseError(Exception):
        pass

    class FileDatabase(Database):
        def __init__(self, filename):
            try:
                self.file = open(filename)
            except IOError as exc:
                raise DatabaseError('failed to open') from exc

If the call to `open()` raises an exception, the problem will be reported as a `DatabaseError`, with a `__cause__` attribute that reveals the `IOError` as the original cause.

### Traceback attribute

The following example illustrates the `__traceback__` attribute.

    def do_logged(file, work):
        try:
            work()
        except Exception as exc:
            write_exception(file, exc)
            raise exc

    from traceback import format_tb

    def write_exception(file, exc):
        ...
        type = exc.__class__
        message = str(exc)
        lines = format_tb(exc.__traceback__)
        file.write(... type ... message ... lines ...)
        ...

In today's Python implementation, this would not work because `exc` has no `__traceback__`. The programmer would have to retrieve the traceback from `sys.exc_info()` and pass it along as a separate argument. With this proposal, the traceback is carried by the exception.

### Enhanced reporting

The default exception handler will be modified to report chained exceptions. The chain of exceptions is traversed by following the `__cause__` and `__context__` attributes, with `__cause__` taking priority. In keeping with the chronological order of tracebacks, the most recently raised exception is displayed last; that is, the display begins with the description of the innermost exception and backs up the chain to the outermost.

The tracebacks are formatted as usual, with one of the lines:

    The above exception was the direct cause of the following exception:

or

    During handling of the above exception, another exception occurred:

between tracebacks, depending whether they are linked by `__cause__` or `__context__` respectively. Here is a sketch of the procedure:

    def print_chain(exc):
        if exc.__cause__:
            print_chain(exc.__cause__)
            print('The above exception was the direct cause...')
        elif exc.__context__:
            print_chain(exc.__context__)
            print('During handling of the above exception, ...')
        print_exc(exc)

In the `traceback` module, the `format_exception`, `print_exception`, `print_exc`, and `print_last` functions will be updated to accept an optional `chain` argument, `True` by default. When this argument is `True`, these functions will format or display the entire chain of exceptions as just described. When it is `False`, they will show only the outermost exception.

### C API

The `PyErr_Set*` calls for setting exceptions will not set the `__context__` attribute on exceptions. `PyErr_NormalizeException` will always set the `traceback` attribute to its `tb` argument and the `__context__` and `__cause__` attributes to `None`.

A new API function, `PyException_SetContext(exc, ctx)`, will help C programmers provide chained exception information. This function will first normalize the current exception so it is an instance, then set its `__context__`. A similar API function `PyErr_FormatAppend` was suggested earlier; it is not included here.

## Compatibility Issues

Chained exceptions mean that exception objects can hold references to other exception objects, and to tracebacks, and thereby to frames and their local variables. This can create reference cycles: a traceback refers to a frame, whose locals may include the exception being handled, which refers to the traceback. In Python 2 the same risk existed with `sys.exc_info()`. The cycle collector will reclaim such cycles, but the lifetime of local variables may be extended until it runs. To reduce the problem for the common `except E as name` form, the name bound by the clause will be deleted at the end of the handler, as though by `del name`.

Because the `raise` statement with three arguments is already slated for removal in Python 3000, no new incompatibility arises from the traceback being carried by the instance.

Code that inspects `sys.exc_info()` continues to work. Code that defines its own `__context__`, `__cause__`, or `__traceback__` attributes on exception classes will see them overwritten, which is considered unlikely enough to be acceptable.

## Open Issues

- **Suppressing the context.** A programmer who deliberately translates an exception may not want the implicit context to appear in the output. A future extension could allow `raise ... from None` for this.
- **Mutation of `__context__`.** Whether the interpreter should avoid creating cycles in the chain when an exception is re-raised inside its own handler. The reference implementation checks and breaks such cycles.
- **Naming.** Alternatives such as `__previous__` and `__reason__` were considered and rejected in favor of `__context__` and `__cause__`, which are more descriptive.
