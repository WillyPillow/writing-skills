# Summary
[summary]: #summary

This RFC proposes the *2017 Rust Roadmap*, in accordance with [RFC 1728](https://github.com/rust-lang/rfcs/pull/1728). The goal of the roadmap is to lay out a vision for where the Rust project should be in a year's time. **This year's focus is improving Rust's *productivity*, while retaining its emphasis on fast, reliable code**. At a high level, by the end of 2017:

* Rust should have a lower learning curve
* Rust should have a pleasant edit-compile-debug cycle
* Rust should provide a solid, but basic IDE experience
* Rust should provide easy access to high quality crates
* Rust should be well-equipped for writing robust, high-scale servers
* Rust should have 1.0-level crates for essential tasks
* Rust should integrate easily into large build systems
* Rust's community should provide mentoring at all levels

In addition, we should make significant strides in exploring two areas where we're not sure how best to focus our energies, and where the use of Rust is likely to have a major impact: machine learning and embedded devices.

Finally, the Rust compiler is the single biggest bottleneck... in this process, it should serve as a platform for the tooling above, and so a number of the goals depend on structural improvements to the compiler.

# Motivation
[motivation]: #motivation

Rust 1.0 was released in May 2015, and the language has since gone through two years of steady, compatible improvement. The 2016 roadmap focused on stabilizing the foundation and on expanding the set of platforms and the ecosystem. Rust today is a language whose strengths are well known: memory safety without garbage collection, predictable performance, and fearless concurrency. The common feedback from users, in surveys, on forums and in conversations, is that while Rust is powerful, working with it can be unproductive in ways that are not essential to its design. People struggle during the first weeks. They wait a long time for the compiler. They miss the code completion and navigation that they enjoy in other languages. They have trouble choosing between multiple crates for the same task, or find that the crate they need does not exist or has not reached a stable release.

The 2017 roadmap therefore focuses on productivity: removing friction that does not serve the core promises of the language. The aim is not to make Rust less rigorous but to make the rigor easier to live with.

The roadmap is organized into a handful of themes, each with a small number of concrete goals. Not every goal will be reached, and some will depend on community contributors rather than on the core teams. The point is to supply a shared direction, so that contributors can see how their work fits and so that effort is not dissipated.

# Detailed design
[detailed-design]: #detailed-design

## Rust should have a lower learning curve

Learning Rust is hard because the ownership and borrowing model asks the programmer to internalize a discipline that other languages do not demand. We cannot, and do not wish to, remove it. But we can lower the cost of acquiring it.

- **Ergonomic improvements.** Continue the work on the borrow checker to accept more programs that are intuitively correct. The most important is *non-lexical lifetimes*, which allows borrows to end when the reference is last used rather than at the end of the enclosing scope. An implementation plan should be agreed and landed in early 2017, with an initial version available on nightly by mid-year.
- **Error messages.** Continue investing in diagnostics, including suggestions for common errors and links to explanatory text. Every error code should have a long-form explanation with examples.
- **Documentation.** Complete the second edition of the book, with an emphasis on teaching ownership through examples. Improve the reference and the standard library documentation, adding runnable examples to every public item.
- **Learning resources beyond text.** Support interactive and video-based materials, workshops and other formats.

## Rust should have a pleasant edit-compile-debug cycle

Compile times are the top complaint of experienced users. The goal is to make rebuilding after a small change fast.

- **Incremental compilation.** Ship incremental compilation in a form usable by default for development builds, and gather data on how well it works on real projects.
- **Parallelism.** Work on parallelizing code generation across more cores, and on improving the build pipeline so that Cargo makes more effective use of the machine.
- **Faster type-checking and trans.** Identify and fix the worst algorithmic hot spots through profiling of real crates, and expose the compiler's own time-reports.
- **Debugging.** Improve debug information so that debuggers show Rust types well, and make the debugging experience on all tier-one platforms consistent.

## Rust should provide a solid, but basic IDE experience

Many developers will not consider a language without editor support. Rather than build a bespoke IDE, we aim for a set of reliable building blocks that editors can use:

- A compiler-independent service providing completion, go-to-definition, find-references and rename, driven by the same front end as rustc where possible. A first version should be ready for broad testing by the end of the year.
- Reliable formatting via rustfmt, with a stable default style. Ensure that `rustfmt` can handle the entire language, and adopt a style RFC process.
- Solid support for the Language Server Protocol if it matures, so that one implementation can serve many editors.

## Rust should provide easy access to high quality crates

Cargo and crates.io are among Rust's greatest strengths. Discovery and trust remain weak.

- Improve crates.io search and ranking, with signals such as download counts, recent activity and documentation coverage.
- Add categories and curated lists so users find the recommended crate for each task.
- Display documentation builds, build status and license information prominently.
- Develop a policy for *crate evolution*, including how crates are deprecated and how maintainers are transferred.
- Make the Cargo workflow better for large teams: workspaces, features, and build scripts.

## Rust should be well-equipped for writing robust, high-scale servers

Servers are the area where Rust has the largest number of production users. Needs include asynchronous I/O, a coherent story about futures, and mature libraries for protocols.

- Settle on a futures-based foundation and support its adoption by key crates; continue the work on `tokio` and related libraries.
- Investigate language support for asynchronous programming, such as generators or `async`/`await` syntax, and write an RFC if the design is clear.
- Provide guidance on error handling, logging, metrics and tracing for services.

## Rust should have 1.0-level crates for essential tasks

A number of foundational crates, among them libraries for serialization, HTTP, date and time, regular expressions, random numbers and logging, should reach a stable 1.0 release with a commitment to compatibility. The Libs team will maintain a list of such crates and work with maintainers on API review, documentation and testing. This is the basis of the "Rust Platform" idea, in which a curated set of crates is distributed alongside the compiler.

## Rust should integrate easily into large build systems

Large organizations use Bazel, Buck, Make, and custom systems. They need a way to invoke rustc with reproducible inputs and outputs and to integrate third-party crates.

- Document the compiler's command line and the format of its outputs.
- Provide a way to retrieve dependency information from Cargo in machine-readable form.
- Reduce the amount of ambient state (environment variables, global caches) that influences compilation.

## Rust's community should provide mentoring at all levels

Rust's community is its strongest asset. Mentoring takes many forms: guiding newcomers to the language, guiding new contributors to the compiler, and developing experienced contributors into team members. We will label issues for newcomers, hold regular office hours, and write contributor guides. Teams should designate mentors for each accepted RFC.

## Exploration: machine learning and embedded

For machine learning, the project will gather the interested community members, identify blockers, and assess whether Rust's strengths fit the field. For embedded devices, we will push on stabilizing the parts of the language and toolchain required to run on bare metal, including cross-compilation and `no_std` support.

# How We Teach This
[how-we-teach-this]: #how-we-teach-this

The roadmap will be published on the project blog, and the team leads will report progress at regular intervals. Each goal will map to tracking issues so that anyone can follow along.

# Drawbacks
[drawbacks]: #drawbacks

A roadmap risks raising expectations that are not fulfilled, since the project depends mostly on volunteers. It may also divert attention from valuable work that does not fit under any theme. We mitigate this by phrasing goals as directions and by leaving room for contributions elsewhere.

# Alternatives
[alternatives]: #alternatives

We could have no roadmap, or one that is a long list of features. The RFC 1728 process, which asks for a short, themed vision, was adopted precisely to avoid those outcomes.

# Unresolved questions
[unresolved]: #unresolved-questions

Which goals depend on foundational compiler work that has not yet been scheduled? How should the project measure progress on "pleasant" or "lower learning curve", which are subjective? These will be addressed through surveys and by tracking concrete proxies such as build times and the number of questions on common errors.
