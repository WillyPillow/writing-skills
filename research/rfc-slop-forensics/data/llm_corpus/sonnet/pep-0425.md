# PEP 425: Compatibility Tags for Built Distributions

- **Status:** Draft
- **Type:** Standards Track
- **Created:** 27-Jul-2012
- **Post-History:** 8-Aug-2012

## Abstract

This PEP specifies a tagging system to indicate with which versions of Python a built or binary distribution is compatible. A set of three tags indicate which Python implementation and language version, ABI, and platform a built distribution requires. The tags are terse because they will be included in filenames.

## Rationale

Today, Python distributions that include compiled extensions or that depend on a specific platform are difficult to name in a way that lets an installer choose the right file without downloading and opening it. Source distributions have a single name, since the same source applies everywhere, but a built distribution is the product of a particular interpreter running on a particular operating system with a particular set of build options. If a project publishes several built distributions for the same version, an installer must know which of them can run on the machine at hand.

Historically, the answer has been a set of ad hoc conventions. The `bdist_*` family of commands in distutils produces names that encode the platform and Python version in different ways, none of which are machine-parseable with certainty. Installers resort to guessing, to trial installation, or to compiling from source.

A small, regular tagging scheme makes the answer obvious. If the compatibility information can be placed into the filename in a fixed position, then a tool can decide whether a file is usable by looking at the name alone, with no network round trip beyond the directory listing.

The tags are also useful to indexes and mirrors, which can filter or sort files without opening them, and to build systems that must label what they have produced.

## Overview

The tag consists of three components, separated by hyphens when used in a filename:

    {python tag}-{abi tag}-{platform tag}

For example, `cp33-cp33m-win32` identifies a build for CPython 3.3, using the CPython 3.3 ABI with pymalloc, on 32-bit Windows. The tag `py27-none-any` identifies a build for Python 2.7 that uses no compiled code and can run on any platform.

A distribution may declare compatibility with several tags at once, by joining alternatives for a component with a dot. For instance, `py2.py3-none-any` states that the same file is valid for both Python 2 and Python 3.

## Details

### Python Tag

The Python tag indicates the implementation and version required by a distribution. Major implementations have abbreviated codes, initially:

- `py`: Generic Python (does not require implementation-specific features)
- `cp`: CPython
- `ip`: IronPython
- `pp`: PyPy
- `jy`: Jython

Other Python implementations should use `sys.implementation.name`.

The version is `py_version_nodot`. CPython gets away with no dot, but if one is needed the underscore `_` is used instead. PyPy should probably use its own versions here, `pp18`, `pp19`.

The version can be just the major version, `2` or `3`, as in `py2` or `py3`, or it can be major and minor, as in `py27` or `py33`. A generic tag with no minor version indicates compatibility with every minor version of that major version.

### ABI Tag

The ABI tag indicates which Python ABI is required by any included extension modules. For implementation-specific ABIs, the implementation is abbreviated in the same way as the Python Tag, e.g. `cp33d` would be the CPython 3.3 ABI with debugging.

The CPython stable ABI is `abi3`, as in the shared library suffix `abi3.so`.

Other Python implementations might define their own ABI tags, using their own version scheme.

For CPython, the ABI tag is the Python tag followed by flag letters:

- `d` for a debug build (`Py_DEBUG`),
- `m` for builds using pymalloc,
- `u` for builds with wide Unicode (`Py_UNICODE_SIZE == 4`).

A distribution that includes no extension modules, and therefore has no ABI dependence, uses the tag `none`.

### Platform Tag

The platform tag is simply `distutils.util.get_platform()` with all hyphens `-` and periods `.` replaced with underscore `_`.

- `win32`
- `linux_i386`
- `linux_x86_64`
- `macosx_10_6_x86_64`

A distribution that works on every platform, because it contains only Python source or bytecode and no platform-specific code, uses the tag `any`.

The replacement of punctuation matters because the tag will be embedded in filenames where hyphens separate the components and periods separate alternatives. A platform string containing either would produce an ambiguous or unparseable name.

### Use

The tags are used in the filename of a built distribution. For wheel files (PEP 427), the filename is:

    {distribution}-{version}(-{build tag})?-{python tag}-{abi tag}-{platform tag}.whl

Tools that produce built distributions should record the tags that apply to the file in its metadata, in addition to the filename, so that a mismatch between the two can be detected.

An installer should compute the ordered list of tags that the running interpreter supports and select from the available files the one whose tag appears earliest in that list. The ordering is described next.

### Compressed Tag Sets

To allow one file to serve several environments, each of the three components may itself be a dot-separated set. The full set of tags represented is the Cartesian product of the three sets. A file named `foo-1.0-py2.py3-none-any.whl` is compatible with the tags `py2-none-any` and `py3-none-any`.

An installer must expand compressed sets before comparison.

### Supported Tags and Their Ordering

The list of tags supported by an installation is ordered from most specific to least specific. A typical ordering for CPython 3.3 on 64-bit Linux might be:

1. `cp33-cp33m-linux_x86_64`
2. `cp33-abi3-linux_x86_64`
3. `cp33-none-linux_x86_64`
4. `cp32-abi3-linux_x86_64`
5. `py33-none-linux_x86_64`
6. `py3-none-linux_x86_64`
7. `cp33-none-any`
8. `py33-none-any`
9. `py3-none-any`
10. `py32-none-any`
11. `py31-none-any`
12. `py30-none-any`

The first match wins. The reasoning is that a file built specifically for the interpreter at hand is more likely to be correct and more highly optimized than a generic one. Generic pure-Python files sit at the end of the list as the fallback.

The exact ordering is a recommendation for installers and not part of the tag definition itself. Tools may offer options for the user to override the ordering or to restrict it to certain tags.

## FAQ

**Why isn't the tag in the middle of the version, as in a PEP 386 local version?**
The tag describes the build, not the release. Two files for the same release differ in tags but share a version.

**Why not use the full triple from the compiler, such as `x86_64-linux-gnu`?**
The Python platform string is already available on every installation, is understood by distutils, and does not require any new probing logic.

**What about Linux distributions?**
`linux_x86_64` makes no promises about the libc or other system libraries. That a wheel built on one distribution will work on another is not guaranteed by this PEP. A future PEP may define more precise Linux tags for this purpose.

**Why `none` and `any`, rather than empty?**
Empty components would produce adjacent hyphens, which are harder to read and to parse.

**Does the tag replace requires-python metadata?**
No. The tag is a coarse filter intended for use in filenames. More detailed requirements belong in the metadata.
