PEP: 442
Title: Safe object finalization
Status: Draft
Type: Standards Track
Created: 18-May-2013
Python-Version: 3.4

# Abstract

This PEP proposes to deal with the current limitations of object finalization. The goal is to be able to define and run finalizers for any object, regardless of their position in the object graph.

This PEP doesn't call for any change in Python code. Objects with existing finalizers will benefit automatically.

# Definitions

Reference
: A directional link from an object to another. The target of the reference is kept alive by the reference, as long as the source is itself alive and the reference is not cleared.

Weak reference
: A directional link from an object to another, which doesn't keep alive its target. This PEP focuses on non-weak references.

Reference cycle
: A cyclic subgraph of directional links between objects, which keeps those objects from being collected in a pure reference-counting scheme.

Cyclic isolate (CI)
: A reference cycle in which no object is referenced from outside the cycle and whose objects are still in a usable, non-finalized state.

Finalizer
: A function or method called when an object is intended to be disposed of. In Python, this is the `__del__` method for pure-Python classes, and the `tp_del` slot for extension types.

# Rationale

## Reference-counting and finalization

In CPython, most objects are disposed of as soon as their reference count drops to zero. When this happens, the interpreter calls the object's finalizer, if any, before freeing its memory. Since an object is reclaimed immediately, the finalizer can assume that the object is in a consistent state and that the objects it references are still alive, because the object holds references to them.

## Cyclic garbage collection

Reference counting cannot dispose of objects that participate in reference cycles. For these, CPython has a cyclic garbage collector, implemented in `Modules/gcmodule.c`. The collector detects groups of objects that are unreachable from outside the group, and clears the references they hold in order to break the cycles, after which reference counting does the rest.

## The limitation

When the garbage collector finds a cyclic isolate in which some objects have finalizers, it faces a problem. The finalizers may access other objects in the cycle, and those objects might be cleared by the collector before or after the finalizer runs. There is no natural order that is guaranteed to be safe, since cycles have no root. Because there is no safe order, CPython has chosen to refuse the risk: such objects are not collected at all. They are placed in the `gc.garbage` list instead, where they remain until the application takes care of them.

This policy has three consequences:

1. Objects with a `__del__` method which participate in a reference cycle leak memory, and also leak any resources they hold, such as file descriptors, locks, and database connections.
2. The leak is silent unless `gc.set_debug(gc.DEBUG_UNCOLLECTABLE)` is enabled, so the problem is not easily diagnosed.
3. The behavior depends on an accident of the object graph. A class that works correctly in simple use may leak when somebody stores a back-reference in an instance, or when a new version of the library adds a parent pointer.

Programmers who wish to avoid the problem are told to use weak references, to break cycles by hand, or to avoid `__del__` altogether. These are all valid techniques, but they put a burden on every user of the class, not only on its author, and they are often impractical for third-party objects.

A related issue is that some extension types, for example those wrapping a C resource, need a finalizer and cannot avoid being part of cycles because they refer to Python callbacks.

# Proposal

## Summary of changes

The proposal has three parts:

1. A new slot, `tp_finalize`, on type objects, with the signature `void (*tp_finalize)(PyObject *)`. It is called at most once for each object, before the object's memory is reclaimed or its contents cleared. This is the single entry point for finalization, and replaces `tp_del` for new code.
2. A change to the cyclic garbage collector so that it calls `tp_finalize` on every object in a cyclic isolate before it clears any references, and then checks whether any object was resurrected.
3. A new bit, in the object header, recording whether the finalizer has been called, so that it is not invoked twice.

For Python classes, defining `__del__` fills `tp_finalize` automatically via the `slot_tp_finalize` wrapper. No change is required in Python code.

## Semantics of `tp_finalize`

The `tp_finalize` function is called when the interpreter determines that the object is about to be destroyed. It may be invoked in two situations: when the reference count drops to zero, or when the cyclic garbage collector finds the object in an unreachable cyclic isolate.

The function can execute arbitrary code, including code that creates new references to the object (resurrection). If the object has been resurrected after the finalizer returns, destruction is cancelled, and the object lives on. In that case the finalizer is not called a second time when the object is eventually collected: the "finalized" flag prevents it.

## Changes to the garbage collector

When `collect()` finds a set of unreachable objects, the new algorithm is:

1. Identify unreachable objects, as it does now.
2. Handle weak references to unreachable objects, invoking callbacks as it does now.
3. For each unreachable object whose type has `tp_finalize` and whose "finalized" flag is not set, call `tp_finalize`. Set the flag before the call, so that a finalizer which triggers collection recursively will not run it again.
4. Recompute the set of unreachable objects, since finalizers may have resurrected some of them. Objects that are still reachable are removed from the set, along with everything they reference.
5. Clear the remaining objects through `tp_clear` and let reference counting reclaim them.

Step 4 is critical for safety. It means that after the finalizers have run, the collector never touches an object that is reachable. If a finalizer resurrects the object by storing it in a global, the collector leaves it alone.

## Legacy finalizers

Extension types that define `tp_del` retain their old behavior for backward compatibility. Objects whose types have `tp_del` but no `tp_finalize` continue to be placed in `gc.garbage` when found in cycles. A new `Py_TPFLAGS_HAVE_FINALIZE` flag identifies types that define the new slot, so that old extension modules compiled against older headers are not misinterpreted.

The `gc.garbage` list is retained and continues to hold the legacy uncollectable objects.

## Order of finalizer calls

The order in which finalizers are called within a cyclic isolate is unspecified. Finalizers must not assume that other objects in the isolate have not yet been finalized, but they can assume that no object has been cleared. This is the key guarantee: since clearing happens only after all finalizers have run, every object that a finalizer can reach is still fully intact.

This is a weaker guarantee than the ordering available in reference-counted destruction, but is a strong enough one for the most common uses, such as closing a file or releasing a lock.

# Backwards compatibility

Pure Python code needs no change. Classes with `__del__` that were previously leaked in cycles will now be collected. This is a behavior change but a beneficial one. Programs that inspect `gc.garbage` to find objects with finalizers will find it empty more often.

Some programs might depend, accidentally, on the leak: for instance, a finalizer which never runs because the object is kept alive in `gc.garbage`. Such programs would now see the finalizer run. We consider this an acceptable change.

Extension modules that define `tp_del` continue to work unchanged. Authors are encouraged to migrate to `tp_finalize`. The `tp_del` slot is deprecated, though it will not be removed in the foreseeable future.

# Performance

The additional work in the collector consists of a pass over unreachable objects to find those needing finalization, and a second reachability check if any finalizer ran. Both are proportional to the number of unreachable objects, not to the whole heap, so the cost is small. The additional flag bit uses space already available in the GC header on supported platforms.

For reference-counted destruction, the cost is one additional flag check per deallocation, which is negligible.

# Discussion

## Why not run finalizers in a fixed order?

A natural idea is to order finalizers topologically in the object graph. This is impossible in a cycle, and heuristics for breaking cycles (such as creation order) would be fragile and surprising. Decoupling finalization from clearing is simpler and provides the safety property directly.

## Why not remove `__del__`?

`__del__` is widely used, including in the standard library. Its removal would break compatibility with a large body of code. The goal is to make it behave well.

## Resurrection

Resurrection is permitted and supported. It is rare, and mostly a consequence of the generality of the finalizer. The flag ensures a finalizer runs only once per object even in the presence of resurrection. Users who want a finalizer to run again can create a new object.

# Implementation

A patch implementing the proposal is available on the issue tracker. It adds the slot, the flag, the changes to `gcmodule.c`, and the wrapper for Python classes, with tests covering cyclic isolates containing finalizable objects, resurrection, and nested collections triggered inside finalizers.
