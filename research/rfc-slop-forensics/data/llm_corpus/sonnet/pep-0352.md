# PEP 352: Required Superclass for Exceptions

- Status: Draft
- Type: Standards Track
- Python-Version: 2.5

## Abstract

In Python 2.4 and before, any (classic) class can be raised as an exception. The plan for 2.5 was to allow new-style classes, but this makes the problem worse: it would mean *any* class (or instance) can be raised! This is a problem as it prevents any guarantees from being made about the interface of exceptions. This PEP proposes introducing a new superclass that all raised objects must inherit from. Imposing the restriction will allow a standard interface for exceptions to exist that can be relied upon. It also leads to a known hierarchy for all exceptions to adhere to.

One might counter that requiring a specific base class for a particular interface is unPythonic. However, in the specific case of exceptions there's a good reason (which has generally been agreed to on python-dev): requiring hierarchy helps code that catches exceptions to know what it is dealing with and to write robust handlers. Duck typing works best when the set of attributes involved is small and optional, which is not the case for exceptions, where handlers typically want to print a message, inspect arguments, and reliably catch whole families.

## Rationale

Exceptions are an unusual part of the language. In most places Python uses duck typing: if an object has the right methods, it can be used. Exceptions, though, are treated by the `raise` and `except` statements in a way that is specific to them. When an exception is caught, the interpreter compares classes using the inheritance relation. The `except` clause matches only if the raised class is the named class or a subclass of it. So inheritance is already the central mechanism by which exceptions are organized, and the standard library defines a hierarchy that users expect to be able to rely on.

Today, nothing about that hierarchy is enforced. A string can be raised, as can an instance of an arbitrary old-style class. The consequences include:

* A handler cannot assume that the caught object has a `message` or `args` attribute, so generic logging code has to be defensive.
* A bare `except:` clause catches everything, including exceptions that were not intended to be caught, such as `KeyboardInterrupt` and `SystemExit`, because there is no way to tell them apart from ordinary errors using a class test. The bare clause is the only way to catch string exceptions and exceptions that do not derive from `Exception`.
* New-style classes cannot be exceptions without special handling in the interpreter.

Adding new-style classes to the set of allowed exceptions, as was planned for 2.5, would simplify the interpreter but would further widen the set of legal objects. A restriction is the better course.

## Specification

### The `BaseException` class

A new class, `BaseException`, is added to the `exceptions` module as the root of the exception hierarchy. It provides the following interface, which all exceptions can then rely upon:

* `BaseException(*args)`: the constructor accepts any number of arguments, which are stored in the attribute `args` as a tuple.
* `args`: a tuple of the arguments given to the constructor.
* `message`: a string, set to the first argument if exactly one argument was given, and to the empty string otherwise. This attribute exists for convenience in the common case of an exception with a single message.
* `__str__()`: returns the string form of the sole argument if there is exactly one, the empty string if there are none, and `str(self.args)` if there are several.
* `__repr__()`: returns a string that shows the class name and the arguments in the form of a constructor call.
* `__getitem__(index)`: returns `self.args[index]`. Retained for backward compatibility in the 2.x series only, and removed in 3.0.

In Python 3.0, the `message` attribute is also removed, since it provides only a thin layer over `args[0]`.

### The hierarchy

`BaseException` is the root. Two new levels are inserted so that exceptions that should usually not be caught are separated from ordinary ones:

```
BaseException
 +-- KeyboardInterrupt
 +-- SystemExit
 +-- Exception
      +-- (all other built-in exceptions)
```

`Exception` retains its current role as the base of ordinary errors, so that `except Exception:` becomes a way to catch all errors of the kind that programs normally want to handle, without catching requests to exit. `GeneratorExit` is moved under `BaseException` in later versions for the same reason.

Existing code using `except Exception:` is therefore unaffected by the move of `KeyboardInterrupt` and `SystemExit`, except that it will no longer intercept them, which is almost always the intended behavior.

### Raising and catching

The `raise` statement is changed in stages. In 2.5, raising an object that does not inherit from `BaseException` triggers a `PendingDeprecationWarning`. In 2.6 the warning becomes a `DeprecationWarning`. In 3.0, only instances of classes that derive from `BaseException` can be raised and a `TypeError` is raised for anything else.

Similarly, the `except` clause is changed to accept only classes that derive from `BaseException`, or tuples of them, in 3.0. Before that, the old forms continue to work, with the same warning policy.

String exceptions were already deprecated in 2.5 and are removed in 2.6.

### Bare `except`

A bare `except:` clause continues to catch everything in 2.x. The PEP recommends that new code use `except Exception:` and that tools flag the bare form. The question of whether the bare form should be removed in 3.0 is left open.

### Transition plan

* **Python 2.5:** `BaseException` introduced. `Exception` derived from it. `KeyboardInterrupt` and `SystemExit` re-parented. `PendingDeprecationWarning` for raising objects that do not derive from `BaseException`.
* **Python 2.6:** The warning is raised as a `DeprecationWarning`. String exceptions are removed.
* **Python 3.0:** All raised objects must derive from `BaseException`. Support for `__getitem__` and `message` is removed.

## Backwards compatibility

The principal incompatibility is for code that raises classic classes that do not derive from `Exception`. Such code will continue to work until 3.0, with escalating warnings. Fixing it requires only that the class inherit from `Exception`, which is a one-line change.

Code that catches `KeyboardInterrupt` or `SystemExit` by catching `Exception` will stop doing so. This is expected to be rare, and where present, almost always accidental.

Code that depends on indexing an exception object (`e[0]`) will continue to work in 2.x but must switch to `e.args[0]` before 3.0.

## Rejected ideas

### Retaining duck typing

The argument against restriction is that any object that provides the attributes expected from an exception should be usable as one. The difficulty is that "the attributes expected from an exception" is not a short or stable list, and there is no check that can be made when the exception is raised. Failures appear later, in the handler, which is the worst place for them.

### An abstract base

A suggestion was made to use an interface or abstract base class rather than a concrete one, so that classes could register as exceptions without inheriting. Python has no abstract base class mechanism at present, and a concrete class has the additional benefit of providing a default implementation of the interface.

### Putting `KeyboardInterrupt` and `SystemExit` under `Exception`

Leaving the structure as is would minimize the change but retain the problem that `except Exception:` is too broad for most purposes.

## Reference implementation

A patch against the 2.5 development branch is on the tracker. It adds `BaseException`, changes the base class of the other built-in exceptions, adds the warnings, and updates the documentation and the test suite, including tests of the new hierarchy and of the string forms of exceptions with zero, one and several arguments.
