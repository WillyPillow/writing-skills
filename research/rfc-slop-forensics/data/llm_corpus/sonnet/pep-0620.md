# Abstract

Introduce C API incompatible changes to hide implementation details.

Once most implementation details are hidden, the evolution of CPython internals will be less limited by C API backward compatibility issues. It will be much easier to add new features. It becomes possible to experiment with more advanced optimizations in CPython than just micro-optimizations, such as tagged pointers.

This PEP also defines a process to reduce the number of broken C extensions.

The implementation of this PEP is expected to be done carefully over multiple Python versions. It already started in Python 3.7 and most of the changes are already completed. The "Process to reduce the number of broken C extensions" section dictates the rhythm.

# Motivation

## The C API blocks CPython evolution

Many optimizations have been proposed for CPython over the years: tagged pointers, moving garbage collectors, removing the reference counting from some objects, a tracing JIT that unboxes small integers, and so on. Most of them are blocked by the same obstacle. The C API exposes the memory layout of objects, and a large number of C extensions depend on that layout directly.

Consider `PyObject`. Its definition is public, so any extension can read `ob_refcnt` and `ob_type` through a plain pointer dereference. Macros such as `Py_INCREF()` and `Py_TYPE()` expand into code that touches those fields. As a result, CPython cannot change how reference counts are stored without recompiling every extension, and in many cases cannot change it at all without breaking source compatibility.

The same applies to `PyListObject`, `PyTupleObject`, `PyFrameObject`, `PyThreadState` and many other structures. Macros like `PyList_GET_ITEM()` and `PyTuple_GET_ITEM()` access the internal array directly. If a list ever used a different representation, for example a compact array of unboxed integers, these macros would be wrong.

## Alternate implementations pay the price

PyPy, through its `cpyext` layer, must emulate CPython's object layout for every object that crosses the C boundary. This is slow and complicated, and is a large part of why C extensions run poorly on PyPy. Other implementations, such as GraalPython and RustPython, face similar costs. A C API that exposes fewer implementation details is easier for all of them to support.

## Direct access is rarely needed

In most cases, a function exists that does the same job without exposing the structure. `Py_SET_REFCNT()` and `Py_REFCNT()` exist as functions; `PyList_GetItem()` exists next to `PyList_GET_ITEM()`. The cost of the function call is small compared to the benefit of being able to change the internals. When a function is genuinely missing, adding one is cheap.

# Rationale

## Make structures opaque

The central change is to make structures opaque: the C API should expose a pointer type and a set of functions, but not the structure definition. Extensions then cannot depend on the layout, and CPython is free to change it.

This is the approach already used for `PyInterpreterState`, and it has worked well. The PEP proposes extending it to more types in steps, starting with those whose layout is least likely to be relied on.

## Prefer functions to macros

Macros that access structure members are replaced with static inline functions, then with regular functions when needed. Static inline functions keep source compatibility and compile to the same code as the macro, but they also have type checking, and they do not evaluate their arguments more than once.

A separate issue is that some macros can be used as an lvalue, as in `Py_TYPE(obj) = type;`. Such usage is replaced with explicit setters like `Py_SET_TYPE()`, since a function call cannot be assigned to.

## Do it gradually

Changing everything at once would break too many projects. Changes are made one at a time, announced in advance, and tested against the most popular third-party projects before landing.

# Specification

## Summary of changes

The following changes are made or planned.

**Make structures opaque.** The following structures become opaque: `PyObject`, `PyVarObject`, `PyTypeObject`, `PyThreadState`, `PyFrameObject`, `PyListObject`, `PyTupleObject`, `PyDictObject` and others. For each, accessor functions are added where missing.

**Remove macros that access members.** `PyList_GET_ITEM()`, `PyTuple_GET_ITEM()`, `PyTuple_SET_ITEM()` and similar macros are converted to static inline functions first, then removed from the limited API, then replaced by calls to regular functions.

**Disallow use as lvalue.** `Py_TYPE()`, `Py_REFCNT()` and `Py_SIZE()` can no longer be used on the left of an assignment. Setter functions are provided.

**Deprecate borrowed references where practical.** Functions returning borrowed references make it hard to change the container representation, because the returned pointer must stay valid. New functions returning strong references are added, for instance `PyImport_AddModuleRef()`.

**Remove the `Py_UNICODE` type and related functions.** These expose the wide-character representation that was deprecated by PEP 393.

**Add `Py_SET_*` and `Py_IS_TYPE` helpers.** These are added so that extensions can be updated without using private structure members.

## Process to reduce the number of broken C extensions

The list of changes above is acceptable only if the number of broken projects is small, so the following process applies to each incompatible change.

1. Announce the change on python-dev and in the "What's New" document at least one release before it takes effect.
2. Emit a `DeprecationWarning` or compiler warning where possible, so that maintainers see the problem at build time.
3. Test the change against the top 4000 most downloaded PyPI packages that include C extensions, using an automated build. A package that breaks is reported upstream and, if the fix is simple, a patch is proposed.
4. Wait for at least one full release cycle between the announcement and the removal, and in the meantime keep the old behavior available behind a compatibility header, `pythoncapi_compat.h`.
5. If more than a small number of important projects remain broken at the end of the cycle, postpone the change.

The compatibility header allows C extensions to use the new API while still compiling on older Python versions. It provides implementations of the new functions in terms of the old macros, so a maintainer can update once and support every version.

## Limited API and stable ABI

This PEP does not change the stable ABI guarantees. Opaque structures are in line with the limited API, which already hides most of them. One goal is to make the default API closer to the limited API, so that a project can move to the limited API with fewer edits.

# Backwards Compatibility

The changes are incompatible by definition. Extensions that access structure members directly, or that use macros as lvalues, will fail to compile or, worse, misbehave at runtime if they were compiled against an older version. The process above is intended to limit the impact.

Binary compatibility is not preserved across feature releases for extensions that do not use the stable ABI. This is already the case, since the ABI changes between versions.

The changes are expected to affect a small proportion of projects. In earlier experiments, converting a macro into a function caused fewer than a dozen of the top projects to need a change, and most of those were fixed with a one-line patch.

# Performance

Replacing macros with static inline functions has no performance cost. Replacing them with regular functions has a small cost, because the call is not inlined across the extension boundary. Measurements on several benchmarks showed differences within noise. In exchange, optimizations that were previously impossible become possible.

# Rejected Ideas

**Do nothing.** This leaves CPython unable to adopt any change that touches object layout, which blocks nearly all of the larger optimization ideas.

**Create a new C API alongside the old one.** This was considered, and may eventually be the right answer, but it requires a large new surface and a long period of maintaining both. Gradual hiding of details moves toward the same goal and delivers benefits sooner.

**Break everything in Python 4.** There is no plan for Python 4, and a single large break would be damaging to the ecosystem, as the Python 2 to 3 transition showed.

# Reference Implementation

Most of the work is implemented in the main branch. The `pythoncapi_compat` project provides the compatibility header and a script to update extension code automatically. Further changes are tracked in the issue tracker, with one issue per structure or macro.
