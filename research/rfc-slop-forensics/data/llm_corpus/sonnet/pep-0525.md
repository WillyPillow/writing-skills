# PEP 525: Asynchronous Generators

- **Status:** Draft
- **Type:** Standards Track
- **Requires:** PEP 492, PEP 342
- **Python-Version:** 3.6

## Abstract

PEP 492 introduced support for native coroutines and `async`/`await` syntax to Python 3.5. It is proposed here to extend Python's asynchronous capabilities by adding support for *asynchronous generators*.

## Rationale and Goals

Regular generators, introduced in PEP 255 and extended in PEP 342, have become an everyday tool. They let a function produce a sequence of values lazily, with the state of the computation preserved between values. Iterating over them with `for` is the idiomatic way to consume such sequences.

PEP 492 added coroutines and the `async for` and `async with` statements. `async for` iterates over an *asynchronous iterable*, an object whose `__aiter__` method returns an *asynchronous iterator*, whose `__anext__` method returns an awaitable. Yet within a native coroutine there is no way to write such an iterator conveniently. Today the author must write a class with `__aiter__` and `__anext__`, manage state by hand, and arrange for `StopAsyncIteration` to be raised at the right time.

Consider a function that reads records from a database cursor with a network round trip per page. With a regular generator the code is short and the control flow is plain. With an asynchronous iterator class, the same logic is spread across several methods and instance attributes, and the reader must reconstruct the state machine in their head.

An asynchronous generator removes this friction. A function that contains both `async def` and `yield` becomes an asynchronous generator function, and calling it returns an asynchronous generator object that can be iterated with `async for`. Inside the body, `await` and `async with` are allowed, as in any coroutine.

The goals of this PEP are:

- to make the writing of asynchronous iterators as simple as the writing of synchronous ones;
- to keep the semantics a straightforward combination of generators and coroutines;
- to reuse the existing machinery for `async for`, `__aiter__`, and `__anext__`;
- to provide a clean, well-defined way to finalize an asynchronous generator that is abandoned before it is exhausted.

## Specification

### Asynchronous generator functions

A function defined with `async def` that contains at least one `yield` expression in its body is an *asynchronous generator function*. Calling it returns an *asynchronous generator object*. This object implements the asynchronous iterator protocol and the asynchronous generator methods described below.

    async def ticker(delay, to):
        for i in range(to):
            yield i
            await asyncio.sleep(delay)

    async def run():
        async for i in ticker(1, 10):
            print(i)

The `yield from` construct is not allowed inside an asynchronous generator, and a `return` statement with a value is a `SyntaxError`. A bare `return` ends the generator and causes `StopAsyncIteration` to be raised in the consumer.

The `await` expression is permitted anywhere in the body. This includes `await` inside the expression of a `yield` statement.

### Asynchronous generator objects

Asynchronous generator objects provide the following methods, each of which returns an awaitable:

- `agen.__anext__()` returns an awaitable that, when awaited, runs the generator to the next `yield` and produces the yielded value, or raises `StopAsyncIteration` if the generator returns.
- `agen.asend(value)` resumes the generator, sending `value` as the result of the current `yield` expression, and otherwise behaves like `__anext__()`.
- `agen.athrow(type, [value, [traceback]])` raises an exception at the point where the generator is suspended, and returns an awaitable resolving to the next yielded value.
- `agen.aclose()` throws `GeneratorExit` into the generator and returns an awaitable that completes when the generator has finished.

The awaitables returned by these methods are not themselves coroutines. They are a distinct internal type, which cooperates with the event loop in the same way a native coroutine does when it is awaited.

The object is its own asynchronous iterator: `agen.__aiter__()` returns `agen`.

It is an error to call `asend`, `athrow`, or `__anext__` on an asynchronous generator while a previous awaitable obtained from it is still running. Doing so raises `RuntimeError`. This mirrors the "generator already executing" error of ordinary generators and prevents interleaved execution of the body.

### Finalization

Regular generators are finalized by the garbage collector: when the last reference disappears, `close()` is called and `GeneratorExit` is thrown into the frame, so `try/finally` blocks run. Asynchronous generators need the same guarantee, but cleanup code in the body may itself `await`, which cannot happen inside a synchronous finalizer.

To handle this, the PEP adds two hooks to the interpreter, set with `sys.set_asyncgen_hooks(firstiter, finalizer)` and queried with `sys.get_asyncgen_hooks()`:

- `firstiter` is called the first time an asynchronous generator is iterated. The event loop uses it to keep a weak reference to every live asynchronous generator.
- `finalizer` is called when an asynchronous generator is about to be garbage collected. The event loop uses it to schedule `agen.aclose()` as a task, so that the cleanup code can `await`.

An event loop that does not install these hooks leaves asynchronous generators without automatic finalization. If such a generator is abandoned while suspended inside a `try/finally`, the `finally` block does not run. A `ResourceWarning`-style message is not issued by default in this case, though implementations may choose to add one.

The `asyncio` event loop installs the hooks when `run_forever` is called and restores the previous hooks on exit. It also adds a coroutine method, `loop.shutdown_asyncgens()`, which closes all asynchronous generators that are still alive. Programs that exit the loop deliberately should call it before closing the loop.

### Interaction with `yield` in `finally`

A `yield` inside a `finally` block or an `except` clause of an asynchronous generator is permitted, with a restriction. If `aclose()` is called and the generator yields a value while handling `GeneratorExit`, a `RuntimeError` is raised. This matches the behavior of synchronous generators.

### Changes to the compiler and the `inspect` module

The compiler emits a new code object flag, `CO_ASYNC_GENERATOR`, for asynchronous generator functions. The `inspect` module gains `isasyncgen()` and `isasyncgenfunction()`. The `types` module gains `AsyncGeneratorType`.

The abstract base classes in `collections.abc` gain `AsyncGenerator`, which extends `AsyncIterator` with `asend`, `athrow`, and `aclose`.

## Why StopAsyncIteration

An asynchronous generator that finishes must signal the end of iteration to `async for`. Using `StopIteration` would be ambiguous, since it already has a meaning inside coroutines, where it carries the return value. PEP 492 chose `StopAsyncIteration` for this reason, and asynchronous generators use it unchanged.

## Backwards Compatibility

The proposal is fully backwards compatible. A function that contained both `async def` and `yield` was a `SyntaxError` in Python 3.5, so no working code changes meaning.

The new hooks default to no-ops. Third-party event loops continue to work, though their asynchronous generators will not be finalized automatically until the loop adopts the hooks.

## Performance

Asynchronous generators are expected to be faster than hand-written asynchronous iterator classes. A class-based iterator creates a new awaitable for each call to `__anext__`, and runs each step through attribute lookups on the instance. An asynchronous generator keeps its state in a frame and resumes it directly.

Benchmarks on the reference implementation show that a loop over an asynchronous generator that yields without suspending is about two to three times faster than the equivalent class-based iterator.

## Rejected Ideas

**Allowing `yield from` in asynchronous generators.** The semantics of delegation to another asynchronous generator are subtle, particularly around `asend` and `athrow`, and no concrete use case justified the complexity. Authors can write an explicit `async for` loop with `yield`.

**Allowing `return value`.** Because the consumer sees `StopAsyncIteration`, there is no natural place to deliver the value. Forbidding it keeps the model simple.

**Reusing the existing generator `send`.** Naming the methods `asend`, `athrow`, and `aclose` makes it obvious that they return awaitables, and prevents accidental use of a synchronous method on an asynchronous object.

## Reference Implementation

The reference implementation is available as a patch against the CPython repository. It adds the new object type, the compiler support, the `sys` hooks, the `asyncio` integration, and a comprehensive test suite.
