# PEP 261: Support for "wide" Unicode characters

- Status: Draft
- Type: Standards Track
- Created: 27-Jun-2001
- Python-Version: 2.2

## Abstract

Python 2.1 unicode characters can have ordinals only up to `2**16 - 1`. This range corresponds to a range in Unicode known as the Basic Multilingual Plane. There are now characters in Unicode that live on other "planes". The largest addressable character in Unicode has the ordinal `17 * 2**16 - 1` (`0x10ffff`). For readability, we will call this TOPCHAR and call characters in this range "wide characters".

## Glossary

**Character**: Used by itself, means the addressable units of a Python Unicode string.

**Code point**: A code point is an integer between 0 and TOPCHAR. If you imagine Unicode as a mapping from integers to characters, each integer is a code point. But the integers between 0 and TOPCHAR that do not map to characters are also code points. Some will someday be used for characters. Some are guaranteed never to be used for characters.

**Codec**: A set of functions for translating between physical encodings (e.g. on disk or coming in from a network) into logical Python objects.

**Encoding**: Mechanism for representing abstract characters in terms of physical bits and bytes. Encodings allow us to store Unicode characters on disk and transmit them over networks in a manner that is compatible with other Unicode software.

**Surrogate pair**: Two physical characters that represent a single logical character. Part of a convention for representing 32-bit code points in terms of two 16-bit code points.

**Unicode string**: A Python type representing a sequence of code points with "string semantics" (e.g. case conversions, regular expression compatibility, etc.). Constructed using the `unicode()` function.

## Proposed Solution

One solution would be to merely increase the maximum ordinal to a larger value. Unfortunately the only straightforward implementation of this idea is to use 4 bytes per character on all platforms. This has the effect of doubling the size of most Unicode strings. In order to avoid imposing this cost on every user, Python 2.2 will allow the 4-byte implementation as a build-time option. Users can choose whether they care about wide characters or prefer to preserve memory.

The 4-byte option is called `wide Py_UNICODE`. The 2-byte option is called `narrow Py_UNICODE`.

Most things will behave identically in the wide and narrow worlds.

- `unichr(i)` for 0 <= i < 2**16 (0x10000) always returns a length-one string.
- `unichr(i)` for 2**16 <= i <= TOPCHAR will return a length-one string on wide Python builds. On narrow builds it will return a length-two string consisting of a surrogate pair.
- `unichr(i)` for TOPCHAR < i will raise a `ValueError`.
- `ord()` is always the inverse of `unichr()` for a character that `unichr()` could produce on that build.
- There is an integer value in the sys module that describes the largest ordinal for a character in a Unicode string on the current interpreter. `sys.maxunicode` is 2**16-1 (0xffff) on narrow builds of Python and TOPCHAR on wide builds.
- The `\U` escape in Unicode literals, which previously raised an error for values above 0xffff, now accepts values up to TOPCHAR, with the same narrow-versus-wide behavior as `unichr`.

### Surrogate pairs on narrow builds

On a narrow build, a wide character is represented by two code units: a high surrogate in the range 0xD800 to 0xDBFF followed by a low surrogate in the range 0xDC00 to 0xDFFF. Python does not treat such a pair as a single character. `len(u"\U00010000")` is 2 on a narrow build and 1 on a wide build. Slicing between the halves of a pair is allowed and produces a string containing a lone surrogate.

This is acknowledged as a wart. It is the price of memory economy, and it is the same compromise made by Java and Windows APIs. Programmers who require exact semantics for non-BMP text should use a wide build.

## Codecs

The `utf-8` codec on a narrow build will encode a surrogate pair as a single four-byte UTF-8 sequence, and decode a four-byte sequence into a surrogate pair. On a wide build it will directly handle the code point. In both cases the bytes on disk are identical, which is the point of an encoding.

The `utf-16` codecs are simple on a narrow build and need to combine pairs on a wide build when decoding, and split on encoding. A lone surrogate remaining after decoding is an error in strict mode.

The `utf-32` codec is a candidate for addition in a future PEP.

Codecs that do not support the full range, such as `ascii` and `latin-1`, raise errors as before for any character above their range.

The `unicode-escape` and `raw-unicode-escape` codecs must handle the `\U` escape with the full range, producing a surrogate pair on narrow builds.

## Regular Expressions

The `re` module (and its underlying `sre` engine) must be built to match the width of `Py_UNICODE`. On a narrow build, a pattern like `u"."` will match half of a surrogate pair. This is considered acceptable for this PEP. On a wide build, each character is a single unit and patterns behave as expected. Character classes such as `[\U00010000-\U0010FFFF]` work on wide builds. On narrow builds they are rejected or produce surprising results, and users are advised to avoid them.

## Python API

A new function in the `sys` module or an attribute identifying the build type is not required, since `sys.maxunicode` suffices.

The C API gains no new types. `Py_UNICODE` is typedef'd to a 2-byte or 4-byte unsigned integer depending on the build option. Extension modules that assume `sizeof(Py_UNICODE) == 2` will need to be updated.

## Build-time Option

The option is chosen at configure time:

    ./configure --enable-unicode=ucs2    # narrow (default)
    ./configure --enable-unicode=ucs4    # wide

The default remains narrow, to preserve compatibility with existing binary extension modules and to avoid doubling memory use.

Binary distributors such as Linux vendors may choose wide builds, as they will find it easier to support the languages of their users.

## Rejected Suggestions

**Always use UTF-16 internally with surrogate awareness.** This would make `len`, slicing and indexing aware of surrogate pairs, and would mean O(n) indexing or a more complex data structure. Rejected as too invasive for this release.

**Always wide.** Doubles memory use for all Unicode text, mostly consisting of characters inside the BMP.

**A separate type for wide strings.** This introduces yet another string type, with conversions and operators between each, and makes the language harder to teach.

**Variable-width internal representation (UTF-8).** Efficient in memory, but indexing becomes linear. This is the kind of approach which might be explored in a later release, if memory pressure justifies it.

**A run-time switch.** A global flag at start-up would require that every C extension handle both widths at once, which is difficult.

## Backwards Compatibility

Existing programs compiled and run on a narrow build see no change, except that `\U` escapes above 0xFFFF are no longer errors. Programs on a wide build see different lengths for strings that contain wide characters. Pickles and marshal files that store Unicode strings are encoded in UTF-8 and remain portable between builds.

Extension modules written in C that manipulate `Py_UNICODE` buffers directly must be recompiled against a wide build and audited for assumptions about 2-byte width.

## Implementation

The core change is to make the `Py_UNICODE` typedef depend on a configure-time macro, and to audit places in `Objects/unicodeobject.c` that hard-code 16-bit assumptions: the UTF-8 and UTF-16 codecs, the `unicode-escape` codecs, `unichr`, the Unicode database lookups (`unicodedata`), and the case-mapping tables. The character database, which currently covers the BMP, must be extended to wide characters (at least for property lookup) on wide builds.

On the `sre` side, the `SRE_CODE` type must be at least as wide as `Py_UNICODE`, and `_sre.c` must be compiled with the matching width.

Tests should be added that run on both narrow and wide builds, checking `sys.maxunicode`, `unichr`, `ord`, round-tripping through each codec, and the behavior of `len` with wide characters.

## Open Issues

- Whether to expose surrogate-pair helpers to Python programmers to ease working with narrow builds.
- Whether `unicodedata` should expose properties for non-BMP characters on narrow builds, where a single logical character is a pair.
- How to document the differences between the builds so that application authors know what to test.
