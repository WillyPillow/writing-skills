Title: API for code transformers
Author: Example Author <author@example.org>
Status: Rejected
Type: Standards Track
Created: 04-Jan-2016
Python-Version: 3.6

# Abstract

Propose an API to register bytecode and AST transformers. Add also `-o OPTIM_TAG` command line option to change `.pyc` filenames, `-o noopt` disables the peephole optimizer. Raise an `ImportError` exception on import if the `.pyc` file is missing and the code transformers required to transform the code are missing. Code transformers are not needed for code transformed ahead of time (loaded from `.pyc` files).

# Rationale

## Python optimizations

Python has few optimizations. The compiler performs constant folding and a peephole pass over the bytecode, and that is all. There is no inlining, no type specialization, no dead code elimination beyond trivial cases. The reasons are largely good ones: the language is dynamic, almost anything can be rebound at runtime, and a conservative compiler is easier to reason about.

Yet many ideas for faster execution exist. Some are safe only under assumptions that the user can vouch for, such as "this builtin is never shadowed" or "this global is never modified". Experiments with such optimizers are hampered today because there is no supported way to plug a transformation into the compilation pipeline. Implementers must monkey-patch the import system, wrap `compile()`, or fork the interpreter. These approaches are fragile and do not compose.

## Beyond speed

Code transformers are not only for optimization. Other uses include:

* instrumenting code for coverage or tracing;
* implementing contracts, assertions or logging by rewriting functions;
* adding syntactic sugar by transforming the AST (macros in the weak sense);
* rewriting `assert` statements for better failure messages, as testing frameworks already do through private import hooks.

Each of these tools currently re-implements discovery, caching and invalidation. A common registration API would let tools coexist and let the interpreter handle the details of bytecode caching.

# Proposal

## Code transformer interface

A code transformer is an object with a `name` attribute, and one or both of two methods:

* `ast_transformer(tree, context)` receives the AST of a module and returns a new or modified tree.
* `code_transformer(code, context)` receives a code object and returns a code object.

It must also provide `code_transformer.name`, a unique string identifier, which is incorporated into the cache filename. The `context` object carries the filename and the optimization level.

Transformers must be deterministic: the same input always yields the same output, so that the cache can be trusted.

## Registration

The `sys` module gains a list, `sys.implementation.code_transformers`, in which transformers are registered, and helper functions `sys.set_code_transformers()` and `sys.get_code_transformers()` are provided. At compile time the interpreter applies the registered AST transformers in order, compiles the result, and then applies each bytecode transformer in order. The stages are:

1. parse source to AST;
2. run AST transformers;
3. compile AST to bytecode, including the builtin constant folding;
4. run bytecode transformers, replacing the built-in peephole optimizer when it is disabled;
5. write the result to the `.pyc` cache.

The `compile()` builtin and `exec` of strings go through the same pipeline, with an opt-out argument for callers who need the unmodified code, such as the `dis` and `ast` tools.

## Command line option and cache names

Because the result depends on which transformers were active, the cache filename must encode them. A new option `-o OPTIM_TAG` sets a tag inserted into the `.pyc` filename, for example `module.cpython-36.fat.pyc`. When transformers are registered, the tag is built from their names, so two configurations never read each other's caches.

The option `-o noopt` disables the peephole optimizer. This is useful when a transformer wants to see unoptimized bytecode, and when debugging.

## Missing transformers at import time

If a `.pyc` file was generated with a transformer, and that transformer is not present when the file is loaded, running the cached code could silently violate assumptions. For example, a cache produced by an optimizer that assumes some library is installed. The PEP therefore specifies: if the `.pyc` file is missing and the required transformers are not registered, an `ImportError` is raised rather than falling back to compiling the source. Code transformed ahead of time, loaded from existing `.pyc` files, does not need the transformers at runtime. This permits distribution of pre-optimized bytecode.

# Examples

A trivial AST transformer replacing calls to `len` of a literal string with a constant:

```python
import ast

class FoldLen(ast.NodeTransformer):
    def visit_Call(self, node):
        self.generic_visit(node)
        if (isinstance(node.func, ast.Name) and node.func.id == "len"
                and len(node.args) == 1
                and isinstance(node.args[0], ast.Str)):
            return ast.copy_location(ast.Num(len(node.args[0].s)), node)
        return node

class Transformer:
    name = "foldlen"
    def ast_transformer(self, tree, context):
        return ast.fix_missing_locations(FoldLen().visit(tree))
```

Note that this transformation is only valid if `len` has not been rebound. A real optimizer would need guards or a user-provided promise, which is why the PEP leaves the policy to the transformer.

# Rationale for design choices

**Why a registry and not import hooks?** Import hooks affect only imported modules, require each tool to reimplement caching, and cannot be composed in a defined order. A registry provides ordering and cache coherence.

**Why both AST and bytecode stages?** AST transformations are easier to write correctly and are independent of the bytecode format, which changes between versions. Bytecode transformations are needed for optimizations that operate on generated instructions, such as jump threading. Offering both allows tools to pick the appropriate level.

**Why raise ImportError?** Failing loudly is preferable to running code that expects a transformer which is not there. A missing transformer is an environment problem that the user can fix.

# Backward compatibility

By default, no transformers are registered and behaviour is unchanged. The `.pyc` filename format is unchanged when no tag is set. A new `-o` option does not conflict with existing flags, although `-O` and `-OO` continue to be handled separately and may combine with the tag.

# Security

Code transformers run arbitrary code in the compiler and can change the semantics of any module. Registration therefore requires the same privileges as any other Python code execution. It adds no new capability, but it adds a new place where an attacker with write access to an environment can hide behaviour, since the transformed code no longer corresponds to the source. Tools displaying tracebacks and source should be aware of the discrepancy.

# Alternatives

An approach based on a separate optimizing tool run ahead of time that rewrites `.pyc` files was considered. It avoids changing the interpreter but cannot handle `exec`, `eval` or source distributed without precompilation.

# Rejection

The proposal was rejected. Reviewers felt that it exposed too much of the compiler internals as a stable public API, that the interaction with the cache was fragile, and that the claimed benefits for performance had not been demonstrated. The authors of the related optimization work chose to continue as an external project without a registration mechanism in the interpreter.
