# PEP 510: Specialize functions with guards

- Status: Draft
- Type: Standards Track
- Created: 04-Jan-2016
- Python-Version: 3.6

## Abstract

Add functions to the Python C API to specialize pure Python functions: add specialized codes with guards. It allows to implement static optimizers respecting the Python semantics.

## Rationale

### Python semantics

Python is a very dynamic language. Almost everything can be modified at runtime: builtin functions, module globals, class attributes, the code of a function, and so on. A call such as `len(x)` looks up the name `len` in the module's globals and then in builtins, every time it is evaluated, because either namespace may have changed since the last call.

This dynamism is a barrier for optimizers. A static optimizer that wants to replace `len(x)` with a faster inline operation, or hoist a lookup out of a loop, must prove that `len` still refers to the builtin when the optimized code runs. In the general case it cannot prove this at compile time, so most optimizations that would change observable behaviour are not applied by CPython's peephole optimizer.

### Specialization with guards

The standard solution in dynamic language implementations is *specialization*: generate an optimized version of a function that is valid under some assumptions, and check those assumptions before using it. The assumptions are called *guards*. If every guard passes, the specialized code is run. If any guard fails, the original code is run instead, which is always correct.

For example, the function:

```python
def double_len(seq):
    return len(seq) * 2
```

can be specialized for the assumption "`len` is the builtin `len`" so that the specialized code calls the C function directly, without looking up the name. A guard checks that neither the module globals nor the builtins dictionary has changed in a way that rebinds `len`.

This PEP does not propose any particular optimizer. It adds the plumbing so that third-party optimizers, written in Python or C, can attach specialized code to functions in a safe way. Optimizers and the mechanism for attaching code can then evolve independently.

## Proposal

### Changes to the C API

Add the following to the C API:

```c
int PyFunction_Specialize(PyObject *func,
                          PyObject *code,
                          PyObject *guards);

PyObject* PyFunction_GetSpecializedCodes(PyObject *func);

int PyFunction_RemoveSpecialized(PyObject *func, PyObject *code);

int PyFunction_RemoveAllSpecialized(PyObject *func);
```

`PyFunction_Specialize()` adds a specialized code object (or a callable) to a pure Python function, along with a list of guards. It returns 0 on success and -1 with an exception set on failure. The function can hold several specialized versions, each with its own guards.

`code` may be a code object, which is run with the arguments of the call, or any other callable, which is called with the same arguments. A callable allows an optimizer to supply native code, for instance a function compiled ahead of time.

### Guard API

A guard is a C struct containing a function pointer for the check, and a slot for state. The guard type is a Python object:

```c
typedef struct {
    PyObject_HEAD
    int (*init)(PyObject *guard, PyObject *func);
    int (*check)(PyObject *guard, PyObject **stack, int na, int nk);
} PyFunctionGuard;
```

The `check` function returns one of three values:

- `PYGUARD_UNCHANGED`: the guard still holds;
- `PYGUARD_CHANGED`: the guard does not hold, but may hold later;
- `PYGUARD_ERROR`: an error occurred, and an exception is set.

When the function is called, the interpreter walks through the specialized versions and checks each version's guards. The first version whose guards all return `PYGUARD_UNCHANGED` is used. If none passes, the original code is used. A version that reports `PYGUARD_CHANGED` too many times may be removed, to avoid repeated cost, with a threshold chosen by the implementation.

The `stack` argument passes the call arguments to the guard so that guards may specialize on argument types, such as "argument 0 is an `int`". Guards must not modify the arguments and must be free of side effects, since they run before the function and may run multiple times.

### Built-in guards

Two guards are provided in the first version.

**Dictionary version guard.** CPython dictionaries do not currently expose a version number. A companion proposal adds a private version tag to dictionaries, incremented at each mutation. A guard remembers the version at the time of specialization and compares it with the current one. If globals or builtins are modified, the guard fails. As this is coarse, a more precise per-key guard can be added later.

**Argument type guard.** Verifies that the type of selected arguments equals the type recorded during specialization.

Optimizers may implement their own guards in C.

### Python API

The Python-level equivalents live in a new module, `_specialize`, deliberately kept private until the design has been proven in practice. It exposes `specialize(func, code, guards)`, `get_specialized(func)` and `remove_specialized(func, code)`.

### Changes to function objects

The function object gains an optional pointer to a list of specialized versions. Memory cost for functions without specialization is a single pointer, `NULL`. The call path adds a test of this pointer, and when it is `NULL` proceeds exactly as before, so the cost for unspecialized functions is a branch.

Setting `func.__code__` removes all specialized versions, since the original code they were derived from has been replaced. This ensures that specialized code never outlives its source.

## Use cases

- **Builtin function inlining.** Replace calls to `len`, `isinstance` or `range` with direct operations, guarded on the globals and builtins.
- **Constant propagation of globals.** Replace loads of module constants with their value, guarded on the module dictionary version.
- **Loop unrolling and call specialization by argument types.** Produce a version of a numeric function for `int` arguments.
- **Ahead-of-time compilation.** Compile a hot function with a tool, such as Cython or LLVM-based compilers, and attach the native result as a specialized callable.

An experimental optimizer called `fatoptimizer`, written in pure Python as an AST transformer, serves as the first user. It performs inlining, constant folding and dead code elimination, relying on guards for anything that depends on the environment.

## Rejected alternatives

**Do the optimizations in the compiler unconditionally.** Violates Python semantics where globals can be rebound, which would break code that monkey-patches builtins, notably in testing frameworks.

**A new function type for optimized functions.** The `type(func)` visible to users would change, which could break code, and it would not support attaching code to existing functions.

**Recompile functions when assumptions change.** This is the approach used by JITs with deoptimization. It requires infrastructure that CPython lacks, such as the ability to replace the frame of a running function. Guards allow a simpler approach with similar benefits for short functions.

**Per-bytecode inline caches only.** Caches can speed up attribute and global lookup, and may be done independently. They don't allow whole-function replacement, which unlocks more substantial optimizations.

## Backward compatibility

The change is purely additive at the C API level. There is no change to Python semantics when no specialization is registered. Debuggers and tools that inspect `func.__code__` still see the original code. A profiler may attribute time to the specialized code, which has a different code object; documentation will recommend that optimizers retain meaningful names and line information so that tracebacks remain useful.

Tracebacks raised from specialized code should look identical to those from the original code. The specialized code object is expected to share the file name and line numbers where possible.

## Performance

The cost on the call path is bounded by the number of specialized versions and the cost of their guards. In the worst case, a function with many versions pays for every guard on every call before falling back. To control this, the interpreter limits the number of versions per function (for example, to 4) and removes versions that repeatedly fail.

Benchmarks on microbenchmarks with builtin inlining show speedups of 20 to 40 percent, while macro benchmarks show smaller differences. Expectation: this PEP provides the capability; the gains come from optimizers built upon it.

## Security and safety

Specialized code is arbitrary code, so only trusted optimizers should install it. Because guards are executed before the function, a buggy guard could crash the interpreter or return incorrect results. This is no different from any C extension.

## Unresolved questions

- The exact threshold and policy for dropping versions whose guards keep failing.
- Whether the Python-level module should be public.
- How specialization should interact with generators, coroutines and decorated functions.
