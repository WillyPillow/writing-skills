# PEP 400: Deprecate codecs.StreamReader and codecs.StreamWriter

- **Status:** Draft
- **Type:** Standards Track
- **Created:** 28-Jan-2012
- **Python-Version:** 3.3

## Abstract

`io.TextIOWrapper` and `codecs.StreamReaderWriter` offer the same API [#f1]_. `TextIOWrapper` has more features and is faster than `StreamReaderWriter`. Duplicate code means that bugs should be fixed twice and that we may have subtle differences between the two implementations.

The `codecs` module was introduced in Python 2.0 (see the PEP 100). The `io` module was introduced in Python 2.6 and 3.0 (see the PEP 3116), and reimplemented in C in Python 2.7 and 3.1.

## Proposal

Deprecate `codecs.StreamReader`, `codecs.StreamWriter`, `codecs.StreamReaderWriter`, `codecs.StreamRecoder`, and the `codecs.open()` function in favor of the `io` module. Concretely:

- `codecs.open()` is deprecated in favor of `io.open()`;
- `codecs.StreamReader` and `codecs.StreamWriter` are deprecated, and their use in new code should be replaced by `io.TextIOWrapper` around a binary stream;
- `codecs.StreamReaderWriter` and `codecs.StreamRecoder` are deprecated with them;
- the `streamreader` and `streamwriter` attributes of `codecs.CodecInfo` are retained for compatibility but documented as deprecated.

The incremental encoders and decoders (`codecs.IncrementalEncoder` and `codecs.IncrementalDecoder`) and the stateless `encode()` and `decode()` functions are **not** deprecated. They are used by `TextIOWrapper` itself and are the correct low-level building blocks.

The deprecation is announced in the documentation in Python 3.3, with a `DeprecationWarning` added in a later release. Removal is not scheduled by this PEP.

## Motivation

### Two implementations of the same thing

Since Python 3.0, the built-in `open()` returns objects from the `io` module. A call to `open(name, 'r', encoding='utf-8')` yields a `TextIOWrapper`, which wraps a `BufferedReader` over a `FileIO`. The wrapper decodes bytes to text using an incremental decoder, handles universal newlines, and offers `read`, `readline`, `readlines`, `write`, `seek`, `tell`, and iteration.

The `codecs` module provides `codecs.open()`, which returns a `StreamReaderWriter`: an object that also decodes and encodes, also has `read`, `readline`, `readlines`, `write`, `seek`, and iteration. Its design predates the `io` module and was needed when Python 2's built-in file type dealt only in byte strings. Today the two do almost the same job.

### Behavioral differences

The two are not identical, and the differences are mostly a matter of the older one being worse.

- **Speed.** `TextIOWrapper` is implemented in C and has fast paths for common encodings such as UTF-8, Latin-1, and ASCII. `StreamReaderWriter` is written in Python, and its `read` and `readline` do substantial work in the interpreter. Benchmarks have found `TextIOWrapper` to be several times faster for reading, and even more when iterating over lines.
- **Newlines.** `TextIOWrapper` implements universal newlines. `codecs.open()` always opens the file in binary mode and does no newline translation, so reading a file with Windows line endings produces lines with `\r\n`, and `splitlines` semantics in `readline` follow Unicode line boundaries, so that characters like `\x0b`, `\x0c`, `\x1c`, `\x85`, and ` ` break lines. This is surprising for text files and has been the subject of bug reports.
- **Seeking and telling.** `TextIOWrapper.tell()` returns an opaque cookie that captures decoder state, so that `seek(cookie)` restores a position correctly even in the middle of a multibyte sequence. `StreamReaderWriter` forwards to the underlying binary stream and can get out of sync with its internal buffer.
- **Buffering.** `TextIOWrapper` sits on top of a buffered binary stream, with well-defined flushing and `close` behavior. `StreamReaderWriter` leaves the buffering to whatever it wraps.
- **Features.** `TextIOWrapper` has `line_buffering`, `write_through`, `newline`, `detach()`, and `reconfigure`-like capabilities in later versions. `StreamReaderWriter` has none of them.

### Maintenance burden

Every time a bug appears in the text-stream behavior, such as the treatment of a decoding error at a buffer boundary, there are two places to check. Fixes to `TextIOWrapper` do not reach `codecs`, and vice versa. The `codecs` classes have also accumulated special cases for individual codecs, such as UTF-16 and UTF-8-SIG, that `TextIOWrapper` handles through the incremental decoders' own state.

The standard library gains nothing from keeping both. Users who read the documentation are faced with two ways of doing a job and no obvious guidance on which to choose; the safer course is to point them to the better one.

## Rationale

Deprecation is the least disruptive means of reducing the duplication. It signals intent to library authors, gives them time to migrate, and does not remove any functionality in the same release.

The scope is deliberately limited to the stream classes. The codec registry, the `encode` and `decode` functions, and the incremental interfaces form the heart of the `codecs` module and are in active use. The `io` module depends on them.

## Compatibility and migration

Most code using `codecs.open()` can switch to `io.open()` by changing the function name and, where relevant, the mode:

    # before
    with codecs.open(filename, 'r', encoding='utf-8') as f:
        text = f.read()

    # after
    with io.open(filename, 'r', encoding='utf-8') as f:
        text = f.read()

In Python 3 the built-in `open` is `io.open`, so it can be used directly.

The migration changes behavior in two places that matter.

1. **Newlines.** `io.open` translates `\r\n` and `\r` to `\n` on reading by default. Code that depended on seeing the raw line ending should pass `newline=''`. Code that depended on `codecs` splitting lines at unusual Unicode boundaries should use `str.splitlines` on the full text.
2. **Mode.** `codecs.open` forces binary mode on the underlying file, so a mode of `'w'` writes encoded bytes without newline translation. With `io.open`, writes to a text file translate `\n` to the platform line separator. Pass `newline='\n'` to avoid that.

Code that wraps an existing binary stream, for example a socket's `makefile('rb')` or a subprocess pipe, previously used `codecs.getreader('utf-8')(stream)`. The replacement is `io.TextIOWrapper(stream, encoding='utf-8')`. For streams that are not buffered, wrap them in `io.BufferedReader` first.

Code that subclasses `StreamReader` or `StreamWriter` to implement a custom codec has no direct replacement for the stream classes, but the codec's incremental decoder and encoder now supply the logic. The stream classes may stay in the codec registration for as long as the deprecation lasts. A codec author can provide only the incremental classes and omit the stream classes in new codecs once the deprecation is final.

## Alternatives

**Make `StreamReaderWriter` a thin wrapper around `TextIOWrapper`.** This removes the duplicated logic but changes behavior just as migration would, and creates a hybrid whose semantics are hard to document.

**Fix the differences in `codecs`.** Add universal newline handling, correct `tell` and `seek`, and port the code to C. This duplicates work already done in `io` and perpetuates two implementations.

**Do nothing.** The cost is ongoing, though modest. Python 3 users already default to `open`, and `codecs.open` is mostly found in code written for Python 2 compatibility. Doing nothing leaves it as a trap for new users who find it in older tutorials.

**Remove immediately.** Too disruptive. Large amounts of code, especially the Python 2/3 compatible kind, call `codecs.open`.

## Open issues

Python 2.7 has no `DeprecationWarning` backport plan in this PEP; the deprecation applies to the Python 3 line. Code that must support both can use `io.open`, available since Python 2.6.

How long the deprecation period should last is unspecified. At least two feature releases is reasonable. Also unresolved is whether `codecs.getreader` and `codecs.getwriter`, which return the stream classes registered for a codec, should be deprecated in the same step.
