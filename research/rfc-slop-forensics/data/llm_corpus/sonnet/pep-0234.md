# Abstract

This document proposes an iteration interface that objects can provide to control the behaviour of `for` loops. Looping is customized by providing a method that produces an iterator object. The iterator provides a *get next value* operation that produces the next item in the sequence each time it is called, raising an exception when no more items are available.

In addition, specific iterators over the keys of a dictionary and over the lines of a file are proposed, and a proposal is made to allow spelling `dict.has_key(key)` as `key in dict`.

Note: this is an almost complete rewrite of this PEP, describing the implementation checked into the trunk of the Python 2.2 CVS tree. It is still open for discussion. Some of the more esoteric proposals in the earlier drafts have been withdrawn for now.

# Motivation

The `for` statement currently works only on objects that implement the sequence protocol, that is, objects that support `__getitem__` with consecutive integer indices starting at 0 and an `IndexError` to signal the end. This has several drawbacks.

First, it forces objects that are not naturally indexable by integers to pretend that they are. A file object has no meaningful integer index for its lines, yet `for line in file.readlines()` requires reading the entire file into memory, while the older `xreadlines` helper is a separate special case. A dictionary cannot be looped over directly at all; one must write `for k in d.keys()`, which builds a complete list of keys before the first iteration begins.

Second, the sequence protocol is inefficient for many containers. Looping by integer index means that each step pays for an index lookup and, for linked structures or generators of values, may force an O(n) walk per step or the caching of earlier results.

Third, a user-defined class that wants to be loopable must emulate the full indexing interface, including its error behaviour, even when random access makes no sense. The result is a lot of boilerplate and a number of subtle bugs, such as classes that raise an exception other than `IndexError` at the end of the data.

An iteration protocol that is separate from the sequence protocol solves these problems. Objects expose a lightweight cursor, the iterator, that knows only how to produce the next item. The container is free to implement the cursor however it likes, and the loop machinery asks for nothing more.

# Specification

## Python API Specification

The proposal is to add two things: a way for objects to produce an iterator, and the iterator protocol itself.

An object can be iterated over with `for` if it implements an `__iter__()` method returning an iterator object, or if it implements the traditional sequence protocol via `__getitem__()`. The built-in function `iter()` captures this behaviour:

- `iter(obj)` calls `obj.__iter__()` if that method exists, and returns the result. If `obj` has no `__iter__()` method but supports `__getitem__()`, a built-in iterator that calls `__getitem__()` with successive integers, stopping at `IndexError`, is returned. Otherwise `TypeError` is raised.
- `iter(callable, sentinel)` returns an iterator that calls `callable()` with no arguments on each step and stops when the returned value equals `sentinel`. This permits loops over functions such as `f.readline`, which previously required a `while 1` loop with an explicit test and `break`.

An iterator is an object with a `next()` method taking no arguments. Each call returns the next value of the sequence. When there are no more values, `next()` raises the new built-in exception `StopIteration`. Once an iterator has raised `StopIteration`, later calls to `next()` should continue to raise it; an iterator that "comes back to life" would be a source of confusing behaviour and is considered a bug.

Iterators are also required to have an `__iter__()` method that returns the iterator itself. This lets an iterator be used wherever an iterable is expected, so that `for x in iter(obj)` and `for x in obj` behave the same and so that code can accept either kind of object without checking. Containers are not required to be their own iterators; in fact, most should not be, since a container that is its own iterator can only be traversed one way at a time. A container should return a fresh iterator on each call to `__iter__()`, so that independent loops over the same container do not interfere.

The semantics of the `for` statement change accordingly. The statement

    for x in S:
        BODY

is equivalent to

    it = iter(S)
    while 1:
        try:
            x = it.next()
        except StopIteration:
            break
        BODY

except that the temporary `it` is not visible to the program. A `StopIteration` raised inside `BODY` is not caught by the loop machinery in the sense of the above translation; it propagates like any other exception.

## C API Specification

Types gain a new slot, `tp_iter`, which holds the equivalent of `__iter__()`, and `tp_iternext`, the equivalent of `next()`. The slot `tp_iternext` is expected to return a new reference to the next item, or `NULL` with no exception set to signal exhaustion. This avoids the cost of creating and clearing a `StopIteration` instance for every loop termination, which would otherwise be a measurable overhead for short loops. If an error occurs, `NULL` is returned with an exception set, as usual. A `StopIteration` set explicitly by the slot is also treated as exhaustion by callers.

Two new API functions, `PyObject_GetIter()` and `PyIter_Next()`, wrap these slots for use by extension authors. `PyIter_Next()` returns `NULL` both at the end of iteration and on error; the caller distinguishes the two cases with `PyErr_Occurred()`.

Classes defined in Python get their `tp_iter` and `tp_iternext` slots filled in automatically when they define `__iter__` and `next` respectively.

# Dictionary Iterators

The following is proposed:

1. `for x in dict` iterates over the keys of the dictionary, in the same order as `dict.keys()`. The order is arbitrary but stable as long as the dictionary is not modified.
2. `dict.iterkeys()`, `dict.itervalues()` and `dict.iteritems()` return iterators over the keys, values and key/value pairs respectively. They are the lazy counterparts of `keys()`, `values()` and `items()`.
3. `key in dict` is a new spelling of `dict.has_key(key)`. The `in` operator on a dictionary tests for membership of a key, which is consistent with what iteration over the dictionary yields. The `has_key()` method remains available.

Choosing keys as the default iteration is a deliberate decision. Iterating over `(key, value)` pairs would be convenient in some cases, but it would make `x in dict` ambiguous: should it test for keys or for pairs? Keeping iteration and containment consistent seemed more important than convenience.

Modifying a dictionary while iterating over it is not supported. If the dictionary changes size during iteration, the iterator raises `RuntimeError`, since the result of continuing would be undefined: items might be skipped or returned twice. Assigning a new value to an existing key does not change the size and is therefore permitted.

# File Iterators

The following is proposed: `for line in file` iterates over the lines of a file, in the manner of `xreadlines()`. The file object is its own iterator in the sense that `iter(file)` returns `file`, and `file.next()` returns the next line, raising `StopIteration` at end of file. Because a file already has an inherent position, there is no sensible way for two independent iterators to exist, so this self-iterating behaviour is natural.

Mixing `next()` with other read methods is problematic, because the iterator uses an internal read-ahead buffer for efficiency. The documentation will note that after calling `next()`, the result of `tell()` or of other read methods may not reflect the logical position, and that a program should stick to one style of access.

# Rationale

## Why a separate `next()` method rather than reusing `__getitem__`?

The sequence protocol conflates two ideas: random access and traversal. Making traversal its own protocol lets objects like files, generators and database cursors participate without pretending to be indexable. It also lets an iterator hold arbitrary state, such as a position in a hash table, that would be awkward to recover from an integer.

## Why require `__iter__()` on iterators?

Without it, a function that takes "something to loop over" would need to try `iter()` first and fall back to using the argument directly. Requiring iterators to return themselves makes `iter()` idempotent and keeps such code uniform.

## Why an exception rather than a sentinel return value?

Any sentinel value is also a legitimate item in some sequence. `None`, for example, is a perfectly reasonable thing to store in a list. An exception cannot be confused with data. The C-level optimization described above removes most of the cost.

# Backwards Compatibility

Existing sequence-style classes continue to work unchanged, since `iter()` falls back to `__getitem__()`. Classes that currently define `__iter__` or `next` for other purposes would be affected, though a survey of the standard library found no conflicts.

The change to `in` on dictionaries is the one place where previous code that raised `TypeError` now succeeds. Code that depended on that error is expected to be rare.

Python code that catches `IndexError` from a dictionary-based sequence emulation is unaffected.

# Resolved Issues

- *Should `StopIteration` derive from `IndexError`?* No. Deriving it from `Exception` directly avoids having a loop over a sequence silently swallow genuine `IndexError`s raised from inside iterator code.
- *Should there be a `reset()` or `clone()` method?* Not in this proposal. They are not needed for the `for` loop and would be difficult to implement for iterators over generators or files.
- *Should a dictionary iterator yield items or keys?* Keys, as discussed above.

# Open Issues

- Whether the `iter(callable, sentinel)` form is sufficiently useful to keep, or whether it should be dropped in favour of generators.
- Whether the `in` operator should also work with the file iterator for string containment of lines.
