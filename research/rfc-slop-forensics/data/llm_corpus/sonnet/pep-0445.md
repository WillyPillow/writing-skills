# PEP 445: Add new APIs to customize Python memory allocators

- Status: Draft
- Type: Standards Track
- Python-Version: 3.4

## Abstract

This PEP proposes new Application Programming Interfaces (API) to customize Python memory allocators. The only implementation required to conform to this PEP is CPython, but other implementations may choose to be compatible, or to re-use a similar scheme.

## Rationale

Use cases:

* Application embedding Python may want to isolate Python memory from the memory of the application, or may want to use a different memory allocator optimized for its Python usage.
* Python running on embedded devices with low memory and slow CPU. A custom memory allocator may be required to use efficiently the memory and/or to be able to use all the memory of the device.
* Debug tools for memory allocators:
  * track the memory usage (find memory leaks)
  * get the Python filename and line number where an object was allocated
  * detect buffer underflow and buffer overflow
  * force failures to test the error handling code
  * check if the GIL is held when allocating memory
* Support Valgrind or other memory profilers by using the allocator they provide.

Today most of these things can be done only by recompiling Python or by patching the sources. A few debugging features exist, in the form of the `PYMALLOC_DEBUG` compile-time option, but that cannot be turned on in a production build, and none of it can be replaced by an embedding application.

The functions of the allocator family are also split in a confusing way. There are three groups of functions in the C API:

* the raw allocator functions, `PyMem_RawMalloc()` and its siblings, which are thin wrappers around the system `malloc` family. They may be called without holding the GIL;
* the "memory" functions, `PyMem_Malloc()`, `PyMem_Realloc()` and `PyMem_Free()`, which must be called with the GIL held and, in practice, forward to the system allocator;
* the object allocator, `PyObject_Malloc()` and friends, which use `pymalloc`, a specialized allocator for small objects.

The current implementation has no way to replace any of these at runtime. Even when a replacement is compiled in, the choice is global and fixed.

## Proposal

### API changes

Add a structure describing an allocator:

```c
typedef struct {
    /* user context passed as the first argument to the 4 functions */
    void *ctx;

    /* allocate a memory block */
    void* (*malloc) (void *ctx, size_t size);

    /* allocate a memory block initialized by zeros */
    void* (*calloc) (void *ctx, size_t nelem, size_t elsize);

    /* allocate or resize a memory block */
    void* (*realloc) (void *ctx, void *ptr, size_t new_size);

    /* release a memory block */
    void (*free) (void *ctx, void *ptr);
} PyMemAllocator;
```

Add an enumeration identifying the three domains:

```c
typedef enum {
    /* PyMem_RawMalloc(), PyMem_RawRealloc() and PyMem_RawFree() */
    PYMEM_DOMAIN_RAW,

    /* PyMem_Malloc(), PyMem_Realloc() and PyMem_Free() */
    PYMEM_DOMAIN_MEM,

    /* PyObject_Malloc(), PyObject_Realloc() and PyObject_Free() */
    PYMEM_DOMAIN_OBJ
} PyMemAllocatorDomain;
```

Add two functions to read and replace the allocator of a domain:

```c
void PyMem_GetAllocator(PyMemAllocatorDomain domain, PyMemAllocator *allocator);
void PyMem_SetAllocator(PyMemAllocatorDomain domain, PyMemAllocator *allocator);
```

`PyMem_GetAllocator()` copies the current allocator of the domain into the structure. `PyMem_SetAllocator()` installs a new one. Neither function allocates memory. To wrap an existing allocator, a user calls `PyMem_GetAllocator()`, stores the result in their own context, and then installs an allocator whose functions call the stored one.

Add a function to install a family of debug hooks:

```c
void PyMem_SetupDebugHooks(void);
```

This function installs, on top of each domain's current allocator, hooks that detect common errors: writes before the start or after the end of a block (by padding the block with recognizable byte patterns and verifying them on release), use of freed memory (by filling freed blocks with a distinctive pattern), a mismatch between the allocator domain used to allocate and the one used to free, and calls to the non-raw functions without the GIL held. The function is idempotent.

Add a function that exposes the arena allocator of `pymalloc` in the same way:

```c
typedef struct {
    void *ctx;
    void* (*alloc) (void *ctx, size_t size);
    void (*free) (void *ctx, void *ptr, size_t size);
} PyObjectArenaAllocator;

void PyObject_GetArenaAllocator(PyObjectArenaAllocator *allocator);
void PyObject_SetArenaAllocator(PyObjectArenaAllocator *allocator);
```

The arena allocator is used by `pymalloc` to obtain large blocks (256 KiB), which it subdivides. Replacing it allows, for instance, use of memory-mapped regions or of a memory pool reserved by the host application.

### Semantics

Calls to `PyMem_SetAllocator()` are only valid if no memory allocated by the old allocator will be released by the new one. In practice this means they must be done early, before `Py_Initialize()`, or the new allocator must be able to handle blocks of the old one (typically by forwarding the free and realloc operations on pointers it does not recognize).

The raw domain must be thread-safe and must be usable without the GIL. The other two domains are called with the GIL held, and need not be thread-safe, so a replacement allocator may rely on the GIL for mutual exclusion.

The `PyMem_Malloc(0)` case is unchanged: it returns a distinct non-NULL pointer where possible, as in the existing contract.

### Changes to existing behavior

Currently, the `PyMem_*` functions are macros in some build configurations and bypass the function pointer entirely. This PEP changes the macros to expand to calls to the functions, and removes `PyMem_MALLOC` and related macros from the public API to avoid compiled extensions embedding the allocator choice. Extensions using the macros will be recompiled for the new version as usual for minor releases, since the C ABI is not stable across them.

The debug build (`--with-pydebug`) continues to enable the debug hooks by default. In addition, the environment variable `PYTHONMALLOC=debug` is accepted by a normal build to enable the hooks with no recompilation. The values `malloc` and `pymalloc` are also accepted to force the choice of the underlying allocator.

### Examples

A hook that counts allocations might be written as:

```c
static PyMemAllocator orig;
static size_t count;

static void *
hook_malloc(void *ctx, size_t size)
{
    count++;
    return orig.malloc(orig.ctx, size);
}

void
install_counter(void)
{
    PyMemAllocator alloc;
    PyMem_GetAllocator(PYMEM_DOMAIN_MEM, &orig);
    alloc = orig;
    alloc.malloc = hook_malloc;
    PyMem_SetAllocator(PYMEM_DOMAIN_MEM, &alloc);
}
```

A complete wrapper would also override `calloc`, `realloc` and `free`.

## Performance

The additional indirection through a function pointer was measured on the standard benchmark suite. The difference was below the noise in nearly all tests, and the worst case slowdown observed was about 1%. The hot path of `pymalloc` is not affected, since the object domain still calls `pymalloc` directly through the function pointer, and no extra layer is introduced unless hooks are installed.

## Alternatives

### Only a debug-mode hook

A narrower proposal would provide only the debugging functionality, without allowing replacement. This does not address the use cases of embedding applications and of platforms with unusual memory.

### Link-time replacement

Python could rely on the platform's ability to interpose `malloc`, as `LD_PRELOAD` does. This captures all allocations in the process, not just Python's, and it is not portable.

### Per-interpreter allocators

An allocator could be selected per interpreter instead of globally. This is more flexible, but the current C API stores no allocator on the interpreter state, and most allocation calls occur in contexts with no interpreter at hand, such as `PyMem_RawMalloc()` in startup code.

### A single domain

Having only one domain would be simpler, but would remove the ability to hook the object allocator without affecting raw allocations, which must remain free of Python-specific constraints.

## Backwards compatibility

The change is source-compatible for all code that uses the documented functions. It affects extensions that use the `PyMem_MALLOC` family of macros, which were never documented as public but are used in some projects. Those will continue to compile in 3.4 through compatibility definitions that call the functions.

## Reference implementation

The patch is attached to the corresponding tracker issue. It includes the C changes, tests that install a counting hook in each domain, and documentation updates for the C API reference.
