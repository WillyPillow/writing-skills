PEP: 403
Title: General purpose decorator clause (aka "@in" clause)
Status: Deferred
Type: Standards Track
Created: 13-Oct-2011
Python-Version: 3.4

# Abstract

This PEP proposes the addition of a new `@in` decorator clause that makes it possible to override the name binding step of a function or class definition.

The new clause accepts a single simple statement that can make a forward reference to decorated function or class definition.

This new clause is designed to be used whenever a "one-shot" function or class is needed, and placing the function or class definition before the statement that uses it actually makes the code harder to read. It also avoids any name shadowing concerns by making sure the new name is visible only to the statement in the `@in` clause.

This PEP is based heavily on many of the ideas in PEP 3150 (Statement Local Namespaces) so some elements of the rationale will be familiar to readers of that PEP. That PEP has now been withdrawn in favour of this one.

# PEP Deferral

Like PEP 3150, this PEP currently exists in a deferred state. Unlike PEP 3150, this PEP was not deferred because of any technical difficulty with its implementation, but because the need it addresses is not yet clearly compelling to enough core developers.

# Basic Examples

Before diving into the rationale, a few examples of how the new clause would be used may help.

Defining a callback for a registration function:

```python
@in register_callback(button, event="click")
def on_click(event):
    show_dialog(event.target)
```

Here the function `on_click` is defined and immediately passed to `register_callback`, with the forward reference being written as the name `on_click` in the `@in` clause. After the statement completes, the name `on_click` is no longer bound in the enclosing scope.

Sorting with a complex key:

```python
@in sorted_items = sorted(items, key=key_func)
def key_func(item):
    return (item.priority, -item.age, item.name)
```

The result of the `@in` statement is bound to `sorted_items`; the helper `key_func` is local to the statement.

Creating a thread:

```python
@in t = threading.Thread(target=worker)
def worker():
    for chunk in download(url):
        process(chunk)
t.start()
```

# Rationale

## The problem

Python programmers often need to supply a callable to some other function. For simple cases, `lambda` expressions suffice. For anything involving more than a single expression, the only available option is a `def` statement, which binds a name in the enclosing scope. The name is chosen only to be passed to the next statement, and then never used again.

The usual pattern puts the definition first:

```python
def key_func(item):
    return (item.priority, -item.age, item.name)

sorted_items = sorted(items, key=key_func)
```

This ordering is natural for the interpreter but often unnatural for the reader. The reader encounters a function whose purpose is not yet clear, and must read forward to learn what it is for. The important statement, the one that expresses the logic of the surrounding code, comes last. In many cases, the intent of the code is obscured, since the helper is longer than the statement that uses it.

Other languages deal with this by providing anonymous blocks or closures with multi-statement bodies, such as Ruby blocks, or Javascript anonymous functions. Python has deliberately avoided multi-statement lambdas, because of the difficulty of making them fit into the indentation-based syntax.

## Name pollution

The second problem is that every such helper leaves a name in the namespace. At module scope, this is visible to every user of the module and shows up in `dir()`. At class scope, it becomes a class attribute, which can interfere with the intended class interface. In a function, it can shadow another name that the programmer wanted to keep. It is common to see helper names with a leading underscore for this reason, or to delete them with `del` after use, which adds noise.

## Decorators as a partial answer

Decorators were introduced to put the modifier before the function definition, because the modifier was important to understanding what the function is. They can also be abused to approximate the behavior desired here:

```python
@register_callback(button, event="click")
def on_click(event):
    show_dialog(event.target)
```

This works when the callable's role is to be registered somewhere, and the return value of the registration can be ignored or is the original function. It does not work in general, because the decorated name is rebound to the result of the decorator, which is typically not what the programmer wants. For example, `sorted` would return a list, not a function, and so the name would be bound to the wrong thing. A generic mechanism is needed that separates the call from the name binding.

# Proposal

This PEP proposes the addition of an optional `@in` clause to the syntax for function and class definitions. The clause precedes the definition, like a decorator, and contains a simple statement:

```
in_clause: '@in' simple_stmt
```

It is followed by a `def` or `class` statement, optionally preceded by ordinary decorators.

The semantics are as follows:

1. The decorated function or class is defined as usual, including application of any ordinary decorators, but its name is *not* bound in the enclosing namespace.
2. The simple statement in the `@in` clause is executed. Within that statement, and only there, the name of the function or class refers to the newly defined object.
3. After the statement completes, the temporary binding is removed.

The effect is equivalent to the following expansion, where `_tmp` is an inaccessible name:

```python
def _tmp(item):
    ...
sorted_items = sorted(items, key=_tmp)
```

with the substitution of `_tmp` for `key_func` in the statement. The actual implementation need not use a real temporary name; the compiler can arrange for a hidden local slot.

## Which statements are allowed

The `@in` clause accepts only a simple statement, meaning an expression statement, an assignment, an augmented assignment, a `return`, a `yield`, a `del`, and similar. Compound statements are not allowed, since they would require nested indentation. A `return` in the `@in` clause returns from the enclosing function, after the definition executes.

## Scoping

The name of the definition is visible only in the `@in` statement. In particular, it is not visible in the body of the function itself unless the function refers to itself recursively. Recursion by name is not supported in the first version; a function wishing to call itself must use some other mechanism.

This restriction avoids the question of what the name refers to inside a closure that outlives the statement, such as a thread target. When the closure runs later, the name is no longer bound.

# Discussion

## Why not multi-statement lambda?

Multi-statement lambdas have repeatedly been proposed and rejected. The syntax is awkward, and in a language with significant whitespace there is no good way to nest blocks within an expression. The `@in` clause sidesteps this by preserving the block structure of a `def`, and moving the expression elsewhere.

## Why reuse decorator syntax?

The decorator position is already understood by Python readers as "things that apply to the next definition". This choice also means that the grammar change is small. The PEP uses `@in` as the introducing token because `in` is already a keyword, so there is no ambiguity with existing decorators, which must be expressions.

## Interaction with PEP 3150

PEP 3150 proposed a `given` clause that provided a statement-local namespace in which several names could be defined. This PEP is narrower: it handles a single definition, and builds on existing syntax. If experience shows a need for several local names, PEP 3150 could be revisited.

# Rejected and Alternative Syntaxes

- Placing the clause after the definition, as in `def f(): ... in statement`. This was dismissed because it hides the important statement after the body.
- Using `@with`, `@as`, or `@for`. Each of these has an existing meaning and would be confusing.
- A dedicated keyword such as `given` or `where`. New keywords require a `__future__` import and incur a bigger compatibility cost.

# Reference Implementation

None currently exists. The change can be implemented in the parser, with a small addition to the compiler to emit a definition into a hidden local slot, then the statement, then a deletion of the slot.
