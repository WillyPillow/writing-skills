# PEP 246: Object Adaptation

- PEP: 246
- Title: Object Adaptation
- Status: Draft
- Type: Standards Track
- Created: 21-Mar-2001
- Python-Version: 2.5

## Abstract

This proposal puts forth an extensible cooperative mechanism for the adaptation of an incoming object to a context which expects an object supporting a specific protocol (say a specific type, class, or interface).

This proposal provides a built-in "adapt" function that, for any object X and any protocol Y, can be used to ask the Python environment for a version of X compliant with Y. Behind the scenes, the mechanism asks object X: "Are you now, or do you know how to wrap yourself to provide, a supporter of protocol Y?". And, if this request fails, the function then asks protocol Y: "Does object X support you, or do you know how to wrap it to obtain such a supporter?" This duality is important, because protocols can be developed after objects are, or vice versa, and this PEP lets either case be supported non-invasively with regard to the pre-existing component[s].

Lastly, if neither the object nor the protocol know about each other, the mechanism may check a registry of adapter factories, where adapters are registered to provide a specific protocol for a given type.

## Rationale

Currently there is no standardized mechanism in Python for checking if an object supports a particular protocol. Typically, existing Python code either checks the type of an object, or tests for a particular attribute, or simply calls a method and handles the exception that results if the method does not exist. Each of these approaches has well-known weaknesses.

Type checks with `isinstance` or `type` are brittle. They reject objects that would work perfectly well because they happen to belong to a different class hierarchy. File-like objects are the standard example: a function that checks `isinstance(f, file)` refuses a `StringIO`, even though that object offers every method the function needs.

Attribute probing with `hasattr` is more flexible but equally unreliable. The presence of a `read` attribute says nothing about its signature or semantics, and two unrelated protocols may use the same method name for different purposes. It also shifts the burden of checking onto every consumer, so that the same few lines are repeated throughout a code base.

Calling the method and catching `AttributeError` or `TypeError` mixes the question of whether the object is suitable with the effects of running the operation. An `AttributeError` raised deep inside the operation can be confused with one raised by the missing method.

A fourth approach is to convert eagerly: `str(x)`, `int(x)`, `list(x)`. This works for built-in types, but each conversion function is a closed special case. There is no way to add a new "convert to X" operation that follows the same conventions, and no way to say that a given object can be viewed as something without being converted into a copy.

What is wanted is a single standard question, "give me a version of this object that supports this protocol", whose answer can be extended by third parties without modifying either the object's class or the protocol's definition. This is the problem of adaptation. It arises in GUI toolkits, web frameworks, database layers and component systems, each of which has re-invented some form of it. Zope's interfaces, Twisted's components and PyProtocols all provide adaptation, with incompatible APIs. A shared minimal core would allow these systems to interoperate and let simple programs use adaptation without importing a framework.

## Specification

### The adapt function

This PEP proposes a new built-in function, `adapt`:

```python
adapt(obj, protocol, alternate=_marker)
```

Its semantics, in order, are:

1. If `obj` already satisfies `protocol`, it is returned unchanged. For protocols that are classes, this means `isinstance(obj, protocol)` is true.
2. Otherwise, if `obj` has a method `__conform__`, call `obj.__conform__(protocol)`. If it returns something other than `None`, return that.
3. Otherwise, if `protocol` has a method `__adapt__`, call `protocol.__adapt__(obj)`. If it returns something other than `None`, return that.
4. Otherwise, if neither succeeded, then if an `alternate` argument was provided, return it; otherwise raise `TypeError`.

Using `None` to signal "I don't know" means that an adaptation can never legitimately produce `None`. This restriction is accepted for simplicity. A protocol for which `None` is a meaningful result can wrap it in a sentinel object.

### The `__conform__` method

An object may define `__conform__(self, protocol)` to declare which protocols it supports and how. For example:

```python
class Circle:
    def __conform__(self, protocol):
        if protocol is Drawable:
            return DrawableCircle(self)
```

The method may return `self` to declare that the object already supports the protocol without wrapping. It must return `None` for protocols it does not know about, and it must not raise an exception to signal non-support. An exception that does propagate out of `__conform__` is treated as an error in the program and is not caught by `adapt`.

### The `__adapt__` method

A protocol may define `__adapt__(self, obj)` to say how it recognizes objects that support it. A typical implementation checks for required attributes, or consults a registry:

```python
class Drawable:
    @classmethod
    def __adapt__(cls, obj):
        if hasattr(obj, "draw"):
            return obj
```

By convention, `__adapt__` is not called for objects that `__conform__` has already accepted, and the protocol is free to apply its own policy. This asymmetry allows a protocol written after the class to adapt it without changing it, and a class written after the protocol to adapt itself without changing the protocol.

### The adapter registry

Where neither side has anything to offer, `adapt` may consult a global registry mapping `(type, protocol)` pairs to factory callables. The module `adaptation` provides the registration function:

```python
adaptation.register_adapter(from_type, to_protocol, factory)
```

When `adapt` is called with `obj` of type `T`, the registry is searched for an entry matching `T`, then for each base class of `T` in method resolution order. The first match is used, and `factory(obj)` is returned. This lookup runs after `__conform__` and `__adapt__`, so objects and protocols always take precedence over global registrations. The registry is a fallback for situations where neither party can be modified, such as adapting a built-in `dict` to a user-defined `Mapping` protocol.

### Transitivity

The proposal does not specify transitive adaptation. If A can be adapted to B and B to C, `adapt(a, C)` does not automatically chain the two. Transitivity is attractive, but it also leads to surprising and hard-to-diagnose behavior when long chains lose information. A framework that wants it may implement it inside its own `__adapt__` methods.

## Motivation for the duality

Why check both the object and the protocol? The reason is that either one may be the more recent. If only objects were asked, every protocol written after a class would require modifying that class, which is impossible for built-ins and unacceptable for third-party code. If only protocols were asked, every new class would need to be known to the protocol in advance. The two-sided query allows each party to be written in ignorance of the other, with the glue supplied by whichever side knows more.

## Backward compatibility

The PEP adds a built-in name, `adapt`, and two optional special methods. Code that already defines a global called `adapt` is unaffected, as the module global shadows the built-in. Classes that define a method named `__conform__` or `__adapt__` for other purposes will be called with a protocol argument; these are reserved names under the usual convention for double-underscore identifiers, so the risk is small.

No existing behavior changes, since nothing in the language or standard library calls `adapt` unless programmers do so explicitly.

## Reference implementation

A pure Python implementation is sketched below.

```python
_marker = object()

def adapt(obj, protocol, alternate=_marker):
    if isinstance(protocol, type) and isinstance(obj, protocol):
        return obj
    try:
        conform = obj.__conform__
    except AttributeError:
        pass
    else:
        result = conform(protocol)
        if result is not None:
            return result
    try:
        adapter = protocol.__adapt__
    except AttributeError:
        pass
    else:
        result = adapter(obj)
        if result is not None:
            return result
    factory = _lookup_registry(type(obj), protocol)
    if factory is not None:
        return factory(obj)
    if alternate is _marker:
        raise TypeError("can't adapt %r to %r" % (obj, protocol))
    return alternate
```

The cost of the function for the common case, where the object already is an instance of the protocol, is one `isinstance` call.

## Open issues

Whether `adapt` should be a built-in or live in a standard library module is debated. A built-in gives the mechanism the weight needed to become a convention, while a module is easier to revise. This PEP proposes the built-in, with the registry kept in a module.

The treatment of `isinstance` in step 1 interacts with proposals to customize `isinstance` through the metaclass hook. If those are adopted, step 1 should defer to them.

Handling of a protocol that is a tuple of alternatives, as accepted by `isinstance`, is unspecified. A natural reading is to try each element in order.

Whether adapters should be permitted to return a view that is not identical across calls, and what that means for identity-based code, is not covered here. Users should treat an adapted object as a proxy and not rely on identity.
