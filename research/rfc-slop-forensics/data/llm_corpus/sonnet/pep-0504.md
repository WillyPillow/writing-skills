PEP: 504
Title: Using the System RNG by default
Author: Example Author <author@example.org>
Status: Withdrawn
Type: Standards Track
Created: 15-Sep-2015
Python-Version: 3.6

# Abstract

Python currently defaults to using the deterministic Mersenne Twister random number generator for the module level APIs in the `random` module, requiring users to know that when they're performing "security sensitive" work, they should instead switch to using the cryptographically secure `os.urandom` or `random.SystemRandom` interfaces or a third party library like `cryptography`.

Unfortunately, this approach has resulted in a situation where developers that aren't aware that they're doing security sensitive work use the default module level APIs, and thus expose their users to unnecessary risks.

This isn't an acute problem, but it is a chronic one, and the often long delays between the introduction of security flaws and their exploitation means that it is difficult for developers to naturally learn from experience.

In order to provide an eventually pervasive solution to the problem, this PEP proposes that Python switch to using the system random number generator by default in Python 3.6, and require developers to opt in to using the deterministic random number generator process wide either through a new `random.ensure_repeatable()` API in Python 3.6 or by calling `random.seed()`.

# Proposal

Currently, module level functions such as `random.random()` and `random.choice()` share a hidden instance of `random.Random`, seeded from system entropy at import time and producing output from the Mersenne Twister. The generator is fast, has a very long period and is well suited to simulation, but its internal state can be recovered from a modest number of consecutive outputs, after which all future and past output is predictable.

This PEP proposes the following changes:

1. In Python 3.6 the hidden module-level instance becomes an instance of `random.SystemRandom`, backed by the operating system's cryptographically secure source (`os.urandom`). Calls to `random.seed()` with an explicit argument, or to a new function `random.ensure_repeatable()`, switch the module-level instance back to a seeded Mersenne Twister, so existing programs that depend on reproducibility continue to work if they follow the long-documented practice of seeding.
2. `random.Random` remains the explicit class name for the deterministic generator, and `random.SystemRandom` remains the explicit name for the secure one.
3. A `random.ensure_repeatable()` function is added. It installs a seeded deterministic generator for the module level functions without requiring the caller to choose a seed value; it picks one from system entropy and exposes it for logging.
4. The `random` documentation is revised so that the first thing a reader encounters is a statement of which generator the module level functions use and how to switch.

# Rationale

## The practical problem

Most programmers are not security specialists, and most do not think of themselves as doing security sensitive work. But many everyday tasks have security implications: generating a session identifier, a password reset token, a temporary filename in a shared directory, a CSRF token, a "random" password given to a new user, or a nonce. For each of these, the `random` module is the first tool a developer meets. It has a friendly name, it is mentioned in tutorials, and it works.

The documentation does contain a warning that the module is not suitable for cryptographic purposes. That warning is correct, and it is inadequate. A warning only helps those who read it, and by definition developers who do not recognise their task as sensitive are the ones least likely to look for one.

## Why this is a chronic and not an acute problem

An insecure token generator does not fail visibly. The tokens look random, the application works, and tests pass. The weakness is exposed only if an attacker collects enough outputs and does the work of state recovery, which may happen years after the code was written. Developers receive no feedback, and so, unlike a crash or a failed test, the mistake teaches nothing.

## Why change the default and not only the documentation?

Making the safe option the default converts a mistake that requires specialist knowledge to avoid into one that requires specialist knowledge to commit. Programs that need reproducible sequences, such as simulations, games with replayable seeds, and test suites, are written by people who already know they need reproducibility, because it is something they must actively want. These users must opt in, and they will find the means to do so because their programs would otherwise produce different output on each run, which is easily noticed. In contrast, the cost of the present arrangement is silent.

# Performance considerations

The system generator is slower than the Mersenne Twister. Calling `os.urandom` involves a system call for each request, and the cost per call is roughly an order of magnitude higher for small requests. Programs generating millions of random numbers in tight loops, such as Monte Carlo simulations, will observe a noticeable slowdown unless they opt in to the deterministic generator.

This is partly mitigated by two facts. First, such programs are generally written by people aware of the performance tradeoff and willing to switch generators explicitly. Second, buffering of entropy requests in the implementation can reduce the number of system calls, and modern operating systems provide very fast kernel generators.

# Compatibility

The proposal changes observable behaviour in some cases:

* Programs that call `random.seed(n)` continue to work and produce the same sequences as before, since seeding switches to the deterministic generator.
* Programs that never seed but whose output happens to be consumed by tests that expect nondeterminism are unaffected.
* Programs that call `random.getstate()` or `random.setstate()` without seeding would need a deterministic generator to exist. The proposal handles this by treating these calls as an opt in to the deterministic generator, with a deprecation period during which they emit a warning.
* Programs that rely on the module-level generator being forked identically into subprocesses lose that property. With a system generator, each process draws independently. This arguably fixes a latent bug, since forked workers sharing state generate duplicate "random" values.

The most significant risk is performance regression, particularly on platforms where `os.urandom` is slow or where entropy may be scarce, for example early in the boot sequence of embedded systems.

# Alternatives considered

**Documentation only.** The status quo. It has been tried, and the problem persists.

**A new module.** Introduce a `secrets` module offering convenient, hard-to-misuse tools for common security tasks, and leave the `random` module alone. This addresses discoverability by providing a clear destination, and it avoids all compatibility costs. It does not protect developers who do not realise they should look for it.

**Emitting a warning.** Warn when the module level functions are used without prior seeding. This would affect a vast amount of legitimate code and generate noise that users would quickly learn to suppress.

**Different name for the module level functions.** Retire the unseeded module functions entirely. Too disruptive.

# Withdrawal

During discussion, the preferred approach became adding the `secrets` module, which gives the benefits of discoverability and an obvious secure interface for token and password generation without changing the default behaviour of an existing module. That module was accepted and added separately. As a result the author has withdrawn this proposal, which is preserved for the record of the reasoning, in particular the analysis of why defaults matter for security-relevant APIs.
