# Abstract

This PEP specifies a programmatic interface for pip and other distribution or installation tools to use when working with Python source trees (both the developer tree - e.g. the git tree - and source distributions).

The programmatic interface allows decoupling of pip from its current hard dependency on setuptools, able for two key reasons:

1. It enables new build systems that may be much easier to use without requiring them to even appear to be setuptools.
2. It facilitates setuptools itself changing its user interface without breaking pip, giving looser coupling.

The interface needed to permit pip to install build systems also enables pip to install build time requirements for packages which is an important step in getting pip to full feature parity with the installation components of easy-install.

As PEP 426 is draft, we cannot utilise the metadata format it defined. However PEP 426 is likely to be revised, and the interface this PEP defines should be able to be adapted to whatever the eventual metadata format is.

# Motivation

Today, pip runs `setup.py` in the root of a source tree to do almost everything: to discover metadata, to build wheels, to install in development mode, and to run tests. Every package that is installable from source must supply a `setup.py` that imports setuptools or distutils, whether or not its author wants to use those tools. Setuptools in turn has accumulated a large and idiosyncratic interface, and its own authors cannot change it without risking breaking pip, which depends on undocumented details such as the arguments accepted by the `egg_info` and `bdist_wheel` commands.

This has several consequences:

- Authors who want to use a different build tool, such as a system that generates extension modules from a different language or one that takes a declarative configuration, must write a `setup.py` shim that pretends to be setuptools. Several projects have done exactly this, each with different fragility.
- Build-time dependencies cannot be declared. A package that needs Cython or numpy to build has no standard way of saying so, and pip cannot install them before running `setup.py`. Authors resort to bootstrapping tricks such as calling `easy_install` from within `setup.py`, which bypasses pip's control of network access, hashes and index choice.
- Setuptools cannot evolve its command-line interface, since pip effectively defines it.

This PEP defines a layer between pip and the build tool so that each side can change independently.

# Rationale

The approach follows what has worked in other ecosystems: a project declares the tool that builds it, and the installer drives that tool through a small, versioned, documented interface. The interface is defined as a set of subprocess commands rather than as a Python API, because build systems may need to run in an environment that differs from the one in which the installer runs, and because the commands can be implemented by tools not written in Python.

The configuration lives in a new file, `pypa.json`, at the root of the source tree. A JSON file is easily parsed by installers without extra dependencies. The file declares the build system's requirements and the commands used to invoke it.

# Specification

## Source tree layout

A source tree is a directory that contains a `pypa.json` file at its root. If no such file exists, the installer assumes the legacy behaviour and invokes `setup.py` with setuptools as the build system, with a set of default requirements of `["setuptools", "wheel"]`. This ensures that existing projects continue to work.

## The `pypa.json` file

The file is a JSON object. The following keys are defined:

- `schema_version`: the integer `1`. Installers must reject unknown versions.
- `bootstrap_requires`: a list of PEP 508 requirement strings which must be installed before any of the commands below can be run.
- `build_requires`: a list of strings naming build-time dependencies. This list may be extended dynamically by the `build_requires` command described below.
- `metadata_requires`: a list of strings naming dependencies needed to compute metadata.
- `commands`: an object mapping command names to command lines, each a list of strings, to be executed with the source tree as the working directory.

An example for a hypothetical build tool, `flit`:

    {
        "schema_version": 1,
        "bootstrap_requires": ["flit>=0.5"],
        "commands": {
            "wheel": ["flit", "wheel", "--output-dir", "{OUTPUT_DIR}"],
            "dist_info": ["flit", "dist-info", "--output-dir", "{OUTPUT_DIR}"]
        }
    }

Placeholders in command lines are expanded by the installer. `{OUTPUT_DIR}` is a directory in which the command must place its results. `{PYTHON}` is the path of the interpreter the build should target.

## Commands

All commands are run in a subprocess in an environment prepared by the installer with the `bootstrap_requires` installed. Standard output and standard error are connected to the installer's, which may capture them. A non-zero exit status signals failure.

- `dist_info`: write a `.dist-info` directory containing the package's metadata into `{OUTPUT_DIR}`. This allows installers to learn the dependencies of a package without building it.
- `wheel`: build a wheel and place it in `{OUTPUT_DIR}`. The wheel must be the only file produced there. The wheel's metadata must agree with the output of `dist_info`.
- `develop`: install the project in-place in the target environment so that changes to the source are reflected immediately. The command receives `{PREFIX}` for the install location. This command is optional.
- `build_requires`: print a JSON list of additional build-time requirements on standard output. This is called after the bootstrap requirements are installed, so the answer may depend on them. The installer installs these before calling `wheel`.

Commands not listed in the `commands` object are considered unsupported, and the installer must fall back or fail with a clear message.

## Environment and isolation

The installer should run each command in a clean environment into which only the declared requirements have been installed, so that undeclared dependencies are detected. It is permitted to share an environment between commands in one run. The installer must set the `PYTHONPATH` or equivalent only as needed for the requirements it installed, and it should not leak the installing environment's packages by default.

## Handling of source distributions

A source distribution is a source tree packaged as an archive; it must contain the `pypa.json` file at its root, and installers treat the unpacked archive as a source tree. This means no separate mechanism is needed for sdists.

## Conda and other consumers

The same interface may be used by non-pip consumers, such as conda-build, to obtain metadata and wheels from a source tree. Such tools may choose to reuse the built wheel or to use the interface only for metadata.

# Evolution of the interface

The `schema_version` allows incompatible changes. Backwards-compatible additions, such as new optional commands, can be made without increasing the version. Installers must ignore unknown keys and unknown commands.

# Backwards Compatibility

Projects without `pypa.json` behave exactly as before. Setuptools is expected to ship a thin shim implementing the commands over its existing `egg_info` and `bdist_wheel` machinery, so that projects can opt in by supplying a `pypa.json` that invokes it.

# Rejected Alternatives

**Python API entry point.** Having the installer import a module and call functions was considered. It is simpler for Python build tools but forces build and installer to share an interpreter and imposes import-time side effects. The subprocess model isolates them.

**Metadata in setup.cfg.** Declarative metadata in an existing file was considered but there was no suitable standard file in common use for build-system configuration.

**Using entry points.** Requires the build system to be installed before it can be discovered, which is the problem the interface is trying to solve.

# Open Issues

- Whether to permit shell-style quoting in commands. The proposal is no: commands are argument lists.
- Whether `develop` should be made mandatory.
- Naming of the file. `pypa.json` is a placeholder and might be better under a name reflecting build systems specifically.
