# PEP 570: Python Positional-Only Parameters

- **Status:** Draft
- **Type:** Standards Track
- **Created:** 20-Jan-2018
- **Python-Version:** 3.8

## Abstract

This PEP proposes to introduce a new syntax, `/`, for specifying positional-only parameters in Python function definitions.

Positional-only parameters have no externally-usable name. When a function accepting positional-only parameters is called, positional arguments are mapped to these parameters based solely on their order.

When designing APIs (application programming interfaces), library authors try to ensure correct and intended usage of an API. Without the ability to specify which parameters are positional-only, library authors must be careful when choosing appropriate parameter names. This care must be taken even for required parameters or when the parameters have no external semantic meaning for callers of the API.

In this PEP, we discuss:

- Python's history and current semantics for positional-only parameters
- the problems encountered by not having them
- how these problems are handled without language support
- the proposed syntax and its semantics
- alternatives that were considered and rejected

## Motivation

The existing semantics of Python function definitions give every parameter a name that callers may use as a keyword. In most code that is a feature. In some code it is a trap.

### Names that mean nothing to the caller

Consider the built-in `len`. Its single parameter is conceptually "the object whose length is wanted." Documentation calls it `obj`, but a caller writing `len(obj=x)` is not doing anything useful, and indeed `len` rejects it. The built-ins implemented in C have always been able to declare parameters that are positional only, but a function written in Python cannot.

The result is that the Python language cannot express, in its own syntax, signatures that the standard library uses all the time. Documentation shows these with a `/` in the signature printed by `help()`, a convention already used by the `inspect` module and by Argument Clinic, but it is a notation that cannot be typed into a `def` statement.

### Names become part of the API

When a parameter can be passed by keyword, its name is part of the public interface. Renaming it is a breaking change even when nobody intended callers to use it. Consider a library function:

    def clamp(value, low, high):
        ...

If a user has written `clamp(value=5, low=0, high=10)`, the maintainer cannot rename `value` to `x` without breaking that call. Library authors currently deal with this by choosing names carefully, by prefixing with underscores, or by never renaming, none of which is a satisfying answer.

### Interaction with `**kwargs`

A function that accepts arbitrary keyword arguments can collide with its own parameter names. The classic case is a function that wants to accept any keyword, including one named `self`:

    class Counter(dict):
        def update(self, *args, **kwargs):
            ...

    c = Counter()
    c.update(self=1)   # TypeError: got multiple values for argument 'self'

`dict.update` in CPython accepts this call. The pure-Python equivalents cannot. Authors resort to extracting `self` from `*args` by hand, as `collections.UserDict` does, which obscures the intent.

### Subclass compatibility and performance

When parameter names are not part of the contract, subclasses may override a method with different names without breaking the Liskov substitution principle as enforced by type checkers. Also, a function that does not need to map keyword arguments can parse its arguments faster, and positional-only parameters allow implementations to avoid some of the overhead.

### Existing workarounds

Libraries have devised conventions. One is to prefix the parameter with a double underscore, as in `def f(__x)`. Type checkers treat these as positional-only. But the convention is invisible at runtime, it is ugly, and it interacts badly with name mangling inside classes. Others take `*args` and unpack them manually, losing the signature.

## Rationale

The proposal aims to give Python code the same expressive power as built-in functions. The `/` marker was chosen because it is already the notation used in the output of `help()` and by Argument Clinic, so there is already a body of documentation in which it appears. Users of the standard library will already have seen it.

## Specification

A new marker `/` may appear in a function's parameter list. Every parameter to the left of `/` is positional-only. Every parameter to the right follows the existing rules.

    def name(positional_only_parameters, /, positional_or_keyword_parameters,
             *, keyword_only_parameters):
        ...

Some examples:

    def f(a, b, /, c, d, *, e, f):
        ...

Here `a` and `b` are positional-only, `c` and `d` may be passed either way, and `e` and `f` must be passed by keyword.

    f(10, 20, 30, d=40, e=50, f=60)    # valid
    f(10, b=20, c=30, d=40, e=50, f=60)  # invalid: b is positional-only
    f(10, 20, 30, 40, 50, f=60)         # invalid: e is keyword-only

### Rules

- The `/` must appear after at least one parameter. `def f(/, a)` is a syntax error.
- The `/` may appear at most once and must precede any `*` or `*args`.
- Parameters to the left of `/` may have default values, subject to the existing rule that a parameter with a default may not be followed by one without, unless the latter is keyword-only. Thus `def f(a=1, /, b)` is an error.
- A positional-only parameter may have the same name as a key in `**kwargs`.

        def f(a, /, **kwargs):
            return a, kwargs

        f(10, a=20)   # returns (10, {'a': 20})

This makes it easy to write a function that accepts arbitrary keywords without collision.

### Lambdas

The same syntax is permitted for `lambda`:

    lambda a, /, b: a + b

### Introspection

The `inspect` module already recognizes `Parameter.POSITIONAL_ONLY` as a parameter kind. With this PEP, `inspect.signature` reports it for Python functions as well. The `code` object gains an attribute `co_posonlyargcount`, which holds the number of positional-only parameters. The `types.CodeType` constructor gains a corresponding argument, which is a compatibility concern for tools that create code objects directly.

### Error messages

Passing a positional-only argument by keyword produces a `TypeError` naming the offending parameters:

    TypeError: f() got some positional-only arguments passed as keyword arguments: 'a'

## How to Teach This

Introduce `/` as the counterpart of `*`. Whereas `*` says "everything after me must be named," `/` says "everything before me must not be." Together they form the three zones of a signature:

    def f(positional_only, /, standard, *, keyword_only): ...

For most users, this will be an advanced feature, and tutorial text should say so. It should be explained in the reference section on function definitions, with a short note in the tutorial under "More on Defining Functions."

Guidance for library authors: use positional-only parameters when the name has no meaning to callers, when you may want to rename, or when you want to accept arbitrary keyword arguments. Prefer ordinary parameters when the name makes call sites clearer.

## Rejected Ideas

### A decorator

A decorator could mark parameters as positional-only. This would be implemented at runtime by wrapping the function, with obvious overhead, and cannot express the intent to a static analyzer without special handling.

### Using `__` prefixes in the language

Giving the existing convention official semantics would reuse the syntax but would break code that already uses such names for other reasons and would require name-mangling exceptions.

### Placing `/` at the right end of the positional-only group, as a prefix to a parameter

Some designs put a marker on each positional-only parameter. They are verbose and make the signature hard to scan.

### A different marker such as `|` or `//`

None had the advantage of matching the documentation notation already in use.

## Backwards Compatibility

The `/` token was previously illegal in a parameter list, so no existing valid code changes meaning. Tools that parse Python source, such as linters and formatters, must be updated to handle the new grammar. Code that creates `CodeType` objects directly must supply the new count.

## Reference Implementation

An implementation is available as a branch of CPython and modifies the grammar, the compiler, the function-call machinery and `inspect`.
