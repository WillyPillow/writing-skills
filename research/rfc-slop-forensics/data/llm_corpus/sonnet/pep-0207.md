PEP: 207
Title: Rich Comparisons
Status: Final
Type: Standards Track
Created: 25-Jul-2000
Python-Version: 2.1

# Abstract

This PEP proposes several new features for comparisons:

- Allow separately overloading of `<`, `>`, `<=`, `>=`, `==`, `!=`, both in classes and in C extensions.
- Allow any of those overloaded operators to return something else besides a Boolean result.

# Motivation

The current comparison machinery in Python is built around a single three-way function. A class may define `__cmp__(self, other)`, which returns a negative number, zero, or a positive number, depending on whether `self` is less than, equal to, or greater than `other`. Extension types implement the same idea via the `tp_compare` slot. All six comparison operators are then derived from the result of this one function.

This design is simple, and it works well for types with a total ordering, such as integers, strings, and tuples. It breaks down for several important kinds of objects.

**Numerical arrays.** The Numeric extension and its successors want `a < b` to produce an array of Boolean values, one per element, so that results can be used as masks. This cannot be expressed with `__cmp__`, since the result must be a single integer.

**Symbolic and deferred computation.** A library for building symbolic expressions, or for constructing database queries, would like `x == 5` to produce an expression object that can later be evaluated or translated into SQL. Again, a Boolean result is not appropriate.

**Partial orders.** Sets are ordered by inclusion, and two sets can be neither smaller nor larger than one another, nor equal. A three-way comparison has no way to say "incomparable". Under the current scheme, one must return some arbitrary value, which makes `a <= b` and `a >= b` both false for incomparable sets only by accident.

**Efficiency.** Testing for equality is often much cheaper than computing a full ordering. For example, comparing two long sequences for equality can stop at the first mismatch in length, without having to determine which is larger. Complex numbers and some other types can be tested for equality, but have no meaningful order at all, and currently raise an exception or provide an arbitrary ordering.

All of these problems have been worked around in ad hoc ways. The goal of this PEP is to provide the language-level hooks so that workarounds are not needed.

# Proposed Semantics

## New special methods

Six new special methods are added for classes:

```
__lt__(self, other)    # self <  other
__le__(self, other)    # self <= other
__eq__(self, other)    # self == other
__ne__(self, other)    # self != other
__gt__(self, other)    # self >  other
__ge__(self, other)    # self >= other
```

Each takes the other operand as its only argument and may return any Python object. Returning `NotImplemented` indicates that the method does not know how to compare the operands, in which case the interpreter tries the reflected operation on the other operand. If both sides return `NotImplemented`, the interpreter falls back to the older mechanisms.

## Reflected operations

For binary operators, if the left operand does not implement the operation, the right operand is consulted with the swapped operator. The swapped pairs are:

- `<` and `>`
- `<=` and `>=`
- `==` and `==`
- `!=` and `!=`

So, evaluating `a < b` first calls `a.__lt__(b)`. If that returns `NotImplemented`, then `b.__gt__(a)` is tried. If a subclass of the type of the left operand appears on the right, the subclass's reflected method is tried first, which follows the convention used for arithmetic operators.

## Fallback

If neither operand supplies a rich comparison, the interpreter falls back to `__cmp__`, if one is defined, as it does today. If there is no `__cmp__` either, the default comparison is by object identity for equality tests, and an arbitrary but consistent order, such as by address, for ordering tests. This fallback for ordering is retained for compatibility, although future versions might consider making ordering comparisons of unrelated types an error.

## Return values and truth

Because comparisons can return arbitrary objects, there is the question of what happens when the result is used in a Boolean context, such as an `if` statement or a `while` loop. The result is simply tested for truth like any other object. For an array type, this means that `if a < b:` might raise an exception, since the truth value of an array is ambiguous. This is intended: the programmer should write `if (a < b).all():` or the like.

Comparison chains such as `a < b < c` are evaluated as `a < b and b < c`, with each comparison evaluated at most once. The `and` operator tests truth of the intermediate result and returns it if it is false. Thus, for rich objects, a chained comparison returns the first false result, or the last result.

## No implied relationships

The six methods are independent. Python does not assume that `a == b` is the opposite of `a != b`, or that `a <= b` is equivalent to `a < b or a == b`. Programmers are responsible for making their methods consistent, where consistency makes sense. For symbolic or array types, these identities do not hold.

This lack of derivation is a deliberate choice. A decorator or mixin might be written later to fill in the missing operators from a small number of primitives, but it would be a library matter.

# C API

## New type slot

A new slot, `tp_richcompare`, is added to the type object. It has the signature:

```c
PyObject *(*richcmpfunc)(PyObject *, PyObject *, int);
```

The third argument is one of the constants `Py_LT`, `Py_LE`, `Py_EQ`, `Py_NE`, `Py_GT`, `Py_GE`. The function returns a new reference to the result, or `Py_NotImplemented`, or NULL with an exception set.

A type that wants to use rich comparison sets this slot. Since adding a slot changes the layout of the type object, a flag, `Py_TPFLAGS_HAVE_RICHCOMPARE`, is added to indicate that the slot is present. Extension modules compiled against earlier versions do not set the flag, and thus their types are not consulted.

## New API functions

```c
PyObject *PyObject_RichCompare(PyObject *o1, PyObject *o2, int op);
int PyObject_RichCompareBool(PyObject *o1, PyObject *o2, int op);
```

The first returns the object produced by the comparison. The second converts it to a C integer, with -1 indicating an error. Existing code that uses `PyObject_Compare` continues to work; it first tries `__cmp__` and, if that is not available, uses `==` and `<` to derive the three-way result.

# Built-in Types

Built-in types are converted to the new mechanism where this makes sense. The basic numeric types, strings, tuples, and lists implement `tp_richcompare` and return Boolean results. Lists and tuples compare lexicographically, using `==` first to find the first differing position and then the requested operator to decide the result.

Complex numbers support only `==` and `!=`. Ordering comparisons raise `TypeError`, since no natural order exists. For backward compatibility the exception is not raised in the first release, and a warning is issued instead.

Dictionaries support equality, and may support ordering as before using the fallback.

# Backward Compatibility

The change is compatible with all existing code. Classes that define `__cmp__` keep working, and so do extensions that provide `tp_compare`. Code which relies on the existing fallback for ordering unrelated objects continues to see the same behavior.

One visible difference is the effect on `sort()` and similar functions, which use `<`. They now invoke `__lt__` where present. Types that define only `__eq__` and not `__lt__` will lose their ordering unless `__cmp__` is also present.

# Implementation

The reference implementation modifies `Objects/object.c` to add `PyObject_RichCompare`, changes the evaluation of comparison opcodes in `ceval.c` to call it, adds the new slots to class instances and the new special method names to `typeobject`, and converts the built-in types incrementally.

# Open Issues

- Whether to emit deprecation warnings when only `__cmp__` is provided.
- Whether `NotImplemented` should be usable in contexts other than rich comparisons, for example arithmetic.
- Whether the default `==` should continue to be identity-based.
