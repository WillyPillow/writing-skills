Title: A circuit breaking protocol and binary operators

# Abstract

Inspired by PEP 335, PEP 505, PEP 531, and the related discussions, this PEP proposes the definition of a new circuit breaking protocol (using the method names `__then__` and `__else__`) that provides a common underlying semantic foundation for:

* conditional expressions: `LHS if COND else RHS`
* logical conjunction: `LHS and RHS`
* logical disjunction: `LHS or RHS`
* the None-aware operators proposed in PEP 505
* the rich comparison chaining model proposed in PEP 535

Taking advantage of the new protocol, it further proposes that the definition of conditional expressions be revised to also permit the use of `if` and `else` respectively as right-associative and left-associative general purpose short-circuiting operators:

* Right-associative short-circuiting: `LHS if RHS`
* Left-associative short-circuiting: `LHS else RHS`

In order to make logical inversion (`not EXPR`) consistent with the above changes, it also proposes the introduction of a new logical inversion protocol (using the method name `__not__`).

# Motivation

Python's short-circuiting operators each decide, in their own way, whether to evaluate their right-hand operand. `and` evaluates the right side if the left is truthy, `or` if the left is falsey, and the conditional expression chooses between two branches by truthiness of a condition. All three consult `bool()` on a single value and nothing else.

That design is simple, and for most programs sufficient. But several proposals have arisen because the truth test is the only customisation point:

* PEP 505 wants to short-circuit on `None` rather than on falsiness, so that `0` and `""` count as valid values.
* PEP 531 generalises that idea to "existence checking" on arbitrary types, such as `NaN`-like missing values or empty optional wrappers.
* PEP 535 wants comparison chains such as `a < b < c` to behave sensibly for objects, like array types, whose comparisons do not return booleans.
* PEP 335 wanted overloadable `and` and `or` for similar reasons.

Each proposal invents its own mechanism. A unified protocol would let all of them be expressed as ordinary library behaviour, and would avoid adding half a dozen new operators.

# Specification

## The circuit breaking protocol

A type participates in the protocol by defining two methods:

* `__then__(self)` is called when the left operand has been evaluated and the operator is deciding whether to continue. It returns either a special sentinel `NotImplemented`-style marker indicating "stop with this result", or a value to be passed to the right-hand side.
* `__else__(self, other)` is called to combine the left operand with the result of the right-hand side when evaluation has proceeded.

More precisely, define the internal operation `circuit_break(value)` as:

1. If `type(value)` defines `__then__`, call it. If the result is the `CircuitBreaker` marker, the expression's result is `value` itself.
2. Otherwise evaluation continues with the right-hand operand.

Types that do not define `__then__` use the default behaviour, which is equivalent to testing `bool(value)`.

## Defining and, or and conditional expressions

With this machinery, the existing operators can be restated:

* `LHS and RHS` evaluates `LHS`, applies `circuit_break`, and, if evaluation continues, evaluates `RHS` and applies `LHS.__else__(RHS_result)` if defined, otherwise returns `RHS_result`.
* `LHS or RHS` is the dual: it stops when `LHS` is considered truthy.
* `LHS if COND else RHS` evaluates `COND`, applies the protocol, and then selects either `LHS` or `RHS` according to the outcome.

Existing built-in types do not define the new methods. Their behaviour is therefore identical to today's.

## Binary short-circuiting operators

The conditional expression grammar is extended so that each half may appear alone:

* `LHS if RHS` is right-associative. It evaluates `RHS`, and if the protocol says to continue, yields `LHS`; otherwise yields `RHS`.
* `LHS else RHS` is left-associative. It evaluates `LHS`, and if the protocol says to stop, yields `LHS`; otherwise evaluates and yields `RHS`.

Combined, `A if B else C` is read as `A if (B else C)` for the purposes of the grammar, with the traditional meaning preserved by definition of the two operators on builtin truthiness.

An example showing the practical effect, using a hypothetical `missing` marker type:

```python
class Missing:
    def __then__(self):
        return CircuitBreaker      # stop: treat as absent
    def __else__(self, other):
        return other

result = config.get("timeout") else DEFAULT_TIMEOUT
```

If `config.get("timeout")` returns an ordinary value, including `0`, that value is the result. If it returns a `Missing` instance, the right-hand side is used.

## Logical inversion

For consistency, `not EXPR` is defined via a new `__not__` method. If the operand's type defines `__not__`, it is called and its result returned. Otherwise the result is `not bool(EXPR)` as at present. This allows types such as the `Missing` marker above to define what "inversion" means, so that `not x else y` and similar constructs remain coherent.

## Comparison chaining

Following PEP 535, the chained form `a < b < c` is defined as `(a < b) and (b < c)` with the middle operand evaluated once. Because `and` now consults the circuit breaking protocol, a comparison result type that defines `__then__` and `__else__` can control how chained comparisons combine: for example, an array type can return an elementwise logical conjunction instead of attempting to coerce the first comparison to `bool`, which fails.

# Rationale

The design aims to reduce several competing proposals to one primitive. A protocol keyed on the left-hand operand follows the precedent set by arithmetic operators, where the left operand's type chooses the behaviour. Separating the decision to continue (`__then__`) from the combination of results (`__else__`) keeps each method trivial to implement and makes the common cases, where only one of the two is needed, convenient.

Making `if` and `else` binary operators is more contentious. It gives the None-aware idioms concise spellings without introducing new symbols such as `??`, and it follows from the observation that the conditional expression is already two short-circuiting binary operations fused together. The cost is a larger grammar and a less familiar reading of `else` in expressions.

# Backwards compatibility

For all existing types, behaviour is unchanged, since none define the new methods. Code that uses `else` or `if` as binary operators was a syntax error previously, so nothing valid changes meaning. The grammar change must be examined for ambiguity with comprehension syntax, in which `if` already introduces a filter clause. The proposal resolves this by requiring parentheses when a binary `if` appears directly in a comprehension's filter position.

# Performance

The additional lookup for `__then__` is performed on the type and can be cached in the type's slots. Short-circuit evaluation of builtin types takes a fast path that avoids the lookup, so a regression is expected only for types that opt in.

# Open questions

* Should the sentinel for "stop" be a public name, and where would it live?
* Whether `__then__` should be allowed to return a replacement for the left operand, enabling coercion.
* How to document the extremely terse operator forms so that they do not harm readability. Several reviewers have argued that `LHS else RHS` reads poorly relative to a dedicated None-coalescing spelling.
* Interaction with PEP 505's optional chaining operators, which this PEP leaves to a follow-up.

# Deferral

Because the proposal depends on the outcome of several related PEPs, none of which has yet been accepted, this PEP is deferred. It is retained as a record of the design space and as a starting point should the related proposals proceed.
