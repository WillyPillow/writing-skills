# PEP 323: Copyable Iterators

- **Status:** Draft
- **Type:** Standards Track
- **Python-Version:** 2.5
- **Created:** 25-Oct-2003

## Abstract

This PEP suggests that some iterator types should support shallow copies of their instances by exposing a `__copy__` method which meets some specific requirements, and indicates how code using an iterator might exploit such a `__copy__` method when present.

## Motivation

The iterator protocol introduced in Python 2.2 is deliberately minimal. An iterator has an `__iter__` method that returns itself and a `next` method that returns the next item or raises `StopIteration`. This simplicity has made iterators easy to write and easy to compose, and it is one reason the protocol has spread through the language and the standard library.

The same simplicity has a cost. Once an iterator has been advanced, there is no way to go back, and there is no way to say "give me another iterator that will produce the same remaining items from this point on". Some algorithms need exactly that. A typical case is a lookahead or backtracking parser that reads tokens from an iterator, tentatively consumes some of them, and wants to rewind if the attempt fails. Another is a function that must traverse the same stream twice, once to gather statistics and once to act on them, when the stream is too large or too expensive to materialize as a list.

Today such code has two options. It can require its argument to be a sequence, which excludes generators and other lazy sources. Or it can call `list()` on the iterator and work on the copy, which gives up the memory and latency advantages that made an iterator attractive in the first place. A third option is `itertools.tee`, which returns independent iterators over a single underlying one. It is general, but it must buffer every item that one of its outputs has consumed and the others have not, and it cannot take advantage of the fact that many iterators could be cloned far more cheaply than by buffering.

Many built-in iterators have trivially small state. An iterator over a list is a reference to the list plus an index. An iterator over a `range`-like object is a current value plus a step. Copying such an iterator costs a few words and loses nothing. It is wasteful that client code has no standard, documented way to ask for that cheap copy when it is available.

## Rationale

The proposal is to standardize an optional method, `__copy__`, on iterator objects, and to specify what it must do. The choice of `__copy__` is deliberate. The `copy` module already looks for that method when `copy.copy` is called, so no new protocol machinery is needed. An iterator that defines `__copy__` automatically becomes shallow-copyable by existing means, and an iterator that does not define it keeps whatever behavior it has today.

The method is optional because not every iterator can support it. An iterator reading from a file, a socket, or a pipe cannot be copied in any meaningful way: the underlying resource has a single position, and two iterators advancing it independently would corrupt each other's view. A generator holds a suspended frame, and copying a frame is not something the implementation can do safely in general. These iterators should simply not provide `__copy__`, and callers must be prepared for that.

## Specification

### Requirements on `__copy__`

An iterator type MAY define a `__copy__` method taking no arguments. If it does, the method MUST satisfy the following.

1. It returns a new iterator object, distinct from the original.
2. The new iterator and the original, taken at the moment of the call, will each independently produce the same sequence of items from that point on, as long as the underlying data is not modified by other means.
3. Advancing either iterator afterward MUST NOT affect the other.
4. The copy is shallow. Items produced by the two iterators may be the same objects. The method does not copy the underlying container or the items.
5. The method MUST be cheap: its cost should not grow with the number of items already consumed or remaining. An iterator for which a copy would require buffering or replaying data SHOULD NOT define `__copy__`.

Requirement 5 matters because client code will use the presence of `__copy__` to decide on a strategy. If `__copy__` could be arbitrarily expensive, the presence of the method would tell the caller nothing.

An iterator whose underlying data is mutable may of course observe mutations made through other references. A list iterator and its copy both see an element appended to the list after the copy was made. This is the same behavior as two independent iterators created over the same list, and it is not considered a violation of requirement 2.

### Which standard iterators gain `__copy__`

The following built-in and standard-library iterators SHOULD support `__copy__` in Python 2.5:

- iterators over lists, tuples, and strings, as returned by `iter()` on those types;
- iterators over dictionary keys, values, and items are excluded, since a dictionary can change size during iteration and the copied iterator would then have to replicate the check that detects this; they MAY gain support later;
- `itertools.count` and `itertools.repeat`;
- `itertools.tee` objects, where the copy shares the underlying buffer;
- `xrange` iterators.

Generator iterators do not support `__copy__`. File iterators do not support it either.

### Using `__copy__` from client code

Code that wants a copy of an iterator should try the cheap route first and fall back gracefully:

    import copy

    def copy_or_tee(it):
        try:
            clone = it.__copy__
        except AttributeError:
            a, b = itertools.tee(it)
            return a, b
        return it, clone()

The pattern shows the intended contract. When `__copy__` exists, the caller keeps the original and receives one clone. When it does not, `itertools.tee` supplies two replacements, and the caller must stop using the original iterator afterward.

This PEP also suggests that `itertools.tee` itself use the pattern internally. Given an iterator with `__copy__`, `tee(it)` can return the original and a clone, avoiding the shared buffer entirely. The result is that `tee` becomes cheaper on the common cases and degrades to the current behavior on the rest.

Because `copy.copy` already honors `__copy__`, callers who prefer the standard idiom may call `copy.copy(it)`. In that case, an iterator without `__copy__` will fall back to the generic reduction machinery, which may either produce an unusable copy or raise an exception. For this reason client code that needs a guaranteed behavior should test for the attribute directly instead of relying on `copy.copy`.

## Backward Compatibility

The proposal adds an optional method. Existing iterator types, including all user-defined ones, continue to work unchanged. The only visible change is that some built-in iterators begin to respond to `copy.copy` with a working independent copy where previously the result was either an error or an object sharing state.

That last point deserves attention. At present `copy.copy(iter([1, 2, 3]))` may return an object that behaves unpredictably, because the generic fallback does not know what the iterator's state means. Making the result well-defined is an improvement, but it is a change in behavior, and code that depended on the old accidental result will notice.

## Reference Implementation

A reference implementation for list, tuple, and string iterators, `xrange`, `itertools.count`, and `itertools.repeat` can be done in a few lines each in C. Each iterator type allocates a new object of its own type and copies its small amount of state, including a new reference to the underlying sequence. No cooperation from the sequence type is required.

For `itertools.tee`, the copy shares the existing linked buffer node, which is already the mechanism by which the two outputs of a single `tee` call share data.

## Alternatives Considered

**A new protocol method with a different name.** A name such as `__clone__` or `copy` would avoid any confusion with the generic copy machinery. It was rejected because it would add a second way of saying the same thing and would not integrate with `copy.copy`.

**Making all iterators copyable.** This is not possible without limiting what iterators can be. Generators, file readers, and wrappers around network connections cannot meaningfully be duplicated.

**Requiring `__copy__` to be deep.** Deep copying would duplicate the underlying container, which is both expensive and, for large data, defeats the purpose.

**A separate "forkable iterator" abstract base class.** Python 2.5 has no such facility for iterators, and the check for an attribute is idiomatic and adequate.

## Open Issues

Whether dictionary iterators should be copyable remains open. The difficulty is the "dictionary changed size during iteration" check, which would need to be duplicated precisely.

There is also the question of whether `__copy__` should be documented as part of the iterator protocol or merely as an optional extension. This PEP takes the latter position: the core protocol stays as small as before.
