PEP: 405
Title: Python Virtual Environments
Status: Draft
Type: Standards Track
Created: 13-Jun-2011
Python-Version: 3.3

# Abstract

This PEP proposes to add to Python a mechanism for lightweight "virtual environments" with their own site directories, optionally isolated from system site directories. Each virtual environment has its own Python binary (allowing creation of environments with various Python versions) and can have its own independent set of installed Python packages in its site directories, but shares the standard library with the base installed Python.

# Motivation

The utility of Python virtual environments has already been well established by the popularity of existing third-party virtual-environment tools, primarily Ian Bicking's `virtualenv`. Virtual environments are already widely used for dependency management and isolation, ease of installing and using Python packages without system-administrator access, and automated testing of Python software across multiple Python versions, among other uses.

Existing virtual environment tools suffer from lack of support from the behavior of Python itself. Tools such as `virtualenv` have to work around the fact that Python was not designed with isolated environments in mind. They do so by copying parts of the standard library into each environment and then patching `site.py` and other modules, or by monkeypatching at startup. This is brittle: the workarounds must track changes in each Python release, they bloat environments with duplicated files, and they cannot reliably support all platforms.

Moreover, because the environment-specific logic lives outside the interpreter, it is unavailable to tools that do not know about it. A virtual environment's marker is not something that the interpreter, `distutils`, or an IDE can detect in a standard way.

This PEP proposes to add native interpreter support for virtual environments. The goal is a simple mechanism, built into Python itself, that third-party tools can build on, that works the same on all platforms, and that does not require copying the standard library.

# Specification

When the Python binary is executed, it attempts to determine its prefix (which it stores in `sys.prefix`), which is then used to find the standard library and other key files, and by the `site` module to determine the location of the site-package directories. Currently the prefix is found (assuming `PYTHONHOME` is not set) by first walking up the filesystem tree looking for a marker file (`os.py`) that signifies the presence of the standard library, and falling back to the build-time prefix hardcoded in the binary.

This PEP proposes to add a new first step to this search. If a file named `pyvenv.cfg` is found either adjacent to the Python executable, or one directory above it, this file is scanned for lines of the form `key = value`. If a `home` key is found, this signifies that the Python binary belongs to a virtual environment, and the value of the `home` key is the directory containing the Python executable used to create this virtual environment.

In this case, prefix-finding continues as normal using the value of the `home` key as the effective Python binary location, which finds the prefix of the base installation. `sys.base_prefix` is set to this value, while `sys.prefix` is set to the directory containing `pyvenv.cfg` (or the directory above, if the file was found one level up from the binary).

The `site` module uses `sys.prefix` for locating site-package directories. Because the two prefixes are now distinct, the virtual environment has its own `site-packages`, while the standard library is found through `sys.base_prefix` and is shared with the base installation. `sys.exec_prefix` and `sys.base_exec_prefix` follow the same pattern.

## Isolation

If the `pyvenv.cfg` file also contains a key `include-system-site-packages` with a value of `true` (case-insensitive), the `site` module will also add the site-package directories of the base installation to `sys.path`, after those of the virtual environment. Otherwise, the base installation's site-packages are not added, and the virtual environment is fully isolated from them. The default created by the supplied tool is `false`.

User site-packages (`~/.local`) are likewise disabled in an isolated environment.

## Creating virtual environments

The creation of the directory layout is performed by a new module in the standard library, `venv`. The module provides an `EnvBuilder` class, which can be subclassed by third-party tools to customize creation, and a command-line interface:

```
python3 -m venv /path/to/new/environment
```

Creation consists of the following steps:

1. Create the target directory and any needed parents.
2. Create `pyvenv.cfg` with the `home` key set to the directory of the creating interpreter, and with `include-system-site-packages` set as requested.
3. Create the directory structure for the environment: `bin` (`Scripts` on Windows), `lib/pythonX.Y/site-packages` (`Lib\site-packages` on Windows) and `include`.
4. Place a Python executable in `bin`. On POSIX systems this is a symlink to the base executable where the platform supports symlinks, or a copy where it does not. On Windows, the launcher is copied.

The `EnvBuilder` class provides hooks, such as `post_setup(context)`, which allow subclasses to install additional software, like setuptools or pip, into the new environment.

## Activation scripts

For convenience, the module also provides optional `activate` scripts that modify the shell's `PATH` and prompt so that the environment's executables are found first. The scripts are conveniences only: invoking the environment's Python executable directly by its full path is sufficient to use the environment, with no activation needed.

## API

The `sys` module gains `sys.base_prefix` and `sys.base_exec_prefix`. Outside a virtual environment, these equal `sys.prefix` and `sys.exec_prefix`, so code can detect a virtual environment by checking whether they differ.

# Backward Compatibility

The change is invisible to Python installations without a `pyvenv.cfg` file in the relevant location. The new `sys` attributes are additions only.

Third-party tools that currently implement virtual environments can continue to do so. Over time they can be reimplemented on top of `venv`, or can check `sys.base_prefix` to adopt the new behavior.

Existing code that tests `sys.real_prefix`, the attribute set by `virtualenv`, will not find it in `venv` environments and should switch to comparing `sys.prefix` with `sys.base_prefix`.

# Rationale

## Why not copy or symlink the standard library?

Copying makes every environment large and out of date when the base installation is upgraded. Symlinks are not available on all platforms and the semantics differ. By teaching the interpreter to locate the shared standard library through the `home` key, neither is needed.

## Why a configuration file instead of an environment variable?

An environment variable must be set before the interpreter is run, and so requires activation. A file located relative to the executable travels with the environment: running `/path/to/env/bin/python` is enough.

## Why a distinct module?

Placing creation in the standard library means that it ships with every installation and can be relied upon by documentation and tutorials.

## Why not support copying of the standard library on request?

Some platforms and use cases, such as environments to be moved between machines, might require this. The `EnvBuilder` API permits a subclass to implement copying, but the standard library does not include it.

# Reference Implementation

A reference implementation is available as a patch against the CPython repository. It modifies `Modules/getpath.c` and `PC/getpathp.c` to detect `pyvenv.cfg`, modifies `Lib/site.py` to honor `include-system-site-packages`, and adds `Lib/venv` with the `EnvBuilder` class and a `__main__` module.

# Open Questions

- How should Windows launcher scripts interact with environments?
- Should `venv` provide a means to upgrade an environment when the base installation changes?
- Should pip and setuptools be installed by default?
