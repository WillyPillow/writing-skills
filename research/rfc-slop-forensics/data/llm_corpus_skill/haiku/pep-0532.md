## Abstract

This PEP proposes a circuit breaking protocol built from two method names, `__then__` and `__else__`. The protocol would give one semantic basis to five constructs: the conditional expression `LHS if COND else RHS`, logical conjunction (`LHS and RHS`), logical disjunction (`LHS or RHS`), the None-aware operators proposed in PEP 505, and the rich comparison chaining model proposed in PEP 535.

The PEP also proposes a second change. The keywords `if` and `else` would work as general purpose short-circuiting binary operators: `LHS if RHS` (right-associative) and `LHS else RHS` (left-associative). ## Specification

The first part of the proposal defines the protocol through the two method names. The specification has to say what each method receives, what it returns, and what the interpreter does with the returned value. Without those details the protocol cannot be checked, and an implementer would have to guess. [TODO: the exact semantics of `__then__` and `__else__`.]

The second part changes the grammar of conditional expressions. The two new forms are the following.

1. `LHS if RHS`, right-associative. A chain `a if b if c` groups as `a if (b if c)`.
2. `LHS else RHS`, left-associative. A chain `a else b else c` groups as `(a else b) else c`.

These forms are described in the abstract but no expression of either form is shown with its value. The specification must state, for `x = a if b`, what `x` becomes when `b` is false, in which order the operands are evaluated, and whether `b` is tested for truth or passed to a method.
