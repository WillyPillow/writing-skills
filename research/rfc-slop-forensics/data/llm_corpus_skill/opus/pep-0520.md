## Abstract

The class definition syntax is ordered by its nature, so the attributes defined in a class body are ordered too. Apart from helping readability, that order is sometimes significant. If it were available outside the class definition, code could use the attribute order without extra boilerplate, such as a metaclass or a manual list of attribute names. Since the information already exists while the class body runs, access to the definition order is a reasonable expectation.

Python does not currently preserve the attribute order from the class definition. This PEP changes that. The order in which attributes are introduced in the class body will be stored in the `__definition_order__` attribute of the class. This allows introspection of the original definition order, for example by class decorators. [TODO: the abstract is cut off here; confirm the remaining examples.]

## Motivation

The body of a class statement runs top to bottom, like any other block. When it finishes, the names it bound are copied into the class's `__dict__`. That mapping does not record the order in which the names were bound, so the order is lost.

Code that needs the order has two options today. The first is a metaclass whose `__prepare__` returns an ordered mapping, which then records the order somewhere on the class:

```python
class OrderedMeta(type):
    @classmethod
    def __prepare__(mcls, name, bases):
        return collections.OrderedDict()

    def __new__(mcls, name, bases, ns):
        cls = super().__new__(mcls, name, bases, dict(ns))
        cls._order = [k for k in ns if not k.startswith("__")]
        return cls
```

The second is to repeat the names by hand:

```python
class Record:
    _fields = ("id", "name", "created")
    id = Field(int)
    name = Field(str)
    created = Field(datetime)
```

Both options have costs. A metaclass can conflict with a metaclass the class or its bases already use, unless one derives from the other, and it cannot be added to a class without changing that class's type. The manual list repeats each name and can drift from the class body when someone adds or reorders a field.

## Specification

### What is stored

After a class statement runs, the new class has an attribute `__definition_order__`. Its value is a tuple of the names bound in the class body, in the order in which each name was first bound.

```python
class Record:
    id = Field(int)
    name = Field(str)
    created = Field(datetime)

    def describe(self):
        ...

assert Record.__definition_order__ == ("id", "name", "created", "describe")
```

## Backwards compatibility

The PEP adds a new dunder attribute. Python reserves names that both begin and end with a double underscore for its own use. Code that already defines `__definition_order__` for its own purposes would be affected; the rule for user-supplied values above decides how.
