## Abstract

This PEP changes how Python reads and writes integers in bases other than ten. The changes target Python 3.0. The parts that do not break existing code are also added to Python 2.6, so that every integer literal valid in 3.0 is also valid in 2.6. The proposal has three parts:

1. Octal literals are written with a leading `0o` or `0O`, instead of a leading `0`.
2. Binary literals are supported, with a leading `0b` or `0B`.
3. String formatting can produce binary representations of integers.

## Motivation

In Python 2.5, an integer literal with a leading zero is octal. `010` is eight, not ten. A reader who has not met this rule reads `010` as ten, and the program silently computes with eight. Leading zeros are common in data that people type by hand, such as dates, times, and zero-padded identifiers:

```python
month = 08   # SyntaxError in 2.5: 8 is not an octal digit
month = 07   # seven, by coincidence the intended value
code = 0100  # sixty-four, not one hundred
```

The first line fails, which at least tells the programmer something is wrong. The third line does not fail. [TODO: author to give an instance of this mistake from a bug report or mailing-list thread.]

The rule also applies when strings are converted to integers with base 0, where the base is taken from the string's prefix: `int("010", 0)` returns 8. Data read from a file can therefore be misread in the same way. [TODO: confirm this behavior in 2.5.]

Hexadecimal literals already have an explicit prefix, `0x`. Octal is the only base whose prefix is a single zero, which looks like an ordinary leading digit. An explicit letter in the prefix makes octal as visible as hexadecimal.

Binary has no literal form in Python 2.5. A program that works with bit masks, such as hardware register values or flags in a file format, writes them in hexadecimal and the reader converts mentally, or writes `int("1011", 2)` at run time. ## Specification

### Literals in Python 3.0

The grammar for integer literals in 3.0 accepts these forms:

| Base | Prefix | Example | Value |
|---|---|---|---|
| 10 | none | `255` | 255 |
| 16 | `0x` or `0X` | `0xff` | 255 |
| 8 | `0o` or `0O` | `0o377` | 255 |
| 2 | `0b` or `0B` | `0b11111111` | 255 |

A decimal literal may not start with `0`, unless the whole literal is zero, which may be written with any number of zeros, such as `0` or `000`. A literal such as `0777` is a `SyntaxError` in 3.0.

The decision to make `0777` an error, rather than read it as decimal 777, is the one in this PEP that matters most for existing code. Code ported from 2.x that contains `0777` meant octal. If 3.0 read it as decimal, the program would keep running with the wrong value, which is the same silent failure the motivation describes, now in the opposite direction. An error makes the porting programmer look at each such literal. [TODO: author to confirm this is the reason for the decision, and to say whether reading it as decimal was considered.]

### Conversion from strings

`int(s, 0)` follows the same rules as the literal grammar: it accepts the `0x`, `0o` and `0b` prefixes, and rejects a decimal string with a leading zero. `int(s, 8)` accepts an optional `0o` prefix. `int(s, 2)` accepts an optional `0b` prefix, as `int(s, 16)` already accepts `0x`.

`int(s, 10)`, and `int(s)` with no base, still accept leading zeros. `int("010")` returns 10, in both 2.x and 3.0. Data with zero-padded decimal numbers is read as decimal, as it is today. [TODO: confirm that `int("010")` returns 10 in 2.5.]

### Output

`oct(n)` returns a string with the `0o` prefix in 3.0, so that its output is a valid 3.0 literal. A new built-in, `bin(n)`, returns a string with the `0b` prefix:

```python
>>> bin(10)
'0b1010'
>>> oct(8)
'0o10'
```

### Python 2.6

Python 2.6 accepts the `0o` and `0b` literal prefixes, the corresponding `int()` behavior, and `bin()`. It keeps accepting `0777` as an octal literal, and `oct()` keeps its 2.x output, because changing either would change the meaning of existing 2.x programs. [TODO: author to decide whether 2.6 warns about leading-zero octal literals in a mode that checks for 3.0 compatibility.]

With these changes, a program written with the new prefixes runs on both 2.6 and 3.0, which is the point of adding the new forms to 2.6 at all.

## The choice of prefix

Octal needs a prefix that cannot be read as the start of a decimal number. `0o` follows the pattern of `0x` and `0b` by naming the base with a letter.

The cost of `0o` is the uppercase form. `0O17` sets a zero next to a capital O, which are hard to tell apart in many fonts. This draft keeps the uppercase form, as the abstract does, for consistency with `0X` and `0B`. It suggests that style guides recommend the lowercase form. ## Backwards compatibility

The changes break 2.x code in 3.0 in three places:

1. Literals with a leading zero, such as `0777`, become syntax errors. Programs must change them to `0o777`.
2. `int(s, 0)` rejects strings with a leading zero.
3. `oct()` returns `'0o777'` instead of `'0777'`. Code that parses the output of `oct()`, or compares it to a string, must change.

The 2to3 conversion tool can rewrite the first case mechanically, because the old meaning is unambiguous. [TODO: author to confirm 2to3 will include such a fixer.] The second and third cases depend on data and on how the program uses strings, and cannot be fixed by rewriting source.

In 2.6, the changes add forms and break nothing, as described above. [TODO: author to confirm that no existing 2.x program uses `0o` or `0b` in a way the new grammar would change. Both are syntax errors in 2.5 as far as this draft can tell, which would make the claim hold.]
