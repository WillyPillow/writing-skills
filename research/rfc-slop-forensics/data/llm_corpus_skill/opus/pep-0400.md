# PEP 400: Deprecate codecs.StreamReader and codecs.StreamWriter

## Abstract

`io.TextIOWrapper` and `codecs.StreamReaderWriter` offer the same API for reading and writing text over a byte stream [#f1]_. This PEP proposes deprecating `codecs.StreamReader`, `codecs.StreamWriter` and `codecs.StreamReaderWriter`, and making `codecs.open()` return an `io.TextIOWrapper`. Python would then have one implementation of encoded text streams instead of two.

## Background

The `codecs` module was introduced in Python 2.0 by PEP 100. It defines codecs as a set of functions and classes, among them `StreamReader` and `StreamWriter`, which wrap a byte stream and decode or encode text as it passes through. `StreamReaderWriter` combines the two for streams opened for both reading and writing, and `codecs.open()` returns one.

The `io` module was introduced in Python 2.6 and 3.0 by PEP 3116. Its `TextIOWrapper` class does the same job: it wraps a buffered byte stream and exposes `read()`, `readline()`, `write()` and iteration over text. The `io` module was reimplemented in C in Python 2.7 and 3.1. In Python 3, the built-in `open()` returns a `TextIOWrapper` in text mode.

Since then, CPython has shipped two classes that wrap a byte stream with an encoding. Most code uses the `io` one, because `open()` returns it.

## Specification

The change has two parts.

First, `codecs.open()` returns an `io.TextIOWrapper` instead of a `codecs.StreamReaderWriter`. It keeps its current signature. Its `encoding`, `errors` and `buffering` arguments are passed to the underlying `io` objects. ## Rationale

The decision to deprecate the `codecs` classes, rather than the `io` one, follows from where users already are. `open()` returns a `TextIOWrapper`, the C implementation is in `io`, and new features are added there. Keeping `codecs` and removing `io` is not a real option.

The decision to redirect `codecs.open()` rather than deprecate it is meant to let existing callers keep working. Callers who use `codecs.open()` only to get an encoding argument, as was common in Python 2 code, get the faster class without changing anything. ## Migration for users

Most callers need no change. A caller of `codecs.open()` that only reads and writes text keeps working, because `TextIOWrapper` provides the methods `StreamReaderWriter` provides.

A caller that constructs a stream class directly migrates as follows:

1. Replace `codecs.getreader(enc)(stream)` with `io.TextIOWrapper(stream, encoding=enc)`.
2. Replace `codecs.getwriter(enc)(stream)` with the same call, and call `flush()` where the old code relied on unbuffered writes. [TODO: confirm whether `write_through=True` gives the old behavior exactly.]
3. If the stream is not a buffered binary stream, wrap it in `io.BufferedReader` or `io.BufferedWriter` first. [TODO: check which stream types `TextIOWrapper` accepts that the codecs classes did not, and the reverse.]

A codec author whose codec defines its own stream classes should check that the codec's incremental decoder and encoder give the same results, because `TextIOWrapper` uses only those. A codec whose incremental classes are missing or incomplete will not work through `codecs.open()` after this change. ## Alternatives

The status quo keeps both implementations. It costs nothing now, and it continues the duplicated maintenance and the behavioral drift described in the motivation.

1. Reimplement `StreamReaderWriter` as a thin wrapper around `TextIOWrapper`, keeping the class and its name. This removes most duplicated logic without a deprecation, but keeps two public names for one thing.
2. Fix the behavioral differences in `codecs` and keep both. This addresses drift, but not duplication.
3. Document the preference for `io` without deprecating anything. This costs nothing, and does not reduce the maintenance burden.

## Open questions

1. The deprecation and removal schedule.
2. What `codecs.open()` should do with bytes-to-bytes codecs, which `TextIOWrapper` cannot wrap.
3. Whether the stream classes should remain available for codecs that cannot be expressed through incremental encoders and decoders.
