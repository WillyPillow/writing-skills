# PEP 504: Using the system RNG by default

## Abstract

The module-level functions of the `random` module, such as `random.random()`, `random.choice()` and `random.randint()`, draw from a deterministic Mersenne Twister generator. A developer doing security-sensitive work is expected to know this and switch to `os.urandom`, `random.SystemRandom`, or a third-party library such as `cryptography`. This PEP proposes that the module-level functions use the operating system's random number generator by default, and that a program which needs a repeatable sequence asks for one explicitly.

## Motivation

The current default requires the developer to classify their own work. A developer who knows that a value is a session token, a password reset code or a nonce will use `secrets`-style interfaces such as `random.SystemRandom`. A developer who does not recognize the work as security-sensitive uses the module-level functions, and their users then depend on values an attacker may be able to predict, because Mersenne Twister output can be reconstructed from enough observed values [TODO: citation].

The problem is chronic rather than acute. No single misuse is likely to cause a widespread incident on the day it ships. The difficulty is that the delay between introducing the flaw and someone exploiting it is often long, so the developer who made the choice rarely sees its consequence and cannot learn from it. Documentation warnings have the same weakness: they reach only the developers who read the documentation for a function they believe they already understand.

A fix that depends on each developer learning the distinction therefore cannot become pervasive. A fix that changes the default can, because it protects the developers who never learn the distinction.

## Goals and non-goals

The goals are these:

- A program that calls `random.random()` or any other module-level function, without ever calling `random.seed()`, gets values from the operating system's generator.
- A program that needs a repeatable sequence, such as a simulation or a test with a fixed seed, continues to get one, with no more than a one-line change and preferably none.
- `random.Random` instances keep their current behavior. Only the module-level functions change.

Non-goals:

- This PEP does not change `random.Random`, `random.SystemRandom` or `os.urandom`.
- This PEP does not make the `random` module the recommended interface for cryptography. A developer who knows their work is security-sensitive should still use a purpose-built interface.
- This PEP does not address the quality of the operating system's generator on any platform.

## Proposal

### The default generator

At import time, the `random` module binds its module-level functions to an instance of `random.SystemRandom` instead of an instance of `random.Random`.

### Opting into determinism

A call to `random.seed(n)`, or to `random.setstate(state)`, at module level switches the module-level functions to a fresh `random.Random` instance, seeded as requested. Once switched, the module stays in deterministic mode for the life of the process.

The reason for switching on `seed()` is that a program which calls `seed()` has declared that it wants a repeatable sequence. A program can get a repeatable sequence from the module-level functions today only by calling `seed()` or `setstate()`, so programs that rely on determinism keep working without changes.

### Example

A script that generates a temporary password:

```python
import random, string
password = "".join(random.choice(string.ascii_letters) for _ in range(16))
```

Under this proposal the script draws each letter from the operating system's generator, with no change to its source.

A simulation that fixes its seed:

```python
import random
random.seed(1234)
samples = [random.gauss(0, 1) for _ in range(1000)]
```

Under this proposal the call to `seed()` switches the module to a Mersenne Twister instance, and the simulation produces the same samples as before.

## Design decisions

### Why change the default rather than add warnings

The force behind this decision is the one described in the motivation: the developers at risk are those who do not know their work is security-sensitive, and a warning in documentation does not reach them. A runtime warning on every module-level call would reach them, but it would also fire for every simulation, game and test that uses the module correctly.

### Why switch modes on `seed()`

This decision serves the second goal: existing deterministic programs keep working. The cost is implicit behavior. A reader of `random.random()` cannot tell which generator it uses without knowing whether any code in the process has called `seed()`.

The decision is moderately expensive to reverse. Once programs rely on `seed()` selecting Mersenne Twister, removing that rule would break them.

`SystemRandom` makes a call to the operating system for each value, whereas Mersenne Twister computes values in process. The module-level functions are therefore expected to become slower for programs that do not call `seed()`. ## Drawbacks

The proposal makes the behavior of the module-level functions depend on hidden global state: whether anything has called `seed()`. Today the behavior depends only on which function is called.

The proposal also makes the module slower for a class of programs that did nothing wrong, such as games and procedural generation that never fix a seed and do not need security.

Finally, it may weaken the incentive for developers to learn which generator suits their work, because the default now hides the difference.
