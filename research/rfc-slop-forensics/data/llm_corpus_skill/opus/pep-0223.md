## Abstract

Change `\x` escapes, in both 8-bit and Unicode strings, to consume exactly the two hex digits that follow. This PEP treats the change as the correction of a flaw in the original design. It argues that the change leads to clearer expression in all kinds of string, a cleaner story for Unicode, better compatibility with Perl regular expressions, and minimal risk to existing code.

## The current rule

Today a `\x` escape in a string literal consumes every hex digit that follows it, however many there are. [TODO: confirm this description against the current tokenizer, and state what happens to the value when more than two digits are consumed. The draft assumes that only the low-order 8 bits are kept, as in C.]

Under that rule, the following literal does not contain the characters the writer probably meant:

```python
s = "\x41BC"
```

A reader may expect `"A"` followed by `"BC"`, three characters. The current rule reads `41BC` as one hex number, so `s` holds a single character. The same thing happens whenever a hex escape is followed by a letter from `a` to `f`, from `A` to `F`, or by a digit. To get the intended string today, the writer must split the literal:

```python
s = "\x41" "BC"
```

## Proposal

A `\x` escape consumes exactly the two characters that follow it. Both must be hex digits. The value of the escape is the byte, or the code point, with that two-digit hex value.

Under this rule, `"\x41BC"` is the three-character string `"ABC"`.

If fewer than two hex digits follow `\x`, the literal is invalid. [TODO: confirm that the author wants a compile-time error, and name the exception. A suggested alternative for the author to evaluate is to accept one digit, as some other languages do. That would keep more existing literals valid, but it reintroduces a rule that depends on the next character.]

The rule is the same in 8-bit strings and in Unicode strings. A Unicode string can still name any code point. Code points above `\xff` use the existing `\u` escape with four hex digits. ## Why the current rule is a flaw

The abstract calls the current rule a design flaw. The draft can state two concrete reasons from the examples above. [TODO: the author's own account of the flaw, and its origin, if they want it recorded.]

First, the meaning of an escape depends on characters that are not part of it. Whether `"\x41"` is followed by `"BC"` or by `"GH"` changes how many characters the escape consumes. A reader must scan past the escape to know where it ends.

Second, in an 8-bit string, consuming more than two hex digits can never produce a value larger than one byte. The extra digits are read and then discarded. A rule that reads input only to throw it away does not help any writer.

## Effects claimed for the change

The abstract claims four effects. Each is stated here with what supports it and what is still missing.

### Clearer expression in all kinds of string

With a fixed length, an escape ends at a known position. The writer no longer needs to split a literal to put a hex digit after an escape. This follows from the rule itself.

### A cleaner Unicode story

In a Unicode string, a greedy `\x` could in principle produce a value above 255. Then `\x` would be a second, variable-length way of writing code points, next to `\u`. With the proposed rule, `\x` always names a value from 0 to 255 in both kinds of string, and `\u` names larger code points. Each escape then has one meaning. ## Backwards compatibility

The change alters the meaning of existing source code for the two forms named in the previous section. It is a change to the language's lexical rules. Once released, reverting it would change the meaning of literals again, so it should be treated as hard to undo.

The change also affects any code that builds string literals from escapes, such as `eval` on generated source and tools that generate Python code. [TODO: whether such code is known to emit `\x` with more than two digits.]
