# PEP 346: User defined ("`with`") statements

## Abstract

This PEP combines the "Reliable Acquisition/Release Pairs" of PEP 310 with the "Anonymous Block Statements" of PEP 340. It takes the parts of PEP 340 that this PEP's author considers sound, combines them with parts of PEP 310, and arranges the result into one proposal for a statement that runs setup code before a block and cleanup code after it, whether the block finishes normally or raises. It borrows from other PEPs where needed so that it can be read on its own.

## Motivation

Python code often needs to pair two actions around a block: acquire a lock and release it, open a file and close it, start a transaction and either commit or roll it back. The correct way to write such a pair today is `try`/`finally`:

```python
lock.acquire()
try:
    update_shared_state()
finally:
    lock.release()
```

This pattern has three weaknesses. The acquisition and the release are far apart in the source once the block grows. The programmer must remember to put the acquisition outside the `try`, so that a failed acquisition does not trigger a release. And the pattern cannot be factored into a reusable function without passing the block in as a callable, which loses access to the enclosing function's local variables and to `return`, `break` and `continue`.

PEP 310 and PEP 340 each address this problem. [TODO: check the following descriptions against the text of the two PEPs. They are this draft's reading of the PEP titles, not of their contents.] PEP 310 proposes a statement that calls an acquire method on an object before the block and a release method after it. PEP 340 proposes a more general anonymous block statement that lets a generator control the execution of the block.

## Specification

### Syntax

```
with_stmt: 'with' expression ['as' target] ':' suite
```

### Semantics

The statement

```python
with EXPR as VAR:
    BLOCK
```

behaves as follows:

1. Evaluate `EXPR` to obtain a manager object.
2. Call the manager's `__enter__()` method. If `as VAR` is present, assign its return value to `VAR`.
3. Execute `BLOCK`.
4. Whether `BLOCK` completes normally, raises an exception, or is left by `return`, `break` or `continue`, call the manager's `__exit__()` method.

If `__enter__()` raises, `BLOCK` is not executed and `__exit__()` is not called. This is the property that the `try`/`finally` pattern achieves by placing the acquisition outside the `try`.

`__exit__()` receives information about how `BLOCK` ended. [TODO: the author should specify its signature. ### The `with` statement is not a loop

`BLOCK` runs at most once. A `break` or `continue` inside `BLOCK` applies to the nearest enclosing loop, as it would if the `with` statement were not there.

### Writing managers as generators

Writing a class with `__enter__()` and `__exit__()` methods for every pair of actions is verbose. This PEP therefore also proposes a decorator that turns a generator function into a manager factory:

```python
@statement_template
def locked(lock):
    lock.acquire()
    try:
        yield
    finally:
        lock.release()

with locked(my_lock):
    update_shared_state()
```

The generator runs up to its single `yield` when the statement calls `__enter__()`. The yielded value becomes the value assigned to `VAR`. When `BLOCK` ends, `__exit__()` resumes the generator. If `BLOCK` raised, the exception is raised inside the generator at the `yield`, so that the generator's own `try`/`finally` or `try`/`except` handles it.

A generator used this way must yield exactly once. [TODO: the author should specify the error raised when it yields a second time or does not yield at all.]

## Examples

The following examples show managers that the statement makes reusable. Each removes a `try`/`finally` block from the calling code.

A file that is closed when the block ends:

```python
@statement_template
def opened(path):
    f = open(path)
    try:
        yield f
    finally:
        f.close()

with opened("/etc/passwd") as f:
    for line in f:
        print line.rstrip()
```

A database transaction that commits on success and rolls back on any exception:

```python
@statement_template
def transaction(db):
    db.begin()
    try:
        yield
    except:
        db.rollback()
        raise
    else:
        db.commit()
```

## Design decisions

### Why one statement for both sources

The two source PEPs offer different mechanisms. PEP 310 places the setup and cleanup in methods of an object. PEP 340 places them in a generator. This PEP keeps the method protocol as the underlying mechanism and adds the generator form on top of it. Each manager, whatever its origin, presents the same two methods to the statement.

The reason given by this draft is that a protocol of two methods is the smallest thing the statement needs to call. Classes that already manage a resource, such as locks and files, can implement the methods directly, and the decorator covers the case where a generator is easier to write. ### Why no looping

Allowing `BLOCK` to run more than once would make `break` and `continue` inside the block ambiguous: they could refer to the `with` statement or to an enclosing loop. Keeping the block single-shot means that wrapping existing code in a `with` statement never changes what its `break` and `continue` statements do. [TODO: the author should confirm that this is the reason for the choice; it is this draft's reasoning, not a recorded decision.]

The cost is that the statement cannot express retry loops or other patterns that run a block repeatedly. Code that needs such patterns keeps using a `for` or `while` loop.

## Backwards compatibility

`with` becomes a keyword. Any existing code that uses `with` as an identifier stops compiling. No other existing syntax changes meaning.

## Drawbacks

The proposal adds two ways to write a manager, a class and a decorated generator, which a reader must learn to recognize. The generator form also hides the call to `__exit__()` behind the decorator, so a reader must understand both generators and the decorator to follow the control flow.

A `with` statement's effect depends on the manager, so a reader cannot tell from the statement alone whether an exception from the block will propagate. That depends on the open question about suppression.
