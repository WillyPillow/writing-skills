## Abstract

This PEP introduces a new C API to optimize calls of objects. It introduces a new "vectorcall" protocol and calling convention, based on the "fastcall" convention that CPython already uses internally. Any user-defined extension class can use the new features.

Most of the new API is private in CPython 3.8. The plan is to finalize its semantics and make it public in Python 3.9.

This PEP deals only with the Python/C API. It does not affect the Python language or the standard library.

## Motivation

To call an object from C, code uses the `tp_call` slot of the object's type. Its signature is

```c
PyObject *tp_call(PyObject *callable, PyObject *args, PyObject *kwargs);
```

where `args` is a tuple and `kwargs` is a dict or `NULL`. A caller that holds its arguments in local variables or on the interpreter's value stack must therefore build a tuple, and often a dict, for every call. The callee then unpacks them again. For a call with a few positional arguments, building and freeing these containers is work that neither side needs.

CPython already avoids that work internally. The fastcall convention passes positional arguments as a C array and keyword names as a tuple, without building an argument tuple or a keyword dict. [TODO: list which internal call paths use fastcall today, for example calls of Python functions and of built-in functions declared with `METH_FASTCALL`.]

The fastcall convention is not available to third-party extension types. A class written in C, such as a function or method type in Cython or another compiler, must implement `tp_call`, so every call to it goes through the tuple-and-dict path, even when the caller had the arguments in an array. [TODO: name the projects or types the author has in mind, and include a benchmark that shows the cost of the `tp_call` path compared with the fastcall path for such a type. The PEP's claim to "optimize calls" needs a measured number.]

This PEP makes the fastcall convention available to any extension type, as a protocol called vectorcall.

## Specification

### The calling convention

A vectorcall function has the signature

```c
typedef PyObject *(*vectorcallfunc)(PyObject *callable,
                                    PyObject *const *args,
                                    size_t nargsf,
                                    PyObject *kwnames);
```

1. `callable` is the object being called.
2. `args` points to a C array of the positional arguments, followed by the values of the keyword arguments.
3. `nargsf` is the number of positional arguments, possibly combined with flags (see below).
4. `kwnames` is a tuple of the keyword argument names, in the same order as their values in `args`, or `NULL` if there are no keyword arguments.

### Calling an object

A new function calls any object with the vectorcall convention:

```c
PyObject *_PyObject_Vectorcall(PyObject *callable,
                               PyObject *const *args,
                               size_t nargsf,
                               PyObject *kwnames);
```

If the callable's type supports vectorcall, the function calls the per-instance pointer directly. Otherwise, it builds a tuple and a dict from the arguments and calls `tp_call`. Callers do not need to know which path is taken. ## Staging: private in 3.8, public in 3.9

Most of the new API is private in 3.8. [TODO: list which names are private and which, if any, are public in 3.8, and whether any part enters the stable ABI.]

The C API is the decision in this PEP that is most expensive to reverse. Once extension modules are compiled against a public signature or a public type slot, changing it breaks those modules. The staging keeps the 3.8 version changeable: if early users find a problem in the convention or in the opt-in mechanism, it can be fixed in 3.9 without a deprecation cycle. ## Backwards compatibility

The PEP adds new API and a new type flag. It does not remove or change the behavior of `tp_call`, and types that do not set the flag are called as before.
