# PEP 439: Inclusion of implicit pip bootstrap in Python installation

## Abstract

This PEP proposes shipping a small `pip` bootstrap executable with every Python installation. When a user runs `pip` for the first time, the bootstrap downloads and installs pip itself, then runs the user's command. The pip implementation is not added to the standard library. The PEP adds no package management or installation mechanism beyond those defined by PEP 427 ("The Wheel Binary Package Format 1.0") and [TODO: distlib PEP number and title].

## Motivation

To install a third-party module today, a new user must first install a package installer. The Python installation does not include one. The usual instructions send the user to download and run a separate script, or to install a system package, before `pip install` works. That first step is where new users stop. [TODO: give evidence, for example support questions, mailing list threads or survey data, showing that installing the installer is a common obstacle. The PEP should not rely on this claim without it.] Documentation for third-party libraries also cannot say "run `pip install x`" and expect it to work, because they cannot assume pip is present.

The goal is that on a fresh Python installation, `pip install <name>` works as the first command a user types, with no prior setup.

## Non-goals

This PEP does not add pip to the standard library. Pip's release cycle is faster than Python's, and a copy in the standard library would be frozen at the version shipped with each Python release. [TODO: author to confirm this is the reason; the abstract states the non-goal but not why.]

This PEP does not define a new packaging format, installer behavior or metadata. The bootstrap installs pip from a wheel, as defined by PEP 427, and from then on pip does all the work.

## Specification

### What ships with Python

The Python installation includes a `pip` command. On Unix-like systems it is a script on the default `PATH` next to the `python` executable. On Windows it is [TODO: specify; for example a launcher in the `Scripts` directory, and whether the installer adds that directory to `PATH`].

The command contains only the code needed to find, download, verify and install pip. It does not contain pip.

### First run

When the user runs `pip` and pip is not installed, the bootstrap does the following:

1. Determine the install location. If the user has write access to the Python installation's site-packages, install there. Otherwise install into the user site-packages directory. [TODO: confirm the rule. This choice decides whether an unprivileged user on a shared system gets a working pip, and whether an administrator's first `pip` run modifies the system installation.]
2. Download the latest pip wheel from the package index.
3. Verify the download (see "Security" below).
4. Install the wheel.
5. Run pip with the user's original arguments.

The user sees one message saying pip is being installed, followed by the output of their command.

### Later runs

Once pip is installed, the `pip` command finds it and passes control to it directly. The bootstrap does not check for updates. Updating pip is pip's job.

### Without network access

If the download fails, the bootstrap prints a message explaining that pip could not be installed and how to install it manually, and exits with a failure status. It does not leave a partial installation. [TODO: decide whether the installation should also bundle a pip wheel for offline use. ## Security

Security is the hardest question in this design, and the one reviewers should focus on.

The bootstrap downloads and executes code on behalf of a user who only asked to install a package. If an attacker can substitute the download, they get code execution with the user's privileges, and possibly with an administrator's if the first run was privileged. Any version of this design must answer how the bootstrap knows the wheel it received is the real pip.

The minimum requirement is that the download uses HTTPS and the bootstrap verifies the server certificate. [TODO: confirm that the standard library on every supported platform can verify certificates by default. If it cannot on some platform, state what the bootstrap does there: refuse, or fall back.]

HTTPS verifies the server, not the file. A compromised index, or a compromised pip release, would pass that check. A stronger option is to verify a signature on the wheel against a key shipped with Python. [TODO: the author should state whether signature verification is in scope. If it is, specify who holds the key, how it is rotated, and what happens when a Python release ships with a key that has since been revoked.]

Hash pinning is a middle option: the bootstrap ships with the hash of a specific pip release and refuses anything else. This gives strong verification but means each Python release can only bootstrap the pip version it was built with. ## Compatibility

Users who already have pip installed see no change, because the bootstrap passes control to the installed pip. Users who have a different program named `pip` earlier on their `PATH` also see no change. [TODO: check whether any existing tool installs a `pip` command at the same path the bootstrap would use.]

Scripts that test for the absence of pip, for example by running `pip --version` and checking for failure, will now trigger a download instead. [TODO: decide whether `--version` and `--help` should run without bootstrapping.]

1. Bundle a full pip installation with each Python release, outside the standard library but installed by default. This removes the network step and the security question on first run, but ships a pip that ages with the Python release.
2. Provide the bootstrap as a standard library module, run as `python -m getpip`, rather than as a `pip` command. This makes the step explicit to the user, at the cost of one extra command.
3. Keep the status quo and improve the documentation for installing pip.
