## Abstract

In Python 2.4 and earlier, the `raise` statement accepts an instance of any classic class, or the class itself. Python 2.5 is planned to allow new-style classes as well. Without a further rule, any object of any class could then be raised. This PEP proposes a new built-in class that every raised object must inherit from. With the restriction in place, every exception has an interface that handlers can rely on, and all exceptions belong to one known hierarchy.

## Motivation

Code that handles an exception usually did not create it. A traceback printer, a logging handler, a test runner, or a bare `except:` clause near the top of a program all receive exceptions raised by code they know nothing about. Each of them needs some interface to the exception: a way to get a printable message, and the arguments it was created with.

Today nothing guarantees that interface. The built-in exceptions inherit from `Exception`, which stores its constructor arguments in `args` and defines `__str__`. A user-defined exception that does not inherit from `Exception` has neither. This class is accepted by `raise` in Python 2.4:

```python
class NotAnException:
    pass

raise NotAnException()
```

A handler that reads `e.args` from such an object fails with an `AttributeError` while it is handling the original error. The handler then reports the wrong problem. The original exception may be lost.

The plan to allow new-style classes in 2.5 widens the gap. In 2.4, only classic classes can be raised, which already excludes, for example, instances of built-in types. Once new-style classes are allowed, `raise` would accept an instance of any class at all, so no assumption about a raised object would be safe.

The language already treats `Exception` as the conventional base. The documentation recommends that user exceptions derive from it. [TODO: check what the 2.4 documentation says, and quote it.] This PEP turns the convention into a rule that `raise` enforces.

## Specification

### A required superclass

A new built-in class, `BaseException`, is added. In the version where the restriction takes full effect (see the transition plan), `raise` accepts an object only if one of the following is true:

1. It is an instance of `BaseException` or of a subclass of it.
2. It is a class that is `BaseException` or a subclass of it. In this case `raise` instantiates it, as it does for exception classes today.

Any other object passed to `raise` causes a `TypeError`.

The rule applies only to `raise`. An `except` clause may still name any class or tuple of classes. [TODO: author to decide whether `except` clauses that name a class outside the hierarchy should warn, since such a clause can never match once the rule is in force.]

### The interface

`BaseException` defines the interface that handlers may rely on:

- `args`: the tuple of positional arguments passed to the constructor.
- `__str__`: returns a string built from `args`. With no arguments, it returns the empty string. With one argument, it returns `str` of that argument. With more, it returns `str` of the tuple.
- `__repr__`: returns the class name followed by the repr of `args`.

These are the behaviors that `Exception` has in 2.4. [TODO: verify each against the 2.4 implementation; the point of this section is that existing handlers see no change for exceptions that already derive from `Exception`.]

This PEP adds nothing else to the interface. A larger interface would be more useful to handlers, but each attribute added here becomes a requirement on every exception ever raised. [TODO: author to decide whether a dedicated message attribute belongs in the base interface.]

### The hierarchy

`Exception` becomes a subclass of `BaseException`. All existing built-in exceptions remain subclasses of `Exception`, so `except Exception:` catches exactly what it catches today.

The open question is whether any built-in exception should inherit from `BaseException` directly instead of from `Exception`. The candidates are exceptions that do not signal an error in the program: `KeyboardInterrupt`, raised when the user interrupts the program, and `SystemExit`, raised by `sys.exit()`. Code that writes `except Exception:` to recover from errors catches both today, so a program can swallow the user's interrupt or its own request to exit. Moving them out from under `Exception` fixes that, at the cost of changing what existing `except Exception:` clauses catch. [TODO: author to decide whether this PEP makes that move or leaves it to a separate PEP. If it makes the move, the compatibility section needs an entry for it.]

## Why a required base class is justified here

Python generally does not require an object to inherit from a particular class to be used in a particular way. A function that reads from a file accepts any object with a `read` method. A reasonable objection to this PEP is that exceptions should work the same way: any object with `args` and `__str__` should be raisable.

## Transition plan

Code that raises objects not derived from `Exception` exists. The transition must give its authors time to change it. The proposed steps are:

1. In 2.5, add `BaseException` and make `Exception` a subclass of it. Allow new-style classes to be raised only if they derive from `BaseException`. Classic classes that do not derive from it can still be raised, as in 2.4.
2. In a later 2.x release, raising a classic class that does not derive from `BaseException` issues a `DeprecationWarning`. [TODO: author to choose the release.]
3. In the release after that, or in Python 3.0, such a `raise` causes a `TypeError`. [TODO: author to choose.]

Leaving aside the hierarchy question above, step 1 does not change the behavior of `raise` for code that runs on 2.4. A new-style class that does not derive from `BaseException` cannot be raised in 2.4, so the new restriction on new-style classes in step 1 breaks nothing.

String exceptions, raised with `raise "some message"`, are a separate case. They predate class-based exceptions and do not belong to any class hierarchy. [TODO: author to decide whether this PEP covers them, and if so, on what schedule they are deprecated and removed.]

## Backwards compatibility

Exceptions that derive from `Exception` keep their behavior. `BaseException` provides the same `args`, `__str__` and `__repr__` that `Exception` provides in 2.4, assuming the verification in the interface section confirms it.

Code that raises classic classes not derived from `Exception` keeps working in 2.5. It produces a warning in a later release and an error after that, as set out in the transition plan.

Code that catches exceptions changes only if the hierarchy changes. If `KeyboardInterrupt` and `SystemExit` move under `BaseException` directly, then `except Exception:` no longer catches them. A program that relied on catching them that way would then exit, or be interrupted, where it previously continued.
