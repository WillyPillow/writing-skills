# PEP 570: Python positional-only parameters

## Abstract

This PEP proposes a new marker, `/`, in function definitions. Parameters before the marker are positional-only: callers cannot pass them by keyword, and their names are not part of the function's interface. A call maps positional arguments to these parameters by order alone.

## Background

Python functions written in Python have no way to declare a positional-only parameter. Every parameter can be passed by keyword, so every parameter name is part of the public interface. Renaming one is a breaking change.

Functions implemented in C already behave differently. Many built-ins accept only positional arguments. For example, `len(obj=[1, 2])` raises `TypeError`, because `len` has no keyword parameter named `obj`. Documentation for such functions uses `/` in the signature to show this, as in `divmod(a, b, /)`. ## Motivation

### Parameter names become public interface

A library author who writes

```python
def clamp(value, low, high): ...
```

has also committed to the names `value`, `low` and `high`. A caller can write `clamp(value=x, low=0, high=1)`, and renaming `value` to `x` breaks that caller. Most callers pass these arguments by position, and the names carry no meaning for them. The author still cannot rename them without a deprecation period. The abstract's point is that this care is needed even for required parameters and for parameters with no meaning to callers. A positional-only marker lets the author say which names are public and which are not.

### Collisions with `**kwargs`

A function that accepts arbitrary keyword arguments cannot accept a keyword whose name matches one of its own parameters:

```python
def format_record(fmt, **fields):
    return fmt.format(**fields)

format_record("{fmt}", fmt="x")  # TypeError: multiple values for 'fmt'
```

The caller wants to pass `fmt` as a field, but Python binds it to the parameter. If `fmt` were positional-only, the name would not be available as a keyword, and `fmt="x"` would go into `fields`. Wrappers, decorators and string formatting functions have this problem. [TODO: cite a standard library function that works around this today, and how it does so.]

### Matching C function signatures

Alternative implementations and pure-Python fallbacks of C modules need to match the C function's signature exactly. Without positional-only parameters, the Python version accepts keyword calls that the C version rejects, so code that works on one implementation fails on the other. ## Specification

### Syntax

A `/` in a parameter list marks every parameter before it as positional-only:

```python
def f(a, b, /, c, d, *, e, f):
    ...
```

Here `a` and `b` are positional-only, `c` and `d` can be passed by position or keyword, and `e` and `f` are keyword-only.

The rules are:

1. `/` may appear at most once.
2. `/` must come after at least one parameter.
3. `/` must come before `*` or `*args`, if either is present.
4. Positional-only parameters may have default values. Once one parameter has a default, every later positional parameter must have one too, as today.

The same syntax applies to `lambda`.

### Semantics

When a function is called, positional arguments fill positional-only parameters first, in order. A keyword argument whose name matches a positional-only parameter is not bound to it. If the function has `**kwargs`, the keyword goes there. Otherwise the call raises `TypeError`.

Parameter names before `/` are still available inside the function body. They are private names, not absent ones.

### Introspection

`inspect.signature` already has a parameter kind `POSITIONAL_ONLY`, used for C functions. Python functions with `/` report that kind for their positional-only parameters. Code objects gain a count of positional-only parameters, so that tools reading code objects can find the boundary. ## Why `/`

The choice of `/` follows existing usage. Argument Clinic and the documentation of built-in functions already write positional-only parameters with `/`, so users who have read a built-in's signature have already seen it. The marker also mirrors `*`, which separates positional-or-keyword parameters from keyword-only ones. A full signature then reads left to right as positional-only, then either, then keyword-only.

## When to use it

The marker is for library authors who need to keep parameter names private. A short guide:

1. Use `/` when a parameter's name has no meaning to callers, such as the single argument of a function like `len`.
2. Use `/` when the function takes `**kwargs` and callers may need to pass a key with the same name as a positional parameter.
3. Do not use `/` when naming the argument at the call site makes the call easier to read. Flags and options are the common case; they are usually better keyword-only.

The `format_record` example from the motivation becomes:

```python
def format_record(fmt, /, **fields):
    return fmt.format(**fields)

format_record("{fmt}", fmt="x")  # returns "x"
```

## Compatibility

This is new syntax. Existing code does not use it and is unaffected. Code that uses it does not run on earlier Python versions, which is the usual cost of new syntax.

Changing an existing parameter to positional-only is a breaking change for callers who pass it by keyword. Library authors who adopt the feature for existing functions need a deprecation period. [TODO: decide whether the PEP recommends a pattern for that transition.]

## Drawbacks

The feature adds a concept to function definitions, which are already complex with defaults, `*args`, keyword-only parameters and `**kwargs`. Most functions do not need it, and readers will meet it mainly in library code.

Library authors may overuse it, making calls less readable when callers would benefit from naming arguments. The PEP leaves that judgment to authors.

1. A decorator that marks parameters as positional-only. This needs no grammar change, but it runs at call time, adds overhead, and is invisible to tools that read signatures statically.
2. A naming convention, such as a leading double underscore, that makes the parser treat a parameter as positional-only. This needs no new token, but it ties semantics to names, which Python does not otherwise do.
3. Keep the status quo and accept `*args` with manual unpacking for functions that need positional-only behavior. This works today, but the signature no longer documents the parameters.
