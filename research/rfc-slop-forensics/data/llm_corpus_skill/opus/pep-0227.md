## Abstract

This PEP adds statically nested scoping, also called lexical scoping, to Python. It becomes the standard rule in Python 2.2, and is available in Python 2.1 as an option that a module enables in its source. Python 2.1 also warns about code whose meaning would change under the new rule.

Python 2.0 resolves every name in one of exactly three namespaces: the local namespace of the current function, the global namespace of the module, and the built-in namespace. Under this PEP, a name that is not bound in the current function is also looked up in the namespaces of the functions that enclose it in the source. The most visible effect is that a lambda, or any nested function, can use variables of the function around it.

## Motivation

A nested function in Python 2.0 cannot see the local variables of the function it is defined in. This code fails:

```python
def make_adder(n):
    return lambda x: x + n

add3 = make_adder(3)
add3(1)   # NameError: n
```

The lambda's body refers to `n`. `n` is not local to the lambda, so Python 2.0 looks for it in the module's globals and then in the built-ins, finds it in neither, and raises `NameError`. `n` is a local variable of `make_adder`, which is the function the lambda is written in, but the 2.0 rule never looks there.

The usual workaround passes the value through a default argument:

```python
def make_adder(n):
    return lambda x, n=n: x + n
```

This works, but it has three costs. The idiom is unclear to anyone who has not seen it before. It adds a parameter that a caller can override by accident: `add3(1, 10)` returns 11. And it copies the value at the time the function is defined, so it cannot express a reference to a variable that changes later.

The same problem affects code that passes callbacks, such as functions given to `map` and `filter`, and handlers in GUI programs. ## Specification

### The resolution rule

A name is bound in a block if the block assigns to it, uses it as the target of a `for` loop, imports it, defines it with `def` or `class`, or has it as a parameter. A function body is a block. A class body is also a block, with an exception described below.

When a name is used in a function, it is resolved as follows:

1. If the name is bound in the current function, it refers to the local binding.
2. Otherwise, if the name is bound in the nearest enclosing function, it refers to that binding. If not, the next enclosing function is checked, and so on outward.
3. Otherwise, the name is global, and is looked up first in the module's globals and then in the built-ins, as in 2.0.

A `global` statement in a function makes the name global in that function, and rule 1 and 2 do not apply to it there.

The resolution is static. The compiler decides which namespace each name refers to from the source text alone, before the code runs. Whether a name is bound in an enclosing function depends on where the function is written, not on which function called it.

### Class bodies

Names bound in a class body are not visible to functions nested inside the class:

```python
class C:
    x = 1
    def f(self):
        return x   # global x, not C.x
```

Methods refer to class attributes through `self` or the class name, as in 2.0. If class bodies took part in rule 2, an unqualified `x` in a method would find the value bound in the class body. `self.x` can find a different value, because instances and subclasses can override the attribute, so the two spellings would disagree. ### Rebinding

Rule 2 applies to using a name, not to binding it. Assigning to a name inside a nested function makes that name local to the nested function, as in 2.0. A nested function therefore cannot assign to a variable of the enclosing function. This PEP does not provide a way to do so. ### Constructs that are no longer allowed

Two constructs make it impossible to decide statically which names a function binds:

- `from module import *` inside a function binds names that the compiler cannot see.
- A bare `exec` statement inside a function can bind any name.

If a function contains either construct and also contains a nested function with free variables, the compiler cannot tell whether a free variable of the nested function refers to the enclosing function. This PEP makes such code a `SyntaxError`. [TODO: author to confirm the exact conditions, for example whether `exec` with an explicit namespace, `exec code in d`, is still allowed.]

## Changes in meaning

Existing code can change meaning. The case is a nested function that uses a name that is both global and bound in an enclosing function:

```python
x = "global"

def f():
    x = "local to f"
    def g():
        return x
    return g()
```

In 2.0, `f()` returns `"global"`. Under this PEP it returns `"local to f"`. No error marks the change; the program just computes a different result.

Python 2.1 detects this case at compile time and issues a warning for each such name. Code that compiles in 2.1 without these warnings has the same meaning under the new rule, apart from the `SyntaxError` cases above. 1. In 2.1, the old rule remains the default. A module can enable the new rule with a statement in its source. [TODO: author to name the mechanism.] The compiler warns about code whose meaning would change, and about the constructs that become errors.
2. In 2.2, the new rule becomes the only rule.

## Implementation

A variable of a function that a nested function uses can outlive the call that created it. In `make_adder`, the lambda is returned, and `n` must survive after `make_adder` returns. The implementation stores such variables in a separate cell object, which both the enclosing function and the nested function refer to. Variables that no nested function uses are stored as before.

One consequence is reference cycles. A nested function that refers to itself, for example a recursive helper, holds a reference to the cell holding the function. Such a cycle is not freed by reference counting alone and depends on the cycle collector. [TODO: author to state the effect on programs that run with the cycle collector disabled.]
