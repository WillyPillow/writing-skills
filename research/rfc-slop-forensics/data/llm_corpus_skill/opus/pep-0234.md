# PEP 234: Iterators

## Abstract

This document proposes an iteration interface that objects can provide to control the behavior of `for` loops. An object customizes looping by providing a method that produces an iterator object. The iterator provides a *get next value* operation, which returns the next item in the sequence each time it is called and raises an exception when no items remain.

The PEP also proposes specific iterators over the keys of a dictionary and over the lines of a file, and proposes that `dict.has_key(key)` may be spelled `key in dict`.

This version of the PEP describes the implementation checked into the trunk of the Python 2.2 CVS tree. It remains open for discussion.

## Motivation

A `for` loop today works only with objects that support indexing. The loop calls `__getitem__` with the integers 0, 1, 2 and so on, and stops when it gets an `IndexError`. This works for lists, tuples and strings, but it forces any other object that wants to support `for` to pretend to be a sequence.

Three kinds of object show the cost of that pretense.

A dictionary has no natural integer index. To loop over its keys, a program must first build a list with `dict.keys()`, which copies every key before the loop starts. [TODO: the author should give a measurement of the cost of this copy for a large dictionary, if one is available.]

A file has lines, but reading line `i` makes sense only if lines `0` to `i - 1` have already been read. A class that wraps a file and implements `__getitem__` must check that it is called with consecutive integers, and it cannot support random access honestly.

A generator of values that has no length, such as one that reads from a socket until the connection closes, has the same problem as the file.

In all three cases, what the loop needs is a way to ask for the next item, not a way to ask for item `i`.

## Specification

### The iterator protocol

An iterator is an object with a method `next()` that takes no arguments. Each call returns the next item. When no items remain, `next()` raises the new built-in exception `StopIteration`. Once an iterator has raised `StopIteration`, further calls should also raise it.

An iterator also has a method `__iter__()` that returns the iterator itself. This lets an iterator be used wherever an iterable object is expected, including in a `for` loop.

### Iterable objects

An object is iterable if it has a method `__iter__()` that returns an iterator. A list, for example, returns a new iterator over its elements each time `__iter__()` is called, so two loops over the same list do not interfere.

### The built-in `iter()`

A new built-in function `iter(obj)` returns an iterator for `obj`:

1. If `obj` has an `__iter__()` method, `iter()` calls it and returns the result.
2. Otherwise, if `obj` supports `__getitem__`, `iter()` returns an iterator that calls `obj.__getitem__` with 0, 1, 2 and so on, and raises `StopIteration` when `__getitem__` raises `IndexError`.
3. Otherwise, `iter()` raises `TypeError`.

Rule 2 is what keeps existing sequence classes working in `for` loops.

### The `for` loop

The statement

```python
for x in obj:
    body
```

is now defined in terms of the protocol. The loop calls `iter(obj)` once, then calls the iterator's `next()` method before each pass, binds the result to `x` and runs `body`. When `next()` raises `StopIteration`, the loop ends and runs its `else` clause, if any.

### Dictionary iterators

Dictionaries implement `__iter__()`, which returns an iterator over their keys. A program can therefore write

```python
for key in d:
    print key, d[key]
```

without building a list of keys first.

### File iterators

File objects implement `__iter__()`, which returns an iterator over the lines of the file. A program can write

```python
for line in f:
    process(line)
```

Each `next()` call returns one line, including its trailing newline, in the same form as `f.readline()`. The iterator raises `StopIteration` at end of file.

### `key in dict`

The `in` operator on a dictionary tests whether a key is present. `key in d` has the same result as `d.has_key(key)`. `key not in d` is its negation.

This follows from defining `in` for any iterable object: `x in obj` is true if iterating over `obj` yields an item equal to `x`. For a dictionary, iterating yields the keys, so `in` tests the keys. Dictionaries implement the test directly, through a hash lookup, rather than by iterating.

## Design decisions

### Why a separate iterator object

The protocol separates the iterable object from the iterator. The alternative, letting the iterable object itself keep the position, would make two simultaneous loops over the same list share one position, so nested loops over one list would fail. [TODO: confirm that this is the author's reason.]

### Why an exception to signal the end

### Why iterating a dictionary yields keys

A dictionary could have yielded keys, values or pairs. This PEP chooses keys. Keys are the choice that makes `for k in d` consistent with `k in d`: in both cases, the dictionary is treated as the collection of its keys. [TODO: confirm that this is the author's reason.]
