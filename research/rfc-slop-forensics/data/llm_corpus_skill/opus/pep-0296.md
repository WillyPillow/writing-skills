## Abstract

This PEP proposes a new standard type, `bytes`, together with a builtin constructor of the same name. A `bytes` object is an array of bytes stored efficiently. It differs in some characteristics from several similar implementations that already exist in or around Python.

## Motivation

Programs that read files in binary mode, parse network protocols, or hand buffers to C extensions all work with sequences of raw bytes. Python can already hold such a sequence in more than one kind of object. The proposal rests on two claims: none of those objects is the right general-purpose container for binary data, and a dedicated builtin type fixes that.

The abstract refers to "several implementations that are similar" without naming them. Candidates for the author to confirm or replace are the `str` type, the `array` module with typecode `'B'`, the `buffer` object, and arrays from third-party numeric packages. ## What is decided

The abstract fixes three things:

1. A new type is added to Python's standard set of types, not shipped as a library class.
2. A builtin named `bytes` constructs instances of it.
3. Each instance stores its byte values compactly.

## Decisions to settle

Each subsection names the force that makes a decision necessary and the options visible from the abstract. The options listed here were not supplied by the author. They are suggestions for the author to evaluate, not options that were considered and rejected.

### Mutability

This is the decision that is most expensive to reverse, so it needs the most justification. If `bytes` objects are immutable, they can be hashed and used as dictionary keys, and they can be shared without defensive copies. If they are mutable, a program can fill one in place from a file or socket, which avoids allocating a new object for each read.

Suggested options:

1. Immutable, like `str`.
2. Mutable in both contents and length, like `array.array`.
3. Mutable contents with a fixed length, so that the object can serve as a reusable buffer but never reallocates.

Whichever option ships, later releases cannot change it without breaking code that depends on hashing or on in-place writes. [TODO: the author's choice, the use case that decides it, and the cost accepted.]

### Result of indexing

Indexing a `str` returns a string of length 1, while indexing an `array.array('B')` returns an integer. Returning an integer matches the idea of an array of numeric byte values. Returning a length-1 `bytes` keeps the behavior of `str` for code ported from it. The choice also fixes what iteration yields, and so it affects every loop over a `bytes` object. ### Relationship to `str`

In current Python, `str` already holds 8-bit data, so `bytes` and `str` overlap. Three questions follow:

1. Does a `bytes` object compare equal to a `str` with the same contents?
2. Does it hash the same, so that the two can stand for each other as dictionary keys?
3. Which `str` methods, if any, does `bytes` also provide (for example `find`, `split` and `startswith`)?

The answer to the first two questions is hard to change later, because programs will store `bytes` objects in dictionaries and sets keyed on the current behavior. [TODO: decisions and reasons.]

### Buffer interface and memory ownership

For `file.write`, `socket.send` and C extensions to accept a `bytes` object without conversion, the type must expose the buffer interface. A separate question is whether a `bytes` object may refer to memory it does not own, such as a region of a memory-mapped file. That would avoid copies, but it raises the question of what happens when the owner releases the memory while a `bytes` object still refers to it.
