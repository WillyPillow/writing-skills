# PEP 442: Safe object finalization

## Abstract

CPython's cyclic garbage collector refuses to collect reference cycles that contain an object with a finalizer. Such cycles are moved to `gc.garbage` and stay in memory for the life of the process. This PEP changes the collector so that it calls finalizers on objects in cyclic garbage and then collects them. Python code does not change. Objects that already define finalizers get the new behavior automatically.

## Definitions

A *finalizer* is code that runs when an object is about to be destroyed. In Python, it is a `__del__` method. In C, it is the deallocation logic of an extension type. This PEP adds a third kind, described below.

*Cyclic trash* is a group of objects that refer to each other and that nothing outside the group refers to. Reference counting alone never frees cyclic trash, because each object keeps the next one alive. The cyclic collector exists to find and free it.

An object is *resurrected* if its finalizer creates a new reference to it from outside the trash, for example by storing `self` in a global list.

## The current limitation

The collector frees cyclic trash by clearing references inside the group until the reference counts reach zero. Consider two objects that refer to each other, where one has a `__del__`:

```python
class A:
    def __del__(self):
        print(self.partner.name)

a, b = A(), B()
a.partner, b.partner = b, a
del a, b
gc.collect()
```

If the collector clears `b` first, `a.__del__` runs when `a` is freed and finds `b` partly torn down. It may read an attribute that has been cleared, or call a method on an object whose state is gone. In C, this can mean reading freed memory.

## Goal

The goal is that finalizers run for any object, wherever it sits in the object graph, and that objects in cyclic trash are freed afterward. A reader can check the goal by two properties. First, no object lands in `gc.garbage` only because it has a finalizer. Second, every finalizer sees the objects it references in a usable state.

## Specification

### The finalization slot

C types gain a new slot, `tp_finalize`. It holds a function that runs the type's cleanup logic while the object is still intact. For classes defined in Python, `tp_finalize` calls `__del__`.

Separating finalization from deallocation is the central idea of the PEP. Today the two happen in one step, so finalization cannot happen while the rest of the cycle is intact. With a separate slot, the collector can call every finalizer in the trash first, while all references are still valid, and free memory only afterward.

### The collection algorithm

When the collector has identified a group of cyclic trash, it proceeds as follows:

1. Call `tp_finalize` on each object in the group that has one and has not yet been finalized. Mark each such object as finalized.
2. Recompute which objects in the group are still unreachable. A finalizer may have resurrected some of them.
3. If any object in the group was resurrected, stop. Leave the whole group alive and do not clear it. It will be examined again in a later collection.
4. Otherwise, clear references inside the group with `tp_clear`, which lets reference counting free the objects.

Step 1 runs every finalizer while all the objects in the group are intact. This is what removes the ordering problem: no finalizer can see a partly cleared object, because no object has been cleared yet.

Step 3 handles resurrection conservatively. The collector could try to separate resurrected objects from the rest, but a resurrected object may reference any other object in the group, so the safe choice is to keep all of them. ### Calling finalizers at most once

Each object carries a flag, set in step 1, that records that its finalizer has run. A finalizer never runs twice on the same object, even if it is resurrected and later becomes trash again. Without the flag, an object whose finalizer resurrects it would be finalized on every collection and never freed.

The flag also applies when an object is freed by reference counting. When the count reaches zero, the object's finalizer runs if the flag is clear. A C type that defines the older `tp_del` slot keeps its current behavior and its cycles still go to `gc.garbage`. Only types that define `tp_finalize` get the new behavior. ## Consequences

Cycles containing Python objects with `__del__` are collected. The main visible change is that `gc.garbage` is empty in cases where it used to fill up. [TODO: name programs or test suites where this was observed.]

Finalizers now run in an order that is unspecified within a group. A finalizer that depended on a particular order was already unreliable, because the old behavior was not to run it at all for cyclic trash. Finalizers that run outside the collector, through reference counting, keep their existing order.

A finalizer may see other objects in the group whose own finalizers have already run. Those objects are intact in memory, but they may have closed files or released resources. A finalizer that calls methods on its neighbors must handle that state. This is the cost the PEP accepts: it guarantees memory safety, not that neighbors are still in their pre-finalization state.

Resurrection is supported but delays collection of the group. A program that resurrects objects in a loop keeps memory alive longer than one that does not.

## Compatibility

The PEP does not change the Python language or any Python-level API. Code that inspects `gc.garbage` to find leaks will see fewer entries. C extensions that define `tp_del` see no change. Extensions that want the new behavior must implement `tp_finalize`.
