# PEP 383: Non-decodable bytes in system character interfaces

## Abstract

POSIX defines file names, environment variables and command line arguments as character data. The C APIs that deliver them, however, pass arbitrary bytes, whether or not those bytes are valid in any particular encoding. Python 3 presents these values as `str`, so it must decode the bytes, and some byte sequences cannot be decoded in the locale's encoding. This PEP proposes a way to embed such bytes in character strings so that the original byte string can be recreated exactly.

## Motivation

A Python 3 program reads a directory listing with `os.listdir()`, a command line with `sys.argv`, and the environment with `os.environ`. Each value arrives from the operating system as bytes and is decoded with the file system encoding, which on POSIX systems comes from the locale.

Nothing in POSIX requires those bytes to be valid in that encoding. A file created by a program running under a Latin-1 locale may have the name `caf\xe9`. On a system whose locale is UTF-8, the byte `0xE9` followed by the end of the name is not valid UTF-8, so the name cannot be decoded.

Python then has three options, none of them acceptable:

1. Raise an exception. A program that lists a directory then fails because of one file it may not even care about.
2. Skip the value. `os.listdir()` then silently omits files, and a backup program or a file manager that uses it loses data without an error.
3. Return bytes for that value only. Every caller must then handle a list that mixes `str` and `bytes`, and most callers will not.

What a program needs is a `str` for every value, which it can display, compare and pass back to the operating system, with the guarantee that passing it back yields the original bytes.

## Specification

### The error handler

This PEP adds a codec error handler named `surrogateescape`.

When decoding, the handler replaces each byte that cannot be decoded with a single code point in the range U+DC80 to U+DCFF. The byte with value `b`, where `b` is between 0x80 and 0xFF, becomes the code point U+DC00 + `b`. The byte 0xE9 therefore becomes U+DCE9.

When encoding, the handler replaces each code point in the range U+DC80 to U+DCFF with the byte whose value is the code point minus 0xDC00. Any other code point that cannot be encoded raises an error as it does today.

Bytes below 0x80 are never replaced. [TODO: the author should confirm this restriction and say how the handler behaves with encodings where a byte below 0x80 can be part of an invalid sequence.]

### Example

On a system with a UTF-8 locale, the name `b"caf\xe9"` decodes as follows:

```python
>>> b"caf\xe9".decode("utf-8", "surrogateescape")
'caf\udce9'
>>> 'caf\udce9'.encode("utf-8", "surrogateescape")
b'caf\xe9'
```

The program receives a `str` of four characters. Encoding it with the same handler returns the original four bytes.

### Use in system interfaces

On POSIX systems, the following interfaces decode with the file system encoding and the `surrogateescape` handler:

- `os.listdir()` when given a `str` argument;
- `sys.argv`;
- `os.environ`.

Every interface that passes a `str` to the operating system as a file name, argument or environment value encodes it with the file system encoding and the same handler. As a result, `open(name)` works for every `name` returned by `os.listdir()`.

## Rationale

### Why lone surrogates

The replacement code points must meet two conditions. They must be valid elements of a Python `str`, so that ordinary string operations work. They must also be code points that a successful decode never produces, so that a decoded string cannot be confused with one that contains escaped bytes.

Code points in the range U+DC80 to U+DCFF are low surrogates. In valid Unicode text they appear only after a high surrogate, as the second half of a UTF-16 pair. A strict UTF-8 decoder does not produce them, because UTF-8 forbids encoding surrogates. A lone low surrogate in a string decoded from UTF-8 can therefore only come from this handler.

[TODO: the author should say whether this argument holds for every encoding Python supports as a file system encoding, or only for UTF-8. A codec that can decode some byte sequence to a lone low surrogate would make the mapping ambiguous for that codec. This draft does not know whether any such codec exists.]

The range has exactly 128 code points, one for each byte value from 0x80 to 0xFF, so the mapping is one-to-one.

### Alternatives for the author to evaluate

The following alternatives are suggested by this draft. They are not options recorded as considered and rejected.

- Map undecodable bytes to code points in a Private Use Area. Private use code points can appear in valid text, so a file whose name legitimately contains one could not be distinguished from an escaped byte.
- Expose bytes-only versions of every interface and leave the `str` interfaces unchanged. A program that wants correctness would then need to use bytes throughout, which is the situation the `str` interfaces were meant to avoid.
- Use a dedicated escape character followed by a hex representation. A legitimate file name could contain the escape character, so the mapping would need its own escaping.

## Consequences

A `str` returned by these interfaces may now contain lone surrogates. Such a string cannot be encoded with the default `strict` handler in any encoding, so the following call fails:

```python
>>> 'caf\udce9'.encode("utf-8")
UnicodeEncodeError: ...
```

This is a deliberate choice. A program that writes a file name to a text file or a terminal will get an error rather than silently write bytes that the reader may not interpret correctly. The cost is that a program which does this today without trouble, because all its file names happen to be valid, may fail later when it meets one that is not. The program must then choose a handler, such as `surrogateescape` to reproduce the original bytes or `replace` to show a placeholder.

The mapping is tied to the file system encoding. A string produced under one locale and encoded under another does not, in general, reproduce the original bytes. [TODO: the author should say whether this case needs to be documented as a limitation or handled.]

Strings that contain lone surrogates compare unequal to strings that decode the same bytes in a different way. Two programs that list the same directory under different locales may therefore see different names for the same file.

## Backwards compatibility

For a value whose bytes are valid in the file system encoding, the decoded `str` is the same as before, because the handler is only invoked for bytes that fail to decode.

For a value whose bytes are not valid, behavior changes from whatever Python 3 does today to returning a `str` with lone surrogates. [TODO: the author should describe the current behavior precisely, so that this section can state exactly what changes for each interface.]

Code that already uses the bytes versions of these interfaces is unaffected.
