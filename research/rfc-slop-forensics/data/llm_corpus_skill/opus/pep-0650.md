# PEP 650: Specifying installer requirements for Python projects

## Abstract

Python package installers do not fully interoperate. pip is the most widely used installer and a de facto standard, but other installers, such as Poetry and Pipenv, are also popular because they offer features suited to certain workflows that do not match how pip operates. There is no standard file for declaring a project's dependencies, so dependencies written in one tool's format can be installed only by that tool, or by exporting them to a requirements file, which can lose information. This PEP proposes a way for a project to declare which installer handles its dependencies, and a small interface through which any tool can ask that installer to install them.

## Context

A project that depends on other packages records those dependencies somewhere so that the project can be set up on a new machine. Each installer has its own place for this:

- pip reads requirements files, listed one requirement per line.
- Poetry reads its own section of `pyproject.toml` and a lock file.
- Pipenv reads a `Pipfile` and a `Pipfile.lock`.

The abundance of installers is good for users with specific needs. The problem is only that a tool which wants to support all of them cannot do so without knowing each one.

## Goals and non-goals

Goals:

1. A project declares, in one standard place, which installer installs its dependencies.
2. A tool that knows nothing about that installer can install the project's dependencies by calling a standard interface.
3. Existing installers can support the interface without changing their own file formats.

Non-goals:

- This PEP does not define a standard dependency file format. Each installer keeps its own.
- This PEP does not define a lock file format.
- This PEP does not choose a default installer or rank installers.
- This PEP does not cover building packages, only installing a project's dependencies.

## Proposal

### Declaring the installer

A project adds a table to its `pyproject.toml`:

```toml
[install-system]
requires = ["poetry"]
install-backend = "poetry.installer_api"
```

`requires` lists the packages needed to run the installer. `install-backend` names a Python module, or a module and an object separated by a colon, that implements the interface below.

### The backend interface

The backend module provides these functions:

```python
def invoke_install(path, *, dependency_group=None, **kwargs) -> int: ...
def invoke_uninstall(path, *, dependency_group=None, **kwargs) -> int: ...
def get_dependencies_to_install(path, *, dependency_group=None, **kwargs) -> list[str]: ...
```

`path` is the project's root directory. `dependency_group` names an optional subset of dependencies, such as development or test dependencies, in whatever terms the installer uses. Each install and uninstall function returns zero on success and nonzero on failure.

### The universal installer

A universal installer is any tool that reads `[install-system]`, installs the packages in `requires` into an isolated environment, imports the backend and calls `invoke_install`. It need not be a separate program; an existing installer can act as one.

### Example

A user clones a project that uses Poetry and runs a universal installer in the project directory. The universal installer:

1. Reads `[install-system]` from `pyproject.toml`.
2. Installs `poetry` into an isolated environment.
3. Imports `poetry.installer_api`.
4. Calls `invoke_install(".")`.

Poetry reads its own files and installs the dependencies. The universal installer never parses Poetry's format.

## Design decisions

### Delegate to the installer rather than standardize a format

The central tension in this proposal is between interoperability and installer diversity. A single standard dependency format would give the strongest interoperability, because any tool could read any project. It would also require every installer to express its features in that format or give them up, and the features that differ between installers are the reason users choose them.

This PEP resolves the tension by standardizing only the entry point. The installer keeps its format, and other tools reach it through a function call.

The cost is that a tool cannot read a project's dependencies without running the installer's code, which means installing the installer and trusting it. A standard format would let a tool read the dependencies statically.

This decision is expensive to reverse. Once projects declare backends and tools call them, a later standard format would have to coexist with this interface.

### Run the backend in an isolated environment

Installing the installer's own requirements into the environment being set up would mix the installer's dependencies with the project's. ## Failure behavior

If the `[install-system]` table is missing, the universal installer cannot know which installer to use. [TODO: the author should decide whether it then falls back to a default, such as reading a requirements file, or reports an error.]

If installing `requires` fails, or the backend cannot be imported, the universal installer reports the failure and makes no changes to the target environment.

If `invoke_install` returns nonzero, the universal installer reports the failure. The state of the target environment is then whatever the backend left. [TODO: the author should say whether backends must leave the environment unchanged on failure, or whether partial installs are allowed.]

## Security

Calling the backend runs code from the packages listed in `requires`. Installing a project's dependencies can already run code from those dependencies, for example when a dependency is built from source. ## Backwards compatibility

Projects that do not add `[install-system]` are unaffected. Installers that do not provide a backend continue to work as they do today, but cannot be invoked through the interface. ## Drawbacks

The interface adds a layer between the user and their installer. When an installation fails, the error passes through the universal installer, which may make it harder to find.

The proposal also does not let a tool read dependencies without executing code, which some tools, such as security scanners, need.
