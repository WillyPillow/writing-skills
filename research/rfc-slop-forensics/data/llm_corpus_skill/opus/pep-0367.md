# PEP 367: New super

## Abstract

A method that calls the same method on a base class must today name its own class and its own instance:

```python
super(Foo, self).foo(1, 2)
```

This PEP proposes syntactic sugar so that the same call is written

```python
super.foo(1, 2)
```

Inside a method, the bare name `super` produces a super object bound to two things: the class in which the method was defined, and the instance (or, for a class method, the class object) on which the method is currently acting. The current built-in `super` type is renamed `__builtin__.__super__`, and `__builtin__.super` is kept as an alias for it until it is removed in Python 3.0. Assignment to the name `super` becomes a `SyntaxError`, as assignment to `None` is.

## Motivation

The existing call repeats information the interpreter already has. Consider a typical cooperative method:

```python
class Foo(Base):
    def foo(self, a, b):
        return super(Foo, self).foo(a, b)
```

Both arguments to `super` are fixed by where the call appears. The first is always the class whose body contains the method. The second is always the method's first parameter. A programmer who writes them by hand can get them wrong in ways that do not fail immediately.

The first argument causes most of the trouble. If the class is renamed, every `super(Foo, self)` inside it must be updated. If a method body is copied from one class to another and the class name is not changed, the call still runs, but it starts the method lookup from the wrong point in the method resolution order. Depending on the hierarchy, this either skips a class or calls the same method again.

The second argument repeats the name of the first parameter. That name is `self` by convention, `cls` for class methods, and something else in a minority of code. Writing it again adds nothing.

The goal of the PEP is that a cooperative call names only the method and its arguments.

## Specification

### Semantics of `super`

Within the body of a function defined directly in a class body, the expression `super` evaluates to the same object that the call `__super__(C, first)` returns today, where

- `C` is the class object created by the enclosing class statement, and
- `first` is the current value of the function's first positional parameter.

Attribute access on that object behaves as attribute access on the result of `__super__(C, first)` does now. The call `super.foo(1, 2)` therefore looks up `foo` starting after `C` in the method resolution order of `type(first)`, or of `first` itself if `first` is a class, and calls the result with `(1, 2)`.

For a class method, the first parameter holds the class, so `super` binds to that class. For a static method there is no first parameter bound to an instance or class. ### Renaming the built-in

The existing built-in type is made available as `__builtin__.__super__`. For the rest of the 2.x series, `__builtin__.super` stays an alias for `__super__`, so the call `super(Foo, self)` continues to work.

Under the new semantics, the bare name `super` inside a method body refers to the bound super object, not to the built-in type. The two-argument call `super(Foo, self)` inside a method would therefore call the bound super object, not the type. In Python 3.0, `__builtin__.super` is removed. Code that needs the explicit form uses `__super__(Foo, self)`.

### Assignment to `super`

Assigning to `super` is a `SyntaxError`, in the same way that assigning to `None` is. This covers plain assignment, augmented assignment, use as a function parameter name, use as a target in `for` or `with` statements, and use in `import ... as super`.

The reason for this rule is that the compiler must recognize the name `super` reliably. If a local variable could be named `super`, then the expression `super.foo` inside a method would be ambiguous between that variable and the new sugar, and the compiler could not decide which code to emit.

## Rationale

### Why sugar rather than a new function

The proposal changes the meaning of a name rather than adding a function such as `super_of(self)`. A function would still need its argument, and could not discover the defining class without help from the compiler. The defining class is the error-prone argument, so a solution that leaves it out must involve the compiler.

### Why make `super` reserved

Reserving the name follows from the compiler needing to recognize it, as explained under "Assignment to `super`". The cost is that any existing code that binds `super`, such as a parameter named `super`, stops compiling. ## Backwards compatibility

The following existing code is affected:

1. Code that binds the name `super`. It becomes a `SyntaxError`.
2. Code that calls `super(Foo, self)` inside a method. It must keep working through Python 2.x; the mechanism is the open question noted under "Renaming the built-in".
3. Code that calls the built-in `super` outside a method body, for example in a helper function. It continues to work in 2.x through the alias, and must change to `__super__` in 3.0.
4. Code that passes the built-in as a value, for example `f = super`. Inside a method body, `f` would now hold a bound super object rather than the type.

## Drawbacks

The proposal gives one name two meanings: a type at module level during the transition, and a bound object inside a method body. A reader must know where the name appears to know what it means.

It also makes the meaning of a function's body depend on where the function was defined. Moving a function from a class body to module level changes what `super` means, even though the source text of the function is unchanged.

Finally, reserving a name that is currently an ordinary built-in sets a precedent. Today only `None` has this treatment.
