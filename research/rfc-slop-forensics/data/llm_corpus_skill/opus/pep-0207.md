# PEP 207: Rich comparisons

## Abstract

Python classes and C extension types can currently customize comparison through a single hook, `__cmp__`, which returns a negative number, zero or a positive number. This PEP proposes two changes. First, each of the six operators `<`, `>`, `<=`, `>=`, `==` and `!=` can be overloaded separately. Second, an overloaded operator may return any object, not only a Boolean.

## Motivation

The current hook forces every comparison through one three-way answer. Two kinds of type do not fit that model.

The first kind has an ordering that is not total. For such a type, `a < b` and `b < a` can both be false while `a == b` is also false. Sets ordered by inclusion are one example: `{1}` is neither a subset nor a superset of `{2}`. Floating-point NaN is another: it is unequal to everything, including itself. A three-way result has no value for "unordered", so `__cmp__` cannot express either case. The second kind wants comparisons to return something other than true or false. A numeric array package, for example, would like `a < b` on two arrays to compare them element by element and return an array of results. With `__cmp__`, the result is reduced to a single integer before the user sees it, so the element-wise answer is lost. There is also a smaller case: some types can test equality cheaply but cannot order their values at all. Today such a type must either invent an arbitrary ordering in `__cmp__` or raise an exception, which breaks `==` along with `<`. With separate operators, the type defines `__eq__` and `__ne__` and leaves the ordering operators undefined.

The goal of this PEP is that each comparison operator has its own hook, and that the hook's result reaches the user unchanged.

## Specification

### Python classes

A class may define any of the following methods:

| Operator | Method | Reflected method |
|---|---|---|
| `a < b` | `__lt__` | `__gt__` |
| `a <= b` | `__le__` | `__ge__` |
| `a > b` | `__gt__` | `__lt__` |
| `a >= b` | `__ge__` | `__le__` |
| `a == b` | `__eq__` | `__eq__` |
| `a != b` | `__ne__` | `__ne__` |

Each method takes `self` and the other operand and may return any object. A method that does not support the given operand returns the singleton `NotImplemented`.

The reflected method column drives how the interpreter tries the right operand. To evaluate `a < b`, the interpreter does the following:

1. Call `a.__lt__(b)`. If the result is not `NotImplemented`, use it.
2. Otherwise call `b.__gt__(a)`, the reflected operation. If the result is not `NotImplemented`, use it.
3. Otherwise fall back to `__cmp__`, as today.

Reflection swaps `<` with `>` and `<=` with `>=`, because `a < b` is the same question as `b > a`. It does not swap `<` with `>=`, because that would assume a total order, which is exactly what this PEP does not assume. For the same reason, the interpreter never derives `__ne__` from `__eq__`, or `__le__` from `__lt__` and `__eq__`. [TODO: confirm with the author. Deriving `!=` from `==` when only `__eq__` is defined would be convenient for most classes; the author should state whether the convenience was weighed against the cost for types like arrays, where `not (a == b)` is not meaningful.]

Step 3 keeps existing classes working. A class that defines only `__cmp__` behaves as it does now.

### C extension types

Type objects gain a new slot, `tp_richcompare`, with the signature:

```c
PyObject *tp_richcompare(PyObject *a, PyObject *b, int op);
```

`op` is one of six constants, `Py_LT`, `Py_LE`, `Py_EQ`, `Py_NE`, `Py_GT` and `Py_GE`. The function returns a new reference to any object, or `Py_NotImplemented`, or `NULL` with an exception set.

A single slot with an operator argument, instead of six slots, keeps the type object small and lets an implementation share most of its code across the six operators. [TODO: confirm this is the reason; the author should state whether six separate slots were considered.]

A type advertises the slot with a flag in `tp_flags`. [TODO: specify the flag name and how the interpreter treats types compiled against older headers that do not have the slot.]

### C API

The existing `PyObject_Compare` keeps its meaning. A new function, `PyObject_RichCompare(a, b, op)`, applies the lookup order above and returns the resulting object. A second function, `PyObject_RichCompareBool(a, b, op)`, returns an int: 1 if the result is true, 0 if false, -1 on error. It is the function to call when C code needs a truth value.

### Chained comparisons

A chained comparison such as `a < b < c` currently means `a < b and b < c`, with `b` evaluated once. That meaning is unchanged. With rich comparisons, the `and` calls the truth value of the result of `a < b`. For a type whose comparisons return arrays, that truth value may be ambiguous, and such a type can raise an exception from its truth test. This PEP does not change `and` to combine non-Boolean results. [TODO: confirm. An element-wise chained comparison would need a different rule for `and`, which is outside this PEP.]

### Built-in uses of comparison

Some built-in operations compare objects internally: sorting, `in` on lists, `min` and `max`, dictionary lookup. These need a truth value, not an arbitrary object. They call the rich comparison, then take the truth value of the result. [TODO: list which operator each built-in uses, for example whether `list.sort` uses only `<` and whether `in` uses `==`. ## Compatibility

Classes and types that define only `__cmp__` keep their behavior through the fallback in step 3. Code that compares objects of such classes sees no change.

Code that calls a comparison and assumes the result is `True`, `False`, `0` or `1` can break when given an object of a type whose comparisons return other values. This is the intended effect for types that opt in. It only reaches code that receives those types. [TODO: identify any standard library code that relies on comparison results being integers.]

## Drawbacks

A class that wants a full ordering now needs to define up to six methods instead of one. Many classes have a total order, and for them the extra methods are repetition. [TODO: decide whether the PEP should offer a helper for this case, or leave it to a later proposal.]

Allowing comparisons to return arbitrary objects means a reader can no longer assume `a < b` is a Boolean. Code that reasons about comparisons, such as sorting, has to call the truth test explicitly.
