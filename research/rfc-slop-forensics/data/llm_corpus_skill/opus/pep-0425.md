# PEP 425: Compatibility tags for built distributions

## Abstract

This PEP specifies three tags that say which Python installations a built or binary distribution can be installed on. The Python tag names the implementation and language version. The ABI tag names the binary interface the distribution's compiled code expects. The platform tag names the operating system and architecture. The tags are short because they appear in distribution filenames.

## Motivation

A source distribution can be built for whatever Python installs it. A built distribution cannot. It may contain compiled extension modules that only load into one interpreter, of one version, built one way, on one operating system and architecture. Installing it anywhere else produces an import error at best and a crash at worst.

An installer that downloads a built distribution therefore needs to know, before downloading or installing it, whether it will work. Today nothing in the distribution's name states this in a form installers agree on. ## The tags

### Python tag

The Python tag names the implementation and the language version the distribution needs. It is an abbreviation of the implementation followed by the version digits:

| Implementation | Abbreviation |
|---|---|
| Any implementation | `py` |
| CPython | `cp` |
| PyPy | `pp` |
| IronPython | `ip` |
| Jython | `jy` |

`cp33` means CPython 3.3. `py2` means any Python 2 implementation. `py27` means any implementation of Python 2.7.

A pure-Python distribution that uses only the language uses the generic `py` prefix. A distribution with compiled code for CPython uses `cp`. [TODO: specify how a new implementation obtains an abbreviation, and who maintains the list.]

### ABI tag

The ABI tag names the binary interface that compiled code in the distribution was built against. Two CPython builds of the same version can have different ABIs. A build with debugging enabled, or with a different Unicode representation, lays out objects differently, and an extension compiled for one may crash in the other.

### Platform tag

The platform tag is the result of `distutils.util.get_platform()` with every hyphen and period replaced by an underscore. For example, `linux-x86_64` becomes `linux_x86_64`, and `win-amd64` becomes `win_amd64`. A distribution that runs on every platform uses `any`.

Reusing an existing function means the tag matches what build tools already compute, so no new platform naming scheme is introduced. [TODO: confirm that `get_platform()` gives enough detail on Linux. ## Use in filenames

A built distribution's filename ends with the three tags, separated by hyphens, in the order Python, ABI, platform:

```text
example-1.0-cp33-cp33m-linux_x86_64.whl
example-1.0-py2-none-any.whl
```

The first is a distribution with an extension module for CPython 3.3, built with `pymalloc`, for 64-bit Linux. The second is pure Python 2 code that runs anywhere.

The filename format of each built distribution type, such as wheel, is defined in that format's own specification. This PEP defines only the tags.

### Compressed tag sets

A distribution that supports several values of one tag lists them separated by periods:

```text
example-1.0-py2.py3-none-any.whl
```

This file claims compatibility with any Python 2 and any Python 3. The installer expands the set into every combination of the listed values: `py2-none-any` and `py3-none-any`.

The period is chosen because hyphens and underscores already have meanings in the filename. [TODO: confirm that no tag value can contain a period, which is what makes this unambiguous.]

## Choosing a distribution

An installer computes the list of tags the running interpreter supports and orders it from most to least preferred. It then picks the available distribution whose tags appear earliest in that list.

The ordering is the part of this specification installers are most likely to get wrong, and it decides which file a user ends up with. For a CPython 3.3 interpreter on 64-bit Linux, the list begins:

1. `cp33-cp33m-linux_x86_64`
2. `cp33-abi3-linux_x86_64` [TODO: only if a stable-ABI tag is adopted]
3. `cp33-none-linux_x86_64`
4. `cp3-none-linux_x86_64`
5. `cp32-none-linux_x86_64`, and so on through earlier versions
6. `py33-none-any`
7. `py3-none-any`
8. `py32-none-any`, and so on

The ordering prefers a build that matches the interpreter exactly, because it is most likely to be fast and correct. It falls back to more general builds, and finally to pure Python. ### A worked selection

Suppose a project publishes three files for one release:

```text
example-1.0-cp33-cp33m-linux_x86_64.whl
example-1.0-cp33-cp33m-win_amd64.whl
example-1.0-py2.py3-none-any.whl
```

A CPython 3.3 interpreter on 64-bit Linux built with `pymalloc` finds `cp33-cp33m-linux_x86_64` first in its list and installs the first file. The same interpreter version on Windows installs the second. A PyPy interpreter matches neither compiled file, because its Python tag starts with `pp`. It expands the third file's set to `py2-none-any` and `py3-none-any`, finds `py3-none-any` in its list and installs the pure-Python file.

A CPython 3.3 debug build on Linux has a different ABI tag. It skips the first file and also falls back to the pure-Python one. That is the outcome the ABI tag exists to produce: without it, the debug build would load an extension compiled for a different object layout. [TODO: confirm the debug build's ABI tag letter.]

## Why the tags are terse

Filenames have practical length limits on some filesystems and tools, and a distribution filename already contains a project name and version. [TODO: give the specific limit that drove this, if there is one.] Short tags also make the filename readable to a person deciding which file to download.

The cost of terseness is that the tags must be decoded. A user who sees `cp33m` must know that `m` means a `pymalloc` build. Installers do this decoding, and the specification is the reference for users who need it.

## Compatibility

The tags are new, so no existing filename changes meaning. Existing binary formats that use other naming schemes are not affected. Once a format adopts these tags, its filename format is effectively permanent: installers in the field will parse files by these rules, and changing the tags later would make older installers reject or mis-select new files. This is the decision in this PEP that is most expensive to reverse.
