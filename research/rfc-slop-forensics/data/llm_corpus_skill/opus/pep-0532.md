# PEP 532: A circuit breaking protocol and binary operators

## Abstract

Python has three expression forms that decide whether to evaluate an operand at all: the conditional expression `LHS if COND else RHS`, logical conjunction `LHS and RHS`, and logical disjunction `LHS or RHS`. Each one hard-codes its decision as a call to `bool()` and gives the operand's type no further say in the result. This PEP proposes a circuit breaking protocol, made of two new special methods named `__then__` and `__else__`, that lets the type of the deciding operand choose the value an expression produces when evaluation stops early.

The protocol is meant to be a shared semantic basis for the existing forms above, for the None-aware operators proposed in PEP 505, and for the rich comparison chaining model proposed in PEP 535. Using the protocol, this PEP further proposes that `if` and `else` become usable as binary short-circuiting operators on their own:

- `LHS if RHS`, which is right-associative and evaluates `RHS` first;
- `LHS else RHS`, which is left-associative and evaluates `LHS` first.

The PEP also proposes a change to logical inversion (`not EXPR`) so that it stays consistent with the new protocol.

## Motivation

This PEP draws on PEP 335, PEP 505, PEP 531 and the discussions around them. Each of those proposals wants an expression that stops evaluating early under a condition other than plain truth. PEP 505 wants to stop when a value is not `None`. PEP 535 wants a chained comparison such as `a < b < c` to behave sensibly when the comparisons return arrays or other non-boolean objects.

## Specification

### The circuit breaker protocol

A circuit breaker is any object whose type defines `__bool__` together with `__then__`, `__else__` or both. Both methods take only `self`:

- `type(obj).__then__(obj)` gives the value of a short-circuited expression when `bool(obj)` is true.
- `type(obj).__else__(obj)` gives the value of a short-circuited expression when `bool(obj)` is false.

If a type does not define one of these methods, the interpreter behaves as if the method returned `obj` unchanged. Ordinary objects therefore keep their current behavior.

### The binary `else` operator

The expression `LHS else RHS` is evaluated as follows:

1. Evaluate `LHS` and call the result `_lhs`.
2. If `bool(_lhs)` is true, the value of the expression is `type(_lhs).__then__(_lhs)`, and `RHS` is not evaluated.
3. Otherwise, evaluate `RHS`. Its value is the value of the expression.

With the default method, `LHS else RHS` gives the same result as `LHS or RHS`.

### The binary `if` operator

The expression `LHS if RHS` is evaluated as follows:

1. Evaluate `RHS` and call the result `_rhs`.
2. If `bool(_rhs)` is false, the value of the expression is `type(_rhs).__else__(_rhs)`, and `LHS` is not evaluated.
3. Otherwise, evaluate `LHS`. Its value is the value of the expression.

With the default method, `LHS if RHS` gives the same result as `RHS and LHS`. The right operand is evaluated first, which matches the order in the existing conditional expression, where the condition is evaluated before either branch.

### Logical conjunction and disjunction

Under this proposal, `a or b` is defined as `a else b`, and `a and b` is defined as `b if a`. For every type that defines neither new method, these definitions reduce to the current behavior. For a type that defines them, `and` and `or` now consult the type.

### The conditional expression

The ternary form `A if C else B` cannot be read as `(A if C) else B` under the rules above. A counterexample uses only built-in values: with `A = 0`, `C = True` and `B = 1`, the current expression gives `0`. The binary reading first gives `0 if True`, which is `0`, and then gives `0 else 1`, which is `1` because `0` is false.

### Precedence and associativity

`LHS if RHS` is right-associative, so `a if b if c` groups as `a if (b if c)`. `LHS else RHS` is left-associative, so `a else b else c` groups as `(a else b) else c`. ## Example: None-aware operations

The protocol can express the main PEP 505 case without dedicated syntax. Consider a circuit breaker type, here called `exists`, that wraps a value:

```python
class exists:
    def __init__(self, value):
        self.value = value
    def __bool__(self):
        return self.value is not None
    def __then__(self):
        return self.value
    def __else__(self):
        return self.value
```

With this type, `exists(config.timeout) else 30` evaluates `config.timeout` once. If the value is not `None`, the expression gives that value and does not evaluate `30`. If the value is `None`, it gives `30`. Unlike `config.timeout or 30`, it keeps a configured timeout of `0`, because `0` is not `None`.

The guard form uses the binary `if`. The expression `user.name if exists(user)` gives `user.name` when `user` is not `None`. When `user` is `None`, it gives `None` and does not evaluate `user.name`.

## Rationale

The protocol has two methods, not one, because the two short-circuit outcomes are different results. For `else`, the early result comes from a true left operand; for `if`, it comes from a false right operand. A single method would need a flag argument saying which branch was taken.

## Backwards compatibility

The binary forms `LHS if RHS` and `LHS else RHS` are currently syntax errors, so adding them changes the meaning of no valid program.

If `and` and `or` are redefined through the protocol, existing programs keep their behavior for every type that does not define `__then__` or `__else__`. The names `__then__` and `__else__` are reserved for the language by Python's convention on dunder names, but a third-party type could already define them. ## Performance

The current `and`, `or` and conditional expression call `bool()` on one operand. Under this proposal, a short-circuited `and`, `or` or binary operator must also look up an optional method on the operand's type. ## Drawbacks

The proposal gives `if` and `else` a second meaning. A reader who sees `x else y` must know that it is not part of a ternary expression, and `x if y` reads in English as a condition rather than as an operator whose value may be `y`.

Redefining `and` and `or` means that a library type can change what these keywords return. Code that today assumes `a or b` gives either `a` or `b` would no longer hold for such types.

## Open questions

The central question is whether one protocol should carry all the cases listed in the abstract, or whether PEP 505 and PEP 535 should keep separate, narrower mechanisms. The protocol's benefit is that new short-circuiting behavior needs no new syntax. Its cost is that every short-circuit expression in the language becomes overridable.

Other open questions are marked inline: the ternary expansion, the change to `not`, operator precedence, the PEP 535 expansion, and whether a None-aware helper type is added.
