## Abstract

This proposal defines a hierarchy of Abstract Base Classes (ABCs), as introduced by PEP 3119, to represent number-like classes. The hierarchy is

    Number :> Complex :> Real :> Rational :> Integral

where `A :> B` means "A is a supertype of B". The hierarchy is inspired by Scheme's numeric tower [#schemetower]_.

## Motivation

A function that accepts numbers today has no standard way to ask what kind of number it was given. It can test `isinstance(x, (int, float))`, which rejects numeric types defined outside the core, or it can try an operation and catch the failure, which does not tell it whether, for example, `x` has an exact numerator and denominator. PEP 3119 provides the mechanism for answering such questions with ABCs and `isinstance`. This PEP supplies the ABCs for numbers.

The ABCs are useful only if they mirror distinctions that already matter to code. The mathematical chain from integers to rationals to reals to complex numbers is such a distinction: each level supports operations that the level above does not guarantee. Ordering is defined on the reals but not on the complex numbers, and a numerator is defined on the rationals but not on all reals. The hierarchy in this PEP follows that chain.

## The hierarchy

Each ABC below states what an object must support to register as that ABC. The method sets are a proposal for the author to confirm. [TODO: confirm or revise each list.]

`Number` is the root. It requires no operations. Its role is to let code ask "is this a number at all?" without committing to any particular structure. A type that is numeric but fits none of the lower levels can register here alone.

`Complex` requires the arithmetic operations `+`, `-`, `*`, `/` and `**`, unary `-` and `+`, `abs()`, equality, the attributes `real` and `imag`, the method `conjugate()`, and conversion with `complex()`. It does not require ordering, because the complex numbers have no ordering compatible with arithmetic.

`Real` adds what holds for real numbers and not for complex ones: the ordering comparisons `<`, `<=`, `>` and `>=`; conversion with `float()`; `math.floor`, `math.ceil` and `round`; and `//`, `%` and `divmod`. For a `Real`, `real` returns the value itself and `imag` returns 0, so that a `Real` is also a valid `Complex`.

`Rational` adds the attributes `numerator` and `denominator`. Given these, a default `float()` can be defined as the quotient of the two.

`Integral` adds conversion with `int()`, use as a sequence index, and the bitwise operations `<<`, `>>`, `&`, `^`, `|` and `~`. For an `Integral`, `numerator` returns the value itself and `denominator` returns 1.

The following example shows the intended use:

```python
from numbers import Real

def clamp(x, lo, hi):
    if not isinstance(x, Real):
        raise TypeError("clamp() requires a real number")
    return max(lo, min(x, hi))
```

`clamp` needs ordering, so `Real` is the weakest ABC it can require. A third-party decimal or fixed-point type that registers as `Real` passes the check without `clamp` naming it.

## Registration of the built-in types

The PEP proposes to register the built-in types as follows: `complex` as `Complex`, `float` as `Real`, and `int` as `Integral`. [TODO: list every built-in and standard-library numeric type the PEP registers, including `bool` and `decimal.Decimal`, with the ABC for each.]

Registering `float` as `Real` is the decision most open to dispute. A float is a finite binary approximation. It does not satisfy all the laws of real arithmetic: addition is not associative, and `float('nan')` is not equal to itself. ## Arithmetic between different implementations

The hardest problem in this design is mixed-type arithmetic. When `a + b` involves two different implementations of the same ABC, for example a user-defined `Rational` and the built-in `int`, Python calls `a.__add__(b)` and then, if that returns `NotImplemented`, `b.__radd__(a)`. The ABCs say what each type supports, but not who is responsible for the result when the two types differ.

A suggested rule for the author to evaluate is the following:

1. An implementation's `__add__` handles operands of types it knows and returns `NotImplemented` for others.
2. Its `__radd__` handles operands of types it knows. For an operand it does not know but that is an instance of a known ABC, it converts both operands to the corresponding built-in type (`int`, `float` or `complex`) and computes with that.
3. If neither condition holds, it returns `NotImplemented`.

Under this rule, two independent third-party `Rational` types can still be added, at the cost of falling back to `float` and losing exactness. ## What the hierarchy does not cover

The following are deliberate exclusions, stated so that readers do not expect them:

1. Algebraic structures other than the numeric chain, such as groups, rings or fields. [TODO: confirm, and give the reason, for example that no standard-library code would use them.]
2. Types such as vectors, matrices and intervals, which support some arithmetic but are not in the chain.
3. A promise of exact results. `Real` and `Complex` do not say whether arithmetic is exact or rounded (see the previous section on `float`).

## Backwards compatibility

The PEP adds a module of ABCs and registers existing types with them. It does not change how the existing numeric types compute. Code that does not import the new module sees new superclasses on the built-in types, through `isinstance` and `issubclass`, and nothing else.
