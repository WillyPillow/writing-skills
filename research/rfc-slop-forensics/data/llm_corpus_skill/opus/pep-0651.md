## Abstract

This PEP proposes that Python treat machine stack overflow differently from runaway recursion. Programs could then set the maximum recursion depth to fit their needs, and the interpreter would give additional safety guarantees.

If this PEP is accepted, the following program will run safely to completion:

```python
sys.setrecursionlimit(1_000_000)

def f(n):
    if n:
        f(n-1)

f(500_000)
```

and the following program will raise a `StackOverflow` exception, without crashing the VM:

```python
sys.setrecursionlimit(1_000_000)

class X:
    def __add__(self, other):
        return self + other

X() + 1
```

## Motivation

CPython has one limit, the recursion limit, that guards two different resources.

The first resource is the logical depth of Python calls. A program that recurses without end, by mistake, should get an exception it can catch and report, rather than run until memory is exhausted. The recursion limit serves that purpose well.

The second resource is the machine stack, which the C code of the interpreter uses. Each nested call that goes through C code takes some amount of machine stack. If the machine stack is exhausted, the process crashes, typically with a segmentation fault, and no Python exception can be raised. The recursion limit protects the machine stack only indirectly: it caps the number of nested calls, and the default is chosen low enough that the stack does not run out on typical platforms. [TODO: the current default limit, and the platforms and stack sizes it was chosen for, if the author has them.]

Because one number serves both purposes, a program cannot set it correctly for both. A program that recurses deeply on purpose, such as a parser for deeply nested input or a recursive tree walk, needs a high limit. A high limit removes the protection for the machine stack, and the program can then crash. The first example in the Abstract shows this case. Today, `sys.setrecursionlimit(1_000_000)` followed by `f(500_000)` can crash the interpreter. [TODO: confirm that the first example crashes on a current CPython build, and on which platforms.]

The second example shows recursion that goes through C. The expression `self + other` calls the `nb_add` slot of `X`, which calls `X.__add__`, which evaluates `self + other` again. Each level passes through C code, so each level uses machine stack. With a recursion limit of one million, the machine stack runs out long before the limit is reached, and the interpreter crashes. ## Proposal

The PEP separates the two limits:

1. The recursion limit, set with `sys.setrecursionlimit`, bounds the depth of Python calls. Exceeding it raises `RecursionError`, as today.
2. A separate check bounds the use of the machine stack. Exceeding it raises a new exception, `StackOverflow`.

With the two limits separate, a program can raise the recursion limit as high as it needs, and the interpreter still protects the machine stack.

### Python-to-Python calls

For the first example to run to completion, a call from Python code to a Python function must not use machine stack in proportion to the depth of recursion. Otherwise 500,000 nested calls of `f` would still exhaust the machine stack, however the check is done. The PEP therefore requires that the interpreter execute such calls without a nested call to the C evaluation function. [TODO: confirm that this is part of the proposal and not an existing property of the interpreter, and describe the mechanism, for example by having the evaluation loop push a new frame and continue in the same C call.]

Calls that go through C, such as calls through type slots like `nb_add`, calls to built-in functions that call back into Python, and calls from C extensions, still use machine stack at each level. These are the calls that the machine-stack check protects. The second example is such a case.

## Safety guarantees

The abstract promises "additional safety guarantees". The guarantee this draft can state is the following: a pure Python program cannot crash the VM by exhausting the machine stack, whatever recursion limit it sets. Exhaustion is reported as `StackOverflow` instead.

## Backwards compatibility

Code that catches `RecursionError` to handle deep recursion is affected by the place of `StackOverflow` in the hierarchy (see above).

Programs that today crash may instead raise `StackOverflow`. Programs that today raise `RecursionError` at the default limit continue to do so. [TODO: confirm that the default recursion limit is unchanged.]
