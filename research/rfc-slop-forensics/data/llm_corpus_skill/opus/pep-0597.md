# PEP 597: Add optional EncodingWarning

## Abstract

This PEP adds a warning category, `EncodingWarning`. Python emits it when `open()` is called without an `encoding` argument, so that the locale's default encoding is used. The warning is off by default. A new command-line option, `-X warn_default_encoding`, and a new environment variable, `PYTHONWARNDEFAULTENCODING`, turn it on. The PEP also adds `"locale"` as a value for `encoding`, which asks for the locale encoding explicitly and does not trigger the warning.

## Motivation

When `open()` is called in text mode without an `encoding`, it uses the locale's preferred encoding. That encoding differs between systems. On most Linux and macOS systems it is UTF-8. On Windows it is usually a legacy code page. [TODO: confirm the default on each platform for the Python version this PEP targets, and whether UTF-8 mode changes it.]

Code that omits `encoding` therefore behaves differently depending on where it runs. A developer on Linux writes and reads a file containing non-ASCII text, and everything works. A user on Windows runs the same code and gets a `UnicodeDecodeError`, or silently gets the wrong characters. The developer never sees the bug, because their locale hides it.

```python
with open("names.txt") as f:      # no encoding
    names = f.read()               # fails on Windows if the file is UTF-8
```

The usual fix is to pass `encoding="utf-8"`. Developers forget it, and no tool tells them. Linters can flag a missing argument, but they cannot follow a file path through a library that passes `encoding=None` along to `open()`. The goal is to give developers a way to find every place their program opens a file with the locale encoding, at runtime, including through libraries.

## Specification

### `EncodingWarning`

`EncodingWarning` is a new subclass of `Warning`. Python emits it when `encoding` is omitted or `None` in:

1. `open()` and `io.open()` in text mode,
2. `io.TextIOWrapper`,
3. [TODO: list the other standard library functions that open text files with the default encoding and should emit the warning, for example in `pathlib`, `subprocess` with `text=True`, and `tempfile`.]

The warning message names the function and suggests passing `encoding`.

### Enabling the warning

The warning is emitted only when one of these is set:

1. the command-line option `-X warn_default_encoding`,
2. the environment variable `PYTHONWARNDEFAULTENCODING` set to a non-empty string.

The flag is available to Python code as `sys.flags.warn_default_encoding`.

When the flag is not set, Python does not emit the warning at all. This is different from emitting it and filtering it out. The reason is cost: checking a flag is cheaper than creating a warning and running it through the filters on every `open()` call. [TODO: confirm with the author, and give a measurement if one exists.]

### The `"locale"` encoding

`encoding="locale"` tells `open()` and `TextIOWrapper` to use the locale encoding, which is what omitting the argument does today. It does not emit the warning.

This value exists for code that really wants the locale encoding, for example a program that reads a file the user wrote in a text editor on the same machine. Without it, such code would have to call `locale.getpreferredencoding(False)` and pass the result, which is longer and computes the encoding at a different time than `open()` would. With `"locale"`, the code states its intent and the warning stays meaningful for the cases that are mistakes.

### Helper for wrapper functions

A library function that takes an `encoding` argument and passes it to `open()` has a problem. If its caller omits the encoding, the library passes `None`, and the warning points at the library's `open()` call. The library author cannot fix that line, because the omission is in the caller.

This PEP proposes a helper, `io.text_encoding(encoding, stacklevel=2)`. It returns `encoding` unchanged if it is not `None`. If it is `None`, it emits `EncodingWarning` pointing at the caller's frame, at the given stack level, and returns `"locale"`. A wrapper calls it once at the top:

```python
def read_config(path, encoding=None):
    encoding = io.text_encoding(encoding)
    with open(path, encoding=encoding) as f:
        ...
```

Now the warning names the line that called `read_config` without an encoding, which is where the fix belongs. [TODO: the abstract does not mention this helper. The author should confirm it is part of this PEP or move it to an open question.]

## How a developer uses it

A developer who wants to find missing `encoding` arguments in their project does the following:

1. Run the test suite with `PYTHONWARNDEFAULTENCODING=1` set, or with `python -X warn_default_encoding`.
2. Add `-W error::EncodingWarning` to turn each warning into an exception, so that each one fails a test with a traceback.
3. For each failure in the project's own code, add `encoding="utf-8"` if the file's encoding is fixed, or `encoding="locale"` if the file comes from the user's environment.
4. For each failure inside a dependency, report it to that project, or check whether the project's wrapper accepts an `encoding` argument that the developer's code omitted.

Step 4 is where the helper in the previous section matters. Without it, every warning from a wrapper looks like a bug in the dependency, even when the missing argument is in the developer's call.

## Rationale

### Why off by default

The warning is for developers checking their own code. Most users of a Python program did not write it and cannot act on a warning about it. Turning the warning on for everyone would show them messages about library code they do not control. [TODO: confirm. The author should also state whether a later Python version is expected to enable the warning by default, or to change the default encoding instead.]

### Why a separate category

A new category lets developers filter these warnings independently of `DeprecationWarning` and others, with `-W error::EncodingWarning` in a test run, for example. It also leaves room to change the default encoding later without the warning meaning "this is deprecated" today. [TODO: author to confirm this reason.]

## Compatibility

When the flag is off, nothing changes. When it is on, the only new behavior is the warning.

`encoding="locale"` is a new value. On Python versions without this PEP, passing it raises `LookupError`, because no codec has that name. Code that must run on older versions cannot use it directly. [TODO: recommend a pattern for such code, such as checking `sys.flags` or the Python version.]

A third-party codec registered under the name `"locale"` would be shadowed. [TODO: check whether any such codec exists.]

## Drawbacks

An opt-in warning reaches only developers who turn it on. Developers who most need it, those who have never thought about encodings, are least likely to know the option exists. The PEP accepts this, because the alternative is warning every user about code they did not write.

Libraries must adopt `io.text_encoding` before their users get accurate warning locations. Until then, warnings point into library code.
