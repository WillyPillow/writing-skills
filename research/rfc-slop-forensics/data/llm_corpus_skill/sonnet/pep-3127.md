# PEP 3127: Integer Literal Support and Syntax

## Abstract

This PEP proposes changes to the Python core to rationalize the treatment of string literal representations of integers in different radices (bases). The changes target Python 3.0. The backward-compatible parts should also go into Python 2.6, so that every valid 3.0 integer literal is also valid in 2.6. The proposal has three parts:

a) Octal literals must be written with a leading `0o` or `0O` instead of `0`.
b) Binary literals are supported, with a leading `0b` or `0B`.
c) Binary numbers are supported in string formatting.

## Motivation

A Python integer literal can be written in decimal, octal or hexadecimal. Hexadecimal literals start with `0x`. Octal literals start with a plain `0`. Decimal literals must not start with `0` unless the value is zero.

The octal rule is the source of the trouble. A leading zero is the only marker, and it is also what a person writes to pad a decimal number to a fixed width. The following lines show the effect.

```python
a = 123      # decimal, value 123
b = 0123     # octal, value 83
c = 0o123    # the proposed spelling of b
```

A programmer who writes `0123` to line up a column of numbers gets 83, and the interpreter does not complain. A programmer who writes `09` gets a syntax error, because `9` is not an octal digit, and the message does not explain the reason to a person who thought the number was decimal. The same notation pattern, a zero followed by a letter, already marks hexadecimal with `0x`. The proposal extends this pattern to octal with `0o` and to binary with `0b`, so that all three non-decimal radices are marked by a prefix of the same shape. A reader who sees `0o755` sees at once that the literal is octal. The usual use of octal in programs is file permission modes, and the reader of `0755` in that context may or may not know the convention. Binary literals are a separate addition. Programs that work with bit masks and hardware flags write values like `0b1010`, and today they must convert by hand to hexadecimal or decimal and put the binary form in a comment. ## Specification

The PEP changes three things.

### Octal literals

A literal that starts with `0o` or `0O`, followed by one or more octal digits, is an octal integer. The value of `0o755` is the number written 755 in base eight, which is 493 in decimal. The leading `0` form for octal literals is no longer valid in 3.0. ## Compatibility and the 2.6 plan

The abstract divides the changes into those that are backward compatible and those that are not. The `0o` and `0b` prefixes are new syntax that was invalid before, so accepting them in 2.6 breaks no valid program. Removing the leading-zero octal form breaks programs that use it, so that part can only happen in 3.0.

The plan gives every valid 3.0 integer literal a valid spelling in 2.6. This allows a program to move to the 3.0 forms while still running on 2.6, in preparation for the later move. The two versions then overlap on the new syntax.

## Rationale

The single claim in the abstract is that the treatment should be rationalized, and the examples above show what that means: one prefix pattern for the three non-decimal radices, and no radix that depends on the absence of a marker.

The decision to remove the old form cannot be reversed easily. After 3.0 is released, restoring the old form would give two spellings with the same value, which affects every reader. The decision to add `0b` is easier to defend, since it adds a form and removes none.

## Alternatives

The following are suggestions for the author to evaluate, and the draft does not claim that the author considered them.

- Leave octal as it is and add only the binary literal. This avoids the compatibility cost. It keeps the confusing case.
- Require a different marker for octal, such as a trailing letter. This avoids a leading-zero issue and breaks the parallel with `0x`.
- Keep the old form and add a warning in 3.0 instead of an error. This eases the transition. It leaves two spellings in the language.
