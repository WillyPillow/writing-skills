# PEP 327: Decimal Data Type

## Abstract

This PEP proposes a Decimal data type for every use where decimals are needed but binary floating point is too inexact. The type supports the standard Python functions and operations and must comply with the decimal arithmetic ANSI standard X3.274-1996.

Decimal is floating point, not fixed point, and its precision is bounded. Precision is the upper limit on the number of significant digits in a result. The user can set the precision. The type also keeps a notion of significant trailing zeroes, so that fixed-point usage is possible.

The work is based on code and test functions by Eric Price, Aahz and Tim Peters. Shortly before Python 2.4a1, the `decimal.py` reference implementation moved into the standard library. [TODO: the supplied abstract ends mid-sentence ("along with the ..."). State what moved with it.]

## The problem

### An example

Binary floating point stores most decimal fractions approximately. The number 0.1 has no exact binary representation, so a program that adds 0.1 ten times gets a value that differs from 1.0 by a small amount. A program that compares the sum to 1.0 gets the wrong answer.

The difference is small, but it matters wherever people expect decimal arithmetic to behave like arithmetic done by hand. Money is the usual case. ## Design

### Floating point, not fixed point

The central decision in the abstract is that Decimal is floating point and not fixed point. A fixed-point type has a fixed number of digits after the decimal point. A floating-point type keeps a count of significant digits and moves the point. The abstract states the choice and then adds the means to recover fixed-point behavior: a user-settable precision and the notion of significant trailing zeroes.

This is the hardest problem in the design, because the two models serve different users and the PEP wants to serve both with one type. [TODO: author to explain why one type was chosen over two. The material does not give a reason, and a reviewer will ask why fixed-point users do not get their own type.]

### Bounded precision

Precision is the maximum number of significant digits in a result. An operation whose exact result has more digits than the precision is rounded. [TODO: author to specify the rounding modes, the default precision, and where the precision setting lives, for example per thread, per context or global.]

A bounded precision gives predictable cost, because the number of digits cannot grow without limit. It also means that results are not always exact. [TODO: author to say which operations are exact and which round, and to state how the user is told that rounding happened.]

### Significant trailing zeroes

The type distinguishes values that are numerically equal but carry different numbers of trailing zeroes, such as 1.5 and 1.50. This notion is what allows fixed-point usage: a user can keep two digits after the point by keeping the zeroes. ## Rationale

**The force.** Binary floating point cannot represent most decimal fractions exactly. Programs that need decimal results cannot get them with the built-in float. [TODO: author to give a concrete case from users or from the mailing list.]

**Cost accepted.** The standard library gains a type with its own context, rounding and special-value rules. Users must learn them. **Reversibility.** The behavior of equality, hashing and string output becomes public as soon as people store Decimal values. These decisions are the most expensive to change and need the most justification.
