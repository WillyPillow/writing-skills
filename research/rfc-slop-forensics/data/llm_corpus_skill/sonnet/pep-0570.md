# PEP 570: Python Positional-Only Parameters

## Abstract

This PEP proposes a new syntax, `/`, for specifying positional-only parameters in Python function definitions.

Positional-only parameters have no externally usable name. When a function that accepts positional-only parameters is called, positional arguments map to these parameters by order alone.

## Context

A library author designs a function and picks a name for each parameter. In Python today, every parameter that a function defines in ordinary syntax can be passed by keyword. The name is therefore part of the function's public interface, whether or not the author wanted it to be.

The abstract describes the consequence. Without a way to mark parameters as positional-only, authors "must be careful when choosing appropriate parameter names". The care is needed "even for required parameters or when the parameters have no external semantic meaning for callers of the API".

A short illustration of the situation, for the author to confirm or replace:

```python
def distance(a, b):
    ...

distance(a=1, b=2)   # allowed today
```

The author of `distance` may not intend `a` and `b` as names callers should use. A caller can still write them, and after that the author cannot rename the parameters without breaking that caller. ## Specification

A `/` in the parameter list ends the group of positional-only parameters. Every parameter before it is positional-only.

```python
def f(a, b, /, c, d):
    ...
```

In this illustration, `a` and `b` can be passed only by position. `c` and `d` can be passed by position or by keyword. [TODO: confirm the exact rules, including the placement of defaults, the interaction with `*args` and keyword-only parameters, and what the parser does with a misplaced `/`.]

## Rationale

### The force

Library authors need to keep the freedom to rename parameters. A positional-only marker gives them that freedom. The abstract states the problem: care in naming is required even when the name means nothing to the caller.
