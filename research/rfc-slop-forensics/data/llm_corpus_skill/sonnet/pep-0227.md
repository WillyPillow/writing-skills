# PEP 227: Statically Nested Scopes

## Abstract

This PEP adds statically nested scoping, also called lexical scoping, to Python 2.2. It is available as a source level option in Python 2.1. In addition, Python 2.1 will issue warnings about constructs whose meaning changes when the feature is enabled.

The language definition for 2.0 and before has exactly three namespaces for resolving names: local, global and built-in. Nested scopes add a fourth step: an unbound local name can be resolved in the namespaces of the enclosing functions. The most visible consequence is that a lambda, or any other nested function, can refer to a variable in the surrounding function. Today a lambda often needs default arguments to create the binding inside its own namespace.

## Motivation

Consider a function that builds and returns another function.

```python
def make_adder(n):
    return lambda x: x + n
```

Under the rules of 2.0, this code does not do what it appears to do. When the lambda runs, the name `n` is not local to the lambda, so Python looks in the global namespace and then in the built-in one. It does not look in `make_adder`, where `n` lives. The call `make_adder(3)(4)` fails with a `NameError`, unless a global `n` exists, in which case it silently uses that.

The accepted workaround is to pass the value as a default argument.

```python
def make_adder(n):
    return lambda x, n=n: x + n
```

The default argument evaluates `n` when the lambda is created and stores it as a local name of the lambda. The workaround has three problems. The reader has to know the idiom to understand why `n=n` is there. The lambda gains a parameter that callers can override by accident: `make_adder(3)(4, 10)` returns 14. And the same trick must be repeated for every enclosing name that the inner function uses.

The same limitation applies to nested `def` statements, not only to lambdas, which the abstract states ("and other nested functions"). A helper function defined inside another function cannot use the outer function's variables without the same device.

The goal of the PEP is to let a nested function see the variables of its enclosing functions by the rules that a reader expects from the program text.

## Specification

The PEP changes the name resolution rule. In 2.0 and before, a name is looked up in the local namespace, then the global namespace, then the built-in namespace. With nested scopes, the lookup of a name that is not local proceeds through the namespaces of the enclosing functions, from the innermost outward, before the global and built-in ones.

The order is therefore:

1. The local namespace of the function.
2. The namespaces of each enclosing function, innermost first.
3. The global namespace.
4. The built-in namespace.

The rule is static. Which namespace a name belongs to is decided by the program text when the function is compiled, and does not depend on what happens when the program runs. A name is local to a function if the function binds it anywhere, for example by assignment. Otherwise the compiler looks for the nearest enclosing function that binds it. ## Compatibility

The change affects programs whose meaning depends on where a name was found. The following program shows the case.

```python
x = 1

def f():
    x = 2
    def g():
        return x
    return g()
```

Under the rules of 2.0, `f()` returns 1, because `g` does not see the `x` of `f`, and the lookup falls to the global namespace. With nested scopes, `f()` returns 2. The program is valid under both definitions and gives different answers. The abstract says that Python 2.1 will warn about such constructs. The warning is issued when a function refers to a name that is not local, is bound in an enclosing function, and is also bound at the global level. A program written for 2.2 that relies on nested scopes does not run on 2.0, since the same text gives a `NameError`. The programmer who needs to support both must keep the default-argument idiom. This is a limit of the change and the PEP does not remove it.

## Alternatives

The following alternatives are suggestions for the author to evaluate. They are not alternatives recorded as considered.

- Keep the three namespaces and document the default-argument idiom. This is the status quo, with the problems listed in Motivation.
- Add a special syntax for closing over a name, so that each use is marked. This avoids a change in the default lookup. It requires the programmer to know the rule at each use.
- Make only lambdas see enclosing names. The abstract names "other nested functions" as part of the consequence, so this alternative contradicts the proposal.
