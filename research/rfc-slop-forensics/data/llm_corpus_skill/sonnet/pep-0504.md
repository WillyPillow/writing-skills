# PEP 504: Using the System RNG by default

## Abstract

The module-level functions of the `random` module use the Mersenne Twister, a deterministic generator. A developer who does security-sensitive work must know to use `os.urandom`, `random.SystemRandom` or a third-party library such as `cryptography` instead. Developers who do not know that their work is security-sensitive use the default functions and expose their users to risk.

This PEP proposes a way to make the secure choice the default for the module-level API over time. ## The problem

### What happens today

The module-level functions in `random` share one hidden instance of a deterministic generator. Anyone who observes enough of its output can predict later output. That is acceptable for simulations and games, and unacceptable for session tokens, password reset codes and similar values.

Python has secure tools for the second case, namely `os.urandom`, `random.SystemRandom` and third-party libraries. The existing guidance is that the developer picks the secure tool when the work needs it.

### Why the existing guidance fails

The guidance assumes the developer knows the work is security-sensitive. The abstract describes the case where they do not: a developer writes a function that generates a code for a user, calls `random.choice`, and ships it. Nothing in the language tells them the choice matters.

The abstract also explains why experience does not correct this. Long delays often separate the introduction of a flaw from its exploitation, so a developer cannot learn from the consequences of their own code. The abstract calls the problem chronic, not acute: it does not claim a flood of incidents. [TODO: author to supply any concrete incident, vulnerability report or code survey. ## Design

### The central tension

The change has to serve two groups whose needs conflict. Developers who need reproducible sequences, such as test authors and simulation authors, rely on seeding the shared generator and getting the same output each run. Developers who need unpredictability want the opposite. A system generator cannot be seeded to a repeatable state, so a default switch takes reproducibility away from the first group unless they opt in to something else.

This conflict is the hardest problem in the proposal and it needs the most space. The supplied material states the security side of the argument in detail and says nothing about the reproducibility side.
