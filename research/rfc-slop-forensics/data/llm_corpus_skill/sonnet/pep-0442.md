# PEP 442: Safe object finalization

## Abstract

This PEP proposes to deal with the current limitations of object finalization. The goal is to define and run finalizers for any object, regardless of its position in the object graph. The PEP calls for no change in Python code. Objects that have finalizers today benefit automatically.

## Context

Objects in a running program refer to each other. When the last reference to an object goes away, the interpreter reclaims it. Objects that form a cycle never reach a reference count of zero, so a separate collector has to find them.

The abstract states that the current rules for finalization have limitations that depend on where an object sits in the object graph. The goal sentence says the fix is to run finalizers "regardless of position". It follows that today some positions prevent a finalizer from running, or prevent the collector from reclaiming the object.

## Goals and non-goals

Goals:

1. A finalizer can be defined for any object and will run when the object is reclaimed, wherever it sits in the object graph.
2. Existing code with finalizers needs no change. The abstract says "objects with existing finalizers will benefit automatically".

Non-goals:

1. The PEP makes no change to Python syntax or to the language-level API. The abstract says it "doesn't call for any change in Python code". [TODO: confirm whether the C API changes. ## Design

### The central tension

Safety is in the title, so the hard problem is that a finalizer is arbitrary code that runs while the object graph is being torn down. Such code can look at objects that are already half reclaimed, or bring an object back to life by storing a reference to it somewhere reachable. A mechanism that runs finalizers on any object in any position must define what the finalizer may rely on. [TODO: this paragraph is inferred from the title word "safe". The design must therefore answer three questions. In what order do finalizers in one cycle run? What state is each object in when its finalizer runs?
