# PEP 352: Required Superclass for Exceptions

## Abstract

In Python 2.4 and before, any classic class can be raised as an exception. The plan for 2.5 was to allow new-style classes as well, which makes the problem larger: any class or instance could then be raised. This permissiveness prevents the language from making any guarantee about the interface of an exception. This PEP proposes a new superclass from which every raised object must inherit. With that restriction, a standard exception interface can exist and callers can rely on it. The restriction also gives all exceptions a known hierarchy.

A reader may object that requiring a base class for the sake of an interface is unPythonic. The PEP argues that exceptions are a special case. ## Background

Python's `raise` statement accepts an object and a handler in an `except` clause selects handlers by class. In Python 2.4 the object can be an instance of any classic class, with no requirement that the class derive from a particular base.

```python
class Old:
    pass

try:
    raise Old()
except Old:
    pass
```

This code is valid in 2.4 and will remain valid in 2.5 under the plan that allows new-style classes. The plan makes the following code valid too.

```python
class New(object):
    pass

raise New()
```

Under the 2.5 plan, therefore, a program could raise an instance of a class that was never meant to be an exception, such as a file wrapper or a dictionary subclass.

## Motivation

The code that catches an exception often has to do something with it other than match its type. It might log the exception, show it to a user, or re-raise it wrapped in another. To do that, the code needs to know what the object offers. If every raised object is an arbitrary instance, the code can assume nothing: an attribute that exists on one exception may not exist on another, and there is no single way to turn an exception into a message.

The abstract states this directly: without a restriction on what can be raised, no guarantee can be made about the interface of exceptions. The language cannot add a method to all exceptions, because it has no way to say which objects are exceptions. A new feature that needs a hook on every exception, such as a standard way to attach information, has nowhere to put it. A second consequence concerns hierarchy. A hierarchy of exception classes lets a handler catch a family of related errors with one clause. Today the standard exceptions form a hierarchy only by convention, and nothing ties user-defined exceptions into it. Requiring a common superclass gives every exception a position in a tree that tools and programmers can reason about. In particular, a handler can name the superclass to mean "any exception". ## Rationale

The principal rationale is the one given in Motivation: a guaranteed interface and a known hierarchy.

The PEP has to address the objection from the abstract. Python generally prefers duck typing, in which an object is judged by what it can do, not by what it inherits from. A requirement that raised objects derive from a given class goes against that preference. The PEP's answer is that exceptions are different, because "there's a good reason" in their case. A strong version would name what duck typing cannot give here: the interpreter has to inspect the object at the moment of `raise`, before any attribute lookup that the object might customize, and can only do so cheaply by checking a class. That sentence is a suggestion for the author to evaluate, not the author's stated argument.]

Alternatives, labelled as suggestions for the author to evaluate:

- Define the interface as a protocol and check for it at `raise` time. This keeps duck typing. It lets objects pass the check that are not meant to be exceptions, and the hierarchy benefit disappears.
- Only warn. The language could issue a warning when a raised object lacks the base. This is cheaper to adopt. It leaves the guarantee unenforced, so callers still cannot rely on the interface.
- Do nothing. The 2.5 plan to allow new-style classes proceeds, and the interface remains undefined. The Motivation section is the case against this.
