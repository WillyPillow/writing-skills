# PEP 367: New Super

## Abstract

This PEP proposes syntax that builds a `super` object automatically inside a method. The object binds to two things: the class in which the method was defined, and the instance on which the method is running (or the class, for a classmethod).

The proposed spelling replaces this call:

```python
super(Foo, self).foo(1, 2)
```

with this one:

```python
super.foo(1, 2)
```

The current built-in `super` would be renamed `__super__` and the name `super` would stop referring to it in Python 3.0. Assigning to `super` would become a `SyntaxError`, as assignment to `None` is.

## Context

The explicit form `super(Foo, self)` names the class twice: once in the `class` statement and once inside every method that calls `super`. The method also has to name its first argument, whatever the author called it.

Two consequences follow from this repetition.

1. Renaming the class requires editing every `super(Foo, self)` call inside it. A call left unedited either fails with a `NameError` or, if the old name is still bound to another class, silently skips the wrong part of the hierarchy. The PEP's premise is that the interpreter already knows both values at the call site, so the programmer should not have to restate them.

## Specification

### The new form

Inside a method body, the expression `super.foo(1, 2)` means what `super(Foo, self).foo(1, 2)` means today, where `Foo` is the class whose body contains the method and `self` is the instance or class the method acts on.

For a classmethod, the second binding is the class object. The abstract states this rule but does not say how the interpreter finds that object when the method's first parameter has an arbitrary name. ### The old form

The current built-in remains reachable under the name `__builtin__.__super__`. The name `__builtin__.super` is removed in Python 3.0.

The abstract gives these two facts and no more. It leaves open what happens to existing code that calls `super(Foo, self)` in a 2.x release before the removal, and what the removal does to such code in 3.0. ## Open questions

1. How the defining class and first argument are found for each kind of method.
2. How the new form behaves in nested functions and inside methods defined with unusual signatures. For instance, a method declared with `*args` has no named first parameter.
3. What happens in a function that is defined at module level and then assigned as a method.
4. Whether `super` can be used outside a method, and what error results.
5. How the removal of the old built-in interacts with the existing documentation and with tools that read it.

## Review checklist

A reviewer who disagrees with the proposal can point to these decisions:

* repurposing the existing name `super` instead of choosing a new one;
* removing the old built-in in 3.0;
* making assignment a `SyntaxError`.

The first and second are the expensive ones to reverse, and each needs a stated reason in the final PEP.
