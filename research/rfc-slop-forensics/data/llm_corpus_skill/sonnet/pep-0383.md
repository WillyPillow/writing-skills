# PEP 383: Non-decodable Bytes in System Character Interfaces

## Abstract

POSIX defines file names, environment variables and command line arguments as character data. The C APIs, however, accept arbitrary bytes, whether or not those bytes are valid in any particular encoding. This PEP proposes to embed such bytes in character strings in a way that lets the program recreate the original byte string.

## The problem

### An example

Consider a directory that contains a file whose name is the byte sequence `0x66 0xFF 0x6F`. Suppose the system encoding is UTF-8. The byte `0xFF` cannot occur in valid UTF-8, so a strict decoder rejects the name.

A program that lists the directory wants a string for each entry. It has three choices today: fail, drop or replace the bad byte, or return bytes instead of a string. The first makes the program unusable on that directory. The second loses information, so the program cannot open the file afterward, because the replacement string names a different file. ### The same problem in three places

The abstract names three sources: file names, environment variables and command line arguments. In each, the operating system hands the program bytes and the language presents characters. ### Why a lossy fix is not enough

A decoder that substitutes a fixed replacement character maps several different byte sequences to one string. After that, the program cannot recover which bytes it received. For a file name, that means it cannot open, rename or delete the file. For an environment variable, it cannot pass the value to a child process unchanged. The PEP requires the opposite property: the original bytes must be recoverable.

## Goals and non-goals

Goals:

1. Every byte sequence that the operating system returns decodes to a string.
2. Encoding that string with the same mechanism returns exactly the original bytes.
3. Strings that came from valid input are unchanged.

### What the representation has to satisfy

Any choice of representation has to meet these conditions.

1. It must be reversible, so the mapping from bytes to characters has an exact inverse.
2. It must not collide with characters that appear in valid input. If a valid name could contain the same character, the inverse could not tell the two cases apart.
3. It must be usable by the string type without special handling at every call site.

The second condition is the hard one. A representation that reuses code points a valid string can contain makes decoding ambiguous. ## Rationale

**The force.** POSIX describes the three data kinds as character data, yet the C API accepts arbitrary bytes. A language that exposes only strings cannot name every file on a POSIX system unless it can carry the bytes through. Three alternatives are suggestions for the author to evaluate, not recorded options:

* Return bytes whenever decoding fails. This keeps information but makes the return type depend on the data.
* Raise an error on undecodable input, as a strict decoder does. This is safe but makes some files unreachable.
* Use a separate path type that holds bytes and offers a display form.

**Cost accepted.** Strings from the system may contain characters that no encoding can emit. Code that processes names as text has to deal with them. A program that writes such a string to a destination with a strict encoding will fail there instead of at the point of origin. [TODO: author to list further costs and to say who bears them.]

**Reversibility.** The chosen mapping becomes visible to every program that touches a file name. Changing it later would change the string value of names. This is the most expensive decision in the PEP, and the representation needs the most justification of anything in the document.
