# PEP 439: Inclusion of implicit pip bootstrap in Python installation

## Abstract

This PEP proposes the inclusion of a pip bootstrap executable in the Python installation, to simplify the use of third-party modules by Python users.

This PEP does not propose to include the pip implementation in the Python standard library. It also does not propose any package management or installation mechanism beyond those provided by PEP 427 ("The Wheel Binary Package Format 1.0") and the distlib PEP. ## Design

### The bootstrap executable

The installation contains an executable. When a user runs it for the first time, it obtains `pip` and installs it, and later runs hand control to the installed `pip`. ### Why a bootstrap and not a bundled `pip`

The force is that the project wants users to have an installer without making the installer part of the standard library. The standard library moves with each Python release, and `pip` moves on its own schedule. [TODO: the supplied material does not give this reason. The author should confirm it or state the real one.]

Options:

- *Do nothing.* The user installs `pip` by hand. This keeps the installation small and leaves the first-install problem unsolved.
- *Bundle `pip` in the standard library.* This removes the first-install problem and ties the installer to the release cycle. The abstract rules it out.
- *Ship a bootstrap that obtains `pip`, as proposed.* This solves the first-install problem and keeps `pip` independent. It requires network access at the first run. [TODO: state whether a network is assumed, and what happens without one.]
